Le chatter en Odoo 20 : suivre un emprunt

Un emprunt change de durée, passe à « Rendu », reçoit une relance : aujourd'hui, rien n'en garde trace. Le chatter donne à chaque emprunt son historique, ses notes et ses abonnés. Trois lignes de code suffisent à l'afficher ; le reste de l'article explique pourquoi il faut en écrire une quatrième.

~17 minutes de lecture · niveau intermédiaire · parcours Framework & ORM

Ce que tu vas apprendre

Brancher

mail.thread, tracking=True et la balise <chatter/>.

Écrire

Des notes depuis le code avec message_post — et un Markup.

Accorder

Le droit de poster avec les droits d'accès de l'article précédent.

Prérequis

  • Le module biblio des articles précédents, avec ses droits d'accès : groupes Accueil et Bibliothécaire, et la restriction « un emprunt rendu est figé ».
  • L'action planifiée de relance des retards.
  • Le serveur Odoo 20 joignable sur http://localhost:8069, base biblio.

1. Première dépendance : mail

Jusqu'ici, le module ne dépendait que de base. Le chatter appartient au module mail (« Discussion ») ; il faut le déclarer :

    'version': '20.0.1.8.0',
    'depends': ['base', 'mail'],

Sur une base où biblio est déjà installé, une simple mise à jour suffit : Odoo installe la nouvelle dépendance au passage. Mais pas seulement elle. Le journal de -u biblio :

ALLOW access to module.button_install on ['Discuss'] Loading module mail (17/29) Loading module auth_signup (18/29) Loading module auth_totp_mail (19/29) ... Loading module sms (28/29) Loading module biblio (29/29)

La base passe de 17 à 29 modules : mail, plus onze modules en installation automatique qui se déclenchent dès que leurs dépendances sont présentes — inscription, robot de discussion, SMS, connecteurs de messagerie… Aucune alerte, rien à confirmer. Sur une base de production, c'est à savoir avant la mise à jour, pas après.

2. Brancher le chatter

Dans models/library_loan.py, le modèle hérite de deux mixins :

from markupsafe import Markup

class LibraryLoan(models.Model):
    _name = 'library.loan'
    _description = "Emprunt"
    _inherit = ['mail.thread', 'mail.activity.mixin']
    _mail_post_access = 'read'
  • mail.thread apporte les messages et les abonnés ;
  • mail.activity.mixin apporte les activités planifiées (le bouton « Activité ») ;
  • _mail_post_access est la quatrième ligne annoncée : l'étape 5 lui est consacrée.

Les champs à historiser reçoivent tracking=True :

    member_id = fields.Many2one('library.member', ..., tracking=True)
    copy_id = fields.Many2one('library.copy', ..., tracking=True)
    duration = fields.Integer(string="Durée (jours)", default=14, required=True, tracking=True)
    date_due = fields.Date(..., compute='_compute_date_due', store=True, tracking=True)
    state = fields.Selection([...], ..., tracking=True)

date_due est un champ calculé stocké : il se suit comme les autres, la capture ci-dessous le montre.

Enfin la vue : une balise, après la <sheet> du formulaire.

L'accueil prolonge un emprunt en cours de 14 à 21 jours puis le marque rendu. Dans le chatter :

Les trois changements arrivent dans un seul message, avec leur auteur, alors qu'il y a eu deux écritures (la durée, puis le retour). Le suivi n'écrit rien au moment du write : il note les valeurs initiales et produit le message au moment de la validation de la transaction. L'échéance, recalculée à partir de la durée, figure elle aussi.

v19 → v20 : les valeurs suivies ne sont plus des enregistrements

En 19, chaque ligne de suivi était un enregistrement mail.tracking.value, relié au message par tracking_value_ids. En 20, mail écrit le suivi dans le corps HTML du message, d'un type nouveau, tracking :

message_type : tracking body : <div>4 oct. 2026 → <b>11 oct. 2026</b> <i>(À rendre le)</i><br>14 → <b>21</b> …</div> 'tracking_value_ids' in mail.message : False 'mail.tracking.value' dans le registre : False

Le modèle existe encore, mais dans un module à part, mail_tracking (« Discuss Tracking »), qui ne s'installe pas tout seul. Un rapport, un export ou un test v19 qui lit message.tracking_value_ids lève AttributeError tant que ce module n'est pas installé.

3. Écrire dans le chatter depuis le code

Le suivi dit ce qui a changé. Une note dit pourquoi, ou ce que le code a fait. Dans action_return, après la remise en rayon :

            loan.copy_id.state = 'available'
            loan.message_post(
                body=Markup("Exemplaire <b>%s</b> rendu et remis en rayon.") % loan.copy_id.name,
                message_type='comment',
                subtype_xmlid='mail.mt_note',
            )

message_type='comment' avec le sous-type mail.mt_note fait une note : interne, visible dans le chatter, pas envoyée aux abonnés. C'est d'ailleurs le sous-type que message_post prend quand on n'en donne aucun (mail_thread.py, repli sur mail.mt_note) ; l'écrire rend l'intention lisible. Un message destiné aux abonnés demanderait subtype_xmlid='mail.mt_comment'.

Même principe dans l'action planifiée de relance, qui laisse désormais une trace sur chaque emprunt relancé :

        for emprunt in a_relancer:
            emprunt.reminder_count += 1
            emprunt.reminder_date = aujourdhui
            emprunt.message_post(
                body=Markup("Relance n°%s : <b>%s jour(s)</b> de retard.")
                % (emprunt.reminder_count, emprunt.days_late),
                message_type='comment',
                subtype_xmlid='mail.mt_note',
            )

Une chaîne est échappée : il faut un Markup

Le corps d'un message est du HTML, mais message_post considère une chaîne Python ordinaire comme du texte, et l'échappe. Même appel, sans Markup :

loan.message_post(body="Exemplaire <b>BIB-0008</b> contrôlé : bon état.", ...)
body stocké : <p>Exemplaire &lt;b&gt;BIB-0008&lt;/b&gt; contrôlé : bon état.</p>

Et Markup ne rend pas dangereux ce qu'on y injecte : l'opérateur % échappe les valeurs, seul le gabarit reste du HTML. Un nom d'exemplaire qui contiendrait <script>x</script> ressort <b>&lt;script&gt;x&lt;/script&gt;</b>. D'où la règle : le HTML dans le Markup(...), les données après le % — jamais une f-string passée à Markup.

4. Abonnés, et le suivi qu'on n'a pas

Un emprunt créé par l'accueil, puis rendu dans la foulée, dans la même transaction (c'est le cas d'un script ou d'une sonde) :

Deux choses à lire sur cette capture.

  • Un abonné : le créateur d'un document est abonné d'office. Les emprunts antérieurs à l'installation du chatter, eux, n'en ont aucun — l'icône affiche 0 sur la capture précédente. Pour abonner l'adhérent, il faudrait message_subscribe(partner_ids=...) ; ce n'est pas fait ici : un abonné est destinataire des messages non internes du document, et ce choix mérite d'être fait délibérément.
  • Pas de suivi : la création d'un document appelle _track_discard() sur lui (mail_thread.py:397). Tout ce qui change avant la validation de la transaction n'est pas historisé. En utilisation normale, créer puis rendre sont deux requêtes et le suivi fonctionne ; dans un script d'import ou un test qui fait tout d'un bloc, il est muet. Même comportement en 19.

5. Qui peut poster ? _mail_post_access

Poster un message sur un document demande un droit sur ce document. Lequel ? Par défaut, mail.thread déclare :

    _mail_post_access = 'write'  # access required on the document to post on it

Or l'article précédent a posé une restriction : un emprunt rendu n'est plus modifiable, par personne. Avec la valeur par défaut, l'essai est sans appel :

note sur un emprunt rendu, accueil → AccessError note sur un emprunt rendu, admin → AccessError L'opération demandée ne peut pas être effectuée en raison de la politique de sécurité. (Type de document : Message, Opération : create)

Plus personne ne peut commenter un prêt clos — pas même pour noter « adhérent prévenu par téléphone ». Et c'est pire : action_return poste sa note après être passé à « Rendu ». L'emprunt est déjà figé quand la note arrive, et le bouton « Marquer comme rendu » échoue pour l'accueil :

_mail_post_access = 'write' : accueil clique « Marquer comme rendu » → AccessError _mail_post_access = 'read' : accueil clique « Marquer comme rendu » → OK

D'où la quatrième ligne. Avec _mail_post_access = 'read', quiconque peut lire l'emprunt peut y poster ; les deux essais passent, pour l'accueil comme pour l'administrateur. C'est le réglage que le cœur applique lui-même aux partenaires et aux utilisateurs. Le figement porte sur les données de l'emprunt ; la conversation autour, elle, reste ouverte.

Chatter et sécurité se testent ensemble

Ni la restriction ni le chatter n'ont d'erreur isolément ; c'est leur combinaison qui casse un bouton. Et l'administrateur n'est pas un bon testeur : il passe partout où un profil métier bute. Chaque bouton qui écrit dans le chatter se vérifie avec un utilisateur de chaque groupe.

Récapitulatif

  • Ajouter mail aux dépendances d'un module installé l'installe à la mise à jour — avec ses modules en installation automatique.
  • mail.thread, tracking=True et <chatter/> suffisent à l'historique.
  • Le suivi est produit à la validation de la transaction, en un message par document ; il est ignoré pour un document créé dans la même transaction.
  • En 20, les valeurs suivies sont écrites dans le corps du message ; tracking_value_ids demande le module mail_tracking.
  • message_post échappe une chaîne : le HTML passe par Markup, les valeurs par %.
  • _mail_post_access vaut 'write' par défaut : avec une restriction en écriture, il faut le passer à 'read'.

Le chatter garde la trace des relances ; il ne les envoie pas. La suite de la série fera partir un vrai courriel vers l'adhérent en retard.
