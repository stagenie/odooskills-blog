Réécrire un script XML-RPC en JSON-2 pour Odoo 20, ligne à ligne

Un script Python d'intégration classique (authenticate, execute_kw, lecture, création, modification, confirmation d'une commande) et sa traduction en JSON-2, appel par appel, exécutées toutes les deux sur la même base Odoo 20. Avec les pièges que la traduction fait apparaître, et le cas des clés API créées en 19.

~11 minutes de lecture · niveau intermédiaire · parcours Intégrations

Ce que tu vas apprendre

Traduire

Passer chaque execute_kw en appel JSON-2 : arguments positionnels → nommés, ids, context, valeurs de retour.

Éviter les pièges

create qui renvoie une liste, read sans ids qui renvoie [], None que XML-RPC ne sait pas transporter, la langue.

Reprendre les clés 19

Pourquoi une clé API sans portée est refusée par Odoo 20, même par l'ancien script, et comment les repérer.

Prérequis

  • Une instance Odoo 20 Community avec Ventes, sa base de démonstration, et une clé API à portée rpc. La création de la clé, l'avertissement de dépréciation et le détail des codes d'erreur sont dans XML-RPC est déprécié : passer à l'API JSON-2 d'Odoo 20 ; cet article part de là et se concentre sur la réécriture.
  • Python 3, bibliothèque standard seulement (xmlrpc.client d'un côté, urllib et json de l'autre).

1. Le script de départ, en XML-RPC

Un script d'intégration comme il en existe des milliers : il s'authentifie, lit trois sociétés, crée un client et le modifie, crée un devis d'une ligne et le confirme, puis tente une suppression interdite pour montrer comment il récupère une erreur. Les paramètres de connexion viennent de variables d'environnement : le mot de passe n'est pas dans le code.

import os
import xmlrpc.client

URL = os.environ["ODOO_URL"]                      # http://localhost:8069
DB = os.environ["ODOO_DB"]                        # ma_base
LOGIN = os.environ["ODOO_LOGIN"]                  # admin
PASSWORD = os.environ["ODOO_PASSWORD"]            # mot de passe ou clé API

common = xmlrpc.client.ServerProxy(f"{URL}/xmlrpc/2/common")
uid = common.authenticate(DB, LOGIN, PASSWORD, {})
models = xmlrpc.client.ServerProxy(f"{URL}/xmlrpc/2/object")

def call(model, method, args, kwargs=None):
    return models.execute_kw(DB, uid, PASSWORD, model, method, args, kwargs or {})

# 1. Lire : trois sociétés
for p in call("res.partner", "search_read",
              [[("is_company", "=", True)]], {"fields": ["name", "city"], "limit": 3}):
    print(p["id"], p["name"], p["city"])

# 2. Créer un client, puis le modifier
partner_id = call("res.partner", "create", [{"name": "Client importé", "city": "Lyon"}])
call("res.partner", "write", [[partner_id], {"phone": "+33 4 00 00 00 00"}])

# 3. Un devis d'une ligne, confirmé
[product_id] = call("product.product", "search", [[("default_code", "=", "E-COM08")]])
order_id = call("sale.order", "create", [{
    "partner_id": partner_id,
    "order_line": [(0, 0, {"product_id": product_id, "product_uom_qty": 4})],
}])
call("sale.order", "action_confirm", [[order_id]])
print(call("sale.order", "read", [[order_id]],
           {"fields": ["name", "state", "amount_total"], "context": {"lang": "fr_FR"}}))

# 4. Une erreur métier : supprimer la commande confirmée
try:
    call("sale.order", "unlink", [[order_id]], {"context": {"lang": "fr_FR"}})
except xmlrpc.client.Fault as exc:
    print("Fault", exc.faultCode, exc.faultString.splitlines()[0])

Sur Odoo 20, il tourne sans changement (sortie en partie 3). Le serveur, lui, écrit un WARNING de dépréciation par requête : neuf pour ce script, une par authenticate ou execute_kw. Autre détail du journal, qui compte pour la suite : toutes les requêtes XML-RPC sont notées 200, y compris la suppression refusée. L'erreur voyage dans le corps de la réponse, pas dans le code HTTP.

… "POST /xmlrpc/2/object#sale.order.unlink HTTP/1.1" 200 372 19 0.005 0.012 rw … "POST /json/2/sale.order/unlink HTTP/1.1" 422 2592 18 0.005 0.008 rw

La seconde ligne est la même suppression faite par la version JSON-2 : là, l'échec se voit dans le journal d'accès, et dans n'importe quel outil de supervision HTTP.

2. La même chose en JSON-2

La structure ne bouge pas : une fonction call() et les quatre blocs. Ce qui change : l'authentification disparaît au profit d'une clé envoyée à chaque requête, et call() prend des arguments nommés au lieu de listes.

import json
import os
import urllib.error
import urllib.request

URL = os.environ["ODOO_URL"]                      # http://localhost:8069
DB = os.environ["ODOO_DB"]                        # ma_base
KEY = os.environ["ODOO_KEY"]                      # clé API à portée rpc

class OdooError(Exception):
    def __init__(self, status, body):
        super().__init__(f"{status} {body['name']}: {body['message']}")
        self.status, self.body = status, body

def call(model, method, **params):
    request = urllib.request.Request(
        f"{URL}/json/2/{model}/{method}", method="POST",
        data=json.dumps(params).encode(),
        headers={"Authorization": f"bearer {KEY}", "X-Odoo-Database": DB,
                 "Content-Type": "application/json"},
    )
    try:
        with urllib.request.urlopen(request, timeout=30) as response:
            return json.load(response)
    except urllib.error.HTTPError as exc:
        raise OdooError(exc.code, json.load(exc)) from None

# 1. Lire : trois sociétés
for p in call("res.partner", "search_read",
              domain=[("is_company", "=", True)], fields=["name", "city"], limit=3):
    print(p["id"], p["name"], p["city"])

# 2. Créer un client, puis le modifier
[partner_id] = call("res.partner", "create", vals_list=[{"name": "Client importé", "city": "Lyon"}])
call("res.partner", "write", ids=[partner_id], vals={"phone": "+33 4 00 00 00 00"})

# 3. Un devis d'une ligne, confirmé
[product_id] = call("product.product", "search", domain=[("default_code", "=", "E-COM08")])
[order_id] = call("sale.order", "create", vals_list=[{
    "partner_id": partner_id,
    "order_line": [(0, 0, {"product_id": product_id, "product_uom_qty": 4})],
}])
call("sale.order", "action_confirm", ids=[order_id])
print(call("sale.order", "read", ids=[order_id],
           fields=["name", "state", "amount_total"], context={"lang": "fr_FR"}))

# 4. Une erreur métier : supprimer la commande confirmée
try:
    call("sale.order", "unlink", ids=[order_id], context={"lang": "fr_FR"})
except OdooError as exc:
    print(exc.status, exc.body["name"], exc.body["message"])

La correspondance tient parce qu'Odoo appelle, dans les deux cas, la même méthode Python avec les mêmes valeurs. JSON-2 vérifie simplement les noms avant l'appel : il lie le corps de la requête à la signature de la méthode et répond 422 si ça ne colle pas (addons/rpc/controllers/json2.py).

4. Les pièges de la traduction

read sans ids : une liste vide, sans erreur

En XML-RPC, un read sans ids échouait bruyamment (Fault 1 … IndexError: list index out of range). En JSON-2, ids est facultatif (il vaut une liste vide par défaut) : l'appel réussit et ne lit rien.

call("res.partner", "read", fields=["name"])
[]

Même chose pour write ou un bouton : sans ids, write et action_confirm répondent true en 200, et rien n'est modifié. Quand un appel « marche » mais n'a aucun effet, vérifier ids en premier.

Les arguments positionnels ne passent plus

La tentation est de garder les listes d'execute_kw dans une clé args. JSON-2 ne connaît pas cette clé : il la prend pour un argument nommé args.

search → 422 werkzeug.exceptions.UnprocessableEntity : missing a required argument: 'domain' search_read → 500 builtins.TypeError : BaseModel._read_format() got an unexpected keyword argument 'args'

search a une signature fermée, l'erreur est claire. search_read accepte des arguments libres qu'il transmet plus loin : l'erreur arrive tard, en 500. Pour trouver le bon nom d'un argument, lire la signature de la méthode dans le code d'Odoo : search_read(self, domain, fields, offset, limit, order, **read_kwargs).

create renvoie une liste

En XML-RPC, create appelé avec un seul dictionnaire renvoyait un entier. En JSON-2, il renvoie la liste des ids, même pour un seul enregistrement, et même si tu passes un dictionnaire seul au lieu d'une liste (vals_list={"name": …} → [49]). Un partner_id = call(…, "create", …) recopié tel quel donne une liste, que le write suivant enveloppe dans une autre liste. Déballer le résultat : [partner_id] = ….

Une méthode qui renvoie None

XML-RPC ne sait pas transporter None : le serveur Odoo encode ses réponses avec allow_none=False (addons/rpc/controllers/xmlrpc.py). Appeler par exemple action_archive sur un contact donne :

Fault 1 … TypeError: cannot marshal None unless allow_none is enabled

Le piège est que l'archivage, lui, est bien fait : relu ensuite, le contact a active à False. Le client reçoit une erreur pour une opération réussie. En JSON-2, la même méthode renvoie null, en 200. Si ton ancien script entourait certains appels d'un try/except Fault: pass pour cette raison, la réécriture permet de les retirer.

La langue et les champs : rien de nouveau, mais à corriger au passage

  • Sans context, les deux protocoles répondent en anglais. L'article de la commande (id 21) se lit « Storage Box » en XML-RPC comme en JSON-2, alors que l'utilisateur est en français : Odoo n'applique que le contexte envoyé par le client. La réécriture est le bon moment pour ajouter context={"lang": "fr_FR"} là où un libellé ou un message d'erreur est affiché.
  • fields n'est pas obligatoire, mais sans lui search_read renvoie tous les champs : 174 clés pour un seul contact, dans les deux protocoles. Toujours lister les champs utiles.

Chaque requête est sa propre transaction

Comme avec execute_kw, chaque appel JSON-2 est validé ou annulé seul. Dans le script, le client et la commande restent créés quand la suppression échoue. Une suite d'appels qui doit réussir ou échouer en bloc relève d'une méthode côté serveur (un module), pas d'une suite de requêtes.

5. Les clés API créées en 19

Beaucoup de scripts XML-RPC n'utilisent déjà plus de mot de passe : Odoo 19 acceptait déjà une clé API à la place de PASSWORD, dans authenticate comme dans execute_kw. C'est toujours vrai en 20 : avec une clé à portée rpc, le script de la partie 1 fonctionne sans modification (authenticate renvoie 2). Une clé API d'Odoo 20 peut donc servir aux deux scripts pendant la transition.

Le cas délicat est celui des clés créées en 19. L'assistant de la 19 les enregistrait sans portée (colonne scope vide). Pour reproduire une telle clé sur une base 20, une clé a été créée puis sa portée effacée en base (UPDATE res_users_apikeys SET scope = NULL), comme elle le serait après une migration qui la recopie telle quelle. Résultat :

Conséquence pratique : après le passage d'une base de 19 à 20, un script XML-RPC qui s'authentifie avec une clé de la 19 peut tomber avant même d'être réécrit. Il reçoit uid = False, puis Fault 3 Access Denied au premier execute_kw ; rien dans le message ne parle de portée.

Venant de la 19 : la portée vide n'ouvre plus rien

En 19, une clé sans portée donnait accès à tous les appels RPC : la vérification acceptait scope IS NULL OR scope = 'rpc', et l'assistant créait justement des clés sans portée (odoo/addons/base/models/res_users.py de la branche 19.0). En 20, la portée est obligatoire et la vérification stricte (scope = 'rpc'). Le code source d'Odoo 20 ne contient aucune conversion des anciennes clés ; ce que fait le service de migration d'Odoo sur ce point n'a pas été vérifié ici. Le plus sûr est de le constater sur ta base migrée.

Repérer et traiter les clés concernées

Sur la base migrée, une requête suffit :

SELECT k.id, k.name, u.login, k.expiration_date
  FROM res_users_apikeys k JOIN res_users u ON u.id = k.user_id
 WHERE k.scope IS NULL;
  • La voie propre : recréer une clé par intégration avec l'assistant d'Odoo 20 (durée limitée, portée rpc), la déployer, puis supprimer l'ancienne depuis Mes préférences › Sécurité. C'est aussi l'occasion de remplacer les clés sans date d'expiration, fréquentes en 19.
  • Le dépannage, si une intégration doit repartir tout de suite : UPDATE res_users_apikeys SET scope = 'rpc' WHERE scope IS NULL;. Essayé sur la base de test, la clé est de nouveau acceptée (200). C'est une écriture SQL directe que l'interface ne propose pas, et elle conserve les durées de la 19 : à réserver à l'urgence, avant une vraie rotation.

6. La migration d'un script, dans l'ordre

  1. Créer une clé API d'Odoo 20 (portée rpc) pour l'utilisateur de l'intégration et la mettre à la place du mot de passe ou de l'ancienne clé : le script XML-RPC continue de tourner, et les clés de la 19 sont hors du chemin.
  2. Remplacer la fonction call() et la connexion (partie 2), sans toucher au reste.
  3. Reprendre chaque appel avec le tableau de la partie 3 : arguments nommés, ids, context, déballage des create.
  4. Remplacer les except Fault par un traitement par code HTTP ; retirer ceux qui masquaient les retours None.
  5. Comparer les sorties des deux versions sur une base de test, comme dans la partie 3, puis vérifier qu'aucun WARNING … rpc.controllers.xmlrpc n'apparaît plus au journal.

Récapitulatif

  • Un script XML-RPC se traduit en JSON-2 appel par appel : même méthode, mêmes valeurs, mais des arguments nommés, et ids et context à part.
  • Plus d'authenticate : une clé API à portée rpc dans l'en-tête de chaque requête.
  • create renvoie une liste ; read ou write sans ids ne font rien, sans erreur ; None passe enfin.
  • Les erreurs deviennent des codes HTTP : 422 pour une règle métier, 401 pour la clé, 403 pour les droits.
  • Les clés API sans portée créées en 19 sont refusées par Odoo 20, en JSON-2 comme en XML-RPC : les repérer avec scope IS NULL et les recréer.
