Plusieurs clients sur un serveur Odoo 20 : dbfilter et isolation

Un seul processus Odoo peut servir plusieurs bases, une par client, chacune derrière son nom de domaine. Reste à savoir ce qui sépare vraiment ces clients et ce qu'ils partagent sans le savoir. Cet article le mesure sur trois bases servies par un seul odoo-bin : un filtre trop large puis corrigé, les sessions, le filestore, le rôle PostgreSQL, les tâches planifiées, Nginx par domaine, et le moment où il faut un processus par client.

~16 minutes de lecture · niveau intermédiaire · parcours Infrastructure

Ce que tu vas apprendre

Aiguiller

Un dbfilter qui donne une base par nom de domaine, et rien d'autre, avec Nginx devant.

Cloisonner

Ce qui est séparé par base (données, fichiers, sessions) et ce que le processus partage (tâches planifiées, rôle, code).

Décider

Les signes qui imposent de passer à un processus, voire à un serveur, par client.

Prérequis

  • Un serveur Odoo 20 installé comme service (Installer Odoo 20 sur un serveur Ubuntu) et publié en HTTPS derrière Nginx (Mettre Odoo 20 en HTTPS avec Nginx).
  • Savoir créer, dupliquer et lister des bases, et ce que fait le gestionnaire de bases. Ces gestes, comme le réglage des workers et des limites, ne sont pas repris ici : on part d'un serveur qui tourne déjà.
  • Pour reproduire : trois bases client-a, client-b et client-c, copies d'une même base de démonstration dont la société a été renommée « Client A », « Client B », « Client C », servies par un seul odoo-bin à l'écoute sur localhost:8069. Les noms client-a.example et client-b.example sont simulés par l'en-tête Host de curl.

1. Un processus, plusieurs bases : ce qui est séparé, ce qui est partagé

Une base Odoo, c'est une base PostgreSQL et un dossier de pièces jointes. Le processus odoo-bin, lui, n'est attaché à aucune base : à chaque requête il en choisit une, charge son registre (les modèles de ses modules installés) s'il ne l'a pas déjà, et répond. Plusieurs clients sur un serveur, c'est donc d'abord une question d'aiguillage (quelle base pour quelle requête), puis de cloisonnement (ce qui reste commun une fois la base choisie).

Séparé par basePartagé par le processus
Tables, utilisateurs, mots de passe, clés d'APIPort, workers, fils des tâches planifiées
Pièces jointes : <data_dir>/filestore/<base>/Rôle PostgreSQL (db_user), utilisateur système, data_dir
Registre chargé en mémoireDossier des sessions : <data_dir>/sessions/
Modules installés, paramètres systèmeCode Python sur le disque, modules chargés au démarrage (server_wide_modules)

Chaque base chargée ajoute son registre à la mémoire du processus : mesuré au repos (mémoire résidente lue après la première page de chaque base), de 4 à 8 Mo par base de 69 modules, sur un processus d'environ 150 Mo. Sous charge, ce sont les requêtes qui consomment ; au repos, une base de plus coûte peu, et les limites viennent d'abord de ce qui est partagé dans la colonne de droite.

2. Le nom de domaine choisit la base : dbfilter = ^%d$

Le dbfilter est une expression régulière appliquée aux noms des bases, après deux substitutions faites pour chaque requête à partir de l'en-tête Host : %h devient le nom complet, %d son premier élément. Odoo retire d'abord le port et un éventuel www.. Avec dbfilter = ^%d$, le nom client-a.example ne laisse passer que la base client-a. La route /web/database/list montre la liste vue depuis chaque nom :

for h in client-a.example client-b.example www.client-a.example:443 inconnu.example; do
  curl -s -H "Host: $h" -H 'Content-Type: application/json' \
       -d '{"jsonrpc":"2.0","method":"call","params":{}}' http://localhost:8069/web/database/list; echo
done
{"jsonrpc": "2.0", "id": null, "result": ["client-a"]} {"jsonrpc": "2.0", "id": null, "result": ["client-b"]} {"jsonrpc": "2.0", "id": null, "result": ["client-a"]} {"jsonrpc": "2.0", "id": null, "result": []}

Une seule base pour un nom : Odoo la prend sans rien demander, et /web/login affiche directement la connexion du bon client. Un nom inconnu n'a aucune base : /web/login renvoie vers le sélecteur de bases (303), qui n'en liste aucune et propose « Create Database ». C'est une raison de plus pour que Nginx ne transmette que les noms connus (section 8).

%d ne prend que le premier élément du nom. Le schéma « un sous-domaine par client » sous un domaine commun lui va bien ; le schéma inverse, non :

erp.client-a.example -> [] (%d vaut « erp » pour tous les clients) client-a.erp.example -> ["client-a"]

Si les clients arrivent par leur propre domaine avec un préfixe commun (erp.client-a.example), utilisez %h et nommez la base comme le nom complet : ^%h$ et une base erp.client-a.example (le point est admis dans un nom de base). Le www. est retiré aussi pour %h : ne commencez pas un nom de base par www..

Piège : un filtre non ancré

Le filtre est appliqué avec re.match : il est ancré au début, pas à la fin. Avec ^%d, sans le $, une copie de test client-a-test devient visible sur le domaine de production de ce client :

dbfilter = ^%d client-a.example -> ["client-a", "client-a-test"] dbfilter = ^%d$ client-a.example -> ["client-a"]

Le $ final n'est pas un détail de style : sans lui, deux bases répondent au même nom, et les conséquences sont celles de la section suivante.

3. Un filtre trop large : la démonstration, puis la correction

Un réglage qu'on rencontre : dbfilter = ^client-, « toutes les bases de clients ». Le serveur fonctionne, chaque client se connecte. Mais depuis client-a.example, le sélecteur de bases affiche maintenant les trois clients :

Ce n'est pas qu'une fuite de noms. Depuis le domaine du client A, sans rien forcer d'autre que les paramètres prévus par Odoo, on travaille dans la base du client B :

# 1. Choisir la base dans l'URL : la session passe sur client-b (302 vers la même page)
curl -s -o /dev/null -w '%{http_code}\n' -H 'Host: client-a.example' 'http://localhost:8069/web/login?db=client-b'

# 2. Se connecter à client-b en le nommant
curl -s -H 'Host: client-a.example' -H 'Content-Type: application/json' \
     -d '{"jsonrpc":"2.0","method":"call","params":{"db":"client-b","login":"admin","password":"admin"}}' \
     http://localhost:8069/web/session/authenticate

# 3. API JSON-2 : la base est choisie par un en-tête
curl -s -H 'Host: client-a.example' -H 'X-Odoo-Database: client-b' -H "Authorization: bearer $CLE_CLIENT_B" \
     -H 'Content-Type: application/json' -d '{"domain":[["id","=",1]],"fields":["name"]}' \
     http://localhost:8069/json/2/res.company/search_read
302 … "db": "client-b", "uid": 2 … [{"id": 1, "name": "Client B"}]

Le cookie de session suit la même logique. Une session ouverte sur la base A, renvoyée telle quelle sur client-b.example, reste valide : la session porte le nom de sa base, et le filtre l'accepte sur ce domaine. La requête arrive sur le domaine de B et elle est servie dans la base de A : le domaine ne dit plus rien du client servi.

Couper la liste des bases (list_db = False) ne change rien à ces trois appels : la liste répond AccessDenied (« Database management functions blocked, admin disabled database listing. »), le sélecteur affiche « The database manager has been disabled by the administrator », mais ?db=client-b, /web/session/authenticate et l'en-tête X-Odoo-Database passent comme avant (302, connexion, Client B). list_db cache la liste ; c'est le filtre qui décide de ce qui est joignable.

La correction : dbfilter = ^%d$. Mêmes appels depuis client-a.example :

?db=client-b -> 200 : paramètre ignoré, page de connexion du client A authenticate client-b -> "Database not found." X-Odoo-Database -> 404 « No database is selected and the requested URL is not server-wide. » cookie de A sur client-b.example -> SessionExpiredException

Le dernier cas laisse une ligne au journal, utile pour repérer un filtre resserré après coup :

WARNING client-a odoo.http: Logged into database 'client-a', but dbfilter rejects it; logging session out.

La session refusée n'est pas enregistrée : la même session, renvoyée ensuite sur client-a.example, est toujours connectée. Un navigateur, de toute façon, n'envoie pas ce cookie à l'autre domaine : Odoo le pose sans attribut Domain (Set-Cookie: session_id=…; HttpOnly; Path=/), il reste lié au nom exact qui l'a reçu.

4. Le filtre aiguille, il ne verrouille pas

L'en-tête Host est écrit par le client HTTP, pas par le serveur. Avec proxy_mode, c'est X-Forwarded-Host qui le remplace, et lui aussi peut être écrit par n'importe qui. Sur le port d'Odoo atteint directement :

curl -s -H 'Host: client-a.example' -H 'X-Forwarded-Host: client-b.example' \
     -H "Authorization: bearer $CLE_CLIENT_B" -H 'Content-Type: application/json' \
     -d '{"domain":[["id","=",1]],"fields":["name"]}' http://localhost:8069/json/2/res.company/search_read
[{"id": 1, "name": "Client B"}]

Ce n'est pas une faille en soi : choisir la base B par un en-tête, c'est l'équivalent de taper client-b.example, et il faut toujours les identifiants de B. Mais cela fixe le rôle de chacun : le filtre range les requêtes, les mots de passe et les clés d'API protègent chaque base. Trois conséquences pratiques :

  • Odoo écoute sur 127.0.0.1 (la valeur par défaut de http_interface en Odoo 20) et seul Nginx est joignable de l'extérieur : c'est lui qui écrit X-Forwarded-Host (section 8).
  • Un compte administrateur par client, avec un mot de passe propre à chaque base : une base dupliquée garde ceux de sa source.
  • Le gestionnaire de bases ne consulte pas le filtre pour agir : avec le mot de passe maître, il supprime aussi une base que le filtre exclut. Sur un serveur partagé, list_db = False et un mot de passe maître fort, ou le gestionnaire fermé chez Nginx.

5. Sessions et filestore : séparés par base, sur un même disque

Les sessions sont des fichiers, tous dans <data_dir>/sessions/, quelle que soit la base. Chaque fichier contient le nom de sa base et l'utilisateur connecté ; c'est ce champ que le filtre contrôle à chaque requête (section 3). Après quelques connexions sur les deux clients :

db= client-b uid= None db= client-a uid= 2 db= client-b uid= 2

Les pièces jointes, elles, sont rangées par base : <data_dir>/filestore/<base>/. Le même fichier déposé chez les deux clients est stocké deux fois, une fois par base, même s'il porte la même empreinte :

a = env['ir.attachment'].create({'name': 'contrat.txt', 'raw': b'Contrat type, identique dans les deux bases\n'})
print(env.cr.dbname, a.id, a.store_fname)
client-a 500 26/26adbc1c899e95b8bab24e38e5c018cad7b54ac4 -> filestore/client-a/26/26adbc1c… client-b 500 26/26adbc1c899e95b8bab24e38e5c018cad7b54ac4 -> filestore/client-b/26/26adbc1c…

Le même identifiant 500 dans les deux bases ne mélange rien : chaque base a sa table et son dossier. La séparation tient tant que c'est Odoo qui choisit la base. Elle ne tient plus quand c'est du code Python qui s'exécute : dans le même processus, tout code a le rôle PostgreSQL et l'utilisateur système de tous les clients. Exécuté dans la console de la base client-a (le même code dans un module installé chez A ferait pareil) :

import os
from odoo.modules.registry import Registry
from odoo.tools import config

print("je suis", env.cr.dbname, env.company.name)
with Registry('client-b').cursor() as cr:
    cr.execute("SELECT name FROM res_company WHERE id = 1")
    print("lu dans l'autre base :", cr.fetchone()[0])
p = os.path.join(config.filestore('client-b'), '26', '26adbc1c899e95b8bab24e38e5c018cad7b54ac4')
print("fichier de l'autre base :", open(p).read().strip())
je suis client-a Client A lu dans l'autre base : Client B fichier de l'autre base : Contrat type, identique dans les deux bases

Conclusion directe : un module développé pour un seul client et installé sur un serveur partagé a accès à tous les clients. Les actions serveur saisies à l'écran, elles, passent par un bac à sable qui refuse import (« forbidden opcode(s) in 'import os' ») ; c'est le code des modules qui compte.

6. Un rôle PostgreSQL par client ? Pas dans un seul processus

L'idée vient vite : un rôle PostgreSQL par client, pour qu'une base ne puisse pas lire l'autre. Un processus Odoo n'a qu'un db_user, et il ne liste que les bases dont ce rôle est propriétaire (datdba = current_user). Une base client-d créée par un autre rôle, odoo_d, à côté des trois premières :

liste vue depuis client-d.example -> [] X-Odoo-Database: client-d -> 404, et au journal : ERROR client-d odoo.registry: Failed to load registry WARNING client-d odoo.http: Database or registry unusable, trying without psql, rôle odoo, base client-d : SELECT login FROM res_users ERROR: permission denied for table res_users

La base de l'autre rôle est bien protégée, mais elle est aussi hors de portée du processus : pour la servir, il faut un second processus lancé avec db_user = odoo_d. Un rôle par client, c'est un processus par client. Inversement, tant que tous les clients partagent un processus, ils partagent son rôle, et la section 5 s'applique.

7. Les tâches planifiées : partagées, et hors du filtre

Les fils de tâches planifiées (max_cron_threads, 2 par défaut) parcourent les bases l'une après l'autre. Pour le mesurer : dans client-a, une tâche qui dure 30 secondes (env.cr.execute("SELECT pg_sleep(30)")), dans client-b une tâche instantanée, toutes deux dues chaque minute. Avec un seul fil (extrait du journal, date et chemin du module raccourcis) :

14:06:48,982 INFO client-a ir_cron: Job 'Relance lente A' (26) starting 14:07:19,032 INFO client-a ir_cron: Job 'Relance lente A' (26) fully done (… duration 30.05s) 14:07:19,050 INFO client-b ir_cron: Job 'Tâche rapide B' (26) starting 14:07:19,084 INFO client-b ir_cron: Job 'Tâche rapide B' (26) fully done (… duration 0.04s)

La tâche du client B attend la fin de celle du client A : 30 secondes de retard, à chaque passage. Même résultat en mode multi-processus avec workers = 2 et un seul processus de tâches planifiées (B démarre à la seconde où A finit). Avec deux fils, un fil libre saute la tâche verrouillée de A et passe à B, quand il est éveillé :

14:10:01,786 INFO client-a ir_cron: Job 'Relance lente A' (26) starting 14:10:02,794 INFO client-b ir_cron: Job 'Tâche rapide B' (26) starting 14:10:02,831 INFO client-b ir_cron: Job 'Tâche rapide B' (26) fully done (… duration 0.04s) 14:10:31,842 INFO client-a ir_cron: Job 'Relance lente A' (26) fully done (… duration 30.06s) 14:11:03,888 INFO client-a ir_cron: Job 'Relance lente A' (26) starting 14:11:31,918 INFO client-b ir_cron: Job 'Tâche rapide B' (26) starting

Au premier passage, B part une seconde après A. Au suivant, il attend 28 secondes : le second fil dormait encore (chaque fil ne se réveille qu'environ une fois par minute, à un moment légèrement décalé), et le premier a enchaîné A puis B. Un second fil réduit le retard, il ne le supprime pas.

Un client dont les tâches sont lourdes (relances en masse, synchronisations) retarde donc les autres dès qu'il occupe tous les fils. Deuxième point, plus surprenant : le dbfilter ne compte pas pour les tâches planifiées. Elles tournent sur les bases de db_name si cette option est remplie, sinon sur toutes les bases du rôle. Un processus réglé avec dbfilter = ^aucune$, qui ne sert aucune base en HTTP, exécute quand même celles de la base de son rôle :

{"jsonrpc": "2.0", "id": null, "result": []} INFO client-d ir_cron: Job 'Base: Auto-vacuum internal data' (1) starting INFO client-d ir_cron: Job 'Tâche D' (3) starting

D'où le réglage : db_name donne la liste des clients dont les tâches doivent tourner, dbfilter l'aiguillage HTTP. Sans dbfilter, db_name sert aussi de filtre, mais sans tenir compte du domaine : tous les noms voient toute la liste (["client-a", "client-b"] depuis client-a.example comme depuis un nom inconnu). Les deux ensemble, donc.

Piège : le client ajouté au filtre, oublié dans db_name

Avec db_name = client-a,client-b et dbfilter = ^%d$, la base client-c est servie normalement sur client-c.example (page de connexion, 200) mais ses tâches planifiées ne tournent jamais : sa tâche de test, due chaque minute, n'a laissé aucune ligne au journal pendant les mesures, et aucune erreur. Dès que client-c est ajouté à db_name et le service redémarré, elle part au premier passage (« Job 'Tâche C' (26) starting »). Pas de courriels envoyés, pas de relances. Chaque nouveau client s'ajoute aux deux endroits, et le service redémarre. Notez aussi qu'au démarrage, Odoo crée toute base de db_name qui n'existe pas : une faute de frappe y crée une base neuve, avec le seul module base.

Avec plusieurs bases dans db_name, -u est refusé (« Cannot use -i/--init or -u/--update with multiple databases ») : les mises à jour se font base par base, -d sur la ligne de commande remplaçant la liste (odoo-bin -c /etc/odoo.conf -d client-a -u mon_module --stop-after-init --no-http). Enfin, les modules chargés au démarrage (server_wide_modules, base,rpc,web par défaut) le sont une fois pour le processus : en ajouter un l'active pour tous les clients.

8. Nginx par domaine et la configuration d'Odoo

Côté Nginx, un bloc server par client, un bloc par défaut qui ne répond à rien, et des en-têtes posés par Nginx, jamais repris de la requête. Le réglage commun va dans un fichier inclus :

# /etc/nginx/snippets/odoo-proxy.conf : commun à tous les clients
location / {
    proxy_pass http://127.0.0.1:8069;
    proxy_set_header Host              $host;
    proxy_set_header X-Forwarded-Host  $host;
    proxy_set_header X-Forwarded-For   $remote_addr;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_read_timeout 720s;
}
# /etc/nginx/sites-enabled/odoo-clients.conf
# Un nom inconnu (ou l'adresse IP seule) : aucune base, aucune page.
server {
    listen 443 ssl default_server;
    ssl_reject_handshake on;
}
server {
    listen 80 default_server;
    return 444;
}

# Un bloc par client : le nom de domaine choisit la base (dbfilter = ^%d$).
server {
    listen 443 ssl;
    server_name client-a.example;
    ssl_certificate     /etc/letsencrypt/live/client-a.example/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/client-a.example/privkey.pem;
    include snippets/odoo-proxy.conf;
}
server {
    listen 443 ssl;
    server_name client-b.example;
    ssl_certificate     /etc/letsencrypt/live/client-b.example/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/client-b.example/privkey.pem;
    include snippets/odoo-proxy.conf;
}
server {
    listen 80;
    server_name client-a.example client-b.example;
    return 301 https://$host$request_uri;
}

Cette configuration passe nginx -t (Nginx 1.24, certificats d'essai auto-signés) et a été lancée devant le processus Odoo de l'article, sur des ports d'essai. Ce qu'elle donne, avec curl --resolve pour viser le serveur sous chaque nom :

curl -sk --resolve client-a.example:443:127.0.0.1 -H 'Content-Type: application/json' \
     -H 'X-Forwarded-Host: client-b.example' \
     -d '{"jsonrpc":"2.0","method":"call","params":{}}' https://client-a.example/web/database/list
{"jsonrpc": "2.0", "id": null, "result": ["client-a"]}
  • L'en-tête X-Forwarded-Host forgé par le client est remplacé par Nginx : la base reste client-a.
  • Un nom absent de la configuration : la poignée de main TLS est refusée (« tlsv1 unrecognized name »), aucune page, aucun certificat d'un client montré à un autre nom.
  • L'adresse IP en HTTP : réponse vide (444). Un nom de client en HTTP : 301 vers HTTPS.
  • Une clé d'API du client B envoyée sur client-a.example : 401 « Invalid apikey », elle n'existe pas dans la base A.

Côté Odoo, la configuration correspondante, vérifiée derrière ce Nginx :

[options]
http_interface = 127.0.0.1
proxy_mode = True
dbfilter = ^%d$
db_name = client-a,client-b
list_db = False
max_cron_threads = 2

Avec elle : connexion sur client-a.example et client-b.example (200), liste des bases fermée (AccessDenied), connexion à client-b demandée depuis client-a.example refusée (« Database not found. »). En mode multi-processus, le websocket s'ajoute au fichier commun comme pour un seul client (voir l'article HTTPS avec Nginx en fin de page).

9. Quand passer à un processus, ou à un serveur, par client

Un processus partagé convient à des clients de même confiance, sur la même version d'Odoo, avec des modules communs ou standard. Chacun des signes suivants pousse vers un processus par client (un service, un port, un data_dir, un rôle PostgreSQL, une seule base dans db_name et dbfilter = ^client-a$, un upstream Nginx par client) :

SignePourquoi un processus partagé ne suffit plus
Un module spécifique pour un seul clientSon code lit les autres bases et leurs fichiers (section 5).
Un rôle PostgreSQL par client exigé (contrat, audit, RGPD)Un processus = un rôle (section 6).
Des tâches planifiées lourdes chez un clientElles occupent les fils communs et retardent les autres (section 7).
Des versions ou des jeux de modules différentsUn processus charge un seul code Odoo et un seul addons_path.
Des mises à jour à des dates différentesUn redémarrage pour un client coupe tous les autres.

Le serveur séparé vient ensuite, quand la mémoire, le processeur ou PostgreSQL deviennent eux-mêmes le point commun gênant, ou quand un client exige que ses données ne partagent pas une machine.

10. Ce qui change entre Odoo 19 et Odoo 20

Sur l'aiguillage lui-même, rien : le code de la 19.0 publique (lu, non exécuté) applique le même filtre, avec les mêmes substitutions, la même règle pour la session et l'en-tête X-Odoo-Database, la même liste de bases par propriétaire, et les mêmes bases pour les tâches planifiées. Ce qui change est autour :

Odoo 19Odoo 20
http_interface par défaut0.0.0.0, toutes les interfaces127.0.0.1 : Odoo n'est joignable que par le proxy, sauf réglage contraire
Service RPC db (lister, créer, dupliquer les bases par XML-RPC)présentretiré : Invalid service name: db
Code de l'aiguillageodoo/http.pypaquet odoo/http/ (router.py) ; gestion des bases dans odoo/modules/db.py
Requête sans base sur une route non globale404 « … not found in the server-wide controllers »404 « … is not server-wide », avec un renvoi vers /web/login

Venant de la 19

Un serveur multi-clients 19 passe en 20 avec le même dbfilter, le même db_name et la même configuration Nginx. Deux vérifications : si Odoo était joint directement par son adresse IP, régler http_interface (ou, mieux, passer par Nginx) ; si un script d'administration passait par le service RPC db (/xmlrpc/2/db), le réécrire : odoo-bin db pour créer, dupliquer, renommer, sauvegarder ou supprimer, /web/database/list ou psql pour lister.

À retenir

  • dbfilter = ^%d$, avec le $ : une base par nom, et rien d'autre. Un filtre plus large permet de travailler dans la base d'un client depuis le domaine d'un autre, et list_db = False n'y change rien.
  • Le filtre range les requêtes, il ne protège pas : Host et X-Forwarded-Host s'écrivent librement. Odoo sur 127.0.0.1, Nginx qui pose les en-têtes, un mot de passe par base.
  • Les tâches planifiées ignorent le filtre : db_name doit lister chaque client, et une tâche longue chez un client retarde les autres, et un second fil ne fait que réduire ce retard.
  • Dans un processus partagé, tout code Python voit tous les clients : même rôle PostgreSQL, même système de fichiers. Un module spécifique, un rôle par client ou des versions différentes imposent un processus par client.
