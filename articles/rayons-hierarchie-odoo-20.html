Les rayons en Odoo 20 : une hiérarchie avec _parent_store

Informatique, puis Odoo, puis Développement : les exemplaires de la Bibliothèque se rangent maintenant dans des rayons emboîtés. Un modèle qui se contient lui-même, une colonne parent_path tenue à jour par Odoo, l'opérateur child_of pour chercher « tout ce qui est sous ce rayon » en une requête, un panneau de recherche en arbre, et la garde qui empêche un rayon de devenir son propre descendant.

~13 minutes de lecture · niveau intermédiaire · parcours Framework & ORM

Ce que tu vas apprendre

Déclarer

Un modèle hiérarchique : parent_id, _parent_store, parent_path et un nom complet calculé.

Chercher

child_of et parent_of, ce qu'ils deviennent en SQL, et le panneau de recherche en arbre.

Protéger

Déplacer un sous-arbre, refuser une boucle, et ce qui a changé depuis la 19 sur ce point.

1. Un modèle qui se contient lui-même

Un rayon a un nom et, éventuellement, un rayon parent. Le parent est un Many2one vers le même modèle ; les enfants, le One2many inverse. Ces deux champs suffisent à décrire un arbre. Le reste du fichier sert à le parcourir vite et à l'afficher lisiblement :

# models/library_shelf.py
from odoo import api, fields, models


class LibraryShelf(models.Model):
    _name = 'library.shelf'
    _description = "Rayon"
    _parent_store = True
    _rec_name = 'complete_name'
    _order = 'complete_name'

    name = fields.Char(string="Nom", required=True)
    parent_id = fields.Many2one(
        'library.shelf',
        string="Rayon parent",
        index=True,
        ondelete='restrict',
    )
    parent_path = fields.Char(index=True)
    child_ids = fields.One2many('library.shelf', 'parent_id', string="Sous-rayons")
    complete_name = fields.Char(
        string="Rayon",
        compute='_compute_complete_name',
        recursive=True,
        store=True,
    )

    @api.depends('name', 'parent_id.complete_name')
    def _compute_complete_name(self):
        for shelf in self:
            if shelf.parent_id:
                shelf.complete_name = f"{shelf.parent_id.complete_name} / {shelf.name}"
            else:
                shelf.complete_name = shelf.name
LigneRôle
parent_idLe lien vers le rayon du dessus. _parent_name vaut 'parent_id' par défaut : avec ce nom de champ, rien d'autre à déclarer.
ondelete='restrict'On ne supprime pas un rayon qui a des sous-rayons : la base refuse (clé étrangère library_shelf_parent_id_fkey). Sans cet attribut, un Many2one facultatif vaut 'set null' et les sous-rayons deviendraient des racines en silence.
_parent_store = TrueOdoo tient à jour la colonne parent_path à chaque création et à chaque changement de parent.
parent_path = fields.Char(index=True)La colonne elle-même, à déclarer. À l'installation et à chaque mise à jour du module, Odoo vérifie que ce champ est déclaré et indexé (_check_parent_path) et écrit une erreur au journal sinon.
complete_name« Informatique / Odoo / Développement ». Il dépend du nom complet du parent, donc de lui-même : recursive=True le déclare. Oublié, Odoo 20 écrit au chargement UserWarning: Field library.shelf.complete_name should be declared with recursive=True.
_rec_name, _orderLe nom complet sert de nom affiché et de tri : les listes sortent dans l'ordre alphabétique des chemins, donc branche par branche.

Le modèle reçoit ses deux lignes dans security/ir.access.csv : lecture pour l'accueil, tous les droits pour le bibliothécaire. Le menu Configuration › Rayons pointe sur une liste et un formulaire ordinaires. Le module passe en 20.0.1.17.0.

access_library_shelf_desk,Rayons : consultation,library.shelf,group_library_desk,r,
access_library_shelf_manager,Rayons : gestion,library.shelf,group_library_manager,crud,

2. Ce que contient parent_path

Après la mise à jour du module, on crée cinq rayons depuis la console et on y range les neuf exemplaires de la base :

Shelf = env['library.shelf']
info = Shelf.create({'name': "Informatique"})
odoo_ = Shelf.create({'name': "Odoo", 'parent_id': info.id})
dev = Shelf.create({'name': "Développement", 'parent_id': odoo_.id})
adm = Shelf.create({'name': "Administration", 'parent_id': odoo_.id})
py = Shelf.create({'name': "Python", 'parent_id': info.id})
Copy = env['library.copy']
def put(codes, shelf):
    Copy.search([('name', 'in', codes)]).write({'shelf_id': shelf.id})
put(['BIB-0001', 'BIB-0002', 'BIB-0003', 'BIB-0006'], dev)
put(['BIB-0007', 'BIB-0008', 'BIB-0009'], adm)
put(['BIB-0004', 'BIB-0005'], py)
for s in Shelf.search([]):
    print(s.id, repr(s.complete_name), s.parent_path)
env.cr.commit()
1 'Informatique' 1/ 2 'Informatique / Odoo' 1/2/ 4 'Informatique / Odoo / Administration' 1/2/4/ 3 'Informatique / Odoo / Développement' 1/2/3/ 5 'Informatique / Python' 1/5/

parent_path est le chemin des identifiants, de la racine au rayon, chacun suivi d'une barre. Tout ce qui est sous « Odoo » (id 2) a un chemin qui commence par 1/2/. Une recherche de descendants devient une comparaison de début de chaîne, sans remonter l'arbre étage par étage. La colonne porte l'index B-tree demandé par index=True :

library_shelf__parent_path_index CREATE INDEX … ON public.library_shelf USING btree (parent_path)

Odoo calcule ce chemin lui-même. On ne l'écrit jamais : il n'apparaît dans aucune vue.

3. Ranger les exemplaires

Le rayon se pose sur l'exemplaire, pas sur le livre : deux exemplaires d'un même titre peuvent être rangés à deux endroits. Un champ de plus dans models/library_copy.py, ajouté à la liste et au formulaire de l'exemplaire :

    shelf_id = fields.Many2one(
        'library.shelf',
        string="Rayon",
        index=True,
        ondelete='restrict',
    )

Côté rayon, on veut voir combien d'exemplaires il contient, sous-rayons compris. C'est le premier usage de child_of :

    copy_ids = fields.One2many('library.copy', 'shelf_id', string="Exemplaires")
    copy_count = fields.Integer(
        string="Exemplaires (sous-rayons compris)",
        compute='_compute_copy_count',
    )

    def _compute_copy_count(self):
        Copy = self.env['library.copy']
        for shelf in self:
            shelf.copy_count = Copy.search_count([('shelf_id', 'child_of', shelf.id)])

    def action_view_copies(self):
        self.ensure_one()
        return {
            'type': 'ir.actions.act_window',
            'name': self.env._("Exemplaires de %(shelf)s", shelf=self.complete_name),
            'res_model': 'library.copy',
            'view_mode': 'list,form',
            'domain': [('shelf_id', 'child_of', self.id)],
            'context': {'default_shelf_id': self.id},
        }

4. Chercher dans l'arbre : child_of et parent_of

Deux opérateurs de domaine parcourent la hiérarchie. Dans la console :

Copy = env['library.copy']
print(Copy.search([('shelf_id', 'child_of', 2)]).mapped('name'))   # 2 = Odoo
print(Copy.search([('shelf_id', '=', 2)]).mapped('name'))
print(env['library.shelf'].search([('id', 'parent_of', 3)]).mapped('complete_name'))   # 3 = Développement
['BIB-0007', 'BIB-0008', 'BIB-0009', 'BIB-0001', 'BIB-0002', 'BIB-0003', 'BIB-0006'] [] ['Informatique', 'Informatique / Odoo', 'Informatique / Odoo / Développement']
  • child_of : le rayon et tous ses descendants. Avec =, la recherche ne trouve rien : aucun exemplaire n'est rangé directement dans « Odoo ».
  • parent_of : le rayon et tous ses ancêtres, jusqu'à la racine. Utile pour un fil d'Ariane ou pour hériter d'un réglage posé plus haut.
  • Les deux acceptent un identifiant ou une liste d'identifiants.

Ce que reçoit PostgreSQL, en demandant à l'ORM la requête au lieu de l'exécuter (deux appels internes, utiles pour comprendre, pas pour du code métier) :

from odoo.fields import Domain
print(Domain('shelf_id', 'child_of', 2).optimize_full(Copy))
print(Copy._search([('shelf_id', 'child_of', 2)]).select())
[('shelf_id', 'any!', [('parent_path', '=like', '1/2/%')])] SQL('SELECT "library_copy"."id" FROM "library_copy" LEFT JOIN "library_shelf" AS "library_copy__shelf_id" ON ("library_copy"."shelf_id" = "library_copy__shelf_id"."id") WHERE ("library_copy"."shelf_id" IS NOT NULL AND "library_copy__shelf_id"."id" IS NOT NULL AND "library_copy__shelf_id"."parent_path" LIKE %s)', '1/2/%')

Odoo lit d'abord le parent_path du rayon demandé (1/2/), puis réécrit child_of en parent_path LIKE '1/2/%' : une seule requête, quelle que soit la profondeur de l'arbre. C'est tout l'intérêt de _parent_store. Sans lui, l'opérateur marche encore, mais Odoo descend l'arbre niveau par niveau, une requête par étage (odoo/orm/domains.py, _operator_child_of_domain).

5. Un panneau de recherche en arbre

Pour le personnel de l'accueil, la hiérarchie doit se voir dans la liste des exemplaires. La vue de recherche accepte un <searchpanel> : une colonne à gauche, construite à partir d'un champ.

<record id="library_copy_view_search" model="ir.ui.view">
    <field name="name">library.copy.search</field>
    <field name="model">library.copy</field>
    <field name="arch" type="xml">
        <search string="Exemplaires">
            <field name="name"/>
            <field name="book_id"/>
            <field name="shelf_id"/>
            <filter string="Sans rayon" name="no_shelf" domain="[('shelf_id', '=', False)]"/>
            <group>
                <filter string="Rayon" name="group_shelf" context="{'group_by': 'shelf_id'}"/>
            </group>
            <searchpanel>
                <field name="shelf_id" string="Rayons" icon="folder" enable_counters="1"/>
            </searchpanel>
        </search>
    </field>
</record>

Parce que library.shelf a un champ parent, le panneau affiche les rayons en arbre et, quand on clique sur un rayon, filtre avec child_of plutôt qu'avec = (addons/web/static/src/search/search_model.js). Les compteurs (enable_counters) cumulent aussi les sous-rayons.

Un détail d'affichage reste à régler. Pour remplir le panneau, Odoo lit les rayons avec le contexte hierarchical_naming=False (addons/web/models/models.py, search_panel_select_range), mais c'est au modèle d'en tenir compte. Sans rien faire, la branche « Informatique » contient « Informatique / Odoo » puis « Informatique / Python » : le chemin complet répété dans l'arbre. On reprend la façon de faire de product.category :

    @api.depends_context('hierarchical_naming')
    def _compute_display_name(self):
        if self.env.context.get('hierarchical_naming', True):
            return super()._compute_display_name()
        for shelf in self:
            shelf.display_name = shelf.name

Venant de la 19 : l'icône du panneau

En 19, une catégorie du panneau prenait par défaut l'icône fa-folder de FontAwesome. En 20, FontAwesome n'est plus chargé et le défaut devient folder, un nom d'icône Material, avec icon_class pour la variante (search_arch_parser.js). Un attribut icon="fa-…" recopié d'un module 19 est à renommer.

6. Renommer, déplacer un sous-arbre

Deux opérations courantes sur un arbre, essayées dans la console sans valider la transaction (env.cr.rollback() à la fin) :

odoo_ = env['library.shelf'].browse(2)
odoo_.name = "Odoo 20"
env.flush_all()
print(env['library.shelf'].search([('id', 'child_of', 2)]).mapped('complete_name'))

logiciels = env['library.shelf'].create({'name': "Logiciels"})
odoo_.parent_id = logiciels
env.flush_all()
env.invalidate_all()
for s in env['library.shelf'].search([], order='id'):
    print(s.complete_name, s.parent_path)
env.cr.rollback()
['Informatique / Odoo 20', 'Informatique / Odoo 20 / Administration', 'Informatique / Odoo 20 / Développement'] Informatique 1/ Logiciels / Odoo 20 6/2/ Logiciels / Odoo 20 / Développement 6/2/3/ Logiciels / Odoo 20 / Administration 6/2/4/ Informatique / Python 1/5/ Logiciels 6/
  • Renommer « Odoo » recalcule le nom complet des deux sous-rayons : c'est la dépendance parent_id.complete_name, suivie de proche en proche grâce à recursive=True.
  • Déplacer « Odoo » sous « Logiciels » réécrit le parent_path du rayon et de ses descendants (1/2/3/ devient 6/2/3/) : une seule écriture côté Python, Odoo met à jour tout le sous-arbre en SQL.
  • Les exemplaires ne bougent pas : ils restent dans « Développement », qui a simplement changé de place.

7. Refuser les boucles

Un arbre n'a pas de cycle. Que se passe-t-il si l'on donne à « Informatique » le parent « Informatique / Odoo / Développement », son propre petit-enfant ? Le formulaire laisse choisir, le nom complet calculé à l'écran devient même « Informatique / Odoo / Développement / Informatique ». Mais l'enregistrement est refusé :

Ce contrôle vient de _parent_store : en mettant à jour les chemins, Odoo vérifie que le nouveau parent n'est pas dans le sous-arbre du rayon déplacé, et lève une UserError. En console, un essai équivalent donne :

UserError | Vous créez une boucle dans vos enregistrements 'Rayon'. Un enregistrement ne peut pas être un enfant de lui-même ni de l’un de ses propres sous-éléments. Veuillez sélectionner un autre parent.

Pour tester une hiérarchie sans passer par une écriture, la méthode est _has_cycle() : False sur nos rayons. Un modèle à parent sans _parent_store n'a pas cette garde automatique : il lui faut une contrainte. C'est la forme qu'emploie le cœur, par exemple sur res.partner, qui double ainsi la garde de son propre _parent_store :

# odoo/addons/base/models/res_partner.py (Odoo 20)
    @api.constrains('parent_id')
    def _check_parent_id(self):
        if self._has_cycle():
            raise ValidationError(_('You cannot create recursive Partner hierarchies.'))

Venant de la 19 : deux changements

Le refus de boucle de _parent_store affichait en 19 un simple « Recursion Detected. », sans dire quel modèle ni quoi faire ; Odoo 20 donne le message ci-dessus (odoo/orm/models.py, _parent_store_update). Et _check_recursion(), déjà marqué obsolète depuis la 18, a disparu : hasattr(env['library.shelf'], '_check_recursion') vaut False en 20. Une contrainte if not self._check_recursion() portée telle quelle lève une AttributeError : la remplacer par if self._has_cycle() (la condition s'inverse).

Supprimer un rayon parent

Avec ondelete='restrict', supprimer « Odoo » tant qu'il a des sous-rayons est refusé par PostgreSQL. Dans la console, l'erreur remonte brute : ForeignKeyViolation: update or delete on table "library_shelf" violates foreign key constraint "library_shelf_parent_id_fkey". Vider ou déplacer les sous-rayons d'abord.

8. Quatre tests de plus

Le fichier tests/test_shelf.py reprend la classe commune BiblioCase de l'article 17 et garde les quatre comportements vus plus haut :

from odoo.exceptions import UserError

from .common import BiblioCase


class TestShelf(BiblioCase):

    @classmethod
    def setUpClass(cls):
        super().setUpClass()
        Shelf = cls.env['library.shelf']
        cls.info = Shelf.create({'name': "Informatique"})
        cls.odoo = Shelf.create({'name': "Odoo", 'parent_id': cls.info.id})
        cls.dev = Shelf.create({'name': "Développement", 'parent_id': cls.odoo.id})
        cls.copy_1.shelf_id = cls.dev
        cls.copy_2.shelf_id = cls.odoo

    def test_parent_path(self):
        self.assertEqual(self.dev.parent_path, f"{self.info.id}/{self.odoo.id}/{self.dev.id}/")
        self.assertEqual(self.dev.complete_name, "Informatique / Odoo / Développement")

    def test_child_of(self):
        copies = self.env['library.copy'].search([('shelf_id', 'child_of', self.info.id)])
        self.assertEqual(copies, self.copy_1 | self.copy_2)
        self.assertEqual(self.info.copy_count, 2)
        self.assertEqual(self.dev.copy_count, 1)

    def test_move_subtree(self):
        logiciels = self.env['library.shelf'].create({'name': "Logiciels"})
        self.odoo.parent_id = logiciels
        self.assertEqual(self.dev.parent_path, f"{logiciels.id}/{self.odoo.id}/{self.dev.id}/")
        self.assertEqual(self.dev.complete_name, "Logiciels / Odoo / Développement")
        self.assertEqual(self.info.copy_count, 0)

    def test_no_loop(self):
        with self.assertRaises(UserError):
            self.info.parent_id = self.dev

Récapitulatif

  • Un modèle hiérarchique, c'est un Many2one vers lui-même ; _parent_store et la colonne parent_path rendent la recherche dans l'arbre rapide.
  • child_of devient une comparaison de début de chemin (LIKE '1/2/%'), en une requête ; parent_of remonte vers la racine.
  • Le nom complet est un champ calculé stocké et recursive=True : il suit les renommages et les déplacements.
  • Le panneau de recherche affiche l'arbre, cumule les compteurs et filtre par child_of ; hierarchical_naming y raccourcit les noms.
  • Odoo 20 refuse une boucle avec un message clair, et _check_recursion() laisse la place à _has_cycle().
