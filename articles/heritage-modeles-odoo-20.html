Hériter d'un modèle Odoo 20 : l'adhérent est un partenaire

Un adhérent a un nom, un courriel, un téléphone, une adresse. Odoo sait déjà tout cela : c'est un res.partner. Plutôt que de recopier ces champs, on délègue — et l'adhérent devient un partenaire muni d'une carte, sans une seule colonne en double.

~16 minutes de lecture · niveau intermédiaire · parcours Framework & ORM

Ce que tu vas apprendre

Les trois héritages

Étendre, copier, déléguer : trois mécanismes, trois usages, une seule syntaxe qui se ressemble.

La délégation

_inherits en pratique, ses deux attributs obligatoires et ce qu'elle écrit réellement en base.

Ce qu'elle entraîne

Les droits du modèle parent, désormais exigés, et une suppression qui n'est pas symétrique.

Prérequis

  • Le module biblio des articles précédents : les livres, les exemplaires et leur relation un-à-plusieurs.
  • Le serveur Odoo 20 joignable sur http://localhost:8069, base biblio.
  • Aucune dépendance nouvelle : res.partner vient du module base, déjà dans depends.

Trois héritages, trois intentions

Le mot « héritage » recouvre trois mécanismes distincts dans Odoo. Ils s'écrivent de façon voisine, ce qui en fait une source d'erreurs durable. La question à se poser n'est pas « comment j'hérite ? » mais « quelle phrase je veux écrire ? ».

Les deux premiers sont familiers. L'extension est ce qu'on fait pour ajouter un champ à un modèle standard : un _inherit seul, sans _name, et tous les partenaires de la base gagnent le champ. Le prototype, lui, crée un modèle neuf qui reprend les champs d'un autre sans lien entre leurs données — le cœur d'Odoo 20 en compte vingt-trois, par exemple website.event.menu qui reprend website.seo.metadata.

Le troisième est celui qui nous intéresse.

1. Le modèle library.member

Un adhérent, c'est une personne du carnet d'adresses plus un numéro de carte et une date d'adhésion. Crée models/library_member.py :

from odoo import api, fields, models


class LibraryMember(models.Model):
    _name = 'library.member'
    _description = "Adhérent"
    _inherits = {'res.partner': 'partner_id'}
    _order = 'card_number'

    partner_id = fields.Many2one(
        'res.partner',
        string="Partenaire",
        required=True,
        ondelete='cascade',
    )
    card_number = fields.Char(string="Numéro de carte", required=True, copy=False)
    join_date = fields.Date(
        string="Date d'adhésion",
        default=fields.Date.context_today,
    )

    _card_number_unique = models.Constraint(
        'UNIQUE(card_number)',
        "Ce numéro de carte est déjà attribué à un autre adhérent.",
    )

    @api.depends('card_number', 'partner_id.name')
    def _compute_display_name(self):
        for member in self:
            member.display_name = f"{member.name} ({member.card_number})"

Puis, dans models/__init__.py :

from . import library_book
from . import library_copy
from . import library_member

Deux lignes portent tout le mécanisme. _inherits est un dictionnaire : à gauche le modèle délégué, à droite le nom du champ qui le pointe. Ce champ, il faut le déclarer — Odoo ne le crée pas.

Remarque au passage : _compute_display_name lit member.name alors que le modèle ne déclare aucun champ name. C'est déjà la délégation à l'œuvre.

Le piège : deux attributs non négociables

Le champ de délégation doit être required=True et porter un ondelete valant 'cascade' ou 'restrict'. Ce n'est pas une recommandation : sans eux, le serveur refuse de démarrer.

TypeError: Field definition for _inherits reference 'partner_id' in 'library.member' must be marked as 'delegate', 'required' with ondelete='cascade' or 'restrict'

Le message parle de delegate, mais il ne faut surtout pas l'écrire : Odoo pose delegate=True tout seul dès que le nom du champ figure dans _inherits. Les deux seuls attributs à ajouter à la main sont bien required et ondelete.

2. Ce que la base contient vraiment

La question décisive : combien de fois le nom de l'adhérent est-il stocké ? Une seule. Regarde la table :

SELECT column_name FROM information_schema.columns
 WHERE table_name = 'library_member' ORDER BY column_name;
card_number create_date create_uid id join_date partner_id write_date write_uid

Pas de name, pas d'email, pas de phone. Les champs du partenaire ne sont pas recopiés : ils deviennent des champs liés et non stockés, calculés à la lecture depuis partner_id. On peut le vérifier modèle en main :

name | inherited True | related 'partner_id.name' | store False email | inherited True | related 'partner_id.email' | store False phone | inherited True | related 'partner_id.phone' | store False city | inherited True | related 'partner_id.city' | store False

Et la clé étrangère qui tient l'ensemble :

FOREIGN KEY (partner_id) REFERENCES res_partner(id) ON DELETE CASCADE UNIQUE (card_number)
Ce qu'on croitCe qui se passe
« L'adhérent copie les champs du partenaire. »Il les emprunte : aucune colonne, aucune duplication, aucune désynchronisation possible.
« Il faut créer le partenaire d'abord. »Créer l'adhérent crée le partenaire dans la même opération.
« Les champs empruntés sont en lecture seule. »Ils s'écrivent depuis l'adhérent ; la valeur part dans le partenaire.

3. Lire, écrire, chercher un champ délégué

Tout se passe comme si les champs appartenaient au modèle. Créer un adhérent en renseignant directement des champs du partenaire fonctionne :

adherent = env['library.member'].create({
    'name': "Équipe Développement",       # champ de res.partner
    'email': 'dev@example.org',           # champ de res.partner
    'card_number': 'CARTE-001',           # champ de library.member
})

Odoo crée le partenaire, puis l'adhérent qui le pointe. L'écriture traverse dans les deux sens : modifier le téléphone depuis l'adhérent met à jour le partenaire, et modifier la ville depuis le partenaire se voit aussitôt depuis l'adhérent. Il n'y a qu'une donnée.

La recherche aussi traverse, sans effort particulier :

env['library.member'].search([('name', '=', "Équipe Développement")])
env['library.member'].search([('email', 'like', 'dev@')])

C'est la différence de fond avec un simple Many2one vers res.partner : là, il aurait fallu écrire ('partner_id.name', '=', …) et afficher le nom par un champ related déclaré à la main, champ par champ.

Quand ne pas déléguer

La délégation dit « est un », pas « a un ». Un livre a un auteur : c'est un Many2one, et l'article précédent l'a montré. Un adhérent est une personne du carnet d'adresses : c'est une délégation. Se tromper de sens donne un modèle qui s'écroule dès qu'un même partenaire doit apparaître deux fois — ce que la contrainte d'unicité du numéro de carte, elle, autorise sans problème.

4. Les droits : le parent compte désormais

Comme tout modèle, l'adhérent a besoin de sa ligne. Ajoute-la à security/ir.access.csv :

id,name,model_id,group_id/id,operation,domain
access_library_book_user,library.book utilisateur,library.book,base.group_user,crud,
access_library_copy_user,library.copy utilisateur,library.copy,base.group_user,crud,
access_library_member_user,library.member utilisateur,library.member,base.group_user,crud,

Mais cette ligne ne suffit plus à elle seule. En version 20, un modèle qui délègue voit le domaine d'accès de son parent ajouté comme restriction. On peut le lire tel qu'Odoo le calcule :

>>> env['library.member']._access_domain('read') [('partner_id', 'any', ['|', '|', ('partner_share', '=', False), ('company_id', 'parent_of', [1]), ('company_id', '=', False)])]

Le domaine qui apparaît entre crochets n'est pas celui de l'adhérent : c'est celui de res.partner, transposé à travers le champ de délégation. Conséquence directe : un utilisateur qui n'a pas accès aux partenaires ne verra aucun adhérent, quelle que soit la ligne posée sur library.member. Et si le parent lui est totalement fermé, l'accès est refusé sans condition.

Ce qui change depuis Odoo 19

En version 19, seules les règles d'enregistrement du modèle parent remontaient vers l'enfant ; le droit d'accès au modèle parent, lui, n'était pas exigé. En version 20, c'est le domaine d'accès complet — permissions comprises — qui devient une restriction sur l'enfant.

En pratique, un module qui déléguait vers un modèle réservé à un groupe restreint fonctionnait en 19 et se referme en 20. Le comportement se désactive au besoin par _check_inherits_access = False sur le modèle enfant — c'est ce que fait mail.mail dans le cœur — mais c'est un contournement à assumer, pas un réglage par défaut.

Ici, rien à faire : base.group_user donne déjà accès aux partenaires. Le piège ne se manifeste que sur des modèles parents protégés — et il se manifeste alors en silence, par une liste vide.

7. Une suppression qui n'est pas symétrique

C'est le comportement le plus contre-intuitif de la délégation, et il découle directement du ondelete='cascade' posé sur le champ :

ActionEffet
Supprimer l'adhérentLe partenaire reste. La personne sort de la bibliothèque, pas du carnet d'adresses.
Supprimer le partenaireL'adhérent disparaît avec lui, par la clé étrangère.

Ce sens-là est le bon : l'adhérent n'a aucune existence sans son partenaire, tandis que le partenaire vit très bien sans carte de bibliothèque. Mais il implique qu'une suppression faite depuis le carnet d'adresses — un endroit où l'on ne pense pas à la bibliothèque — emporte silencieusement une adhésion. Si ce n'est pas souhaitable, ondelete='restrict' est l'autre valeur admise : la suppression du partenaire est alors refusée tant qu'une adhésion existe.

Ce qui ne change pas depuis Odoo 19

Le mécanisme de délégation lui-même est identique : mêmes attributs, même effet en base, mêmes gardes au chargement. Le cœur d'Odoo 20 s'en sert toujours abondamment — product.product délègue à product.template, hr.employee à hr.version. Seule la propagation des droits du parent, vue plus haut, a été renforcée.

Pense-bête des héritages

La phrase à écrireLe mécanisme
« J'ajoute un champ aux partenaires. »_inherit = 'res.partner', sans _name
« Je veux les mêmes champs dans un modèle à part. »_inherit = 'autre.modele' et _name = 'mon.modele'
« Mon enregistrement EST un partenaire. »_inherits = {'res.partner': 'partner_id'}
« Mon enregistrement A un partenaire. »fields.Many2one('res.partner') — pas d'héritage

Et le champ de délégation, toujours écrit de la même façon : fields.Many2one('modele.parent', required=True, ondelete='cascade').

Récapitulatif

  • Trois héritages : l'extension modifie un modèle, le prototype en copie les champs, la délégation relie deux enregistrements.
  • _inherits exige un Many2one required=True avec ondelete='cascade' ou 'restrict' — sinon le serveur ne démarre pas.
  • Ne jamais écrire delegate=True : Odoo le pose lui-même.
  • Les champs du parent ne sont pas copiés : aucune colonne côté enfant, mais lecture, écriture et recherche fonctionnent dessus.
  • En version 20, l'accès au modèle parent est exigé : sans lui, la liste de l'enfant reste vide.
  • Supprimer l'enfant laisse le parent ; supprimer le parent emporte l'enfant.
  • Déléguer répond à « est un ». Pour « a un », un Many2one suffit.

La suite de la série met ces adhérents à contribution : les emprunts, qui relieront une personne, un exemplaire et deux dates.
