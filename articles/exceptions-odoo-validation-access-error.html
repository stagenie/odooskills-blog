UserError, ValidationError, AccessError en Odoo 20 : lire et corriger

« Opération invalide », « Erreur de validation », « Erreur d'accès », « Enregistrement manquant » : quatre fenêtres, quatre exceptions Python, quatre causes bien distinctes. Le titre de la fenêtre te dit déjà laquelle a été levée ; le message, quoi corriger.

~6 minutes de lecture · niveau débutant · parcours Framework & ORM

La réponse en bref

FenêtreExceptionCe qu'elle ditCorriger
Opération invalideUserErrorl'action n'a pas de sens dans l'état actuel du documentchanger l'état d'abord (annuler, compléter)
Erreur de validationValidationErrorune contrainte @api.constrains refuse la donnéecorriger la valeur saisie
Erreur d'accèsAccessErroril manque un groupe, ou une règle masque l'enregistrementajouter le groupe ou revoir ir.access
Enregistrement manquantMissingErrorl'id visé n'existe plusrecharger ; en code, filtrer par exists()

Les quatre classes sont définies dans odoo/exceptions.py et héritent toutes de UserError. Elles sont identiques à celles de la 19.0 : ce qui suit vaut pour les deux versions.

1. Les provoquer toutes les quatre dans le shell

Le plus sûr moyen de reconnaître une exception est de la déclencher soi-même. Sur une base de démo avec Ventes installé, ce script passe à odoo-bin shell quatre opérations vouées à l'échec. Chacune tourne dans un savepoint : l'échec est annulé et ne pollue pas la suite.

from odoo.exceptions import UserError, ValidationError, AccessError, MissingError

def essai(action):
    try:
        with env.cr.savepoint():
            action()
    except UserError as e:
        print(f"{type(e).__name__} (HTTP {e.http_status}) | {e}\n")

acme = env['res.partner'].browse(10)              # Acme Corporation
portail = env['res.users'].search([('login', '=', 'portal')])

essai(lambda: env['sale.order'].browse(7).unlink())                # S00007 confirmée
essai(lambda: acme.write({'parent_id': acme.child_ids[0].id}))     # boucle
essai(lambda: env['sale.order'].with_user(portail).browse(7).name) # commande d'un autre
essai(lambda: env['res.partner'].browse(999999).name)              # id inexistant
print([issubclass(c, UserError) for c in (ValidationError, AccessError, MissingError)])

Deux enseignements tiennent dans cette sortie. D'abord, un seul except UserError les a toutes attrapées : la dernière ligne le confirme, ValidationError, AccessError et MissingError sont des sous-classes de UserError. Ensuite, chaque classe porte un attribut http_status : 422 pour UserError et ValidationError, 403 pour AccessError, 404 pour MissingError. C'est le code que reçoit un appel d'API.

2. Ce que voit l'utilisateur, ce que garde le journal

Dans le navigateur, le client web choisit le titre de la fenêtre d'après le nom de l'exception (web/static/src/core/errors/error_dialogs.js) et affiche le message tel quel. Les voici capturées sur la même démo :

Ces quatre fenêtres n'ont qu'un bouton Fermer : pas de « Voir les détails techniques », pas de pile d'appels. C'est voulu, l'erreur est destinée à l'utilisateur. Côté serveur, le journal n'en garde qu'une ligne WARNING, sans trace :

2026-10-21 11:21:12,718 61715 WARNING ma_base odoo.http: Vous ne pouvez pas supprimer un devis envoyé ou une commande client confirmée. Vous devez l'annuler au préalable. 2026-10-21 11:22:12,095 61715 WARNING ma_base odoo.http: Enregistrement inexistant ou supprimé.

Pour savoir quelle ligne a refusé un accès, relance le serveur avec --dev=access : chaque AccessError est alors suivie de sa pile complète dans le journal (odoo/http/router.py, même comportement en 19). Les trois autres exceptions restent sur une ligne : leur message suffit en général.

3. Lire le message et corriger la cause

UserError : « Opération invalide »

Le message dit ce qui bloque et, souvent, quoi faire. Ici, _unlink_except_draft_or_cancel (sale/models/sale_order.py) refuse de supprimer une commande qui n'est ni en devis ni annulée : il faut l'annuler d'abord. Pour retrouver la méthode, cherche le texte anglais du message dans les sources (le msgid du fichier .po du module si l'écran est en français).

ValidationError : « Erreur de validation »

Une contrainte @api.constrains a jugé la donnée invalide, et Odoo annule toute l'écriture. Le refus de boucle vient de _check_parent_id sur res.partner ; la référence trop courte, d'une contrainte de module. On corrige la valeur, pas le code, sauf si la règle elle-même est fausse.

AccessError : « Erreur d'accès »

Elle prend deux formes, à distinguer avant d'agir :

  • « Vous n'êtes pas autorisé à accéder aux enregistrements… » suivi d'une liste de groupes : l'utilisateur n'a aucun droit sur le modèle. Ajoute-lui l'un des groupes cités, ou, dans ton module, une ligne security/ir.access.csv pour son groupe.
  • « Oups ! … top secrets » : le modèle lui est ouvert, mais une règle à domaine exclut cet enregistrement (ici, la commande d'un autre client pour l'utilisateur portail). Lis ce domaine en console : env['sale.order'].with_user(u)._access_domain('read').

Avant d'appeler une méthode pour le compte d'un utilisateur, teste plutôt que d'attraper :

portail = env['res.users'].search([('login', '=', 'portal')])
commande = env['sale.order'].with_user(portail).browse(7)
print(commande.has_access('read'))
print(env['res.partner'].browse([10, 999999]).exists())
False res.partner(10,)

MissingError : « Enregistrement manquant »

L'id existe dans la page ou dans ton code, plus dans la base : supprimé dans un autre onglet, par une action planifiée, ou id écrit en dur. Côté code, exists() (ci-dessus) garde les seuls enregistrements présents : 999999 a disparu du résultat sans erreur. À noter : ouvrir dans le navigateur l'URL d'un id inexistant ne lève pas de MissingError, le client affiche seulement une notification « Il semble que les enregistrements avec ID 999999 soient introuvables ».

4. Les lever toi-même

Dans un module, deux exceptions servent tous les jours : UserError pour refuser une action, ValidationError dans une contrainte pour refuser une donnée. Le module d'exemple qui a produit la fenêtre « Erreur de validation » ci-dessus tient en un fichier :

from odoo import api, models
from odoo.exceptions import UserError, ValidationError


class SaleOrder(models.Model):
    _inherit = 'sale.order'

    @api.constrains('client_order_ref')
    def _check_client_order_ref(self):
        for order in self:
            if order.client_order_ref and len(order.client_order_ref) < 4:
                raise ValidationError(self.env._(
                    "La référence client « %s » est trop courte (4 caractères minimum).",
                    order.client_order_ref))

    def action_confirm(self):
        for order in self:
            if not order.order_line:
                raise UserError(self.env._(
                    "La commande %s n'a aucune ligne : ajoutez un article avant de la confirmer.",
                    order.name))
        return super().action_confirm()

Essayé en console sur un devis vide, puis sur une référence de deux lettres :

UserError | La commande S00027 n'a aucune ligne : ajoutez un article avant de la confirmer. ValidationError | La référence client « AB » est trop courte (4 caractères minimum).

Rédige le message pour l'utilisateur : ce qui bloque et comment s'en sortir, avec le nom du document. AccessError et MissingError, en revanche, se lèvent rarement à la main : la première vient des droits (check_access la lève pour toi), la seconde de l'ORM.

Un except UserError attrape aussi les trois autres

Puisqu'elles héritent de UserError, un bloc except UserError: pass écrit pour ignorer un refus métier avale aussi un défaut de droits ou un enregistrement disparu, sans laisser de trace. Attrape la classe la plus précise (except AccessError avant except UserError), ou mieux, teste avant d'agir avec has_access() et exists().

À retenir

  • Le titre de la fenêtre donne l'exception : Opération invalide = UserError, Erreur de validation = ValidationError, Erreur d'accès = AccessError, Enregistrement manquant = MissingError.
  • Une AccessError qui liste des groupes = droit manquant sur le modèle ; « Oups ! » = règle à domaine sur l'enregistrement. --dev=access met la pile au journal.
  • Tu lèves UserError et ValidationError ; tu préviens les deux autres avec has_access() et exists().
  • Les quatre héritent de UserError : attrape la plus précise.
