Dépendances Python d'un module Odoo 20 : external_dependencies et venv

Ton module a besoin d'une bibliothèque Python qu'Odoo ne fournit pas. Quelle version de Python choisir, où installer la bibliothèque, comment la déclarer dans le manifeste et ce qu'Odoo 20 fait quand elle manque : la réponse, rejouée sur un module d'exemple.

~6 minutes de lecture · niveau intermédiaire · série Astuces dev Odoo 20

Édition : Community. Vérifié sur Odoo 20.0 Community, octobre 2026, Ubuntu 24.04, Python 3.12, base de démonstration, un environnement virtuel neuf et un petit module d'exemple, mon_slug, qui utilise la bibliothèque python-slugify.

La réponse en bref

  1. Python 3.12 à 3.14 pour Odoo 20, dans un environnement virtuel (venv) réservé à Odoo.
  2. Dans ce venv : pip install -r requirements.txt, puis packaging et les bibliothèques de tes modules.
  3. Dans le manifeste : 'external_dependencies': {'python': ['python-slugify>=8']}, avec le nom PyPI du paquet.
  4. Odoo vérifie à l'installation et à la mise à jour du module, pas au démarrage : installe la bibliothèque sur chaque serveur avant d'y déployer le code.

1. La version de Python et le venv

Les bornes sont écrites dans odoo/release.py : MIN_PY_VERSION = (3, 12) et MAX_PY_VERSION = (3, 14). En dessous de 3.12, Odoo refuse de démarrer (Outdated python version detected, Odoo requires Python >= 3.12 to run.) ; au-dessus de 3.14, il démarre avec un avertissement Python … is not officially supported. Le requirements.txt suit les distributions : ses versions épinglées visent Python 3.12 (Ubuntu 24.04), 3.13 et 3.14. La 19 acceptait encore Python 3.10 : un serveur en 3.10 ou 3.11 qui faisait tourner une 19 doit changer de Python pour passer en 20.

Installe les bibliothèques dans un venv, jamais dans le Python du système. Depuis le dossier des sources d'Odoo :

python3.12 -m venv venv
venv/bin/python --version
venv/bin/pip install -r requirements.txt
venv/bin/python odoo-bin --version
Python 3.12.3 … Successfully installed Babel-2.10.3 Jinja2-3.1.2 MarkupSafe-2.1.5 Pillow-10.2.0 … zope.interface-8.7 Odoo Server 20.0

Sur le poste de test, sous Ubuntu 24.04, pip a installé 65 paquets. Ensuite, lance toujours Odoo avec ce Python (venv/bin/python odoo-bin, ou le venv choisi comme interpréteur dans ton IDE) : une bibliothèque installée ailleurs n'existe pas pour Odoo.

Deux paquets absents de requirements.txt peuvent te manquer : packaging, que la section suivante explique, et phonenumbers, que le module standard account_peppol déclare lui-même en dépendance externe.

2. Déclarer la bibliothèque dans le manifeste

Le module d'exemple calcule un « slug » (le nom d'un article réduit à des minuscules sans accents, séparées par des tirets) avec python-slugify :

# mon_slug/__manifest__.py
{
    'name': "Slug des articles",
    'version': '20.0.1.0.0',
    'author': 'OdooSkills',
    'depends': ['product'],
    'external_dependencies': {
        'python': ['python-slugify>=8'],
    },
    'license': 'LGPL-3',
}
# mon_slug/models/product_template.py
from slugify import slugify

from odoo import api, fields, models


class ProductTemplate(models.Model):
    _inherit = 'product.template'

    slug = fields.Char(compute='_compute_slug')

    @api.depends('name')
    def _compute_slug(self):
        for product in self:
            product.slug = slugify(product.name or '')

Ce que lit Odoo 20 dans external_dependencies :

  • python : une liste de noms de paquets PyPI (python-slugify), pas de noms d'import (slugify). Odoo cherche d'abord les métadonnées du paquet installé ; avec le nom d'import, il se rabat sur un import et l'accepte, mais l'écrit dans le journal : python external dependency on 'slugify' does not appear to be a valid PyPI package.
  • Version et marqueurs : la syntaxe de pip est comprise (>=8, ; python_version >= '3.13'). Une version installée hors bornes est refusée : External dependency version mismatch: python-slugify>=99 (installed: 9.1.3).
  • bin : des exécutables cherchés dans le PATH.
  • apt : un dictionnaire facultatif qui ajoute au message d'erreur, sur Debian et Ubuntu, la commande apt install à lancer.

Pour lire une version (>=8), Odoo a besoin du paquet packaging. Dans un venv construit seulement avec requirements.txt, il manque, et l'installation tombe sur une exception qui ne parle pas de ton module :

Exception: Package `packaging` is required to parse `python-slugify>=8` external dependency and is not installed

venv/bin/pip install packaging règle la question. Un nom seul, sans version, passe sans lui. Côté apt, la clé doit reprendre exactement la chaîne de la liste python, version comprise : avec 'apt': {'python-slugify>=99': 'python3-slugify'}, le message se termine par Peut être installé en exécutant : apt install python3-slugify ; avec la clé 'python-slugify', cette ligne n'apparaît pas. Les modules standard d'Odoo évitent le piège : sur 641 manifestes, les cinq qui déclarent une dépendance externe (dont account_peppol avec phonenumbers) la donnent sans version.

3. Ce qu'Odoo 20 fait quand la bibliothèque manque

Sans python-slugify dans le venv, le bouton Activer de la fiche du module (menu Applications) s'arrête net :

Le module reste « non installé ». En ligne de commande, -i mon_slug écrit le même message dans le journal (odoo.exceptions.UserError) et s'arrête avec le code retour 255. La mise à jour (-u) refait le contrôle : c'est là qu'une exigence de version relevée dans le manifeste se fait sentir, avec Impossible de mettre à jour le module "mon_slug".

La correction tient en une commande, dans le venv qui fait tourner Odoo, puis l'installation passe :

Le script slug.py se contente de lire le champ sur les premiers articles de la démo :

for p in env['product.template'].search([], limit=4, order='id'):
    print(p.id, p.name, '->', p.slug)

Pour garder la liste à jour, note aussi tes bibliothèques dans un requirements.txt à la racine de ton dépôt de modules ; un pip install -r suffit alors sur chaque machine.

Installé ici, absent là-bas : la base entière ne démarre plus

external_dependencies n'est contrôlé qu'à l'installation et à la mise à jour. Au démarrage, Odoo importe simplement le code des modules installés. Si tu copies la base ou le code sur un serveur dont le venv n'a pas la bibliothèque, le from slugify import slugify échoue et c'est tout le registre qui tombe, pas seulement le module :

Ordre sûr pour un déploiement : pip install dans le venv du serveur, puis le code, puis -u du module.

À retenir

  • Odoo 20 tourne sur Python 3.12 à 3.14, dans un venv à lui ; lance-le toujours avec le Python de ce venv.
  • external_dependencies : noms PyPI, versions à la pip (elles exigent packaging), clé apt identique à la chaîne déclarée.
  • Le contrôle se fait à l'installation et à la mise à jour : message clair, module laissé non installé.
  • Au démarrage, une bibliothèque absente fait tomber toute la base : installe-la avant de déployer.
