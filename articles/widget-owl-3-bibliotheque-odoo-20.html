Un widget OWL 3 en Odoo 20 : le badge de retard des emprunts

« 3 j de retard » en rouge, « À rendre dans 2 j » en orange, « Rendu » en gris : un widget de champ OWL 3 écrit pour le module Bibliothèque, branché sur la liste et les cartes des emprunts, testé avec Hoot. Avec les trois réflexes d'Odoo 19 qui, en Odoo 20, cassent un widget sans prévenir.

~11 minutes de lecture · niveau intermédiaire · parcours Web et interface

Ce que tu vas apprendre

Déclarer

Le descripteur d'un widget de champ : supportedTypes, extractProps pour les options de la vue, fieldDependencies pour les champs voisins.

Calculer

Un composant OWL 3 : useProps et ses types t, une valeur par défaut, des getters, un gabarit où tout passe par this.

Tester

Un test Hoot qui monte une vraie vue liste à une date figée, et ce qu'il attrape quand on oublie une dépendance.

Prérequis

  • Le module biblio des articles précédents, jusqu'aux rayons hiérarchiques, avec les emprunts, leur échéance date_due et leur état. On n'ajoute ici qu'un dossier JavaScript, un fichier de test et deux lignes de vue. Le module a été essayé avec l'API JSON-2 de l'étape suivante déjà en place ; le widget n'en dépend pas.
  • La vue carte des emprunts (<card>) vient de Kanban, graphique et pivot en Odoo 20.
  • Un navigateur récent. Aucun outil JavaScript à installer : Odoo 20 assemble lui-même les fichiers du module.

Jusqu'ici, la liste des emprunts affichait l'échéance comme une date brute et colorait toute la ligne en rouge en cas de retard. La carte, elle, construisait son propre badge « N j de retard » en QWeb à partir du champ calculé days_late. Deux affichages, deux logiques. Un widget de champ les remplace par un seul composant. Il se pose sur le champ date_due et le client web l'utilise partout où la vue le demande. Le chemin est toujours le même : la vue nomme le widget, le registre le retrouve, le composant calcule et affiche.

Quatre fichiers changent dans le module :

biblio/
├── __manifest__.py                         # version 20.0.1.19.0, section assets
├── static/src/late_badge/
│   ├── late_badge_field.js                 # le composant et son descripteur
│   └── late_badge_field.xml                # le gabarit OWL
├── static/tests/late_badge_field.test.js   # le test Hoot
└── views/library_loan_views.xml            # widget="late_badge" sur la liste et la carte

1. Le composant : des props typées et quatre getters

Un composant OWL reçoit des props (les paramètres que lui passe le composant parent, ici la vue) et expose des getters (des propriétés recalculées à chaque lecture, que le gabarit affiche).

Voici le fichier complet, tel qu'il tourne dans le module :

import { Component, t, useProps } from "@odoo/owl";
import { _t } from "@web/core/l10n/translation";
import { registry } from "@web/core/registry";
import { formatDate } from "@web/views/fields/formatters";
import { standardFieldProps } from "@web/views/fields/standard_field_props";

const { DateTime } = luxon;

export class LateBadgeField extends Component {
    static template = "biblio.LateBadgeField";

    // OWL 3 : `static props` est ignoré, les props se déclarent avec useProps()
    props = useProps({
        ...standardFieldProps,
        warnDays: t.number().optional(3),
    });

    get record() {
        return this.props.record;
    }

    /** Jours restants avant l'échéance (négatif = retard), null si pas d'échéance. */
    get days() {
        const due = this.record.data[this.props.name];
        if (!due) {
            return null;
        }
        const today = DateTime.local().startOf("day");
        return Math.round(due.startOf("day").diff(today, "days").days);
    }

    get status() {
        if (this.record.data.state === "returned") {
            return "returned";
        }
        if (this.days === null) {
            return "none";
        }
        if (this.days < 0) {
            return "late";
        }
        return this.days <= this.props.warnDays ? "soon" : "ok";
    }

    get label() {
        const days = this.days;
        switch (this.status) {
            case "returned":
                return _t("Rendu");
            case "late":
                return _t("%s j de retard", -days);
            case "soon":
                return days === 0 ? _t("À rendre aujourd'hui") : _t("À rendre dans %s j", days);
            case "ok":
                return formatDate(this.record.data[this.props.name]);
            default:
                return "";
        }
    }

    get badgeClass() {
        return {
            returned: "text-bg-secondary",
            late: "text-bg-danger",
            soon: "text-bg-warning",
            ok: "text-bg-success",
        }[this.status];
    }
}

export const lateBadgeField = {
    component: LateBadgeField,
    displayName: _t("Badge de retard"),
    supportedTypes: ["date"],
    // champs lus par le widget même si la vue ne les affiche pas
    fieldDependencies: [{ name: "state", type: "selection" }],
    extractProps: ({ options }) => ({
        warnDays: options.warn_days,
    }),
};

registry.category("fields").add("late_badge", lateBadgeField);

Ce qu'il faut y lire, de haut en bas :

  • Les props se déclarent par useProps(), dans un champ de classe, et non plus par static props. Les types viennent de l'objet t d'OWL 3 : t.number(), t.string(), t.object()… standardFieldProps apporte les quatre props que le client web passe à tout widget de champ : id, name, readonly et record. Le widget natif relative_date d'Odoo 20 est écrit sur ce modèle.
  • t.number().optional(3) porte la valeur par défaut. Dans le source d'OWL 3, la valeur passée à optional() est appliquée quand la prop vaut undefined, donc quand la vue ne donne pas l'option. La carte des emprunts s'en sert : elle ne précise rien et obtient 3 jours.
  • Les données sont dans this.props.record.data, indexées par nom de champ. this.props.name vaut ici "date_due". Un champ Date y arrive sous forme d'objet luxon (bibliothèque de dates fournie par le client web, d'où le const { DateTime } = luxon), ou false s'il est vide.
  • Le nombre de jours se calcule dans le navigateur, à la date du jour de l'utilisateur : l'échéance et aujourd'hui sont ramenés à minuit avant la différence, pour ne compter que des jours entiers. Un résultat négatif signifie un retard.
  • Les libellés passent par _t(), avec %s pour le nombre. Ce sont ces chaînes qui partiront dans le fichier de traduction (étape 6).

2. Le gabarit : tout ce qui est au composant prend this.

<?xml version="1.0" encoding="UTF-8"?>
<templates xml:space="preserve">

    <!-- OWL 3 : tout ce qui appartient au composant se lit avec `this.` -->
    <t t-name="biblio.LateBadgeField">
        <span t-if="this.status !== 'none'"
              class="o_late_badge badge rounded-pill"
              t-att-class="this.badgeClass"
              t-out="this.label"/>
    </t>

</templates>

Le nom du gabarit, biblio.LateBadgeField, est celui de static template dans le composant. Le préfixe du module évite toute collision avec un autre gabarit. Les classes badge, rounded-pill et text-bg-* sont celles de Bootstrap, déjà chargé par le client web : aucun CSS à écrire. Le badge ne s'affiche pas quand l'échéance est vide.

En OWL 3, un gabarit n'accède plus aux membres du composant par leur nom seul. On écrit this.label, this.badgeClass, this.status, this.props.record. L'essai a été fait : avec t-out="label" et t-att-class="badgeClass", la liste affiche cinq badges vides, et la console du navigateur ne signale aucune erreur. Seules les variables locales du gabarit (celles d'un t-foreach ou d'un t-set) s'écrivent sans this.

3. Le descripteur : ce que le client web sait du widget

La dernière partie du fichier JavaScript n'est pas le composant, mais l'objet qui le décrit (lateBadgeField), enregistré dans le registre fields sous le nom late_badge. C'est ce nom que la vue écrira dans widget="…". Trois clés y travaillent :

CléRôleDans le badge
supportedTypesTypes de champ acceptés par le widget["date"] : il n'a de sens que sur une date
extractPropsTraduit les attributs et options de la vue en props du composantoptions="{'warn_days': 3}" devient la prop warnDays
fieldDependenciesChamps que le client web doit charger en plus, même si la vue ne les affiche passtate, pour reconnaître un emprunt rendu

Quand extractProps rend warnDays: undefined (vue sans option), c'est la valeur par défaut de useProps qui s'applique.

Le champ voisin qui n'arrive pas

Le widget lit this.props.record.data.state, mais le client web ne charge que les champs présents dans la vue. La liste des emprunts a une colonne État, la carte non. Sans fieldDependencies (essai : la ligne mise en commentaire), la carte de l'emprunt rendu affiche « 6 j de retard ». Pourtant, cette carte est rangée dans la colonne « Rendu » du regroupement par état. Le regroupement ne remplit pas record.data.state. Aucun message, aucune erreur : seulement un mauvais badge.

La règle : tout champ lu par le widget, autre que le sien, se déclare dans fieldDependencies avec son nom et son type. C'est ce que fait le widget de signature d'Odoo 20 pour write_date.

4. Brancher : le manifeste et deux lignes de vue

Le client web ne charge un fichier JavaScript ou un gabarit que s'il est déclaré dans un bundle (paquet de fichiers servi au navigateur). Le back-office, c'est web.assets_backend. Le second bundle, web.assets_unit_tests, sert au test de l'étape 5. Dans __manifest__.py, la version passe à 20.0.1.19.0 et une section assets apparaît :

    'assets': {
        'web.assets_backend': [
            'biblio/static/src/late_badge/late_badge_field.js',
            'biblio/static/src/late_badge/late_badge_field.xml',
        ],
        'web.assets_unit_tests': [
            'biblio/static/tests/**/*',
        ],
    },

Côté vues, l'échéance de la liste reçoit le widget avec son option. Dans la carte, le badge QWeb maison et sa branche t-else disparaissent au profit du même widget, sans option :

<!-- views/library_loan_views.xml, vue liste -->
<field name="date_due" widget="late_badge" options="{'warn_days': 3}"/>

<!-- même fichier, vue carte (pied de carte) -->
<field name="date_due" widget="late_badge"/>

Il reste à mettre à jour le module (bouton Mettre à jour dans Applications, ou option -u biblio d'odoo-bin). La mise à jour s'est faite sans aucun avertissement dans le journal. Sur le jeu d'essai, le 8 novembre, la liste donne les quatre états :

La vue carte affiche les mêmes badges, sans option dans la vue : le seuil de 3 jours est celui de useProps, et l'état « Rendu » arrive par fieldDependencies.

Le serveur garde en cache les bundles déjà construits. Pendant qu'on modifie le JavaScript, il vaut mieux travailler avec ?debug=assets dans l'adresse. Pendant l'essai, sans ce paramètre, une modification du fichier n'était pas reprise par le serveur déjà lancé.

5. Tester avec Hoot : une vraie vue, une date figée

Le badge dépend de la date du jour. Le tester à la main oblige à fabriquer des emprunts aux bonnes dates. Hoot, le lanceur de tests JavaScript d'Odoo 20, monte une vue réelle sur des données simulées, à une date imposée par mockDate :

import { expect, test } from "@odoo/hoot";
import { queryAllTexts } from "@odoo/hoot-dom";
import { mockDate } from "@odoo/hoot-mock";
import { defineMailModels } from "@mail/../tests/mail_test_helpers";
import {
    defineModels,
    fields,
    models,
    mountView,
} from "@web/../tests/web_test_helpers";

class LibraryLoan extends models.Model {
    _name = "library.loan";
    date_due = fields.Date({ string: "À rendre le" });
    state = fields.Selection({
        selection: [
            ["ongoing", "En cours"],
            ["returned", "Rendu"],
        ],
    });
    _records = [
        { id: 1, date_due: "2026-11-21", state: "ongoing" },
        { id: 2, date_due: "2026-11-10", state: "ongoing" },
        { id: 3, date_due: "2026-11-05", state: "ongoing" },
        { id: 4, date_due: "2026-11-02", state: "returned" },
        { id: 5, date_due: false, state: "ongoing" },
    ];
}

defineMailModels(); // biblio dépend de mail : ses services veulent ses modèles
defineModels([LibraryLoan]);

test("le badge suit l'échéance et l'état, sans colonne state dans la vue", async () => {
    mockDate("2026-11-08 10:00:00");
    await mountView({
        type: "list",
        resModel: "library.loan",
        arch: `<list><field name="date_due" widget="late_badge"/></list>`,
    });
    expect(".o_late_badge").toHaveCount(4);
    expect(queryAllTexts(".o_late_badge")).toEqual([
        "Nov 21",
        "À rendre dans 2 j",
        "3 j de retard",
        "Rendu",
    ]);
    expect(".o_late_badge.text-bg-danger").toHaveCount(1);
});

test("l'option warn_days élargit la fenêtre d'alerte", async () => {
    mockDate("2026-11-08 10:00:00");
    await mountView({
        type: "list",
        resModel: "library.loan",
        arch: `<list><field name="date_due" widget="late_badge" options="{'warn_days': 15}"/></list>`,
    });
    expect(queryAllTexts(".o_late_badge")).toEqual([
        "À rendre dans 13 j",
        "À rendre dans 2 j",
        "3 j de retard",
        "Rendu",
    ]);
});
  • Le modèle simulé déclare seulement les champs utiles. La vue du premier test n'a pas de colonne state : le test vérifie donc aussi fieldDependencies.
  • defineMailModels() plutôt que defineWebModels() : biblio dépend de mail, et les services de mail démarrent avec le client web simulé. Avec defineWebModels() seul, les deux tests échouent sur « Cannot find a definition for model "discuss.channel" ».
  • La date attendue est "Nov 21" et non « 21 nov. » : les tests formatent les dates à l'anglaise.

Les tests se lancent dans le navigateur, connecté à la base, avec un filtre sur le module :

http://localhost:8069/web/tests?debug=assets&filter=%22%40biblio%22

Le filtre compte : sans les guillemets, Hoot a lancé une grande partie des suites des autres modules, dont des tests sans rapport en échec sur cette base. Le test attrape bien l'oubli décrit plus haut : quand on retire fieldDependencies, les deux tests passent au rouge, avec « 6 j de retard » reçu à la place de « Rendu ».

6. Traduire les libellés du widget

Les chaînes passées à _t() dans le JavaScript s'exportent avec le reste du module, marquées odoo-javascript. Une fois le fichier i18n/biblio.pot régénéré, on y trouve par exemple :

#. module: biblio
#. odoo-javascript
#: code:addons/biblio/static/src/late_badge/late_badge_field.js:0
msgid "%s j de retard"
msgstr ""

Le libellé « Rendu » existait déjà comme valeur de l'état : l'export ajoute la référence JavaScript à l'entrée existante, sans la dupliquer. La méthode (régénérer le .pot, puis compléter les .po) est celle de Traduire un module en Odoo 20. Tenir le .pot à jour compte : à l'import d'un .po, Odoo écarte toute traduction dont la source n'y figure pas.

Venant de la 19 : trois réflexes à perdre

En 19, un widget déclarait static props = { ...standardFieldProps, warnDays: { type: Number, optional: true } } et static defaultProps = { warnDays: 3 }. Les deux ont été essayés sur ce widget en Odoo 20 :

  • static defaultProps : erreur au premier affichage, et la fenêtre « Oups ! » remplace la liste. La console donne la marche à suivre : Component "LateBadgeField" defines a static "defaultProps", which Owl 3 ignores. Declare the defaults through the props schema instead, e.g. "props = useProps({ someProp: t.string().optional(defaultValue) })".
  • static props seul : aucune erreur, aucune validation, et pas de valeur par défaut. Sur les cartes, sans option dans la vue, l'emprunt à rendre dans 2 jours s'affiche « 10 nov. » en vert au lieu de « À rendre dans 2 j » en orange.
  • Le gabarit sans this. : badges vides, sans erreur (étape 2).

Les autres changements tiennent au client web : standardFieldProps est écrit en types t (19 : { type: String }), et le widget natif remaining_days s'appelle relative_date.

À retenir

  • Un widget de champ, c'est un composant OWL 3 et un descripteur enregistré dans le registre fields. La vue l'appelle par son nom : widget="late_badge".
  • En Odoo 20, les props se déclarent par useProps() avec les types t, et la valeur par défaut se passe à optional(). static defaultProps lève une erreur ; static props est ignoré sans erreur : ni validation, ni valeur par défaut.
  • Dans le gabarit, this. devant chaque membre du composant. Sans lui, l'affichage est vide et aucune erreur ne s'affiche.
  • Un champ lu par le widget qui n'est pas le sien se déclare dans fieldDependencies, sinon il manque dès qu'une vue ne l'affiche pas.
  • Un test Hoot à date figée (mockDate) vérifie les cas limites en quelques secondes. Lancé avec filter="@biblio", il ne lance que la suite du module.
