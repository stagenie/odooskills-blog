Action contextuelle Odoo 20 : une entrée dans le menu Actions

Tu coches quelques lignes d'une liste, tu ouvres le menu Actions et ton traitement est là, à côté d'Exporter et d'Archiver. En Odoo 20, il suffit d'une action serveur avec binding_model_id. Exemple complet sur les contacts de la démo, rejoué de bout en bout.

~5 minutes de lecture · niveau intermédiaire · série Astuces dev Odoo 20

Édition : Community. Vérifié sur Odoo 20.0 Community, octobre 2026, base de démonstration (Ventes installé) et module d'exemple.

La réponse en bref

  1. Écris la méthode métier sur le modèle (def action_…(self)) : elle reçoit les lignes cochées.
  2. Déclare en XML un ir.actions.server avec model_id, binding_model_id (le même modèle), state="code" et le code action = records.action_…().
  3. Ajoute binding_view_types="list" pour la réserver à la liste (défaut : liste et formulaire).
  4. -u ton_module, recharge la page, coche des lignes : l'entrée est dans Actions.

1. La méthode : le travail sur les lignes cochées

Le cas d'école : sur la liste des clients, cocher plusieurs sociétés et leur poser d'un clic l'étiquette « À relancer ». Le traitement va dans une méthode du modèle, que tu peux tester et réutiliser ailleurs (un bouton, une tâche planifiée) :

# mon_module/models/res_partner.py
from odoo import models
from odoo.fields import Command


class ResPartner(models.Model):
    _inherit = 'res.partner'

    def action_etiqueter_a_relancer(self):
        tag = self.env.ref('mon_module.categ_a_relancer')
        self.write({'category_id': [Command.link(tag.id)]})
        return {
            'type': 'ir.actions.client',
            'tag': 'display_notification',
            'params': {
                'message': f"{len(self)} contact(s) étiqueté(s) « À relancer ».",
                'type': 'success',
                'next': {'type': 'ir.actions.client', 'tag': 'soft_reload'},
            },
        }

self contient toutes les lignes cochées : un seul write pour le lot. La valeur renvoyée est une action que le client web exécute ensuite : ici une notification verte, puis soft_reload, qui recharge la liste pour faire apparaître la nouvelle étiquette.

2. L'action serveur liée au modèle

Le branchement dans le menu se fait en données, dans un fichier XML déclaré dans data du manifeste :

<!-- mon_module/data/res_partner_actions.xml -->
<odoo>
    <record id="categ_a_relancer" model="res.partner.category">
        <field name="name">À relancer</field>
    </record>

    <record id="action_etiqueter_a_relancer" model="ir.actions.server">
        <field name="name">Étiqueter « À relancer »</field>
        <field name="model_id" ref="base.model_res_partner"/>
        <field name="binding_model_id" ref="base.model_res_partner"/>
        <field name="binding_view_types">list</field>
        <field name="state">code</field>
        <field name="code">action = records.action_etiqueter_a_relancer()</field>
    </record>
</odoo>
ChampRôle
model_idle modèle sur lequel le code s'exécute (records en sera un recordset)
binding_model_idle modèle dont les vues affichent l'entrée : c'est lui qui crée l'action contextuelle
binding_view_typeslist, form ou list,form (valeur par défaut)
state + code« Exécuter le code » : le Python évalué, où records = les lignes cochées

Le code d'une action de type code tourne une seule fois pour toute la sélection, pas une fois par ligne : la notification annonce bien « 2 contact(s) » pour deux lignes cochées. Et si le code affecte une variable action, elle est renvoyée au navigateur, d'où action = records.…().

3. Liste, formulaire, groupe : vérifier en console

Avec binding_view_types à list, la fiche d'un contact n'affiche pas l'entrée dans son menu Actions. Pour limiter l'action à certains utilisateurs, renseigne group_ids dans le même enregistrement :

<field name="group_ids" eval="[Command.link(ref('base.group_system'))]"/>

Ce script, passé à odoo-bin shell, interroge les deux mécanismes : la barre d'outils que le serveur envoie avec chaque vue, et get_bindings, qui filtre les actions pour un utilisateur donné. Le groupe y est posé en console pour l'essai, puis annulé :

# verifier_action.py
NOM = 'Étiqueter « À relancer »'
vues = env['res.partner'].get_views([(False, 'list'), (False, 'form')], {'toolbar': True})
for vt in ('list', 'form'):
    noms = [a['name'] for a in vues['views'][vt]['toolbar'].get('action', [])]
    print(vt, '->', NOM in noms)

act = env.ref('mon_module.action_etiqueter_a_relancer')
act.group_ids = env.ref('base.group_system')
for user in (env.ref('base.user_admin'), env.ref('base.user_demo')):
    noms = [a['name'] for a in env['ir.actions.actions'].with_user(user).get_bindings('res.partner')['action']]
    print(user.name, '->', NOM in noms)
env.cr.rollback()

Même déclaration dans le fichier XML, puis -u : le résultat est identique (Marc Demo ne la voit plus). Et si un utilisateur hors du groupe appelle quand même l'action, le serveur refuse : AccessError: You don't have enough access rights to run this action.

4. La même chose depuis l'interface

En mode développeur, Paramètres > Technique > Actions > Actions de serveur liste toutes les actions serveur, dont celle du module. Sur une action créée à la main, le bouton Créer une action contextuelle remplit binding_model_id avec le modèle de l'action ; une fois liée, le bouton devient Supprimer une action contextuelle. Le champ Groupes autorisés est le group_ids vu plus haut.

Pratique pour un essai, mais une action créée ainsi vit dans la base seulement : pour un traitement qui doit suivre tes déploiements, garde le XML du module. Ce formulaire n'affiche pas binding_view_types : pour une entrée « liste seulement », passe par le XML.

Le même binding_model_id fonctionne sur une fenêtre (ir.actions.act_window en target="new") pour ouvrir un assistant sur la sélection, et sur un rapport, qui rejoint alors le menu Imprimer au lieu d'Actions.

Visible dans le menu ne veut pas dire exécutable

Sans group_ids, Odoo exige au lancement le droit d'écriture sur le modèle et sur chacune des lignes cochées. Essai avec un utilisateur interne de base : l'entrée figure bien dans son menu, mais l'exécution sur une société de la démo lève AccessError et le journal note Forbidden server action 'Étiqueter « À relancer »' executed while the user … does not have access to res.partner(…). Avec group_ids, c'est l'appartenance au groupe qui est contrôlée à la place : réserve donc l'action au bon groupe plutôt que de laisser le refus tomber au clic.

À retenir

  • Une action contextuelle = une action dont binding_model_id est rempli ; le menu Actions d'une liste n'apparaît qu'avec des lignes cochées.
  • Action serveur de type code : records = la sélection, code exécuté une fois, variable action renvoyée au navigateur.
  • binding_view_types choisit liste et/ou formulaire ; group_ids masque l'entrée et contrôle le lancement.
  • Sans groupe, le lancement exige le droit d'écriture sur les lignes cochées.
