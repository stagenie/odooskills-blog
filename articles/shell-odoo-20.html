Le shell Odoo 20 : explorer et corriger une base avec odoo-bin shell

odoo-bin shell ouvre une console Python branchée sur une base Odoo : tout l'ORM sous la main, sans navigateur. C'est l'outil le plus rapide pour vérifier une donnée, corriger un enregistrement ou installer un module. C'est aussi le plus traître : rien n'est écrit sans commit, sauf quand tout l'est d'un coup. Les pièges, un par un, sur la démonstration native.

~12 minutes de lecture · niveau intermédiaire · parcours Framework & ORM

Ce que tu vas apprendre

Lancer

La console interactive ou un script passé par <, les options utiles, ce que contiennent env et self.

Lire, écrire, valider

search, browse, read, puis env.cr.commit() et env.cr.rollback(), et installer un module depuis la console.

Éviter les pièges

Le superutilisateur, l'installation qui valide tout, l'instantané de lecture, la transaction avortée, la tâche planifiée qui bloque.

Prérequis

  • Odoo 20 installé depuis les sources, avec son fichier de configuration : installer Odoo 20 sur Ubuntu.
  • Une base de test avec les données de démonstration, Ventes et Inventaire installés. Les exemples lisent des commandes et des contacts de la démo (Acme Corporation, Gemini Furniture…), tu peux les rejouer tels quels.
  • Jamais sur une base de production pour apprendre : la console écrit avec tous les droits.

1. Lancer la console

La sous-commande shell prend les mêmes options que le serveur. Trois suffisent :

./odoo-bin shell -c odoo.conf -d ma_base --no-http --log-level=warn
OptionPourquoi
-c odoo.confLe même fichier que le serveur : chemin des modules, connexion PostgreSQL. Sans lui, la console ne trouve ni tes modules ni ta base.
-d ma_baseLa base à ouvrir. Oubliée (et absente du fichier de configuration), la console démarre quand même, mais sans env : elle affiche No environment set, use `./odoo-bin shell -d dbname` to get one.
--no-httpInterdit d'ouvrir le port HTTP. Sans elle, si le fichier de configuration a workers > 0 (cas d'un serveur de production), la console tente d'ouvrir le port du serveur qui tourne et s'arrête sur OSError: [Errno 98] Adresse déjà utilisée. Avec workers = 0, le port n'est pas ouvert de toute façon : mets l'option toujours, elle ne coûte rien.
--log-level=warnCoupe la quinzaine de lignes INFO du démarrage (chargement des modules, du registre). Le journal sort sur la sortie d'erreur, tes print() sur la sortie standard : 2>/dev/null fait le même tri.

Lancée dans un terminal, la console liste ses variables puis donne l'invite Python :

Deux options de confort :

  • --shell-file=raccourcis.py exécute un fichier au démarrage de la session interactive (il prime sur la variable PYTHONSTARTUP). Pratique pour retrouver tes raccourcis :
# raccourcis.py
Partner = env['res.partner']
SO = env['sale.order']
acme = Partner.search([('name', '=', 'Acme Corporation')])
>>> acme, SO.search_count([]) (res.partner(10,), 24)
  • --shell-interface=ipython (ou ptpython, bpython) choisit une console plus confortable, à condition que le paquet soit installé dans l'environnement Python d'Odoo. Sinon, Odoo retombe sur la console Python standard sans le moindre message : l'erreur d'import est avalée (odoo/cli/shell.py). Si l'invite reste >>>, c'est que pip install ipython manque dans ce venv.

Le message « AutoReload watcher running »

Si ton fichier de configuration contient dev_mode = reload, la console démarre aussi le surveillant de fichiers et écrit au journal « AutoReload watcher running with inotify » puis « Initiating shutdown ». Ce n'est pas une erreur : le serveur intégré s'arrête aussitôt et laisse la place à la console. --log-level=warn le fait taire.

Piège n°1 : tu es superutilisateur

env.su vaut True : aucun droit d'accès, aucune restriction ne s'applique. Un « ça marche dans la console » ne prouve donc rien pour un utilisateur réel. Pour vérifier ce que voit un vendeur, change d'utilisateur :

demo = env.ref('base.user_demo')
Param = env['ir.config_parameter']
print("superutilisateur :", Param.search_count([]))
try:
    print("Marc Demo :", Param.with_user(demo).search_count([]))
except Exception as e:
    print(type(e).__name__, "|", str(e).splitlines()[0])
SO = env['sale.order']
print(SO.with_user(demo).has_access('unlink'), SO.has_access('unlink'))

3. Lire : un script passé par <

Taper ligne à ligne convient pour une question rapide. Dès que la vérification fait plus de trois lignes, écris-la dans un fichier et donne-le à la console par l'entrée standard. Un fichier lire.py sur les commandes de vente de la démo :

SO = env['sale.order']
print(SO.search_count([]), SO.search_count([('state', '=', 'sale')]))
orders = SO.search([('state', '=', 'sale')], order='amount_total desc', limit=3)
for o in orders:
    print(o.name, '|', o.partner_id.name, '|', o.amount_total, o.currency_id.name, '|', len(o.order_line), 'lignes')
print(orders[0].order_line.mapped('product_id.display_name'))
print(orders[0].read(['name', 'state', 'date_order']))
print(SO.browse(999999).exists())
./odoo-bin shell -c odoo.conf -d ma_base --no-http --log-level=warn < lire.py
  • search() rend un recordset ; on lit ses champs par attribut, et les champs relationnels se suivent (o.partner_id.name) sans écrire de jointure.
  • mapped('product_id.display_name') parcourt un chemin sur toutes les lignes d'un coup.
  • read() rend des dictionnaires, utile pour voir les valeurs brutes.
  • browse(999999) ne vérifie rien : il fabrique un recordset sur cet identifiant. exists() filtre ce qui existe vraiment en base, ici rien.

Piège n°2 : sans print(), rien ne s'affiche

Avec une entrée redirigée, la console ne lance pas d'invite interactive : elle lit tout le fichier et l'exécute comme un module Python (exec). Une expression seule n'est donc jamais affichée :

echo "env['res.partner'].search_count([])" | ./odoo-bin shell -c odoo.conf -d ma_base --no-http --log-level=warn
echo "print(env['res.partner'].search_count([]))" | ./odoo-bin shell -c odoo.conf -d ma_base --no-http --log-level=warn
43

La première commande n'affiche rien, la seconde 43. Même règle : --shell-file est ignoré dans ce mode. Si le script lève une exception, la console affiche la trace et sort avec le code 1, ce qui permet de l'enchaîner dans un script shell.

4. Écrire, puis valider : env.cr.commit()

Écrire se fait comme dans un module : on affecte le champ, ou on appelle write(). Le script ecrit.py pose une référence interne sur le contact Acme Corporation :

acme = env['res.partner'].search([('name', '=', 'Acme Corporation')])
print("avant :", acme.ref)
acme.ref = "CLI-0042"
print("après :", acme.ref)

La session affiche bien la nouvelle valeur. Puis un second script, relit.py, relit le contact dans un nouveau processus, et la référence n'y est pas. Il faut ajouter env.cr.commit() pour qu'elle soit écrite :

acme = env['res.partner'].search([('name', '=', 'Acme Corporation')])
acme.ref = "CLI-0042"
env.cr.commit()
print("validé :", acme.ref)

La console ouvre une transaction et ne la valide jamais d'elle-même : elle l'annule (cr.rollback()) juste avant de te donner la main et juste après que tu l'as rendue, que tu quittes par Ctrl+D ou que ton script se termine (odoo/cli/shell.py). C'est une sécurité : tu peux tout essayer, rien ne reste. Les deux commandes à retenir :

CommandeEffet
env.cr.commit()Écrit en base tout ce qui a été fait depuis le dernier commit ou rollback. Définitif.
env.cr.rollback()Annule tout ce qui n'a pas été validé, et ouvre une nouvelle transaction.
with env.cr.savepoint():Un point de reprise : si le bloc lève une exception, seul ce bloc est annulé (section 7).

La bonne habitude pour une correction : faire, relire, puis seulement valider. Tant que le commit n'est pas passé, un rollback rattrape tout.

5. Installer et désinstaller un module depuis la console

Un module est un enregistrement de ir.module.module. Le bouton « Activer » de l'écran Applications appelle button_immediate_install() ; la console peut faire de même. Avec le module des dates d'expiration, product_expiry :

Module = env['ir.module.module']
avant = set(Module.search([('state', '=', 'installed')]).mapped('name'))
Module.search([('name', '=', 'product_expiry')]).button_immediate_install()
apres = set(Module.search([('state', '=', 'installed')]).mapped('name'))
print("installés :", sorted(apres - avant))
print('use_expiration_date' in env['product.template']._fields)
installés : ['product_expiry', 'sale_stock_product_expiry'] True
  • Les dépendances et les modules d'auto-installation suivent : ici le pont sale_stock_product_expiry, puisque Ventes et Inventaire sont déjà là.
  • Odoo recharge le registre : dans la même session, product.template connaît déjà le nouveau champ.
  • Désinstaller, c'est button_immediate_uninstall() sur le même enregistrement ; les modules qui en dépendent partent avec :
Module = env['ir.module.module']
avant = set(Module.search([('state', '=', 'installed')]).mapped('name'))
Module.search([('name', '=', 'product_expiry')]).button_immediate_uninstall()
apres = set(Module.search([('state', '=', 'installed')]).mapped('name'))
print("désinstallés :", sorted(avant - apres))
print('use_expiration_date' in env['product.template']._fields)
désinstallés : ['product_expiry', 'sale_stock_product_expiry'] False

Sans le mot immediate, button_install() ne fait que marquer le module : son état passe à 'to install', aucun modèle n'est créé ('stock.landed.cost' in env reste False pour stock_landed_costs), et l'installation attend le prochain démarrage avec mise à jour.

Piège n°3 : l'installation valide toute ta transaction

Avant d'installer, button_immediate_install() appelle lui-même self.env.cr.commit(), puis recharge le registre (odoo/addons/base/models/ir_module.py, _button_immediate_function). Tout ce que la session avait écrit sans le valider part en base avec lui, et le rollback qui suit n'annule plus rien :

acme = env['res.partner'].search([('name', '=', 'Acme Corporation')])
acme.ref = "BROUILLON-7"        # un essai, jamais validé

env['ir.module.module'].search([('name', '=', 'product_expiry')]).button_immediate_install()

env.cr.rollback()               # on croit tout annuler…
print("après rollback :", acme.ref)

Règle simple : installer ou désinstaller dans une session propre, juste après un commit ou un rollback volontaire. Même chose pour button_immediate_upgrade(), qui passe par la même fonction.

Pour un déploiement, la ligne de commande reste la voie normale : les options -i et -u avec --stop-after-init, ou la sous-commande odoo-bin module. Elles font l'objet d'un article à part de la série. La console sert quand tu es déjà dedans et veux enchaîner : installer, puis vérifier aussitôt le résultat en Python.

6. La console ne voit pas les écritures des autres

Odoo ouvre ses connexions PostgreSQL en isolation REPEATABLE READ (odoo/sql_db.py) : dès sa première requête, une transaction lit un instantané figé de la base. Ce qu'un utilisateur valide dans le navigateur pendant ce temps reste invisible à la console. Pour le montrer, le script simule cet utilisateur avec une seconde connexion, validée à la sortie du bloc with :

acme = env['res.partner'].search([('name', '=', 'Acme Corporation')])
print("lu par la session :", acme.ref)

# une autre connexion écrit et valide (comme le navigateur ou un second shell)
with env.registry.cursor() as autre_cr:
    autre_cr.execute("UPDATE res_partner SET ref = 'WEB-0007' WHERE id = %s", [acme.id])

env.invalidate_all()
print("après invalidate_all :", acme.ref)
env.cr.rollback()
print("après rollback :", acme.ref)
lu par la session : False après invalidate_all : False après rollback : WEB-0007

Vider le cache de l'ORM (invalidate_all()) ne suffit pas : Odoo relit bien la base, mais dans le même instantané. Seule une nouvelle transaction, après rollback() ou commit(), voit la nouvelle valeur. Dans une session interactive qui dure, fais un env.cr.rollback() avant de relire une donnée que quelqu'un a pu changer entre-temps.

7. Après une erreur SQL, la transaction est morte

Dans la console interactive, une exception ne ferme pas la session : tu gardes la main. Mais si l'erreur vient de PostgreSQL (clé étrangère, contrainte d'unicité…), la transaction entière est perdue et toutes les requêtes suivantes échouent :

P = env['res.partner']
try:
    P.create({'name': "Contact test", 'country_id': 999999})
    env.flush_all()
except Exception as e:
    print(type(e).__name__, "|", str(e).splitlines()[0])
try:
    print(P.search_count([]))
except Exception as e:
    print(type(e).__name__, "|", str(e).splitlines()[0])
env.cr.rollback()
print(P.search_count([]))
ForeignKeyViolation | insert or update on table "res_partner" violates foreign key constraint "res_partner_country_id_fkey" InFailedSqlTransaction | current transaction is aborted, commands ignored until end of transaction block 43

Le message current transaction is aborted ne désigne pas la requête fautive mais la suivante : la vraie cause est plus haut. Le remède, env.cr.rollback(), efface aussi tes écritures non validées. Pour tenter une opération risquée sans tout perdre, entoure-la d'un point de reprise :

P = env['res.partner']
try:
    with env.cr.savepoint():
        P.create({'name': "Contact test", 'country_id': 999999})
except Exception as e:
    print(type(e).__name__)
print(P.search_count([]))
ForeignKeyViolation 43

Seul le bloc est annulé, la session continue sans rollback.

8. Lancer une tâche planifiée depuis la console

method_direct_trigger() est la méthode du bouton « Exécuter manuellement » d'une action planifiée (ir.cron). Elle n'exécute pas la tâche dans ta transaction : elle ouvre un nouveau curseur, comme le ferait le planificateur (odoo/addons/base/models/ir_cron.py). Deux conséquences.

Pour l'essai, une tâche dont le code écrit la référence d'Acme Corporation, créée et validée depuis la console (la tâche, lancée dans une autre transaction, doit pouvoir la lire) :

acme = env['res.partner'].search([('name', '=', 'Acme Corporation')])
cron = env['ir.cron'].create({
    'name': "Sonde shell : référence Acme",
    'model_id': env.ref('base.model_res_partner').id,
    'state': 'code',
    'code': f"env['res.partner'].browse({acme.id}).write({{'ref': 'CRON-0001'}})",
    'interval_number': 1, 'interval_type': 'days',
})
env.cr.commit()

Le résultat t'est invisible. Dans une nouvelle session :

acme = env['res.partner'].search([('name', '=', 'Acme Corporation')])
cron = env['ir.cron'].search([('name', '=', "Sonde shell : référence Acme")])
print("avant :", acme.ref)
cron.method_direct_trigger()
print("après la tâche :", acme.ref)
env.cr.rollback()
print("après rollback :", acme.ref)
avant : False après la tâche : False après rollback : CRON-0001

C'est l'instantané de la section 6 : la tâche a validé dans sa propre transaction, la tienne ne le voit qu'après un rollback.

Piège n°4 : la console qui se fige

Si ta session a modifié sans les valider les enregistrements que la tâche va écrire (ici, acme.ref = "LOCAL-0001" juste avant method_direct_trigger()), la tâche attend que ta transaction libère la ligne, et ta transaction attend la fin de la tâche. La console ne rend jamais la main. Vu depuis PostgreSQL :

SELECT pid, state, wait_event_type, left(regexp_replace(query, '\s+', ' ', 'g'), 45) AS requete
  FROM pg_stat_activity
 WHERE datname = current_database() AND pid <> pg_backend_pid();
pid | state | wait_event_type | requete --------+---------------------+-----------------+----------------------------------------------- 865523 | idle in transaction | Client | DELETE FROM ir_cron_trigger WHERE cron_id = 865524 | active | Lock | UPDATE "res_partner" SET "ref" = "__tmp"."re

La connexion de la console est « idle in transaction », celle de la tâche attend un verrou (Lock). Un signal d'interruption n'y change rien : il a fallu tuer le processus. La parade : env.cr.commit() (ou rollback()) avant de déclencher une tâche.

Récapitulatif

  • odoo-bin shell donne env et self sur une base, en superutilisateur : les droits ne s'y appliquent pas, with_user() les rétablit.
  • Un script passé par < s'exécute d'une traite ; seuls les print() s'affichent.
  • La console annule tout à l'entrée et à la sortie : sans env.cr.commit(), rien n'est écrit.
  • button_immediate_install() installe un module depuis la console, mais valide au passage tout ce qui traînait dans la transaction.
  • La session lit un instantané figé : rollback() pour voir les écritures des autres, celles d'une tâche planifiée comprises.
  • Après une erreur SQL, la transaction est perdue jusqu'au rollback() ; un savepoint() limite les dégâts.
