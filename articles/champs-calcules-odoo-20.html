Champs calculés Odoo 20 : store, inverse, search, « failed to assign »

Un compute qui marche, puis tout ce qui le fait échouer : la branche oubliée qui lève Compute method failed to assign, la dépendance manquante qui laisse une valeur périmée, le champ qu'on ne peut ni écrire ni chercher. Chaque cas a été exécuté sur la démo d'Odoo 20, avec un petit module sur les commandes de vente.

~13 minutes de lecture · niveau intermédiaire · parcours Framework & ORM

Ce que tu vas apprendre

Calculer, stocker

compute et @api.depends, ce que change store=True et pourquoi la méthode reçoit plusieurs enregistrements.

« failed to assign »

Le message exact, quand il apparaît, quand il n'apparaît pas (et c'est pire), et le correctif.

Écrire, chercher

inverse, search, puis compute_sudo, precompute, recursive et @api.depends_context.

Prérequis

  • Une base Odoo 20 Community avec Ventes et les données de démonstration, en français : le devis S00003 (deux lignes, 11 unités) et le client « Acme Corporation » viennent de là.
  • Un module demo_calcules qui dépend de sale_management et hérite de sale.order ; son code est donné section par section. Les champs se déclarent en Python, il faut donc un module : pas de raccourci par la console.
  • La console ./odoo-bin shell -c odoo.conf -d ma_base pour les essais (présentée dans l'article sur le shell Odoo 20). Les séries qui écrivent finissent par env.cr.rollback().

1. Le calcul minimal : compute et @api.depends

Un champ calculé est un champ ordinaire auquel on donne le nom d'une méthode. La méthode reçoit un recordset et doit affecter le champ sur chaque enregistrement ; elle ne renvoie rien. @api.depends liste les champs dont la valeur dépend :

# demo_calcules/models/sale_order.py
from odoo import api, fields, models


class SaleOrder(models.Model):
    _inherit = 'sale.order'

    line_count = fields.Integer("Nombre de lignes", compute='_compute_line_count')

    @api.depends('order_line')
    def _compute_line_count(self):
        for order in self:
            order.line_count = len(order.order_line)
order = env['sale.order'].search([('name', '=', 'S00003')])
print(order.line_count, len(order.order_line))
2 2

Sans autre attribut, le champ n'est pas stocké : aucune colonne en base, la valeur est calculée à la lecture puis gardée en cache jusqu'à ce qu'une dépendance change. Il est en lecture seule, n'est pas recopié par copy, et ne se cherche pas (section 5).

2. store=True : une colonne, recalculée quand une dépendance change

Avec store=True, la valeur est écrite dans une colonne de sale_order : on peut la chercher, la trier, la grouper. Odoo la recalcule quand un champ de @api.depends est modifié, y compris à travers une relation (order_line.product_uom_qty). Le print sert à voir sur quels enregistrements la méthode est appelée :

    total_qty = fields.Float("Quantité totale", compute='_compute_total_qty', store=True)

    @api.depends('order_line.product_uom_qty')
    def _compute_total_qty(self):
        print("_compute_total_qty sur", self)   # trace, à retirer ensuite
        for order in self:
            order.total_qty = sum(order.order_line.mapped('product_uom_qty'))

À l'installation du module, la colonne est créée puis remplie pour toutes les commandes existantes, en un seul appel :

_compute_total_qty sur sale.order(16, 12, 10, 18, 17, 15, 14, 13, 11, 9, 4, 8, 7, 6, 20, 19, 3, 2, 21, 22, 23, 24, 5, 1)

Ensuite, seules les commandes touchées sont recalculées, et seulement quand on relit le champ (ou au prochain flush) :

SO = env['sale.order']
order = SO.search([('name', '=', 'S00003')])
print(order.total_qty)
order.order_line[0].product_uom_qty = 12
print(order.total_qty)
drafts = SO.search([('state', '=', 'draft')])
drafts.order_line.write({'product_uom_qty': 2})
print(drafts.mapped('total_qty'))
for name in ('line_count', 'total_qty'):
    f = SO._fields[name]
    print(name, f.store, f.readonly, f.compute_sudo, f.copy)
env.cr.rollback()
11.0 _compute_total_qty sur sale.order(3,) 13.0 _compute_total_qty sur sale.order(3, 5, 2, 1) [4.0, 2.0, 4.0, 6.0] line_count False True False False total_qty True True True False

Deux leçons. Le write sur les lignes de quatre devis déclenche un appel avec les quatre commandes : c'est pour cela qu'une méthode de calcul boucle toujours sur self et ne suppose jamais un seul enregistrement (pas de self.ensure_one(), pas de self.total_qty = … hors de la boucle). Et la dernière ligne montre les défauts : un champ stocké est calculé en superutilisateur (compute_sudo=True), un champ non stocké avec les droits de l'utilisateur (compute_sudo=False), règle posée dans odoo/orm/fields.py (compute_sudo vaut store par défaut).

3. « Compute method failed to assign » : la branche oubliée

Un champ qui classe les commandes selon la quantité totale. Il manque un cas : la commande sans ligne, dont la quantité vaut 0.

    size_label = fields.Char("Taille", compute='_compute_size_label')

    @api.depends('total_qty')
    def _compute_size_label(self):
        for order in self:
            if order.total_qty >= 10:
                order.size_label = "grosse"
            elif order.total_qty > 0:
                order.size_label = "petite"

Sur S00003 (11 unités), tout va bien. Sur une commande neuve, sans ligne, le script taille.py suivant échoue à la cinquième ligne :

SO = env['sale.order']
acme = env['res.partner'].search([('name', '=', "Acme Corporation")])
order = SO.create({'partner_id': acme.id})
print(order.name, order.total_qty)
print(order.size_label)

Le message est ValueError: Compute method failed to assign sale.order(36,).size_label : la méthode a été appelée sur la commande 36 et n'a rien affecté à size_label. Odoo s'en aperçoit après l'appel, en lisant le cache, d'où un traceback qui ne passe pas par _compute_size_label. Pour trouver la branche fautive, cherche dans la méthode le chemin qui ne contient pas d'affectation : un if/elif sans else, un continue, un return au milieu de la boucle, ou une boucle sur un autre recordset que self.

Le correctif : affecter dans tous les cas.

            elif order.total_qty > 0:
                order.size_label = "petite"
            else:
                order.size_label = False
_compute_total_qty sur sale.order(39,) S00039 0.0 False

Variante tout aussi sûre : poser la valeur par défaut avant le if (order.size_label = False), puis la remplacer.

Quand l'erreur ne se produit pas

L'erreur n'est levée que pour un champ non stocké et en lecture seule (test if self.readonly and not self.store dans Field.__get__). La même méthode sans branche else, posée sur un champ stocké ou sur un champ modifiable, ne dit rien :

    size_label_stored = fields.Char(compute='_compute_size_label_stored', store=True)
    size_label_rw = fields.Char(compute='_compute_size_label_rw', readonly=False)
    # même corps que _compute_size_label, sans else
order = SO.create({'partner_id': acme.id})
print("stocké :", repr(order.size_label_stored), "| modifiable :", repr(order.size_label_rw))
env.cr.rollback()
_compute_total_qty sur sale.order(37,) stocké : False | modifiable : False
Champ calculéBranche sans affectation
non stocké, lecture seule (le cas par défaut)ValueError: Compute method failed to assign …
store=Trueaucune erreur, la valeur devient False
readonly=False ou avec inverseaucune erreur, la valeur devient False

Le silence n'est pas une bonne nouvelle : un champ stocké qui reste à False sur une partie des enregistrements passe les tests et se remarque des semaines plus tard dans un rapport. La règle « une affectation par enregistrement, dans tous les cas » vaut pour tous les champs calculés.

Le message, son type (ValueError) et la condition sont les mêmes dans la branche 19.0 : un correctif écrit pour la 19 vaut pour la 20.

4. inverse : écrire sur un champ calculé

Un délai de livraison en jours, calculé à partir de la date de commande et de la date de livraison promise (commitment_date). La méthode inverse fait le chemin dans l'autre sens : on saisit un délai, elle écrit la date.

# en tête du fichier : from datetime import timedelta

    delivery_days = fields.Integer(
        "Délai (jours)",
        compute='_compute_delivery_days',
        inverse='_inverse_delivery_days',
        search='_search_delivery_days',      # section 5
    )

    @api.depends('date_order', 'commitment_date')
    def _compute_delivery_days(self):
        for order in self:
            if order.date_order and order.commitment_date:
                order.delivery_days = (order.commitment_date - order.date_order).days
            else:
                order.delivery_days = 0

    def _inverse_delivery_days(self):
        for order in self:
            order.commitment_date = order.date_order + timedelta(days=order.delivery_days)

Un champ avec inverse n'est plus en lecture seule par défaut. Dans la console, l'écriture appelle l'inverse tout de suite, et le calcul suit dans l'autre sens :

from datetime import timedelta
order = env['sale.order'].search([('name', '=', 'S00003')])
print(order.date_order, order.commitment_date, order.delivery_days)
order.delivery_days = 15
print(order.date_order, order.commitment_date, order.delivery_days)
order.commitment_date = order.date_order + timedelta(days=40)
print(order.delivery_days)
env.cr.rollback()
2026-10-07 06:16:42 False 0 2026-10-07 06:16:42 2026-10-22 06:16:42 15 40

Dans le formulaire, il suffit d'afficher le champ (vue héritée de sale.view_order_form) :

<field name="payment_term_id" position="after">
    <field name="total_qty"/>
    <field name="delivery_days"/>
    <field name="commitment_date"/>
</field>

Le formulaire ne déclenche pas l'inverse à la frappe : la valeur saisie part au serveur avec l'enregistrement, et c'est le write qui appelle _inverse_delivery_days. Pour une mise à jour immédiate à l'écran, il faudrait que commitment_date soit lui-même calculé à partir de delivery_days.

Un inverse doit savoir traiter toutes les valeurs

Ici, saisir 0 donne une date promise égale à la date de commande, au lieu de l'effacer. Un inverse reçoit aussi False, 0 ou une valeur absurde : décide explicitement de ce que chacune écrit. Et comme le calcul, il boucle sur self : un write sur plusieurs commandes l'appelle une fois pour toutes.

5. search= : chercher sur un champ non stocké

Un champ non stocké n'a pas de colonne : un domaine qui le cite ne peut pas devenir du SQL. Sans méthode de recherche, la recherche échoue ; avec une méthode qui ne gère pas l'opérateur demandé aussi :

    def _search_delivery_days(self, operator, value):
        if operator != '>':
            return NotImplemented
        orders = self.search([('commitment_date', '!=', False)])
        return Domain('id', 'in', orders.filtered(lambda o: o.delivery_days > value).ids)
SO = env['sale.order']
for domain in ([('line_count', '>', 1)], [('delivery_days', '<', 10)]):
    try:
        SO.search(domain)
    except Exception as e:
        print(type(e).__name__, ":", e)
order = SO.search([('name', '=', 'S00003')])
order.delivery_days = 15
print(SO.search([('delivery_days', '>', 10)]).mapped('name'))
env.cr.rollback()
ValueError : Field has no SQL representation because it is not stored in condition ('line_count', '>', 1) UserError : Opérateur non pris en charge sur Délai (jours) 'Commande client' (sale.order) dans [('delivery_days', '<', 10)] ['S00003']

La méthode reçoit l'opérateur et la valeur, et rend un domaine qui remplace la condition (Domain s'importe de odoo.fields ; une liste est encore acceptée). Quand elle rend NotImplemented, l'ORM essaie l'opérateur contraire et nie le résultat, puis abandonne avec le UserError ci-dessus. Elle ne reçoit jamais = : Odoo le transforme en in avant de l'appeler. La syntaxe des domaines est détaillée dans l'article sur les domaines Odoo 20.

La méthode d'exemple parcourt les commandes en Python : acceptable sur quelques centaines d'enregistrements, pas sur un gros volume. Si la recherche, le tri ou le regroupement comptent, stocke le champ.

Venant de la 19 : un autre message pour la même erreur

En 19.0, le domaine passait l'optimisation et l'erreur tombait plus tard, à la traduction en SQL, avec ValueError: Cannot convert sale.order.line_count to SQL because it is not stored. En 20, la condition est refusée dès l'optimisation du domaine, et le message devient Field has no SQL representation because it is not stored in condition (…). Même type d'exception : seul un test qui comparait le texte est à revoir.

6. compute_sudo, precompute, recursive

compute_sudo

Vu à la section 2 : True par défaut pour un champ stocké (la valeur en base doit être la même pour tous), False pour un champ non stocké. Mets compute_sudo=True sur un non stocké quand le calcul lit des modèles que l'utilisateur ne voit pas, et compute_sudo=False sur un stocké seulement si tu sais pourquoi.

precompute=True

Un champ stocké est normalement calculé après l'insertion, au flush, par un UPDATE. Avec precompute=True, il est calculé avant et part dans l'INSERT. Deux champs identiques, l'un précalculé :

    ref_label = fields.Char(compute='_compute_ref_label', store=True)
    ref_label_pre = fields.Char(compute='_compute_ref_label_pre', store=True, precompute=True)
    # les deux méthodes : f"REF-{order.partner_id.id}", @api.depends('partner_id')

On espionne les requêtes qui écrivent dans sale_order pendant un create puis un flush_all() :

import re
SO = env['sale.order']
acme = env['res.partner'].search([('name', '=', "Acme Corporation")])
orig = type(env.cr).execute
log = []
def spy(self, query, params=None, log_exceptions=True):
    q = str(query)
    m = re.match(r"""SQL\(['"]\s*(INSERT INTO|UPDATE) "sale_order"[^_]""", q)
    if m:
        log.append((m.group(1).split()[0], [c for c in ('ref_label', 'ref_label_pre') if f'"{c}"' in q]))
    return orig(self, query, params, log_exceptions)
type(env.cr).execute = spy
order = SO.create({'partner_id': acme.id})
print("après create :", log)
env.flush_all()
print("après flush  :", log)
type(env.cr).execute = orig
env.cr.rollback()
après create : [('INSERT', ['ref_label_pre'])] _compute_total_qty sur sale.order(38,) après flush : [('INSERT', ['ref_label_pre']), ('UPDATE', ['ref_label'])]

À réserver aux champs dont la valeur doit exister dès l'insertion : un champ required, une contrainte SQL, ou des lignes créées en lot par leur document. La documentation du champ prévient : une valeur par défaut, ou une valeur passée au create, empêche le précalcul, et un précalcul fait enregistrement par enregistrement perd l'avantage du calcul en lot. Un champ précalculé qui dépend d'un champ stocké non précalculé perd son precompute, avec un avertissement au chargement.

recursive=True

Un champ qui dépend de lui-même à travers une relation, comme la profondeur d'une étiquette de contact dans son arbre :

# demo_calcules/models/res_partner_category.py
class ResPartnerCategory(models.Model):
    _inherit = 'res.partner.category'

    depth = fields.Integer("Profondeur", compute='_compute_depth', store=True, recursive=True)

    @api.depends('parent_id.depth')
    def _compute_depth(self):
        for tag in self:
            tag.depth = tag.parent_id.depth + 1 if tag.parent_id else 0
Tag = env['res.partner.category']
parent = Tag.create({'name': "Clients"})
child = Tag.create({'name': "Grands comptes", 'parent_id': parent.id})
grandchild = Tag.create({'name': "Export", 'parent_id': child.id})
print([(t.name, t.depth) for t in parent | child | grandchild])
child.parent_id = False
print([(t.name, t.depth) for t in parent | child | grandchild])
env.cr.rollback()
[('Clients', 0), ('Grands comptes', 1), ('Export', 2)] [('Clients', 0), ('Grands comptes', 0), ('Export', 1)]

Détacher « Grands comptes » recalcule aussi son enfant « Export ». Sans recursive=True, le résultat est le même (Odoo pose l'attribut lui-même), mais un avertissement apparaît à chaque chargement du registre : voir la figure de la section suivante. Déclare-le, ne compte pas sur la rustine.

7. @api.depends_context : une valeur qui dépend du contexte

Certains calculs ne dépendent pas d'un champ mais du contexte : la langue, la société, une clé posée par une action. @api.depends_context le dit à l'ORM, qui garde alors une valeur en cache par contexte. Le statut du devis en toutes lettres, dans la langue de l'utilisateur :

    state_label = fields.Char("Statut en clair", compute='_compute_state_label')

    @api.depends('state')
    @api.depends_context('lang')
    def _compute_state_label(self):
        labels = dict(self._fields['state']._description_selection(self.env))
        for order in self:
            order.state_label = labels[order.state]
order = env['sale.order'].search([('name', '=', 'S00003')])
print(order.state_label, "|", order.with_context(lang='en_US').state_label)
Devis | Quotation

Les deux lectures portent sur la même commande, dans deux contextes : chacune a sa valeur. Un tel champ reste non stocké : une colonne ne peut contenir qu'une valeur, pas une par langue.

Venant de la 19 : le champ stocké dépendant du contexte est signalé

Odoo 20 avertit au chargement quand un champ stocké déclare depends_context=… en attribut (seconde ligne de la figure ; exceptions : lang pour un champ traduit, company pour un champ company_dependent). La branche 19.0 n'a pas ce contrôle. Il ne voit que l'attribut du champ : avec le décorateur @api.depends_context sur la méthode, rien n'est signalé. Le conseil ne change pas : ce champ-là ne se stocke pas.

8. Le piège silencieux : la dépendance manquante

Le même total que total_qty, mais avec @api.depends('order_line') au lieu de 'order_line.product_uom_qty' :

    total_qty_stale = fields.Float(compute='_compute_total_qty_stale', store=True)

    @api.depends('order_line')
    def _compute_total_qty_stale(self):
        for order in self:
            order.total_qty_stale = sum(order.order_line.mapped('product_uom_qty'))
order = env['sale.order'].search([('name', '=', 'S00003')])
print(order.total_qty, order.total_qty_stale)
order.order_line[0].product_uom_qty = 12
print(order.total_qty, order.total_qty_stale)
env.cr.rollback()
11.0 11.0 _compute_total_qty sur sale.order(3,) 13.0 11.0

Ajouter ou retirer une ligne recalcule le champ ; modifier la quantité d'une ligne existante, non. La valeur stockée reste à 11, sans erreur ni avertissement. Règle : @api.depends cite chaque champ lu par la méthode, avec son chemin complet. Pour un champ déjà faux en base, corriger le depends ne suffit pas : il faut aussi recalculer les enregistrements existants (par exemple env.add_to_compute(Model._fields['total_qty_stale'], records) puis un flush_all(), dans un script de migration).

Récapitulatif

  • Une méthode de calcul boucle sur self et affecte le champ sur chaque enregistrement, dans tous les cas : l'ORM l'appelle en lot.
  • store=True crée une colonne recalculée quand une dépendance change ; le champ est alors calculé en superutilisateur par défaut.
  • « Compute method failed to assign » n'apparaît que sur un champ non stocké en lecture seule ; ailleurs, la même faute donne False en silence. Message identique en 19 et en 20.
  • inverse rend le champ modifiable, search le rend cherchable ; sans elle, Odoo 20 refuse la condition avec « Field has no SQL representation ».
  • precompute pour une valeur requise à l'insertion, recursive pour un champ qui dépend de lui-même, @api.depends_context pour une valeur par langue ou société, jamais stockée.
