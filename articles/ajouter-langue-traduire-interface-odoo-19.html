Série Traduction Odoo · Article 1/4 — Technique

Ajouter une deuxième langue à Odoo 19 et traduire l'interface

Activer une langue, charger ses traductions, régler la langue par utilisateur, puis traduire un contenu champ par champ — et comprendre où Odoo 19 range réellement ces traductions depuis la disparition d'ir.translation.

~12 minutes de lecture · démonstration Français → Anglais

Ce que tu vas apprendre

① Activer une langue et charger ses traductions

Par l'assistant graphique Ajouter des langues comme en ligne de commande avec --load-language — deux chemins pour le même résultat.

② Choisir la langue au bon niveau

Langue d'un utilisateur, langue de la société, langue de rendu : savoir lequel agit sur quoi évite les surprises sur les documents et les courriels.

③ Traduire un contenu depuis l'interface — et savoir où il est stocké

Le bouton de traduction champ par champ, puis la vraie nouveauté : Odoo 19 range les traductions dans une colonne jsonb, plus dans une table ir.translation qui n'existe plus.

Prérequis

  • Une instance Odoo 19 CE et un compte administrateur (accès au groupe Paramètres).
  • Au moins une application métier installée (Contacts, Ventes…) pour disposer d'un champ traduisible à manipuler.
  • Un accès au serveur pour la partie en ligne de commande et la vérification en base (facultatif, mais c'est là que tout devient limpide).

Le modèle mental d'Odoo 19 : un champ traduisible = une colonne jsonb où chaque code de langue porte sa valeur.

Étape 1 — Activer une deuxième langue

Une installation neuve d'Odoo démarre avec l'anglais ; une installation francophone a le français actif. Ajouter une langue, c'est deux choses en une seule opération : rendre la langue disponible (le champ active de res.lang) et charger ses traductions pour tous les modules installés.

Depuis l'interface : Paramètres → Traductions → Langues, puis le bouton Ajouter une langue. L'assistant ci-dessous ouvre un modèle transitoire base.language.install.

Sous le capot, valider cet assistant exécute une méthode courte et sans surprise : la langue passe à active = True, puis les traductions officielles sont chargées module par module.

def lang_install(self):
    self.ensure_one()
    mods = self.env['ir.module.module'].search([('state', '=', 'installed')])
    self.lang_ids.active = True
    mods._update_translations(self.lang_ids.mapped('code'), self.overwrite)

L'option Écraser les traductions existantes (overwrite) mérite un mot : cochée, elle remplace tes traductions personnalisées par les traductions officielles du catalogue. Utile pour repartir propre, dangereux si tu as peaufiné des libellés à la main.

La même chose en ligne de commande

Sur un serveur, charger une langue sans passer par l'interface tient en une commande. C'est le réflexe pour scripter le provisionnement d'une base :

odoo-bin -d ma_base --load-language=en_US --stop-after-init

La langue est activée et ses traductions chargées, puis le processus s'arrête. On vérifie ensuite l'état directement en base : les deux langues sont bien actives.

SELECT code FROM res_lang WHERE active = true ORDER BY code;
-- en_US
-- fr_FR

Étape 2 — Choisir la langue au bon niveau

Rendre une langue disponible ne bascule l'interface de personne. La langue s'applique à trois niveaux distincts, qu'il faut savoir distinguer :

NiveauOùCe que ça change
Utilisateurres.users.lang — PréférencesLa langue de l'interface de cette personne, et de ses courriels.
SociétéLangue de la sociétéLa langue par défaut des documents (devis, factures) émis par la société.
Renduself.env.context.get('lang')La langue dans laquelle l'ORM lit un champ traduisible à un instant donné.

Pour changer sa propre langue : le menu utilisateur en haut à droite → Préférences → champ Langue. Le petit globe à côté du champ rappelle qu'on est en terrain multilingue.

Le point à retenir : la langue de l'utilisateur et celle du client à qui on envoie un document sont deux choses différentes. Une facture part dans la langue du client (portée par son contact), pas dans celle du comptable qui l'édite.

Étape 3 — Traduire un contenu champ par champ

Les traductions officielles couvrent les libellés d'Odoo (les intitulés de menus, de boutons, de champs). Mais les données — le nom d'un produit, une description commerciale — c'est toi qui les saisis, donc c'est à toi de les traduire.

Dès qu'au moins deux langues sont actives, un petit bouton portant le code de la langue courante (ici FR) apparaît à côté de chaque champ marqué comme traduisible. Sur une fiche produit, il se niche au bout du champ Nom :

Un clic sur ce bouton ouvre une fenêtre de traduction listant une ligne par langue active. On y saisit la valeur anglaise en face de la valeur française, on valide, et l'enregistrement porte désormais ses deux versions. À la lecture, Odoo servira automatiquement la bonne selon la langue de rendu.

Bon à savoir — le bouton de traduction n'apparaît que si la fiche est enregistrée. Sur un tout nouvel enregistrement jamais sauvegardé, Odoo demande d'abord de valider la fiche avant de proposer la traduction.

Étape 4 — Où Odoo 19 range-t-il ces traductions ?

C'est ici que la version 19 diffère nettement des versions d'avant 16. Pour le voir, rien ne vaut un champ traduisible fait maison. Un modèle minimal suffit :

from odoo import fields, models


class TradDemoProduct(models.Model):
    _name = 'trad.demo.product'
    _description = "Produit vitrine (démo traduction)"

    name = fields.Char(string="Désignation", translate=True, required=True)
    description = fields.Text(string="Description", translate=True)
    reference = fields.Char(string="Référence interne")  # non traduisible

Une fois le module installé, on crée un enregistrement et on écrit sa valeur dans les deux langues, simplement en changeant la langue de rendu du contexte :

rec = env['trad.demo.product'].with_context(lang='fr_FR').create({
    'name': 'Chaise de bureau',
    'description': 'Chaise ergonomique réglable en hauteur.',
    'reference': 'CHAISE-001',
})
rec.with_context(lang='en_US').write({
    'name': 'Office chair',
    'description': 'Height-adjustable ergonomic chair.',
})

Maintenant, la révélation. On regarde comment PostgreSQL a réellement typé les colonnes :

\d trad_demo_product

--  Column     |  Type
-- ------------+-------------------
--  name       | jsonb
--  description| jsonb
--  reference  | character varying

Les deux champs traduisibles sont des colonnes jsonb ; le champ non traduisible reste un character varying classique. Et le contenu du champ name pour notre enregistrement ?

{
    "en_US": "Office chair",
    "fr_FR": "Chaise de bureau"
}

Toutes les langues d'un même enregistrement cohabitent dans une seule cellule, indexées par code de langue. C'est exactement le schéma du diagramme d'ouverture : la traduction ne vit plus dans une table à part, elle vit avec la donnée.

⚠️ Le changement à connaître — ir.translation a disparu

Jusqu'à Odoo 15, chaque traduction était une ligne dans une table géante ir.translation. Ce modèle n'existe plus : le chercher dans une base 19 renvoie une erreur, et tout code hérité qui l'interroge (self.env['ir.translation']) casse.

À la place, chaque champ translate=True est une colonne jsonb. Conséquences concrètes : plus de jointure lourde pour lire une traduction, la sauvegarde/restauration d'un enregistrement embarque ses langues, et une migration depuis une ancienne version convertit automatiquement la colonne texte en jsonb.

À retenir

  • Ajouter une langue = la rendre active et charger ses traductions, via l'assistant ou --load-language.
  • Trois niveaux de langue : utilisateur, société, contexte de rendu — ne pas confondre la langue de celui qui édite et celle du destinataire.
  • Le bouton de code langue n'apparaît que sur les champs translate=True, et seulement à partir de deux langues actives.
  • Odoo 19 stocke les traductions en jsonb, une valeur par code de langue, dans la colonne même du champ — ir.translation n'existe plus.

Reste une grande zone d'ombre : le catalogue de traductions officielles ne connaît pas tes modules. Traduire ton propre code — fichiers .po, fonction _(), traductions côté JavaScript — c'est le sujet du prochain article, cette fois vers l'arabe et son écriture de droite à gauche.
