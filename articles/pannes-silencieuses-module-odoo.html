Pannes silencieuses d'un module 19 sous Odoo 20 : t-esc, datas, t-set

Ton module 19 passe en Odoo 20, s'installe avec un code de sortie 0, et pourtant un rapport sort vide, une pièce jointe pèse 0 octet, un utilisateur ne voit plus rien. Quatre changements d'Odoo 20 ne lèvent aucune erreur à l'installation : voici comment les rendre visibles en une commande, et la ligne à changer pour chacun.

~6 minutes de lecture · niveau intermédiaire · parcours Qualité & tests

La réponse en bref

  1. t-esc / t-raw dans un gabarit QWeb serveur n'affichent plus rien → t-out.
  2. Un <t t-set> placé dans le corps d'un t-call n'arrive plus au gabarit appelé → le passer en attribut du t-call.
  3. ir.attachment créé avec datas= donne une pièce jointe vide → raw= avec les octets bruts.
  4. Une ligne d'accès sans groupe (« tout le monde » en 19) est devenue une restriction → groupe base.group_everyone.

Pour les débusquer : un test par panne, lancé avec --test-tags. Ce qui ne dit rien au chargement échoue en rouge dans le test.

1. Le symptôme : tout s'installe, rien ne marche

Pour reproduire les quatre pannes, un module minimal demo_silence, écrit comme en 19 et seulement passé en version 20.0.1.0.0 : un modèle demo.fiche, trois gabarits, une méthode qui joint une note, un fichier de droits.

<template id="carte">
    <p class="carte">Client : <t t-esc="client"/></p>
</template>
<template id="adresse">
    <p class="adresse">Ville : <t t-out="ville"/></p>
</template>
<template id="fiche">
    <div class="fiche">
        <t t-call="demo_silence.carte"/>
        <t t-call="demo_silence.adresse">
            <t t-set="ville" t-value="'Bruxelles'"/>
        </t>
    </div>
</template>
def action_joindre_note(self):
    for fiche in self:
        self.env['ir.attachment'].create({
            'name': 'note.txt',
            'res_model': self._name,
            'res_id': fiche.id,
            'datas': base64.b64encode(b'Bonjour'),

Le fichier de droits est déjà au format ir.access d'Odoo 20 : c'est la conversion « évidente » d'un ancien ir.model.access.csv dont la première ligne n'avait pas de groupe. -i demo_silence --stop-after-init se termine avec le code 0, sans un seul avertissement sur ces lignes. On rend ensuite la fiche, on joint la note et on compte les fiches visibles, dans odoo-bin shell :

Trois résultats faux, un refus, et un administrateur qui, lui, voit tout. Le t-esc et le datas laissent un WARNING dans le journal, au moment de l'exécution seulement ; le t-set ne laisse rien. Quant aux droits, seul un utilisateur ordinaire tombe sur l'AccessError : en recette faite avec le compte administrateur, la panne passe inaperçue.

2. La cause : ce que la 19 tolérait, la 20 l'a retiré

Chaque ligne ci-dessous a été lue dans les sources : la branche 19.0 publique d'Odoo et la 20.0.

Écrit pour la 19Odoo 19Odoo 20
t-esc, t-raw alias de t-out (ir_qweb.py, _compile_directive_esc) plus de directive : l'attribut tombe dans les « inconnus », un WARNING, aucune sortie (odoo/addons/base/models/ir_qweb.py:1927-1929)
t-set dans le corps d'un t-call une compatibilité rendait le corps et recopiait ses variables vers le gabarit appelé (is_deprecated_version) le corps n'est plus qu'un contenu passé à l'appelé, évalué sur une copie des valeurs (ir_qweb.py:2693) : la variable reste dans le corps
create({'datas': …}) champ datas en base64, décodé à la création clé retirée avec un warnings.warn, contenu vide (ir_attachment.py:533-536) ; reste raw (:616)
droit sans groupe accès pour tous (group_id IS NULL OR … dans ir_model.py) ligne sans groupe = restriction (ir_access.py:128-131), combinée en OU(permissions) ET ET(restrictions) (odoo/orm/models.py:3647) : elle ne donne aucun droit

Le dernier cas mérite une phrase de plus : une restriction sans domaine ne filtre rien, mais elle n'ouvre rien non plus. Sans permission qui le concerne, l'utilisateur interne n'a plus aucun accès ; seul le groupe Administrateur garde le sien grâce à la seconde ligne. Le groupe base.group_everyone, nouveau en 20, contient tous les utilisateurs (internes, portail, public) et redonne le sens « tout le monde ».

3. L'astuce : un test par panne

Ce qu'Odoo ne signale pas, un test l'affirme. Quatre assertions courtes, chacune sur le résultat attendu et non sur le code, suffisent :

from odoo.tests import TransactionCase, tagged


@tagged('post_install', '-at_install')
class TestSilence(TransactionCase):

    def _rendu(self):
        return str(self.env['ir.qweb']._render('demo_silence.fiche', {'client': 'Acme Corporation'}))

    def test_1_t_esc(self):
        self.assertIn('Client : Acme Corporation', self._rendu())

    def test_2_t_set_dans_t_call(self):
        self.assertIn('Ville : Bruxelles', self._rendu())

    def test_3_piece_jointe(self):
        fiche = self.env['demo.fiche'].create({'name': 'F1'})
        fiche.action_joindre_note()
        att = self.env['ir.attachment'].search([('res_model', '=', 'demo.fiche'), ('res_id', '=', fiche.id)])
        self.assertEqual(att.raw.content, b'Bonjour')

    def test_4_lecture_utilisateur_interne(self):
        self.env['demo.fiche'].create({'name': 'F1'})
        demo = self.env.ref('base.user_demo')
        self.assertEqual(self.env['demo.fiche'].with_user(demo).search_count([]), 1)

Le quatrième test est celui qu'on oublie : il lit avec with_user, un utilisateur interne sans droit d'administration. Un test exécuté en superutilisateur contourne tous les droits et ne verrait rien. On lance le module avec ses tests :

./odoo-bin -d ma_base -u demo_silence --test-tags /demo_silence --stop-after-init
echo $?

Cette fois le code de sortie vaut 1 : une intégration continue ou un script de mise en production s'arrête. Deux réglages complètent les tests pour ce qui n'en a pas encore :

  • Faire de l'avertissement datas une exception : lancer Odoo avec python -W error::UserWarning odoo-bin …. La création lève alors UserWarning: Use raw, datas has beeen removed à l'endroit exact de l'appel. Le réglage vaut pour tous les UserWarning : à réserver à une base de test.
  • Chercher les directives inconnues dans le journal : grep "Unknown directives" odoo.log après un passage de recette. Le WARNING n'apparaît qu'au rendu du gabarit, jamais au chargement du module.

4. Le correctif, ligne par ligne

Avant de corriger, une recherche dans les sources du module donne la liste des endroits à reprendre (résultat dans la figure 3) :

grep -rnE "t-(esc|raw)=|['\"]datas['\"]|<t t-call=\"[^\"]*\">" demo_silence/
awk -F, 'FNR>1 && $4=="" && $6==""' demo_silence/security/ir.access.csv

La seconde commande liste les lignes d'accès sans groupe et sans domaine : une restriction utile a toujours un domaine (multi-société par exemple), une ligne vide des deux côtés est presque toujours un ancien « tout le monde ». Les quatre corrections :

L'attribut du t-call est une expression Python, d'où les guillemets simples autour de 'Bruxelles'. raw prend les octets tels quels : plus de base64, ni à l'écriture ni à la lecture (att.raw.content). Après -u demo_silence, la même console affiche Client : Acme Corporation, Ville : Bruxelles, 7 b'Bonjour' et demo : 1, et les tests passent :

Le t-set ne laisse aucune trace

Des quatre pannes, c'est la seule sans la moindre ligne dans le journal : seul un test sur le rendu la voit. Et la recherche ne trie pas pour toi : un <t t-call="…"> ouvert reste légitime quand son corps est un contenu affiché par l'appelé (t-out="0"). Regarde s'il contient un t-set : c'est lui qu'il faut sortir en attribut.

À retenir

  • Un code de sortie 0 à l'installation ne prouve rien : t-esc, t-set dans un t-call, datas= et le droit sans groupe passent tous le chargement.
  • Écrire en Odoo 20 : t-out, attribut du t-call, raw=, base.group_everyone.
  • Un test par résultat attendu, dont un avec with_user sur un utilisateur ordinaire, transforme ces silences en code de sortie 1.
  • python -W error::UserWarning et grep "Unknown directives" sur le journal complètent les tests en recette.
