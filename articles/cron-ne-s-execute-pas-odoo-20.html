L'action planifiée ne s'exécute pas en Odoo 20 : les vérifications

Le cron est là, dans la liste, et pourtant rien ne se passe. Neuf causes possibles, de la case « Actif » décochée au serveur lancé sans thread cron, en passant par la base neutralisée, le module resté « à mettre à jour » et le code qui plante en silence. Chacune a été reproduite sur un serveur Odoo 20, avec la ligne de journal qui la trahit et le moyen de la lever.

~14 minutes de lecture · niveau intermédiaire · parcours Framework & ORM

Ce que tu vas apprendre

Regarder

Les champs de ir.cron qui comptent, ceux que le formulaire n'affiche pas, et les lignes du journal à chercher.

Diagnostiquer

Les neuf causes d'un cron muet, reproduites une à une, avec le correctif de chacune.

Relancer

« Exécuter manuellement », _trigger(), et ce que la 20 a changé dans la mécanique depuis la 19.

Prérequis

  • Un serveur Odoo 20 que tu peux arrêter et relancer, et l'accès à son journal.
  • La console odoo-bin shell : toutes les vérifications de cet article y ont été faites. Elle est présentée dans l'article sur le shell Odoo 20.
  • Le mode développeur, pour voir le menu Technique.

1. Où regarder

Les actions planifiées se trouvent dans Paramètres › Technique › Automatisation › Actions planifiées, mode développeur activé. Le formulaire montre l'essentiel de la planification :

Le serveur ne lit que quelques colonnes de la table ir_cron. Les voici, avec les deux que le formulaire ne montre pas :

ChampLibelléCe qu'il dit
activeActifUne action inactive n'est jamais prise.
nextcallProchaine date d'exécutionStockée en UTC, affichée dans ton fuseau. L'action n'est prise que si elle est passée.
interval_number, interval_typeExécuter tou(te)s lesDe combien avancer nextcall après un passage.
user_idUtilisateur de l'outil de planificationLe code tourne avec ses droits.
priorityPriorité0 passe avant 10, à échecs égaux.
lastcall(absent du formulaire)Date du dernier passage, réussi ou non.
failure_count, first_failure_date(absents du formulaire)Échecs consécutifs et date du premier ; remis à zéro au premier succès.

Pour lire l'état complet d'une action, une petite fonction dans la console suffit. Elle servira tout au long de l'article ; le compteur demo_cron.passages est celui que le cron de test incrémente à chaque passage réussi :

def etat(env, cron_id=26):
    env.invalidate_all()
    c = env['ir.cron'].with_context(active_test=False).browse(cron_id)
    print(f"active={c.active} nextcall={c.nextcall} lastcall={c.lastcall} "
          f"failure_count={c.failure_count} first_failure_date={c.first_failure_date} "
          f"passages={env['ir.config_parameter'].get_int('demo_cron.passages')}")

La règle du serveur, en une requête

Toutes les minutes environ, chaque thread cron se réveille et cherche, base par base, les actions prêtes. La condition est écrite en SQL dans ir_cron.py (méthode _get_ready_sql_condition) :

active IS TRUE
AND (nextcall <= %(now)s
    OR id IN (
        SELECT cron_id
        FROM ir_cron_trigger
        WHERE call_at <= %(now)s
    )
)

Active, et soit l'heure est passée, soit un déclencheur (ir.cron.trigger) est échu. Les actions prêtes sont traitées dans l'ordre failure_count, priority, id : une action qui échoue passe derrière les autres. Chaque passage laisse deux lignes dans le journal, à chercher par le nom de l'action :

INFO ma_base odoo.addons.base.models.ir_cron: Job 'Démo : compter les passages' (26) starting INFO ma_base odoo.addons.base.models.ir_cron: Job 'Démo : compter les passages' (26) fully done (#loop 1; done 0; remaining 0; duration 0.05s)

Pas de ligne starting : le serveur n'a pas pris l'action (causes 1 à 6). Une ligne failed : il l'a prise et le code a échoué (causes 7 et 8). Le nom de la base figure sur chaque ligne : c'est la première chose à vérifier quand plusieurs bases tournent sur le même serveur.

2. Un cron de test

Pour reproduire chaque panne, il faut une action dont on voit l'effet. Celle-ci, créée en console sur une base de démonstration, incrémente un paramètre système à chaque passage. Le code est celui qu'on écrirait par habitude en Odoo 19 :

from odoo import fields
cron = env['ir.cron'].create({
    'name': "Démo : compter les passages",
    'model_id': env.ref('base.model_res_partner').id,
    'state': 'code',
    'code': (
        "n = int(env['ir.config_parameter'].get_param('demo_cron.passages', '0')) + 1\n"
        "env['ir.config_parameter'].set_param('demo_cron.passages', str(n))\n"
    ),
    'interval_number': 1,
    'interval_type': 'days',
    'nextcall': fields.Datetime.now(),
})
env.cr.commit()
print(cron.id, cron.name, cron.user_id.login, cron.active, cron.nextcall, cron.lastcall, cron.failure_count)
26 Démo : compter les passages __system__ True 2026-10-07 08:29:41 False 0

ir.cron délègue name, model_id, state et code à une action serveur (_inherits), comme en 19. Sans user_id, l'utilisateur est celui qui crée : ici le superutilisateur de la console. Le serveur démarre, et une minute plus tard… le cron échoue. Ce sera la cause 7 ; le code est ensuite corrigé pour la suite des essais.

3. Les causes, une à une

Cause 1 : l'action est inactive

La plus simple, à soupçonner d'abord après une copie de base ou une désactivation automatique (causes 6 et 7). On désactive l'action en laissant une date passée, puis on demande si elle est prête, avec la méthode même qu'utilise le serveur :

from datetime import timedelta
from odoo import fields
from odoo.addons.base.models.ir_cron import IrCron
etat(env)
cron = env['ir.cron'].browse(26)
cron.write({'active': False, 'nextcall': fields.Datetime.now() - timedelta(hours=1)})
env.cr.commit()
pretes = [j['id'] for j in IrCron._get_all_ready_jobs(env.cr)]
print("inactive, nextcall passée -> prête :", 26 in pretes)
print("_trigger() ->", cron._trigger())
env.cr.commit()
active=True nextcall=2026-10-08 08:29:41 lastcall=2026-10-07 08:31:15 failure_count=0 first_failure_date=False passages=1 inactive, nextcall passée -> prête : False _trigger() -> ir.cron.trigger()

Non prête, et _trigger() ne crée aucun déclencheur : sur une action inactive, les déclenchements immédiats sont abandonnés en silence (_trigger_list). Une minute plus tard, le compteur n'a pas bougé. Correctif : réactiver l'action, et chercher pourquoi elle avait été désactivée (causes 6 et 7).

Cause 2 : la prochaine date est dans le futur

Active, mais prévue pour demain :

cron = env['ir.cron'].with_context(active_test=False).browse(26)
cron.write({'active': True, 'nextcall': fields.Datetime.now() + timedelta(days=1)})
env.cr.commit()
pretes = [j['id'] for j in IrCron._get_all_ready_jobs(env.cr)]
print("active, nextcall demain -> prête :", 26 in pretes)
active, nextcall demain -> prête : False

Le piège classique : une action quotidienne créée à 10 h avec une prochaine date à 10 h le lendemain ne tourne pas « tout de suite ». Et un passage ne recale nextcall que si elle est échue : une action lancée à la main ne décale pas son prochain rendez-vous. Pour la faire passer maintenant sans toucher à la date, crée un déclencheur :

etat(env)
cron = env['ir.cron'].browse(26)
print("_trigger() ->", cron._trigger())
env.cr.commit()
active=True nextcall=2026-10-08 08:33:09 lastcall=2026-10-07 08:31:15 failure_count=0 first_failure_date=False passages=1 _trigger() -> ir.cron.trigger(3,) active=True nextcall=2026-10-08 08:33:09 lastcall=2026-10-07 08:34:27 failure_count=0 first_failure_date=False passages=2

La troisième ligne est relue quelques secondes plus tard : le serveur a exécuté l'action dans la seconde (le commit d'un déclencheur échu réveille les threads cron par un NOTIFY PostgreSQL), lastcall a bougé, nextcall non.

Cause 3 : le serveur n'a pas de thread cron

Les actions planifiées ne tournent que dans un serveur Odoo démarré, et seulement s'il a des threads (ou, avec --workers, des processus) dédiés. Leur nombre est --max-cron-threads, 2 par défaut. À 0, il n'y en a plus aucun. Au démarrage normal, le journal les annonce :

INFO ? odoo.service.server: HTTP service running on 127.0.0.1:9139 INFO ? odoo.service.server.ThreadedServer.cron0: Alive INFO ? odoo.service.server.ThreadedServer.cron1: Alive

Avec --max-cron-threads=0, la ligne HTTP service running est seule. Le même déclencheur, posé sur ce serveur, attend :

active=True nextcall=2026-10-08 08:33:09 lastcall=2026-10-07 08:34:27 failure_count=0 first_failure_date=False passages=2 _trigger() -> ir.cron.trigger(4,) active=True nextcall=2026-10-08 08:33:09 lastcall=2026-10-07 08:34:27 failure_count=0 first_failure_date=False passages=2

Soixante-dix secondes plus tard, rien. Le déclencheur reste en base ; au redémarrage avec les threads par défaut, il est consommé au premier tour, une minute après cron0: Alive. Cherche donc max_cron_threads dans le fichier de configuration, la ligne de commande et le service systemd : un serveur web secondaire est souvent lancé à 0 pour laisser les crons à un seul nœud — très bien, à condition que ce nœud tourne. Même idée pour un serveur de développement arrêté le soir : aucune action ne passera la nuit.

Cause 4 : la base n'est pas dans -d

Quelles bases les threads cron visitent-ils ? La réponse tient en une fonction, cron_database_list() : la liste -d (db_name) si elle est donnée, sinon toutes les bases dont le rôle PostgreSQL est propriétaire. --db-filter n'y figure pas : il ne filtre que les requêtes HTTP.

import re
from odoo.service.server import cron_database_list
from odoo.tools import config
print("-d", config['db_name'], "| --db-filter", config['dbfilter'])
print("  bases visitées par les crons :", cron_database_list())
config['db_name'] = []
bases = cron_database_list()
hors = [b for b in bases if not re.match(config['dbfilter'], b)]
print("sans -d, même --db-filter")
print("  bases visitées par les crons :", len(bases), "dont hors --db-filter :", len(hors))
-d ['ma_base'] | --db-filter ^ma_base$ bases visitées par les crons : ['ma_base'] sans -d, même --db-filter bases visitées par les crons : 61 dont hors --db-filter : 60

Deux pannes symétriques en découlent :

  • un serveur lancé avec -d prod n'exécute jamais les actions d'une autre base, même si on s'y connecte par le navigateur. Ajoute-la à la liste (-d prod,test) ou donne-lui son propre serveur ;
  • un serveur lancé sans -d exécute les actions de toutes les bases du rôle, y compris une copie de production restaurée « pour voir » — qui enverra alors ses courriels. D'où la cause 6.

Cause 5 : un module est resté « à mettre à jour »

Une mise à jour de module interrompue laisse parfois un module dans l'état to upgrade, to install ou to remove. Tant que c'est le cas, le serveur saute la base entière. Reproduit en passant sale_management à to upgrade puis en déclenchant l'action :

WARNING ma_base odoo.addons.base.models.ir_cron: Skipping database ma_base because of modules to install/upgrade/remove.

Aucune action de la base ne passe, pas seulement la tienne. Correctif : terminer l'opération (-u module, voir les modules en ligne de commande) et lire l'erreur qui l'avait interrompue. Le code prévoit un filet : si la plus ancienne action prête attend depuis plus de 5 heures, le serveur remet les états d'office (MAX_FAIL_TIME, _check_modules_state) — cinq heures sans aucun cron.

Cause 6 : la base est neutralisée

Une base de test copiée de la production devrait toujours être neutralisée : odoo-bin neutralize -d <base>, ou l'option du même nom au chargement d'une sauvegarde. Entre autres effets, le script SQL du module base désactive toutes les actions planifiées sauf le nettoyage automatique. Avant et après, sur la base de test :

Cron = env['ir.cron']
print("actions planifiées actives :", Cron.search_count([]), "| neutralisée :", env['ir.config_parameter'].get_bool('database.is_neutralized'))
print("restantes :", Cron.search([]).mapped('cron_name'))
print("démo active :", Cron.with_context(active_test=False).browse(26).active)
actions planifiées actives : 22 | neutralisée : False … $ ./odoo-bin neutralize -c odoo.conf -d ma_base INFO ? odoo.cli.neutralize: Starting ma_base database neutralization INFO ? odoo.modules.neutralize: Neutralization finished actions planifiées actives : 1 | neutralisée : True restantes : ['Base: Auto-vacuum internal data'] démo active : False

La base porte un bandeau rouge « Base de données neutralisée pour les tests ». Elle ne verrouille rien : cron.active = True réactive une action, comme sur la capture. En revanche, les réactivations indirectes sont bloquées : la méthode toggle(), que des modules appellent pour allumer ou éteindre un cron selon qu'il a du travail, ne fait rien sur une base neutralisée :

cron = env['ir.cron'].with_context(active_test=False).browse(26)
print("toggle ->", cron.toggle('res.partner', []), "| active :", cron.active)
cron.active = True
print("write active=True -> active :", cron.active)
toggle -> True | active : False write active=True -> active : True

Réactive seulement ce dont le test a besoin : une base neutralisée dont on rallume la file des courriels n'est plus neutralisée que de nom.

Cause 7 : le code échoue

C'est ici que le cron de test est tombé dès son premier passage. Le journal ne laisse aucun doute :

En Odoo 20, get_param et set_param ont disparu au profit de méthodes typées : get_str, get_int, get_float, get_bool et leurs set_*. Toute action planifiée ou action serveur copiée d'une 19 qui lit un paramètre système tombe ainsi. Le code corrigé :

n = env['ir.config_parameter'].get_int('demo_cron.passages') + 1
env['ir.config_parameter'].set_int('demo_cron.passages', n)

Ce qu'un échec laisse en base, relu juste après :

active=True nextcall=2026-10-08 08:29:41 lastcall=2026-10-07 08:30:49 failure_count=1 first_failure_date=2026-10-07 08:30:49 passages=0

lastcall avance aussi quand le cron échoue

L'aide du champ parle du « dernier passage réussi », mais après un échec le serveur appelle la même replanification qu'après un succès (_reschedule_later) : lastcall prend l'heure de l'échec et nextcall saute à l'intervalle suivant — ici, au lendemain. Un lastcall récent ne prouve donc rien : regarde failure_count. Et une action quotidienne qui échoue ne réessaie pas avant demain.

La désactivation automatique

Un cron qui échoue sans cesse finit désactivé. Il faut que les deux seuils soient atteints : 5 échecs consécutifs (MIN_FAILURE_COUNT_BEFORE_DEACTIVATION) et un premier échec vieux de plus de 7 jours (MIN_DELTA_BEFORE_DEACTIVATION). Pour le voir sans attendre une semaine, le code fautif est remis et l'historique vieilli :

cron.write({
    'code': "n = int(env['ir.config_parameter'].get_param('demo_cron.passages', '0')) + 1\n",
    'failure_count': 2,
    'first_failure_date': fields.Datetime.now() - timedelta(days=8),
})
etat(env)
cron._trigger()
env.cr.commit()
# … puis, après ce passage :
etat(env)
cron.write({'failure_count': 4})
cron._trigger()
env.cr.commit()
# … et après le suivant :
etat(env)
active=True nextcall=2026-10-08 08:33:09 lastcall=2026-10-07 08:37:17 failure_count=2 first_failure_date=2026-09-29 08:37:40 passages=3 active=True nextcall=2026-10-08 08:33:09 lastcall=2026-10-07 08:37:40 failure_count=3 first_failure_date=2026-09-29 08:37:40 passages=3 active=False nextcall=2026-10-08 08:33:09 lastcall=2026-10-07 08:37:47 failure_count=0 first_failure_date=False passages=3

Au moment de la désactivation, les compteurs sont remis à zéro : une action désactivée par le serveur ressemble ensuite à n'importe quelle action désactivée. Deux traces restent :

  • le journal, avec le WARNING … has been deactivated after failing 5 times ;
  • le canal Discuss des administrateurs, où le module mail recopie les deux messages :
canal : Administrateurs - OdooBot | Cron job 'Démo : compter les passages' (26) has been deactivated after failing 5 times. More information can b - OdooBot | Cron job 'Démo : compter les passages' (26) is failing and will be deactivated if you don't take action. More

Le chatter de l'action, lui, ne dit rien : le serveur écrit active par une requête SQL directe, sans passer par le suivi des champs. Seules les modifications faites par un utilisateur y apparaissent (« Oui → Non (Actif) »).

Venant de la 19 : un avertissement avant la désactivation

Les seuils (5 échecs, 7 jours) et les champs failure_count / first_failure_date sont les mêmes qu'en 19. Ce qui est nouveau en 20 : le message « is failing and will be deactivated if you don't take action », envoyé une fois les 7 jours passés dès le 2ᵉ échec consécutif (puis à intervalles espacés pour les crons très fréquents), et le suivi du champ active dans le chatter. En 19, seul le message de désactivation existait, sans avertissement préalable.

Cause 8 : l'utilisateur du cron n'a pas les droits

Le code tourne avec les droits de user_id, pas en superutilisateur. Le même code corrigé, confié à l'utilisateur de démonstration :

cron.write({'active': True, 'user_id': env.ref('base.user_demo').id})
print(cron.user_id.name, cron.user_id.has_group('base.group_system'))
cron._trigger()
env.cr.commit()
Marc Demo False ERROR ma_base odoo.addons.base.models.ir_cron: Job 'Démo : compter les passages' (26) server action #488 failed … odoo.exceptions.AccessError: You are not allowed to access 'System Parameter' (ir.config_parameter) records. This operation is allowed for the following groups: - Role / Administrator Contact your administrator to request access if necessary.

Le journal nomme le modèle et le groupe requis. Deux corrections possibles : un utilisateur d'exécution qui a les droits (souvent base.user_root dans les données d'un module), ou un sudo() ciblé dans la méthode appelée, pour la seule opération qui le justifie — voir l'environnement et sudo en Odoo 20. Pense à cette cause quand un cron qui marchait s'arrête après un changement de groupes de son utilisateur.

Cause 9 : l'action est déjà en cours

Pendant un passage, le serveur verrouille la ligne de l'action (FOR NO KEY UPDATE SKIP LOCKED) : un second thread la saute, et l'interface refuse d'y toucher. Reproduit en tenant le même verrou depuis une seconde transaction, comme le ferait un cron long :

cron = env['ir.cron'].browse(26)
autre = env.registry.cursor()            # une autre transaction, comme un cron en cours
autre.execute("SELECT id FROM ir_cron WHERE id = 26 FOR NO KEY UPDATE")
try:
    cron.method_direct_trigger()
except Exception as e:
    print(type(e).__name__, ":", e)
try:
    cron.write({'priority': 3})
except Exception as e:
    print(type(e).__name__, ":", e)
autre.rollback(); autre.close()
env.cr.rollback()
UserError : Tâche 'Démo : compter les passages' déjà en cours d’exécution UserError : L'enregistrement ne peut pas être modifié à l'instant : Cette tâche 'cron' est actuellement en cours d'exécution et ne peut pas être modifiée. Veuillez réessayer dans quelques minutes

Si le message persiste, cherche la transaction qui tient le verrou dans pg_stat_activity : un cron très long, ou une session de console restée ouverte avec des écritures non validées sur les mêmes lignes. La durée d'un cron est par ailleurs bornée par --limit-time-real-cron (par défaut, la valeur de --limit-time-real).

4. Lancer à la main, et ce que cela prouve

« Exécuter manuellement »

Le bouton du formulaire appelle method_direct_trigger(). Il exécute l'action dans le processus du serveur web, sans thread cron, mais comme le planificateur : même verrou, nouveau curseur, mêmes droits (ceux de user_id), même comptage des échecs. Il contourne donc les causes 1 à 6 et reproduit les causes 7 à 9 :

cron = env['ir.cron'].browse(26)
res = cron.method_direct_trigger()            # utilisateur du cron : Marc Demo
print(res['type'], res['tag'], '|', res['params']['data']['name'], '|', res['params']['data']['message'][:60])
env.cr.commit()
etat(env)
cron.user_id = env.ref('base.user_admin')
print(cron.method_direct_trigger())           # utilisateur du cron : Mitchell Admin
env.cr.commit()
etat(env)
ir.actions.client display_exception | builtins.RuntimeError | active=True nextcall=2026-10-08 08:33:09 lastcall=2026-10-07 08:38:34 failure_count=2 first_failure_date=2026-10-07 08:38:17 passages=3 True active=True nextcall=2026-10-08 08:33:09 lastcall=2026-10-07 08:38:34 failure_count=0 first_failure_date=False passages=4

En cas d'erreur, la méthode ne lève pas d'exception : elle renvoie une action display_exception, que l'interface affiche en fenêtre d'erreur, et l'échec compte (failure_count passe à 2). Le succès suivant remet tout à zéro. Lecture du diagnostic : si le bouton marche et que l'action ne passe jamais seule, le problème est côté planificateur (causes 1 à 6) ; s'il échoue, il est dans le code ou les droits.

Depuis la console, valide avant de déclencher

Le cron tourne dans sa propre transaction. Des écritures non validées de ta session sur les lignes qu'il touche le mettent en attente d'un verrou que toi seul peux relâcher : env.cr.commit() d'abord. Le détail est dans l'article sur le cron des retards.

_trigger() : programmer depuis le code

Quand un traitement doit suivre un événement (une commande confirmée, un fichier reçu), mieux vaut un déclencheur qu'un cron à la minute : env.ref('mon_module.mon_cron')._trigger() le programme dès la validation de la transaction, _trigger(at=une_date) plus tard, une liste de dates pour plusieurs rendez-vous. Trois règles vues plus haut : un déclenchement immédiat est ignoré sur une action inactive, nextcall ne bouge pas, et un serveur sans thread cron les laisse en attente.

Venant de la 19 : coalesce, et des passes plus longues

  • _trigger(at, coalesce=15) (nouveau) repousse chaque déclencheur à la fin de sa fenêtre de 15 minutes : cent déclenchements rapprochés, un seul réveil.
  • Un cron qui traite par lots avec _commit_progress() (déjà là en 19) est relancé dans la même passe tant qu'il reste du travail, au moins 10 fois et pendant au moins 120 secondes (MIN_TIME_PER_JOB, 10 secondes en 19).
  • _rollback_progress() (nouveau) annule le lot en cours avec la même logique.

Récapitulatif

  • Une action passe si elle est active et que sa date ou un déclencheur est échu, dans une base que les threads cron visitent : la liste -d, ou toutes les bases du rôle sans elle.
  • Le journal tranche : pas de starting, le planificateur ne l'a pas prise ; un failed, c'est le code ou les droits.
  • lastcall bouge aussi en cas d'échec : le bon indicateur est failure_count.
  • Neutraliser une base désactive ses crons ; un module bloqué en « à mettre à jour » les suspend tous.
  • Un code d'action écrit pour la 19 peut casser en 20 : get_param est devenu get_str, get_int, get_bool…
  • En 20, un avertissement précède la désactivation automatique, dans le journal et dans le canal des administrateurs.
