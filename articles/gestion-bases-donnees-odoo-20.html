Gestion des bases de données Odoo 20 : créer, dupliquer, filtrer

Créer, dupliquer, renommer, supprimer et lister des bases, depuis le gestionnaire web ou avec odoo-bin db : ce que chaque opération fait vraiment dans PostgreSQL et sur le disque, les droits qu'il faut au rôle, le filtre des bases et le mot de passe maître, sur un serveur 20.0.

~15 minutes de lecture · niveau débutant · parcours Fondamentaux

Ce que tu vas apprendre

Les opérations

Créer, dupliquer, renommer, supprimer : la commande, la sortie réelle, et ce qui arrive au filestore et aux connexions ouvertes.

Qui voit quelle base

Propriétaire PostgreSQL, dbfilter, %d, list_db : comment Odoo choisit les bases qu'il montre, et ce que le filtre ne protège pas.

Ce qui change en 20

PostgreSQL 16, service db retiré de XML-RPC, --db-system, route de renommage : chaque écart vérifié contre la 19.

Prérequis

  • Un Odoo 20 Community installé (voir Installer Odoo 20 sur Ubuntu et le lancer dans PyCharm), son fichier de configuration et un PostgreSQL 16 ou plus.
  • Un terminal avec psql et curl.
  • Un serveur de développement, pas ta production : on y supprime des bases.

Tu es en Odoo 19 ? L'article Gestion des bases de données Odoo 19 reste valable pour ta version. Celui-ci reprend le sujet pour Odoo 20, avec des sorties relevées sur un serveur 20.0 et les écarts avec la 19 en fin d'article.

Une instance Odoo peut servir plusieurs bases sur le même PostgreSQL : une par client, une de développement, une copie de la production pour tester. On les gère par deux portes, le gestionnaire web et la commande odoo-bin db, qui appellent le même code. Dans les exemples, ma_base est une copie de démonstration et odoo.conf le fichier de configuration du serveur.

1. Une base Odoo : une base PostgreSQL et un filestore

Une base Odoo, c'est deux morceaux qui vont toujours ensemble : la base PostgreSQL (une table par modèle, plus la configuration : modules installés, vues, droits, paramètres) et le filestore, le dossier <data_dir>/filestore/<nom de la base>/ où vivent les pièces jointes et les images. Toutes les opérations d'Odoo traitent les deux ; un createdb ou un dropdb lancé à la main ne touche que le premier.

Quand Odoo crée une base, il ne laisse pas PostgreSQL choisir : CREATE DATABASE … ENCODING 'unicode' LC_COLLATE 'C' TEMPLATE template0 (odoo/modules/db.py:352-358), puis l'extension pg_trgm et un GRANT CREATE ON SCHEMA public TO PUBLIC (:364, :382). Sur une base fraîchement créée :

$ psql -d postgres -Atc "select datname, pg_get_userbyid(datdba), pg_encoding_to_char(encoding), datcollate, datctype
                        from pg_database where datname = 'ma_base_vierge'"
ma_base_vierge|odoo|UTF8|C|fr_FR.UTF-8
$ psql -d ma_base_vierge -Atc "select extname from pg_extension"
plpgsql
pg_trgm

Le tri C est voulu (le commentaire du source parle d'index plus utiles), mais il se voit : les listes triées par nom suivent l'ordre des octets, majuscules d'abord, lettres accentuées à la fin. L'ORM n'ajoute aucune clause COLLATE à ses ORDER BY. Comparaison dans la même base :

$ psql -d ma_base -c "SELECT string_agg(n, ' < ' ORDER BY n) AS collation_base,
                             string_agg(n, ' < ' ORDER BY n COLLATE \"fr_FR\") AS collation_fr
                      FROM unnest(ARRAY['zoé','Éric','abc','Zoé','émile']) AS n;"
         collation_base         |          collation_fr
--------------------------------+--------------------------------
 Zoé < abc < zoé < Éric < émile | abc < émile < Éric < zoé < Zoé

Le choix du modèle passe par l'option --db-template (défaut template0, odoo/tools/config.py:429) : avec un autre modèle, Odoo n'écrit plus LC_COLLATE 'C' et la base hérite du tri de ce modèle. Retiens surtout la règle inverse : une base que tu recrées à la main pour y charger un dump doit l'être avec les mêmes réglages (createdb -T template0 -E UTF8 --lc-collate=C), sinon le tri change sans prévenir.

2. Le rôle PostgreSQL : CREATEDB, pas superutilisateur

Odoo se connecte avec un seul rôle (db_user). Pour gérer des bases, ce rôle a besoin de créer des bases, pas d'être superutilisateur. Le serveur de démonstration tourne ainsi :

$ psql -d postgres -c "\du odoo"
     List of roles
 Role name | Attributes
-----------+------------
 odoo      | Create DB

Trois conséquences à connaître :

  • Le rôle postgres est refusé. Le serveur s'arrête avant même de se connecter (odoo/cli/server.py:37-44) : 
    $ odoo-bin -c odoo.conf -r postgres --stop-after-init
Using the database user 'postgres' is a security risk, aborting.
  • Odoo ne voit que les bases dont son rôle est propriétaire. La liste vient de pg_database, filtrée sur datdba = rôle courant, sans les modèles ni la base postgres (odoo/modules/db.py:701-732). Quand la liste vient de PostgreSQL (cas habituel, section 6), une base restaurée par un autre rôle n'y apparaît pas tant que tu n'as pas fait ALTER DATABASE … OWNER TO odoo.
  • Les opérations globales passent par une base système. Créer, renommer ou supprimer une base demande d'être connecté à une autre : Odoo 20 lit pour cela l'option --db-system (défaut postgres, config.py:431), nouvelle en 20 ; son aide cite aussi le bus et la maintenance. À régler si ton rôle n'a pas accès à la base postgres.

Enfin, PostgreSQL lui-même : Odoo 20 demande la version 16 ou plus (odoo/release.py:41). Sur un serveur plus ancien, il démarre avec un simple avertissement (odoo/sql_db.py:712-713) : vérifie select version() avant de créer quoi que ce soit.

unaccent = True sans superutilisateur : la base perd aussi pg_trgm

L'option unaccent demande à Odoo d'activer l'extension du même nom à la création des bases, puis de rendre la fonction unaccent() immuable. Avec un rôle qui n'est pas superutilisateur, cette dernière étape échoue, et comme les trois ordres partagent la même transaction (odoo/modules/db.py:360-377), tout est annulé, pg_trgm compris. Le journal de création le dit une fois, puis plus rien :

ERROR ? odoo.sql_db: bad query: b'ALTER FUNCTION unaccent(text) IMMUTABLE'
ERROR: must be owner of function unaccent
WARNING ? odoo.modules.db: Unable to create PostgreSQL extensions : must be owner of function unaccent

La base est utilisable, mais sans extension : les champs déclarés index='trigram' n'ont pas leur index, sans message. Après installation de Discussion sur deux bases, ma_base_fr créée avec unaccent = True et ma_base_vierge sans :

$ psql -d ma_base_fr -Atc "select indexname from pg_indexes where tablename = 'mail_blacklist'"
mail_blacklist_pkey
mail_blacklist_unique_email
$ psql -d ma_base_vierge -Atc "select indexname from pg_indexes where tablename = 'mail_blacklist'"
mail_blacklist_pkey
mail_blacklist_unique_email
mail_blacklist__email_index

Le comportement est le même en 19 (bloc identique). Avec un rôle non superutilisateur, laisse unaccent à False et contrôle pg_extension après chaque création. Pour réparer une base touchée : CREATE EXTENSION pg_trgm; (le propriétaire de la base peut le faire lui-même), puis une mise à jour des modules concernés ; un simple redémarrage ne suffit pas. Relevé : après l'extension et -u mail, mail_blacklist__email_index apparaît.

3. Créer une base

En ligne de commande : odoo-bin db init

La sous-commande db est la version ligne de commande du gestionnaire. Elle n'a pas de mot de passe maître : elle se connecte avec le rôle du fichier de configuration, donc quiconque peut la lancer sur le serveur a déjà les droits. Ses six actions :

$ odoo-bin db --help
…
Command-line version of the database manager.

Commands are all filestore-aware.

positional arguments:
  {init,load,dump,duplicate,rename,drop}
    init                Create and initialize a database
    load                Load a dump file.
    dump                Create a dump with filestore.
    duplicate           Duplicate a database including filestore.
    rename              Rename a database including filestore.
    drop                Delete a database including filestore

Les options de connexion (-c, -D, --db_host…) se placent avant l'action. init accepte --with-demo, --language (défaut en_US), --country, --username et --password (défaut admin pour les deux : change-les dès qu'une base n'est plus jetable), et --force qui supprime d'abord une base du même nom.

$ odoo-bin db -c odoo.conf init ma_base_fr --language fr_FR --country FR --password '…'
INFO ? odoo.modules.db: Create database `ma_base_fr`.
INFO ? odoo.modules.loading: Initializing database ma_base_fr
INFO ma_base_fr odoo.modules.loading: Loading module base (1/1)
…
INFO ma_base_fr odoo.modules.loading: Loading module base_report_wkhtmltox (2/16)
…

Moins de dix secondes sur le serveur de démonstration : sans --with-demo, la base reçoit seulement base et les modules qui s'installent d'office avec lui (seize au total ici, dont web, base_setup, bus, auth_totp, auth_passkey, rpc, api_doc). La langue française est active, la société principale porte le pays demandé. Pour ajouter des applications, enchaîne avec odoo-bin -c odoo.conf -d ma_base_fr -i sale --stop-after-init ou odoo-bin module install.

Deux contrôles valent d'être connus. Le nom d'abord : lettres, chiffres, _, - et ., premier caractère alphanumérique, deux caractères au minimum (DB_NAME_RE, odoo/modules/db.py:44), vérifié dans la fonction de création elle-même, donc aussi en ligne de commande :

$ odoo-bin db -c odoo.conf init "ma_base test"
…
ValueError: Invalid db_name='ma_base test'

L'autre, plus traître : le serveur crée lui-même toute base passée à -d qui n'existe pas (odoo/cli/server.py:101-105) et y installe base. Une faute de frappe dans -d ma_bsae ne donne pas d'erreur, elle donne une base vide de plus.

$ odoo-bin -c odoo.conf -d ma_base_fautedefrappe --stop-after-init
INFO ma_base_fautedefrappe odoo.modules.loading: Initializing database ma_base_fautedefrappe
INFO ma_base_fautedefrappe odoo.modules.loading: 1 modules loaded in 3.48s, 8630 queries (+8630 extra)
INFO ma_base_fautedefrappe odoo.modules.loading: 16 modules loaded in 1.72s, 5321 queries (+5321 extra)

Depuis le gestionnaire web

Le bouton Create Database du gestionnaire (section 7) ouvre le même formulaire qu'au premier lancement d'un serveur sans base : mot de passe maître, nom, identifiant et mot de passe de l'administrateur, téléphone, langue, pays, données de démonstration. Le bouton Duplicate d'une ligne demande le nouveau nom et propose la case Neutralize.

4. Dupliquer une base

Dupliquer, c'est le geste de tous les jours : une copie pour tester une mise à jour, une base de recette, une base de formation. Odoo fait un CREATE DATABASE … TEMPLATE <source> (la copie est faite par PostgreSQL lui-même, bien plus vite qu'un dump suivi d'une restauration), puis copie le filestore (odoo/modules/db.py:467-508). Avec -n, la copie est neutralisée avant de devenir visible :

$ odoo-bin db -c odoo.conf duplicate -n ma_base ma_base_copie
INFO ? odoo.modules.db: Duplicate database `ma_base` to `ma_base_copie`.
INFO ? odoo.modules.neutralize: Neutralization finished
INFO ma_base_copie odoo.modules.loading: loading 69 modules...
INFO ma_base_copie odoo.registry: Registry loaded in 0.948s

Trois secondes pour une base de démonstration avec ses 564 fichiers de filestore. Ce qui distingue la copie de l'original :

Relevéma_basema_base_copie
database.uuid9473…2f6a… (nouveau)
database.secretvaleur d'originenouvelle valeur
database.create_datedate d'originedate de la copie
database.is_neutralizedabsentTrue
Actions planifiées actives211
Serveurs de courriel sortant actifs01 (le leurre de la neutralisation)
Fichiers du filestore564564

Le nouvel identifiant n'est pas un détail : c'est lui qui distingue la copie de l'original auprès des services externes ; le secret, lui, sert notamment à signer les jetons anti-CSRF des formulaires (odoo/http/requestlib.py:234) : la copie ne partage pas ceux de l'original. Ce que la neutralisation coupe exactement, module par module, est détaillé dans Copier la prod en base de test Odoo 20 : db dump, load, neutralize.

Si la cible existe déjà, la commande refuse sans rien toucher, et -f la supprimerait d'abord :

$ odoo-bin db -c odoo.conf duplicate ma_base ma_base_copie
Target database ma_base_copie exists, aborting.

	use `--force` to delete the existing database anyway.

Attention à la source : pour que PostgreSQL accepte de la copier, personne ne doit y être connecté. Odoo coupe donc toutes les connexions ouvertes sur la base d'origine avant la copie (_drop_conn, odoo/modules/db.py:487). Sur une production en service, cela coupe les utilisateurs : dans ce cas, passe par une sauvegarde.

5. Renommer et supprimer

rename fait un ALTER DATABASE … RENAME TO puis déplace le dossier du filestore ; drop fait un DROP DATABASE puis efface le dossier (odoo/modules/db.py:527-547, 672-698). Les deux commencent par couper les connexions ouvertes sur la base. Démonstration avec une session psql laissée ouverte pendant le renommage :

$ psql -d ma_base_copie -c "select pg_sleep(20)" &
$ odoo-bin db -c odoo.conf rename ma_base_copie ma_base_recette
INFO ? odoo.modules.db: RENAME DB: ma_base_copie -> ma_base_recette
FATAL:  terminating connection due to administrator command
…

La ligne FATAL vient de la session psql, coupée par Odoo. Un serveur Odoo qui travaillait sur cette base perd de même ses connexions.

Supprimer une base qui n'existe pas ne donne pas un message propre mais une trace Python ; la dernière ligne suffit :

$ odoo-bin db -c odoo.conf drop ma_base_absente
…
psycopg2.errors.InvalidCatalogName: database "ma_base_absente" does not exist

When trying to drop ma_base_absente

Le gestionnaire web, lui, a un bouton Delete par base, mais aucun bouton de renommage : la route /web/database/rename existe en 20 (web/controllers/database.py:217) sans que la page ne l'utilise. On l'appelle donc à la main, avec le mot de passe maître :

$ curl -s -o /dev/null -w "%{http_code}\n" -d master_pwd='…' -d name=ma_base_recette -d new_name=ma_base_essai \
    http://localhost:8069/web/database/rename
303

Préfère tout de même odoo-bin db rename : la route contrôle le format du nom de la base source, pas celui du nouveau nom. Un nouveau nom contenant une espace est accepté, la base est renommée et disparaît de la liste filtrée ; il faut ensuite la renommer de nouveau en ligne de commande.

6. Lister et filtrer les bases : dbfilter, -d, list_db

La liste que voit un visiteur (sélecteur de base, gestionnaire, choix de la base d'une requête sans session) se construit en deux temps (odoo/http/router.py:70-121) : les bases du rôle (section 2), puis un filtre. La route JSON /web/database/list renvoie le résultat ; on la questionne en faisant varier le filtre au démarrage du serveur.

$ curl -s -H 'Content-Type: application/json' -d '{"jsonrpc":"2.0","method":"call","params":{}}' \
    http://localhost:8069/web/database/list
Réglage du serveurEn-tête HostBases listées
--db-filter='^ma_base'indifférentma_base, ma_base_essai, ma_base_fr, ma_base_vierge
--db-filter='^ma_base$'indifférentma_base
--db-filter='^ma_base_%d$'essai.exemple.comma_base_essai
www.vierge.exemple.com:443ma_base_vierge
autre.exemple.comaucune
pas de filtre, -d ma_base,ma_base_essaiindifférentma_base, ma_base_essai
--no-database-listindifférenterreur AccessDenied : « Database management functions blocked, admin disabled database listing. »

À lire dans ce tableau :

  • Le filtre est une expression régulière testée en début de nom (re.match) : ^ma_base laisse passer toutes les bases qui commencent ainsi. Termine par $ dès que tu vises une base précise.
  • %d vaut le premier mot du nom d'hôte, après retrait du port et d'un www. initial ; %h vaut l'hôte entier, lui aussi sans port ni www.. C'est le réglage classique d'un serveur qui sert un client par sous-domaine (dbfilter = ^%d$).
  • Sans filtre, -d (ou db_name dans le fichier) donne la liste exposée, séparée par des virgules. Avec un filtre, c'est le filtre qui décide.
  • list_db = False (ou --no-database-list) coupe la liste et le gestionnaire : la page affiche « The database manager has been disabled by the administrator » et un POST /web/database/create répond 403. Il faut alors une base désignée par db_name ou par le filtre.

Le filtre choisit ce qu'on voit, pas ce qu'on peut détruire

Le dbfilter n'est pas une barrière de sécurité. Les actions du gestionnaire contrôlent le mot de passe maître, pas le filtre : serveur lancé avec --db-filter='^ma_base$', un POST /web/database/drop sur ma_base_essai, absente de la liste, répond 303 et le journal écrit DROP DB: ma_base_essai. Le mot de passe maître donne la main sur toutes les bases du rôle. De même, sans db_name, les tâches planifiées tournent sur toutes ces bases, filtre ou pas (odoo/service/server.py:112-114).

Pour isoler des clients sur un même PostgreSQL : un rôle par instance, et en production list_db = False. Le diagnostic d'un gestionnaire qui refuse d'agir est dans Gestionnaire de bases Odoo 20 : Access Denied et mot de passe maître.

7. Le gestionnaire /web/database/manager et le mot de passe maître

Le gestionnaire web liste les bases filtrées, avec pour chacune Backup, Duplicate et Delete, et en bas Create Database, Restore Database et Set Master Password (web/static/src/public/database_manager.qweb.html:58-79). Une base créée par une autre version d'Odoo y porte une icône d'avertissement.

Chaque action (sauf le changement du mot de passe maître lui-même) vérifie d'abord que list_db est actif, puis le mot de passe maître, admin_passwd dans le fichier de configuration (web/controllers/database.py:132-141). Un mauvais mot de passe donne une page en 403 qui dit pourquoi :

$ curl -s -d master_pwd=faux -d master_pwd_new=x http://localhost:8069/web/database/change_password | grep -o 'Could not[^<]*'
Could not change_password database. Database management function blocked, bad admin password.

Trois règles sur ce mot de passe :

  • Sa valeur par défaut est admin (odoo/tools/config.py:230). Tant qu'il vaut admin, le gestionnaire affiche un avertissement et le premier mot de passe saisi dans une action devient le nouveau mot de passe maître (database.py:132-139).
  • Il est stocké haché, en pbkdf2_sha512 à 600 000 tours (config.py:23-25). Une valeur en clair dans le fichier reste acceptée. Après Set Master Password, la ligne devient : 
    admin_passwd = $pbkdf2-sha512$600000$…
  • Perdu, il ne se retrouve pas : on remplace la ligne par une nouvelle valeur et on redémarre. Pour le mot de passe d'un utilisateur, c'est un autre sujet : Odoo 20 mot de passe oublié : réinitialiser l'admin en shell ou SQL.

« Set Master Password » réécrit ton fichier de configuration

Pour enregistrer le nouveau mot de passe, Odoo relit le fichier, change la ligne et réécrit toutes les options (odoo/tools/config.py:1031-1039). Relevé sur un fichier qui commençait par un commentaire : après le changement, les commentaires ont disparu et une section [colors] de huit lignes a été ajoutée à la fin. Et si le compte qui fait tourner Odoo ne peut pas écrire ce fichier, la page revient sans erreur (seule la sortie d'erreur du serveur le signale) alors que le nouveau mot de passe ne vit qu'en mémoire, jusqu'au prochain redémarrage. Si ton odoo.conf est versionné ou commenté, change le mot de passe dans le fichier, à la main, et garde le gestionnaire pour le reste.

8. Neutraliser, sauvegarder, restaurer : le survol

Trois opérations complètent la gestion des bases ; on ne fait ici que les situer.

  • Neutraliser une copie (tâches planifiées, courriels, paiements) : case Neutralize du gestionnaire, option -n de db duplicate et de db load, ou odoo-bin neutralize sur une base existante. Détail et vérifications dans Copier la prod en base de test Odoo 20.
  • Sauvegarder : odoo-bin db dump ma_base ma_base.zip ou le bouton Backup produisent un zip (dump SQL, manifeste, filestore). Un pg_dump seul oublie le filestore.
  • Restaurer : odoo-bin db load ou Restore Database, sous un nouveau nom de préférence.

La sauvegarde planifiée, sa rotation et la restauration complète auront leur propre article dans cette série, à venir.

À retenir

  • Une base Odoo = une base PostgreSQL + un filestore : passe par Odoo (gestionnaire ou odoo-bin db) pour que les deux suivent.
  • Le rôle d'Odoo a besoin de CREATEDB et doit être propriétaire de ses bases ; Odoo ne voit pas les autres.
  • Dupliquer, renommer et supprimer coupent les connexions ouvertes sur la base concernée, la source comprise pour une duplication.
  • dbfilter filtre en début de nom et ne protège rien : la sécurité, c'est list_db = False, un mot de passe maître solide et un rôle par instance.
  • En 20, le service db de XML-RPC n'existe plus et PostgreSQL 16 est le minimum.
