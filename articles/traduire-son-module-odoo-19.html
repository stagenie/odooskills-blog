Marquer les chaînes avec _() et _t, extraire le catalogue .pot, écrire un fichier .po arabe et l'importer — jusqu'à voir le backend basculer en écriture de droite à gauche. Puis, quand le catalogue ne suffit pas, traduire une donnée directement par Python.

~15 minutes de lecture · démonstration Français → Arabe (RTL)

Ce que tu vas apprendre

① Marquer les chaînes traduisibles de ton code

_() côté Python, _t côté JavaScript, et l'extraction automatique des textes de tes vues QWeb — les trois sources d'un catalogue de traduction.

② Générer et remplir le catalogue .pot / .po

La commande odoo-bin i18n export produit le modèle ; un fichier .po par langue porte les traductions.

③ Importer et rendre le résultat — y compris en RTL

Charger l'arabe, importer le .po, et constater que le backend se retourne de droite à gauche sans effort supplémentaire.

Prérequis

  • Un module custom installable en Odoo 19 CE, et un accès serveur pour lancer odoo-bin.
  • Avoir déjà activé une deuxième langue — le sujet du premier article de la série.
  • Des notions de la structure d'un module (modèle, vue, assets JS).

Le cycle de traduction d'un module : .pot (modèle) → .po (par langue) → import.

Étape 1 — Marquer les chaînes à traduire

Odoo ne devine pas ce qui doit être traduit : c'est à toi de marquer les chaînes. Trois cas, trois outils.

Côté Python — la fonction _()

Toute chaîne destinée à l'utilisateur — un message d'erreur, une notification — s'enveloppe dans _(), importée depuis odoo :

from odoo import _, fields, models
from odoo.exceptions import UserError


class DemoOrder(models.Model):
    _name = 'blog.i18n.order'
    _description = "Commande de démonstration"

    name = fields.Char(string="Référence", required=True, default="Brouillon")
    state = fields.Selection(
        selection=[('draft', "Brouillon"), ('confirmed', "Confirmée")],
        string="État", default='draft',
    )

    def action_confirm(self):
        self.ensure_one()
        if self.state == 'confirmed':
            raise UserError(_("Cette commande est déjà confirmée."))
        self.state = 'confirmed'
        return {
            'type': 'ir.actions.client', 'tag': 'display_notification',
            'params': {'message': _("Commande confirmée avec succès."), 'type': 'success'},
        }

Les libellés de champs (string="Référence"), les valeurs de sélection ("Brouillon", "Confirmée") et la description du modèle sont récupérés automatiquement : pas de _() à mettre dessus.

Piège classique : _("Bonjour %s") % name, jamais _("Bonjour %s" % name). On traduit le gabarit, on interpole ensuite — sinon la valeur se retrouve figée dans le texte à traduire. Pour une chaîne construite au chargement du module, on utilise _lt() (traduction paresseuse).

Côté JavaScript — la fonction _t

Dans le code client (OWL, services), l'équivalent s'importe depuis le cœur web :

import { _t } from "@web/core/l10n/translation";

const message = _t("Bonjour depuis le module de démonstration.");

En Odoo 19, les fichiers JS d'un addon sont traités comme des modules ES natifs : l'ancienne annotation /** @odoo-module **/ n'est plus nécessaire.

Côté QWeb — automatique

Le texte statique d'une vue est extrait sans rien marquer. Ce simple bloc dans le formulaire finira dans le catalogue :

<div class="alert alert-info" role="alert">
    Bienvenue sur la commande de démonstration.
</div>

Étape 2 — Générer le catalogue .pot

Odoo 19 introduit une commande dédiée odoo-bin i18n, avec les sous-commandes export, import et loadlang. Pour produire le modèle de traduction (le .pot) de ton module :

odoo-bin i18n export -d ma_base blog_i18n_demo

Le fichier atterrit dans blog_i18n_demo/i18n/blog_i18n_demo.pot. Sans option -l, c'est le modèle (pot, msgstr vides) qui est généré ; c'est exactement ce qu'on veut comme point de départ.

Son contenu est instructif : chaque terme est annoté de sa provenance.

#. module: blog_i18n_demo
#. odoo-python
#: code:addons/blog_i18n_demo/models/demo_order.py:0
msgid "Cette commande est déjà confirmée."
msgstr ""

#. module: blog_i18n_demo
#. odoo-javascript
#: code:addons/blog_i18n_demo/static/src/js/greeting.js:0
msgid "Bonjour depuis le module de démonstration."
msgstr ""

#. module: blog_i18n_demo
#: model_terms:ir.ui.view,arch_db:blog_i18n_demo.view_blog_i18n_order_form
msgid "Bienvenue sur la commande de démonstration."
msgstr ""

#. module: blog_i18n_demo
#: model:ir.model.fields.selection,name:...__state__draft
msgid "Brouillon"
msgstr ""

Les commentaires #. odoo-python et #. odoo-javascript distinguent la source de chaque chaîne — pratique pour repérer d'un coup d'œil ce qui vient du serveur et ce qui vient du client.

Étape 3 — Traduire dans un fichier .po

On duplique le .pot en ar_001.po (le code de l'arabe) et on remplit chaque msgstr. La seule règle : ne jamais toucher au msgid, c'est la clé de correspondance.

# blog_i18n_demo/i18n/ar_001.po
msgid ""
msgstr ""
"Language: ar_001\n"
"Content-Type: text/plain; charset=UTF-8\n"

#. module: blog_i18n_demo
msgid "Cette commande est déjà confirmée."
msgstr "هذا الطلب مؤكد بالفعل."

#. module: blog_i18n_demo
msgid "Confirmer la commande"
msgstr "تأكيد الطلب"

#. module: blog_i18n_demo
msgid "Brouillon"
msgstr "مسودة"

Le fichier peut aussi s'éditer avec un outil dédié (Poedit et consorts), mais un éditeur de texte suffit parfaitement pour un module de cette taille.

Étape 4 — Importer et voir le résultat

Deux commandes : d'abord charger l'arabe (si ce n'est pas déjà fait), puis importer le fichier .po en écrasant l'existant avec -w :

odoo-bin i18n loadlang -d ma_base -l ar_001
odoo-bin i18n import  -d ma_base -l ar_001 -w blog_i18n_demo/i18n/ar_001.po

Il ne reste qu'à régler la langue de l'utilisateur sur l'arabe. Le formulaire du module apparaît alors traduit — et comme l'arabe est déclaré droite-à-gauche, Odoo inverse toute la disposition : la barre latérale passe à droite, les champs s'alignent à droite, les boutons migrent à gauche.

Étape 5 — Traduire une donnée par Python

Le catalogue .po couvre le code (libellés, messages). Mais parfois il faut traduire une donnée — le nom d'un produit importé, une valeur créée par script — directement, sans passer par l'interface. Comme un champ translate=True est un jsonb, Odoo 19 offre trois gestes propres, à essayer dans un odoo-bin shell.

Écrire la valeur d'une seule langue

Il suffit de fixer la langue dans le contexte : l'écriture ne touche que cette langue, les autres restent intactes.

>>> demo = env['product.template'].browse(315)
>>> demo.with_context(lang='ar_001').write({'name': 'حامل جداري قابل للتعديل'})

Écrire plusieurs langues d'un coup

La méthode update_field_translations prend un dictionnaire {code_langue: valeur} et écrit toutes les langues en une passe :

>>> demo.update_field_translations('name', {
...     'en_US': 'Adjustable wall mount',
...     'ar_001': 'حامل جداري قابل للتعديل',
... })

Relire toutes les traductions

Symétriquement, get_field_translations renvoie la valeur de chaque langue active :

>>> demo.get_field_translations('name')
([{'lang': 'ar_001', 'source': 'Adjustable wall mount', 'value': 'حامل جداري قابل للتعديل'},
  {'lang': 'en_US', 'source': 'Adjustable wall mount', 'value': 'Adjustable wall mount'},
  {'lang': 'fr_FR', 'source': 'Adjustable wall mount', 'value': 'Support mural réglable'}],
 {'translation_type': 'char', 'translation_show_source': False})

Et sous le capot, une seule cellule jsonb porte les trois versions :

{
    "en_US": "Adjustable wall mount",
    "fr_FR": "Support mural réglable",
    "ar_001": "حامل جداري قابل للتعديل"
}

Règle d'or : écris toujours via l'ORM (with_context, update_field_translations), jamais par un UPDATE SQL brut sur la colonne. La clé source en_US doit toujours exister ; l'effacer d'un jsonb à la main fait planter la lecture du champ.

⚠️ En Odoo 19 — la commande odoo-bin i18n

Les anciens réflexes --i18n-export et --i18n-import, passés comme options du serveur, sont supplantés par une sous-commande à part entière : odoo-bin i18n export, import, loadlang. Plus lisible, et surtout scriptable proprement — c'est la forme à privilégier en 19.

À distinguer : les traductions de code (_(), _t, QWeb) vivent dans le catalogue chargé depuis les .po ; les traductions de données d'un enregistrement (un champ translate=True) vivent, elles, dans une colonne jsonb — le sujet de l'article 1.

À retenir

  • Marquer : _() en Python, _t en JavaScript, rien à faire pour le texte QWeb (extrait tout seul).
  • Interpoler après la traduction : _("… %s") % valeur, jamais l'inverse.
  • Le cycle .pot → .po → import passe par odoo-bin i18n export / import / loadlang.
  • Le RTL est gratuit : déclarer la langue droite-à-gauche suffit, Odoo inverse la mise en page sans code supplémentaire.

Traduire du code, c'est le métier du développeur. Mais un chef de projet ou un consultant a besoin de traduire des données — produits, courriels, libellés — sans ouvrir un éditeur. C'est l'objet de la série jumelle, côté fonctionnel.
