Odoo 20 mot de passe oublié : réinitialiser l'admin en shell ou SQL

L'écran de connexion refuse l'administrateur et plus personne n'a ses droits pour changer son mot de passe. Il te reste l'accès au serveur : quatre lignes dans odoo-bin shell, ou une requête SQL, et tu te reconnectes sans redémarrer Odoo.

~5 minutes de lecture · niveau débutant · série Astuces dev Odoo 20

Édition : Community. Vérifié sur Odoo 20.0 Community, octobre 2026, base de démonstration avec un serveur lancé. Les mots de passe montrés (Demo-Odoo20-a, -b, -c) sont des valeurs de démonstration : choisis les tiens.

La réponse en bref

  1. Shell (le plus sûr) : env['res.users'].search([('login', '=', 'admin')]).password = 'nouveau' puis env.cr.commit(), dans odoo-bin shell -d ma_base.
  2. SQL (sans Python) : UPDATE res_users SET password = 'nouveau' WHERE login = 'admin'; Odoo accepte ce texte en clair et le remplace par un hachage à la première connexion.
  3. Pas de redémarrage : la connexion marche tout de suite.
  4. Si l'écran demande ensuite un code de vérification, la double authentification est active : UPDATE res_users SET totp_secret = NULL WHERE login = 'admin';

1. Par le shell : retrouver l'admin, puis changer son mot de passe

Avant de changer un mot de passe, vérifie quel compte est administrateur : son identifiant n'est pas toujours admin, surtout sur une base créée depuis le gestionnaire de bases, où l'identifiant est souvent une adresse électronique. Le groupe base.group_system (rôle Administrateur) donne la réponse. Le second script change le mot de passe. Les deux passent à odoo-bin shell par redirection d'entrée, avec le même fichier de configuration que ton serveur :

Ce qui se passe à l'affectation admin.password = '…' : le champ password de res.users est un champ calculé dont la méthode inverse, _set_password, hache la valeur avant de l'écrire en base. Tu ne manipules jamais le hachage toi-même. Le shell tourne en super-utilisateur, il peut donc modifier l'administrateur sans connaître l'ancien mot de passe.

Le serveur peut rester allumé : la connexion avec Demo-Odoo20-a a été acceptée aussitôt après le script, et l'ancien mot de passe refusé. En production, lance plutôt le shell avec --no-http (comme ici) pour ne pas ouvrir un second port HTTP à côté du service.

Pour un autre utilisateur, remplace simplement le login dans le search. Dans l'interface, un administrateur qui se connecte peut aussi le faire depuis la fiche de l'utilisateur ; le shell sert quand plus personne ne peut entrer.

Sans env.cr.commit(), rien n'est enregistré

odoo-bin shell annule la transaction à sa sortie. Le même script sans la ligne env.cr.commit() affiche bien fait pour admin, mais la connexion avec le nouveau mot de passe échoue (AccessDenied, et dans le journal Login failed for login:admin from 127.0.0.1) : c'est toujours l'ancien qui marche. Pas de message, pas d'avertissement : le print te trompe.

2. En SQL : le mot de passe en clair, haché à la connexion

Sans accès au Python d'Odoo (une base restaurée sur un autre serveur, un conteneur dont seul PostgreSQL est joignable), une requête suffit. La colonne s'appelle password, dans la table res_users :

UPDATE res_users SET password = 'Demo-Odoo20-b' WHERE login = 'admin';

Pourquoi ça marche : Odoo vérifie les mots de passe avec une CryptContext de passlib qui connaît deux formats, pbkdf2_sha512 et plaintext, ce dernier marqué « déprécié ». Un mot de passe en clair est donc reconnu, puis, la connexion réussie, remplacé par un hachage pbkdf2-sha512 à 600 000 tours. La dernière requête le montre.

Tant que personne ne s'est connecté, le mot de passe reste lisible dans la table, et dans toute sauvegarde faite entre-temps. Pour ne jamais l'écrire en clair, calcule le hachage toi-même avec le passlib du venv d'Odoo, et colle-le dans l'UPDATE :

$ venv/bin/python -c "from passlib.context import CryptContext; print(CryptContext(['pbkdf2_sha512'], pbkdf2_sha512__rounds=600_000).hash('Demo-Odoo20-c'))"
$pbkdf2-sha512$600000$D6E0hpASImSs1VrL.b93zg$XcuekzBtCmvvVk7bt9n0q7TnEx0f/BB2u5qojAnFIojHwec2vr9ute128Q2yXEWESoNQuOJ.KXsVR01Dkg5dSA
UPDATE res_users SET password = '$pbkdf2-sha512$600000$D6E0hpASImSs1VrL.b93zg$XcuekzBtCmvvVk7bt9n0q7TnEx0f/BB2u5qojAnFIojHwec2vr9ute128Q2yXEWESoNQuOJ.KXsVR01Dkg5dSA'
WHERE login = 'admin';

Connexion acceptée avec Demo-Odoo20-c. Le nombre de tours (600 000) est le minimum fixé dans res_users.py ; un paramètre système password.hashing.rounds plus élevé l'augmente pour les prochains hachages. Tape cette requête dans la console psql : passée par psql -c "…", les $ du hachage seraient interprétés par Bash.

3. Le mot de passe passe, mais Odoo demande un code

Le module auth_totp (double authentification) s'installe automatiquement avec le client web. Si l'administrateur l'avait activée et n'a plus son téléphone, le bon mot de passe mène à un second écran :

Le secret est rangé dans la colonne totp_secret de res_users. La vider désactive la double authentification pour ce compte :

UPDATE res_users SET totp_secret = NULL WHERE login = 'admin';

Après cette requête, la connexion avec le seul mot de passe aboutit de nouveau. Pense à réactiver la double authentification une fois l'accès retrouvé.

À ne pas confondre : le mot de passe maître (admin_passwd du fichier de configuration) protège le gestionnaire de bases, pas la connexion à une base. Le changer ne rouvre pas l'accès à l'administrateur, et inversement.

À retenir

  • Shell : user.password = '…' puis env.cr.commit(), sinon tout est annulé à la sortie.
  • SQL : un mot de passe en clair dans res_users.password est accepté, puis haché à la première connexion.
  • Pour ne rien laisser en clair, colle un hachage pbkdf2-sha512 calculé avec passlib.
  • Code de vérification demandé : totp_secret = NULL sur le compte.
