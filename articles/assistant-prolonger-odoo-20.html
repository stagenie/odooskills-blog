L'assistant en Odoo 20 : prolonger en lot

Prolonger un emprunt, c'est ouvrir sa fiche et changer la durée. En prolonger quatre avant les vacances, c'est quatre fiches. Un assistant fait le travail en une fois : on coche dans la liste, on choisit « Prolonger » dans le menu Actions, on saisit un nombre de jours. Derrière, un TransientModel, un modèle qui ne garde rien longtemps — à condition, en Odoo 20, de le lui dire.

~14 minutes de lecture · niveau intermédiaire · parcours Framework & ORM

Ce que tu vas apprendre

Écrire

Un TransientModel qui reçoit la sélection de la liste et agit dessus.

Brancher

Une action liée au menu Actions, une fenêtre avec pied de page, et son droit d'accès.

Nettoyer

La durée de vie des assistants, qu'Odoo 20 ne respecte plus sans déclaration explicite.

Prérequis

  • Le module biblio des articles précédents : emprunts avec chatter, groupes « Accueil » et « Bibliothécaire », fichier security/ir.access.csv.
  • Quelques emprunts en cours, et au moins un emprunt rendu.
  • Le serveur Odoo 20 joignable sur http://localhost:8069, base biblio.

1. Un modèle qui ne dure pas

Un assistant (on dit aussi wizard) est un modèle comme les autres, à une différence près : il hérite de models.TransientModel. Sa table existe bel et bien en base, ses enregistrements aussi, le temps de remplir la fenêtre et de cliquer sur le bouton. Ensuite, une tâche planifiée de nettoyage les supprime. On y met donc ce qui sert à une opération : les emprunts choisis, un nombre de jours, un motif. Rien de ce qu'on veut retrouver demain.

La dernière ligne vient du champ Many2one lui-même : à la mise à jour de la base, un Many2one d'un modèle ordinaire vers un modèle transitoire lève ValueError: Many2one … from Model to TransientModel is forbidden (odoo/orm/fields_relational.py). Normal : l'emprunt survivrait à l'assistant qu'il désigne.

2. Le modèle de l'assistant

Un dossier wizard/ à côté de models/, importé depuis le __init__.py du module (from . import wizard), et dedans library_loan_extend.py :

from markupsafe import Markup

from odoo import api, fields, models
from odoo.exceptions import UserError


class LibraryLoanExtend(models.TransientModel):
    _name = 'library.loan.extend'
    _description = "Prolonger des emprunts"
    # Explicite : en 20.0, la valeur héritée tombe à 0 dans la tâche de nettoyage.
    _transient_max_hours = 1.0

    loan_ids = fields.Many2many(
        'library.loan',
        string="Emprunts",
        default=lambda self: self._default_loan_ids(),
    )
    days = fields.Integer(string="Jours supplémentaires", default=7, required=True)
    reason = fields.Char(string="Motif")

    @api.model
    def _default_loan_ids(self):
        if self.env.context.get('active_model') != 'library.loan':
            return False
        return self.env['library.loan'].browse(self.env.context.get('active_ids', []))

    def action_extend(self):
        self.ensure_one()
        if self.days <= 0:
            raise UserError("Le nombre de jours doit être positif.")
        rendus = self.loan_ids.filtered(lambda e: e.state == 'returned')
        if rendus:
            raise UserError(
                "Ces emprunts sont déjà rendus : %s" % ", ".join(rendus.mapped('reference'))
            )
        for emprunt in self.loan_ids:
            emprunt.duration += self.days
            corps = Markup("Prolongé de <b>%s</b> jour(s).") % self.days
            if self.reason:
                corps += Markup(" Motif : %s") % self.reason
            emprunt.message_post(body=corps, message_type='comment', subtype_xmlid='mail.mt_note')
        return {'type': 'ir.actions.act_window_close'}

Trois choses à lire dans ce code :

  • La sélection arrive par le contexte. Quand l'assistant est ouvert depuis le menu Actions d'une liste, le client web met dans le contexte active_model (le modèle de la liste) et active_ids (les lignes cochées). La valeur par défaut de loan_ids les lit, et vérifie d'abord le modèle : ouvert depuis ailleurs, avec des identifiants de livres, l'assistant démarre vide au lieu de charger n'importe quels emprunts.
  • On prolonge la durée, pas l'échéance. date_due est un champ calculé stocké à partir de date_out et duration depuis l'article sur les retards ; ajouter des jours à duration suffit, l'échéance suit.
  • La note passe par Markup. Le motif est saisi par l'utilisateur : Markup(" Motif : %s") % self.reason l'échappe, comme on l'a vu avec le chatter.

Essai depuis la console, en tant qu'utilisateur de l'accueil, avec le contexte que le client web enverra :

ids = env['library.loan'].search([('reference', 'in', ['EMP/2026/0002', 'EMP/2026/0003'])]).ids
W = env['library.loan.extend'].with_user(accueil).with_context(active_model='library.loan', active_ids=ids)
w = W.create({'days': 5})
w.action_extend()
loan_ids par défaut : ['EMP/2026/0003', 'EMP/2026/0002'] days 5 action : {'type': 'ir.actions.act_window_close'} date_due : [2026-09-15, 2026-09-03] -> [2026-09-20, 2026-09-08] duration [19, 19] active_model='library.book' -> loan_ids : library.loan() avec un emprunt rendu -> UserError: Ces emprunts sont déjà rendus : EMP/2026/0007

Le contrôle des emprunts rendus est fait avant toute écriture : si un seul emprunt de la sélection est rendu, aucun n'est prolongé. Prolonger les autres en silence laisserait croire que tout est passé. (Et la restriction posée à l'article sur les droits d'accès refuserait de toute façon d'écrire sur un emprunt rendu — mais avec un message qui ne dit pas lequel.)

3. La fenêtre et l'entrée du menu Actions

Un fichier views/library_loan_extend_views.xml, déclaré dans le manifeste après les vues de l'emprunt :

<record id="library_loan_extend_view_form" model="ir.ui.view">
    <field name="name">library.loan.extend.form</field>
    <field name="model">library.loan.extend</field>
    <field name="arch" type="xml">
        <form string="Prolonger des emprunts">
            <group>
                <field name="days"/>
                <field name="reason"/>
            </group>
            <field name="loan_ids">
                <list>
                    <field name="reference"/>
                    <field name="copy_id"/>
                    <field name="member_id"/>
                    <field name="date_due"/>
                    <field name="state"/>
                </list>
            </field>
            <footer>
                <button name="action_extend" type="object" string="Prolonger" class="btn-primary"/>
                <button string="Annuler" special="cancel" class="btn-secondary"/>
            </footer>
        </form>
    </field>
</record>

<record id="library_loan_extend_action" model="ir.actions.act_window">
    <field name="name">Prolonger</field>
    <field name="res_model">library.loan.extend</field>
    <field name="view_mode">form</field>
    <field name="target">new</field>
    <field name="binding_model_id" ref="model_library_loan"/>
    <field name="binding_view_types">list</field>
</record>
  • target="new" ouvre l'action dans une fenêtre par-dessus la liste.
  • <footer> remplace les boutons habituels du formulaire (enregistrer, annuler) par les siens ; special="cancel" ferme sans rien faire.
  • binding_model_id accroche l'action au menu Actions des emprunts, sans aucun menu ni bouton à écrire. binding_view_types vaut list,form par défaut (odoo/addons/base/models/ir_actions.py) ; ici, list seul : l'assistant est fait pour des sélections.

4. Le droit d'accès de l'assistant

Un assistant est un modèle : sans ligne dans ir.access.csv, personne ne peut en créer un enregistrement — pas même l'administrateur. Une ligne pour l'accueil suffit, le groupe « Bibliothécaire » l'hérite :

access_library_loan_extend_desk,Prolonger des emprunts : assistant,library.loan.extend,group_library_desk,cr,

cr et pas plus : le client web crée l'enregistrement de l'assistant au clic sur « Prolonger », puis appelle la méthode. Essayé depuis l'écran avec ce seul droit, tout passe ; en console, une modification de l'assistant est refusée (Vous n'êtes pas autorisé à modifier les enregistrements 'Prolonger des emprunts'), ce qui ne gêne personne. La suppression, elle, est faite par la tâche de nettoyage, en superutilisateur.

Sans la ligne : l'entrée disparaît, et Odoo 20 ne dit plus rien

Même module, sans la ligne d'accès. La mise à jour sort sans erreur ni avertissement, et l'utilisateur de l'accueil qui coche ses quatre emprunts voit ceci :

Le serveur ne propose une action liée qu'aux utilisateurs qui peuvent lire son res_model (get_bindings, odoo/addons/base/models/ir_actions.py). Pas de droit, pas d'entrée — sans message. En console, la vraie raison s'affiche :

AccessError: Vous n'êtes pas autorisé à créer des enregistrements 'Prolonger des emprunts' (library.loan.extend). Aucun groupe n'autorise actuellement cette opération.

Changement par rapport à Odoo 19

En 19, la même mise à jour écrivait dans le journal un avertissement The models ['library.loan.extend'] have no access rules in module biblio, consider adding some, avec la ligne CSV à copier (odoo/modules/loading.py). Ce contrôle n'existe plus en 20 : le seul signe d'un droit oublié est une entrée qui manque à l'écran. Le filtrage du menu Actions, lui, est le même dans les deux versions.

Une autre idée reçue à écarter : un assistant n'est pas réservé à celui qui l'a créé. Aucune restriction n'est ajoutée d'office ; en console, l'administrateur lit sans difficulté l'assistant ouvert par l'accueil. Le compositeur de courriels du module mail se protège lui-même, par une restriction sur create_uid. Pour prolonger des emprunts, ce n'est pas nécessaire.

5. Le nettoyage, à déclarer en Odoo 20

Chaque ouverture de l'assistant laisse une ligne dans library_loan_extend, et ses liens dans la table library_loan_library_loan_extend_rel. Deux réglages bornent leur vie, lus dans la configuration du serveur :

  • _transient_max_hours : option --transient-age-limit, 1 heure par défaut ;
  • _transient_max_count : option --osv-memory-count-limit, 0 (pas de limite) par défaut.

La tâche planifiée « Base : données internes de l'aspiration automatique », une fois par jour, appelle _transient_vacuum() sur chaque assistant et supprime ce qui a dépassé l'heure. Les liens de la table de relation partent avec, par ON DELETE CASCADE.

En 20.0, sans déclaration, rien n'est jamais supprimé

Première version de l'assistant, sans la ligne _transient_max_hours. Un enregistrement vieilli de trois heures en SQL, puis la tâche lancée à la main :

env.ref('base.autovacuum_job').method_direct_trigger()
DEBUG ir_autovacuum: Calling library.loan.extend()._transient_vacuum() DEBUG ir_autovacuum: library.loan.extend()._transient_vacuum vacuumed 'library.loan.extend' records, remaining False valeurs lues par la classe : 0 0 ← _transient_max_count, _transient_max_hours dans un nouveau processus : [(17,), (18,)] ← la ligne de trois heures est toujours là

La tâche passe, et ne supprime rien : elle a lu une durée de vie de 0, qui veut dire « illimitée ». La cause est dans odoo/tools/func.py : les deux réglages sont des lazy_classproperty écrites avec une lambda, et en 20 leur valeur est mise en cache sous un nom tiré de celui de la fonction — <lambda> pour les deux. La première lue impose sa valeur à l'autre. Or, pour trouver les méthodes à appeler, la tâche passe d'abord en revue tous les attributs de chaque classe (inspect.getmembers, dans odoo/addons/base/models/ir_autovacuum.py), par ordre alphabétique : _transient_max_count (0) est lue avant _transient_max_hours, qui vaut alors 0 à son tour — avant même l'appel de _transient_vacuum().

La même petite classe, sous les deux versions :

class T:
    _transient_max_count = lazy_classproperty(lambda _: 0)
    _transient_max_hours = lazy_classproperty(lambda _: 1.0)
inspect.getmembers(T)
print("heures", T._transient_max_hours, "nombre", T._transient_max_count)
Odoo 19 : heures 1.0 nombre 0 Odoo 20 : heures 0 nombre 0

Le remède tient en une ligne : déclarer la durée dans l'assistant, _transient_max_hours = 1.0. Un attribut ordinaire, plus de cache partagé. Même essai, la tâche supprime la ligne de trois heures et garde la récente :

INFO odoo.models.unlink: User #1 deleted library.loan.extend records with IDs: [17] dans un nouveau processus : [(18,)]

Relire le résultat dans un nouveau processus n'est pas un détail : la console qui a lancé la tâche garde l'image de la base d'avant, et voit encore la ligne supprimée.

Récapitulatif

  • Un assistant est un TransientModel : une vraie table, vidée par une tâche planifiée.
  • La sélection de la liste arrive par active_model et active_ids ; vérifier le modèle avant de s'en servir.
  • Contrôler toute la sélection avant d'écrire : tout ou rien.
  • binding_model_id suffit à placer l'assistant dans le menu Actions.
  • Sans droit de lecture sur l'assistant, l'entrée disparaît du menu ; Odoo 20 ne prévient plus au chargement.
  • En 20.0, déclarer _transient_max_hours dans l'assistant, sinon il n'est jamais nettoyé.
