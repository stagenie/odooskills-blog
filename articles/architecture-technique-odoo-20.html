Architecture technique d'Odoo 20 : couches, registre, requêtes

PostgreSQL, le registre, les modules, la couche HTTP, les workers et le client web OWL 3 : ce qui se trouve sous le capot d'Odoo 20, chaque couche observée sur un serveur qui tourne, et ce qui a changé depuis la 19.

~14 minutes de lecture · niveau débutant · parcours Fondamentaux

Ce que tu vas apprendre

Les couches

Du navigateur à PostgreSQL : à quoi sert chaque étage, où il vit dans le code source, ce que ton module y ajoute.

Le trajet d'une requête

Session, registre, route, authentification, dispatcher, ORM, transaction : et la ligne de journal qui résume le tout.

Ce qui change en 20

Python 3.12, PostgreSQL 16, ir.access, zoneinfo, OWL 3, écoute sur 127.0.0.1 : chaque écart prouvé, rien de supposé.

Prérequis

  • Un Odoo 20 Community qui démarre (voir Installer Odoo 20 sur Ubuntu et le lancer dans PyCharm) et une base de test avec l'application Ventes.
  • Un terminal : on lance odoo-bin, odoo-bin shell et curl.
  • Aucune connaissance de l'ORM n'est demandée : cet article est la carte, les suivants sont le terrain.

Tu viens d'Odoo 19 ? L'article Architecture technique Odoo 19 reste valable pour ta version. Celui-ci reprend la même question pour Odoo 20, avec des sorties relevées sur un serveur 20.0.

Odoo est une application web écrite en Python, posée sur PostgreSQL. Un seul programme, odoo-bin, sert à la fois les écrans, l'API et les tâches planifiées. Entre le clic dans le navigateur et la ligne écrite en base, la requête traverse une pile de couches qu'il vaut mieux connaître avant d'écrire son premier module : c'est là que se logent la plupart des « ça marche chez moi, pas en production ».

1. Les couches, un seul programme

Chaque couche a son dossier dans le code source d'Odoo 20, et ton module intervient sur la plupart d'entre elles sans jamais les recoder :

CoucheDans le source 20.0Ce que ton module y apporte
Client webaddons/web/static/src/, OWL dans web/static/lib/owl/ vues XML, composants OWL, styles
HTTPodoo/http/ (router, dispatcher, session, stream…) rien : la couche est fournie
Contrôleurscontrollers/ de chaque module, table des routes dans ir.httptes routes @http.route, si tu en as besoin
Registreodoo/orm/registry.py, chargement dans odoo/modules/loading.py tes classes de modèles, rangées au chargement du module
ORModoo/orm/ (models, fields, domains, environments) champs, méthodes, contraintes, droits ir.access
PostgreSQLodoo/sql_db.py (pool de connexions, curseurs) tes tables, créées par l'ORM
Filestoredossier filestore/<base> du répertoire de données les fichiers de tes champs binaires et pièces jointes
Serveurodoo/service/server.py (threaded, prefork, gevent) tes actions planifiées, exécutées par les fils ou workers cron

La particularité d'Odoo par rapport à un framework web classique tient en une phrase : tu n'écris presque jamais de contrôleur. Le client web appelle les méthodes de tes modèles par une route générique, /web/dataset/call_kw, et l'API externe fait de même par /json/2. Ton travail se concentre sur le modèle et la vue ; le reste de la pile est fourni et commun à tous les modules.

2. PostgreSQL et le filestore : là où vivent les données

Une base PostgreSQL par instance cliente : tout y est, les données métier comme la configuration (modules installés, vues, droits, paramètres). Chaque modèle a sa table : res.partner devient res_partner, sale.order devient sale_order. Les fichiers (pièces jointes, images) vont dans le filestore, une arborescence sur disque par base, référencée par la colonne store_fname de ir_attachment. Une sauvegarde sans le filestore est une sauvegarde incomplète.

Odoo 20 relève le minimum à PostgreSQL 16 (13 en 19.0) et Python à 3.12 (3.10 en 19.0). Sur la base de démonstration :

>>> odoo.release.MIN_PY_VERSION, odoo.release.MAX_PY_VERSION, odoo.release.MIN_PG_VERSION
((3, 12), (3, 14), 16)
>>> env.cr.execute("show server_version"); env.cr.fetchone()[0]
'16.15 (Ubuntu 16.15-0ubuntu0.24.04.1)'

Dans la base, à côté des tables des modèles, Odoo tient des tables techniques que tu croiseras dans psql. Les plus utiles à reconnaître sont les tables de signalisation :

$ psql -d ma_base -Atc "select relname from pg_class where relname like 'orm_signaling%' and relkind = 'r' order by 1"
orm_signaling_assets
orm_signaling_default
orm_signaling_groups
orm_signaling_registry
orm_signaling_routing
orm_signaling_stable
orm_signaling_templates

Elles servent à prévenir les autres processus Odoo qui partagent la base : quand un module est installé, une ligne est ajoutée à orm_signaling_registry et chaque processus recharge son registre à sa prochaine requête ; les autres tables font de même pour les caches (assets, routes, groupes, gabarits…).

PostgreSQL plus ancien que 16 : un simple avertissement

Odoo 20 ne refuse pas de démarrer sur un PostgreSQL plus ancien que 16 : il compare la version du serveur à MIN_PG_VERSION et émet seulement un avertissement (odoo/sql_db.py:712-713, journal py.warnings), comme le faisait déjà la 19 avec son minimum de 13. Or le source 20.0 emploie déjà de la syntaxe récente, par exemple un index unique NULLS NOT DISTINCT sur les taux de change (odoo/addons/base/models/res_currency.py:431), apparue avec PostgreSQL 15 : sur un PostgreSQL 14, cet index ne peut pas se créer, et même sur un 15 rien n'est garanti. Un démarrage réussi sur une version plus ancienne que 16 ne prouve donc rien : vérifie la version du serveur avant tout le reste.

3. Le registre : les modèles d'une base, assemblés en mémoire

Le registre est la pièce la moins visible et la plus centrale. Pour chaque base qu'il sert, Odoo charge les modules installés dans l'ordre de leurs dépendances et assemble une classe par modèle à partir de tous les fichiers Python qui le définissent ou l'étendent. Le résultat est gardé en mémoire tant que personne ne signale de changement. Dans odoo-bin shell (voir le shell Odoo 20), après l'installation du petit module de la section suivante :

>>> env.registry
<odoo.orm.registry.Registry object at 0x7f68f0db5b80>
>>> len(env.registry)
451
>>> 'mon_module.mon_module' in env.registry
True
>>> env['mon_module.mon_module']._table
'mon_module_mon_module'
>>> [c.__module__ for c in type(env['res.partner']).__mro__[:4]]
['odoo.orm.models', 'odoo.addons.sale.models.res_partner', 'odoo.addons.account_edi_ubl_cii.models.res_partner', 'odoo.addons.stock.models.res_partner']

Quatre choses à retenir de cette sortie :

  • 451 modèles dans ce registre : ceux des 70 modules installés sur cette base, pas ceux des 679 modules trouvés dans l'addons_path. Un modèle d'un module non installé n'existe pas, même si son code est sur le disque.
  • La classe de res.partner est une pile : la classe assemblée par le registre, puis les extensions de sale, account_edi_ubl_cii, stock… La plus récemment chargée est en tête : ton super() appelle l'extension chargée avant la tienne. Ici, une méthode redéfinie dans l'extension de sale qui appelle super() passe la main à celle d'account_edi_ubl_cii, puis à stock, et ainsi de suite jusqu'au code de base.
  • Un registre par base : deux bases sur le même serveur peuvent avoir des modèles différents. C'est le registre, pas le code, qui décide de ce qui existe.
  • env relie un registre, un curseur PostgreSQL, un utilisateur et un contexte. C'est par lui que tout code métier passe : env['res.partner'] donne un recordset vide du modèle.

Le même registre sert le serveur web, le shell, les commandes odoo-bin module et les tests : c'est pour cela qu'une erreur de chargement d'un module bloque tout, comme on va le voir.

4. Les modules et l'addons_path

Un module est un dossier Python avec un __manifest__.py. Odoo le cherche dans les dossiers de l'addons_path (option --addons-path ou clé du fichier de configuration) ; sur un serveur, on y met d'ordinaire …/odoo/addons et un dossier à soi, par exemple …/mes_modules. Le squelette le plus rapide reste scaffold :

$ odoo-bin scaffold mon_module …/mes_modules
$ find mon_module -type f | sort

La trace se lit comme une coupe de l'architecture : le registre (Registry.new) charge les modules (load_modules), qui chargent leurs fichiers de données (load_data), qui demandent au registre le modèle nommé par le fichier CSV. Ce modèle, ir.model.access, n'existe plus en Odoo 20.

Le scaffold d'Odoo 20 génère encore l'ancien fichier de droits

Le gabarit de scaffold écrit toujours security/ir.model.access.csv au format 19 (odoo/cli/templates/default/security/ir.model.access.csv.template). En Odoo 20, les droits d'accès et les règles d'enregistrement sont réunis dans un seul modèle, ir.access (odoo/addons/base/models/ir_access.py:64-66). Supprime le fichier généré et écris security/ir.access.csv :

id,name,model_id,group_id/id,operation

Avec ce fichier et le manifeste qui le cite, le même -i mon_module se termine sans erreur (« Registry loaded »). Le détail des colonnes, des groupes et du domaine est dans Les droits d'accès en Odoo 20 : ir.access.

Deuxième règle de l'addons_path : la version du manifeste. Odoo n'installe que les modules dont la version commence par la série courante (20.0.x.y.z, ou une version courte comme 0.1, complétée en 20.0.0.1). Le même module, manifeste réglé sur 19.0.1.0.0 :

$ odoo-bin -c odoo.conf -d ma_base --addons-path=…/odoo/addons,…/mes_modules -i mon_module19 --stop-after-init --no-http
WARNING ma_base odoo.modules.module: The module mon_module19 has an incompatible version, setting installable=False
$ echo $?
0
$ psql -d ma_base -Atc "select name, state from ir_module_module where name = 'mon_module19'"
mon_module19|uninstallable

Code retour 0, aucune erreur : seul l'avertissement dit que rien n'a été installé. La règle n'est pas nouvelle (la même fonction check_version existe en 19.0), mais c'est le premier piège d'un portage : un module 19 recopié tel quel dans un addons_path Odoo 20 est ignoré sans bruit. La liste des erreurs qui suivent, une fois la version changée, est dans Module Odoo 19 sous Odoo 20 : les messages d'erreur et leur correctif.

5. La couche HTTP : d'une adresse à une méthode Python

En Odoo 20, la couche HTTP n'est plus un gros fichier odoo/http.py mais un paquet, odoo/http/ : router.py (l'application WSGI et le service d'une requête), dispatcher.py, session.py, stream.py, retrying.py… Les imports d'un module ordinaire ne changent pas : from odoo.http import request, route, Controller, Response fonctionne toujours. Voici le trajet d'une requête du client web :

(/jsonrpc apparaît deux fois : la table contient deux règles pour cette adresse, qui mènent à la même fonction.)

Le module installé à la section 4 n'a pas une ligne de contrôleur. Il est pourtant appelable de l'extérieur dès son installation, parce que JSON-2 expose les méthodes publiques de tous les modèles, sous les droits de l'utilisateur de la clé :

$ curl -s -X POST http://localhost:8069/json/2/mon_module.mon_module/create \
    -H "Authorization: bearer $CLE" -H "Content-Type: application/json" \
    -d '{"vals_list": [{"name": "Premier", "value": 42}]}'
[1]
$ curl -s -X POST http://localhost:8069/json/2/mon_module.mon_module/search_read \
    -H "Authorization: bearer $CLE" -H "Content-Type: application/json" \
    -d '{"domain": [], "fields": ["name", "value", "value2"]}'
[{"id": 1, "name": "Premier", "value": 42, "value2": 0.42}]

Sans clé, la réponse est un 401 au message explicite (User not authenticated, use an API Key with a Bearer Authorization header.) ; sur un modèle mal orthographié, un 404 (the model 'res.partnr' does not exist). Quand plusieurs bases tournent sur le même serveur, l'en-tête X-Odoo-Database désigne la base visée (odoo/http/router.py:507). Le détail de l'API est dans XML-RPC est déprécié : passer à l'API JSON-2 d'Odoo 20. Les anciennes routes /xmlrpc et /jsonrpc répondent encore, avec un avertissement au journal : dépréciées depuis Odoo 19, leur retrait est annoncé pour Odoo 22 (addons/rpc/controllers/__init__.py:6-9).

Dernier détail du schéma, l'étape 2 : Odoo ouvre d'abord un curseur en lecture seule pour les routes déclarées readonly dans @http.route ; /web/dataset/call_kw le calcule selon la méthode appelée (addons/web/controllers/dataset.py:28), si bien qu'un web_search_read peut en profiter. Il ne l'obtient vraiment que si une réplique PostgreSQL est configurée (db_replica_host) ; sinon il prend la base principale, et le journal note rw en fin de ligne, comme ici sur un serveur sans réplique.

6. Le serveur : fils, workers, cron et WebSocket

odoo-bin choisit son mode au démarrage (odoo/service/server.py:1553-1592) :

  • --workers=0 (défaut) : ThreadedServer, un seul processus ; les requêtes HTTP et les actions planifiées tournent dans des fils. C'est le mode du poste de développement.
  • --workers=N : PreforkServer, un processus maître qui lance N processus WorkerHTTP, des WorkerCron (autant que --max-cron-threads) et un serveur gevent pour les connexions longues (/websocket, port --gevent-port, 8072 par défaut). C'est le mode de production.

Le démarrage en prefork se lit dans le journal : le maître charge le registre, puis chaque worker annonce qu'il est vivant, avec son propre numéro de processus.

Trois lignes méritent l'attention. HTTP service running on 127.0.0.1:8069 : Odoo 20 n'écoute que la boucle locale par défaut. Evented/WebSocket service running on 127.0.0.1:8072 : le temps réel (messages, notifications) passe par ce port en prefork, et le proxy doit lui envoyer le chemin /websocket ; adressé au port HTTP, il échoue (dernière ligne, 400, et le code du bus le dit : « Is the connection opened on the evented port (8072)? », addons/bus/websocket.py:861). Enfin, Odoo 20 ajoute --gevent-workers (systèmes POSIX seulement, 1 par défaut, odoo/tools/config.py:498-501) pour lancer plusieurs serveurs gevent sur le même port ; l'option n'existe pas en 19.0.

Joint par son adresse IP, le serveur reste muet

La valeur par défaut de --http-interface est passée de 0.0.0.0 (19.0) à 127.0.0.1 (odoo/tools/config.py:289). Un serveur sans proxy, appelé par http://IP:8069, ne répond donc plus, sans erreur au journal. Derrière Nginx sur la même machine, c'est exactement ce qu'il faut ; sans proxy ou en conteneur, règle http_interface = 0.0.0.0 dans le fichier de configuration. Les deux montages sont décrits dans Mettre Odoo 20 en HTTPS avec Nginx et Installer Odoo 20 avec Docker.

Chaque ligne de requête suit le même format (odoo/http/server_log.py:36) : statut, taille de la réponse, nombre de requêtes SQL, temps passé dans PostgreSQL, temps passé hors SQL, mode du curseur. La première requête d'un worker paie le calcul à froid (82 requêtes SQL pour /web/login, table des routes comprise) ; en mode développement, /web/webclient/load_menus passe de 21 requêtes au premier appel à 2 au suivant. Cette ligne est le premier outil de diagnostic des lenteurs, avant tout profileur (voir Journaux Odoo 20 : _logger, --log-handler, --log-sql).

Le client web est une application JavaScript chargée une fois, puis qui ne parle plus au serveur que par des appels JSON. Ouvrir l'application Ventes déclenche ces requêtes, relevées dans le navigateur :

Toute la logique d'affichage est dans le navigateur ; le serveur ne fait que répondre aux appels de méthodes, toujours par call_kw, toujours sous les droits de l'utilisateur connecté. Le temps réel ne passe pas par la page : un SharedWorker partagé par les onglets ouvre la connexion, et seul le journal du serveur la montre ("GET /websocket?version=saas-19.5-1 HTTP/1.1" 101).

À retenir

  • Odoo 20 = un processus Python, une base PostgreSQL 16 ou plus, un filestore, un client web OWL 3 : à sauvegarder, surveiller et dimensionner ensemble.
  • Le registre décide de ce qui existe dans une base : un modèle d'un module non installé n'existe pas, un module dont la version ne commence pas par 20.0 n'est jamais installé.
  • Toute requête suit le même trajet : session, registre, route, authentification, dispatcher, ORM, transaction, ligne de journal.
  • Ton module touche surtout l'ORM et les vues ; JSON-2 expose ses méthodes sans contrôleur, sous les droits de la clé.
  • Les pièges d'architecture d'Odoo 20 sont silencieux ou trompeurs : écoute en 127.0.0.1, module 19 ignoré, scaffold qui génère encore ir.model.access.csv.
