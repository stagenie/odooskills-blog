__manifest__.py Odoo 19 décrypté

Les 33 clés reconnues, les trois qui n'ont aucune valeur par défaut, celles qui sont mortes depuis dix ans — et surtout la règle de version qui fait disparaître un module de la liste des applications sans le moindre message d'erreur.

~14 minutes de lecture · niveau intermédiaire · parcours Fondamentaux

Ce que tu vas apprendre

La liste réelle des clés

Lue dans _DEFAULT_MANIFEST, pas dans un article de blog recopié depuis la v12.

Les quatre pièges

version, depends, auto_install, hooks : chacun testé sur une base réelle.

L'ordre exact des hooks

Une trace de journal, pas un schéma approximatif. On saura quoi mettre dans lequel.

Prérequis — une instance Odoo 19 en local, l'accès au dossier source, et le mode développeur pour voir les onglets techniques d'un module. Les quatre modules de démonstration utilisés ici tiennent chacun en un manifeste et un __init__.py.

1. Trente-trois clés, et trois obligations

Le manifeste passe par une fusion avec un dictionnaire de valeurs par défaut. Ce dictionnaire est la seule liste faisant autorité, et son commentaire d'ouverture est explicite sur ce qui manque :

# odoo/odoo/modules/module.py — Odoo 19.0
_DEFAULT_MANIFEST = {
    # Mandatory fields (with no defaults):
    # - author
    # - license
    # - name
    # Derived fields are computed in the Manifest class.
    'application': False,
    'bootstrap': False,             # web
    'assets': {},
    'auto_install': False,
    'category': 'Uncategorized',
    'cloc_exclude': [],
    'configurator_snippets': {},    # website themes
    'configurator_snippets_addons': {},
    'countries': [],
    'data': [],
    'demo': [],
    'demo_xml': [],
    'depends': [],
    'description': '',              # defaults to README file
    'external_dependencies': {},
    'init_xml': [],
    'installable': True,
    'images': [],                   # website
    'images_preview_theme': {},
    'live_test_url': '',
    'new_page_templates': {},
    'post_init_hook': '',
    'post_load': '',
    'pre_init_hook': '',
    'sequence': 100,
    'summary': '',
    'test': [],
    'theme_customizations': {},
    'update_xml': [],
    'uninstall_hook': '',
    'version': '1.0',
    'web': False,
    'website': '',
}

Trente-trois clés avec valeur par défaut, plus trois sans défaut — name, author, license. Deux d'entre elles sont « obligatoires » au sens documentaire seulement : leur absence produit un avertissement, pas une erreur.

if not manifest.get('author'):
    author = manifest.get('contributors') or manifest.get('maintainer') or ''
    manifest['author'] = str(author)
    _logger.warning("Missing `author` key in manifest for %r, defaulting to %r", module, str(author))

Un manifeste sans author se replie sur contributors, puis sur maintainer, puis sur la chaîne vide. Deux clés non documentées reconnues en secours, à connaître quand on reprend le module d'un tiers.

Le tri utile : ce qu'on écrit vraiment

CléRôleVerdict
name, version, author, license, depends, data Le noyau. Aucun module sérieux ne s'en passe.Toujours
category, summary, description, website, sequence Métadonnées d'affichage dans la liste des applications.Recommandé
application, installable, auto_install Comportement d'installation et place dans le menu Applications.Selon le cas
assets, external_dependencies, demo, countries Bundles front, dépendances Python/binaires, données de démo, restriction géographique.Selon le cas
pre_init_hook, post_init_hook, uninstall_hook, post_load Points d'entrée Python du cycle de vie. Section 5.Selon le cas
init_xml, update_xml, demo_xml, test Ancêtres de data et demo. Encore acceptés, plus alimentés. Mort
bootstrap, web Vestiges de l'ancien client web.Ne pas écrire
configurator_snippets, images_preview_theme, new_page_templates, theme_customizations Réservées aux thèmes Website.Hors sujet
live_test_url, images, price, currency, support Champs commerciaux de l'Apps Store. price, currency et support ne figurent pas dans _DEFAULT_MANIFEST : ils sont lus par la plateforme, pas par le serveur.Article 3/3

Nouveauté v19 — la classe Manifest

La fonction historique load_manifest() est dépréciée en 19.0 au profit d'une classe. Le code qui lit un manifeste par programme doit basculer :

warnings.warn("Since 19.0, use Manifest", DeprecationWarning)

# à la place :
from odoo.modules import Manifest
mod = Manifest.for_addon('sale')          # ou Manifest._from_path(chemin)
print(mod['version'], mod['depends'])

2. version — la clé qui fait disparaître le module

« Mon module n'apparaît pas dans la liste des applications » : dans la grande majorité des cas, la cause tient dans cette clé. Odoo ne se contente pas de lire la version, il la réécrit, puis il la juge.

def adapt_version(version: str) -> str:
    """Reformat the version of the module into a canonical format."""
    version_str_parts = version.split('.')
    if not (2 <= len(version_str_parts) <= 5):
        raise ValueError(f"Invalid version {version!r}, must have between 2 and 5 parts")
    serie = release.major_version
    ...
    if len(version_parts) <= 3 and not version.startswith(serie):
        # prefix the version with serie
        return f"{serie}.{version}"
    return version

La ligne critique est l'avant-dernière. Un module porté depuis la 18 dont on a oublié de bumper la version ne provoque aucune erreur. Il produit un avertissement noyé dans le journal, puis il est mis de côté :

if manifest['installable'] and not check_version(str(manifest['version']), should_raise=False):
    _logger.warning("The module %s has an incompatible version, setting installable=False", module)
    manifest['installable'] = False
2026-07-26 05:37:11 WARNING vs19_blog_manifest odoo.modules.module:
  The module oski_mf_version_wrong has an incompatible version, setting installable=False

En base, le module existe mais dans un état qui l'exclut de tout :

SELECT name, latest_version, state FROM ir_module_module WHERE name LIKE 'oski_mf%';

         name          | latest_version |     state
-----------------------+----------------+---------------
 oski_mf_depends_empty | 19.0.1.0.0     | installed
 oski_mf_hooks         | 19.0.1.0.0     | installed
 oski_mf_version_short | 19.0.1.0       | installed     <-- declare '1.0'
 oski_mf_version_wrong |                | uninstallable <-- declare '18.0.1.0.0'

⚠️ Le réflexe à prendre

  • Toujours écrire la forme canonique complète : '19.0.1.0.0'. Elle est explicite, elle survit à un grep, et elle interdit l'oubli de bump lors d'un port.
  • Après tout port de version, chercher incompatible version dans le journal avant de chercher pourquoi le module n'apparaît pas.
  • Le préfixage automatique de '1.0' fonctionne, mais il masque l'information : le manifeste ne dit plus pour quelle série le module est écrit.

3. depends — la liste vide n'existe pas

Déclarer 'depends': [] pour « ne dépendre de rien » ne fonctionne pas. Le chargeur réécrit la valeur, et le commentaire du code nomme la pratique par son nom :

if module == 'base':
    manifest['depends'] = []
elif not manifest['depends']:
    # prevent the hack `'depends': []` except 'base' module
    manifest['depends'] = ['base']

Vérification en base sur le module démonstration déclaré avec une liste vide :

SELECT d.name FROM ir_module_module_dependency d
JOIN ir_module_module m ON m.id = d.module_id
WHERE m.name = 'oski_mf_depends_empty';

 name
------
 base

Seul le module base a le droit à une liste réellement vide. Pour tous les autres, omettre la clé et écrire ['base'] reviennent exactement au même — autant l'écrire, pour que la lecture du manifeste ne mente pas.

4. auto_install — trois formes, pas une

La forme booléenne est la seule que la plupart des manifestes utilisent. Il en existe deux autres, bien plus précises, et le code les documente lui-même :

# auto_install is either `False` (by default) in which case the module
# is opt-in, either a list of dependencies in which case the module is
# automatically installed if all dependencies are (special case: [] to
# always install the module), either `True` to auto-install the module
# in case all dependencies declared in `depends` are installed.
if isinstance(manifest['auto_install'], Iterable):
    manifest['auto_install'] = auto_install_set = set(manifest['auto_install'])
    non_dependencies = auto_install_set.difference(depends)
    assert not non_dependencies, (
        "auto_install triggers must be dependencies,"
        f" found non-dependencies [{', '.join(non_dependencies)}] for module {module}"
    )
elif manifest['auto_install']:
    manifest['auto_install'] = set(depends)

Résultat mesuré sur un manifeste dont depends vaut ['base', 'mail'] :

ÉcritInterprétéSens
auto_install=FalseFalse Le module s'installe uniquement sur décision explicite. Défaut.
auto_install=True{'base', 'mail'} S'installe dès que toutes les dépendances sont présentes.
auto_install=['mail']{'mail'} S'installe dès que mail est présent, même si le reste ne l'est pas. C'est la forme des modules pont.
auto_install=[]set() Aucun déclencheur à satisfaire, donc toujours installé.
auto_install=['sale']
avec depends=['base']		 AssertionError: auto_install triggers must be dependencies, found non-dependencies [sale] for module demo

La troisième ligne mérite d'être retenue. Un module pont entre deux applications — typiquement depends = ['sale', 'account'] — n'a aucune raison de s'installer dès que base est là. Écrire auto_install = ['sale', 'account'] exprime la condition réelle, alors que True l'exprime aussi mais devient faux dès qu'une dépendance technique est ajoutée à la liste six mois plus tard.

⚠️ Le piège différé de auto_install=True

  • Manifeste initial : depends = ['sale', 'account'], auto_install = True. Le pont s'installe quand les deux applications sont là. Comportement voulu.
  • Six mois plus tard, quelqu'un ajoute 'web' ou 'mail' à depends pour une raison technique. True se recalcule sur la nouvelle liste — la condition d'installation a changé en silence.
  • La forme liste ne bouge pas : elle continue à ne surveiller que les modules nommés.

5. Les quatre hooks et leur ordre réel

Plutôt qu'un schéma, une mesure. Un module de démonstration déclare les quatre points d'entrée, chacun écrivant dans le journal, plus une trace au moment de l'import du paquet Python.

# content/blog/modules/oski_mf_hooks/__manifest__.py
{
    'name': 'OdooSkills — Ordre des hooks',
    'version': '19.0.1.0.0',
    'license': 'LGPL-3',
    'depends': ['base'],
    'data': ['data/demo_record.xml'],
    'pre_init_hook': '_pre_init',
    'post_init_hook': '_post_init',
    'uninstall_hook': '_uninstall',
    'post_load': '_post_load',
}
# __init__.py
from . import models

def _post_load():
    _logger.warning("HOOK 1/4 post_load — import du paquet Python, aucun registre")

def _pre_init(env):
    _logger.warning("HOOK 2/4 pre_init_hook — tables du module PAS encore creees")

def _post_init(env):
    count = env['res.partner'].search_count([])
    _logger.warning("HOOK 3/4 post_init_hook — donnees XML chargees, %s partenaires", count)

def _uninstall(env):
    _logger.warning("HOOK 4/4 uninstall_hook — desinstallation en cours")

Trace obtenue à l'installation, dans l'ordre où elle est sortie :

WARNING odoo.addons.oski_mf_hooks.models.res_partner: HOOK 1bis — chargement du module Python models/res_partner.py
WARNING odoo.addons.oski_mf_hooks:                     HOOK 1/4 post_load — import du paquet Python, aucun registre
WARNING odoo.addons.oski_mf_hooks:                     HOOK 2/4 pre_init_hook — tables du module PAS encore creees
WARNING odoo.addons.oski_mf_hooks:                     HOOK 3/4 post_init_hook — donnees XML chargees, 3 partenaires

Deux enseignements que le schéma habituel ne donne pas.

Premier : post_load s'exécute après l'import des sous-paquets, puisque from . import models est la première ligne de __init__.py. Ce n'est donc pas le tout premier point d'entrée du module — le code au niveau module de chaque fichier Python le précède.

Second : post_load est appelé au chargement du paquet Python, sans base de données ni registre. Sa signature ne prend aucun argument, contrairement aux trois autres.

# odoo/odoo/modules/module.py — load_openerp_module()
manifest = Manifest.for_addon(module_name)
if post_load := manifest.get('post_load'):
    getattr(sys.modules[qualname], post_load)()   # aucun argument
HookSignatureÉtat du systèmeUsage légitime
post_load() Paquet Python importé. Ni registre, ni curseur, ni base. Monkey-patch d'une fonction du framework, enregistrement d'un type. À l'échelle du serveur, pas d'une base.
pre_init_hook(env) Environnement disponible, tables du module pas encore créées. Préparer une colonne calculée coûteuse en SQL brut, vérifier une précondition, refuser l'installation.
post_init_hook(env) Tables créées, fichiers data chargés. Peupler des enregistrements calculés, configurer des paramètres système. S'exécute à l'installation seule, pas à la mise à jour.
uninstall_hook(env) Module encore présent, désinstallation en cours. Nettoyer ce que l'ORM ne supprimera pas : colonnes ajoutées à la main, tâches planifiées externes, fichiers.

La ligne post_init_hook contient le piège le plus fréquent : il ne rejoue pas à chaque -u. Un initialisation de données qui doit survivre aux mises à jour relève d'un script de migration, pas de ce hook.

6. Quatre détails qui font gagner du temps

description se remplit tout seul depuis le README

La valeur par défaut est la chaîne vide, mais le commentaire du code annonce la suite — defaults to README file. Les noms cherchés sont fixés :

README = ['README.rst', 'README.md', 'README.txt', 'README']

Maintenir un long description triple-quoté dans le manifeste n'a donc plus d'intérêt : un README.md à la racine du module est versionné, lisible sur une forge, et alimente la fiche du module.

external_dependencies échoue tôt, pas tard

Déclarer les paquets Python requis évite le ImportError au premier appel en production. La vérification s'appuie sur la syntaxe standard des exigences, marqueurs d'environnement compris :

'external_dependencies': {
    'python': ['qrcode', 'pandas>=2.0'],
    'bin': ['wkhtmltopdf'],
},

application décide de la visibilité, pas de la nature

La clé ne change rien au fonctionnement : elle place le module dans la vue « Applications » plutôt que dans la liste complète. Un module technique qui la déclare à True pollue l'écran d'installation d'un client ; un vrai module métier qui l'oublie devient introuvable.

installable=False contamine ce qui en dépend

La valeur ne masque pas le module : elle le place à l'état uninstallable, exactement celui qu'une version incompatible produit. Et l'état se propage. Un cinquième module de démonstration déclare une dépendance sur celui qui porte la version 18.0.1.0.0 :

{
    'name': 'OdooSkills — Depend sur un module non installable',
    'version': '19.0.1.0.0',
    'depends': ['oski_mf_version_wrong'],
    'installable': True,
}
ERROR vs19_blog_manifest odoo.modules.loading:
  Some modules have inconsistent states, some dependencies may be missing: ['oski_mf_dep_on_bad']
SELECT name, state FROM ir_module_module WHERE name LIKE 'oski_mf_%bad%' OR name LIKE '%version_wrong';

         name          |     state
-----------------------+---------------
 oski_mf_dep_on_bad    | to install     <-- bloque, jamais installe
 oski_mf_version_wrong | uninstallable

Le module reste figé à to install et n'atteint jamais l'état installé. Un oubli de bump de version sur un module socle bloque donc toute la pile qui s'appuie dessus — avec pour seul indice une ligne ERROR qui ne nomme pas le vrai coupable.

Récapitulatif

  • 33 clés avec valeur par défaut, plus name, author et license sans défaut. Le reste de ce qu'on lit en ligne relève du folklore ou de l'Apps Store.
  • version est réécrite puis jugée. Une série qui ne correspond pas force installable=False avec un simple avertissement. Écrire '19.0.1.0.0', toujours.
  • depends: [] devient ['base'] pour tout module autre que base.
  • auto_install accepte une liste, et cette forme est la bonne pour un module pont : elle ne se recalcule pas quand depends grossit.
  • Ordre des hooks mesuré : import Python → post_load → pre_init_hook → post_init_hook. Seul post_load n'a pas d'argument.

Dernière étape de la série : les clés que le serveur ignore mais que la plateforme lit — price, currency, support, images, live_test_url — et tout ce qu'implique la publication d'un module sur l'Odoo Apps Store.
