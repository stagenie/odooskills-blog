Piloter Odoo 20 depuis Claude Code : JSON-2 et un serveur MCP minimal

On pose une question en français dans le terminal ; l'assistant interroge Odoo, répond avec les bons devis et écrit une note dans le fil, après avoir demandé la permission. Le tout repose sur un serveur MCP d'une centaine de lignes de Python, sans dépendance ni module Odoo. Il parle à l'API JSON-2 avec la clé d'un utilisateur technique, sur une liste blanche de modèles.

~12 minutes de lecture · niveau intermédiaire · parcours Intégrations

Ce que tu vas apprendre

Exposer

Écrire un serveur MCP minimal : trois outils (search_read, fields, post_note) au-dessus de /json/2, limités à deux modèles.

Brancher

Le déclarer dans Claude Code avec claude mcp add, sans écrire la clé dans le projet, puis l'approuver.

Encadrer

Ce que l'assistant peut faire et ce qu'il ne peut pas faire : demandes d'autorisation, liste blanche, et surtout les droits de l'utilisateur de la clé.

Prérequis

  • Odoo 20 Community avec Ventes et sa base de démonstration. Aucun module à installer : la route /json/2 est fournie par le module rpc, installé d'office.
  • Python 3 sur la machine de l'assistant : le serveur n'utilise que la bibliothèque standard.
  • Claude Code, connecté à un compte. L'article a été exécuté avec la version 2.1.322 ; les écrans de la CLI sont en anglais.
  • Les bases de l'API : XML-RPC est déprécié : passer à l'API JSON-2 d'Odoo 20.

MCP (Model Context Protocol) est un protocole qui permet à un assistant d'appeler des outils déclarés par un programme à part, le serveur MCP. En mode stdio, l'assistant lance ce programme et lui parle par l'entrée et la sortie standard, une ligne JSON-RPC par message. Chaque outil a un nom, une description et un schéma d'arguments. L'assistant choisit l'outil, le serveur fait l'appel à Odoo et renvoie le résultat.

Odoo 20 Enterprise contient un module ai_mcp (il figure dans la liste des modules d'une base Enterprise 20). Le code Community 20.0 n'a ni module ai_*, ni aucune mention de MCP. En Community, on écrit donc soi-même le serveur. Le plus simple est de le poser au-dessus de JSON-2, l'API externe d'Odoo 20.

1. Côté Odoo : un utilisateur technique et sa clé API

L'assistant agira avec les droits du propriétaire de la clé. Ne lui donnez jamais une clé d'administrateur. Créez un utilisateur interne dédié, ici « Assistant IA », avec le seul droit Ventes : Utilisateur : tous les documents. Tout ce qu'il écrit sera signé de son nom dans les fils de discussion. Les traces restent donc lisibles.

La clé se crée connecté en « Assistant IA » : menu utilisateur › Mes préférences › onglet Sécurité › Clés API, description Claude Code, puis copier la clé affichée. Elle ne sera plus jamais montrée. Elle a la portée rpc, la seule acceptée par /json/2. Pour un utilisateur qui n'est pas administrateur, la date d'expiration est obligatoire : créée par programme sans date, la clé est refusée (« La clé API doit avoir une date d'expiration »). Notez l'échéance : à cette date, le serveur MCP recevra des 401.

Ces droits sont la barrière qui tient quoi qu'il arrive. Avec la clé de « Assistant IA », un unlink envoyé directement à JSON-2 est refusé par Odoo :

POST /json/2/sale.order/unlink {"ids": [999999]} HTTP 403 {"name": "odoo.exceptions.AccessError", "message": "You are not allowed to delete 'Sales Order' (sale.order) records.\n\nThis operation is allowed for the following groups:\n\t- Sales / Administrator\n\t- Default access for new users\n …"}

À l'inverse, le même utilisateur interne peut lire res.users par JSON-2 (réponse 200). Si l'assistant ne doit pas y toucher, c'est le serveur MCP qui doit l'en empêcher.

2. Le serveur MCP : trois outils, une liste blanche

Le fichier odoo_mcp.py, dans le dossier du projet où l'on lance l'assistant. Il est complet, et c'est celui qui a tourné pour cet article. À lire dans l'ordre : odoo() (l'appel JSON-2 et la liste blanche), TOOLS (ce que voit l'assistant), call_tool(), puis handle() et la boucle de lecture (le protocole).

"""Serveur MCP minimal pour Odoo 20 Community : 3 outils au-dessus de l'API JSON-2.

Transport stdio : une requête JSON-RPC par ligne sur stdin, une réponse par ligne sur stdout.
Rien d'autre ne doit sortir sur stdout : les traces vont sur stderr.
Configuration par variables d'environnement : ODOO_URL, ODOO_DB, ODOO_API_KEY, ODOO_MODELS.
"""
import json
import os
import sys
import urllib.error
import urllib.request

URL = os.environ["ODOO_URL"].rstrip("/")
DB = os.environ["ODOO_DB"]
KEY = os.environ["ODOO_API_KEY"]
MODELS = set(os.environ.get("ODOO_MODELS", "res.partner,sale.order").split(","))


def odoo(model, method, **params):
    """POST /json/2/<model>/<method> ; les paramètres sont les clés du corps JSON."""
    if model not in MODELS:
        raise ValueError(f"modèle non autorisé : {model} (autorisés : {', '.join(sorted(MODELS))})")
    params.setdefault("context", {"lang": "fr_FR"})
    req = urllib.request.Request(
        f"{URL}/json/2/{model}/{method}",
        data=json.dumps(params).encode(),
        headers={"Authorization": f"bearer {KEY}", "X-Odoo-Database": DB,
                 "Content-Type": "application/json"},
    )
    try:
        with urllib.request.urlopen(req, timeout=30) as resp:
            return json.load(resp)
    except urllib.error.HTTPError as e:
        err = json.load(e)  # {name, message, arguments, context, debug}
        raise ValueError(f"HTTP {e.code} {err.get('name')} : {err.get('message')}") from None


TOOLS = [
    {"name": "search_read",
     "description": "Cherche des enregistrements Odoo et renvoie les champs demandés.",
     "inputSchema": {"type": "object", "required": ["model"], "properties": {
         "model": {"type": "string", "description": "ex. sale.order"},
         "domain": {"type": "array", "description": "domaine Odoo, ex. [[\"state\", \"=\", \"sale\"]]"},
         "fields": {"type": "array", "items": {"type": "string"}},
         "limit": {"type": "integer", "default": 20},
         "order": {"type": "string", "description": "ex. amount_total desc"}}}},
    {"name": "fields",
     "description": "Liste les champs d'un modèle Odoo (nom, libellé, type, modèle lié).",
     "inputSchema": {"type": "object", "required": ["model"],
                     "properties": {"model": {"type": "string"}}}},
    {"name": "post_note",
     "description": "Écrit une note interne dans le fil (chatter) d'un enregistrement.",
     "inputSchema": {"type": "object", "required": ["model", "id", "body"], "properties": {
         "model": {"type": "string"}, "id": {"type": "integer"}, "body": {"type": "string"}}}},
]


def call_tool(name, args):
    model = args["model"]
    if name == "search_read":
        return odoo(model, "search_read", domain=args.get("domain", []),
                    fields=args.get("fields", ["display_name"]),
                    limit=min(int(args.get("limit", 20)), 200), order=args.get("order"))
    if name == "fields":
        return odoo(model, "fields_get", attributes=["string", "type", "relation"])
    if name == "post_note":
        ids = odoo(model, "message_post", ids=[args["id"]], body=args["body"],
                   message_type="comment", subtype_xmlid="mail.mt_note")
        return {"message_id": ids}
    raise ValueError(f"outil inconnu : {name}")


def handle(msg):
    method, params = msg.get("method"), msg.get("params") or {}
    if method == "initialize":
        return {"protocolVersion": params.get("protocolVersion", "2025-06-18"),
                "capabilities": {"tools": {}},
                "serverInfo": {"name": "odoo-json2", "version": "0.1.0"}}
    if method == "ping":
        return {}
    if method == "tools/list":
        return {"tools": TOOLS}
    if method == "tools/call":
        try:
            data = call_tool(params["name"], params.get("arguments") or {})
            return {"content": [{"type": "text", "text": json.dumps(data, ensure_ascii=False)}]}
        except Exception as e:  # l'erreur est rendue au modèle, le serveur continue
            return {"content": [{"type": "text", "text": str(e)}], "isError": True}
    raise LookupError(method)


for line in sys.stdin:
    if not line.strip():
        continue
    msg = json.loads(line)
    if "id" not in msg:  # notification (notifications/initialized…) : pas de réponse
        continue
    try:
        reply = {"jsonrpc": "2.0", "id": msg["id"], "result": handle(msg)}
    except LookupError as e:
        reply = {"jsonrpc": "2.0", "id": msg["id"],
                 "error": {"code": -32601, "message": f"Method not found: {e}"}}
    print(json.dumps(reply, ensure_ascii=False), flush=True)
    print(f"[odoo-mcp] {msg['method']}", file=sys.stderr, flush=True)
  • stdout est réservé au protocole. Un print() de mise au point sur la sortie standard casse l'échange : les traces partent sur stderr.
  • La configuration vient de l'environnement (ODOO_URL, ODOO_DB, ODOO_API_KEY, ODOO_MODELS) : rien de secret dans le fichier.
  • La liste blanche est vérifiée avant tout appel. Un modèle absent de ODOO_MODELS ne quitte jamais la machine.
  • Aucun outil générique. Pas de write, pas d'unlink, pas d'outil « appeler n'importe quelle méthode ». La seule écriture est une note interne : message_post avec le sous-type mail.mt_note, comme le bouton Note du fil. Le texte passé en body est échappé par Odoo : un <b> ou un lien envoyé ainsi est enregistré comme du texte (essayé).
  • Une erreur est rendue à l'assistant (isError), au lieu d'arrêter le serveur : il peut lire le message, corriger son appel ou l'expliquer.

L'essayer sans assistant

Le protocole se teste à la main, en envoyant les messages ligne par ligne sur l'entrée standard (la demande tools/list, qui renvoie les trois outils, est omise ici pour la longueur).

export ODOO_URL=http://localhost:8069 ODOO_DB=ma_base ODOO_API_KEY=<la clé> ODOO_MODELS=res.partner,sale.order
printf '%s\n' \
 '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"essai","version":"0"}}}' \
 '{"jsonrpc":"2.0","method":"notifications/initialized"}' \
 '{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"search_read","arguments":{"model":"sale.order","domain":[["state","=","draft"]],"fields":["name","amount_total"],"order":"amount_total desc","limit":2}}}' \
 '{"jsonrpc":"2.0","id":4,"method":"tools/call","params":{"name":"search_read","arguments":{"model":"res.users","fields":["login"]}}}' \
 | python3 odoo_mcp.py
{"jsonrpc": "2.0", "id": 1, "result": {"protocolVersion": "2025-06-18", "capabilities": {"tools": {}}, "serverInfo": {"name": "odoo-json2", "version": "0.1.0"}}} [odoo-mcp] initialize {"jsonrpc": "2.0", "id": 3, "result": {"content": [{"type": "text", "text": "[{\"id\": 2, \"name\": \"S00002\", \"amount_total\": 3389.63}, {\"id\": 1, \"name\": \"S00001\", \"amount_total\": 2001.0}]"}]}} [odoo-mcp] tools/call {"jsonrpc": "2.0", "id": 4, "result": {"content": [{"type": "text", "text": "modèle non autorisé : res.users (autorisés : res.partner, sale.order)"}], "isError": true}} [odoo-mcp] tools/call

La notification notifications/initialized n'a pas d'id : elle ne reçoit pas de réponse. Les lignes [odoo-mcp] sont les traces de stderr, mêlées à la sortie dans le terminal.

3. Le déclarer dans Claude Code, sans écrire la clé

Dans le dossier du projet, la portée project écrit la déclaration dans un fichier .mcp.json partageable. La clé y est notée ${ODOO_API_KEY} entre apostrophes, pour que le shell ne la remplace pas : Claude Code la lira dans l'environnement au lancement.

claude mcp add odoo -s project \
  -e ODOO_URL=http://localhost:8069 -e ODOO_DB=ma_base \
  -e 'ODOO_API_KEY=${ODOO_API_KEY}' -e ODOO_MODELS=res.partner,sale.order \
  -- python3 odoo_mcp.py
{
  "mcpServers": {
    "odoo": {
      "type": "stdio",
      "command": "python3",
      "args": [
        "odoo_mcp.py"
      ],
      "env": {
        "ODOO_URL": "http://localhost:8069",
        "ODOO_DB": "ma_base",
        "ODOO_API_KEY": "${ODOO_API_KEY}",
        "ODOO_MODELS": "res.partner,sale.order"
      }
    }
  }
}

Avant toute approbation, et sans la variable dans l'environnement, claude mcp list le dit clairement :

odoo: python3 odoo_mcp.py - ⏸ Pending approval (run `claude` to approve) … └ [Warning] [odoo] mcpServers.odoo: Missing environment variables: ODOO_API_KEY

On exporte la clé dans le shell (export ODOO_API_KEY=…, ou un gestionnaire de secrets), puis on lance claude. Un serveur venu d'un .mcp.json n'est jamais démarré sans accord : au premier lancement, Claude Code demande s'il faut l'utiliser.

L'accord est enregistré dans settings.local.json, le fichier de réglages local du projet ("enabledMcpjsonServers": ["odoo"]), propre au poste. Ensuite, claude mcp list affiche odoo: python3 odoo_mcp.py - ✔ Connected. Le .mcp.json peut aller dans le dépôt du projet ; la clé, jamais.

4. Une vraie demande, deux autorisations

Session lancée avec claude --permission-mode manual, pour que chaque appel d'outil soit soumis. La demande, en français :

Dans Odoo, quels sont les trois devis en brouillon les plus élevés ? Ensuite, écris une note interne sur le premier : « Devis le plus élevé du moment : à relancer cette semaine. »

L'assistant a d'abord demandé l'outil search_read avec des arguments qu'il a construits seul à partir des descriptions du serveur : modèle sale.order, domaine [["state", "=", "draft"]], champs name, partner_id, amount_total, currency_id, date_order, ordre amount_total desc, limite 3. Accepté par 1. Yes, puis la seconde demande :

Le choix 2 (« don't ask again ») vaut pour cet outil dans ce dossier. Pour une écriture, mieux vaut garder 1. Yes à chaque fois. La réponse, après les deux appels :

Côté Odoo, la note est dans le fil du devis S00002, signée par l'utilisateur de la clé :

Sans terminal interactif : claude -p

En mode non interactif, personne ne peut répondre à une demande d'autorisation. L'outil est donc refusé, sauf s'il est autorisé d'avance par son nom complet, mcp__<serveur>__<outil> :

claude -p "Combien de devis en brouillon y a-t-il dans Odoo ? Réponds en une phrase."
# Je n'ai pas pu compter les devis : l'accès à l'outil Odoo `mcp__odoo__search_read` a été refusé, …

claude -p "Combien de devis en brouillon y a-t-il dans Odoo ? Réponds en une phrase." \
  --allowedTools mcp__odoo__search_read
# Il y a 4 devis en brouillon dans Odoo : S00001, S00002, S00003 et S00005.

N'autorisez ainsi que les outils de lecture. Une écriture lancée sans personne pour la relire est exactement ce que le dialogue d'autorisation sert à éviter.

5. Ce que l'assistant ne peut pas faire

Deuxième demande, volontairement hors du cadre : lister les utilisateurs et supprimer un devis.

L'assistant a bien appelé search_read sur res.users, après la même demande d'autorisation. Le serveur a refusé avant d'appeler Odoo. Pour la suppression, il n'a trouvé aucun outil. Les erreurs d'Odoo lui reviennent de la même façon. Un champ inconnu dans un domaine, par exemple, donne un 500, et non le 422 d'une erreur métier ; il est relayé tel quel :

HTTP 500 builtins.ValueError : Invalid field res.partner.bogus in condition ('bogus', '=', 1)

La clé est aussi à la portée de l'outil Bash

La variable ODOO_API_KEY est exportée dans le shell qui lance claude. Toute commande que l'assistant exécute en hérite. Un curl vers /json/2 lancé par l'outil Bash contournerait la liste blanche et les trois outils : une telle commande, si elle est proposée, est à refuser. Dans cet essai, l'assistant n'a pas tenté cette voie, et l'a dit (figure précédente). Mais la seule barrière qui tient dans tous les cas, ce sont les droits de l'utilisateur de la clé dans Odoo. Donnez-lui le minimum, et jamais de groupe d'administration.

Venant de la 19

Le serveur ne dépend que de JSON-2, qui existait déjà en 19. L'écart est du côté de la clé : en 20, la route /json/2 exige une clé de portée rpc. Une clé créée en 19 sans portée reçoit un 401 (voir Réécrire un script XML-RPC en JSON-2). Il faut alors créer une nouvelle clé.

À retenir

  • En Community, pas de serveur MCP fourni : une centaine de lignes de Python au-dessus de /json/2 suffisent, en stdio, sans dépendance.
  • Peu d'outils, précis : lire (search_read, fields) et une seule écriture limitée (post_note). Une liste blanche de modèles, vérifiée avant tout appel.
  • claude mcp add -s project écrit un .mcp.json partageable ; la clé y reste ${ODOO_API_KEY} et vient de l'environnement. Le serveur doit être approuvé une fois.
  • Chaque appel d'outil demande l'autorisation en mode manual ; en claude -p, seuls les outils passés dans --allowedTools sont utilisables.
  • La barrière qui tient toujours : un utilisateur technique aux droits minimaux, avec une clé de portée rpc et une date d'expiration à surveiller.
