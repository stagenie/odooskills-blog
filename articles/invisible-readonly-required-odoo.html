invisible, readonly, required conditionnels en Odoo 20 : adieu attrs

Ton ancien module masquait un champ avec attrs et Odoo 20 refuse de l'installer. La condition s'écrit désormais en clair, directement dans l'attribut invisible, readonly ou required. Démonstration sur le formulaire de commande de la démo.

~5 minutes de lecture · niveau intermédiaire · série Astuces dev Odoo 20

Édition : Community. Vérifié sur Odoo 20.0 Community, octobre 2026, base de démonstration (Ventes) et module d'exemple.

La réponse en bref

  1. Écris la condition en expression Python dans l'attribut lui-même : invisible="state == 'sale'", readonly="invoice_count > 0", required="state == 'sale'".
  2. Dans les lignes d'un document, column_invisible="parent.state != 'sale'" masque la colonne entière ; invisible ne vide que la cellule.
  3. attrs et states sont refusés à l'installation depuis la 17 ; Odoo 20 n'a pas changé de règle.
  4. Inutile de déclarer les champs que lit la condition : Odoo les ajoute à la vue.

1. Le message qui t'amène ici

Le module d'exemple hérite du formulaire de commande client. Écrit à l'ancienne, il rend les conditions de paiement obligatoires sur une commande confirmée, et la référence client obligatoire au-delà de 1 000 :

<field name="payment_term_id" position="attributes">
    <attribute name="attrs">{'required': [('state', '=', 'sale')],
                             'readonly': [('invoice_count', '>', 0)]}</attribute>
</field>
<field name="client_order_ref" position="attributes">
    <attribute name="attrs">{'required': [('state', '=', 'sale'), ('amount_total', '>', 1000)]}</attribute>
</field>

L'installation s'arrête net :

Le contrôle porte sur la vue combinée : une seule vue héritée fautive bloque tout le module, même si le reste est propre.

2. Traduire un attrs en expression

Chaque clé de l'ancien dictionnaire devient un attribut, et chaque domaine devient une expression Python qui renvoie vrai ou faux :

Ancien domaineExpression Odoo 20
[('state', '=', 'sale')]state == 'sale'
[('state', 'in', ['draft', 'sent'])]state in ['draft', 'sent']
[('reference', '=', False)]not reference
[('a', '=', 'x'), ('b', '>', 0)] (ET implicite)a == 'x' and b > 0
['|', ('state', '=', 'cancel'), ('locked', '=', True)]state == 'cancel' or locked
states="draft,sent" (visible dans ces états)invisible="state not in ['draft', 'sent']"

Le formulaire de commande d'Odoo 20 lui-même en est rempli : invisible="state == 'sale'" sur la date d'expiration, readonly="state == 'cancel' or locked" sur les adresses, readonly="qty_invoiced > 0" sur le prix unitaire des lignes. Le module d'exemple réécrit :

<field name="payment_term_id" position="attributes">
    <attribute name="required">state == 'sale'</attribute>
    <attribute name="readonly">invoice_count &gt; 0</attribute>
</field>
<field name="client_order_ref" position="attributes">
    <attribute name="required">state == 'sale' and amount_total &gt; 1000</attribute>
</field>

Cette fois, -i mon_module passe sans erreur. Un détail d'écriture : dans un attribut XML, < doit s'écrire &lt;, sinon le fichier ne se lit même pas (Unescaped '<' not allowed in attributes values). Le > brut est accepté ; le cœur l'écrit souvent &gt;.

3. Le résultat à l'écran

Ouvre le devis S00001 d'Acme Corporation, encore en brouillon : rien n'est imposé, la date d'expiration s'affiche, les lignes n'ont pas de colonnes de livraison ni de facturation.

Ouvre maintenant la commande confirmée S00004 (2 240 au total, sans conditions de paiement) :

  • Conditions de paiement passe en requis : vide, le champ est marqué en rouge.
  • L'onglet Autres informations est rouge aussi : il contient la référence client, requise puisque le total dépasse 1 000. Sur la commande S00008 (462), la même référence reste facultative.
  • La date d'expiration a disparu et les colonnes Délivré et Facturé sont apparues : ce sont les conditions du formulaire standard.

Enfin, sur S00007, une facture brouillon a été créée : invoice_count vaut 1 et les conditions de paiement passent en lecture seule. Ces conditions sont évaluées dans le navigateur, sur les valeurs courantes du formulaire.

4. Ce que la condition peut lire

NomContenu
un champ du modèlesa valeur courante dans le formulaire : un Many2one vaut un id ou False, un One2many ou Many2many la liste des ids, une date le texte 'AAAA-MM-JJ'
idl'id de l'enregistrement, False tant qu'il n'est pas enregistré
parent.champdans les lignes d'un One2many, un champ du document parent
context, uidle contexte de l'action, l'id de l'utilisateur
allowed_company_ids, current_company_idles sociétés cochées, la société active
today, nowla date et l'heure du navigateur, en texte : 'AAAA-MM-JJ' et 'AAAA-MM-JJ HH:MM:SS'

Le champ n'a pas besoin d'être dans la vue. amount_total n'apparaît nulle part dans le formulaire de commande, sauf dans la condition du module. Ce script, passé à odoo-bin shell, lit la vue telle que le navigateur la reçoit :

# champs_ajoutes.py
from lxml import etree
arch = env['sale.order'].get_views([(False, 'form')])['views']['form']['arch']
for node in etree.fromstring(arch).xpath("//field[@name='amount_total']"):
    print(etree.tostring(node).decode().strip())
<field name="amount_total" invisible="True" readonly="True" data-used-by="required=&quot;state == 'sale' and amount_total &gt; 1000&quot; (field,client_order_ref)" on_change="1"/>

Odoo a ajouté le champ, invisible et en lecture seule, et note dans data-used-by quelle condition le réclame. Une ligne <field name="state" invisible="1"/> posée seulement pour servir une condition n'est donc plus nécessaire.

Une nuance pour column_invisible : la condition vaut pour toute la colonne, elle est donc évaluée pour la liste, avec le contexte et parent, jamais avec les champs d'une ligne. Pour masquer selon la ligne, mets invisible : la colonne reste, la cellule se vide. Le formulaire standard combine les deux, column_invisible="parent.state != 'sale'" sur les quantités livrées, invisible="display_type" sur les lignes de section.

Une condition de vue ne protège pas la donnée

readonly et required ne jouent que dans le formulaire. Le client de S00004 est en lecture seule à l'écran, la référence client y est requise ; en console, rien ne bloque :

so = env['sale.order'].browse(4)
print(so.name, so.state, so.amount_total, '| client :', so.partner_id.name)
so.write({'partner_id': env.ref('base.res_partner_12').id, 'client_order_ref': False})
print(so.name, so.state, '| client :', so.partner_id.name, '| réf. client :', so.client_order_ref)
env.cr.rollback()
S00004 sale 2240.0 | client : Gemini Furniture S00004 sale | client : Azure Interior | réf. client : False

Un import, l'API ou une action serveur écrivent par le même ORM. Si la règle compte, double-la côté Python : @api.constrains et ValidationError.

À retenir

  • attrs="{'invisible': [...]}" devient invisible="expression" ; idem pour readonly et required, et states devient un test sur state.
  • |, &, = deviennent or, and, == ; < s'écrit &lt; dans le XML.
  • column_invisible pour la colonne (avec parent.), invisible pour la cellule.
  • Les champs lus par la condition sont ajoutés par Odoo ; la vraie règle métier reste en Python.
