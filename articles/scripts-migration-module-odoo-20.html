Migrer un module 19 → 20 : scripts pre, post, end et upgrade_code

Faire passer un module de la 19 à la 20, c'est deux travaux distincts. Le code d'abord : odoo-bin upgrade_code en réécrit une partie, le reste se fait à la main. Les données ensuite : quand le module change de forme (un champ renommé, un format revu), ce sont les scripts du dossier migrations/ qui préservent ce qui est déjà en base. Voici les deux, sur un vrai module, avec l'ordre d'exécution relevé dans le journal et ce qui se perd quand on oublie un script.

~13 minutes de lecture · niveau intermédiaire · parcours Framework & ORM

Ce que tu vas apprendre

Porter le code

Ce que fait Odoo 20 d'un module 19, les scripts d'upgrade_code fournis pour la 20, et ce qu'il reste à corriger à la main.

Migrer les données

Écrire des scripts pre, post et end, savoir ce qui est disponible à chaque étape et dans quel ordre ils passent.

Ne rien perdre

Ce qui arrive sans script pre, ou sans changement de version : aucune erreur, des données en moins.

Prérequis

  • Une instance Odoo 20 Community lancée depuis les sources (./odoo-bin), et le module à porter sous Git : upgrade_code réécrit les fichiers sur place.
  • Savoir installer et mettre à jour un module en ligne de commande : voir Installer, mettre à jour, désinstaller un module Odoo 20 en CLI.
  • Une base de test, jamais la production, pour rejouer chaque mise à jour : voir Copier la prod en base de test Odoo 20.

Ce guide porte un module, pas une base entière : migrer toute une base Odoo 19 vers la 20 en Community passe par OpenUpgrade, dont la branche 20.0 ne contient encore aucun script de migration (relevé du 11/11/2026).

1. Le module d'exemple, écrit pour la 19

Le module oski_parc suit le matériel prêté aux contacts : une désignation, un numéro, une référence calculée à partir d'un préfixe stocké en paramètre système, un rapport « Fiche de prêt ». Il est volontairement écrit comme on l'écrivait en 19, version 19.0.1.0.0 :

from odoo import api, fields, models, tools
from odoo.osv import expression


class OskiParcMateriel(models.Model):
    _name = 'oski.parc.materiel'
    _description = 'Matériel prêté'
    _rec_names_search = ['name', 'numero']

    name = fields.Char('Désignation', required=True)
    numero = fields.Char('Numéro')
    reference = fields.Char('Référence', compute='_compute_reference', store=True)
    partner_id = fields.Many2one('res.partner', 'Prêté à')
    date_pret = fields.Date('Date du prêt')
    company_id = fields.Many2one('res.company', 'Société', default=lambda self: self.env.company)

    @api.model
    @tools.ormcache()
    def _prefixe(self):
        return self.env['ir.config_parameter'].sudo().get_param('oski_parc.prefixe', 'MAT')

    @api.depends('numero')
    def _compute_reference(self):
        for rec in self:
            rec.reference = f"{self._prefixe()}-{rec.numero}" if rec.numero else False

    @api.model
    def _changer_prefixe(self, prefixe):
        self.env['ir.config_parameter'].sudo().set_param('oski_parc.prefixe', prefixe)
        self.env.registry.clear_cache()

    @api.model
    def _domaine_en_pret(self, partner=None):
        domaine = [('partner_id', '!=', False)]
        if partner:
            domaine = expression.AND([domaine, [('partner_id', '=', partner.id)]])
        return domaine

S'y ajoutent les droits au format 19 (security/ir.model.access.csv et une règle multi-société ir.rule en XML), une liste, un formulaire, un menu, et le rapport, dont le gabarit passe un titre au sous-gabarit par un t-set placé dans le corps du t-call :

Installé sur une base Odoo 19 neuve, il fonctionne : trois matériels saisis, références MAT-PC-0042, MAT-VP-0007, MAT-PE-0103, rapport complet avec son titre. Hors l'absence de clé author dans le manifeste (ajoutée ensuite), le seul signal est un DeprecationWarning: Since 19.0, odoo.osv is deprecated use odoo.fields.Domain au chargement.

2. Ce qu'Odoo 20 fait du module tel quel

Le même dossier, copié dans les chemins d'une instance Odoo 20 et installé avec -i oski_parc :

WARNING ma_base odoo.modules.module: The module oski_parc has an incompatible version, setting installable=False

Rien d'autre : pas d'erreur, code de sortie 0, et le module reste à l'état uninstallable dans ir_module_module. Odoo 20 rend non installable toute version complète d'une autre série, comme 19.0.1.0.0 (odoo/modules/module.py, contrôle déjà présent en 19 pour 19.0). Attention aux versions courtes : 1.0.0 est complétée en 20.0.1.0.0 et passe le contrôle. Un module 19 bien versionné ne peut donc pas s'installer par accident sur une base 20 ; en contrepartie, une installation scriptée qui ne lit pas le journal croit avoir réussi. Les erreurs que le module provoquerait une fois installable sont détaillées dans Module Odoo 19 sous Odoo 20 : les messages d'erreur et leur correctif.

Changer la version du manifeste est donc la dernière étape du port, pas la première : tant qu'elle reste en 19.0.x, le module 19 peut cohabiter sans danger avec une instance 20 pendant le travail.

4. upgrade_code : les scripts fournis pour passer en 20

odoo-bin upgrade_code existe toujours en 20. Il applique aux fichiers sources des scripts de réécriture rangés dans odoo/upgrade_code/, nommés par la version qui a introduit le changement. Ses options, lues dans odoo-bin upgrade_code --help : --script NOM ou --from VERSION (l'un des deux est obligatoire), --to (par défaut 20.0), --glob, --dry-run, --addons-path. Les scripts qui concernent le passage de 19 à 20 sont ceux en 19.x et 20.0, plus un script nommé sans version :

19.1-00-t-callt-set du corps d'un t-call → attribut du t-call
19.3-00-account-groups, 19.3-00-account-report-foldabledonnées comptables (groupes de comptes, rapports) : modules de localisation
19.3-00-base64-in-xmltype="base64" avec file= → type="bytes" dans les données XML

Cette liste est celle de la 20.0 utilisée ici (septembre 2026). La branche 20.0 publique relue le 11/11/2026 en compte deux de plus : 19.5-00-material-symbols-icons (icônes FontAwesome → <i class="oi" data-icon="…"/>) et 20.0-00-search-date-filters (retire start_month, end_month, start_year, end_year des filtres de date). La branche 19.0 publique, elle, s'arrête aux scripts 18.5.

On lance les scripts un par un, limités au module par --glob, sur une copie sous Git :

./odoo-bin upgrade_code --addons-path=mes_addons --glob 'oski_parc/**/*' --script 19.4-00-ir-access

Avec --glob 'oski_parc/**/*', --from 19.0 s'arrête quand même, sur KeyError: 'ar_base' dans 19.3-00-account-groups.py : ce script cherche des fichiers de plans comptables que le motif exclut. La branche 20.0 publique a depuis remplacé cet accès par un .get() qui ignore le plan absent (non rejoué ici). --from 19.4 passe, mais saute 19.1-00-t-call. Lancer les scripts un par un avec --script marche dans tous les cas.

6. Les scripts de migration : où, quand, avec quoi

upgrade_code réécrit des fichiers. Il ne touche à aucune base. Dès qu'une nouvelle version du module change la forme des données déjà enregistrées, il faut un script de migration, exécuté par Odoo pendant le -u. Ils se rangent dans le module, un dossier par version :

oski_parc/
└── migrations/
    ├── 0.0.0/
    │   ├── pre-journal.py
    │   ├── post-journal.py
    │   └── end-journal.py
    └── 20.0.1.1.0/
        ├── pre-renommer_numero.py
        ├── post-prefixe_et_references.py
        └── end-supprimer_parametre.py
  • Nom des fichiers : seuls les fichiers .py commençant par pre-, post- ou end- sont lus, triés par nom dans chaque dossier. Le dossier peut porter la version complète (20.0.1.1.0) ou la seule version du module (1.1.0), complétée par la série d'Odoo.
  • Condition : un dossier passe si version installée < version du dossier ≤ version du manifeste. Le dossier spécial 0.0.0 passe à chaque montée de version : en premier pour pre, en dernier pour post et end.
  • Signature : chaque fichier définit migrate(cr, version) (les noms _cr et _version sont aussi acceptés). version est la version installée avant la mise à jour ; une autre signature arrête tout, comme on le verra.

La version 20.0.1.1.0 du module fait trois changements : le champ numero devient numero_serie, le préfixe passe du paramètre système à un champ de la société (oski_parc_prefixe), et la référence prend la forme PRÉFIXE/NUMÉRO au lieu de PRÉFIXE-NUMÉRO. Chaque changement a son script.

pre : renommer la colonne avant que l'ORM ne la remplace

Au chargement, l'ORM voit un champ numero_serie sans colonne et crée une colonne vide. Le script pre passe juste avant : il renomme la colonne, et l'ORM la trouve déjà remplie. À ce stade, le nouveau code du module n'est pas chargé ; on travaille en SQL.

import logging

_logger = logging.getLogger(__name__)


def migrate(cr, version):
    # avant le chargement du nouveau code : SQL seulement
    cr.execute("""
        SELECT 1 FROM information_schema.columns
         WHERE table_name = 'oski_parc_materiel' AND column_name = 'numero'
    """)
    if not cr.fetchone():
        return
    cr.execute("ALTER TABLE oski_parc_materiel RENAME COLUMN numero TO numero_serie")
    cr.execute("SELECT count(*) FROM oski_parc_materiel WHERE numero_serie IS NOT NULL")
    _logger.info("colonne numero renommée en numero_serie (%s valeurs gardées)", cr.fetchone()[0])

Le test d'existence rend le script rejouable : relancé sur une base déjà migrée, il ne fait rien.

post : l'ORM est là, recalculer

Après le chargement, le modèle et ses nouveaux champs existent : on peut ouvrir un environnement. La référence est un champ calculé stocké dont la formule a changé ; Odoo ne recalcule pas tout seul les valeurs déjà enregistrées (sans script, elles restent à l'ancien format, section 8). Ici, écrire le préfixe sur la société en recalcule déjà une partie ; add_to_compute couvre tous les cas, matériel sans société compris :

import logging

from odoo import SUPERUSER_ID, api

_logger = logging.getLogger(__name__)


def migrate(cr, version):
    # après le chargement du module : l'ORM est là, nouveaux champs compris
    env = api.Environment(cr, SUPERUSER_ID, {})
    prefixe = env['ir.config_parameter'].get_str('oski_parc.prefixe')
    if prefixe:
        env['res.company'].search([]).oski_parc_prefixe = prefixe
    # le format de la référence a changé : recalculer toutes les références stockées
    materiels = env['oski.parc.materiel'].search([])
    env.add_to_compute(materiels._fields['reference'], materiels)
    materiels.flush_recordset(['reference'])
    _logger.info("préfixe %r repris, %s références recalculées", prefixe, len(materiels))

end : nettoyer quand tout le monde est à jour

Les scripts end passent une fois tous les modules mis à jour. C'est l'endroit des nettoyages : un autre module mis à jour dans le même -u a pu lire l'ancien paramètre dans son propre script post.

import logging

_logger = logging.getLogger(__name__)


def migrate(cr, version):
    # tous les modules sont à jour : l'ancien paramètre ne sert plus à personne
    cr.execute("DELETE FROM ir_config_parameter WHERE key = 'oski_parc.prefixe'")
    _logger.info("paramètre oski_parc.prefixe supprimé (%s ligne)", cr.rowcount)

Les trois scripts de 0.0.0 se contentent de journaliser leur étape, la version reçue et la présence du modèle dans le registre :

# imports et _logger comme dans le script post
def migrate(cr, version):
    env = api.Environment(cr, SUPERUSER_ID, {})
    _logger.info("pre 0.0.0 : version installée %s, modèle chargé : %s",
                 version, 'oski.parc.materiel' in env.registry)

7. La montée de version, lue dans le journal

Sur la base de test, le module est en 20.0.1.0.0 avec trois matériels, et le préfixe a été changé en PARC (les références stockées, elles, sont restées en MAT-… : la 1.0.0 ne les recalculait pas). Le manifeste passe en 20.0.1.1.0 ; odoo-bin module list montre l'écart entre la base et le disque :

oski_parc 20.0.1.0.0 20.0.1.1.0 'installed' Parc de matériel prêté

Ce que le journal établit :

  • L'ordre : pre de 0.0.0 puis de 20.0.1.1.0 ; post de 20.0.1.1.0 puis de 0.0.0 ; end dans le même ordre que post. Le préfixe de chaque ligne Running upgrade dit l'étape : [>v] pour pre, [v>] pour post, [$v] pour end.
  • Ce qui est disponible : en pre, 'oski.parc.materiel' in env.registry vaut False ; en post et end, True. En pre, le modèle du module n'existe pas encore pour l'ORM : seul le SQL sur ses tables est sûr.
  • La version reçue : 20.0.1.0.0 à toutes les étapes, y compris en end. Un script qui doit savoir d'où l'on vient la compare avec odoo.tools.parse_version, pas en chaîne.
  • La ligne de durée oski_parc.pre from 20.0.1.0.0 to 20.0.1.1.0 in 0.003 seconds résume chaque étape. Quand 0.0.0 passe en dernier, elle annonce « to 0.0.0 » : c'est le dernier dossier exécuté, pas une version cible.
  • Le nettoyage d'Odoo vient après les scripts end : Deleting … ir.model.fields (oski_parc.field_oski_parc_materiel__numero) retire la définition de l'ancien champ.

Après la mise à jour : colonne numero_serie remplie (PC-0042, VP-0007, PE-0103), références PARC/PC-0042…, préfixe PARC sur la société, paramètre système supprimé, et les deux tests du module toujours verts. Pour voir aussi les requêtes SQL d'une mise à jour, --log-sql est présenté dans Journaux Odoo 20.

8. Contre-épreuves : ce qui se perd sans bruit

Deux copies de la même base, prises avant la mise à jour, ont servi à rejouer les oublis les plus courants.

Sans le script pre

Même version 20.0.1.1.0, même -u, fichier pre-renommer_numero.py retiré : code de sortie 0, aucune erreur, aucun avertissement. Les scripts post et end passent normalement.

L'ORM a créé une colonne numero_serie vide, puis le nettoyage de fin a supprimé le champ numero et sa colonne (ALTER TABLE … DROP COLUMN … CASCADE, dans odoo/addons/base/models/ir_model.py). Les numéros ne sont plus dans la base : seule une sauvegarde les rendrait.

Sans changer la version du manifeste

Nouveau code, mais manifeste resté en 20.0.1.0.0 : -u oski_parc n'exécute aucun script, pas même ceux de 0.0.0, et le journal ne le signale pas. Résultat relevé : la colonne numero est supprimée, numero_serie est vide, les références restent à l'ancien format MAT-PC-0042 et le paramètre système est toujours là.

Un champ renommé sans script pre, c'est une suppression

Pour l'ORM, renommer un champ revient à en supprimer un et à en créer un autre. Sans script pre, la mise à jour se termine en succès et supprime la colonne d'origine. Rejouez toujours une montée de version sur une copie de la production et comparez les données avant et après, pas seulement le code de sortie.

Pas de nouvelle version, pas de script

Les scripts ne tournent que si la version du manifeste augmente par rapport à celle enregistrée en base. Ajouter un dossier migrations/ sans changer la version, ou numéroter le dossier au-delà de la version du manifeste, et rien ne s'exécute. Vérifiez avec odoo-bin module list que les deux colonnes de version diffèrent avant le -u.

Dernier essai, sur la copie de l'essai précédent, encore en 20.0.1.0.0 : un script pre-a_signature.py défini comme def migrate(env, version). La mise à jour s'arrête sur TypeError: module oski_parc: `migrate`'s signature should be `(cr, version)`, … is (env, version), code de sortie 255 ; la transaction est annulée et le module reste en 20.0.1.0.0. Le fichier, trié par nom, est passé juste après le pre de 0.0.0 : l'erreur vient avant toute modification.

9. Ce qui a changé depuis la 19

Les mêmes scripts de journal, placés dans un dossier 19.0.1.1.0 et dans 0.0.0 du module 19, ont été rejoués sur la base 19 : même ordre (pre 0.0.0, pre 19.0.1.1.0, post 19.0.1.1.0, post 0.0.0, end 19.0.1.1.0, end 0.0.0), même version reçue. Le gestionnaire de migrations a été comparé à celui de la branche 19.0 publique (relue le 11/11/2026) :

Venant de la 19

Un script de migration s'écrit en 20 comme en 19, dans un dossier 20.0.x.y.z. Ce qui change, c'est le code qu'il appelle : un script post qui utilise get_param, odoo.osv ou ir.model.access échoue en 20 comme le reste du module. Portez-les avec le module, et relisez les lignes de journal que vos outils d'exploitation analysent.

À retenir

  • Un manifeste en 19.0.x.y.z rend le module non installable en 20, sans erreur (une version courte, elle, passe) : changez la version en dernier, une fois le code porté.
  • upgrade_code se lance script par script, avec --glob 'mon_module/**/*', sur un dépôt Git propre ; il ne traite ni odoo.osv, ni get_param, ni t-esc.
  • pre : SQL seulement, avant le nouveau code. post : ORM disponible, après le chargement du module. end : après tous les modules.
  • 0.0.0 passe à chaque montée de version, en premier pour pre, en dernier pour post et end ; la fonction est migrate(cr, version).
  • Un champ renommé sans script pre, ou une version inchangée, et la mise à jour réussit en perdant des données.
