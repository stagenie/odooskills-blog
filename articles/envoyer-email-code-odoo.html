Envoyer un email depuis le code Odoo 20 : message_post, mail.template

Trois façons de faire partir un courriel depuis Python : message_post, un mail.template ou un mail.mail créé à la main. Elles ne laissent pas la même trace et ne préviennent pas les mêmes personnes : le choix, rejoué sur un devis de la démo.

~6 minutes de lecture · niveau intermédiaire · série Astuces dev Odoo 20

Édition : Community. Vérifié sur Odoo 20.0 Community, octobre 2026, base de démonstration avec Ventes, devis S00001 d'Acme Corporation, et un petit module d'exemple qui déclare un gabarit. Aucun serveur sortant : les courriels restent dans la file, rien n'est réellement parti.

1. message_post : la note ou le message

message_post existe sur tout modèle qui hérite de mail.thread (devis, contact, tâche…). Il crée un mail.message dans le chatter, puis un courriel pour chaque personne à prévenir. Tout se joue sur le sous-type. Ce script, passé à odoo-bin shell, poste une note puis un message sur le devis S00001 :

# message_post.py
from markupsafe import Markup
so = env['sale.order'].browse(1).with_user(env.ref('base.user_admin'))
Mail = env['mail.mail'].sudo()
avant = Mail.search([]).ids

note = so.message_post(body="Client rappelé, livraison confirmée.")
msg = so.message_post(
    body=Markup("<p>Votre commande <b>%s</b> part demain.</p>") % so.name,
    subject="Expédition",
    message_type='comment',
    subtype_xmlid='mail.mt_comment',
    partner_ids=so.partner_id.ids,
)
print(note.subtype_id.name, "→ notifiés :", note.notified_partner_ids.mapped('name'))
print(msg.subtype_id.name, "→ notifiés :", msg.notified_partner_ids.mapped('name'))
for m in Mail.search([('id', 'not in', avant)]):
    print(m.id, m.state, m.recipient_ids.email, "|", m.subject)

Ce que montre la sortie :

  • Sans subtype_xmlid, le message est une note (sous-type mail.mt_note, le repli de message_post) : aucun abonné n'est prévenu.
  • Avec mail.mt_comment, le client passé dans partner_ids reçoit le message, et les abonnés du devis inscrits aux « Messages » : ici Marc Demo, le vendeur. L'auteur, Mitchell Admin, n'est pas notifié.
  • Les courriels sont des mail.mail à l'état outgoing. Sous 100 courriels par message (paramètre mail.mail.force.send.limit), Odoo les envoie juste après le commit de la transaction ; au-delà, la file s'en charge.

Attention à partner_ids sur une note : rejoué avec so.message_post(body="Note interne", partner_ids=so.partner_id.ids), le sous-type reste « Notes », mais Acme Corporation est notifiée et un mail.mail part vers son adresse. Un partenaire cité est toujours prévenu.

Dans le shell, with_user(…) fait de l'administrateur l'auteur du message ; sans lui, l'auteur serait OdooBot. Dans une méthode de bouton, l'auteur est l'utilisateur qui clique.

2. mail.template : le gabarit, deux façons de l'envoyer

Dès que le courriel dépasse deux lignes, ou que l'utilisateur doit pouvoir en changer le texte, déclare un gabarit dans les données de ton module :

<!-- mon_courriel/data/mail_template.xml -->
<odoo>
    <record id="mail_template_expedition" model="mail.template">
        <field name="name">Commande : avis d'expédition</field>
        <field name="model_id" ref="sale.model_sale_order"/>
        <field name="subject">{{ object.name }} : votre commande part demain</field>
        <field name="email_from">{{ object.user_id.email_formatted or user.email_formatted }}</field>
        <field name="lang">{{ object.partner_id.lang }}</field>
        <field name="body_html" type="html">
<div>
    <p>Bonjour <t t-out="object.partner_id.name"/>,</p>
    <p>Votre commande <strong t-out="object.name"/>
        (<t t-out="format_amount(object.amount_total, object.currency_id)"/>)
        part demain.</p>
</div>
        </field>
    </record>
</odoo>

Le sujet utilise la syntaxe {{ … }}, le corps du QWeb avec t-out. Pas de destinataire écrit : l'option use_default_to, vraie par défaut, envoie au client du document. Le module installé (-i mon_courriel), deux appels s'offrent à toi :

# template.py
so = env['sale.order'].browse(1).with_user(env.ref('base.user_admin'))
tpl = env.ref('mon_courriel.mail_template_expedition')

mail = env['mail.mail'].sudo().browse(tpl.send_mail(so.id))
print("send_mail :", mail.id, mail.state, mail.recipient_ids.email, "|", mail.subject)
print(mail.body_html.strip())

msg = so.message_post_with_source(tpl, message_type='comment', subtype_xmlid='mail.mt_comment')
print("message_post_with_source :", msg.message_type, "→ notifiés :", msg.notified_partner_ids.mapped('name'))
  • send_mail(res_id) rend le gabarit et crée un mail.mail pour les destinataires du gabarit, sans prévenir les abonnés. Sans force_send=True, il attend la file, l'action planifiée « Mail: Email Queue Manager », qui passe toutes les heures.
  • message_post_with_source(template, …) rend le même gabarit et le publie comme un message_post : message dans le chatter, client et abonnés notifiés selon le sous-type.

Lis le chatter de bas en haut. L'enveloppe à côté du nom marque les messages qui ont notifié par courriel. Le message du gabarit est signé Marc Demo : Odoo déduit l'auteur de l'expéditeur du gabarit, ici le vendeur. La ligne d'OdooBot est le mail.mail de send_mail, lancé depuis le shell : elle n'est que provisoire. Le gabarit a auto_delete vrai par défaut ; une fois le courriel envoyé, Odoo supprime le mail.mail et, comme ce n'est pas une notification, le message avec lui. En rejouant l'étape qui suit un envoi réussi, la ligne disparaît bien de message_ids. Si tu veux une trace durable, prends message_post_with_source.

3. mail.mail : le courriel brut

Pour un courriel qui ne concerne aucun document (fin d'un export, alerte d'administration), crée directement le mail.mail. Aucun rendu : le corps est le HTML que tu passes.

mail = env['mail.mail'].create({
    'subject': "Export terminé",
    'body_html': "<p>Le fichier est prêt.</p>",
    'email_to': env.ref('base.user_admin').email,
})
print(mail.id, mail.state, mail.email_from, mail.model, mail.auto_delete)
22 outgoing "OdooBot" <odoobot@example.com> False False

Sans email_from, l'expéditeur est l'utilisateur courant ; sans model, rien dans le chatter ; auto_delete est faux, le courriel reste visible après l'envoi. Il part avec la file, ou tout de suite par mail.send(). Pour suivre tous ces courriels, active le mode développeur puis ouvre Paramètres › Technique › E-mail › E-mails :

Le HTML passé en str s'affiche en toutes lettres

message_post échappe tout corps de type str et ne garde tel quel qu'un Markup. Rejoué sur le devis :

print(so.message_post(body="<b>Urgent</b>").body)
print(so.message_post(body=Markup("<b>Urgent</b>")).body)
client = "<script>x</script>"
print(so.message_post(body=Markup("<p>Client : %s</p>") % client).body)
<p>&lt;b&gt;Urgent&lt;/b&gt;</p> <b>Urgent</b> <p>Client : &lt;script&gt;x&lt;/script&gt;</p>

Écris donc Markup("…%s…") % valeur : la valeur insérée est échappée, le gabarit non. Jamais Markup(f"…{valeur}…"), qui laisse passer le HTML de la valeur. Même famille de panne dans un gabarit : t-esc ne rend plus rien en Odoo 20 ; rejoué dans body_html, il donne « Bonjour , ».

À retenir

  • message_post sans sous-type = note ; mail.mt_comment pour écrire au client et aux abonnés ; un partenaire de partner_ids est prévenu même sur une note.
  • Un gabarit s'envoie par message_post_with_source (trace durable, abonnés) ou send_mail (destinataires du gabarit, file d'envoi).
  • mail.mail à la main pour un courriel sans document : pas de rendu, pas de chatter.
  • Corps HTML = Markup ; gabarit = t-out.
