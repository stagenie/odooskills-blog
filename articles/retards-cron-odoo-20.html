Les retards en Odoo 20 : compteurs et action planifiée

L'emprunt sait déjà dire s'il est en retard. Il ne sait ni se laisser filtrer, ni se faire compter sur la fiche de l'adhérent, ni se rappeler au bon souvenir de personne. Trois manques, trois mécanismes : search=, les boutons intelligents, et un ir.cron.

~18 minutes de lecture · niveau intermédiaire · parcours Framework & ORM

Ce que tu vas apprendre

Chercher

Rendre un champ calculé non stocké filtrable avec search=, et poser le filtre dans la vue.

Compter

Deux compteurs sur la fiche de l'adhérent : l'un stocké, l'autre surtout pas.

Automatiser

Une action planifiée qui relance les retards toute seule, chaque nuit.

Prérequis

  • Le module biblio des articles précédents, jusqu'aux emprunts (library.loan, son champ calculé is_late).
  • Le serveur Odoo 20 joignable sur http://localhost:8069, base biblio.
  • Au moins un emprunt dont l'échéance est dépassée — sinon rien à voir.

Un champ qui existe sans exister

À la fin de l'article précédent, is_late colorait les lignes en rouge. Mais essaie de chercher dessus :

>>> env['library.loan'].search([('is_late', '=', True)]) ValueError: Field has no SQL representation because it is not stored in condition ('is_late', '=', True)

Normal : il n'y a pas de colonne is_late dans la table. Le champ est calculé à la volée, en Python, au moment où on le lit — le moteur de recherche, lui, ne parle que SQL.

Un champ non stocké est donc affichable mais pas cherchable… tant qu'on ne lui a pas appris à traduire une question en domaine SQL. C'est tout le rôle de l'attribut search=.

1. Rendre is_late cherchable

Un champ devient cherchable de trois façons : il est stocké, il a une expression SQL, ou il nomme une méthode dans search=. C'est exactement ce que dit l'ORM :

@property
def _description_searchable(self) -> bool:
    return bool(self.store or self.search or self.compute_sql)

— odoo/orm/fields.py, Odoo 20.0

Ouvre models/library_loan.py. On ajoute l'attribut, un compteur de jours au passage, et la méthode :

from odoo.fields import Domain

    is_late = fields.Boolean(
        string="En retard",
        compute='_compute_is_late',
        search='_search_is_late',
    )
    days_late = fields.Integer(string="Jours de retard", compute='_compute_is_late')

    @api.depends('date_due', 'date_return', 'state')
    def _compute_is_late(self):
        today = fields.Date.context_today(self)
        for loan in self:
            fin = loan.date_return or today
            loan.is_late = bool(loan.date_due) and loan.state == 'ongoing' and fin > loan.date_due
            loan.days_late = (fin - loan.date_due).days if loan.is_late else 0

    def _search_is_late(self, operator, value):
        if operator != 'in':
            return NotImplemented
        en_retard = Domain('state', '=', 'ongoing') & Domain(
            'date_due', '<', fields.Date.context_today(self)
        )
        return en_retard if True in value else ~en_retard

Une méthode de calcul peut alimenter plusieurs champs : days_late profite du travail déjà fait par _compute_is_late, sans deuxième parcours.

Ce que la méthode reçoit vraiment

Voilà le point qui surprend. On écrit un filtre [('is_late', '=', True)], mais la méthode ne voit jamais un =. Vérifions-le en espionnant la méthode depuis la console (odoo-bin shell) : on l'enveloppe, on lance trois recherches, on regarde ce qui est arrivé.

recu = []
original = type(Loan)._search_is_late

def espion(self, operator, value):
    recu.append((operator, repr(value)))
    return original(self, operator, value)

type(Loan)._search_is_late = espion
Loan.search([('is_late', '=', True)])
Loan.search([('is_late', '=', False)])
Loan.search([('is_late', '!=', True)])
type(Loan)._search_is_late = original
print(recu)
[('in', 'OrderedSet([True])'), ('not in', 'OrderedSet([True])'), ('in', 'OrderedSet([True])'), ('not in', 'OrderedSet([True])'), ('in', 'OrderedSet([True])')]

Trois recherches, cinq appels. Deux enseignements :

  • l'ORM normalise avant d'appeler : tous les = deviennent des in, et la valeur devient une collection. Comparer value à True ne marcherait pas ; il faut True in value ;
  • quand la méthode répond NotImplemented sur not in, Odoo rappelle avec l'opérateur inverse et nie le résultat. D'où le doublement des appels sur les deux recherches négatives. C'est aussi pourquoi notre méthode peut ne gérer qu'un seul opérateur.

La méthode doit rendre un domaine, pas un jeu d'enregistrements : un Domain (ou une liste, acceptée telle quelle). Ce domaine remplace la condition d'origine dans la requête, et c'est ce qui rend la recherche aussi rapide qu'un filtre ordinaire : tout se passe en SQL, aucun enregistrement n'est chargé en Python.

Le piège du « oui, mais je l'ai déjà écrit en boucle »

La tentation est de rendre [('id', 'in', ids)] après avoir parcouru les enregistrements en Python. Ça fonctionne sur trois emprunts et s'écroule sur trente mille : toute la table est chargée à chaque filtre. Si la règle ne s'exprime pas en domaine, c'est souvent qu'il faut stocker le champ, pas contourner.

Le calcul et la recherche doivent dire la même chose

Danger classique : deux définitions du retard qui divergent — l'une en Python, l'autre en SQL. Un contrôle en deux lignes vaut mieux qu'une confiance :

calcules = Loan.search([]).filtered('is_late')
cherches = Loan.search([('is_late', '=', True)])
print(set(calcules.ids) == set(cherches.ids))
True

2. Le filtre dans la vue de recherche

Le champ est cherchable ; reste à l'offrir à l'utilisateur. Une vue de recherche se déclare comme les autres, dans views/library_loan_views.xml :

<record id="library_loan_view_search" model="ir.ui.view">
    <field name="name">library.loan.search</field>
    <field name="model">library.loan</field>
    <field name="arch" type="xml">
        <search string="Emprunts">
            <field name="member_id"/>
            <field name="copy_id"/>
            <filter name="filter_late" string="En retard" domain="[('is_late', '=', True)]"/>
            <filter name="filter_ongoing" string="En cours" domain="[('state', '=', 'ongoing')]"/>
            <separator/>
            <filter name="filter_due" string="Échéance" date="date_due"/>
            <group>
                <filter name="group_member" string="Adhérent" context="{'group_by': 'member_id'}"/>
                <filter name="group_state" string="État" context="{'group_by': 'state'}"/>
            </group>
        </search>
    </field>
</record>

Trois choses à lire dans ce bloc :

  • les <field> du haut alimentent la barre de recherche libre — taper trois lettres proposera « Adhérent contient… » ;
  • un <filter> porte un domain : c'est notre méthode de recherche qui sera appelée derrière ;
  • un <filter> muni de date="…" se déplie en périodes (ce mois-ci, ce trimestre, l'an dernier…) sans une ligne de plus.

Les filtres rassemblés dans un <group> deviennent la colonne « Regrouper par ». Le titre, Odoo le pose lui-même.

Ne pas écrire <group expand="0" string="Regrouper par">

L'idiome traîne dans beaucoup de modules anciens. Dans une vue de recherche il rend la vue invalide et le module refuse de s'installer :

RELAXNG_ERR_INVALIDATTR: Invalid attribute expand for element group Définition de vue library.loan.search invalide dans biblio/views/library_loan_views.xml

Même sanction pour string. Le <group> nu est la forme correcte. Pourquoi ce réflexe faux survit-il ? Parce qu'une vue formulaire n'est pas validée par le schéma, contrairement aux vues liste et recherche : le même attribut y passe sans bruit.

La liste, elle, gagne deux colonnes — les jours de retard et, plus loin, les relances :

<list string="Emprunts" decoration-danger="is_late">
    <field name="copy_id"/>
    <field name="member_id"/>
    <field name="date_out"/>
    <field name="date_due"/>
    <field name="date_return"/>
    <field name="days_late"/>
    <field name="reminder_count"/>
    <field name="state"/>
</list>

3. Remonter les retards sur la fiche de l'adhérent

Un bibliothécaire ne travaille pas sur la liste des emprunts : il ouvre la fiche de l'adhérent au comptoir. Il faut donc que l'information remonte. Dans models/library_member.py :

    loan_ids = fields.One2many('library.loan', 'member_id', string="Emprunts")
    loan_count = fields.Integer(
        string="Nombre d'emprunts",
        compute='_compute_loan_count',
        store=True,
    )
    late_loan_count = fields.Integer(
        string="Nombre de retards",
        compute='_compute_late_loan_count',
    )

    @api.depends('loan_ids')
    def _compute_loan_count(self):
        for member in self:
            member.loan_count = len(member.loan_ids)

    @api.depends('loan_ids.is_late')
    def _compute_late_loan_count(self):
        for member in self:
            member.late_loan_count = len(member.loan_ids.filtered('is_late'))

Deux compteurs presque jumeaux, une différence décisive : store=True sur le premier, rien sur le second. Ce n'est pas une inattention.

Pourquoi un compteur de retards ne se stocke jamais

Odoo ne recalcule un champ stocké que lorsqu'une de ses dépendances est écrite — c'est ce que fait modified() dans l'ORM : « invalidates the cache where necessary, and prepares the recomputation of dependent stored fields ». Or le nombre de retards ne change pas parce qu'on écrit quelque part : il change parce que la nuit est passée. Et minuit n'écrit rien en base.

On peut le voir, sans attendre un mois. Dans la console, on avance l'horloge de trente jours, on vide le cache, et on ne touche à aucun enregistrement :

import datetime
from odoo import fields

avant = {m.card_number: (m.loan_count, m.late_loan_count) for m in Member.search([])}

vrai = fields.Date.context_today
fields.Date.context_today = staticmethod(
    lambda record, timestamp=None: vrai(record, timestamp) + datetime.timedelta(days=30))
env.invalidate_all()

apres = {m.card_number: (m.loan_count, m.late_loan_count) for m in Member.search([])}
env.cr.execute("SELECT card_number, loan_count FROM library_member ORDER BY card_number")
print(avant, apres, dict(env.cr.fetchall()), sep="\n")
{'CARTE-001': (1, 1), 'CARTE-002': (1, 0), 'CARTE-003': (2, 1)} {'CARTE-001': (1, 1), 'CARTE-002': (1, 1), 'CARTE-003': (2, 1)} {'CARTE-001': 1, 'CARTE-002': 1, 'CARTE-003': 2}

CARTE-002 passe de 0 à 1 retard sans qu'une seule écriture ait eu lieu : son échéance est simplement tombée derrière l'horloge. La colonne SQL du compteur stocké, elle, n'a pas bougé — elle n'avait aucune raison de bouger, et c'est bien le problème. Un compteur de retards stocké afficherait la valeur du jour de la dernière modification de la fiche, indéfiniment.

La contrepartie est connue : un champ non stocké n'a pas de colonne. On le vérifie directement :

colonnes library_member : ['card_number', 'create_date', 'create_uid', 'id', 'join_date', 'loan_count', 'partner_id', 'write_date', 'write_uid']

Ni late_loan_count, ni loan_ids — un One2many n'est jamais une colonne, il se lit depuis la clé étrangère d'en face. Conséquence pratique : on ne peut ni trier, ni regrouper sur le nombre de retards. Le filtre de la section 2 reste le bon outil pour ça.

Les boutons intelligents

Reste à l'afficher. Un bouton intelligent, c'est un bouton placé dans un <div name="button_box"> en haut du formulaire, qui montre un chiffre et ouvre la liste correspondante. Deux méthodes d'action, dans le même fichier :

    def action_view_loans(self):
        self.ensure_one()
        return {
            'type': 'ir.actions.act_window',
            'name': f"Emprunts de {self.name}",
            'res_model': 'library.loan',
            'view_mode': 'list,form',
            'domain': [('member_id', '=', self.id)],
            'context': {'default_member_id': self.id},
        }

    def action_view_late_loans(self):
        self.ensure_one()
        action = self.action_view_loans()
        action['name'] = f"Retards de {self.name}"
        action['domain'] = [('member_id', '=', self.id), ('is_late', '=', True)]
        return action

Une méthode d'action rend un dictionnaire : Odoo l'exécute côté navigateur comme si l'utilisateur avait cliqué dans un menu. Le context avec default_ pré-remplit l'adhérent si l'utilisateur crée un emprunt depuis cette liste. Et la seconde méthode réutilise la première au lieu de la recopier : c'est du Python ordinaire.

Côté vue, dans views/library_member_views.xml, juste après <sheet> :

<div class="oe_button_box" name="button_box">
    <button name="action_view_loans" type="object"
            class="oe_stat_button" icon="book_5">
        <field name="loan_count" widget="statinfo" string="Emprunts"/>
    </button>
    <button name="action_view_late_loans" type="object"
            class="oe_stat_button" icon="schedule"
            invisible="late_loan_count == 0">
        <field name="late_loan_count" widget="statinfo" string="Retards"/>
    </button>
</div>

Le widget statinfo affiche la valeur et son libellé ; invisible masque le bouton des retards quand il n'y en a pas — un zéro rouge permanent n'apprend rien à personne.

Changement v19 → v20 : les icônes des boutons

En Odoo 19, l'attribut icon était trié par préfixe : fa-… produisait une icône FontAwesome, oi-… une icône maison, et tout le reste était traité comme le chemin d'une image. Odoo 20 a supprimé FontAwesome et, avec lui, ce tri : la chaîne devient directement <i class="o_button_icon oi" data-icon="…">, rendue par ligature de la police d'icônes.

Un icon="fa-list" hérité d'un module v19 ne lève aucune erreur : il affiche le texte « fa-list » à la place de l'icône. Les noms valides sont ceux des Material Symbols (schedule, list, book_5, warning, group…) et les icônes propres à Odoo, préfixées oi_. Le compte est sans appel : icon="fa- apparaît 621 fois dans les vues XML des addons 19.0, et zéro fois dans celles de la 20.0.

4. Laisser Odoo chercher les retards tout seul

Compter les retards suppose que quelqu'un ouvre l'écran. Pour qu'il se passe quelque chose sans personne devant l'écran, il faut une action planifiée — un enregistrement du modèle ir.cron, que le serveur déclenche à l'heure dite.

Donnons-lui un travail vérifiable : relancer chaque emprunt en retard, une fois par jour au plus. Deux champs de suivi sur l'emprunt, et la méthode :

import logging

_logger = logging.getLogger(__name__)

    reminder_count = fields.Integer(string="Relances", default=0, readonly=True, copy=False)
    reminder_date = fields.Date(string="Dernière relance", readonly=True, copy=False)

    @api.model
    def _cron_relancer_retards(self):
        aujourdhui = fields.Date.context_today(self)
        a_relancer = self.search(
            Domain('is_late', '=', True)
            & (Domain('reminder_date', '=', False) | Domain('reminder_date', '<', aujourdhui))
        )
        for emprunt in a_relancer:
            emprunt.reminder_count += 1
            emprunt.reminder_date = aujourdhui
        _logger.info("Bibliothèque : %s emprunt(s) en retard relancé(s).", len(a_relancer))
        return len(a_relancer)

Trois décisions valent d'être expliquées :

  • Le domaine compose des Domain avec & et | plutôt qu'une liste en notation polonaise. C'est lisible, et c'est la forme recommandée en Odoo 20 — notre _search_is_late est appelée au passage, sans qu'on ait à redire ce qu'est un retard.
  • Le cron est idempotent : la condition sur reminder_date garantit qu'un deuxième passage dans la même journée ne relance personne. Un cron qui n'est pas idempotent finit toujours par s'exécuter deux fois.
  • Il journalise. Une tâche de fond sans trace dans le journal est une tâche dont on ne saura jamais si elle tourne.

Déclare-le maintenant dans data/library_cron.xml :

<?xml version="1.0" encoding="utf-8"?>
<odoo>

    <record id="library_cron_reminder" model="ir.cron">
        <field name="name">Bibliothèque : relancer les emprunts en retard</field>
        <field name="model_id" ref="model_library_loan"/>
        <field name="state">code</field>
        <field name="code">model._cron_relancer_retards()</field>
        <field name="interval_number">1</field>
        <field name="interval_type">days</field>
        <field name="user_id" ref="base.user_root"/>
        <field name="active" eval="True"/>
    </record>

</odoo>

… et ajoute le fichier au manifeste, avant les vues :

    'data': [
        'security/ir.access.csv',
        'data/library_cron.xml',
        'views/library_book_views.xml',
        'views/library_copy_views.xml',
        'views/library_member_views.xml',
        'views/library_loan_views.xml',
    ],

Dans le code, model désigne le modèle pointé par model_id — d'où le @api.model sur la méthode : elle travaille sur le modèle, pas sur un enregistrement. La référence model_library_loan est l'identifiant que le cœur crée automatiquement pour chaque modèle ; il suffit de remplacer les points par des tirets bas.

Mise à jour du module, puis Paramètres → Technique → Automatisation → Actions planifiées (mode développeur activé) :

Les champs Nom, Modèle, Code ne vivent pas dans la table ir_cron : ils appartiennent à l'action serveur. ir.cron est en effet un modèle délégué, exactement le mécanisme de l'article précédent :

class IrCron(models.Model):
    _name = 'ir.cron'
    _inherits = {'ir.actions.server': 'ir_actions_server_id'}

La table ne porte que ce qui relève de la planification — interval_number, interval_type, nextcall, lastcall, priority, user_id, active et deux compteurs d'échec. Tout le reste est emprunté au parent.

Le déclencher sans attendre demain

Le bouton Exécuter manuellement lance le travail immédiatement. Après un clic, la liste des emprunts porte ses relances :

Un second clic dans la même journée ne change rien — c'est l'idempotence recherchée. Depuis la console, la démonstration tient en deux appels :

print(Loan._cron_relancer_retards())   # 1er passage
print(Loan._cron_relancer_retards())   # même jour
2 0

« Exécuter manuellement » ouvre un nouveau curseur

La documentation de la méthode le dit sans détour : « The job is still ran as it would be by the scheduler: a new cursor is used for the execution of the job. » Deux conséquences dans odoo-bin shell :

  • si la session a des écritures non validées sur les lignes que le cron va toucher, le déclenchement s'interbloque : le cron attend un verrou que seule votre transaction peut relâcher. env.cr.commit() d'abord ;
  • le résultat du cron reste invisible de la session en cours, même après env.invalidate_all() : le curseur d'Odoo travaille en repeatable read, donc sur un instantané pris à l'ouverture de la transaction. Il faut une nouvelle transaction pour voir ce que le cron a écrit.

Le cron ne tourne pas ? Regarde d'abord le serveur

Un serveur lancé sans processus de travail (workers = 0, le mode développeur courant) exécute quand même ses crons, mais uniquement tant qu'il tourne : arrête-le le soir, rien ne se passera la nuit. Et la Prochaine date d'exécution fait foi — un cron créé aujourd'hui avec un intervalle d'un jour ne se déclenchera pas forcément dans la minute.

Mémo

BesoinÉcrire

Récapitulatif

  • Un champ calculé non stocké devient cherchable dès qu'il nomme une méthode dans search=.
  • Cette méthode ne reçoit jamais = : l'ORM normalise en in et lui passe une collection de valeurs.
  • Elle rend un domaine, pas des enregistrements — la recherche reste en SQL.
  • Le calcul et la recherche doivent donner le même résultat ; ça se vérifie en deux lignes.
  • Un compteur se stocke s'il dépend de données, jamais s'il dépend de la date du jour.
  • Un bouton intelligent est un bouton dans button_box : une méthode qui rend une action, un chiffre, une icône.
  • En Odoo 20 les icônes n'ont plus de préfixe fa- : un nom de Material Symbol, sinon le nom s'affiche en toutes lettres.
  • Une action planifiée est un ir.cron délégué à une action serveur ; la rendre idempotente n'est pas optionnel.
