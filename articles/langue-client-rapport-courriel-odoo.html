Rapport et courriel dans la langue du client en Odoo 20

Tu travailles en français, ton client lit l'anglais : le courriel, le PDF joint et les textes calculés en Python doivent suivre sa langue, pas la tienne. Trois mécanismes s'en chargent : le champ lang du modèle de courriel, t-lang dans le rapport et with_context(lang=…) dans le code.

~6 minutes de lecture · niveau intermédiaire · série Astuces dev Odoo 20

Édition : Community. Vérifié sur Odoo 20.0 Community, octobre 2026, base de démonstration en français (Ventes, Inventaire, Facturation) à laquelle l'anglais a été ajouté, avec un petit module de rapport d'exemple. Aucun courriel n'est parti : pas de serveur sortant.

1. La langue doit être active, et posée sur le bon partenaire

Le champ lang d'un partenaire ne propose que les langues actives. Sur la base de démonstration française, seul fr_FR l'est : même l'anglais est absent. Pour l'activer en ligne de commande :

./odoo-bin -c odoo.conf -d ma_base --load-language=en_US --stop-after-init

Le choix de la langue se fait ensuite sur la fiche du partenaire, champ lang. Ici, Acme Corporation passe en anglais. Attention : ses trois contacts gardent fr_FR (un contact reprend la langue de sa société quand on la lui attribue, pas quand elle change ensuite). Odoo lit la langue du partenaire du document (partner_id de la facture) : si la facture est adressée à un contact, c'est la langue du contact qui compte.

2. Le courriel : le champ lang du modèle

Un mail.template porte un champ lang, une expression rendue sur chaque enregistrement, par exemple {{ object.partner_id.lang }}. S'il est vide, Odoo prend la langue du partenaire principal du document (_mail_get_partners). Le modèle de facture account.email_template_edi_invoice le laisse vide, et ça suffit. Ce script, passé à odoo-bin shell avec un utilisateur en français, rend le sujet de deux factures de la démo, l'une pour Azure Interior (français), l'autre pour Acme Corporation (anglais) :

# langue_courriel.py
import re
tpl = env.ref('account.email_template_edi_invoice')
factures = env['account.move'].browse([10, 11])     # Azure Interior, Acme Corporation
print("Utilisateur :", env.user.lang, "| champ lang du modèle :", tpl.lang)
print(tpl._render_lang(factures.ids))
sujets = tpl._render_field('subject', factures.ids, compute_lang=True)
for f in factures:
    print(f.name, f.partner_id.name, "→", sujets[f.id])
print("sans compute_lang :", tpl._render_field('subject', [11])[11])
mail = env['mail.mail'].browse(tpl.send_mail(11))
texte = re.sub(r'\s+', ' ', re.sub(r'<[^>]+>', ' ', mail.body_html)).strip()
print(mail.state, "|", mail.subject, "|", texte[:90])
  • _render_lang() renvoie la langue de chaque enregistrement. Odoo regroupe ensuite les enregistrements par langue et rend le modèle avec with_context(lang=…) pour chaque groupe : un envoi groupé mélange sans peine français et anglais.
  • send_mail() passe par ce chemin : le mail.mail créé (état outgoing, en file d'attente) a un sujet et un corps anglais.
  • _render_field(…) sans compute_lang=True rend dans la langue du contexte, donc la tienne. Si tu rends un champ du modèle à la main, passe ce paramètre.

L'interface suit le même calcul. Sur la facture d'Acme Corporation, le bouton Envoyer ouvre l'assistant : libellés en français, courriel en anglais.

Remplis le champ lang toi-même quand le destinataire n'est pas le partenaire principal du document, par exemple {{ object.user_id.lang }} sur un devis, pour un courriel interne destiné au vendeur.

3. Le rapport PDF : t-lang sur le t-call

Un rapport QWeb est rendu dans la langue de celui qui l'imprime, sauf si le gabarit dit le contraire. Les rapports standard le disent : la facture appelle son document avec t-lang="lang" (où lang vaut o.partner_id.lang), le devis avec t-lang="doc.partner_id.lang". Ton propre rapport doit faire de même. Voici celui du module d'exemple, un relevé sur account.move dont les libellés fixes sont traduits dans son i18n/fr.po (« Statement » → « Relevé ») :

<template id="report_releve_document">
    <t t-call="web.external_layout">
        <div class="page">
            <h2>Statement <span t-field="o.name"/></h2>
            <p>Due date: <span t-field="o.invoice_date_due"/></p>
            <p t-foreach="o.invoice_line_ids" t-as="line">
                <span t-field="line.product_id"/>
            </p>
            <p>Total: <span t-field="o.amount_total"/></p>
        </div>
    </t>
</template>

<template id="report_releve">
    <t t-call="web.html_container">
        <t t-foreach="docs" t-as="o">
            <t t-call="mon_rapport_langue.report_releve_document" t-lang="o.partner_id.lang"/>
        </t>
    </t>
</template>

Sans l'attribut t-lang, le relevé d'Acme Corporation sort en français, pour la simple raison que l'utilisateur est en français. Texte extrait du PDF par pdftotext :

11 Relevé FAC/2026/00002 | Échéance : 05/10/2026 | [FURN_8220] Bureau pour quatre personnes | Canapé deux places (Lin) | Total : $ 48 012,50

Avec t-lang et après -u mon_rapport_langue, le script releve.py rend chaque facture, puis les deux dans un seul PDF :

# releve.py
import subprocess, tempfile
def texte(pdf):
    with tempfile.NamedTemporaryFile(suffix='.pdf') as fp:
        fp.write(pdf); fp.flush()
        out = subprocess.run(['pdftotext', fp.name, '-'], capture_output=True, text=True).stdout
    garde = ('Statement', 'Relevé', 'Due', 'Échéance', 'Total', '[FURN', 'Canapé', 'Two-Seat')
    return ' | '.join(l.strip() for l in out.splitlines() if l.strip().startswith(garde))

Report = env['ir.actions.report']
for fid in (10, 11):
    pdf, _f = Report._render_qweb_pdf('mon_rapport_langue.action_report_releve', [fid])
    print(fid, texte(pdf))
pdf, _f = Report.with_context(lang='en_US')._render_qweb_pdf('mon_rapport_langue.action_report_releve', [11])
print("with_context(lang='en_US') :", texte(pdf))
pdf, _f = Report._render_qweb_pdf('mon_rapport_langue.action_report_releve', [10, 11])
with tempfile.NamedTemporaryFile(suffix='.pdf') as fp:
    fp.write(pdf); fp.flush()
    for page in (1, 2):
        out = subprocess.run(['pdftotext', '-f', str(page), '-l', str(page), fp.name, '-'], capture_output=True, text=True).stdout
        print("page", page, ":", [l for l in out.splitlines() if l.startswith(('Statement', 'Relevé'))])

Tout bascule : le texte fixe traduit par le module, le nom des articles (champ traduisible), le format de date (10/05/2026 contre 05/10/2026) et celui du montant. Deux remarques :

  • Report.with_context(lang='en_US') marche aussi, mais impose une langue à tout le lot. Seul t-lang, évalué pour chaque document, sait faire un PDF dont la page 1 est en français et la page 2 en anglais.
  • t-lang ne se pose que sur le nœud qui porte le t-call. Sur un <div>, le rendu échoue : SyntaxError: t-lang is an alias of t-options-lang but only available on the same node of t-call. D'où le découpage en deux gabarits, le document et la boucle.

Un rapport joint à un modèle de courriel (report_template_ids) est rendu par le modèle déjà placé dans la langue du destinataire. Avec le modèle de devis et le devis S00001 d'Acme Corporation, la pièce s'appelle « Quotation - S00001.pdf » (et non « Devis - … ») et son contenu affiche « Quotation # S00001 ».

4. Dans ton code : with_context(lang=…)

Hors rapport et modèle de courriel (un texte de relance que tu composes, un nom de fichier, un message), c'est l'environnement qui décide. Change sa langue sur l'enregistrement que tu lis :

from odoo.tools import format_amount, format_date
facture = env['account.move'].browse(11)
lang = facture.partner_id.lang                   # 'en_US'
f_client = facture.with_context(lang=lang)
print(facture.env.lang, "→", f_client.env.lang)
print(facture.type_name, "/", f_client.type_name)
print(facture.invoice_line_ids.product_id.mapped('name'))
print(f_client.invoice_line_ids.product_id.mapped('name'))
print(format_amount(env, facture.amount_total, facture.currency_id, lang_code=lang),
      "/", format_amount(env, facture.amount_total, facture.currency_id))
print(format_date(env, facture.invoice_date_due, lang_code=lang),
      "/", format_date(env, facture.invoice_date_due))
fr_FR → en_US Facture / Invoice ['Bureau pour quatre personnes', 'Canapé deux places'] ['Four Person Desk', 'Two-Seat Sofa'] $ 48,012.50 / $ 48 012,50 10/05/2026 / 05/10/2026

type_name est calculé avec _('Invoice') : les chaînes traduites du code, les champs traduisibles et les libellés de sélection suivent tous env.lang. Les fonctions de format, elles, prennent la langue en paramètre lang_code. C'est exactement ce que fait l'envoi de factures d'Odoo : move.with_context(lang=mail_lang).type_name.

Les descriptions de lignes restent dans la langue d'origine

Le PDF de la facture d'Acme Corporation sort bien en anglais (« Invoice », « Due Date », « Four Person Desk »), sauf une ligne : « Canapé deux places avec structure en chêne ». C'est le champ name de la ligne, un texte stocké, rempli en français à la création de la facture, avant le changement de langue du client. Les ventes calculent cette description dans la langue du client au moment de la saisie : change donc la langue du partenaire avant de créer ses devis, ou ressaisis la ligne.

À retenir

  • La langue doit être active ; Odoo lit celle du partenaire du document, contact compris.
  • Courriel : lang du modèle, sinon la langue du partenaire principal ; compute_lang=True si tu rends un champ à la main.
  • Rapport : t-lang="o.partner_id.lang" sur le t-call du document, dans la boucle.
  • Code : with_context(lang=…) et lang_code= ; les textes déjà stockés ne se retraduisent pas.
