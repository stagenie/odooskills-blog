Importer le catalogue de la Bibliothèque en Odoo 20 : CSV, XML, load()

Des genres livrés par le module, des rayons créés une seule fois, puis cinq livres et six exemplaires importés depuis des fichiers CSV : par l'assistant d'import, par un script, par l'API. Le fil conducteur est l'identifiant externe, qui décide si une ligne crée un enregistrement ou met à jour celui qui existe déjà.

~13 minutes de lecture · niveau intermédiaire · parcours Framework & ORM

Ce que tu vas apprendre

Livrer des données

Un CSV et un XML dans le module, noupdate, et ce que fait -u des enregistrements qu'un utilisateur a modifiés ou que le fichier ne contient plus.

Importer

Des fichiers prêts pour l'assistant d'import, des relations par identifiant externe, la mise à jour par réimport, et les erreurs que l'on rencontre vraiment.

Automatiser

load() depuis odoo-bin shell et depuis l'API JSON-2, le contexte import_file, et un test Python de l'import.

Prérequis

  • Le module biblio des articles précédents, jusqu'à l'API JSON-2 de la Bibliothèque (version 20.0.1.19.0). On le fait passer en 20.0.1.20.0.
  • Les genres (Many2many, nom unique) et les rayons (hiérarchie _parent_store) sont les cibles des relations importées.
  • Un utilisateur du groupe Bibliothécaire, qui peut aussi créer des contacts : l'import crée auteurs, livres et exemplaires, et les droits ir.access s'appliquent comme pour une saisie.

Un catalogue ne se saisit pas livre par livre. Odoo offre trois chemins pour faire entrer des données en masse : les fichiers de données du module, chargés à l'installation et à chaque mise à jour ; l'assistant d'import de l'interface ; le code, depuis un shell ou l'API. Le CSV de module, l'assistant et le code finissent dans la même méthode de l'ORM, load(fields, data) ; le XML de module passe par la méthode qu'elle appelle elle-même, _load_records. Tous enregistrent leurs identifiants externes dans ir.model.data. Ce qui les distingue tient au préfixe de ces identifiants et à quelques garde-fous du contexte.

Le mécanisme n'a pas bougé depuis Odoo 19 : load(), le chargement des CSV de module et l'assistant ont le même comportement. Ce qui change autour, en Odoo 20, c'est par exemple le champ binaire de l'assistant, que le test de la section 8 rencontre.

1. Les données livrées par le module : un CSV, un XML

Deux familles de données n'ont pas leur place dans un import d'utilisateur : la liste des genres de référence, que le module veut maintenir, et les rayons de départ, que la bibliothèque va renommer à sa guise. On les livre dans data/, chacune dans le format qui lui convient. Les genres, en CSV :

id,name,color
genre_roman,Roman,1
genre_aventure,Aventure,2
genre_science_fiction,Science-fiction,4
genre_policier,Policier,9
genre_jeunesse,Jeunesse,10

Le nom du fichier, library.genre.csv, donne le modèle : Odoo prend ce qui précède le premier tiret (library.genre-reference.csv marcherait aussi). La colonne id porte l'identifiant externe, préfixé automatiquement par le nom du module : biblio.genre_roman. Les rayons, eux, passent par un fichier XML, parce qu'on veut l'attribut noupdate :

<odoo noupdate="1">

    <record id="shelf_general" model="library.shelf">
        <field name="name">Fonds général</field>
    </record>

    <record id="shelf_romans" model="library.shelf">
        <field name="name">Romans</field>
        <field name="parent_id" ref="shelf_general"/>
    </record>

    <record id="shelf_jeunesse" model="library.shelf">
        <field name="name">Jeunesse</field>
        <field name="parent_id" ref="shelf_general"/>
    </record>

    <record id="shelf_reserve" model="library.shelf">
        <field name="name">Réserve</field>
    </record>

</odoo>

Les deux fichiers s'ajoutent au manifeste, après la sécurité, et la version passe en 20.0.1.20.0 :

    'version': '20.0.1.20.0',
    ...
        'data/library_portal_data.xml',
        'data/library.genre.csv',
        'data/library_shelf_data.xml',

Un CSV de module n'a pas d'équivalent de noupdate="1" : le chargeur passe noupdate à vrai pour les fichiers de démonstration seulement. Chaque -u biblio réécrit donc les genres avec les valeurs du fichier, alors que les rayons ne sont plus touchés après leur création. Essai (fait une fois le catalogue de la section 4 importé, puis remis en état) : la couleur du genre Aventure passée de 2 à 3 et son nom changé en « Aventures », le rayon Romans renommé « Romans adultes », puis -u biblio :

avant -u : Fonds général / Romans adultes | Aventures 3
après -u : Fonds général / Romans adultes | Aventures 2

Le rayon a gardé son nom (noupdate), la couleur est revenue à 2. Le nom, lui, a l'air d'avoir résisté : c'est un champ traduisible, et le chargeur de CSV écrit sans langue, donc dans la valeur de référence en_US. La modification faite dans l'interface en français vit dans l'autre clé :

SELECT name FROM library_genre WHERE id = 8;
{"en_US": "Aventure", "fr_FR": "Aventures"}

Une ligne retirée du CSV, c'est un enregistrement supprimé

En fin de mise à jour, Odoo compare les identifiants biblio.* de la base à ceux que les fichiers viennent de charger, et supprime ceux qui manquent (sauf noupdate). Essai, catalogue importé : la ligne genre_jeunesse retirée du fichier, puis -u biblio. Le genre disparaît, et avec lui son lien vers « Le Tour du monde en quatre-vingts jours », qui ne garde que « Aventure » :

INFO ma_base odoo.addons.base.models.ir_model: Deleting 11@library.genre (biblio.genre_jeunesse)

Une valeur de référence que des livres utilisent reste donc dans le fichier : la retirer, c'est la détruire dans toutes les bases au -u suivant.

2. La mise à jour qui bute sur un genre saisi à la main

Le module a vécu avant ce fichier : une base qui a suivi la série peut déjà contenir un genre « Roman » créé dans l'interface. Sans identifiant externe, rien ne le relie à la ligne genre_roman du CSV ; Odoo tente donc de créer un second « Roman », et l'index unique sur le nom l'en empêche. La mise à jour s'arrête, la base reste en 20.0.1.19.0 :

ERROR: duplicate key value violates unique constraint "library_genre_name_uniq_index"
CRITICAL ma_base odoo.service.server: Failed to initialize database `ma_base`.
Exception: Module loading biblio failed: file biblio/data/library.genre.csv could not be processed:
Ce genre existe déjà.

Le remède consiste à donner l'identifiant externe au genre existant avant le chargement du fichier. Un script pre-migrate, placé dans migrations/20.0.1.20.0/, s'exécute justement à ce moment-là, et seulement sur une base où le module était déjà installé :

import csv

from odoo.tools.misc import file_open


def migrate(cr, version):
    with file_open('biblio/data/library.genre.csv') as f:
        rows = list(csv.DictReader(f))
    for row in rows:
        cr.execute("""
            INSERT INTO ir_model_data (module, name, model, res_id, noupdate)
            SELECT 'biblio', %(xid)s, 'library.genre', g.id, false
              FROM library_genre g
             WHERE g.name->>'en_US' = %(name)s
               AND NOT EXISTS (
                   SELECT 1 FROM ir_model_data d WHERE d.module = 'biblio' AND d.name = %(xid)s
               )
        """, {'xid': row['id'], 'name': row['name']})

On relance -u biblio : le script tourne, puis le CSV trouve biblio.genre_roman et met à jour le genre existant (sa couleur passe à 1) au lieu d'en créer un autre. Les quatre genres manquants sont créés :

INFO ma_base odoo.modules.loading: loading biblio/data/library.genre.csv
INFO ma_base odoo.modules.loading: loading biblio/data/library_shelf_data.xml

  1 | Roman            |       1 | biblio.genre_roman

C'est toute la règle de l'import en une phrase : une ligne dont l'identifiant externe existe met à jour, une ligne dont l'identifiant est inconnu crée. Le reste de l'article l'applique au catalogue.

Trois fichiers, dans l'ordre de leurs dépendances : les auteurs (des contacts), les livres, les exemplaires.

Les en-têtes sont les noms techniques des champs. Le suffixe /id dit « cette cellule est un identifiant externe » : author_id/id pour le Many2one vers l'auteur, genre_ids/id pour le Many2many, avec plusieurs identifiants séparés par des virgules (la cellule est entre guillemets). Un identifiant sans point est complété par le préfixe de l'import, __import__ : auteur_hugo désigne __import__.auteur_hugo, créé par le premier fichier. Les genres et les rayons, eux, appartiennent au module : il faut écrire leur préfixe, biblio.genre_roman. Le code d'inventaire des exemplaires n'est pas fourni : la méthode create du modèle le tire de la séquence, comme pour une saisie.

Pour que l'écran d'import propose les fichiers des livres et des exemplaires, leurs deux modèles déclarent get_import_templates (le fichier des auteurs, importé dans Contacts, n'y est pas proposé), la méthode que l'assistant appelle à son ouverture :

    @api.model
    def get_import_templates(self):
        return [{
            'label': self.env._("Modèle d'import des livres"),
            'template': '/biblio/static/import/livres.csv',
        }]

Même chose sur library.copy avec exemplaires.csv. Le lien « Modèle d'import des livres » apparaît dans l'écran d'import, puis dans le panneau Aide (figure suivante). Les trois fichiers sont enregistrés en UTF-8 avec BOM, pour une raison que la section 6 montre.

4. L'assistant d'import : tester, puis importer dans l'ordre

Dans la liste des livres, le menu ⋮ propose Importer. On charge livres.csv : Odoo lit l'en-tête et associe chaque colonne à un champ (author_id/id devient « Auteur / ID externe »). Le bouton Tester fait tout le travail de l'import, puis annule la transaction. Sur une base où les auteurs n'existent pas encore, il le dit, colonne par colonne :

L'ordre compte donc : auteurs.csv dans Contacts › Importer, puis livres.csv, puis exemplaires.csv depuis la liste des exemplaires. Chaque import se termine sur la liste des enregistrements créés :

Une option de l'assistant mérite d'être connue : quand une colonne relationnelle contient des noms et non des identifiants, et qu'elle est en erreur après « Tester », une liste d'options apparaît à côté du message, dont la création des valeurs manquantes (« Créer de nouvelles valeurs »). Côté code, c'est le contexte name_create_enabled_fields : essai, {'author_id': True} crée l'auteur « V. Hugo » au lieu d'échouer. Sans lui, un nom introuvable est une erreur (section 6).

5. Réimporter pour mettre à jour

Les identifiants donnés par le fichier sont maintenant dans ir.model.data, sous le module __import__ :

__import__.auteur_hugo        res.partner   52
__import__.livre_miserables   library.book  29
__import__.livre_germinal     library.book  32
__import__.ex_miserables_1    library.copy   8
…

Réimporter le même fichier, corrigé, ne crée donc rien : chaque ligne retrouve son livre et le met à jour. Essai par l'assistant avec livres.csv : « 5 enregistrements importés avec succès », et toujours cinq livres en base. Sans colonne id, au contraire, chaque import crée de nouveaux enregistrements ; ici, l'ISBN unique bloque le doublon, mais un modèle sans contrainte se remplirait de copies.

Pour corriger des données qui n'ont pas été importées par fichier, on part d'un export : l'option « Je veux mettre à jour des données (export compatible avec l'import) » ajoute la colonne id, et Odoo crée à la volée un identifiant __export__.… pour les enregistrements qui n'en ont pas. Depuis le code, la même lecture :

env['library.book'].search([], limit=3).export_data(['id', 'title', 'genre_ids/id'])
{'datas': [['__import__.livre_germinal', 'Germinal', 'biblio.genre_roman'],
           ['__import__.livre_monte_cristo', 'Le Comte de Monte-Cristo', 'biblio.genre_aventure,biblio.genre_roman'],
           ['__import__.livre_tour_du_monde', 'Le Tour du monde en quatre-vingts jours', 'biblio.genre_aventure,biblio.genre_jeunesse']]}

Le format exporté est exactement celui que load() relit : on modifie le fichier, on le réimporte, les livres sont mis à jour.

6. Les erreurs que l'on rencontre vraiment

load() travaille en tout ou rien : à la moindre erreur, il annule toutes les lignes du fichier et rend ids = False avec un message par ligne fautive (numéro de ligne, champ, texte). Relevés sur la base d'essai, messages de l'ORM en anglais :

CauseMessage
Livres importés avant les auteursNo matching record found for external id 'auteur_hugo' in field 'Auteur'
Auteur donné par son nom, mal orthographiéNo matching record found for name 'V. Hugo' in field 'Auteur'
Deux livres avec le même ISBNUn ISBN ne peut désigner qu'un seul livre. (le message de la contrainte du modèle, sur la ligne en double)
Date au format jour/mois/année sans réglage'15/05/2019' does not seem to be a valid date for field 'Date de parution', avec l'indication Use the format '2012-12-31'
Identifiant biblio.livre_x dans l'assistantThe record biblio.livre_x has the module prefix biblio. […] the record would be deleted when the module is upgraded.

Les noms de colonne en relation par nom (author_id, genre_ids sans /id) marchent aussi : "Roman,Aventure" pose bien les deux genres. Mais un nom cherche une correspondance exacte, et pour un homonyme le code prévoit un simple avertissement (« Found multiple matches ») avant de prendre le premier ; l'identifiant externe ne laisse pas cette marge. Autre constat, côté code : load() écrit aussi les champs déclarés readonly=True, que l'assistant, lui, ne propose pas. Une colonne name passée à load() pour les exemplaires remplace le code tiré de la séquence (essai : MON-CODE accepté).

Les accents cassés par la détection d'encodage

Sans indication, l'assistant devine l'encodage du fichier avec la bibliothèque chardet. Sur notre livres.csv enregistré en UTF-8 sans BOM, peu accentué, elle répond ISO-8859-9 (turc, confiance 0,74). La liste déroulante affiche pourtant « utf-8 » : la valeur devinée n'est pas dans sa liste, le navigateur montre la première option. L'import se déroule sans aucune erreur, et met à jour le titre :

Changer l'encodage dans la liste ne rafraîchit pas l'aperçu : cette option n'est pas de celles qui relancent l'analyse du fichier (essai : windows-1252 puis utf-8, l'aperçu garde « MisÃ©rables »). L'import, lui, utilise bien la valeur choisie : même fichier, encodage utf-8 passé explicitement à execute_import, le titre est correct. Il faut donc choisir l'encodage avant d'importer, sans compter sur l'aperçu. Le plus sûr reste le BOM : avec lui, chardet répond UTF-8-SIG à coup sûr et l'aperçu affiche « Les Misérables ». C'est pour cela que les modèles du module en portent un.

7. Importer par le code : shell, JSON-2, et le contexte import_file

Il n'existe pas de commande odoo-bin import : odoo-bin help liste db, module, i18n, shell, populate…, aucune pour importer un fichier. On écrit un petit script et on le donne à odoo-bin shell. Ici, deux livres : un nouveau, et Germinal dont on corrige le nombre de pages. Le fichier nouveautes.csv, en UTF-8 avec BOM :

id,title,author_id/id,isbn,page_count,genre_ids/id
livre_notre_dame,Notre-Dame de Paris,auteur_hugo,9780000000066,940,biblio.genre_roman
livre_germinal,Germinal,auteur_zola,9780000000042,600,biblio.genre_roman

Le script :

import csv

with open('nouveautes.csv', encoding='utf-8-sig', newline='') as f:
    rows = list(csv.reader(f))
fields, data = rows[0], rows[1:]

result = env['library.book'].load(fields, data)
for message in result['messages']:
    print(message['type'], message.get('rows'), message['message'])
if result['ids']:
    env.cr.commit()
print("livres créés ou mis à jour :", result['ids'])
odoo-bin shell -c odoo.conf -d ma_base --no-http < charger_catalogue.py
livres créés ou mis à jour : [34, 32]

Le livre 34 est Notre-Dame de Paris, créé sous __import__.livre_notre_dame ; le 32 est Germinal, mis à jour (600 pages) parce que livre_germinal existait. Le commit() est indispensable : sans lui, le shell annule tout en sortant. load() étant une méthode publique, l'API JSON-2 la sert aussi, avec la clé d'un utilisateur qui a les droits de création :

curl -s -X POST http://localhost:8069/json/2/library.book/load \
  -H "Authorization: bearer $ODOO_KEY" -H "X-Odoo-Database: ma_base" \
  -H "Content-Type: application/json" \
  -d '{"fields": ["id", "title", "author_id/id", "isbn", "genre_ids/id"],
       "data": [["livre_travailleurs_mer", "Les Travailleurs de la mer", "auteur_hugo", "9780000000073",
                 "biblio.genre_roman,biblio.genre_aventure"]]}'
{"ids": [35], "messages": [], "nextrow": 0}

Une erreur ne change pas le code HTTP : la réponse reste 200 (relevé avec curl -w), avec "ids": false et les messages. Le client doit donc lire ids, pas seulement le statut :

{"ids": false, "messages": [{"rows": {"from": 0, "to": 0}, "record": 0, "type": "error",
  "message": "Un ISBN ne peut désigner qu'un seul livre.", "field": "isbn"}], "nextrow": 0}

Ce que l'assistant ajoute à ce load() nu, c'est un contexte : import_file=True, plus les options de l'écran (name_create_enabled_fields, valeurs vides à ignorer…). Ce drapeau active le contrôle du préfixe vu plus haut, qui refuse, pour un enregistrement à créer, un identifiant préfixé par le nom d'un module connu de la base. Sans lui, rien ne l'arrête.

Un import par code sous le préfixe du module disparaît au -u suivant

Essai : load(['id', 'title', 'isbn'], [['biblio.livre_essai', "Livre d'essai", …]]) depuis le shell. Accepté, livre 38 créé. Au -u biblio suivant, Odoo cherche livre_essai dans les fichiers du module, ne le trouve pas, et le supprime :

INFO ma_base odoo.addons.base.models.ir_model: Deleting 38@library.book (biblio.livre_essai)

Pour des données d'utilisateur, utiliser un identifiant sans point (préfixe __import__) ou un préfixe à soi qui n'est pas un nom de module, ou passer import_file=True dans le contexte pour bénéficier du contrôle.

8. Tester l'import

Les modèles de fichiers font partie du module : un test les relit et vérifie qu'ils s'importent, qu'un réimport met à jour, et que les erreurs annulent tout. Extrait de tests/test_import.py (sept tests au total) :

import csv

from odoo.tests import TransactionCase
from odoo.tools import BinaryBytes, mute_logger
from odoo.tools.misc import file_open


class TestImport(TransactionCase):

    @staticmethod
    def _read(name):
        with file_open(f'biblio/static/import/{name}', 'rb') as f:
            return f.read()

    def _rows(self, name):
        rows = list(csv.reader(self._read(name).decode('utf-8-sig').splitlines()))
        return rows[0], rows[1:]

    def _load(self, model, name):
        fields, data = self._rows(name)
        result = self.env[model].load(fields, data)
        self.assertEqual(result['messages'], [])
        return self.env[model].browse(result['ids'])

    def test_update_by_external_id(self):
        self._load('res.partner', 'auteurs.csv')
        self._load('library.book', 'livres.csv')
        germinal = self.env.ref('__import__.livre_germinal')
        result = self.env['library.book'].load(['id', 'page_count'], [['livre_germinal', '600']])
        self.assertEqual(result['ids'], germinal.ids)
        self.assertEqual(germinal.page_count, 600)

    @mute_logger('odoo.sql_db')
    def test_duplicate_isbn_rolls_back_the_file(self):
        self._load('res.partner', 'auteurs.csv')
        fields, data = self._rows('livres.csv')
        data[1][fields.index('isbn')] = data[0][fields.index('isbn')]
        result = self.env['library.book'].load(fields, data)
        self.assertFalse(result['ids'])
        self.assertIn("ISBN", result['messages'][0]['message'])
        self.assertFalse(self.env.ref('__import__.livre_miserables', raise_if_not_found=False))

    def test_import_wizard(self):
        if 'base_import.import' not in self.env:
            self.skipTest("base_import non installé")
        self._load('res.partner', 'auteurs.csv')
        wizard = self.env['base_import.import'].create({
            'res_model': 'library.book',
            'file': BinaryBytes(self._read('livres.csv')),
            'file_name': 'livres.csv',
            'file_type': 'text/csv',
        })
        preview = wizard.parse_preview({'has_headers': True, 'quoting': '"', 'separator': ',', 'encoding': ''})
        self.assertEqual(preview['options']['encoding'], 'utf-8-sig')
        self.assertEqual(preview['preview'][1][0], "Les Misérables")
        fields = ['/'.join(preview['matches'][index]) for index in range(len(preview['headers']))]
        result = wizard.execute_import(fields, preview['headers'], preview['options'])
        self.assertEqual(len(result['ids']), 5)
        # … (le fichier complet vérifie aussi les correspondances et le titre importé)

Un détail propre à Odoo 20 et deux précautions. Le champ file de l'assistant est un Binary : lui passer des octets nus lève TypeError: base_import.import.file: use BinaryValue instead of bytes, d'où BinaryBytes. Le test du doublon fait volontairement échouer une requête : le journal odoo.sql_db écrirait un ERROR « bad query », que mute_logger fait taire. Enfin, les messages comparés sont soit ceux du module (en français dans le code), soit des identifiants : le test passe quelle que soit la langue de la base.

À retenir

  • CSV du module, assistant, shell ou API : tout passe par load() (le XML par _load_records), et c'est l'identifiant externe qui décide entre création et mise à jour.
  • Un CSV de module est rechargé à chaque -u et ce qui en sort est supprimé ; un XML en noupdate="1" n'est écrit qu'une fois.
  • Ajouter des données de référence à un module déjà installé, c'est d'abord rattacher l'existant (pre-migrate), sinon la mise à jour bute sur les contraintes d'unicité.
  • Les données d'utilisateur vivent sous __import__, jamais sous le préfixe d'un module.
  • Un fichier d'import en UTF-8 avec BOM évite les accents cassés en silence.
