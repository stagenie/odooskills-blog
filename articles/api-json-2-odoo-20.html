XML-RPC est déprécié : passer à l'API JSON-2 d'Odoo 20

Ton script d'intégration marche encore, mais le journal d'Odoo 20 se remplit d'un WARNING à chaque appel : /xmlrpc et /jsonrpc disparaîtront en Odoo 22. Le remplaçant existe déjà : POST /json/2/<modèle>/<méthode>, une clé API dans l'en-tête, des arguments nommés en JSON et de vrais codes HTTP en cas d'erreur.

~13 minutes de lecture · niveau intermédiaire · parcours Intégrations

Ce que tu vas apprendre

Diagnostiquer

Lire l'avertissement de dépréciation, savoir ce qui reste debout en 20 et ce qui est déjà tombé (le service db).

S'authentifier

Créer une clé API à portée rpc, choisir sa durée, et pourquoi une clé « globale » est refusée.

Appeler

/json/2 avec curl, puis un client Python sans dépendance, et les codes 401, 403, 422 qu'il faut savoir lire.

Prérequis

  • Une instance Odoo 20 Community joignable en HTTP et un utilisateur interne. Les exemples tournent sur la base de démonstration avec Ventes : contacts, articles et commandes que tu retrouves sans rien installer d'autre.
  • curl et jq pour les essais en ligne de commande, Python 3 pour le script (bibliothèque standard seulement).
  • Pour la version 19 de ce sujet (contrôleurs, routes, modes d'authentification), voir Controllers HTTP et API REST en Odoo 19.

1. Le symptôme : un WARNING à chaque appel

Voici le script XML-RPC tel qu'on en trouve dans toutes les intégrations Odoo depuis des années : authentification par identifiant et mot de passe, puis execute_kw.

import xmlrpc.client

URL = "http://localhost:8069"
DB, LOGIN, PASSWORD = "ma_base", "admin", "admin"

common = xmlrpc.client.ServerProxy(f"{URL}/xmlrpc/2/common")
uid = common.authenticate(DB, LOGIN, PASSWORD, {})
models = xmlrpc.client.ServerProxy(f"{URL}/xmlrpc/2/object")
partners = models.execute_kw(
    DB, uid, PASSWORD, "res.partner", "search_read",
    [[("is_company", "=", True)]], {"fields": ["name"], "limit": 3},
)
print(uid, partners)

Sur Odoo 20, il fonctionne toujours. Le résultat arrive, mais le serveur écrit au journal un avertissement, une fois par requête HTTP (ici deux : authenticate puis execute_kw) :

Trois informations dans ce message :

  • Ce qui est visé : /xmlrpc, /xmlrpc/2 et /jsonrpc, c'est-à-dire les deux protocoles historiques, quel que soit le langage du client. Une bibliothèque PHP ou Node qui parle JSON-RPC est concernée au même titre que xmlrpc.client.
  • L'échéance : dépréciés depuis la 19, retirés en 22. Odoo 20 est donc une version de transition : tout marche, tout prévient.
  • Le silencieux : --log-handler odoo.addons.rpc.controllers.xmlrpc:ERROR (et …jsonrpc:ERROR) fait taire l'avertissement. C'est un sursis, pas une solution : le jour de la migration en 22, le script tombera sans plus rien dire.

Le module rpc

Ces points d'entrée ne sont pas dans le cœur du serveur mais dans un petit module, rpc (« RPC endpoints »), qui ne dépend que de base et s'installe tout seul (auto_install) : il est présent sur toute base. Il porte les trois contrôleurs : xmlrpc.py, jsonrpc.py et json2.py. Désinstaller rpc pour couper l'ancien protocole couperait donc aussi le nouveau.

Venant de la 19 : le service db a disparu de /jsonrpc

L'avertissement, lui, est identique en 19 et en 20. Ce qui a changé : en 19, /jsonrpc connaissait trois services, common, object et db (lister, créer, sauvegarder des bases). En 20, il n'en reste que deux. Un appel {"service": "db", "method": "list", "args": []} répond par une erreur :

(0, 'Odoo Server Error', 'builtins.ValueError', 'Invalid service name: db')

Les scripts d'exploitation qui listaient ou sauvegardaient les bases par RPC sont à réécrire : la ligne de commande odoo-bin db ou les routes /web/database/… du gestionnaire de bases prennent le relais.

2. Une clé API à portée rpc

JSON-2 n'accepte ni identifiant ni mot de passe : chaque requête porte une clé API. Pour la créer : menu de l'utilisateur (avatar en haut à droite) › Mes préférences › onglet Sécurité › bouton Create API Key. Odoo peut redemander le mot de passe si la session n'est pas récente. L'assistant n'est pas encore traduit dans la version testée : ses libellés restent en anglais.

  • Le nom sert à reconnaître la clé dans la liste, et à la révoquer : un nom par intégration (« Synchronisation boutique », « Export comptable »), jamais un nom de personne.
  • La durée : 1 jour, 1 mois ou 1 an ; Never (sans expiration) n'est proposé qu'aux administrateurs. Pour un utilisateur ordinaire, le plafond vient du groupe technique base.group_user_regular, réglé à 90 jours : il ne voit que deux choix.
  • La portée n'apparaît pas : Odoo Community n'en connaît qu'une, rpc, et l'assistant masque le champ quand il n'y a pas le choix.

Ce que renvoie la console odoo-bin shell sur la même base, pour l'administrateur puis pour l'utilisateur de démonstration :

Desc = env['res.users.apikeys.description']
demo = env['res.users'].search([('login', '=', 'demo')])
print("admin durations", Desc._selection_duration())
print("demo durations", Desc.with_user(demo)._selection_duration())
print("scope selection", Desc._fields['scope'].selection)
admin durations [('1', '1 Day'), ('30', '1 Month'), ('365', '1 Year'), ('0', 'Never')] demo durations [('1', '1 Day'), ('30', '1 Month')] scope selection (('rpc', 'RPC'),)

Après Create Key, une seconde fenêtre affiche la clé, une seule fois : Odoo n'en garde qu'une empreinte. Elle propose aussi un bout de code Python (requests, en-tête Authorization: bearer) ; il lit la clé dans une variable d'environnement mais oublie import os, à ajouter si tu le recopies. Range la clé comme un mot de passe : dans un coffre ou une variable d'environnement, jamais dans le dépôt. Dans la suite, elle est dans $ODOO_KEY.

Venant de la 19 : portée obligatoire, durées resserrées

L'assistant de la 19 proposait sept durées (1 jour, 1 semaine, 1, 3 et 6 mois, 1 an, clé persistante pour l'administrateur) plus une date libre, et choisissait 1 jour par défaut. Il créait surtout des clés sans portée (colonne scope vide), que l'authentification acceptait partout (scope IS NULL OR scope = 'rpc'). En 20, la portée est obligatoire et la comparaison stricte (scope = 'rpc'). Une clé à portée vide, recréée pour l'essai sur une base 20, est refusée par /json/2 avec 401 Invalid apikey, et la vérification de la console renvoie None. Selon l'outil de migration, ces clés peuvent avoir été converties ou non : après une migration, appelle /json/2 avec chaque clé de tes intégrations, et recrée celles qui sont refusées.

Une clé par intégration, et la plus courte possible

La clé donne les droits complets de son utilisateur, pas davantage, pas moins. Pour une intégration, crée un utilisateur interne dédié avec les seuls rôles nécessaires, et sa clé à lui. Une clé expirée est refusée en 401 comme une clé fausse : note sa date d'expiration là où l'équipe la verra.

3. Premier appel : POST /json/2/<modèle>/<méthode>

Trois variables d'environnement suffisent : l'adresse du serveur, le nom de la base, la clé.

export ODOO_URL=http://localhost:8069
export ODOO_DB=ma_base
read -rs ODOO_KEY && export ODOO_KEY     # colle la clé : elle ne s'affiche pas et ne va pas dans l'historique

Puis les trois premières requêtes : les sociétés de la démo, et deux articles lus avec et sans langue.

ÉlémentRôle
POST /json/2/res.partner/search_readLe modèle et la méthode sont dans l'URL. Seul POST est accepté : un GET répond 404 avec "Did you mean POST /json/2/<model>/<method>?".
Authorization: bearer $ODOO_KEYLa clé API. Pas d'étape authenticate, pas d'uid à transporter : la clé désigne l'utilisateur.
X-Odoo-DatabaseLa base visée. Indispensable dès que le serveur en sert plusieurs ; avec une seule base visible, Odoo la prend d'office (les autres appels de l'image s'en passent).
Content-Type: application/jsonLe corps est un objet JSON.
le corpsLes arguments de la méthode, par leur nom : domain, fields, limit… plus deux clés réservées, ids (les enregistrements sur lesquels appeler la méthode) et context.

Les many2one reviennent en paire [id, nom], comme en XML-RPC. Une méthode qui renvoie des enregistrements renvoie leurs ids : create répond [47], une liste, puisqu'il reçoit une liste de valeurs.

La langue n'est pas celle de l'utilisateur

L'utilisateur de la clé est en français, et pourtant le deuxième appel répond « Drawer Black ». La requête JSON-2 n'emporte pas les préférences de l'utilisateur : sans context, elle tourne en anglais. Sur la même clé :

curl -s "$ODOO_URL/json/2/res.users/context_get" -H "Authorization: bearer $ODOO_KEY" -H "Content-Type: application/json" -d "{}"
{"lang": "fr_FR", "tz": "Europe/Brussels", "uid": 2}

Le contexte de l'utilisateur existe bien, mais c'est au client de le passer. Prends l'habitude de mettre dans context tout ce dont la méthode a besoin : la langue d'abord, le fuseau horaire (tz) quand des dates sont en jeu.

4. Traduire un appel XML-RPC en JSON-2

execute_kw mélangeait arguments positionnels et nommés. JSON-2 ne connaît que les noms : il faut donc connaître celui de chaque paramètre dans la signature Python de la méthode. Pour les méthodes de l'ORM les plus courantes :

XML-RPC (execute_kw)Corps JSON-2
'search_read', [[domaine]], {'fields': […], 'limit': 3}{"domain": […], "fields": […], "limit": 3}
'search_count', [[domaine]]{"domain": […]} → 19
'read', [[10]], {'fields': […]}{"ids": [10], "fields": […]}
'create', [{valeurs}]{"vals_list": [{valeurs}]} → [47]
'write', [[48], {valeurs}]{"ids": [48], "vals": {valeurs}} → true
'unlink', [[48]]{"ids": [48]} → true
'name_search', ['acme'], {'limit': 2}{"name": "acme", "limit": 2} → [[10, "Acme Corporation"], [37, "Acme Corporation, Addison Olson"]]
{'context': {'lang': 'fr_FR'}}"context": {"lang": "fr_FR"}

Deux règles qu'Odoo vérifie avant d'exécuter quoi que ce soit (addons/rpc/controllers/json2.py) :

  • Une méthode @api.model (search, search_count, create, name_search…) ne s'appelle pas avec ids : 422, "cannot call res.partner.search with ids".
  • Les arguments doivent coller à la signature : un argument obligatoire manquant ou un nom inconnu donne 422, par exemple "missing a required argument: 'domain'".

Les méthodes privées (nom commençant par _) restent fermées, comme en XML-RPC : /json/2/res.partner/_read_group répond 403, "Private methods (such as 'res.partner._read_group') cannot be called remotely."

5. Un client Python complet, sans dépendance

Le remplaçant du script de la partie 1, avec urllib de la bibliothèque standard : une fonction call() qui envoie la requête et transforme toute réponse en erreur exploitable. Rien à installer sur la machine qui le lance.

import json
import os
import urllib.error
import urllib.request

ODOO_URL = os.environ["ODOO_URL"]          # ex. https://erp.example.com
ODOO_DB = os.environ["ODOO_DB"]            # utile si le serveur sert plusieurs bases
ODOO_KEY = os.environ["ODOO_KEY"]          # la clé API, jamais dans le code


class OdooError(Exception):
    def __init__(self, status, body):
        super().__init__(f"{status} {body['name']}: {body['message']}")
        self.status, self.body = status, body


def call(model, method, **params):
    request = urllib.request.Request(
        f"{ODOO_URL}/json/2/{model}/{method}",
        data=json.dumps(params).encode(),
        headers={
            "Authorization": f"bearer {ODOO_KEY}",
            "X-Odoo-Database": ODOO_DB,
            "Content-Type": "application/json",
        },
        method="POST",
    )
    try:
        with urllib.request.urlopen(request, timeout=30) as response:
            return json.load(response)
    except urllib.error.HTTPError as exc:
        raise OdooError(exc.code, json.load(exc)) from None


fr = {"lang": "fr_FR"}
print(call("sale.order", "search_count", domain=[("state", "=", "sale")]))
for order in call(
    "sale.order", "search_read",
    domain=[("state", "=", "sale")],
    fields=["name", "partner_id", "amount_total"],
    order="amount_total desc", limit=3, context=fr,
):
    print(order["name"], order["partner_id"][1], order["amount_total"])

[partner_id] = call("res.partner", "create",
                    vals_list=[{"name": "Client importé", "city": "Lyon"}])
call("res.partner", "write", ids=[partner_id], vals={"phone": "+33 4 00 00 00 00"})
print(call("res.partner", "read", ids=[partner_id], fields=["name", "city", "phone"]))

try:
    call("sale.order", "unlink", ids=[4], context=fr)
except OdooError as exc:
    print(exc.status, exc.body["name"])
    print(exc.body["message"])
19 S00023 Gemini Furniture 4350.0 S00020 Joel Willis 3389.63 S00004 Gemini Furniture 2240.0 [{'id': 48, 'name': 'Client importé', 'city': 'Lyon', 'phone': '+33 4 00 00 00 00'}] 422 odoo.exceptions.UserError Vous ne pouvez pas supprimer un devis envoyé ou une commande client confirmée. Vous devez l'annuler au préalable.
  • Les arguments Python nommés deviennent tels quels les clés du corps JSON : la fonction call() n'a rien à connaître des méthodes appelées.
  • Les tuples du domaine (("state", "=", "sale")) partent en listes JSON ; Odoo les accepte.
  • Le message de l'erreur métier arrive en français parce que l'appel passe context=fr ; sans lui, il serait en anglais.
  • Chaque requête est une transaction : une erreur annule tout ce que cette requête avait fait, mais pas les requêtes précédentes. Le partenaire créé plus haut reste créé.

6. Lire les erreurs : 401, 403, 422 et le champ debug

En XML-RPC, toute erreur arrivait en réponse 200 avec un fault à décoder ; en JSON-RPC, en 200 avec une clé error. JSON-2 répond avec un vrai code HTTP et un corps JSON toujours de la même forme : name, message, arguments, timestamp, context, debug. Quatre cas réels :

CodeCause (constatée)Que faire
400Corps qui n'est pas du JSON valide : "could not parse the body as json: Expecting value…"Vérifier la sérialisation côté client.
401Pas d'en-tête Authorization ; clé fausse, expirée, révoquée ou sans portée rpc : "Invalid apikey"Recréer ou renouveler la clé. Ne pas réessayer en boucle.
403AccessError : l'utilisateur de la clé n'a pas le droit (ici l'utilisateur de démo sur les paramètres système) ; méthode privéeDonner le rôle manquant à l'utilisateur de l'intégration, ou appeler une méthode publique.
404Modèle inconnu ("the model 'res.partenaire' does not exist"), méthode inexistante ("The method 'res.partner.n_existe_pas' does not exist"), verbe autre que POSTCorriger l'URL ; vérifier que le module du modèle est installé.
422UserError (règle métier) ; arguments qui ne collent pas à la signature ; ids sur une méthode @api.modelLire message : c'est le texte qu'un utilisateur verrait à l'écran.
500Toute autre exception Python. Exemple constaté : search_read avec un argument inconnu (filters) passe le contrôle de signature, puisque la méthode accepte des arguments libres, et échoue plus loin en TypeErrorLire debug, puis corriger l'appel.

Le champ debug contient la trace du serveur

Toutes les réponses d'erreur, 401 compris, portent dans debug la trace Python complète, avec les chemins des fichiers sur le serveur. Précieux pour dépanner ; à ne pas afficher tel quel à un utilisateur final ni à verser dans un journal public. Dans un client, journalise name et message, et garde debug pour le diagnostic.

7. Migrer une intégration existante, dans l'ordre

  1. Repérer les clients : chaque ligne WARNING … odoo.addons.rpc.controllers.xmlrpc ou …jsonrpc est suivie, dans le journal, de la ligne d'accès HTTP avec l'adresse IP de l'appelant et, pour XML-RPC, le modèle et la méthode (POST /xmlrpc/2/object#res.partner.search_read).
  2. Créer un utilisateur interne par intégration, avec ses seuls rôles, et une clé API pour lui.
  3. Remplacer authenticate + execute_kw par call() en nommant les arguments (table de la partie 4), et passer context partout où la langue ou le fuseau comptent.
  4. Traiter les erreurs par code HTTP plutôt qu'en analysant un texte de fault.
  5. Quand le journal ne montre plus aucun WARNING de ce type, l'intégration est prête pour Odoo 22.

Mémo

BesoinOdoo 20
Point d'entréePOST /json/2/<modèle>/<méthode> (module rpc, installé d'office)
AuthentificationAuthorization: bearer <clé API>, clé à portée rpc (Mes préférences › Sécurité)
Choisir la baseX-Odoo-Database: <base>
Argumentspar nom dans le corps JSON ; ids pour les enregistrements, context pour la langue et le fuseau
Durée d'une clé1 jour, 1 mois, 1 an ; sans expiration pour un administrateur ; 90 jours au plus pour un utilisateur ordinaire
Erreurs401 clé, 403 droits, 404 URL, 422 règle métier ou arguments, 500 le reste ; message pour l'humain, debug pour le développeur
/xmlrpc, /jsonrpcfonctionnent, WARNING à chaque appel, suppression prévue en Odoo 22 ; service db retiré

Récapitulatif

  • Le WARNING de dépréciation n'est pas une panne : il annonce la suppression de /xmlrpc et /jsonrpc en Odoo 22.
  • JSON-2 remplace l'identifiant et le mot de passe par une clé API à portée rpc, de durée limitée.
  • Une requête = POST /json/2/<modèle>/<méthode>, les arguments par leur nom, ids et context à part.
  • La langue de l'utilisateur n'est pas appliquée d'office : passer "context": {"lang": "fr_FR"}.
  • Les erreurs ont un vrai code HTTP et un corps JSON stable ; un client de quarante lignes en urllib suffit.
