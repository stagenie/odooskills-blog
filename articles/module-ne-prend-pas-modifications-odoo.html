Mettre à jour un module Odoo 20 qui ne prend pas tes modifications

Tu modifies ton module, tu recharges la page, rien ne change. Odoo 20 relit le Python au démarrage, le XML à la mise à jour (-u), les données noupdate presque jamais, le CSS et le JavaScript quand le cache des assets est vidé. Chaque cas a été rejoué sur un petit module.

~6 minutes de lecture · niveau débutant · série Astuces dev Odoo 20

Édition : Community. Vérifié sur Odoo 20.0 Community, octobre 2026, base de démonstration et module d'exemple.

1. Python, XML, CSS : trois horloges différentes

Le module d'exemple ajoute à la fiche contact un champ calculé (calcul v1), affiché par une vue héritée (Info (vue v1)) sur un fond coloré par une feuille CSS de web.assets_backend. Les trois fichiers ont été modifiés serveur en marche, puis la fiche d'Acme Corporation rouverte à chaque étape dans un navigateur neuf, sans cache :

Le Python est chargé en mémoire au démarrage : un redémarrage suffit, sans -u, pour une méthode modifiée. Les vues vivent en base : -u recopie le XML dans ir.ui.view. Dernière ligne, le piège : un -u lancé à côté met la base à jour et le serveur recharge son registre (Reloading the model registry after database signaling.), mais il garde l'ancien code Python. Relance donc le serveur lui-même :

./odoo-bin -c odoo.conf -d ma_base -u mon_module

2. Un champ ajouté sans -u : erreur 500

Ajoute un champ stocké, maj_note = fields.Char(string="Note module"), et redémarre sans -u. Le Python connaît le champ, la table res_partner n'a pas la colonne : la première requête qui lit un contact échoue. Ici, c'est la page de connexion elle-même :

C'est -u qui crée les colonnes (le journal l'annonce par module mon_module: creating or updating database tables). Après -u mon_module, la colonne existe et la connexion répond de nouveau.

3. noupdate="1" : la donnée qui ne bouge plus

Les données placées dans <data noupdate="1"> sont créées à l'installation, puis laissées à l'utilisateur : -u ne les réécrit pas. C'est le premier soupçon quand « le XML est bon mais la base ne suit pas ». Le module d'exemple crée une étiquette de contact :

<data noupdate="1">
    <record id="categ_client_fidele" model="res.partner.category">
        <field name="name">Client premium</field>
    </record>
</data>

Le nom vient d'être changé dans le fichier (il valait Client fidèle). Ce script, passé à odoo-bin shell, lit la base :

# lire_categ.py
tag = env.ref('mon_module.categ_client_fidele')
imd = env['ir.model.data'].search([('module', '=', 'mon_module'), ('name', '=', 'categ_client_fidele')])
print(tag.name, '| noupdate =', imd.noupdate)

--reinit mon_module recharge les données comme à l'installation, drapeau conservé. Commode en développement, mais il repasse toutes les données noupdate du module et des modules qui en dépendent : les retouches faites dans l'interface partent avec.

En production, la voie propre est un script de migration, joué une fois quand la version du manifeste augmente. Passe-la de 20.0.1.0.0 à 20.0.1.0.1 et crée migrations/20.0.1.0.1/post-migrate.py :

from odoo import api, SUPERUSER_ID


def migrate(cr, version):
    env = api.Environment(cr, SUPERUSER_ID, {})
    tag = env.ref('mon_module.categ_client_fidele', raise_if_not_found=False)
    if tag:
        tag.name = "Client premium"

Au -u suivant, le journal montre le passage, puis lire_categ.py confirme la valeur ; les -u d'après ne rejouent plus le script :

2026-10-21 11:21:26,015 69690 INFO ma_base odoo.modules.migration: module mon_module: Running upgrade [20.0.1.0.1>] post-migrate 2026-10-21 11:21:26,017 69690 INFO ma_base odoo.modules.migration.mon_module.post: mon_module.post from 20.0.1.0.0 to 20.0.1.0.1 in 0.002 seconds
Client premium | noupdate = True

Décocher noupdate dans ir.model.data ne suffit pas

Passer noupdate à False sur l'identifiant externe puis lancer -u ne change rien tant que le fichier garde <data noupdate="1"> : en mise à jour, Odoo saute ce nœud dès que l'enregistrement existe. Passe par le script de migration.

4. CSS et JavaScript : le cache des assets

Au point 1, la page rechargée gardait l'ancienne couleur, et l'adresse du bundle n'avait pas changé : Odoo 20 assemble les fichiers en bundles minifiés et les garde en cache jusqu'au redémarrage. Trois façons de voir ton CSS ou ton JavaScript à jour :

  1. Redémarrer le serveur : le bundle est recalculé sous une nouvelle adresse, que le navigateur recharge. Pas de -u pour un fichier déjà déclaré.
  2. Régénérer les actifs, sans redémarrer : en mode développeur, icône bogue, section Outils. Les bundles stockés sont supprimés et la page se recharge.
  3. ?debug=assets dans l'adresse : fichiers non minifiés, relus à chaque chargement. Idéal pendant que tu écris ton CSS ou ton composant.

5. --dev=reload,xml : le mode qui t'épargne la moitié du travail

Sur ta machine de développement, lance le serveur avec --dev=reload,xml (ou dev_mode = reload,xml dans odoo.conf) :

  • reload surveille les fichiers .py et redémarre le serveur dès qu'un fichier change. Le journal l'annonce :
    2026-10-21 11:24:24,785 75367 INFO ? odoo.service.server: autoreload: python code updated, autoreload activated
    Il faut le paquet Python inotify (ou watchdog) ; sinon un WARNING au démarrage signale le rechargement désactivé.
  • xml lit l'architecture des vues directement dans tes fichiers, et recalcule les assets à chaque chargement. Vue et CSS modifiés ont été visibles au simple rechargement de la page, sans redémarrage ni -u.

Ses limites : xml ne vaut que pour les vues déjà installées et non retouchées dans l'interface ; nouvelle vue, menu, action ou donnée demandent toujours -u. Et reload redémarre sans -u (Odoo retire l'option de la commande relancée) : un champ stocké ajouté sous ce mode a redonné l'erreur 500 du point 2, jusqu'à un redémarrage avec -u mon_module. Réservé au poste du développeur, jamais à la production.

À retenir

  • Python : redémarrer le serveur ; un -u lancé à côté met à jour la base, pas le code en mémoire.
  • Vues, menus, champs nouveaux : -u mon_module ; un champ stocké sans -u donne column … does not exist.
  • noupdate="1" : -u n'y touche pas ; script de migration en production, --reinit seulement en développement.
  • CSS et JS : redémarrage, « Régénérer les actifs » ou ?debug=assets ; --dev=reload,xml automatise une partie, pas le -u.
