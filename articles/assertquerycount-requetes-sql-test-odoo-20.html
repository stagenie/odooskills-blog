assertQueryCount en Odoo 20 : compter les requêtes SQL d'un test

Un champ calculé qui lance une requête par enregistrement passe tous les tests fonctionnels, puis ralentit chaque liste en production. assertQueryCount fige le nombre de requêtes SQL d'un bout de code dans un test : la régression devient un échec, avec le nombre réel et la ligne. Voici comment l'écrire, le stabiliser avec @warmup et @users, lire les requêtes en cause, et ce que le compteur laisse passer.

~11 minutes de lecture · niveau intermédiaire · parcours Qualité & tests

Ce que tu vas apprendre

Mesurer

Lire le nombre réel de requêtes d'un bloc de code, et repérer une requête par enregistrement avant la production.

Stabiliser

Obtenir un nombre qui ne bouge plus d'un lancement à l'autre : @warmup, @users et le flush des écritures.

Expliquer

Afficher les requêtes elles-mêmes avec assertQueries, et connaître les cas où le compteur ne dit rien.

Prérequis

  • Savoir écrire et lancer un test TransactionCase : voir Tests automatisés en Odoo 20 : TransactionCase.
  • Une instance Odoo 20 Community, base ma_base avec les Ventes et les données de démonstration (le test utilise un article de démo). Les nombres de requêtes ci-dessous viennent d'une base où sont aussi installés la Comptabilité et l'Inventaire : sur une autre base, certains changent.
  • Les tests se lancent en ligne de commande, serveur arrêté, avec --test-tags et --stop-after-init.

Ce que compte assertQueryCount

assertQueryCount est un gestionnaire de contexte des classes de test d'Odoo (odoo/tests/common.py). Avant le bloc, il envoie les écritures en attente et exécute les traitements de pré-validation (flush), puis relève le compteur de requêtes du curseur ; après le bloc, il fait un nouveau flush et compare l'écart au nombre attendu. Le nombre attendu se donne en premier argument, ou par login : assertQueryCount(admin=1, demo=1).

Le compteur ne mesure pas un temps : il mesure un nombre de requêtes, qui ne dépend ni de la machine ni de la charge. C'est ce qui en fait un bon garde-fou dans une suite de tests ou une intégration continue.

1. Le module d'essai : un compteur de commandes

Le module oski_requetes_comptees (dépendance : sale) ajoute aux contacts un champ calculé non stocké, le nombre de commandes confirmées. Première version, la plus naturelle à écrire :

from odoo import fields, models


class ResPartner(models.Model):
    _inherit = 'res.partner'

    oski_nb_commandes = fields.Integer('Commandes confirmées', compute='_compute_oski_nb_commandes')

    def _compute_oski_nb_commandes(self):
        # version naïve : une requête COUNT par contact
        for partner in self:
            partner.oski_nb_commandes = self.env['sale.order'].search_count(
                [('partner_id', '=', partner.id), ('state', '=', 'sale')])

Le module n'ajoute pas de modèle : il n'a donc pas besoin de fichier de droits. Les tests partagent une classe de base qui crée dix clients et deux commandes confirmées pour chacun :

from odoo.tests import TransactionCase, users, warmup


class RequetesCommon(TransactionCase):

    @classmethod
    def setUpClass(cls):
        super().setUpClass()
        produit = cls.env.ref('product.product_product_4')
        cls.clients = cls.env['res.partner'].create([{'name': f'Client {i}'} for i in range(10)])
        commandes = cls.env['sale.order'].create([
            {'partner_id': client.id, 'order_line': [(0, 0, {'product_id': produit.id})]}
            for client in cls.clients for _ in range(2)
        ])
        commandes.action_confirm()

2. Premier test : laisser Odoo donner le nombre

On ne devine pas un nombre de requêtes. On écrit 0, on lance le test, et le message d'échec donne le nombre réel. Deux mesures : un client, puis dix.

class TestRequetes(RequetesCommon):

    def test_un_client(self):
        client = self.env['res.partner'].browse(self.clients[0].id)
        with self.assertQueryCount(0):
            self.assertEqual(client.oski_nb_commandes, 2)

    def test_dix_clients(self):
        clients = self.env['res.partner'].browse(self.clients.ids)
        with self.assertQueryCount(0):
            self.assertEqual(clients.mapped('oski_nb_commandes'), [2] * 10)
./odoo-bin -c odoo.conf -d ma_base -u oski_requetes_comptees \
    --test-tags /oski_requetes_comptees --stop-after-init --no-http

Le message dit tout : le nombre réel (10 > 0), le test, le fichier et la ligne du bloc. Dix requêtes pour dix contacts, c'est le schéma « une requête par enregistrement » (souvent appelé N+1) : sur une liste de 80 contacts, ce serait 80 requêtes.

Le login affiché est __system__ : sans décorateur @users, un TransactionCase tourne en superutilisateur. C'est sous ce login que le nombre attendu est cherché ; le premier argument (assertQueryCount(1)) sert de valeur par défaut pour tous les logins.

Mesurer un seul enregistrement peut tromper, dans les deux sens

Avec un seul client, la version naïve fait une requête, exactement comme une version correcte : un test sur un enregistrement ne voit pas le N+1. Mesurez toujours sur plusieurs enregistrements. À l'inverse, self.clients[:1] garde le lot de préchargement des dix clients créés ensemble : après un invalidate_recordset(), lire le champ sur ce « seul » client le calcule pour les dix et le test annonce 10 > 0 in test_un_client. Un browse() neuf mesure vraiment un enregistrement.

3. Corriger, puis figer le nombre

La correction regroupe le comptage en une requête pour tout le lot, avec _read_group (voir read_group en Odoo 20) :

    def _compute_oski_nb_commandes(self):
        # une seule requête GROUP BY pour tous les contacts du lot
        groupes = self.env['sale.order']._read_group(
            [('partner_id', 'in', self.ids), ('state', '=', 'sale')],
            groupby=['partner_id'], aggregates=['__count'])
        nb = {partner.id: count for partner, count in groupes}
        for partner in self:
            partner.oski_nb_commandes = nb.get(partner.id, 0)

Relancé avec assertQueryCount(0), le test annonce maintenant 1 > 0 pour un client et pour dix. On remplace donc les 0 par 1 : le test est vert, et il le restera tant que le calcul ne fait qu'une requête, quel que soit le nombre de contacts.

C'est tout l'intérêt : quelqu'un qui, plus tard, réécrit le calcul en boucle verra le test échouer avec 10 > 1, sans que la valeur calculée ait changé. Le code de sortie 1 suffit à bloquer une intégration continue.

4. Compter pour un vrai utilisateur : @users et @warmup

Le superutilisateur n'est pas soumis aux droits d'accès. Un utilisateur réel, si : ses requêtes ne sont pas les mêmes. Le décorateur @users rejoue la méthode pour chaque login, et le nombre attendu se donne par login. Premier essai, sans autre précaution :

class TestRequetesUtilisateurs(RequetesCommon):

    @users('admin', 'demo')
    def test_froid(self):
        clients = self.env['res.partner'].browse(self.clients.ids)
        with self.assertQueryCount(admin=0, demo=0):
            clients.mapped('oski_nb_commandes')

    @users('admin', 'demo')
    @warmup
    def test_chaud(self):
        clients = self.env['res.partner'].browse(self.clients.ids)
        with self.assertQueryCount(admin=0, demo=0):
            clients.mapped('oski_nb_commandes')

Le même code fait 7 requêtes pour le premier login, 4 pour le second, et 1 avec @warmup. La différence ne vient pas du calcul : ce sont des caches, dont une partie est déjà remplie quand le second login passe. Les requêtes du test à froid se listent en remplaçant assertQueryCount par assertQueries([]) (section suivante). Le détail montré ici est celui d'admin : sept requêtes, sur ces tables :

#Table luePourquoi
1properties_base_definitiondéfinitions de propriétés
2res_usersla fiche de l'utilisateur courant
3res_groups_users_relses groupes
4ir_accessles droits d'accès (modèle unique en Odoo 20)
5ir_modelles modèles visés par ces droits
6res_companyses sociétés autorisées
7sale_orderle GROUP BY du calcul, la seule requête « utile »

Les six premières alimentent des caches (cache des enregistrements et caches ORM des droits) : elles disparaissent dès que ces caches sont remplis. C'est le rôle de @warmup : il exécute la méthode une première fois, sans vérifier les nombres, annule ses données par un point de sauvegarde mais garde les caches ORM, vide le cache des enregistrements, puis exécute la méthode pour de bon. Il reste la requête du calcul. Le test retenu dans le module :

    @users('admin', 'demo')
    @warmup
    def test_dix_clients(self):
        clients = self.env['res.partner'].browse(self.clients.ids)
        with self.assertQueryCount(admin=1, demo=1):
            clients.mapped('oski_nb_commandes')

L'ordre est celui des tests d'Odoo : @users à l'extérieur, @warmup juste au-dessus de la méthode ; la chauffe a ainsi lieu pour chaque login. Les droits de chaque utilisateur se retrouvent dans le SQL : le GROUP BY chaud porte un filtre "sale_order"."company_id" IN %s, issu de la ligne d'accès multi-société de sale.order (voir Les droits d'accès en Odoo 20 : ir.access).

5. Voir les requêtes : assertQueries

Quand un nombre augmente, il faut savoir quelle requête est en trop. assertQueries compare la liste des requêtes du bloc à une liste attendue. Avec une liste vide, il échoue en affichant toutes les requêtes réelles, préfixées par +++ : c'est le moyen le plus court de les lire sans changer le niveau du journal (pour une session entière, voir --log-sql dans Journaux Odoo 20).

        with self.assertQueries([]):
            clients.mapped('oski_nb_commandes')

On peut aussi en faire un test à part entière. Les espaces et la casse sont ignorés, et en Odoo 20 la chaîne ... remplace n'importe quel morceau de la requête : on fige la forme (un GROUP BY sur sale_order) sans recopier le détail du WHERE.

class TestRequetesSql(RequetesCommon):

    @users('admin')
    @warmup
    def test_requete_group_by(self):
        clients = self.env['res.partner'].browse(self.clients.ids)
        with self.assertQueries(['''
            SELECT "sale_order"."partner_id", COUNT(*)
            FROM "sale_order"
            WHERE ...
            GROUP BY "sale_order"."partner_id"
            ORDER BY "sale_order"."partner_id" ASC
        ''']):
            clients.mapped('oski_nb_commandes')

Avec la version naïve, ce test échoue en montrant la requête attendue (---) et les dix requêtes réelles (+++) :

AssertionError: Not the expected queries :
---
            SELECT "sale_order"."partner_id", COUNT(*)
            FROM "sale_order"
            WHERE ...
            GROUP BY "sale_order"."partner_id"
            ORDER BY "sale_order"."partner_id" ASC

+++ SELECT COUNT(*) FROM "sale_order" WHERE ("sale_order"."partner_id" IN %s AND "sale_order"."state" IN %s) AND "sale_order"."company_id" IN %s
+++ SELECT COUNT(*) FROM "sale_order" WHERE ("sale_order"."partner_id" IN %s AND "sale_order"."state" IN %s) AND "sale_order"."company_id" IN %s
… (dix lignes identiques au total)

Les paramètres restent des %s : la comparaison porte sur le texte de la requête, pas sur ses valeurs. Comme pour les nombres, la comparaison n'a lieu qu'au passage réel, pas pendant la chauffe de @warmup.

6. Les écritures et le flush

Une affectation record.champ = valeur ne part pas tout de suite en base : l'ORM la garde jusqu'au prochain flush (voir Cache et SQL en Odoo 20 : flush, invalidate). Par défaut, assertQueryCount fait un flush avant et après le bloc : les écritures en attente avant le bloc ne sont pas comptées, celles du bloc le sont.

class TestRequetesEcriture(RequetesCommon):

    @users('admin')
    @warmup
    def test_ecriture(self):
        client = self.env['res.partner'].browse(self.clients[0].id)
        with self.assertQueryCount(admin=4):
            client.comment = 'Client fidèle'
        with self.assertQueryCount(admin=0, flush=False):
            client.comment = 'Client très fidèle'

Ce test est vert. La première écriture coûte 4 requêtes, relevées avec assertQueries([]) : trois lectures (la société, les utilisateurs liés au contact, ses contacts enfants) et l'UPDATE envoyé par le flush de fin de bloc. La seconde, avec flush=False, en coûte 0 : l'UPDATE partira plus tard, hors du bloc. flush=False sert à mesurer une lecture sans payer les écritures du code autour ; pour mesurer une écriture, gardez le flush par défaut.

flush=False rend une écriture invisible

Avec flush=False, un bloc qui écrit peut afficher 0 requête : le coût réel est reporté hors du bloc, et aucun test ne le mesure plus. Réservez cette option aux blocs qui ne font que lire.

7. Ce que le compteur laisse passer

Trois comportements à connaître, rejoués chacun dans un test d'essai :

  • Moins que prévu = test vert. Un bloc qui fait 1 requête quand on en attend 3 ne fait pas échouer le test : une simple ligne INFO dans le journal. 
    INFO ma_base odoo.addons.oski_requetes_comptees.tests.test_requetes: Query count less than expected for user admin: 1 < 3 in test_moins_que_prevu at …/oski_requetes_comptees/tests/test_requetes.py:69
  • Attendu supérieur à 0, aucune requête = échec. Relire un champ déjà en cache dans le bloc ne fait aucune requête ; si le test en attend une, Odoo 20 échoue : 
    AssertionError: Query count did not detect any queries admin: expected 1 in test_aucune_requete at …/oski_requetes_comptees/tests/test_requetes.py:77
    Ce message signale le plus souvent un bloc qui ne mesure plus ce qu'il croit mesurer : valeur déjà en cache, appel déplacé hors du bloc.
  • Un échec n'arrête pas le test. Chaque dépassement est enregistré comme sous-test et la méthode continue : un test d'essai à deux blocs faux et une assertion fausse a donné 3 failed, 0 error(s) of 1 tests. Le nombre d'échecs du résumé peut donc dépasser le nombre de tests.

Un nombre trop haut ne fait pas échouer : baissez-le

Après une optimisation, le test reste vert avec l'ancien nombre, plus haut. Il ne protège alors plus rien : une régression jusqu'à ce plafond passerait sans bruit. Cherchez Query count less than expected dans le journal des tests et remettez le nombre exact.

8. Ne lancer que les tests de requêtes

Quand l'étiquette is_query_count figure dans --test-tags, Odoo l'ajoute à toute méthode de test dont le source contient self.assertQueryCount. On peut ainsi relancer seulement ces tests, ici limités au module :

./odoo-bin -c odoo.conf -d ma_base -u oski_requetes_comptees \
    --test-tags 'is_query_count/oski_requetes_comptees' --stop-after-init --no-http
INFO ma_base odoo.addons.oski_requetes_comptees.tests.test_requetes: Starting TestRequetes.test_dix_clients ...
INFO ma_base odoo.addons.oski_requetes_comptees.tests.test_requetes: Starting TestRequetes.test_un_client ...
INFO ma_base odoo.addons.oski_requetes_comptees.tests.test_requetes: Starting TestRequetesUtilisateurs.test_dix_clients ...
INFO ma_base odoo.addons.oski_requetes_comptees.tests.test_requetes: Starting TestRequetesEcriture.test_ecriture ...
INFO ma_base odoo.tests.result: 0 failed, 0 error(s) of 4 tests when loading database 'ma_base'

Quatre tests sur cinq : test_requete_group_by, qui n'utilise que assertQueries, est écarté. La détection lit le texte de la méthode : un appel fait depuis une fonction utilitaire n'est pas repéré.

9. Ce qui a changé depuis la 19

Le même module, passé en version 19.0.1.0.0, a été lancé sur une base Odoo 19 neuve (Ventes et démonstration). Les nombres du module sont identiques (1, 1, 1 et 4) ; les différences tiennent aux outils de test :

Les deux bases n'ont pas les mêmes modules installés : les nombres à froid ne se comparent pas un pour un. Ils montrent seulement que les tables de droits interrogées ne sont plus les mêmes.

Venant de la 19

Les tests de nombre de requêtes d'un module 19 se portent presque tels quels : remplacer assertQueriesContain (par assertQueries avec ...), corriger les blocs qui attendaient des requêtes et n'en font plus, et relire les nombres « à froid » (sans @warmup), qui dépendent des tables de droits. Vérifiez aussi la phase des classes sans @tagged : post_install en 20.

À retenir

  • Écrivez assertQueryCount(0), lancez le test et recopiez le nombre réel du message d'échec.
  • Mesurez sur plusieurs enregistrements, chargés par un browse() neuf : c'est là qu'une requête par enregistrement se voit.
  • @users('admin', 'demo') + @warmup donnent un nombre stable, par login ; sans @users, le login est __system__.
  • assertQueries([]) affiche les requêtes réelles ; en Odoo 20, ... sert de joker.
  • Moins que prévu ne fait pas échouer : baissez le nombre après chaque optimisation. Gardez le flush par défaut pour mesurer une écriture.
