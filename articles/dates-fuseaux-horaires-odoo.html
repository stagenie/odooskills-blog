Dates et fuseaux horaires en Odoo 20 : context_today et zoneinfo

Une heure décalée de deux heures, une date qui vaut hier après 22 h, un .localize() qui plante depuis la migration : en Odoo 20, tout passe par context_today, context_timestamp et un fuseau zoneinfo. Pytz est sorti du cœur.

1. Pourquoi l'heure est « décalée »

Un champ Datetime est stocké en UTC, sans fuseau (un datetime « naïf »). Le devis S00002 de la démo, lu dans le shell :

# heure_base.py
from odoo import fields

order = env['sale.order'].browse(2)
print("en base     :", order.date_order)
print("utilisateur :", fields.Datetime.context_timestamp(order, order.date_order))
print("fuseau      :", order.env.tz)
en base : 2026-09-07 06:16:00 utilisateur : 2026-09-07 08:16:00+02:00 fuseau : Europe/Brussels

context_timestamp convertit vers self.env.tz : le fuseau du contexte (clé tz), sinon celui du profil de l'utilisateur, sinon UTC. Dans le shell, l'utilisateur est OdooBot, réglé sur Europe/Brussels dans la démo.

Le client web, lui, ne lit pas ce profil pour afficher l'heure : il convertit dans le fuseau du navigateur. Même utilisateur, même devis, deux navigateurs réglés différemment :

Deux conséquences. À l'écran, un écart d'heure entre deux postes peut venir du seul réglage de leur fuseau, sans rien dans le code. Et tout ce que ton code met en forme sans navigateur (courriel, PDF, message dans le chatter) doit passer par context_timestamp : sinon tu écris l'heure UTC.

2. context_today plutôt que Date.today()

Au démarrage, Odoo force le fuseau de son processus à UTC. fields.Date.today() renvoie donc la date UTC du serveur. fields.Date.context_today(record) renvoie la date vue dans le fuseau de l'utilisateur. Entre 22 h et minuit UTC, en heure d'été à Bruxelles, les deux ne tombent pas le même jour. Le second argument permet de le vérifier sans attendre le soir :

# context_today.py
from datetime import datetime
from odoo import fields

order = env['sale.order'].browse(2)
print("fuseau         :", order.env.tz)
print("Date.today()   :", fields.Date.today())
soir = datetime(2026, 10, 21, 22, 30)      # 22:30 UTC, sans fuseau
print("context_today  :", fields.Date.context_today(order, soir))
ny = order.with_context(tz='America/New_York')
print("à New York     :", fields.Date.context_today(ny, soir))

Date.today() ne prend pas d'instant en argument : elle donne la date UTC du moment où le script tourne (ici en fin de matinée). Le fuseau suit le contexte : with_context(tz=…) suffit à changer de point de vue. Pour une valeur par défaut, passe la fonction sans parenthèses : Odoo l'appelle avec le modèle quand il calcule les valeurs par défaut, comme le fait le cœur.

date = fields.Date(default=fields.Date.context_today)        # date du jour de l'utilisateur
date_order = fields.Datetime(default=fields.Datetime.now)    # instant présent, en UTC

Pour un Datetime, garde now : l'instant est le même partout, seul l'affichage change.

3. zoneinfo : le fuseau en Odoo 20

En Odoo 19, self.env.tz renvoyait un objet pytz. En Odoo 20, c'est un ZoneInfo de la bibliothèque standard, et pytz n'est plus dans les dépendances d'Odoo (requirements.txt). Le cas courant : un rendez-vous saisi à 9 h, heure de Bruxelles, à enregistrer dans un Datetime.

# zoneinfo_demo.py
from datetime import datetime, UTC

order = env['sale.order'].browse(2)
tz = env.tz
print(type(tz).__name__, tz.key)
rdv = datetime(2026, 10, 22, 9, 0).replace(tzinfo=tz)   # 9 h à Bruxelles
print(rdv, "->", rdv.astimezone(UTC).replace(tzinfo=None))
try:
    tz.localize(datetime(2026, 10, 22, 9, 0))           # réflexe pytz
except AttributeError as e:
    print("AttributeError:", e)
try:
    order.date_order = rdv                              # datetime avec fuseau
except ValueError as e:
    print("ValueError:", e)
order.date_order = rdv.astimezone(UTC).replace(tzinfo=None)
print("écrit :", order.date_order)
try:
    from odoo.tools.date_utils import utc
except ImportError as e:
    print("ImportError:", e)

Ligne par ligne :

  • Le nom du fuseau se lit dans tz.key (avec pytz, c'était tz.zone).
  • Avec zoneinfo, .replace(tzinfo=tz) donne le bon décalage (+02:00 ici, heure d'été). Avec pytz, le même .replace() donnait +00:18, d'où le .localize() obligatoire ; le ZoneInfo n'a pas cette méthode.
  • Un champ Datetime refuse une valeur avec fuseau : repasse en UTC, puis .replace(tzinfo=None). Cette règle n'a pas changé depuis la 19.
  • date_utils.utc a disparu : prends UTC dans datetime (Python 3.11 et plus).

Action serveur : timezone n'est plus pytz

Dans le code d'une action serveur, le nom timezone est désormais ZoneInfo (en 19 : pytz.timezone). Un code repris de la 19 avec .localize() échoue à l'exécution ; la forme zoneinfo passe. Exécutés sur S00002 : le code ci-dessous, puis le même avec local = bxl.localize(record.date_order) en deuxième ligne :

bxl = timezone('Europe/Brussels')
local = record.date_order.replace(tzinfo=datetime.timezone.utc).astimezone(bxl)
log("%s : %s en base, %s à Bruxelles" % (record.name, record.date_order, local.strftime('%d/%m/%Y %H:%M')))
zoneinfo -> S00002 : 2026-09-07 06:16:00 en base, 07/09/2026 08:16 à Bruxelles localize -> AttributeError("'ZoneInfo' object has no attribute 'localize'") while evaluating

À retenir

  • En base, un Datetime est en UTC sans fuseau ; le client web l'affiche dans le fuseau du navigateur.
  • Date du jour : fields.Date.context_today(self) ; en valeur par défaut, sans parenthèses.
  • Heure locale en Python (courriel, PDF, chatter) : fields.Datetime.context_timestamp(self, dt).
  • Odoo 20 : self.env.tz et timezone sont des ZoneInfo ; .replace(tzinfo=…) au lieu de .localize(), tz.key au lieu de tz.zone.
