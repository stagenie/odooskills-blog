Première approche du développement Odoo 20 : écrans, debug, module

Avant d'écrire du code, on apprend à lire un écran : mode développeur, infobulle des champs, menu de l'insecte, menu Technique. Puis on refait soi-même ce qu'on vient de lire : un menu, une action, un modèle, deux vues et leurs droits, installés et mis à jour sur Odoo 20.

~15 minutes de lecture · niveau débutant · parcours Fondamentaux

Ce que tu vas apprendre

Lire un écran

Activer le mode développeur, retrouver le nom technique d'un champ, la vue et l'action d'un écran, explorer le menu Technique.

Le chaînage

Menu, action, modèle, vues : les quatre enregistrements qui font un écran, vérifiés dans le shell.

Ton premier module 20

Les mêmes quatre éléments écrits à la main, avec les droits ir.access, installés, mis à jour et relus dans le journal.

Prérequis

  • Un Odoo 20 Community qui démarre (voir Installer Odoo 20 sur Ubuntu et le lancer dans PyCharm), une base avec l'application Ventes et un compte administrateur.
  • Un terminal pour lancer odoo-bin et odoo-bin shell, un éditeur pour écrire quatre petits fichiers.
  • Aucune connaissance de l'ORM : on reste au premier pas.

Tu travailles encore sur Odoo 19 ? Première approche du développement Odoo 19 reste valable pour ta version. Celui-ci reprend la même démarche pour Odoo 20, chaque écran et chaque sortie relevés sur un serveur 20.0, et va un pas plus loin : le premier module.

Odoo a une particularité qui déroute au début : presque tout ce que tu vois à l'écran est une donnée, pas du code compilé. Le menu, l'action qu'il déclenche, la vue qui s'affiche, les droits qui la filtrent sont des enregistrements en base. Le code Python ne décrit que le modèle et sa logique. Comprendre ce chaînage, c'est savoir où regarder avant d'écrire une ligne, et savoir quoi écrire ensuite.

1. Activer le mode développeur

Le mode développeur (on dit aussi « mode debug ») ajoute à l'interface ce qu'un utilisateur n'a pas besoin de voir : noms techniques, menu Technique, éditeur de vues, outils de test. Il se règle par session de navigateur, pas par base ni par utilisateur. Deux façons de l'activer :

  • Par les Paramètres : en bas de la page Paramètres généraux, bloc « Outils développeur ».
  • Par l'adresse : ajoute ?debug=1 à l'URL, par exemple http://localhost:8069/odoo/sales?debug=1. C'est le plus rapide.

Pour en sortir : dernière entrée du menu de l'insecte, « Quitter le mode débogage », ou ?debug= sans valeur dans l'adresse.

ValeurEffet
?debug=1mode développeur simple : c'est celui dont tu auras besoin au quotidien
?debug=assetsen plus, JavaScript et CSS servis non minifiés : lisibles dans les outils du navigateur, mais chaque page charge plus lentement
?debug=testscharge en plus les fichiers de test du client (visites guidées)
?debug=désactive le mode

Ces quatre valeurs sont les seules qu'Odoo 20 reconnaît (addons/web/models/ir_http.py:34-61, liste identique en 19) ; toute autre valeur « vraie » équivaut à 1, et plusieurs se combinent avec une virgule (?debug=assets,tests).

Ne confonds pas ce mode avec l'option --dev de odoo-bin. Sur un serveur lancé avec --dev=all, la page Ventes ouverte sans ?debug n'a ni insecte ni menu Technique (odoo.debug vaut "" dans la console). --dev agit côté serveur : all regroupe access, qweb, reload et xml (odoo/tools/config.py:31), c'est-à-dire traces des erreurs de droits, débogage des gabarits, redémarrage à chaque fichier Python modifié et vues relues depuis le disque. Le détail de ces options est dans Mettre à jour un module Odoo 20 qui ne prend pas tes modifications.

2. L'anatomie d'un écran

Ouvre Ventes en mode développeur. Chaque zone de l'écran vient d'un enregistrement ou d'un champ précis :

ZoneCe que c'estD'où ça vient
1l'applicationmenu racine, ir.ui.menu sans parent
2les sous-menusir.ui.menu enfants ; un menu feuille porte une action
3le titre (fil d'Ariane)le nom de l'action, ir.actions.act_window
4la recherche et le filtre actifla vue search du modèle ; le filtre « Mes devis » est posé par le context de l'action
5le pagercalculé par le client web, rien à écrire
6les types de vue proposésle champ view_mode de l'action
7la listeune vue list, ir.ui.view, sur le modèle sale.order
8l'insecteprésent seulement en mode développeur

Dans Odoo 20, le pager n'est pas en bas de page : il vit dans le panneau de contrôle, à côté des boutons de vue. Les libellés anglais du tableau de bord (« To Confirm », « Sales Revenue ») viennent de la traduction incomplète de la base de démonstration, pas d'une erreur de configuration.

En mode développeur, chaque libellé de formulaire porte un petit ?. Survole celui du champ Client d'un devis :

Tout ce dont tu as besoin pour intervenir sur ce champ est là : son nom (partner_id), le modèle qui le porte (sale.order), son type, le modèle visé (res.partner), le widget qui l'affiche, et les conditions qui le rendent obligatoire ou en lecture seule (ici, en lecture seule quand le devis est annulé ou devenu commande). 4. Le menu de l'insecte

L'icône insecte de la barre du haut ouvre un menu qui dépend de l'écran. Sur un formulaire, il est complet :

Les entrées que tu utiliseras dès le premier jour :

  • Modèle : sale.order ouvre la fiche du modèle, avec la liste de ses champs.
  • Action ouvre l'action courante : res_model, view_mode, domain, context, path.
  • Afficher : Form (« List » sur une liste) ouvre la vue affichée, avec son identifiant XML et son XML ; Arc calculé montre la vue après application de tous les héritages, ce que le navigateur reçoit vraiment.
  • Métadonnées donne l'identifiant de l'enregistrement et son identifiant XML s'il en a un.
  • Droits d'accès liste les droits du modèle. En Odoo 20 c'est une seule entrée, vers le modèle ir.access (web/static/src/webclient/actions/debug_items.js:124-135) ; en 19 il y en avait deux, droits d'accès (ir.model.access) et règles d'enregistrement (ir.rule).

Le pas-à-pas complet de ces entrées, avec la vérification dans le shell, est dans Mode debug Odoo 20 : nom technique d'un champ, d'une vue, d'une action.

6. Lire l'adresse

L'URL du client web dit où tu es. Relevés sur la même base :

Le champ path d'une action est donc ce qui donne une adresse lisible à ton écran : on s'en sert plus bas.

7. Le chaînage, vérifié dans le shell

L'interface montre le chaînage morceau par morceau ; le shell le montre d'un coup. Lance odoo-bin shell sur ta base (voir Le shell Odoo 20) et suis le menu Devis :

$ odoo-bin shell -c odoo.conf -d ma_base --no-http
>>> menu = env.ref('sale.menu_sale_quotations')
>>> menu.complete_name, menu.action
('Ventes/Commandes/Devis', ir.actions.act_window(461,))
>>> a = menu.action
>>> a.res_model, a.view_mode, a.domain, a.context, a.path
('sale.order', 'list,kanban,form,calendar,pivot,graph,activity', False, "{'search_default_my_quotation': 1}", 'sales')
>>> len(env['sale.order']._fields)
124

Le menu porte l'action ; l'action désigne le modèle sale.order, les types de vue proposés, et un contexte qui active le filtre « Mes devis » (zone 4 de la capture), c'est-à-dire [('user_id', '=', uid)]. Pas de domaine sur l'état : la liste « Devis » montre aussi les commandes confirmées (colonne Statut de la capture). Les vues elles-mêmes sont celles du modèle, choisies par priorité quand l'action n'en impose pas.

À toi, sur ta base, avec l'infobulle, le menu de l'insecte et le menu Technique :

#QuestionOù regarder
1Quel modèle affiche la liste des devis ?insecte › Modèle
2Quel est le nom technique du champ Client ?infobulle du libellé
3Quelle adresse ouvre l'action des devis ?insecte › Action, champ path
4Pourquoi la liste n'affiche-t-elle que tes devis ?insecte › Action, champ context
5Combien de champs a sale.order ?Technique › Champs, filtrer sur le modèle
Réponses (base de démonstration avec Ventes)
  1. sale.order.
  2. partner_id, un Many2one vers res.partner.
  3. /odoo/sales (path = sales).
  4. Le contexte {'search_default_my_quotation': 1} active le filtre « Mes devis » (vendeur = utilisateur connecté) ; retire-le de la barre de recherche et les devis de tous les vendeurs s'affichent.
  5. 124 sur cette base ; le nombre change avec les modules installés, qui ajoutent des champs au modèle.

8. À ton tour : les quatre éléments dans un module

Tu sais lire un écran ; en écrire un demande exactement les mêmes pièces. On construit le plus petit module utile : des notes de suivi rattachées à un contact, avec un menu, une action, un modèle, deux vues et une ligne de droits.

8.1 Le squelette

scaffold crée l'arborescence dans un dossier de ton addons_path :

$ odoo-bin scaffold mon_module …/mes_modules
$ find mon_module -type f | sort

Trois lignes comptent. version commence par 20.0 : Odoo 20 n'installe que les modules de sa série (odoo/modules/module.py:500-502). data liste les fichiers à charger, dans l'ordre : les droits d'abord, les vues ensuite. application fait apparaître le module dans le filtre « Applications » de la liste des modules. Sans author, le journal le signale par un WARNING Missing `author` key.

8.3 Le modèle, puis les vues, l'action et le menu

# mon_module/models/models.py
from odoo import fields, models


class MonModuleNote(models.Model):
    _name = 'mon_module.note'
    _description = "Note de suivi"
    _order = 'date desc, id desc'

    name = fields.Char("Objet", required=True)
    partner_id = fields.Many2one('res.partner', string="Contact")
    date = fields.Date("Date", default=fields.Date.context_today)
    description = fields.Text("Détail")

_name est le nom du modèle (la table sera mon_module_note) ; chaque champ devient une colonne. Les quatre éléments de l'écran tiennent dans un seul fichier XML :

<!-- mon_module/views/views.xml -->
<odoo>

        <field name="arch" type="xml">
            <list>
                <field name="date"/>

                <field name="partner_id"/>
            </list>
        </field>
    </record>

    <record id="note_view_form" model="ir.ui.view">
        <field name="name">mon_module.note.form</field>
        <field name="model">mon_module.note</field>
        <field name="arch" type="xml">
            <form>
                <sheet>

                        <field name="name"/>

Mets ce fichier en regard du schéma : deux ir.ui.view, une ir.actions.act_window qui désigne le modèle et ses types de vue, deux ir.ui.menu (l'application, puis le menu qui porte l'action). La liste s'écrit <list>, jamais <tree> (déjà le cas en 19).

La trace se lit de bas en haut : en chargeant un fichier de données, Odoo demande au registre le modèle nommé par le CSV, ir.model.access, et ce modèle n'existe plus en Odoo 20.

En Odoo 20, les droits s'écrivent dans security/ir.access.csv

Le gabarit de scaffold écrit toujours l'ancien fichier (odoo/cli/templates/default/security/ir.model.access.csv.template). Odoo 20 réunit droits d'accès et règles d'enregistrement dans un seul modèle, ir.access. Supprime le fichier généré, écris celui-ci et cite-le dans le manifeste :

id,name,model_id,group_id/id,operation
access_mon_module_note_user,mon_module.note user,mon_module.note,base.group_user,crud

Une ligne = un groupe (ici les utilisateurs internes) et les opérations permises (créer, read, update, delete). Sans aucune ligne, le modèle existe mais aucun utilisateur n'y a accès. Les groupes, le domaine et le piège de la ligne sans groupe sont dans Les droits d'accès en Odoo 20 : ir.access.

t-esc ne plante pas : il n'affiche plus rien

Les tutoriels écrits pour les versions précédentes affichent une valeur dans un gabarit QWeb avec t-esc. En Odoo 20, la directive n'existe plus : pas d'erreur, un avertissement au journal et une balise vide. Rendu du même gabarit dans le shell, avec nom = 'Ready Mat' :

<p><t t-esc="nom"/></p>   →  '<p></p>'
WARNING ma_base odoo.addons.base.models.ir_qweb: Unknown directives or unused attributes: {'t-esc'} from <t t-esc="nom"/>
<p><t t-out="nom"/></p>   →  '<p>Ready Mat</p>'

Écris toujours t-out. Les autres pannes silencieuses d'un code venu de la 19 sont dans Pannes silencieuses d'un module 19 sous Odoo 20 : t-esc, datas, t-set.

La liste complète des écarts techniques est dans Ce qui change techniquement en Odoo 20, et les messages d'erreur d'un module 19 installé sur une 20 dans Module Odoo 19 sous Odoo 20 : les messages d'erreur et leur correctif.

À retenir

  • Un écran Odoo = un menu, une action, un modèle, des vues, et des droits : tout sauf le modèle est une donnée en base, et ton module écrit exactement ces enregistrements.
  • Le mode développeur (?debug=1) est un réglage de session du navigateur ; l'option --dev du serveur ne l'active pas.
  • Infobulle, menu de l'insecte et menu Technique répondent à « quel champ, quelle vue, quelle action » avant d'écrire une ligne.
  • En Odoo 20 : manifeste en 20.0.x.y.z, droits dans security/ir.access.csv, t-out dans les gabarits. Le fichier de droits du scaffold fait échouer l'installation.
  • La boucle de travail : écrire, -u, lire le journal, regarder l'écran, vérifier dans le shell.
