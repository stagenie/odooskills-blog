Tests Odoo 20 : --test-tags, HttpCase, tours et odoo_test_helper

Un module d'exemple, quatre classes de test, et chaque sélection --test-tags vérifiée par le nombre de tests réellement lancés. Puis les tests qui passent par HTTP, un tour joué dans Chrome, ce que devient odoo_test_helper sous Odoo 20, et comment lire un résultat qui annonce « 0 failed » sans avoir rien testé.

~13 minutes de lecture · niveau intermédiaire · parcours Qualité & tests

Ce que tu vas apprendre

Sélectionner

Écrire @tagged et --test-tags pour lancer un module, une classe, une méthode, une phase, ou tout sauf les tests lents.

Tester par HTTP

url_open, authenticate, make_jsonrpc_request, puis un tour start_tour joué dans un vrai navigateur.

Croire le résultat

Codes de sortie 0, 1 et 255, tests sautés en silence, et une commande prête pour l'intégration continue.

Prérequis

  • Les bases des tests Odoo 20 : le dossier tests/, TransactionCase, setUpClass, la ligne de résultat. Elles sont posées dans Tests automatisés en Odoo 20 : TransactionCase ; cet article part de là.
  • Une instance Odoo 20 Community en ligne de commande, une base ma_base réservée aux tests, avec l'application Contacts. Les données de démonstration servent à un seul test.
  • Pour les tours : Google Chrome ou Chromium sur la machine qui lance les tests, et le paquet Python websocket-client dans l'environnement d'Odoo.

1. Le module d'essai : un code client

Le module oski_code_client (dépendance : contacts) pose sur un contact un code lisible, CLI-00042, une seule fois. Le code vit dans un mixin réutilisable, le contact en hérite :

# models/code_mixin.py (extrait : models/res_partner.py suit)
from odoo import fields, models
from odoo.exceptions import UserError


class OskiCodeMixin(models.AbstractModel):
    """Un code lisible 'PRÉFIXE-00042', posé une seule fois, sur n'importe quel modèle."""
    _name = 'oski.code.mixin'
    _description = 'Code lisible (mixin)'
    _oski_code_prefixe = 'REF'

    oski_code = fields.Char('Code', copy=False, index=True, readonly=True)

    def action_oski_generer_code(self):
        for record in self:
            if record.oski_code:
                raise UserError(self.env._("%s a déjà un code.", record.display_name))
            record.oski_code = '%s-%05d' % (self._oski_code_prefixe, record.id)
        return True


# models/res_partner.py
class ResPartner(models.Model):
    _name = 'res.partner'
    _inherit = ['res.partner', 'oski.code.mixin']
    _oski_code_prefixe = 'CLI'

Une vue héritée ajoute le champ et un bouton « Générer le code » à la fiche contact. Deux routes exposent le code : une route HTTP qui répond en JSON, et une route jsonrpc qui le génère.

# controllers/main.py
from odoo import http
from odoo.http import request


class CodeClientController(http.Controller):

    @http.route('/oski/code-client/<int:partner_id>', type='http', auth='user', methods=['GET'])
    def lire_code(self, partner_id):
        partner = request.env['res.partner'].browse(partner_id).exists()
        if not partner:
            raise request.not_found()
        return request.make_json_response({
            'id': partner.id,
            'nom': partner.name,
            'code': partner.oski_code or None,
        })

    @http.route('/oski/code-client/generer', type='jsonrpc', auth='user')
    def generer_code(self, partner_id):
        partner = request.env['res.partner'].browse(partner_id)
        partner.action_oski_generer_code()
        return {'code': partner.oski_code}

Les tests se répartissent en quatre classes, dans trois fichiers. Leur phase et leurs étiquettes décident de quand et comment chacune se lance :

ClasseDécorateurCe qu'elle testeTests

TestCodeClientaucunrègles du code, droits par utilisateur, Form, un contact de démo6

La classe sans décorateur reçoit les étiquettes standard et post_install : c'est la valeur par défaut d'Odoo 20, détaillée dans l'article sur TransactionCase. L'étiquette oski_navigateur est libre : un nom à soi, posé pour pouvoir écarter le test lent.

# tests/test_code_client.py (extrait)
from odoo.exceptions import AccessError, UserError
from odoo.tests import Form, TransactionCase, loaded_demo_data, new_test_user, users


class TestCodeClient(TransactionCase):

    @classmethod
    def setUpClass(cls):
        super().setUpClass()
        cls.client = cls.env['res.partner'].create({'name': 'Client de test'})
        new_test_user(cls.env, login='oski_interne', groups='base.group_user')
        new_test_user(cls.env, login='oski_gestionnaire', groups='base.group_user,base.group_partner_manager')

    @users('oski_gestionnaire')
    def test_gestionnaire_genere_le_code(self):
        # self.env est ici celui de l'utilisateur : ses droits s'appliquent
        client = self.client.with_env(self.env)
        client.action_oski_generer_code()
        self.assertEqual(client.oski_code, 'CLI-%05d' % client.id)

    @users('oski_interne')
    def test_interne_refuse(self):
        client = self.client.with_env(self.env)
        with self.assertRaises(AccessError):
            client.action_oski_generer_code()

    def test_formulaire_code_en_lecture_seule(self):
        with Form(self.env['res.partner']) as fiche:
            fiche.name = 'Client saisi par Form'
            with self.assertRaises(AssertionError):
                fiche.oski_code = 'CLI-MANUEL'
        self.assertFalse(fiche.record.oski_code)

    def test_contact_de_demo(self):
        if not loaded_demo_data(self.env):
            self.skipTest("base sans données de démonstration")
        azure = self.env.ref('base.res_partner_12')
        azure.action_oski_generer_code()
        self.assertEqual(azure.oski_code, 'CLI-%05d' % azure.id)

Trois outils du cadre de test servent ici. @users('login') rejoue la méthode sous cet utilisateur : self.env devient le sien. Le premier essai, avec un simple utilisateur interne, a levé une AccessError : en Odoo 20, le groupe « Utilisateur interne » ne peut modifier que son propre contact (ligne res_partner_rule_write_self de base/security/ir.access.csv). D'où deux utilisateurs, et un test pour chaque cas. Form rejoue la vue : écrire dans un champ en lecture seule y lève AssertionError, comme l'écran l'interdit. loaded_demo_data(env) permet de sauter proprement un test qui a besoin des données de démonstration.

2. Comment --test-tags choisit les tests

Chaque élément de --test-tags s'écrit [-][étiquette][/module][:Classe][.méthode] (odoo/tests/tag_selector.py). Toutes les parties sont facultatives :

  • sans étiquette, une inclusion vaut standard, l'étiquette que portent toutes les classes ; * désigne toutes les étiquettes ;
  • un test est retenu s'il correspond à au moins une inclusion et à aucune exclusion ;
  • une liste qui ne contient que des exclusions reçoit d'office l'inclusion standard, sans module : --test-tags -oski_navigateur seul lance donc tous les tests standard de tous les modules de la base, sauf celui-là ;
  • at_install et post_install sont des étiquettes comme les autres, mais Odoo filtre aussi par phase : les tests at_install d'un module tournent juste après son chargement, les post_install à la fin, après la ligne « Starting post tests ».

--test-tags suffit à activer les tests et implique --stop-after-init (odoo/tools/config.py). À l'inverse, --test-enable sans --test-tags vaut +standard : tous les tests de tous les modules concernés. --test-file chemin/du/test.py existe toujours : Odoo le transforme en sélection par fichier.

Chaque variante, prouvée par le compte

La base porte déjà le module ; les commandes ci-dessous n'ont ni -i ni -u. Le seul nombre qui fait foi est celui de la ligne odoo.tests.result :

--test-tagsTestsLecture
/oski_code_client13les 11 tests du module, plus les deux suites JavaScript transverses du module web (WebSuite, MobileWebSuite)
/oski_code_client:TestCodeClient6une classe
/oski_code_client:TestCodeClient.test_generer_code1une méthode ; :TestCodeClient.test_generer_code sans module donne aussi 1
/oski_code_client,-oski_navigateur12tout sauf le tour
oski_navigateur1une étiquette seule, dans toute la base
/oski_code_client,-:TestCodeClientHttp10exclure une classe : 13 − 3
is_tour/oski_code_client1étiquette ajoutée à la volée aux méthodes dont le source contient self.start_tour

oski_code_client (sans /)11le nom du module vaut encore étiquette, par compatibilité ; les suites transverses ne suivent pas

Deux résultats demandent un œil attentif. Sur une base existante, sans -i ni -u, le test at_install tourne quand même : au chargement, Odoo lance les tests d'installation de tous les modules quand aucun n'est installé ni mis à jour (odoo/modules/loading.py). Et is_tour est le pendant, pour les tours, de l'étiquette is_query_count : sans module, il lancerait tous les tours de la base.

Une sélection fausse ne fait jamais échouer la commande

/oski_code_client.TestCodeClient (un point au lieu de deux-points) cherche une méthode nommée TestCodeClient : 0 test. Un module mal tapé : 0 test. Une syntaxe que la grammaire refuse, /oski_code_client#TestCodeClient, écrit 33 lignes ERROR … Invalid tag (une à chaque module chargé, une à la phase finale), lance 0 test, et le code de sortie reste 0 : un ERROR du journal ne compte pas comme un échec. Après une modification de --test-tags, relisez toujours le « of N tests ».

3. Base neuve, base existante, -i et -u

Le même --test-tags /oski_code_client ne lance pas le même nombre de tests selon la base et l'option d'installation :

SituationCommandeTests
Base neuve, avec démo-d ma_base_neuve -i oski_code_client --with-demo13, le test de démo compris
Base neuve, sans démo-d ma_base_neuve -i oski_code_client13, dont 1 skipped … base sans données de démonstration
Copie d'une base de travail (plusieurs dizaines de modules)-d ma_base -i oski_code_client11
Base où le module est installé-d ma_base -u oski_code_client11
Même base, sans -i ni -u-d ma_base13

La différence de 2 vient des suites JavaScript du module web. La phase post_install ne regarde que les modules installés ou mis à jour par la commande, et tous les modules de la base quand il n'y a ni -i ni -u (odoo/service/server.py). Sur une base neuve, web vient d'être installé : ses suites entrent dans la sélection. Avec -i ou -u du seul module, elles n'y sont pas. Le test sauté reste compté dans le total : cherchez skipped dans le journal si un test doit absolument tourner.

Le nom de la base compte aussi. Les tests HttpCase démarrent un vrai serveur HTTP dans le processus de test ; si le filtre de bases de la configuration en laisse passer plusieurs, une requête sans session n'a pas de base désignée. Sur la base d'essai, avec un --db-filter qui laissait passer plusieurs bases du serveur, le test anonyme a reçu 404 au lieu de la redirection attendue : AssertionError: 404 != 303. Avec --db-filter='^ma_base$', les trois tests HTTP passent. Lancez donc toujours les tests avec un filtre strict sur la base de test.

4. HttpCase : tester les routes

HttpCase hérite de TransactionCase et ajoute un client HTTP vers le serveur du test. Le serveur et le test partagent la même transaction : ce que le test crée est visible des routes, ce que les routes écrivent est visible du test, et tout est annulé à la fin.

# tests/test_http.py (extrait)
from odoo.tests import HttpCase, tagged


@tagged('post_install', '-at_install')
class TestCodeClientHttp(HttpCase):

    @classmethod
    def setUpClass(cls):
        super().setUpClass()
        cls.client = cls.env['res.partner'].create({'name': 'Client du test HTTP'})

    def test_anonyme_renvoye_vers_connexion(self):
        reponse = self.url_open(f'/oski/code-client/{self.client.id}', allow_redirects=False)
        self.assertEqual(reponse.status_code, 303)
        self.assertIn('/web/login', reponse.headers['Location'])

    def test_lecture_json(self):
        self.client.action_oski_generer_code()
        self.authenticate('admin', 'admin')
        reponse = self.url_open(f'/oski/code-client/{self.client.id}')
        self.assertEqual(reponse.status_code, 200)
        self.assertEqual(reponse.json()['code'], self.client.oski_code)

    def test_generer_par_jsonrpc(self):
        self.authenticate('admin', 'admin')
        resultat = self.make_jsonrpc_request('/oski/code-client/generer', {'partner_id': self.client.id})
        self.assertEqual(resultat['code'], 'CLI-%05d' % self.client.id)
        self.assertEqual(self.client.oski_code, resultat['code'])
  • url_open(url, …) envoie un GET, ou un POST dès qu'on lui passe data, files ou json ; une URL qui commence par / est complétée par l'adresse du serveur de test. allow_redirects=False permet de lire la redirection elle-même : une route auth='user' appelée sans session répond 303 vers /web/login.
  • authenticate(login, mot_de_passe) ouvre une session pour les appels suivants. Le mot de passe admin est celui d'une base créée par Odoo ; sur une copie de base de travail, utilisez un utilisateur créé dans le test.
  • make_jsonrpc_request(route, params) enveloppe l'appel JSON-RPC et renvoie directement result ; une erreur côté serveur lève JsonRpcException.

La dernière ligne de test_generer_par_jsonrpc lit dans le test le code que la route vient d'écrire : c'est le partage de transaction à l'œuvre. Pour aller plus loin sur les contrôleurs eux-mêmes (signature, codes de retour), l'article sur les webhooks en Odoo 20 en construit un complet.

5. Un tour : le bouton cliqué dans Chrome

Un tour est un scénario JavaScript, enregistré dans le registre web_tour.tours et joué par un Chrome sans interface. Chaque étape attend qu'un élément correspondant à trigger soit présent et visible, puis exécute run s'il y en a un ; une étape sans run est une simple vérification.

// static/tests/tours/code_client_tour.js
import { registry } from "@web/core/registry";

registry.category("web_tour.tours").add("oski_code_client_tour", {
    steps: () => [
        {
            content: "Le contact n'a pas encore de code : cliquer sur le bouton",
            trigger: ".o_form_view button[name='action_oski_generer_code']",
            run: "click",
        },
        {
            content: "Le code apparaît sur la fiche",
            trigger: ".o_field_widget[name='oski_code']:contains(CLI-)",
        },
        {
            content: "Le bouton a disparu",
            trigger: ".o_form_view:not(:has(button[name='action_oski_generer_code']))",
        },
    ],
});

Le fichier n'est chargé que dans le paquet de ressources des tests, déclaré au manifeste : 'assets': {'web.assets_tests': ['oski_code_client/static/tests/tours/**/*']}. Côté Python, le test crée le contact, puis demande au navigateur d'ouvrir sa fiche et de jouer le tour :

@tagged('post_install', '-at_install', 'oski_navigateur')
class TestCodeClientTour(HttpCase):

    def test_tour_generer_code(self):
        client = self.env['res.partner'].create({'name': 'Client du tour'})
        self.start_tour(f'/odoo/contacts/{client.id}', 'oski_code_client_tour', login='admin')
        self.assertEqual(client.oski_code, 'CLI-%05d' % client.id)

Le premier argument de start_tour est l'URL d'arrivée : en Odoo 20, c'est elle qui fixe la page de départ. Le tour réussi écrit tour succeeded dans le journal, et la ligne suivante du test vérifie en Python, dans la même transaction, ce que le clic a écrit. Lors d'une régression volontaire (code sur 4 chiffres au lieu de 5), le tour est d'ailleurs resté vert, puisque CLI- s'affichait bien : c'est cette assertion Python qui a échoué.

Quand une étape échoue, le test s'arrête au bout de 10 secondes avec le numéro et le texte de l'étape, et Odoo enregistre une capture de l'écran du navigateur (option --screenshots ; par défaut odoo_tests/<base>/screenshots dans le dossier temporaire du système). Une première version du tour commençait par vérifier le champ, encore vide :

FAILED: [1/4] Tour oski_code_client_tour → Step La fiche affiche le champ Code client, encore vide (trigger: .o_form_view .o_field_widget[name='oski_code']). Element has been found. BUT: Element is not visible. TIP: You can use :not(:visible) to force the search for an invisible element. TIMEOUT step failed to complete within 10000 ms.

Un champ en lecture seule et vide n'affiche rien : l'élément existe, sans taille. La version finale part du bouton, visible tant que le code n'existe pas, puis vérifie le texte affiché avec :contains(…).

6. Quel Chrome, et quand il ne démarre pas

Odoo cherche le navigateur dans cet ordre (odoo/tests/common.py, _find_executable) : la variable d'environnement ODOO_BROWSER_BIN si elle désigne un fichier existant, puis google-chrome, chromium, chromium-browser et google-chrome-stable dans le PATH. Il le lance avec un profil temporaire créé dans le dossier temporaire du système (TMPDIR), puis attend 10 secondes que le navigateur annonce son port de débogage. Le dialogue passe par websocket-client : sans ce paquet, les tests navigateur sont sautés.

Sur la machine d'essai, Chrome 155 trouvé par le PATH a joué le tour ; le Chromium d'une installation Playwright, désigné par ODOO_BROWSER_BIN, aussi. En revanche, avec un TMPDIR pointant vers un dossier au chemin très long, Chrome s'arrête aussitôt : le chemin de son socket de contrôle dépasse la longueur permise.

Sans navigateur, le tour est « sauté », pas « en échec »

Quand Chrome ne démarre pas, Odoo lève SkipTest : le test est compté, marqué skipped, et la suite affiche « 0 failed, 0 error(s) » avec un code de sortie 0. Une intégration continue sans Chrome, ou avec un dossier temporaire au chemin trop long, peut rester verte des mois sans jouer un seul tour. Le message dépend de la cause (lecture de odoo/tests/common.py) : Chrome executable not found si aucun navigateur n'est trouvé, websocket-client module is not installed sans ce paquet, Chrome headless failed to start si le navigateur ne répond pas, le seul des trois rejoué ici. Les trois finissent en skipped : c'est ce mot qu'il faut chercher dans le journal. Ici, le correctif a été un TMPDIR court (/tmp).

7. odoo_test_helper sous Odoo 20

Tester un mixin demande un modèle concret qui l'utilise. La bibliothèque OCA odoo_test_helper répond à ce besoin : son FakeModelLoader enregistre, le temps d'un test, des modèles définis dans le dossier tests/. La dernière version publiée sur PyPI est la 2.1.3 (20 février 2026) ; l'intégration continue du projet la teste jusqu'à Odoo 18.0. Installée dans un environnement jetable, avec le test écrit comme le préconise sa documentation :

from odoo.tests import TransactionCase
from odoo_test_helper import FakeModelLoader


class TestMixinFakeModel(TransactionCase):

    def setUp(self):
        super().setUp()
        self.loader = FakeModelLoader(self.env, self.__module__)
        self.loader.backup_registry()
        from .fake_models import FakeDocument      # modèle 'oski.fake.document' qui hérite du mixin
        self.loader.update_registry((FakeDocument,))
        self.addCleanup(self.loader.restore_registry)

L'import échoue : la bibliothèque lit models.MetaModel.module_to_models, un attribut qui s'appelle _module_to_models__ dans Odoo 20. L'erreur survient au chargement du paquet tests du module : le registre ne se charge pas, aucun test ne tourne, pas même ceux des autres fichiers, et le code de sortie vaut 255. Un alias posé à la main ne va pas plus loin : Registry.load() a changé de signature. Ce n'est probablement pas une nouveauté de la 20 : le source public de la 19.0 porte déjà ces deux noms (_module_to_models__, Registry.load(module)). La bibliothèque a toutes les chances d'y échouer de la même façon ; l'essai n'a été fait qu'en 20.

L'alternative native est celle qu'utilise Odoo pour ses propres tests (odoo/addons/test_inherit, test_http…) : un petit module réservé aux tests, qui déclare le modèle concret et ses droits.

# test_oski_code_client/__manifest__.py (extrait)
{
    'name': 'Tests du mixin de code (module de test)',
    'version': '20.0.1.0.0',
    'category': 'Hidden/Tests',
    'depends': ['oski_code_client'],
    'data': ['security/ir.access.csv'],
    'license': 'LGPL-3',
}

# test_oski_code_client/models/document.py
class TestOskiDocument(models.Model):
    _name = 'test.oski.document'
    _inherit = ['oski.code.mixin']
    _description = 'Document de test du mixin de code'
    _oski_code_prefixe = 'DOC'

    name = fields.Char(required=True)

# test_oski_code_client/security/ir.access.csv
# id,name,model_id,group_id/id,operation,domain
# access_test_oski_document,test.oski.document,test.oski.document,base.group_user,crud,

Ses deux tests (préfixe DOC-, refus d'un second code) passent : -i test_oski_code_client --test-tags /test_oski_code_client → « 0 failed, 0 error(s) of 2 tests ». Ce module est à installer sur les bases de test seulement, jamais en production ; Hidden/Tests est la catégorie des modules de test d'Odoo. Les droits passent par ir.access.csv, comme pour tout modèle Odoo 20 (voir les droits d'accès en Odoo 20).

8. Lire le résultat : trois codes de sortie

CodeCe qui s'est passéConstaté avec
0aucun échec ni erreur… y compris si 0 test a tourné, ou si un tour a été sautésuite verte, sélection fausse, Chrome absent
1au moins un FAIL (assertion fausse) ou un ERROR (exception dans un test)régression du format du code : 5 failed of 13
255la base n'a pas pu se charger : aucun test n'a tournéimport impossible dans tests/

Pour un journal court, --log-level=warn ne garde que les avertissements et les erreurs : les FAIL avec leur trace, et la ligne de résultat, qui passe en ERROR dès qu'un test échoue.

Ce niveau masque en revanche le récapitulatif « Failed: … » qu'Odoo 20 écrit en fin de journal : il est émis en INFO. En niveau par défaut, il liste les cinq tests en échec sur une ligne chacun, ce qui est plus pratique dans un rapport d'intégration continue.

9. La commande à confier à l'intégration continue

Ce script réunit ce qui précède : base neuve, filtre de base strict, sélection par module, et deux garde-fous pour les cas où Odoo sort avec 0 sans avoir testé : aucun test lancé, ou un test sauté. Le second couvre toutes les causes d'un tour non joué, puisque chacune passe par SkipTest ; appliqué au journal de l'essai à dossier temporaire trop long (section 6), il le détecte. En intégration continue, la base a ses données de démonstration : aucun test du module n'y est sauté normalement.

#!/bin/bash
# Usage : ODOO="python3 odoo-bin -c odoo-ci.conf" ./lancer_tests.sh <base_neuve> <module1,module2>
set -o pipefail
BASE=$1
MODULES=$2
TAGS=$(echo "$MODULES" | sed 's#[^,]*#/&#g')        # oski_a,oski_b -> /oski_a,/oski_b

$ODOO -d "$BASE" -i "$MODULES" --with-demo --test-tags "$TAGS" \
      --db-filter="^${BASE}\$" --stop-after-init 2>&1 | tee tests.log
RC=$?

grep -q " of 0 tests " tests.log && { echo "ÉCHEC : aucun test lancé"; RC=1; }
grep -q " skipped " tests.log && { echo "ÉCHEC : au moins un test sauté (navigateur ?)"; RC=1; }
echo "Code de sortie : $RC"
exit $RC

Lancé sur une base neuve avec les deux modules, puis avec un nom de module mal tapé :

$ ODOO="python3 odoo-bin -c odoo-ci.conf" ./lancer_tests.sh ma_base_ci oski_code_client,test_oski_code_client … INFO ma_base_ci odoo.tests.result: 0 failed, 0 error(s) of 15 tests when loading database 'ma_base_ci' Code de sortie : 0 $ ODOO="python3 odoo-bin -c odoo-ci.conf" ./lancer_tests.sh ma_base_ci oski_code_clien … WARNING ma_base_ci odoo.modules.loading: invalid module names, ignored: oski_code_clien … WARNING ma_base_ci odoo.tests.result: 0 failed, 0 error(s) of 0 tests when loading database 'ma_base_ci' ÉCHEC : aucun test lancé Code de sortie : 1

15 tests : les 11 du module, les 2 du module de test et les 2 suites JavaScript de web, installé dans le même passage. Sans les garde-fous, la seconde commande serait sortie avec 0. Rejouée telle quelle sur la même base, la première lance aussi 0 test : -i sur des modules déjà installés ne les réinstalle pas, et le garde-fou sort avec 1. D'où une base neuve à chaque passage. Le fichier de workflow lui-même, avec PostgreSQL et Chrome dans le conteneur, fera l'objet de la prochaine étape de cette série.

Venant de la 19

  • La forme des éléments de --test-tags, --test-file, is_tour, la recherche du navigateur et ODOO_BROWSER_BIN sont les mêmes que dans la 19.0 publique (la 20 ajoute surtout la gestion des tests transverses). Ce qui change : une classe sans @tagged est post_install en 20, at_install en 19. Les décorateurs @tagged('post_install', '-at_install') d'un module 19 restent valables, mais une classe 19 sans décorateur ne tourne plus au même moment.
  • start_tour 19 transmettait aussi l'URL au tour (option startUrl) ; en 20, le tour démarre sur la page ouverte par le test. Passez toujours la bonne URL de départ en premier argument.
  • odoo_test_helper 2.1.3 : le source public de la 19.0 porte déjà les noms qui la cassent en 20 (non essayé en 19). Un module qui s'en sert est à porter vers un module de test.

À retenir

  • --test-tags : [-][étiquette][/module][:Classe][.méthode], séparés par des virgules ; deux-points avant la classe, point avant la méthode.
  • Après chaque changement de sélection, relisez « of N tests » : une sélection fausse donne 0 test et un code de sortie 0.
  • HttpCase partage la transaction avec son serveur ; lancez-le avec --db-filter='^ma_base$'.
  • Un tour attend un élément visible ; sans Chrome, il est sauté, pas en échec : vérifiez skipped.
  • odoo_test_helper 2.1.3 ne charge pas sous Odoo 20 : un module de test Hidden/Tests le remplace.
