Filestore Odoo 20 : où il est, le déplacer, le nettoyer

Les pièces jointes d'Odoo ne sont pas dans PostgreSQL mais dans un dossier du serveur. Le retrouver, le changer de disque sans perdre une image, et comprendre pourquoi un fichier supprimé reste sur le disque : trois gestes vérifiés sur Odoo 20.

~5 minutes de lecture · niveau intermédiaire · série Astuces dev Odoo 20

Édition : Community. Vérifié sur Odoo 20.0 Community, octobre 2026, base de démonstration (Ventes, Inventaire) et une copie de son filestore dans un dossier jetable.

La réponse en bref

  1. Où : <data_dir>/filestore/<nom de la base>. Le data_dir vient de ton odoo.conf (ou de -D) ; sans réglage, c'est ~/.local/share/Odoo.
  2. Déplacer : arrêter Odoo, copier le dossier avec rsync -a, changer data_dir, relancer, vérifier qu'aucun fichier ne manque.
  3. Nettoyer : ne rien effacer à la main. Supprime les pièces jointes dans Odoo ; l'action planifiée quotidienne d'aspiration retire ensuite les fichiers que plus rien ne référence.

1. Où est le filestore

Le chemin se calcule en une ligne : data_dir + filestore + le nom de la base. Plutôt que de le deviner, demande-le à Odoo. Ce script, passé à odoo-bin shell avec le même fichier de configuration que ton serveur, affiche la valeur par défaut, la valeur retenue et le fichier d'une pièce jointe :

# ou.py
from odoo.tools import config
print("défaut    :", config._default_options['data_dir'])
print("data_dir  :", config['data_dir'])
print("filestore :", config.filestore(env.cr.dbname))
print("stockage  :", env['ir.attachment']._storage())
att = env['ir.attachment'].search([('store_fname', '!=', False)], order='id', limit=1)
print("exemple   :", att.id, att.name, att.store_fname)
print("fichier   :", att._full_path(att.store_fname))

Ce qu'il faut lire :

  • Défaut : ~/.local/share/Odoo pour un compte qui a un dossier personnel, /var/lib/Odoo sur Linux pour un compte qui n'en a pas. Sur un serveur installé avec data_dir = /opt/odoo/data, le filestore de ma_base est donc /opt/odoo/data/filestore/ma_base.
  • Les noms de fichiers sont l'empreinte SHA-1 du contenu, rangée dans un sous-dossier nommé par ses deux premiers caractères (cf/cf769333…). Deux pièces jointes identiques partagent le même fichier : la base de démonstration compte 498 pièces jointes sur disque pour 282 fichiers.
  • checklist et upload ne sont pas des pièces jointes : ce sont les dossiers de travail du nettoyage, vus au point 3.
  • Stockage file : c'est le défaut. Le paramètre système ir_attachment.location à db mettrait les contenus dans PostgreSQL.

Le même data_dir contient aussi sessions/ (sessions web) et addons/ : déplacer le dossier entier les emmène avec lui.

2. Déplacer le filestore vers un autre disque

  1. Arrête Odoo (sudo systemctl stop odoo ou équivalent). Un serveur en marche écrit dans le filestore : au premier lancement sur le dossier de test, Odoo y a déposé dix paquets JavaScript et CSS compilés, référencés aussitôt dans la base.
  2. Copie en gardant droits et dates : rsync -a /opt/odoo/data/filestore/ma_base/ /srv/odoo-data/filestore/ma_base/ (le / final du chemin source compte). Le compte qui exécute Odoo doit pouvoir y écrire.
  3. Change la configuration : data_dir = /srv/odoo-data dans odoo.conf.
  4. Vérifie avant de relancer, avec ce script et la nouvelle configuration :
# verif.py
import os
from odoo.tools import config
racine = config.filestore(env.cr.dbname)
print("filestore :", racine)
att = env['ir.attachment'].browse(204)
print("pièce 204 :", att.file_size, "octets en base,", len(att.raw.content), "lus")
env.cr.execute("SELECT DISTINCT store_fname FROM ir_attachment WHERE store_fname IS NOT NULL")
manquants = [f for f, in env.cr.fetchall() if not os.path.exists(os.path.join(racine, f))]
print("manquants :", len(manquants))

Relancé sur la nouvelle configuration, le serveur affiche les images des produits et sert la pièce jointe 204 en entier. Garde l'ancien dossier quelques jours avant de le supprimer.

Pour une base seulement, inutile de toucher à data_dir : odoo-bin db rename déplace le filestore avec la base, et odoo-bin db drop l'efface avec elle.

Un fichier absent ne lève aucune erreur

Avant la copie, la même lecture avec la nouvelle configuration donne taille en base : 1396 puis octets lus : 0. Odoo renvoie un contenu vide et se contente d'une ligne INFO … ir_attachment: _file_read reading … dans le journal. Après un déplacement, compte les manquants avec verif.py plutôt que de te fier à l'absence d'erreur.

3. Nettoyer : pourquoi un fichier supprimé reste sur le disque

Supprimer une pièce jointe n'efface pas son fichier : Odoo pose une marque vide du même nom dans checklist/, car la transaction peut encore échouer et le même fichier peut servir à une autre pièce jointe. L'action planifiée « Base : données internes de l'aspiration automatique », quotidienne, parcourt ces marques et efface les fichiers que plus aucune ligne de ir_attachment ne référence. Ce script le montre :

# gc.py
import os
Att = env['ir.attachment']
att = Att.create({'name': 'essai-gc.txt', 'raw': b'fichier a jeter, filestore Odoo 20'})
env.cr.commit()
fname = att.store_fname
chemin = Att._full_path(fname)
coche = os.path.join(Att._full_path('checklist'), fname)
print("créé     :", att.id, fname)
att.unlink()
env.cr.commit()
print("supprimé : fichier présent ?", os.path.exists(chemin), "| coché ?", os.path.exists(coche))
Att._gc_file_store()
print("gc cron  : fichier présent ?", os.path.exists(chemin))
Att._gc_file_store_unsafe(grace_period=0)
print("gc forcé : fichier présent ?", os.path.exists(chemin))

Le passage normal (_gc_file_store, celui de l'action planifiée) a examiné 282 marques anciennes, toutes encore référencées, et n'a rien supprimé : la marque créée une seconde plus tôt n'est pas encore éligible. Odoo 20 attend au moins 30 minutes (jusqu'à une semaine si les délais de transaction PostgreSQL sont plus longs) et vide au passage les fichiers anciens de upload/. Venant de la 19 : le nettoyage effaçait toute marque non référencée sans délai, sous un verrou de la table ir_attachment.

Le passage forcé, grace_period=0, sert à un nettoyage ponctuel, serveur arrêté : une transaction en cours pose sa marque avant d'écrire son fichier, qui n'est donc pas encore référencé. Pour savoir quoi supprimer dans Odoo, regarde ce qui pèse :

env.cr.execute("""
    SELECT coalesce(res_model, '(aucun)'), count(*),
           pg_size_pretty(sum(file_size)::bigint)
    FROM ir_attachment WHERE store_fname IS NOT NULL
    GROUP BY 1 ORDER BY sum(file_size) DESC LIMIT 6""")
for modele, nb, taille in env.cr.fetchall():
    print(f"{modele:<22} {nb:>4}  {taille}")
ir.ui.view 10 12 MB product.template 157 6874 kB quotation.document 5 2699 kB res.partner 215 2198 kB product.product 46 1886 kB mail.call.artifact 4 213 kB

Sur la démonstration, la moitié du volume vient des paquets d'assets web (ir.ui.view), puis des images de produits. Le tri se fait sur les modèles en tête de liste, dans Odoo, puis l'aspiration retire les fichiers.

À retenir

  • Filestore = <data_dir>/filestore/<base> ; config.filestore(env.cr.dbname) donne le chemin exact.
  • Déplacer : serveur arrêté, rsync -a, nouveau data_dir, puis compter les fichiers manquants.
  • Un fichier manquant donne un contenu vide, pas une erreur.
  • Nettoyer dans Odoo, jamais à la main : l'aspiration quotidienne retire les fichiers orphelins après un délai d'au moins 30 minutes.
