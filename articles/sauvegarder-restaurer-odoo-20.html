Sauvegarder et restaurer Odoo 20 : base, filestore, planification

Ce que contient une sauvegarde complète, les trois façons de la faire, ce qui change vraiment quand on restaure une base « copiée » ou « déplacée », et un script de sauvegarde nocturne avec rotation, copie hors du serveur et restauration de contrôle.

~15 minutes de lecture · niveau intermédiaire · parcours Infrastructure

Ce que tu vas apprendre

Tout sauvegarder

La base et le filestore, par le gestionnaire, par odoo-bin db dump ou par pg_dump : ce que chaque fichier contient réellement.

Restaurer sans surprise

« Copie » ou « déplacée » : identifiant de base, URL, tâches planifiées, serveur de courriel, relevés sur les bases restaurées.

Automatiser et vérifier

Un script nocturne lancé par une minuterie systemd, sa rotation, sa copie distante, et la restauration de contrôle qui dit si la sauvegarde sert à quelque chose.

Prérequis

  • Un Odoo 20 Community sur un serveur Linux, installé par exemple comme dans Installer Odoo 20 sur un serveur Ubuntu : utilisateur système odoo, fichier /etc/odoo/odoo.conf, data_dir = /opt/odoo/data. Adapte les chemins aux tiens.
  • Les outils clients de PostgreSQL 16 (pg_dump, pg_restore, psql), tar, rsync, curl.
  • Des essais sur une base de test d'abord : on y restaure, on y écrase, on y supprime.

Pour fabriquer une base de recette à partir de la production (sauvegarde, chargement neutralisé, contrôle module par module), l'article Copier la prod en base de test Odoo 20 : db dump, load, neutralize fait le tour. Ici, on protège la production elle-même : une sauvegarde complète, régulière, conservée ailleurs, et dont on a prouvé qu'elle se restaure.

1. Ce qu'il faut sauvegarder : la base et le filestore

Une base Odoo vit à deux endroits. Dans PostgreSQL, les tables ; sur le disque, le filestore : les pièces jointes, les images des produits et des contacts, les PDF générés, les paquets de fichiers web. La table ir_attachment ne garde que le nom du fichier (store_fname) ; le contenu est sous <data_dir>/filestore/<nom de la base>/ (odoo/tools/config.py:1132-1133). Pour savoir où il est sur ton serveur, demande-le à Odoo plutôt que de le deviner :

$ sudo -u odoo /opt/odoo/venv/bin/python /opt/odoo/odoo/odoo-bin shell -c /etc/odoo/odoo.conf -d ma_base --no-http
>>> from odoo.tools import config
>>> config.filestore(env.cr.dbname)
'/opt/odoo/data/filestore/ma_base'
>>> env['ir.attachment']._filestore()
'/opt/odoo/data/filestore/ma_base'

Sans ligne data_dir dans le fichier de configuration, Odoo prend ~/.local/share/Odoo du compte qui le lance, ou /var/lib/Odoo si ce compte n'a pas de dossier personnel (config.py:547-552). Lancé une fois en root ou depuis ton compte, il écrit ailleurs que le service : c'est la première chose à vérifier quand une sauvegarde « contient » un filestore vide.

Le filestore de la base de démonstration, vu des deux côtés :

Trois choses à en tirer pour la sauvegarde. Un fichier est nommé par l'empreinte SHA-1 de son contenu (odoo/addons/base/models/ir_attachment.py:451) : deux pièces jointes identiques partagent un fichier (498 pièces, 282 fichiers), et un fichier n'est jamais réécrit, un contenu modifié en crée un autre. Une copie incrémentale (rsync) ne transfère donc que les nouveautés. Le dossier checklist sert au nettoyage des fichiers orphelins et upload aux envois en cours ; ils se sauvegardent avec le reste. Enfin, une base PostgreSQL restaurée sans son filestore démarre sans erreur, mais ses pièces jointes sont vides : c'est ce que la vérification de la section 6 détecte.

2. Première voie : le gestionnaire de bases

Sur /web/database/manager, le bouton Backup d'une base ouvre une fenêtre à deux choix : le format (zip ou pg_dump custom format (without filestore)) et la case Include filestore. Le bouton Restore Database, en bas de la page, fait le chemin inverse (section 5).

Le bouton envoie un simple POST sur /web/database/backup (addons/web/controllers/database.py:236-263), qu'on peut appeler sans navigateur. Le mot de passe maître est contrôlé (un mauvais mot de passe répond 403), et le fichier arrive avec un nom horodaté en UTC. Dans un script, lis le mot de passe dans un fichier en 600 (--data-urlencode master_pwd@fichier ; le fichier sans retour à la ligne final, sinon 403) plutôt que de l'écrire sur la ligne de commande, visible dans ps et l'historique :

$ curl -s -D - -o ma_base.zip -d master_pwd='…' -d name=ma_base -d backup_format=zip \
    http://localhost:8069/web/database/backup | grep -i disposition
content-disposition: attachment; filename=ma_base_2026-11-10_19-30-35.zip

Cette voie a deux limites en production. Le gestionnaire n'existe que si list_db est actif, ce qu'on coupe justement sur un serveur exposé (voir Gestionnaire de bases Odoo 20 : Access Denied et mot de passe maître). Et l'archive est fabriquée en entier sur le serveur, dans un fichier temporaire, avant d'être envoyée : prévois la place, et la patience, pour un gros filestore.

Ne cherche plus le service db de XML-RPC pour automatiser la sauvegarde à distance : il n'existe plus en 20 (Invalid service name: db, odoo/http/router.py:136-141). Un ancien script qui appelait dump par /xmlrpc/2/db échoue ; il passe soit par cette route HTTP, soit, mieux, par les deux voies suivantes, sur le serveur lui-même.

3. Deuxième voie : odoo-bin db dump

Même fonction, même zip, sans mot de passe maître : la commande se connecte avec le rôle du fichier de configuration, et doit tourner sous le compte qui peut lire le filestore.

$ sudo -u odoo /opt/odoo/venv/bin/python /opt/odoo/odoo/odoo-bin db -c /etc/odoo/odoo.conf dump ma_base /var/backups/odoo/ma_base.zip
INFO ? odoo.modules.db: DUMP DB: ma_base format zip with filestore
$ sudo -u odoo /opt/odoo/venv/bin/python /opt/odoo/odoo/odoo-bin db -c /etc/odoo/odoo.conf dump --format dump ma_base /var/backups/odoo/ma_base.dump
INFO ? odoo.modules.db: DUMP DB: ma_base format dump with filestore

La seconde ligne de journal dit « with filestore », mais le fichier n'en contient pas : le format dump n'est qu'un pg_dump --format=c (odoo/modules/db.py:610-613). Place les options avant le nom de la base : glissée entre le nom et le chemin, une option fait échouer la commande (dump ma_base --format dump fichier → error: unrecognized arguments: fichier).

Dans le zip, Odoo copie le filestore puis lance pg_dump (odoo/modules/db.py:587-603). Une pièce jointe créée entre les deux est dans le SQL sans son fichier. Sur une base au repos, c'est sans effet ; sur une production active la nuit (tâches planifiées, courriels entrants), c'est une raison de préférer la troisième voie, qui fait l'inverse.

Vers la sortie standard, --format et --no-filestore sont ignorés

Sans chemin (ou avec -), db dump écrit sur la sortie standard, pratique pour compresser ou envoyer à la volée. Mais cette branche appelle la fonction sans ses options (odoo/cli/db.py:247-249) : tu reçois toujours le zip complet.

$ odoo-bin db -c odoo.conf dump --format dump ma_base - > ma_base.dump
INFO ? odoo.modules.db: DUMP DB: ma_base format zip with filestore
$ file ma_base.dump
ma_base.dump: Zip archive data, at least v2.0 to extract, compression method=deflate

Même chose avec --no-filestore : 13,7 Mo et 566 entrées au lieu de 2,8 Mo. Le code est le même dans la branche 19.0. Donne toujours un chemin de fichier quand tu passes une option.

4. Troisième voie : pg_dump -Fc et le filestore à part

C'est la voie des sauvegardes planifiées : les outils de PostgreSQL pour la base, une copie de dossier pour le filestore, chacun dans le format qui lui convient. Toujours dans cet ordre, la base d'abord :

$ sudo -u odoo pg_dump --format=custom --no-owner --file=/var/backups/odoo/ma_base.dump ma_base
$ sudo -u odoo tar -C /opt/odoo/data/filestore -czf /var/backups/odoo/ma_base.filestore.tar.gz ma_base

0,4 s et 6,1 Mo pour la base, 0,2 s et 10,9 Mo pour le filestore sur la démonstration. Le format personnalisé (-Fc) est compressé et se relit avec pg_restore, qui sait restaurer une seule table ou lister le contenu ; --no-owner fait comme Odoo et permet de recharger avec un autre rôle. Pourquoi la base d'abord : un fichier ajouté au filestore pendant l'opération sera en trop dans l'archive, sans conséquence. Dans l'ordre inverse, la base citerait un fichier absent de l'archive.

Avec sudo -u odoo, pg_dump se connecte par la socket locale avec l'authentification peer du serveur décrit en prérequis : pas de mot de passe à écrire dans un script. Sur un PostgreSQL distant, utilise un fichier ~/.pgpass en 600 plutôt qu'une variable d'environnement.

5. Restaurer : copie ou base déplacée

Ce que demande le gestionnaire

La fenêtre Restore Database (figure plus haut) prend un fichier, un nom, la case Neutralize, et pose une question : This database is a copy (choix par défaut) ou This database was moved. Elle envoie copy=true ou copy=false à /web/database/restore, qui appelle odoo.modules.db.restore (odoo/modules/db.py:616-669). La seule différence entre les deux réponses est une ligne : pour une copie, ir.config_parameter.init(force=True) régénère six paramètres (odoo/addons/base/models/ir_config_parameter.py:23-30) : les quatre du tableau, et les deux réglages anti-force brute base.login_cooldown_after et base.login_cooldown_duration, remis à 10 et 60 (à reprendre si tu les avais changés). L'identifiant de base compte : c'est lui qu'Odoo envoie à son serveur de notifications avec le nombre d'utilisateurs et l'URL (tâche « Publisher: Update Notification », addons/mail/models/update.py:25-66), et c'est lui qui distingue deux bases auprès des services en ligne. D'où la règle :

  • « was moved » quand la base restaurée remplace l'originale : nouveau serveur, retour arrière après incident. L'identité est conservée, la base reprend sa place.
  • « is a copy » dès que l'originale continue de tourner à côté : test, formation, recette.

L'URL remise à http://localhost:<port du serveur> ne reste pas : à la connexion suivante d'un administrateur, Odoo l'écrit d'après l'adresse utilisée, sauf si web.base.url.freeze est vrai (odoo/addons/base/models/res_users.py:851-861).

« This database is a copy » ne coupe ni les tâches planifiées ni les courriels

Le tableau le montre : la copie change d'identité, mais garde ses 21 actions planifiées et son serveur sortant de production. Les tâches en retard (ici presque toutes, la sauvegarde datant de plusieurs jours) partent au premier passage du planificateur, et un serveur lancé sans db_name les exécute sur toutes les bases de son rôle, filtre ou pas (odoo/service/server.py:112-114). File d'attente des courriels, relances, envois de factures : la copie parle au monde réel. Une base remise par pg_restore est dans le même cas dès sa création, avant même ta commande neutralize : restaure-la sur une machine sans service Odoo, ou sur un serveur dont le fichier de configuration fixe db_name. Pour une base de test, coche Neutralize (ou -n en ligne de commande) ; le détail de ce qu'elle coupe est dans Copier la prod en base de test, et le fonctionnement du planificateur dans L'action planifiée ne s'exécute pas en Odoo 20.

Le gestionnaire ne restaure plus un .dump

Le gestionnaire propose de produire un fichier « pg_dump custom format », mais en 20 il ne sait plus le relire : restore ouvre le fichier comme un zip, sans autre branche.

$ curl -s -o reponse.html -w "%{http_code}\n" -F master_pwd='…' -F backup_file=@ma_base.dump \
    -F name=ma_base_essai -F copy=true http://localhost:8069/web/database/restore
422
$ grep -o 'Could not restore[^<]*' reponse.html
Could not restore database. File is not a zip file
$ psql -d ma_base_essai -Atc "select count(*) from pg_tables where schemaname = 'public'"
0

Après l'échec, une base vide porte déjà le nom choisi

La base est créée avant l'ouverture du fichier (odoo/modules/db.py:628-632). Elle reste, vide, et un nouvel essai sous le même nom répond « Database 'ma_base_essai' already exists ». Supprime-la (odoo-bin db drop ou bouton Delete) avant de recommencer. En 19, le même formulaire passait un fichier non zip à pg_restore ; en 20, un .dump se restaure à la main (plus bas). La ligne de commande, elle, contrôle le format avant de créer quoi que ce soit : db load ma_base_x ma_base.dump répond « Not a zipped dump file, use `pg_restore` to restore raw dumps… » et aucune base n'apparaît.

En ligne de commande : odoo-bin db load

Pour un zip, db load fait la même chose que le gestionnaire, avec la copie par défaut, --move pour une base déplacée et -n pour neutraliser. Restauration de la production à côté de l'originale, identité conservée :

$ sudo -u odoo /opt/odoo/venv/bin/python /opt/odoo/odoo/odoo-bin db -c /etc/odoo/odoo.conf load --move ma_base_retour ma_base.zip
Restoring ma_base.zip...
INFO ? odoo.modules.db: RESTORING DB: ma_base_retour
INFO ma_base_retour odoo.modules.db: RESTORE DB: ma_base_retour

Six secondes ici ; uuid, secret, date de création et URL identiques à la source, 564 fichiers dans filestore/ma_base_retour. Restaurer sous un autre nom puis échanger, plutôt qu'écraser la base en place avec -f, garde l'originale tant que la restauration n'est pas contrôlée ; l'échange se fait service arrêté, en deux renommages qui déplacent aussi le filestore : db rename ma_base ma_base_avant puis db rename ma_base_retour ma_base.

À la main : createdb, pg_restore, filestore

Pour la troisième voie, et pour tout fichier .dump. Trois règles : recréer la base comme Odoo la crée (template0, UTF-8, tri C), restaurer sans propriétaire, et poser le filestore sous le nouveau nom de base.

$ sudo -u odoo createdb -T template0 -E UTF8 --lc-collate=C ma_base_retour
$ sudo -u odoo pg_restore --no-owner -d ma_base_retour /var/backups/odoo/ma_base.dump
$ sudo -u odoo tar -C /opt/odoo/data/filestore -xzf /var/backups/odoo/ma_base.filestore.tar.gz \
    --transform 's/^ma_base/ma_base_retour/'
$ psql -d postgres -Atc "select datname, pg_get_userbyid(datdba), datcollate, datctype from pg_database where datname = 'ma_base_retour'"
ma_base_retour|odoo|C|fr_FR.UTF-8

4,4 s pour pg_restore, code de sortie 0. Sans -T template0 --lc-collate=C, la base hériterait du modèle du serveur (ici template1 en fr_FR.UTF-8) et les listes triées par nom changeraient d'ordre. Une base restaurée ainsi est une base déplacée : PostgreSQL recopie les paramètres tels quels, uuid compris. Pour en faire une copie de test, neutralise-la puis donne-lui une nouvelle identité, dans cet ordre (la neutralisation remplace le secret par dummysecret, base/data/neutralize.sql:35-38, la seconde commande le régénère) :

INFO ? odoo.cli.neutralize: Starting ma_base_retour database neutralization
INFO ? odoo.modules.neutralize: Neutralization finished
$ echo "env['ir.config_parameter'].init(force=True); env.cr.commit()" | odoo-bin shell -c odoo.conf -d ma_base_retour --no-http
$ psql -d ma_base_retour -Atc "select key, value from ir_config_parameter where key in ('database.uuid', 'database.is_neutralized')"

6. Vérifier une sauvegarde : la restaurer

Un fichier qui existe et qui a une taille raisonnable ne prouve rien : un data_dir mal réglé donne un filestore vide sans aucune erreur dans la base. La seule preuve, c'est une restauration, dans une base de test neutralisée, suivie d'un contrôle. Ce script le fait pour une sauvegarde de la troisième voie :

#!/usr/bin/env bash
# verifier-sauvegarde.sh : restaure une sauvegarde (dump + filestore) dans une base de test neutralisée, puis la contrôle.
set -euo pipefail
DUMP=$1; FILESTORE_TGZ=$2
CONF=${CONF:-/etc/odoo/odoo.conf}
DATA_DIR=${DATA_DIR:-/opt/odoo/data}
PY=${PY:-/opt/odoo/venv/bin/python}
ODOO_BIN=${ODOO_BIN:-/opt/odoo/odoo/odoo-bin}
TEST=${TEST:-ma_base_verif}
LOG=${LOG:-$DATA_DIR/verifier-sauvegarde.log}
[[ $TEST == *_verif ]] || { echo "refus : la base de contrôle doit finir par _verif" >&2; exit 2; }

# 0. Les fichiers se relisent-ils ?
pg_restore --list "$DUMP" > /dev/null
tar -tzf "$FILESTORE_TGZ" > /dev/null

# 1. Restaurer à côté, avec les réglages d'une base créée par Odoo
if psql -d postgres -Atc "SELECT 1 FROM pg_database WHERE datname = '$TEST'" | grep -q 1; then
    "$PY" "$ODOO_BIN" db -c "$CONF" drop "$TEST" 2>>"$LOG"      # base et filestore
fi
createdb -T template0 -E UTF8 --lc-collate=C "$TEST"
pg_restore --no-owner --exit-on-error -d "$TEST" "$DUMP"
mkdir -p "$DATA_DIR/filestore/$TEST"
tar -C "$DATA_DIR/filestore/$TEST" --strip-components=1 -xzf "$FILESTORE_TGZ"

# 2. En faire une copie de test : neutraliser, puis nouvelle identité
"$PY" "$ODOO_BIN" neutralize -c "$CONF" -d "$TEST" 2>>"$LOG"
echo "env['ir.config_parameter'].init(force=True); env.cr.commit()" |
    "$PY" "$ODOO_BIN" shell -c "$CONF" -d "$TEST" --no-http 2>>"$LOG"

# 3. Contrôler : chaque pièce jointe a-t-elle son fichier ?
RES=$("$PY" "$ODOO_BIN" shell -c "$CONF" -d "$TEST" --no-http 2>>"$LOG" <<'PY'
import os
fs = env['ir.attachment']._filestore()
env.cr.execute("SELECT DISTINCT store_fname FROM ir_attachment WHERE store_fname IS NOT NULL")
noms = [r[0] for r in env.cr.fetchall()]
manquants = [n for n in noms if not os.path.isfile(os.path.join(fs, n))]
mods = env['ir.module.module'].search_count([('state', '=', 'installed')])
print(f"modules installés : {mods} | fichiers attendus : {len(noms)} | manquants : {len(manquants)}")
print("VERDICT :", "OK" if not manquants else "FILESTORE INCOMPLET")
PY
)
echo "${RES:-ÉCHEC du contrôle : voir $LOG}"
grep -q "VERDICT : OK" <<< "$RES"

Le contrôle passe par SQL et non par search() : l'ORM écarte par défaut les pièces jointes liées à un champ, images des produits et des contacts comprises (ir_attachment.py:816-824). Sur la sauvegarde de la nuit, puis sur une archive de filestore incomplète :

$ sudo -u odoo ./verifier-sauvegarde.sh /var/backups/odoo/ma_base_2026-11-10_2048.dump /var/backups/odoo/ma_base_2026-11-10_2048.filestore.tar.gz
modules installés : 69 | fichiers attendus : 282 | manquants : 0
VERDICT : OK
$ echo $?
0
$ sudo -u odoo ./verifier-sauvegarde.sh /var/backups/odoo/ma_base_2026-11-10_2048.dump filestore-partiel.tar.gz
modules installés : 69 | fichiers attendus : 282 | manquants : 263
VERDICT : FILESTORE INCOMPLET
$ echo $?
1

Moins de sept secondes pour la démonstration. Le garde-fou du début refuse tout nom qui ne finit pas par _verif (TEST=ma_base → « refus : la base de contrôle doit finir par _verif », code 2) : le script supprime puis recrée cette base à chaque passage. Les messages d'Odoo vont dans $LOG.

Lance-le de préférence sur une autre machine que la production, ou sur un serveur qui fixe db_name : entre pg_restore et la neutralisation, la base restaurée est visible du planificateur d'un serveur qui n'en fixe pas (encadré de la section 5).

Compare le nombre de modules à celui du manifest.json si ta sauvegarde est un zip, et ouvre au moins une fois la base de contrôle dans un navigateur : un bandeau rouge signale qu'elle est neutralisée. Lance ce script chaque semaine sur la dernière sauvegarde, et à chaque changement de serveur, de version de PostgreSQL ou de script.

7. Planifier : script, rotation, copie hors du serveur

Le script

La troisième voie, une empreinte par fichier, une rotation et une copie vers une autre machine. Installé en /usr/local/bin/sauvegarde-odoo.sh, exécuté par le compte odoo :

#!/usr/bin/env bash
# Sauvegarde complète d'une base Odoo 20 : base PostgreSQL, puis filestore.
set -euo pipefail

BASE=${BASE:-ma_base}
DATA_DIR=${DATA_DIR:-/opt/odoo/data}          # data_dir du fichier de configuration
DEST=${DEST:-/var/backups/odoo}
GARDER_JOURS=${GARDER_JOURS:-14}
DISTANT=${DISTANT:-sauvegarde@autre-serveur:/srv/sauvegardes/odoo/}

H=$(date +%Y-%m-%d_%H%M)
P="$DEST/${BASE}_$H"
umask 077
# En cas d'échec, on ne laisse que des fichiers .part, que ni la rotation ni la copie ne prennent pour une sauvegarde.
trap 'echo "ÉCHEC de la sauvegarde $BASE" >&2' ERR

# 1. La base d'abord : un fichier ajouté ensuite sera en trop dans le filestore, jamais manquant.
pg_dump --format=custom --no-owner --file="$P.dump.part" "$BASE"
# 2. Le filestore ensuite ; tar sort en 1 si un fichier change pendant la lecture : ce n'est pas une erreur ici.
tar -C "$DATA_DIR/filestore" --warning=no-file-changed -czf "$P.filestore.tar.gz.part" "$BASE" || [ $? -eq 1 ]
mv "$P.dump.part" "$P.dump"
mv "$P.filestore.tar.gz.part" "$P.filestore.tar.gz"
# 3. Les empreintes, pour contrôler la copie distante.
(cd "$DEST" && sha256sum "${BASE}_$H.dump" "${BASE}_$H.filestore.tar.gz" > "${BASE}_$H.sha256")
# 4. La rotation : on efface ce qui a plus de GARDER_JOURS jours (sauvegardes de cette base seulement).
find "$DEST" -maxdepth 1 -name "${BASE}_20*" -mtime +"$GARDER_JOURS" -print -delete
# 5. La copie hors du serveur : sans --delete, l'autre côté garde sa propre rotation.
rsync -a --exclude='*.part' -e "ssh -o BatchMode=yes" "$DEST"/ "$DISTANT"

echo "sauvegarde $BASE terminée : $(du -ch "$P".dump "$P".filestore.tar.gz | tail -1 | cut -f1)"

Le script ne crée pas son dossier : /var/backups appartient à root. Une fois pour toutes, sudo install -d -o odoo -g odoo -m 700 /var/backups/odoo. La minuterie systemd

Deux fichiers dans /etc/systemd/system/. Le service, de type oneshot, lancé sous le compte odoo :

# odoo-sauvegarde.service
[Unit]
Description=Sauvegarde Odoo (base + filestore)
After=postgresql.service

[Service]
Type=oneshot
User=odoo
Environment=BASE=ma_base DATA_DIR=/opt/odoo/data DEST=/var/backups/odoo
ExecStart=/usr/local/bin/sauvegarde-odoo.sh
# odoo-sauvegarde.timer
[Unit]
Description=Sauvegarde Odoo chaque nuit

[Timer]
OnCalendar=*-*-* 02:30:00
RandomizedDelaySec=15min
Persistent=true

[Install]
WantedBy=timers.target

OnCalendar suit le fuseau horaire du serveur. Persistent=true rattrape une sauvegarde manquée parce que le serveur était éteint à l'heure dite. Avant de les installer, fais relire les deux fichiers par systemd ; il ne dit rien quand tout va bien, et signale par exemple un script absent :

Hors du serveur

Une sauvegarde rangée sur le même disque que la base ne protège que des erreurs de manipulation. La ligne rsync du script pousse les fichiers vers une autre machine, joignable par une clé SSH dédiée, sans mot de passe et limitée à ce dossier. Deux choix à faire en connaissance de cause :

  • Sans --delete, comme ici, une suppression ou un chiffrement malveillant sur le serveur ne se propage pas ; en contrepartie, l'autre machine applique sa propre rotation (la même ligne find, plus généreuse).
  • Mieux encore, inverser le sens : c'est la machine de sauvegarde qui vient chercher les fichiers, et le serveur Odoo n'a aucun accès en écriture chez elle. Un serveur compromis ne peut alors pas effacer ses propres sauvegardes.

Pour un gros filestore, archiver tout le dossier chaque nuit devient lourd. Puisque ses fichiers ne changent jamais (section 1), un rsync -a du dossier lui-même vers l'autre machine ne transfère que les nouveaux ; la base, elle, reste sauvegardée chaque nuit en entier.
