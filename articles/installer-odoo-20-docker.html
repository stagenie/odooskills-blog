Installer Odoo 20 avec Docker

Un fichier Compose, deux conteneurs (Odoo et PostgreSQL), un odoo.conf : Odoo 20 tourne sur un serveur Ubuntu en quelques minutes. Mais un fichier Compose écrit pour Odoo 19 démarre sans erreur… et ne répond jamais. On monte l'installation de zéro, et on passe par les trois pannes qui attendent ceux qui recopient un ancien tutoriel. L'article a été rejoué tel quel, commande par commande, sur un VPS neuf.

~12 minutes de lecture · niveau débutant · parcours Infrastructure

Ce que tu vas apprendre

La pile

Docker Engine depuis le dépôt officiel, l'image odoo:20.0 et PostgreSQL 17 dans un seul compose.yaml.

La configuration

Un odoo.conf monté dans le conteneur, les secrets hors du Compose, une base créée en ligne de commande.

Les pannes

Odoo muet sur son port, NoSectionError au démarrage, pare-feu contourné : le symptôme, la cause, le correctif.

Prérequis

  • Un serveur ou une machine virtuelle sous Ubuntu 24.04 LTS, accessible en SSH avec un compte root ou sudo. La démonstration tourne sur un petit VPS : 2 vCPU, 4 Go de mémoire, 40 Go de disque.
  • Environ 5 Go d'espace disque : l'image Odoo occupe 3,5 Go une fois décompressée, celle de PostgreSQL 650 Mo.
  • Aucune installation préalable de Python ni de PostgreSQL sur l'hôte : tout vit dans les conteneurs.

Les commandes sont lancées en root (sudo -i). Tu préfères une installation « à la main », sans conteneur, pour développer ? Lis plutôt Installer Odoo 20 sur Ubuntu et le lancer dans PyCharm.

Vue d'ensemble

L'installation tient dans un dossier, /opt/odoo20, qui contient quatre choses :

ÉlémentRôle
compose.yamldécrit les deux conteneurs, leurs volumes et le port publié
.envle mot de passe PostgreSQL, lu par Compose, jamais écrit dans le compose.yaml
config/odoo.confla configuration d'Odoo, montée en lecture seule dans le conteneur
addons/tes modules, montés sur /mnt/extra-addons

Les données, elles, ne sont pas dans le dossier : la base PostgreSQL et le filestore d'Odoo (pièces jointes, images) vivent dans deux volumes nommés : des espaces de stockage gérés par Docker, qui survivent aux conteneurs. Supprimer ou recréer un conteneur ne les efface pas ; seule une commande explicite (docker compose down -v) le fait.

1. Installer Docker Engine

Le paquet docker.io d'Ubuntu existe, mais il suit le rythme d'Ubuntu, pas celui de Docker. On installe donc Docker Engine et le greffon Compose depuis le dépôt officiel de Docker :

apt-get update
apt-get install -y ca-certificates curl
install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
chmod a+r /etc/apt/keyrings/docker.asc
nano /etc/apt/sources.list.d/docker.sources
nano en trois gestes. nano ouvre (ou crée) le fichier. Colle le contenu montré (clic droit, ou Ctrl+Maj+V dans la plupart des terminaux), enregistre avec Ctrl+O puis Entrée, quitte avec Ctrl+X.

Contenu du fichier : la source des paquets Docker. noble est le nom de code d'Ubuntu 24.04.

Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: noble
Components: stable
Signed-By: /etc/apt/keyrings/docker.asc

Puis l'installation proprement dite :

apt-get update
apt-get install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin

Vérification : les deux versions, le service actif et le conteneur de test.

docker --version
docker compose version
systemctl is-active docker
docker run --rm hello-world
Docker version 29.8.1, build 4a63305 Docker Compose version v5.5.1 active ... Hello from Docker! This message shows that your installation appears to be working correctly.

Note bien la syntaxe : docker compose, avec une espace. L'ancien exécutable docker-compose (avec un tiret) n'est plus maintenu.

2. Le dossier du projet et les secrets

Deux secrets sont nécessaires : le mot de passe du rôle PostgreSQL odoo, et le mot de passe maître d'Odoo, celui qui protège le gestionnaire de bases (créer, dupliquer, supprimer une base). On les tire au sort avec openssl plutôt que de les inventer :

mkdir -p /opt/odoo20/config /opt/odoo20/addons
cd /opt/odoo20
openssl rand -hex 24     # mot de passe PostgreSQL
openssl rand -hex 16     # mot de passe maître d'Odoo

Chaque commande affiche une suite de caractères aléatoires : copie les deux dans ton gestionnaire de mots de passe. Le mot de passe PostgreSQL va dans un fichier .env :

nano .env
POSTGRES_PASSWORD=MOT_DE_PASSE_POSTGRES

Remplace MOT_DE_PASSE_POSTGRES par la première valeur, enregistre, puis réserve le fichier à root : chmod 600 .env.

Compose lit automatiquement le fichier .env posé à côté du compose.yaml : la variable ${POSTGRES_PASSWORD} y sera remplacée. Si le dossier est versionné avec Git, ajoute .env au .gitignore.

Une seule fois

PostgreSQL ne lit POSTGRES_PASSWORD qu'à la toute première initialisation de son volume. Modifier .env plus tard ne change pas le mot de passe de la base : Odoo échouera à s'y connecter. Une fois la pile démarrée, change le mot de passe dans PostgreSQL et dans les deux fichiers, ou pas du tout.

3. Le fichier odoo.conf

L'image officielle lit sa configuration dans /etc/odoo/odoo.conf. On lui fournit la nôtre :

nano config/odoo.conf
[options]
; Odoo 20 écoute sur 127.0.0.1 par défaut : obligatoire dans un conteneur
http_interface = 0.0.0.0
proxy_mode = True
admin_passwd = MOT_DE_PASSE_MAITRE
db_host = db
db_port = 5432
db_user = odoo
db_password = MOT_DE_PASSE_POSTGRES
list_db = True
addons_path = /mnt/extra-addons
data_dir = /var/lib/odoo

Remplace MOT_DE_PASSE_MAITRE par la seconde valeur tirée à l'étape 2, et MOT_DE_PASSE_POSTGRES par la première, la même que dans .env : c'est avec elle qu'Odoo se connecte à la base. Enregistre, puis règle les droits :

chmod 755 config
chown root:101 config/odoo.conf
chmod 640 config/odoo.conf

Quatre lignes du fichier méritent une explication :

  • http_interface = 0.0.0.0 : la ligne que les tutoriels Odoo 19 n'avaient pas besoin d'écrire. Sans elle, Odoo 20 n'écoute que sur l'interface locale du conteneur, et rien ne l'atteint de l'extérieur (voir la panne n° 1).
  • proxy_mode = True : prépare le passage derrière un reverse proxy, un serveur web (Nginx) placé devant Odoo, qui porte le HTTPS et transmet l'adresse réelle du visiteur.
  • db_host = db : db est le nom du service PostgreSQL dans le Compose ; Docker le résout en adresse IP sur le réseau interne.
  • addons_path = /mnt/extra-addons : ton dossier de modules. Les modules standard d'Odoo sont ajoutés d'office, pas besoin de les lister.

Et les droits ? Dans l'image, Odoo tourne sous l'utilisateur odoo (uid 100, groupe 101), pas sous root. Le fichier doit donc être lisible par le groupe 101, sans l'être par tout le monde puisqu'il contient deux mots de passe. C'est l'objet des trois dernières commandes (voir la panne n° 2). Un ls -l config/odoo.conf affiche alors root messagebus : messagebus est simplement le nom que l'hôte Ubuntu donne au groupe 101, sans rapport avec Odoo.

4. Le fichier compose.yaml

nano compose.yaml
services:
  db:
    image: postgres:17
    environment:
      POSTGRES_DB: postgres
      POSTGRES_USER: odoo
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
    volumes:
      - db-data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U odoo"]
      interval: 10s
      timeout: 5s
      retries: 5
    restart: unless-stopped

  odoo:
    image: odoo:20.0
    depends_on:
      db:
        condition: service_healthy
    ports:
      - "127.0.0.1:8069:8069"
    volumes:
      - odoo-data:/var/lib/odoo
      - ./config:/etc/odoo:ro
      - ./addons:/mnt/extra-addons
    restart: unless-stopped

volumes:
  db-data:
  odoo-data:
  • postgres:17 : Odoo 20 exige PostgreSQL 16 au minimum. Face à un postgres:13 ou postgres:14 recopié d'un vieux tutoriel, il ne s'arrête pas : il émet un simple avertissement et démarre, mais certaines contraintes de la base (NULLS NOT DISTINCT, apparu en PostgreSQL 15) sont perdues en silence. Ne pas s'y fier.
  • healthcheck + condition: service_healthy : le healthcheck est un test de santé que Docker lance toutes les 10 secondes (pg_isready) ; grâce à lui, Odoo attend que PostgreSQL accepte les connexions avant de démarrer, au lieu de simplement attendre que son conteneur existe.
  • "127.0.0.1:8069:8069" : le port n'est publié que sur la boucle locale du serveur. C'est voulu : on n'expose pas Odoo en HTTP clair sur Internet (voir la panne n° 3).
  • ./config:/etc/odoo:ro : le dossier de configuration, monté en lecture seule.
  • Aucun ports: sur db : PostgreSQL n'est pas publié sur l'hôte ; seuls les conteneurs de ce Compose y accèdent.

Avant d'aller plus loin, fais valider le fichier par Compose : docker compose config -q ne doit rien afficher.

5. Créer la première base

On démarre d'abord PostgreSQL seul, puis on crée la base avec un conteneur Odoo à usage unique (run --rm) : installation du module base, chargement du français, arrêt.

docker compose up -d db
docker compose run --rm odoo odoo -d demo20 -i base --load-language=fr_FR --stop-after-init
... INFO demo20 odoo.modules.loading: Modules loaded. ... INFO demo20 odoo.registry: Registry loaded in 18.734s

Entre 20 et 35 secondes sur le VPS de démonstration. Le premier lancement télécharge les deux images : compte plutôt quelques minutes (850 Mo à télécharger pour Odoo, 170 Mo pour PostgreSQL).

Et les données de démonstration ?

Cette base est vide : 16 modules installés, aucune donnée de démonstration. Elles ne se chargent que si on les demande avec --with-demo. Pour une base d'essai avec clients, articles et devis fictifs, ajoute l'option à la commande ci-dessus.

Tu peux aussi créer la base depuis le navigateur, avec l'écran de création de base et le mot de passe maître. La ligne de commande a un avantage : elle se rejoue à l'identique, dans un script ou une documentation d'exploitation.

6. Démarrer et vérifier

docker compose up -d
docker compose ps
docker compose logs odoo | grep "HTTP service running"
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8069/web/login
NAME IMAGE COMMAND SERVICE CREATED STATUS PORTS odoo20-db-1 postgres:17 "docker-entrypoint.s…" db 51 seconds ago Up 50 seconds (healthy) 5432/tcp odoo20-odoo-1 odoo:20.0 "/entrypoint.sh odoo" odoo 16 seconds ago Up 15 seconds 127.0.0.1:8069->8069/tcp, 8071-8072/tcp odoo-1 | ... INFO ? odoo.service.server: HTTP service running on 0.0.0.0:8069 200

Deux indices à lire : (healthy) sur la base, et surtout 0.0.0.0:8069 dans le journal d'Odoo. Si tu y lis 127.0.0.1:8069, la ligne http_interface n'a pas été prise en compte.

La version exacte se lit sans navigateur :

curl -s http://127.0.0.1:8069/web/webclient/version_info \
     -H 'Content-Type: application/json' -d '{"jsonrpc":"2.0","params":{}}'
{"jsonrpc": "2.0", "id": null, "result": {"server_version": "20.0-20260926", "server_version_info": [20, 0, 0, "final", 0, ""], "server_serie": "20.0"}}

Ouvrir Odoo depuis ton poste

Le port n'étant publié que sur la boucle locale du serveur, on y accède par un tunnel SSH, lancé depuis ton poste :

ssh -N -L 8069:127.0.0.1:8069 root@ADRESSE_DU_SERVEUR

Tant que la commande tourne, http://localhost:8069 sur ton poste mène à l'Odoo du serveur. La page /web/database/manager liste la base créée à l'étape 5 :

Connecte-toi à demo20 avec l'identifiant admin et le mot de passe admin, puis change ce mot de passe immédiatement (avatar en haut à droite › Mes préférences › onglet Sécurité › Modifier le mot de passe). L'écran Applications confirme une Odoo 20 Community prête à recevoir ses modules :

Mettre à jour Odoo

L'image odoo:20.0 est reconstruite régulièrement avec les correctifs de la branche 20.0. Mettre à jour, c'est sauvegarder la base, récupérer la nouvelle image, puis mettre à jour les modules de la base avant de relancer le serveur :

docker compose exec -T db pg_dump -U odoo -Fc demo20 > /root/demo20-avant-maj.dump
docker compose pull odoo
docker compose stop odoo
docker compose run --rm odoo odoo -d demo20 -u all --stop-after-init
docker compose up -d
... INFO demo20 odoo.modules.loading: Modules loaded. ... INFO demo20 odoo.registry: Registry loaded in 14.048s

Le tag 20.0 bouge à chaque publication. En production, préfère un tag daté, comme odoo:20.0-20260926 : tu choisis le moment de la mise à jour, et revenir en arrière consiste à remettre l'ancien tag et à restaurer la sauvegarde. Le pg_dump ci-dessus couvre la base (1,3 Mo pour une base neuve) ; le filestore, dans le volume odoo-data, se sauvegarde à part. Une vraie politique de sauvegarde, testée par une restauration, sort du cadre de cet article.

Les trois pannes, reproduites

Chacune a été provoquée volontairement sur le serveur de démonstration. Aucune ne désigne clairement sa cause.

Panne n° 1 : Odoo démarre, mais le port ne répond jamais

Symptôme : un Compose « à l'ancienne », avec ports: - "8069:8069" et sans odoo.conf. Les conteneurs sont Up, aucune erreur, mais le navigateur tourne dans le vide et curl échoue :

odoo-1 | ... INFO ? odoo.service.server: HTTP service running on 127.0.0.1:8069 $ curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8069/web/login 000

Cause : depuis Odoo 20, l'option --http-interface vaut 127.0.0.1 par défaut (elle valait 0.0.0.0 en Odoo 19). Dans un conteneur, « 127.0.0.1 » désigne le conteneur lui-même : la redirection de port de Docker arrive sur une autre interface, où personne n'écoute. L'image officielle ne corrige pas ce défaut.

Correctif : http_interface = 0.0.0.0 dans odoo.conf, ou, sans fichier de configuration, command: -- --http-interface=0.0.0.0 sur le service odoo. Le journal affiche alors HTTP service running on 0.0.0.0:8069, et la même requête répond 200.

Panne n° 2 : NoSectionError: No section: 'options'

Symptôme : le conteneur Odoo s'arrête aussitôt, avec une trace Python qui vient d'un script d'attente de la base :

File "/usr/local/bin/wait-for-psql.py", line 25, in <module> config_options = { k:v for k,v in config.items('options')} configparser.NoSectionError: No section: 'options'

Cause : le fichier contient pourtant bien [options]. Mais le dossier config/ est en droits 700, réservé à root : c'est le cas si ta session utilise un umask 077 (réglage de durcissement courant) ou après un chmod 700 config. L'utilisateur odoo du conteneur ne peut pas lire le fichier, et le lecteur de configuration Python, au lieu de se plaindre d'un fichier illisible, le traite comme vide.

Correctif : chmod 755 config, puis chown root:101 et chmod 640 sur odoo.conf. Pour vérifier l'identité de l'utilisateur de l'image : docker compose run --rm --entrypoint id odoo affiche uid=100(odoo) gid=101(odoo).

Panne n° 3 : le pare-feu est actif, et Odoo reste joignable depuis Internet

Symptôme : UFW refuse tout ce qui entre sauf SSH, et pourtant un port publié en "8069:8069" répond depuis n'importe où :

$ ufw status verbose # extrait Status: active Default: deny (incoming), allow (outgoing), deny (routed) 22/tcp (OpenSSH) ALLOW IN Anywhere # depuis un autre poste : $ curl -s -o /dev/null -w "%{http_code}\n" http://ADRESSE_DU_SERVEUR:8069/web/login 200

Cause : Docker écrit ses propres règles de pare-feu (redirection d'adresse et routage vers les conteneurs) ; le trafic vers un port publié n'emprunte jamais la chaîne que filtre UFW. Avec le gestionnaire de bases ouvert, c'est une porte d'entrée sur tes données.

Correctif : publier sur la boucle locale, "127.0.0.1:8069:8069", comme dans le Compose de cet article. Le même test depuis l'extérieur échoue alors (000). L'accès public passera par un reverse proxy en HTTPS.

Ce qui change par rapport à Odoo 19

  • --http-interface : 127.0.0.1 par défaut au lieu de 0.0.0.0. C'est la panne n° 1.
  • PostgreSQL 16 minimum, Python 3.12 à 3.14 : l'image embarque Ubuntu 24.04 et Python 3.12.3.
  • Le reste de l'image (volumes /var/lib/odoo et /mnt/extra-addons, configuration dans /etc/odoo/odoo.conf, utilisateur odoo) ne change pas : un Compose Odoo 19 se porte en changeant le tag et en ajoutant http_interface, avec PostgreSQL 16 au minimum.

Et pour la production ?

Cette installation est saine, mais elle n'est pas encore une production. Il manque :

  • un reverse proxy Nginx avec HTTPS (certificat Let's Encrypt), les routes /websocket et la redirection HTTP vers HTTPS ;
  • des workers dimensionnés sur la machine et des limites de mémoire ;
  • un gestionnaire de bases fermé (list_db = False) une fois la base de production créée ;
  • la sauvegarde de la base et du volume odoo-data, et surtout un test de restauration ;
  • une procédure de mise à jour avec retour arrière par tag daté.

C'est le programme de l'ebook Déployer Odoo en production : VPS, sécurité, PostgreSQL, systemd, Nginx et HTTPS, plusieurs instances et plusieurs versions sur un même serveur, Docker, sauvegardes, supervision et mises à jour, chaque commande jouée sur un vrai serveur. Son édition Odoo 20 est en cours de rédaction, sur le serveur qui a servi à cet article.

Récapitulatif

  • Docker Engine et docker compose depuis le dépôt officiel de Docker, pas le paquet docker.io.
  • odoo:20.0 + postgres:17 (16 minimum), avec un healthcheck sur la base.
  • Secrets tirés au sort avec openssl rand : PostgreSQL dans .env (droits 600) et dans odoo.conf, mot de passe maître dans odoo.conf.
  • http_interface = 0.0.0.0 dans odoo.conf, sinon Odoo 20 reste muet dans son conteneur.
  • odoo.conf lisible par le groupe 101 du conteneur : dossier 755, fichier root:101 en 640.
  • Port publié sur 127.0.0.1 seulement : Docker passe outre UFW.
  • Base créée par docker compose run --rm odoo odoo -d … -i base ; mise à jour = pg_dump, pull, puis -u all.
