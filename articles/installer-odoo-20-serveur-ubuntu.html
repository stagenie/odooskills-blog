Installer Odoo 20 sur un serveur Ubuntu

Un Odoo de production n'est pas un Odoo de développement lancé sur un serveur. Il tourne sous son propre utilisateur, démarre avec la machine, se relance tout seul s'il tombe, répartit la charge entre plusieurs processus et n'expose rien directement à Internet. On le monte sur un VPS Ubuntu 24.04, sans conteneur, en moins de dix minutes. Chaque commande a été rejouée telle quelle sur le serveur de démonstration.

~13 minutes de lecture · niveau intermédiaire · parcours Infrastructure

Ce que tu vas apprendre

Le socle

Paquets système, PostgreSQL 16, wkhtmltopdf, un utilisateur odoo et les sources 20.0 dans un environnement Python dédié.

La configuration

Un odoo.conf de production : workers, limites de mémoire, gestionnaire de bases fermé, journal dans un fichier.

Le service

Une unité systemd : démarrage au boot, relance automatique, arrêt propre des processus.

Prérequis

  • Un VPS sous Ubuntu 24.04 LTS, accessible en SSH en root (ou avec sudo -i). La démonstration tourne sur 2 vCPU, 4 Go de mémoire et 40 Go de disque.
  • Environ 2 Go d'espace disque : 1,4 Go pour les sources, 260 Mo pour l'environnement Python.
  • Un serveur propre : pas d'autre service sur les ports 8069 et 8072.

Tu cherches à installer Odoo sur ton poste pour développer ? C'est l'objet de Installer Odoo 20 sur Ubuntu et le lancer dans PyCharm. Tu préfères les conteneurs ? Lis Installer Odoo 20 avec Docker.

Odoo n'écoute que sur 127.0.0.1 : ports 8069 (pages et API) et 8072 (temps réel, websocket). L'accès public passera par un reverse proxy Nginx en HTTPS, étape suivante de la série.

1. Les paquets système et PostgreSQL

Ubuntu 24.04 convient exactement : il fournit Python 3.12 et PostgreSQL 16, les deux minimums d'Odoo 20. Aucun dépôt externe n'est nécessaire.

apt-get update
apt-get install -y git curl ca-certificates nano python3-venv python3-dev build-essential \
    libpq-dev libldap2-dev libsasl2-dev postgresql

python3 --version
psql --version
systemctl is-active postgresql
Python 3.12.3 psql (PostgreSQL) 16.15 (Ubuntu 16.15-0ubuntu0.24.04.1) active

git, curl et l'éditeur nano sont souvent déjà présents ; les nommer ne coûte rien sur une image minimale. build-essential, python3-dev et les trois bibliothèques -dev permettent à pip de compiler une dépendance quand aucun paquet précompilé ne convient, typiquement le pilote PostgreSQL (psycopg2) et le client LDAP (python-ldap). Compte un peu plus d'une minute.

2. wkhtmltopdf, pour les rapports PDF

Pour ses devis et factures en PDF, Odoo 20 utilise par défaut wkhtmltopdf. Le paquet d'Ubuntu est compilé sans le « patch Qt » et produit des PDF sans en-tête ni pied de page. On installe celui du projet wkhtmltopdf, publié pour Ubuntu 22.04 (« jammy ») : il n'existe pas de paquet 24.04, et celui-ci s'y installe sans problème.

apt-get install -y fontconfig libfontconfig1 libjpeg-turbo8 libxrender1 xfonts-75dpi xfonts-base
curl -fsSL -o /tmp/wkhtmltox.deb \
    https://github.com/wkhtmltopdf/packaging/releases/download/0.12.6.1-3/wkhtmltox_0.12.6.1-3.jammy_amd64.deb
apt-get install -y /tmp/wkhtmltox.deb
wkhtmltopdf --version
wkhtmltopdf 0.12.6.1 (with patched qt)

La mention (with patched qt) est celle qu'il faut voir. Sans elle, les rapports sortiront sans en-tête ni pied de page.

3. L'utilisateur odoo et son rôle PostgreSQL

Odoo ne tourne jamais en root. On crée un utilisateur système dont le dossier personnel sera /opt/odoo, puis un rôle PostgreSQL du même nom :

useradd --system --create-home --home-dir /opt/odoo --shell /bin/bash odoo
sudo -u postgres createuser --createdb odoo
sudo -u postgres psql -Atc "select rolname, rolcreatedb, rolsuper from pg_roles where rolname='odoo'"
odoo|t|f

Le rôle peut créer des bases (t) mais n'est pas super-utilisateur (f). Et il n'a pas de mot de passe : PostgreSQL, sur Ubuntu, reconnaît l'utilisateur système qui se connecte par la socket locale (authentification peer). Le processus Odoo tournant sous l'utilisateur odoo, il se connecte au rôle odoo sans secret à stocker dans la configuration.

4. Les sources et l'environnement Python

Tout se fait en tant qu'utilisateur odoo (sudo -u odoo), pour que les fichiers lui appartiennent. --depth 1 ne récupère que le dernier état de la branche 20.0, pas tout l'historique :

sudo -u odoo git clone --depth 1 --branch 20.0 https://github.com/odoo/odoo.git /opt/odoo/odoo

sudo -u odoo python3 -m venv /opt/odoo/venv
sudo -u odoo /opt/odoo/venv/bin/pip install --upgrade pip wheel
sudo -u odoo /opt/odoo/venv/bin/pip install -r /opt/odoo/odoo/requirements.txt
sudo -u odoo /opt/odoo/venv/bin/pip install phonenumbers

Sur le VPS de démonstration : 2 min 30 pour le clone (1,4 Go), 1 min 20 pour les dépendances (260 Mo). La dernière ligne n'est pas une option : phonenumbers ne figure pas dans requirements.txt, et sans lui l'activation de l'application Ventes échoue sur une dépendance manquante.

Pour noter la version exacte installée (utile le jour d'une mise à jour ou d'un incident) :

sudo -u odoo git -C /opt/odoo/odoo log -1 --format='%h %cd' --date=short
24b59ae7 2026-09-30

fatal: detected dubious ownership in repository

La même commande lancée en root, sans sudo -u odoo, est refusée par Git : le dépôt appartient à un autre utilisateur. Ne contourne pas avec git config --global --add safe.directory comme le suggère le message : lance simplement Git sous l'utilisateur propriétaire.

5. Le fichier de configuration

sudo -u odoo mkdir -p /opt/odoo/custom-addons /opt/odoo/data
mkdir -p /etc/odoo /var/log/odoo && chown odoo:odoo /var/log/odoo
openssl rand -hex 16     # mot de passe maître : copie-le dans ton gestionnaire de mots de passe
nano /etc/odoo/odoo.conf
nano en trois gestes. nano ouvre (ou crée) le fichier. Colle le contenu montré (clic droit, ou Ctrl+Maj+V dans la plupart des terminaux), enregistre avec Ctrl+O puis Entrée, quitte avec Ctrl+X. 
[options]
admin_passwd = MOT_DE_PASSE_MAITRE
db_user = odoo
dbfilter = ^prod$
list_db = False
addons_path = /opt/odoo/odoo/addons,/opt/odoo/custom-addons
data_dir = /opt/odoo/data
logfile = /var/log/odoo/odoo.log

http_interface = 127.0.0.1
http_port = 8069
gevent_port = 8072
proxy_mode = False

workers = 5
max_cron_threads = 1
limit_memory_soft = 671088640
limit_memory_hard = 805306368
limit_time_cpu = 60
limit_time_real = 120

Remplace MOT_DE_PASSE_MAITRE par la valeur tirée juste avant, enregistre, puis rends le fichier lisible par Odoo et par personne d'autre :

chown root:odoo /etc/odoo/odoo.conf && chmod 640 /etc/odoo/odoo.conf

Le fichier se lit en trois blocs.

Bases et chemins

  • admin_passwd : le mot de passe maître, tiré au sort. Il ne sert qu'aux opérations du gestionnaire de bases.
  • db_user = odoo, sans db_host ni db_password : connexion par la socket locale, authentification peer.
  • dbfilter = ^prod$ et list_db = False : cette instance ne sert qu'une base, prod, et le gestionnaire de bases (création, duplication, suppression, restauration depuis le navigateur) est fermé. Un serveur de production ne doit pas offrir ces boutons au monde.
  • logfile : le journal va dans un fichier, et non dans le journal système.

Réseau

  • http_interface = 127.0.0.1 : c'est déjà la valeur par défaut d'Odoo 20 ; l'écrire évite toute surprise. Odoo n'est joignable que depuis le serveur lui-même.
  • gevent_port = 8072 : le port du service temps réel (notifications, discussions), qui n'existe qu'avec des workers.
  • proxy_mode = False : passera à True en même temps que la pose de Nginx.

Processus et garde-fous

  • workers = 5 : cinq processus pour les requêtes web, selon la règle (2 × nombre de vCPU) + 1, soit 5 sur 2 vCPU. C'est un plafond dicté par le processeur ; vérifie aussi la mémoire : 5 workers + 1 cron à 640 Mo chacun, c'est près de 4 Go dans le pire cas. Au repos, la machine n'en utilise que 770 Mo, mais sur un serveur chargé de 4 Go, 3 workers sont plus prudents.
  • max_cron_threads = 1 : un processus de plus, dédié aux tâches planifiées. Le défaut est 2 ; un seul suffit sur 4 Go.
  • limit_memory_soft (640 Mo) : un worker qui dépasse ce seuil termine sa requête puis est remplacé. limit_memory_hard (768 Mo) : plafond imposé par le système au processus ; toute allocation au-delà échoue, et la requête en cours plante (MemoryError). Les deux mesurent la mémoire virtuelle, pas la mémoire physique réellement occupée.
  • limit_time_cpu / limit_time_real : une requête est interrompue après 60 s de calcul ou 120 s au total.

6. Créer la base prod

Le gestionnaire de bases étant fermé, la base se crée en ligne de commande, toujours sous l'utilisateur odoo :

sudo -u odoo /opt/odoo/venv/bin/python /opt/odoo/odoo/odoo-bin -c /etc/odoo/odoo.conf \
    -d prod -i base --load-language=fr_FR --stop-after-init --no-http
tail -2 /var/log/odoo/odoo.log
sudo -u postgres psql -d prod -Atc "select count(*) from ir_module_module where state='installed'"
... INFO prod odoo.addons.bus.websocket: Disconnecting 0 websockets ... INFO prod odoo.service.server.PreforkServer: Stopping workers gracefully 16

Environ 25 secondes. La commande n'affiche rien à l'écran : avec logfile, tout part dans le journal. Les deux lignes du journal montrent l'arrêt normal de --stop-after-init, et la base compte 16 modules installés. La base est vide : aucune donnée de démonstration (il faudrait --with-demo), ce qui est ce qu'on veut en production.

Le journal contient aussi un avertissement invalid addons directory '/opt/odoo/custom-addons', skipped : le dossier est vide, Odoo l'ignore. Il disparaîtra au premier module que tu y déposeras.

Pourquoi --no-http ? OSError: [Errno 98] Address already in use

Avec workers supérieur à 0, odoo-bin ouvre le port 8069 avant même de traiter -i ou -u, y compris avec --stop-after-init. Lancée pendant que le service tourne, la commande s'arrête aussitôt sur cette erreur. Ici le service n'existe pas encore, mais garde le réflexe : toute commande ponctuelle (-i, -u, shell) prend --no-http.

7. Le service systemd

nano /etc/systemd/system/odoo.service
[Unit]
Description=Odoo 20
After=network.target postgresql.service
Wants=postgresql.service

[Service]
Type=simple
User=odoo
Group=odoo
WorkingDirectory=/opt/odoo
ExecStart=/opt/odoo/venv/bin/python /opt/odoo/odoo/odoo-bin --config /etc/odoo/odoo.conf
Restart=on-failure
RestartSec=5
KillMode=mixed
TimeoutStopSec=30
LimitNOFILE=65536

[Install]
WantedBy=multi-user.target

Enregistre, puis vérifie, recharge et démarre :

systemd-analyze verify /etc/systemd/system/odoo.service
systemctl daemon-reload
systemctl enable --now odoo
  • After= / Wants=postgresql.service : au démarrage de la machine, PostgreSQL passe avant Odoo.
  • User=odoo et WorkingDirectory=/opt/odoo : l'identité et le dossier de travail du processus.
  • Restart=on-failure : relance après un plantage, mais pas après un systemctl stop volontaire.
  • KillMode=mixed : à l'arrêt, le signal va d'abord au processus principal, qui arrête proprement ses workers ; ceux qui traînent encore après 30 secondes sont tués.
  • LimitNOFILE=65536 : relève le nombre de fichiers et de connexions ouverts simultanément (sockets vers PostgreSQL et entre processus, fichiers du filestore), au-dessus de la limite par défaut.

systemd-analyze verify ne doit rien afficher, et enable --now démarre le service et l'inscrit au démarrage de la machine.

Le service se relève-t-il seul ?

On simule un plantage en tuant brutalement le processus principal :

P=$(systemctl show -p MainPID --value odoo); kill -9 $P; sleep 12
echo "ancien $P nouveau $(systemctl show -p MainPID --value odoo) état $(systemctl is-active odoo)"
ancien 27780 nouveau 27834 état active

systemd a relancé Odoo cinq secondes plus tard (RestartSec=5) ; la page de connexion répond de nouveau 200.

9. Première connexion

Tant que Nginx n'est pas posé, on atteint Odoo par un tunnel SSH lancé depuis ton poste :

ssh -N -L 8069:127.0.0.1:8069 root@ADRESSE_DU_SERVEUR

Puis http://localhost:8069 dans le navigateur. Connecte-toi avec admin / admin, et change ce mot de passe tout de suite, et en tout cas avant d'ouvrir Odoo au public avec Nginx : avatar en haut à droite › Mes préférences › onglet Sécurité › Modifier le mot de passe. Ce qui change par rapport à Odoo 19

  • PostgreSQL 16 minimum : le PostgreSQL 16 d'Ubuntu 24.04 suffit. Sur Ubuntu 22.04 (PostgreSQL 14), il faudrait le dépôt officiel de PostgreSQL.
  • Python 3.12 à 3.14 : le Python 3.12 d'Ubuntu 24.04 convient.
  • http_interface vaut 127.0.0.1 par défaut (0.0.0.0 en 19). Sur un serveur derrière Nginx, c'est exactement ce qu'on veut ; mais un Odoo qu'on comptait joindre par http://IP:8069 ne répond plus.
  • Le reste de la procédure (utilisateur, venv, workers, systemd) est identique à Odoo 19.

Ce qui manque encore

  • un reverse proxy Nginx avec certificat HTTPS, les routes /websocket vers le port 8072 et proxy_mode = True : prochain article de la série ;
  • un pare-feu (UFW : SSH, HTTP, HTTPS) et un accès SSH par clé, sans mot de passe ;
  • la rotation du journal, sans quoi odoo.log grossit indéfiniment ;
  • des sauvegardes automatiques de la base et de /opt/odoo/data, avec un test de restauration.

Tout cela, avec la sécurisation du serveur, plusieurs instances et plusieurs versions d'Odoo sur la même machine, la supervision et les mises à jour avec retour arrière, fait l'objet de l'ebook Déployer Odoo en production. Son édition Odoo 20 est en cours de rédaction, sur le serveur qui a servi à cet article.

Récapitulatif

  • Ubuntu 24.04 fournit Python 3.12 et PostgreSQL 16, les minimums d'Odoo 20.
  • wkhtmltopdf 0.12.6.1-3 « jammy », avec (with patched qt).
  • Utilisateur système odoo, rôle PostgreSQL odoo sans mot de passe (authentification peer).
  • Sources --depth 1 --branch 20.0 et venv, installés sous sudo -u odoo ; phonenumbers en plus.
  • odoo.conf : une base (dbfilter), gestionnaire fermé (list_db = False), 5 workers + 1 cron, limites de mémoire et de temps, écoute sur 127.0.0.1.
  • Unité systemd : Restart=on-failure, KillMode=mixed, démarrage au boot.
  • Toute commande odoo-bin ponctuelle prend --no-http, sinon le port 8069 est déjà pris.
