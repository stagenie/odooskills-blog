Numéroter automatiquement en Odoo 20 : ir.sequence

Depuis le troisième article, chaque code d'inventaire est tapé à la main — BIB-0001, BIB-0002… et une contrainte d'unicité pour rattraper les doublons. Odoo sait faire ça tout seul. Mais une séquence ne se pose pas n'importe où, et elle ne promet pas ce qu'on croit.

~18 minutes de lecture · niveau intermédiaire · parcours Framework & ORM

Ce que tu vas apprendre

Déclarer

Une ir.sequence en XML, protégée par noupdate.

Tirer

Le numéro dans create, jamais dans un default.

Assumer

Les trous de numérotation : d'où ils viennent, et ce que coûte de les interdire.

Prérequis

  • Le module biblio des articles précédents : les exemplaires et les emprunts.
  • Le serveur Odoo 20 joignable sur http://localhost:8069, base biblio.
  • Le mode développeur, pour voir le menu Paramètres → Technique → Séquences.

Ce qu'une séquence garantit — et ce qu'elle ne garantit pas

Une séquence Odoo distribue des numéros uniques et croissants. Elle ne promet ni la continuité, ni la réversibilité : un numéro tiré est consommé, même si l'enregistrement qui devait le porter n'est jamais enregistré. C'est un choix, pas un défaut — et tout l'enjeu de cet article est de savoir où ce choix vous arrange et où il vous gêne.

1. Déclarer la séquence

Une séquence est un enregistrement comme un autre : elle se pose dans un fichier de données. Crée data/library_sequence.xml :

<?xml version="1.0" encoding="utf-8"?>
<odoo noupdate="1">

    <record id="library_copy_sequence" model="ir.sequence">
        <field name="name">Bibliothèque : exemplaires</field>
        <field name="code">library.copy</field>
        <field name="prefix">BIB-</field>
        <field name="padding">4</field>
        <field name="number_next">9</field>
        <field name="company_id" eval="False"/>
    </record>

</odoo>

Champ par champ :

  • code est la clé d'appel depuis le Python. Il n'a pas à être un nom de modèle, mais le prendre égal au modèle évite d'inventer un vocabulaire de plus.
  • prefix et padding fabriquent la chaîne : BIB- + un entier sur 4 chiffres.
  • number_next à 9 parce que la bibliothèque a déjà huit exemplaires saisis à la main. Reprendre une numérotation existante, c'est exactement ça : dire à la séquence où le stock s'arrête.
  • company_id à False : une seule séquence pour toutes les sociétés. Avec une société renseignée, next_by_code choisit celle de la société courante, et se rabat sur la séquence sans société s'il n'y en a pas.

Ajoute le fichier au manifeste, avant les vues :

    'data': [
        'security/ir.access.csv',
        'data/library_sequence.xml',
        'data/library_cron.xml',
        'views/library_book_views.xml',
        ...
    ],

Mets le module à jour, puis Paramètres → Technique → Séquences :

v19 → v20 : rien à changer

Le modèle ir.sequence traverse la 20.0 sans un champ de différence : mêmes noms, mêmes types, même comportement. Un fichier de séquences écrit pour la 19 s'installe tel quel. C'est suffisamment rare dans cette migration pour être signalé.

2. Tirer le numéro au bon moment

Le champ devient un champ que l'utilisateur ne saisit plus. Dans models/library_copy.py :

    name = fields.Char(
        string="Code d'inventaire",
        required=True,
        copy=False,
        readonly=True,
        default="Nouveau",
    )

    @api.model_create_multi
    def create(self, vals_list):
        for vals in vals_list:
            if vals.get('name', "Nouveau") == "Nouveau":
                vals['name'] = self.env['ir.sequence'].next_by_code('library.copy') or "Nouveau"
        return super().create(vals_list)

Trois détails qui ne sont pas décoratifs :

  • readonly=True et default="Nouveau" : le formulaire affiche un libellé d'attente, pas un champ vide qui inviterait à taper.
  • copy=False : dupliquer un exemplaire ne doit pas dupliquer son code.
  • le test vals.get('name', "Nouveau") == "Nouveau" laisse passer un code fourni explicitement — utile pour une reprise de données, où les codes viennent du fichier source.

Pourquoi pas un default= ?

La tentation est grande d'écrire simplement :

    # à ne pas faire
    name = fields.Char(default=lambda self: self.env['ir.sequence'].next_by_code('library.copy'))

Un default est évalué quand le formulaire s'ouvre, pas quand l'enregistrement est sauvé. Ouvrir un formulaire pour finalement l'abandonner consomme donc un numéro — et comme on va le voir, ce numéro ne revient jamais. Le même écran ouvert trois fois par hésitation, c'est trois trous dans la numérotation. Dans create, le numéro n'est tiré que lorsqu'un enregistrement est réellement créé.

next_by_code échoue en silence

Si aucune séquence ne porte le code demandé, la méthode ne lève rien : elle écrit une ligne de journal en niveau debug — invisible en exploitation — et renvoie False.

>>> env['ir.sequence'].next_by_code('library.inexistant') False

Sans garde-fou, ce False atterrit dans le champ. D'où le or "Nouveau" : un enregistrement mal nommé se repère d'un coup d'œil, un champ vide ou False se découvre trois mois plus tard.

3. Les trous, et ce qu'ils coûtent à éviter

Par défaut, l'implémentation est standard : Odoo crée une véritable séquence PostgreSQL et lui demande son nextval(). Or une séquence PostgreSQL vit en dehors de la transaction : elle n'est pas annulée par un ROLLBACK. Vérifions-le dans la console, en annulant explicitement le tirage :

seq = env.ref('biblio.library_copy_sequence')
env.invalidate_all()
avant = seq.number_next_actual

with env.cr.savepoint(flush=False) as sp:
    tire = env['ir.sequence'].next_by_code('library.copy')
    sp.close(rollback=True)          # on annule tout

env.invalidate_all()
print(avant, tire, seq.number_next_actual)
prochain avant : 12 | tiré puis annulé : BIB-0012 | prochain après : 13

Le numéro 12 est parti et ne reviendra pas. Ce n'est pas un bogue : c'est le prix de la vitesse. Deux utilisateurs qui créent un exemplaire en même temps n'attendent pas l'un l'autre.

Le compteur affiché n'est pas non plus synchronisé

number_next_actual est un champ calculé qui va lire la séquence PostgreSQL. Comme le tirage se fait en SQL brut, le cache de l'ORM n'apprend jamais que le compteur a bougé :

lu 13 | après un tirage, sans invalidation : 13 | après invalidation : 14

Dans une sonde ou un test, env.invalidate_all() avant chaque lecture, sinon vous comparerez deux fois la même valeur périmée.

L'implémentation « no gap »

L'autre choix, implementation = 'no_gap', abandonne la séquence PostgreSQL : le compteur est une colonne de la table ir_sequence, lue et incrémentée dans la transaction. Le numéro revient donc si la transaction est annulée. Le prix se lit dans le SQL du cœur :

SELECT number_next FROM ir_sequence WHERE id=%s FOR UPDATE NOWAIT

NOWAIT : la seconde transaction n'attend pas son tour, elle échoue tout de suite. Deux transactions concurrentes sur la même séquence, et la deuxième reçoit :

a = env['ir.sequence'].next_by_code('sonde.nogap')   # transaction 1, non validée
# … dans une seconde connexion, sur la même séquence :
b = env2['ir.sequence'].next_by_code('sonde.nogap')
transaction 1 tire : NG-001 (pas encore validée) transaction 2 : LockNotAvailable | could not obtain lock on row in relation "ir_sequence"

Sur une facturation légale, cette continuité vaut son coût et c'est ce que fait la comptabilité d'Odoo. Sur des codes d'inventaire, elle achète une file d'attente contre un problème qui n'existe pas. Le choix par défaut, standard, est le bon ici.

Un trou n'est pas seulement un tirage annulé

Même en no gap, supprimer un enregistrement laisse un trou : le numéro a bien été attribué, c'est la ligne qui a disparu. Aucune implémentation ne protège de ça. Si la continuité est une exigence réglementaire, la réponse est d'interdire la suppression, pas de choisir une séquence.

4. Une référence qui porte son année

L'emprunt, lui, n'avait aucune référence — on le désignait par son exemplaire. Donnons-lui une référence datée, remise à zéro chaque année. Deux réglages suffisent :

<record id="library_loan_sequence" model="ir.sequence">
    <field name="name">Bibliothèque : emprunts</field>
    <field name="code">library.loan</field>
    <field name="prefix">EMP/%(range_year)s/</field>
    <field name="padding">4</field>
    <field name="use_date_range" eval="True"/>
    <field name="company_id" eval="False"/>
</record>

use_date_range demande à Odoo de tenir un compteur par plage de dates. La plage est créée toute seule, à l'année civile, au premier tirage qui en a besoin. Et dans le préfixe, %(range_year)s désigne l'année de la plage — à distinguer de %(year)s, qui est l'année de la date du tirage. La nuance compte dès qu'on enregistre un emprunt daté de l'an dernier.

Côté modèle, le numéro se tire comme le précédent, en passant la date :

    reference = fields.Char(
        string="Référence", required=True, copy=False, readonly=True, default="Nouveau",
    )

    @api.model_create_multi
    def create(self, vals_list):
        for vals in vals_list:
            if vals.get('reference', "Nouveau") == "Nouveau":
                vals['reference'] = self.env['ir.sequence'].next_by_code(
                    'library.loan', sequence_date=vals.get('date_out'),
                ) or "Nouveau"
        emprunts = super().create(vals_list)
        emprunts.filtered(lambda e: e.state == 'ongoing').copy_id.state = 'borrowed'
        return emprunts

sequence_date décide de la plage. Sans ce paramètre, un emprunt saisi en retard porterait l'année du jour de la saisie. Le contrôle est immédiat :

Seq = env['ir.sequence']
print(Seq.next_by_code('library.loan', sequence_date='2025-03-04'))
print(Seq.next_by_code('library.loan', sequence_date='2026-09-23'))
EMP/2025/0001 EMP/2026/0001

Deux compteurs indépendants, deux plages créées sans rien demander :

Les emprunts existants, eux, ont reçu leur référence lors de la reprise :

Ajouter un champ requis à un modèle qui a déjà des données mérite un mot : en créant la colonne, Odoo l'initialise sur les lignes existantes avec la valeur par défaut. Contrôle en SQL après la mise à jour :

valeurs posées sur les lignes existantes : [('Nouveau',)] lignes restées NULL : 0

Toutes portent donc le même libellé d'attente. Une boucle de reprise leur donne ensuite leur vraie référence, dans l'ordre choisi :

for loan in env['library.loan'].search([], order='date_out'):
    if loan.reference in (False, "Nouveau"):
        loan.reference = env['ir.sequence'].next_by_code(
            'library.loan', sequence_date=loan.date_out)

Dans un module distribué, ce genre de reprise a sa place dans un script de migration — pas dans un fichier de données, qui ne s'exécuterait qu'une fois et sans ordre garanti.

5. Faut-il un sudo() pour tirer un numéro ?

Le réflexe est répandu : self.env['ir.sequence'].sudo().next_by_code(...). Regardons ce que le cœur exige réellement. Côté droits, en Odoo 20, ir.sequence est décrite dans ir.access :

[('Role / User', 'r'), ('Rôle / Administrateur', 'crud')]

Un utilisateur interne a donc la lecture seule. Et next_by_code ne vérifie rien de plus : self.browse().check_access('read'). Le reste — l'appel à nextval() comme l'incrément d'une séquence no gap — passe par du SQL brut, qui ne repasse pas par les contrôles de l'ORM. L'essai le confirme, avec un utilisateur qui n'a que le groupe « Utilisateur interne » :

tirage par agent_seq → BIB-0011 tirage no_gap par agent_seq → NG-002 écriture sur la séquence : AccessError Vous n'êtes pas autorisé à modifier les enregistrements 'Séquence' (ir.sequence).

Conclusion : tirer un numéro ne demande pas de sudo(), quelle que soit l'implémentation. En revanche, modifier une séquence — changer son préfixe, repositionner son compteur depuis du code métier — exige bien les droits d'administration, et c'est là, et seulement là, que le sudo() se justifie.

6. noupdate="1" : la ligne qui sauve le compteur

Le fichier de données porte <odoo noupdate="1">. Sans lui, chaque mise à jour du module réécrit l'enregistrement avec les valeurs du XML — number_next compris. Le scénario n'est pas théorique : un administrateur repositionne le compteur à 100 depuis l'écran, quelqu'un déploie une correction du module, et la numérotation repart à 9.

L'essai, dans les deux sens, sur la même base :

compteur posé à 100 depuis l'écran -u biblio AVEC noupdate="1" → prochain = 100 -u biblio SANS noupdate → prochain = 9

Le second cas est exactement la panne : des codes déjà attribués, redistribués.

Le drapeau est posé à la création, et jamais remis

noupdate n'est pas un attribut du fichier : c'est une colonne de ir_model_data, écrite quand l'identifiant externe est créé. Le cœur insère ces lignes avec un ON CONFLICT DO UPDATE qui ne touche que model, res_id et write_date — noupdate n'y figure pas.

Conséquence : un module publié sans noupdate, puis corrigé, laisse les bases déjà installées sans protection — ajouter l'attribut ne remet pas le drapeau à vrai sur l'existant. Il faut le corriger explicitement, par un script de migration ou depuis l'écran des identifiants externes. Vérifié dans les deux sens sur la même base.

Récapitulatif

  • Une séquence promet l'unicité et la croissance, pas la continuité.
  • L'implémentation par défaut s'appuie sur une séquence PostgreSQL : un ROLLBACK ne rend pas le numéro.
  • no_gap rend la continuité au prix d'un verrou qui fait échouer la transaction concurrente immédiatement.
  • Aucune implémentation ne comble le trou laissé par une suppression.
  • Le numéro se tire dans create : un default= consomme dès l'ouverture du formulaire.
  • next_by_code rend False en silence si le code n'existe pas — toujours prévoir la valeur de repli.
  • use_date_range + %(range_year)s donnent une numérotation annuelle sans une ligne de Python.
  • Tirer un numéro ne demande pas sudo() ; modifier la séquence, si.
  • noupdate="1" protège le compteur des mises à jour — et le drapeau ne se pose qu'à la création de l'identifiant externe.

La suite de la série sortira la bibliothèque du back-office : donner à l'adhérent une page où retrouver ses emprunts, sans lui ouvrir la base.
