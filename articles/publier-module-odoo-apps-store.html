Série « Licences & distribution » · Article 3/3

Publier un module sur l'Odoo Apps Store

Les clés que le serveur ignore mais que la plateforme lit, l'arborescence qui conditionne la mise en ligne, le partage 70/30 et le seuil de paiement — et la liste des pratiques qui font retirer un module sans préavis.

~13 minutes de lecture · niveau intermédiaire · parcours Fondamentaux

Ce que tu vas apprendre

Serveur vs plateforme

Où atterrit chaque clé commerciale. Mesuré en base, pas déduit.

L'arborescence exacte

Les deux fichiers sans lesquels un module ne se présente pas correctement.

Les règles qui coûtent cher

Prix le plus bas du web, clé d'activation interdite, code lisible obligatoire.

Prérequis — un module Odoo 19 qui fonctionne, un dépôt Git, et les deux articles précédents de la série : le choix de licence (1/3) et la lecture du manifeste par le serveur (2/3).

1. Auto-publication : il n'y a pas de comité de lecture

Le point qui surprend le plus les développeurs venus d'autres plateformes : il n'existe aucune validation préalable. On enregistre une URL de dépôt, un robot vient lire le code, et le module apparaît. Le contrôle est réactif : il s'exerce après coup, sur signalement ou détection, et il peut aller jusqu'au retrait.

Trois conséquences structurent tout le reste :

RègleConséquence pratique
La branche Git est la version Odoo Une branche 19.0 pour la 19, une branche 18.0 pour la 18. L'URL enregistrée porte le suffixe de branche.
Une vente par version « Starting version 13.0, Every version of the module is sold separately. » Un client qui migre rachète. Chaque branche est une fiche distincte.
Le dépôt est lu, pas déposé Aucun envoi d'archive : c'est la plateforme qui vient cloner. Un module payant impose donc un dépôt privé, avec le compte de la plateforme autorisé en lecture.
# une branche par version, poussée sur le dépôt
git switch -c 19.0 && git push origin 19.0

# URL enregistrée côté plateforme — le # porte le nom de branche
ssh://git@github.com/mon-compte/mon-depot#19.0

Le format d'URL est imposé : « All repositories URL's will follow the standard ssh URI scheme », sous la forme ssh://git@gitServer(:port)/mypath#version.

2. Ce que le serveur lit, ce que la plateforme lit

L'article 2/3 a établi la liste des 33 clés reconnues par le serveur. Les clés commerciales n'y figurent pas — price, currency et support sont absentes de _DEFAULT_MANIFEST. Elles ne sont pourtant pas rejetées. Vérification sur un module vitrine déclarant tout le nécessaire :

# content/blog/modules/oski_store_demo/__manifest__.py
{
    'name': 'Invoice Reminder',
    'version': '19.0.1.0.0',
    'category': 'Accounting',
    'summary': 'Relance automatique des factures echues',
    'author': 'OdooSkills',
    'website': 'https://www.odooskills.com',
    'license': 'OPL-1',
    'depends': ['base'],
    'images': [
        'static/description/icon.png',
        'images/main_screenshot.png',
    ],
    'price': 49.00,
    'currency': 'EUR',
    'support': 'support@odooskills.com',
    'live_test_url': 'https://demo.odooskills.com',
    'installable': True,
    'application': True,
}

Côté Python, les clés survivent : la fusion avec les valeurs par défaut est un dict.update(), donc tout ce qui est écrit reste lisible dans le manifeste chargé.

from odoo.modules.module import _load_manifest

m = _load_manifest('oski_store_demo', raw)
#   manifest['price']         = 49.0
#   manifest['currency']      = 'EUR'
#   manifest['support']       = 'support@odooskills.com'
#   manifest['live_test_url'] = 'https://demo.odooskills.com'

Côté base de données, en revanche, elles disparaissent — sauf une, qui atterrit ailleurs que là où on l'attend :

SELECT name, license, url, to_buy, application, state
FROM ir_module_module WHERE name = 'oski_store_demo';

      name       | license |             url             | to_buy | application |   state
-----------------+---------+-----------------------------+--------+-------------+-----------
 oski_store_demo | OPL-1   | https://demo.odooskills.com | f      | t           | installed

La colonne url contient live_test_url. Le mapping est explicite dans le code, avec un repli sur une clé url qui n'est pas documentée :

# odoo/odoo/addons/base/models/ir_module.py — get_values_from_terp()
'url': terp.get('url') or terp.get('live_test_url', ''),
'to_buy': False

Deux enseignements. D'abord, to_buy est forcé à False : ce drapeau — celui qui affiche le bouton Upgrade sur les vitrines Enterprise vues dans l'article 1/3 — n'est jamais dérivé du prix déclaré. Ensuite, la liste des colonnes de la table le confirme :

SELECT column_name FROM information_schema.columns WHERE table_name = 'ir_module_module';

application author auto_install category_id contributors ... icon id imported latest_version
license maintainer menus_by_module module_type name published_version reports_by_module
sequence shortdesc state summary to_buy url views_by_module web website ...

Ni price, ni currency, ni support. Ces trois clés n'existent que pour la plateforme. Le corollaire est utile : changer le prix dans le manifeste n'a aucun effet sur une instance — il faut pousser sur la branche et laisser le robot repasser.

CléLue par le serveurLue par la plateformeDestination
name, summary, author, website, category ouiouiColonnes de ir.module.module + fiche boutique
licenseouiouiColonne license + mention sur la fiche
live_test_urlouiouiColonne url (!) + bouton d'essai
price, currencynonouiTarif de la fiche uniquement
supportnonouiContact affiché sur la fiche
imagesnonouiVisuels de la fiche (le premier sert de couverture)

3. L'arborescence que le robot attend

Deux chemins sont figés, et c'est là que la plupart des premières publications échouent.

mon-depot/                       # racine du dépôt = racine des modules
├── LICENSE                      # le texte de licence, à la racine du dépôt
└── oski_store_demo/
    ├── __manifest__.py
    ├── __init__.py
    ├── images/
    │   └── main_screenshot.png  # visuel de couverture, déclaré dans 'images'
    ├── static/
    │   └── description/
    │       ├── icon.png         # OBLIGATOIRE — 128x128, vrai PNG
    │       └── index.html       # OBLIGATOIRE — description riche, en anglais
    └── doc/
        └── index.rst            # optionnel, RST strict

La documentation de la page d'envoi est sans ambiguïté sur les deux fichiers imposés : « Starting from version 8.0, the module icon needs to be located at static/description/icon.png » et « The rich-text HTML description comes from the static/description/index.html file in the module folder. »

⚠️ Le piège de l'icône renommée

  • La plateforme le dit elle-même : « changing the file extension of an image does not change its format ». Un JPEG renommé icon.png est rejeté.
  • Vérification en une ligne, sans quitter le terminal : file oski_store_demo/static/description/icon.png doit répondre PNG image data, 128 x 128.
  • Formats acceptés dans la description : png, gif, jpeg. Rien d'autre — un SVG ne s'affichera pas.
  • Toute image utilisée dans index.html doit être déclarée dans la clé images du manifeste, sinon elle n'est pas embarquée.

La page de description est le seul document commercial du module. Elle doit être en anglais, décrire fidèlement ce qui est vendu, et montrer des captures. Sont proscrits : les publicités pour d'autres produits, les liens vers des boutiques concurrentes, les widgets statiques et le JavaScript embarqué.

4. L'argent : 70/30, et une contrainte de prix qui déborde

ParamètreValeurSource
Part de l'éditeur sur une vente70 % « You will get 70% of your modules revenues on our Apps platform. »
Commission de la plateforme30 % sur les ventes, 25 % sur les achats intégrésFAQ Apps
Devises acceptéesEUR ou USD, rien d'autre « Supported currencies are EUR and USD. »
Seuil de versement400 € de ventes non réglées « we will close the POs that have reached or exceeded 400 euros unredeemed sales »
Point de départ conseillé100 € « We think 100 euros is a good starting point. »

La clause de prix le plus bas

C'est la règle la plus contraignante, et la plus souvent enfreinte par inadvertance : « We require that the modules sold on our Apps platform is the lowest (or the same) price on the web, have a proper description, complete with screenshots. » Autrement dit, une promotion lancée sur sa propre boutique sans baisser le prix sur la plateforme place l'éditeur en infraction. Toute politique tarifaire — remises saisonnières, packs, offres de lancement — doit être répercutée aux deux endroits, ou ne pas exister.

Le seuil de 400 € mérite une projection concrète. Sur un module à 49 €, la part éditeur est de 34,30 € par vente ; il faut donc une douzaine de ventes accumulées avant le premier versement. Sur un module à 149 €, quatre ventes suffisent. Le prix conditionne moins le chiffre d'affaires que le délai avant le premier encaissement — argument à peser quand on hésite à valoriser son travail.

5. Ce qui fait retirer un module

Puisque le contrôle est réactif, la sanction arrive après la mise en ligne — et elle peut aller du dépublication à la suspension du compte. Deux interdits touchent directement à ce que l'article 1/3 appelait « l'illusion de la protection ».

InterditPourquoi ça compte pour un module payant
Clé d'activation ou vérification de licence Les règles éditeurs sont explicites : « your app cannot require an activation key to be executed and the customer has ownership of their data at any given time. » Le mécanisme auquel pense spontanément tout éditeur pour protéger son code est précisément celui qui est interdit.
Code obfusqué ou chiffré Le client doit pouvoir lire ce qu'il exécute. Ce qui protège le module payant, c'est la licence OPL-1 et le dépôt privé — pas une transformation du source.
Téléchargement de code à l'exécution Tout chargement de charge utile externe est proscrit : le robot ne peut pas auditer ce qu'il ne voit pas.
Fonctionnalités cachées Ce qui n'est pas décrit sur la fiche ne doit pas exister dans le module. Vaut aussi pour toute télémétrie.
Clonage d'un module Enterprise Réimplémenter à l'identique une application Enterprise est un motif de retrait, distinct de la question de licence.
Absence de support sur un module payant La réponse aux bugs et aux problèmes de configuration fait partie de ce qui est vendu. La clé support n'est pas décorative.

La conclusion rejoint celle du premier article de la série, par un autre chemin. La licence n'est pas une protection technique, et la plateforme interdit explicitement d'en fabriquer une. Ce qui protège un module commercial, c'est le triptyque dépôt privé + licence OPL-1 + support réel. Le reste relève du fantasme d'ingénieur.

6. Les deux checklists

Module gratuit

  • 'license': 'LGPL-3'
  • Aucune clé price ni currency
  • Dépôt public autorisé
  • Branche nommée 19.0
  • static/description/icon.png, vrai PNG 128×128
  • static/description/index.html en anglais
  • Toutes les images déclarées dans images
  • Fichier LICENSE à la racine du dépôt
  • depends complet, testé sur base neuve

Module payant — en plus

  • 'license': 'OPL-1'
  • Dépôt privé, compte plateforme en lecture
  • price + currency (EUR ou USD)
  • support = adresse réellement relevée
  • live_test_url vers une démo qui répond
  • Prix ≤ tout autre prix affiché sur le web
  • Aucune clé d'activation, aucun code obfusqué
  • Une branche et une fiche par version supportée
  • Version bêta ? 19.0.0.9.0, sous 1.0

Un dernier contrôle avant de pousser, qui prend dix secondes et évite un aller-retour d'une journée avec le robot :

# l'icone est-elle un vrai PNG a la bonne taille ?
file oski_store_demo/static/description/icon.png
# -> PNG image data, 128 x 128, 8-bit/color RGBA, non-interlaced

# la description existe-t-elle et est-elle non vide ?
test -s oski_store_demo/static/description/index.html && echo "description OK"

# toutes les images du HTML sont-elles declarees dans le manifeste ?
grep -o 'src="[^"]*"' oski_store_demo/static/description/index.html

Récapitulatif

  • Pas de revue préalable. Le module est mis en ligne par un robot qui lit le dépôt ; le contrôle vient ensuite, et il peut retirer.
  • La branche Git porte la version, et chaque version est vendue séparément depuis la 13.0.
  • price, currency et support n'existent que pour la plateforme : aucune colonne en base. live_test_url, elle, atterrit dans la colonne url.
  • Deux fichiers imposés : static/description/icon.png — vrai PNG — et static/description/index.html en anglais.
  • 70 % pour l'éditeur, versement au-delà de 400 € cumulés, en EUR ou USD, et le prix boutique doit rester le plus bas du web.
  • Les clés d'activation sont interdites. La protection d'un module payant, c'est dépôt privé + OPL-1 + support réel.

Fin de la série. Les trois articles se lisent dans l'ordre : choisir la licence, comprendre ce que le manifeste déclenche, puis publier.
