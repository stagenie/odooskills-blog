Les widgets de champ Odoo 20 : le catalogue utile (badge, handle…)

Le client web d'Odoo 20 enregistre plus d'une centaine de widgets de champ rien que dans le module web. Une trentaine reviennent sans cesse dans les vues standard : badge, handle, percentage, many2many_tags… Voici la liste lue dans le registre réel, avec pour chacun les types acceptés, les options vraiment lues, la syntaxe et le rendu, puis ce qui se passe quand on se trompe.

~13 minutes de lecture · niveau intermédiaire · parcours Web & interface

Ce que tu vas apprendre

Lire le registre

Deux lignes de console pour lister les widgets réellement chargés, leurs types et leurs options, sans se fier à une liste recopiée.

Choisir le bon widget

35 widgets triés par famille : types acceptés, options lues, syntaxe XML et rendu en formulaire, en liste et en carte.

Reconnaître une erreur

Nom inconnu, type non supporté, option mal écrite : ce qu'Odoo 20 fait vraiment, et les noms de la 19 qui ne répondent plus.

Prérequis

  • Savoir écrire un modèle et ses vues dans un module : voir Créer son premier module Odoo 20.
  • Une instance Odoo 20 Community sur http://localhost:8069, base ma_base. Les chiffres du registre ci-dessous viennent d'une base où sont installés sale, stock, account et leurs dépendances : sur une autre base, le total change.
  • Écrire son propre widget n'est pas le sujet ici : c'est l'objet de Un widget OWL 3 en Odoo 20 : le badge de retard des emprunts.

Comment le client web choisit un widget

Un widget de champ est une entrée du registre JavaScript fields. Quand une vue se charge, le client cherche la clé <type de vue>.<widget> (list., form., card.…), puis le nom nu ; si la vue a un js_class, la clé <js_class>.<widget> passe en premier. Sans attribut widget, il fait la même recherche avec le type du champ : char, many2many, date… C'est pourquoi écrire widget="char" sur un champ texte ne change rien.

Le serveur, lui, ne regarde pas cet attribut. Une vue qui porte un nom de widget inventé s'installe sans un avertissement, et une vue dont les options ne sont même pas une expression Python valide est acceptée aussi : l'erreur n'apparaît qu'à l'ouverture, dans le navigateur.

1. Lire le registre au lieu d'une liste toute faite

Ouvrez n'importe quel écran du client web, puis la console du navigateur (F12). Le registre est accessible par le chargeur de modules d'Odoo :

const fields = odoo.loader.modules.get("@web/core/registry").registry.category("fields");
fields.getEntries().length;                               // nombre de widgets chargés
fields.get("badge").supportedTypes;                       // types acceptés
fields.getEntries().filter(([name]) => name.includes(".")).length;   // entrées préfixées
["selection_badge", "remaining_days", "kanban.many2many_tags"].map((n) => fields.contains(n));
["badges_selection", "relative_date", "card.many2many_tags"].map((n) => fields.contains(n));

Sur cette base, 246 widgets sont chargés, dont 35 contiennent un point : surtout des préfixes de type de vue (list., card.…), mais aussi des préfixes de js_class (base_settings.binary) et quelques noms qui contiennent simplement un point (stock.max_qty_to_order). Le total dépend des modules installés : mail, account ou stock ajoutent les leurs. Le module web, présent partout, en apporte 108 à lui seul : 89 noms nus et 19 préfixés. Chaque entrée est un descripteur : fields.get("percentage") montre son composant, ses supportedTypes, ses supportedOptions et sa fonction extractProps.

Un détail compte pour la suite. supportedOptions est une description, pas un contrôle : le client web ne s'en sert pas pour valider la vue. Les options réellement utilisées sont celles que lit extractProps, et les deux listes ne coïncident pas toujours. percentage ne déclare aucune option mais lit digits et no_symbol ; badges_selection en déclare une, badge_limit, et en lit cinq. Pour savoir quelles options un widget accepte, lisez le texte de la fonction :

fields.get("badges_selection").extractProps.toString();

Le registre lu en console est celui des modules installés, patchs compris. Sur cette base, le module sms patche le descripteur de phone : son supportedOptions n'affiche plus que enable_sms, alors que son extractProps lit toujours formatted_field et dial_field. Encore une preuve que supportedOptions ne fait pas foi.

Le critère du catalogue

Les vues XML des modules Community d'Odoo 20 contiennent 3 688 attributs widget, pour 309 noms différents. Parmi les 89 noms nus du module web, le catalogue garde ceux qui sont posés au moins 7 fois, dans au moins 2 modules : il en reste 47. Il en retire les 8 qui sont déjà le widget par défaut de leur type (many2one, one2many, float, text…) et 4 widgets propres à un écran technique (upgrade_boolean des Paramètres, kanban_color_picker, field_selector, password). Restent 35 widgets (même nombre, sans rapport avec les 35 entrées préfixées), rangés ci-dessous par famille. Les autres existent, mais servent un écran précis ou un seul module.

2. Le module d'essai

Pour voir les 35 widgets côte à côte, un petit module oski_widgets_catalogue (dépendance : web seulement) définit un modèle avec un champ par usage, un formulaire, une liste et une carte. Il réutilise les étiquettes de contacts (res.partner.category, qui ont un champ color) et les contacts de démonstration.

class OskiWidgetDemo(models.Model):
    _name = 'oski.widget.demo'
    _description = 'Démonstration des widgets de champ'
    _order = 'sequence, id'

    name = fields.Char('Nom', required=True)
    sequence = fields.Integer('Séquence', default=10)
    state = fields.Selection(
        [('draft', 'Brouillon'), ('open', 'En cours'), ('done', 'Terminé'), ('cancel', 'Annulé')],
        string='Étape', default='draft', required=True)
    priority = fields.Selection(
        [('0', 'Normale'), ('1', 'Haute'), ('2', 'Très haute'), ('3', 'Urgente')],
        string='Priorité', default='0')
    tag_ids = fields.Many2many('res.partner.category', string='Étiquettes')
    progress = fields.Float('Avancement')
    target = fields.Integer('Objectif', default=100)
    rate = fields.Float('Taux de remise')
    # … une trentaine de champs, un par widget essayé

Le droit d'accès s'écrit en Odoo 20 dans security/ir.access.csv :

id,name,model_id,group_id/id,operation,domain
access_oski_widget_demo_user,Démonstration des widgets : utilisateurs,oski.widget.demo,base.group_user,crud,

Le module s'installe sans un avertissement, avec quatre fiches de démonstration.

percentage stocke une fraction : la fiche contient 0.125 et affiche « 12,5 % ». Dans l'autre sens, saisir 50 puis enregistrer écrit 0.5 en base (relu après la saisie). percentpie, lui, attend directement un nombre de 0 à 100 : les deux ne s'échangent pas sans changer les données.

<div name="button_box">

Le champ de max_value doit être dans la vue

options="{'max_value': 'target'}" désigne un champ, mais le widget ne le charge pas tout seul. Dans la carte d'essai sans <field name="target"/>, l'avancement d'une fiche à 20 sur 80 s'affiche « 20/100 », sans erreur : le maximum retombe sur 100. Avec <field name="target" invisible="1"/> dans la carte (ou column_invisible="1" en liste), il redevient « 20/80 ». Un nom de champ qui n'existe pas donne le même « /100 » muet.

7. Liste, formulaire, carte : ce qui change d'une vue à l'autre

Le même widget ne se comporte pas pareil partout. Deux raisons : les entrées préfixées du registre (19 dans web : list.many2many, list.date, form.url, card.many2many_tags…) remplacent le widget nu dans un type de vue, et le composant lui-même regarde le type de vue ou l'état d'édition.

Dans un formulaire en édition, cliquer sur l'interrupteur, une étoile, le favori ou une étape de la barre laisse la valeur en base inchangée et fait apparaître le bouton d'enregistrement. Dans la liste, l'interrupteur et les étoiles sont écrits aussitôt ; dans la carte, les étoiles aussi. La règle est dans Record.update() : une fiche qui n'est pas en édition s'enregistre à chaque modification (sans onchange, et sauf sous-fiche d'un x2many), une fiche en édition attend l'enregistrement.

Un nom de widget faux ne se voit qu'en console

Nom inconnu ou option inconnue : la vue s'affiche, avec le widget par défaut ou sans l'option, et seul un avertissement en console (ou rien du tout) le signale. Un type non supporté peut donner un rendu absurde ou une fenêtre « Oups ! » selon le widget. Après avoir posé un widget, ouvrez la console du navigateur sur la vue : Missing widget et don't support the type sont les deux messages à chercher. Le mode debug aide aussi : son info-bulle sur un libellé de champ affiche le widget utilisé, comme expliqué dans Mode debug Odoo 20 : nom technique d'un champ, d'une vue, d'une action.

Venant de la 19

Une vue 19 qui utilise selection_badge ou remaining_days s'installe en 20 et s'affiche avec le widget par défaut : liste déroulante, date brute. Cherchez ces noms et les clés kanban. dans vos vues et votre JavaScript. Surtout, un formulaire où l'utilisateur basculait un interrupteur ou une étape « qui s'enregistrait toute seule » demande maintenant un clic sur Enregistrer : à prévenir dans la recette. Le préfixe card. est détaillé dans Kanban, graphique et pivot en Odoo 20.

À retenir

  • La liste des widgets d'une base se lit dans le registre fields, depuis la console ; ses options réelles, dans extractProps, pas dans supportedOptions.
  • Le module web en apporte 108 en Odoo 20 ; 35 suffisent à presque toutes les vues : many2many_tags, statinfo, monetary, handle, radio, badge, float_time, boolean_toggle en tête.
  • Le serveur ne valide ni le nom du widget ni ses options : vérifiez la console (Missing widget, don't support the type).
  • Un champ cité dans une option (max_value, end_date_field, currency_field) doit être présent dans la vue, invisible au besoin.
  • En 20, les widgets cliquables d'un formulaire en édition n'enregistrent plus la fiche ; en liste et en carte, si.
