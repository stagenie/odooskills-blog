Copier la prod en base de test Odoo 20 : db dump, load, neutralize

Une copie de production qui garde ses tâches planifiées, son serveur de courriel et ses fournisseurs de paiement en mode réel peut écrire à de vrais clients. Odoo 20 fournit tout ce qu'il faut en ligne de commande : odoo-bin db dump, db load -n et odoo-bin neutralize. Voici ce que chacun fait réellement, ce que la neutralisation coupe sur une base Ventes et Inventaire, et comment le vérifier.

~13 minutes de lecture · niveau intermédiaire · parcours Infrastructure

Ce que tu vas apprendre

Copier

db dump en zip (filestore compris), db load sous un autre nom, db duplicate et ses limites.

Neutraliser

La liste réelle de ce que coupe -n / odoo-bin neutralize, module par module, et le SQL exécuté.

Vérifier

Le bandeau rouge, quatre requêtes SQL et un courriel d'essai : la preuve que la copie ne parle plus au monde extérieur.

Prérequis

  • Un Odoo 20 installé avec son odoo.conf (accès PostgreSQL, data_dir) : voir Installer Odoo 20 sur un serveur Ubuntu.
  • Une base appelée ici ma_base joue la production : démonstration Ventes et Inventaire en français, à laquelle ont été ajoutés un serveur SMTP avec identifiants, une boîte de relève IMAP, un modèle de courriel forcé sur ce serveur, une action webhook et le Virement bancaire en mode réel. Toutes les valeurs sont fictives (smtp.example.com, imap.example.com…).
  • Les commandes sont lancées depuis le dossier des sources (./odoo-bin). Les copies s'appellent ma_base_test et ma_base_essai.

1. La sous-commande odoo-bin db

C'est le gestionnaire de bases de l'écran /web/database/manager, en ligne de commande. Ses six opérations, telles que les liste ./odoo-bin db --help :

positional arguments: {init,load,dump,duplicate,rename,drop} init Create and initialize a database load Load a dump file. dump Create a dump with filestore. duplicate Duplicate a database including filestore. rename Rename a database including filestore. drop Delete a database including filestore

« Filestore » revient partout : les pièces jointes ne sont pas dans PostgreSQL mais dans le dossier filestore/<nom de la base> du data_dir. Une copie faite avec pg_dump seul donne une base dont les images et les PDF sont introuvables ; les commandes db déplacent les deux ensemble.

Deux règles de syntaxe :

  • les options générales se placent avant l'opération : ./odoo-bin db -c odoo.conf dump …, pas db dump -c odoo.conf ;
  • db n'accepte que -c, -D (dossier de données), --addons-path et les options PostgreSQL (-r, -w, --db_host, --db_port, --pg_path, --db_sslmode). Le reste vient du fichier de configuration.

2. Sauvegarder : db dump

./odoo-bin db -c odoo.conf dump ma_base prod.zip

Sur la base de démonstration (71 modules, 14 Mo de filestore), la commande a pris 1,1 s. Le zip contient trois choses :

3. Charger sous un autre nom : db load -n

./odoo-bin db -c odoo.conf load -n ma_base_test prod.zip

Ce que dit le journal, dans l'ordre (odoo/modules/db.py, fonction restore) :

  1. les deux lignes Connection to the database failed en INFO ne sont pas des erreurs : Odoo vérifie que la base cible n'existe pas encore ;
  2. création d'une base vide, puis psql rejoue dump.sql ;
  3. neutralisation, avant que la base ne soit visible des tâches planifiées ;
  4. chargement du registre, puis nouvelle identité de base (voir le tableau) ;
  5. déplacement du filestore dans le data_dir du fichier -c.

Le tout a pris 6,0 s.

Option de loadEffet
-n, --neutralizeneutralise la copie (section 4)
-f, --forcesupprime d'abord une base existante du même nom, filestore compris
--movegarde database.uuid et database.secret de la source

Une base de test ne doit pas partager l'identifiant de la production : garde le comportement par défaut, et réserve --move à la restauration de la production elle-même.

L'aide parle de « pg_dump file », la commande le refuse

load --help annonce dump_file zip or pg_dump file to load. Un fichier produit par dump --format dump s'arrête pourtant net, code de sortie 1 :

Restoring prod.dump... Not a zipped dump file, use `pg_restore` to restore raw dumps, and `psql` to execute sql dumps or scripts.

Ce format se recharge avec pg_restore, et le filestore se copie à part.

4. Ce que la neutralisation coupe réellement

Neutraliser n'est pas une liste figée : Odoo prend chaque module installé et exécute son fichier data/neutralize.sql s'il en a un (odoo/modules/neutralize.py). Odoo 20 en livre 77 ; sur la base Ventes et Inventaire, cinq modules installés en ont un. Pour une base déjà en place, la sous-commande neutralize fait la même chose que load -n :

./odoo-bin neutralize -c odoo.conf -d ma_base_essai

Le détail, module par module, sur cette base :

ModuleCe que fait son neutralize.sql
base
  • archive tous les serveurs sortants et vide leurs identifiants (smtp_user, smtp_pass) ;
  • ajoute un serveur actif neutralization - disable emails vers l'hôte invalid, port 1025, pour qu'un serveur SMTP passé en ligne de commande ne serve pas de secours ;
  • archive toutes les tâches planifiées sauf base.autovacuum_job (nettoyage interne) ;
  • remplace l'URL de chaque action serveur de type webhook par neutralization - disable webhook ;
  • écrit database.is_neutralized = True et remplace database.secret par dummysecret.
mailretire le serveur forcé des modèles de courriel, archive les serveurs de relève (IMAP/POP), supprime les clés de notifications web push, la file mail_push et les appareils enregistrés.
paymentpasse tous les fournisseurs en mode test (is_live = False). Ils restent actifs et publiés.
iapsuffixe les jetons des comptes de services IAP par +disabled (SMS, enrichissement…).
webactive la vue web.neutralize_banner : le bandeau rouge (section 6).

Sur une autre base, la liste change avec les modules : website ajoute son ruban et un robots.txt fermé, les modules de paiement (Stripe, PayPal, Adyen…) et de caisse, les agendas Google et Microsoft, l'authentification OAuth, le stockage en nuage, les localisations à facturation électronique ont chacun leur fichier. Pour lire ce qui s'appliquera à ta base sans rien modifier :

./odoo-bin neutralize -c odoo.conf -d ma_base --stdout > neutralisation.sql

La sortie est le SQL exact, entre BEGIN; et COMMIT;, par exemple pour le module base :

-- deactivate crons
UPDATE ir_cron
   SET active = false
 WHERE id NOT IN (
       SELECT res_id
         FROM ir_model_data
        WHERE model = 'ir.cron'
          AND name = 'autovacuum_job'
          AND module = 'base'
);

Ce que la neutralisation ne touche pas

  • Les données : adresses des clients, courriels déjà en file d'attente, utilisateurs et leurs mots de passe restent ceux de la production. Le leurre empêche l'envoi, il n'efface rien.
  • Les modules sans neutralize.sql : un module maison qui appelle une API externe dans une méthode lancée à la main continue de l'appeler. Ajoute-lui son propre data/neutralize.sql, Odoo le prendra en compte de lui-même.
  • Le fichier de configuration : un smtp_server dans odoo.conf reste là, mais le serveur leurre, actif, passe avant lui.

5. db duplicate : rapide, mais pas sur une production en service

Sur le même serveur PostgreSQL, duplicate évite le passage par un fichier :

./odoo-bin db -c odoo.conf duplicate -n ma_base ma_base_essai

1,5 s, contre 7 s environ pour dump puis load, parce que PostgreSQL copie la base comme modèle (CREATE DATABASE … TEMPLATE ma_base), puis Odoo copie le filestore. Même nouvelle identité qu'un load, même option -n. Mais une base ne sert de modèle que si personne n'y est connecté : Odoo commence donc par couper toutes les connexions à la source. Une session psql ouverte sur ma_base pendant le duplicate :

FATAL: terminating connection due to administrator command SSL connection has been closed unexpectedly connection to server was lost

Sur une production, ce sont les utilisateurs connectés et les tâches planifiées en cours qui sautent. Pour copier la production, dump puis load -n ; duplicate sert à cloner une base de test ou de développement.

Les deux dernières opérations : db rename ancien nouveau renomme la base et son dossier de filestore (mêmes coupures de connexion), db drop ma_base_essai supprime les deux.

6. Vérifier la copie avant de l'ouvrir

Quatre requêtes suffisent, à lancer dans psql -d ma_base_test :

SELECT value AS neutralisee FROM ir_config_parameter WHERE key = 'database.is_neutralized';
SELECT count(*) FILTER (WHERE active) AS crons_actifs, count(*) AS crons FROM ir_cron;
SELECT name, smtp_host, active FROM ir_mail_server ORDER BY id;
SELECT count(*) AS fournisseurs_en_reel FROM payment_provider WHERE is_live;
neutralisee ------------- True (1 row) crons_actifs | crons --------------+------- 1 | 26 (1 row) name | smtp_host | active ---------------------------------+------------------+-------- Relais SMTP | smtp.example.com | f neutralization - disable emails | invalid | t (2 rows) fournisseurs_en_reel ---------------------- 0 (1 row)

Sur ma_base, les mêmes requêtes rendent 0 ligne, 23 tâches actives, le seul relais actif et 4 fournisseurs en réel.

À l'écran, le bandeau rouge s'affiche en haut de chaque page du client web. Dans Paramètres › Technique › Actions planifiées, seule la case « Actif » de l'aspiration automatique reste cochée :

Et l'épreuve du feu, dans la console (le shell Odoo 20), sans valider la transaction :

srv = env['fetchmail.server'].with_context(active_test=False).search([])
srv.write({'active': True, 'state': 'done'})
print("relève réactivée :", srv.name, srv.active, srv.state)
print("tâche de relève active :", env.ref('mail.ir_cron_mail_gateway_action').active)
mail = env['mail.mail'].create({'email_to': 'client@example.com', 'subject': 'Essai', 'body_html': '<p>Essai</p>'})
mail.send()
print("courriel :", mail.state, "|", mail.failure_type, "|", repr(mail.failure_reason))
relève réactivée : Boîte support True done tâche de relève active : False courriel : exception | False | '-2\nNom ou service inconnu'
  • Sur une base normale, confirmer un serveur de relève active la tâche « Mail: Fetchmail Service ». Sur une base neutralisée, ir.cron.toggle() lit database.is_neutralized et ne réactive rien : la boîte se configure, mais rien ne la relève.
  • Le courriel part vers le leurre, l'hôte invalid ne se résout pas, le message passe en exception. Le texte de l'erreur vient du système : « Name or service not known » sur un serveur en anglais.

Pour tester les courriels pour de vrai, ajoute un serveur sortant vers un piège à courriels local (MailHog, Mailpit…), jamais le relais de production.

Une copie non neutralisée sur le serveur de production

Le serveur Odoo lance les tâches planifiées de toutes les bases que son rôle PostgreSQL possède, sauf si db_name est fixé dans odoo.conf (odoo/service/server.py, cron_database_list) ; le dbfilter n'y change rien. Une copie chargée sans -n à côté de la production envoie donc sa file de courriels dans la minute. D'où la règle : toujours -n pour une copie, ou neutralize avant tout démarrage.

Dernier détail : charger avec -n le zip d'une base déjà neutralisée ajoute un second serveur leurre (le premier est archivé avec les autres). Sans gravité, mais inutile : recharge plutôt ce zip sans -n.

7. La même chose depuis le gestionnaire de bases

Quand le gestionnaire de bases est ouvert (list_db actif, mot de passe maître connu), la page /web/database/manager fait les mêmes opérations : ses fenêtres Restore et Duplicate ont chacune une case Neutralize (web/static/src/public/database_manager.qweb.html), qui appelle le même code que load -n et duplicate -n. Sur une production, ce gestionnaire est en général fermé (list_db = False) : la ligne de commande reste alors le seul chemin, et le plus facile à mettre dans un script.

Venant de la 19

  • Paiement : la 19 passait les fournisseurs à l'état « Désactivé » (state = 'disabled', sauf ceux déjà en test). La 20 n'a plus ce champ : elle les passe en mode test (is_live = False), ils restent actifs et publiés.
  • database.secret remplacé par dummysecret : nouveau en 20. Il ne se voit qu'avec neutralize sur place ou load --move -n ; un load ou un duplicate ordinaire génère de toute façon un nouveau secret.
  • db drop d'une base inexistante : la 19 répond « Database … does not exist. », la 20 sort sur une trace psycopg2.errors.InvalidCatalogName (code de sortie 1 dans les deux cas).
  • Inchangés : les six opérations de db, load --move, le refus des fichiers non zip, l'effacement des identifiants SMTP, neutralize --stdout.

Récapitulatif

  • db dump produit un zip SQL + manifeste + filestore, sans arrêter la production.
  • db load -n recharge sous un autre nom, neutralise avant tout démarrage et donne une nouvelle identité à la copie.
  • La neutralisation dépend des modules installés : neutralize --stdout montre le SQL exact pour ta base.
  • Elle coupe tâches planifiées, serveurs de courriel, relève, webhooks, paiements en réel, jetons IAP et notifications push ; elle n'efface aucune donnée.
  • db duplicate déconnecte tout le monde de la source : pas sur une production en service.
  • Avant d'ouvrir la copie : bandeau, quatre requêtes, un courriel d'essai qui doit échouer.
