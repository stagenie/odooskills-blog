Relier deux modèles Odoo 20 : les exemplaires

Un catalogue sait quels livres existent. Une bibliothèque doit savoir combien d'exemplaires elle possède, et où en est chacun. C'est la première relation un-à-plusieurs du module : un Many2one qui porte le lien, un One2many qui le reflète, et un compteur calculé qui se met à jour tout seul.

~15 minutes de lecture · niveau débutant · parcours Framework & ORM

Ce que tu vas apprendre

Le lien

Quel côté de la relation porte vraiment la colonne en base, et ce que décide ondelete.

Le miroir

Un One2many ne stocke rien : il relit le Many2one d'en face.

Le compteur

Un champ calculé stocké, recalculé à chaque mouvement grâce à @api.depends.

Prérequis

  • Le module biblio de l'article précédent, installé et fonctionnel : le modèle library.book, ses droits, sa liste, son formulaire et son menu.
  • Quelques livres enregistrés — les exemples de cet article en utilisent quatre.
  • Le serveur Odoo 20 joignable sur http://localhost:8069, base biblio.

Un livre, plusieurs exemplaires

Développement Odoo : le guide technique est un livre : un titre, un auteur, un ISBN. Mais la bibliothèque en possède trois volumes physiques, chacun avec son code d'inventaire et son état propre — l'un est sur l'étagère, l'autre est emprunté, le troisième a disparu. Un seul modèle ne peut pas porter les deux notions : il en faut un second.

C'est le point à retenir avant d'écrire la moindre ligne : c'est le côté « plusieurs » qui stocke le lien. L'exemplaire sait à quel livre il appartient ; le livre, lui, se contente de demander à Odoo « quels exemplaires pointent vers moi ? ».

1. Le modèle library.copy

Un fichier par modèle : crée models/library_copy.py.

from odoo import api, fields, models


class LibraryCopy(models.Model):
    _name = 'library.copy'
    _description = "Exemplaire"
    _order = 'book_id, name'

    name = fields.Char(string="Code d'inventaire", required=True, copy=False)
    book_id = fields.Many2one(
        'library.book',
        string="Livre",
        required=True,
        ondelete='cascade',
    )
    state = fields.Selection(
        [
            ('available', "Disponible"),
            ('borrowed', "Emprunté"),
            ('lost', "Perdu"),
        ],
        string="État",
        default='available',
        required=True,
    )
    acquisition_date = fields.Date(
        string="Date d'acquisition",
        default=fields.Date.context_today,
    )

Puis déclare-le dans models/__init__.py, à côté du premier :

from . import library_book
from . import library_copy

copy=FalseQuand on duplique un exemplaire, le code d'inventaire n'est pas repris : deux volumes ne peuvent pas porter le même numéro.
SelectionUne liste fermée de valeurs. La première partie du couple est stockée en base, la seconde est affichée.

1.1 Ce que ondelete décide

Un Many2one devient une vraie clé étrangère PostgreSQL. L'attribut ondelete dit à la base quoi faire quand le livre visé est supprimé. Trois valeurs :

ValeurEffet à la suppression du livre
'cascade'Les exemplaires sont supprimés avec lui. C'est le choix logique ici : un exemplaire sans livre n'existe pas.
'restrict'La suppression est refusée tant qu'il reste un exemplaire.
'set null'Le lien est vidé, l'exemplaire survit orphelin. Interdit si le champ est required.

La contrainte posée en base est lisible directement :

SELECT pg_get_constraintdef(c.oid)
  FROM pg_constraint c JOIN pg_class t ON t.oid = c.conrelid
 WHERE t.relname = 'library_copy' AND c.contype = 'f';
FOREIGN KEY (book_id) REFERENCES library_book(id) ON DELETE CASCADE

Le piège : ne rien écrire n'est pas neutre

Sans ondelete, Odoo en choisit un à ta place, et le choix dépend de required : 'restrict' pour un champ obligatoire, 'set null' sinon. Sur ce modèle, l'oubli donne donc restrict, et la suppression d'un livre qui possède des exemplaires échoue :

ForeignKeyViolation: update or delete on table "library_book" violates foreign key constraint "library_copy_book_id_fkey" on table "library_copy"

Dans l'interface, le message est plus aimable — « Un autre modèle utilise l'enregistrement que vous essayez de supprimer » — mais la suppression est bien bloquée. Choisir explicitement évite de découvrir la règle le jour où un utilisateur bute dessus.

Un détail utile : changer ondelete plus tard et relancer une mise à jour du module suffit. Odoo remplace la clé étrangère en place, sans perte de données.

1.2 Un code d'inventaire unique

Deux volumes ne peuvent pas porter le même code. Même mécanisme que l'ISBN de l'article précédent, en attribut de classe :

    _name_unique = models.Constraint(
        'UNIQUE(name)',
        "Ce code d'inventaire est déjà utilisé par un autre exemplaire.",
    )

Et, comme le livre, l'exemplaire mérite un nom affiché parlant :

    @api.depends('name', 'book_id.title')
    def _compute_display_name(self):
        for copy in self:
            copy.display_name = f"{copy.name} ({copy.book_id.title})"

Noter le chemin pointé dans @api.depends : 'book_id.title'. Il traverse la relation. Renommer un livre rafraîchit le nom affiché de tous ses exemplaires.

2. Les droits du nouveau modèle

Chaque modèle a besoin de sa propre ligne de droits — un modèle n'hérite de rien de son voisin, même lié. Ajoute la seconde ligne à security/ir.access.csv :

id,name,model_id,group_id/id,operation,domain
access_library_book_user,library.book utilisateur,library.book,base.group_user,crud,
access_library_copy_user,library.copy utilisateur,library.copy,base.group_user,crud,

C'est l'oubli le plus courant à l'ajout d'un modèle : le serveur démarre, le menu apparaît, et l'écran reste vide ou refuse l'enregistrement. Le journal, lui, l'annonce clairement au chargement.

3. Le miroir : copy_ids

Côté livre, on déclare le reflet de la relation. Dans models/library_book.py, sous les champs existants :

    copy_ids = fields.One2many(
        'library.copy',
        'book_id',
        string="Exemplaires",
    )

Deux arguments, et ils ne sont pas interchangeables : d'abord le modèle visé ('library.copy'), ensuite le nom du champ Many2one qui fait le lien de l'autre côté ('book_id'). Se tromper sur le second produit une erreur au chargement du registre, pas un affichage vide.

Ce champ ne crée aucune colonne. On peut le vérifier en base : seul le compteur de la section suivante y apparaît.

SELECT column_name FROM information_schema.columns
 WHERE table_name = 'library_book' AND column_name IN ('copy_ids', 'copy_count');
copy_count

Un One2many est une question posée à la base, pas une donnée : « donne-moi les exemplaires dont book_id vaut cet identifiant ». D'où une conséquence pratique — une relation un-à-plusieurs ne peut jamais exister seule : sans le Many2one d'en face, il n'y a rien à interroger.

4. Le compteur d'exemplaires

Afficher « 3 exemplaires » sur la fiche du livre demande un champ calculé. Toujours dans library_book.py :

    copy_count = fields.Integer(
        string="Nombre d'exemplaires",
        compute='_compute_copy_count',
        store=True,
    )

    @api.depends('copy_ids')
    def _compute_copy_count(self):
        for book in self:
            book.copy_count = len(book.copy_ids)

Trois éléments indissociables :

ÉlémentRôle
compute='_compute_copy_count'Le nom de la méthode, en chaîne de caractères. Elle affecte la valeur à chaque enregistrement de self.
store=TrueLe résultat est écrit en base. Sans lui, le champ est recalculé à chaque lecture, et il devient impossible de trier ou de filtrer dessus.
@api.depends('copy_ids')La liste des champs qui invalident le calcul. Sans ce décorateur, un champ stocké n'est jamais recalculé : il garde à jamais sa valeur du premier enregistrement.

Le stockage se vérifie en lisant directement la colonne, sans passer par Odoo :

SELECT title, copy_count FROM library_book ORDER BY title;

La valeur suit tous les mouvements : ajout d'un exemplaire, suppression, et même réaffectation. Déplacer un exemplaire d'un livre vers un autre décrémente le premier compteur et incrémente le second, dans la même écriture — Odoo sait que les deux enregistrements dépendent du champ modifié.

Stocké ou non stocké ?

Un champ calculé non stocké se recalcule à chaque affichage : c'est le bon choix pour une valeur qui ne sert qu'à l'écran. Dès qu'on veut trier, filtrer, grouper ou afficher la valeur dans une vue liste sur de gros volumes, il faut store=True — et donc un @api.depends exact, car c'est lui seul qui garantit la fraîcheur de la colonne.

5.2 Les exemplaires dans la fiche du livre

Le plus utile reste de voir les exemplaires depuis le livre. Dans views/library_book_views.xml, ajoute le compteur dans la colonne de droite, puis un onglet sous les groupes existants :

                            <field name="page_count"/>
                            <field name="copy_count"/>
                            <field name="active"/>
                        </group>
                    </group>
                    <group string="Résumé">
                        <field name="summary" nolabel="1"/>
                    </group>
                    <notebook>
                        <page string="Exemplaires" name="copies">
                            <field name="copy_ids">
                                <list editable="bottom">
                                    <field name="name"/>
                                    <field name="state"/>
                                    <field name="acquisition_date"/>
                                </list>
                            </field>
                        </page>
                    </notebook>

Trois choses se jouent ici :

  • <notebook> crée la zone à onglets sous le corps du formulaire ; <page> en est un. L'attribut name sert aux surcharges futures, string est le libellé visible.
  • Une vue liste déclarée à l'intérieur du champ ne vaut que pour cet emplacement. Elle n'a pas besoin d'enregistrement ir.ui.view séparé.
  • editable="bottom" autorise la saisie directement dans la ligne, sans ouvrir de fenêtre. Les nouvelles lignes s'ajoutent en bas ; editable="top" les met en tête.

Inutile de répéter book_id dans cette liste : Odoo le remplit tout seul avec le livre ouvert. Le déclarer y afficherait une colonne redondante, éditable, sur laquelle un utilisateur peut se tromper.

Ce qui change depuis Odoo 19

Sur ce terrain, rien. Many2one, One2many, ondelete, compute/store, @api.depends et <notebook> s'écrivent exactement comme en version 19 — la balise de la vue tabulaire est <list> depuis la 17. Le seul fichier réellement propre à la version 20 dans cet article est security/ir.access.csv, qui a remplacé ir.model.access.csv et les règles ir.rule.

Après l'ajout d'un champ ou d'un fichier de données, toujours un -u : le rechargement automatique des sources ne crée ni colonne ni vue.

Récapitulatif

  • Le côté « plusieurs » porte la colonne et la clé étrangère ; le One2many d'en face ne stocke rien.
  • Le second argument d'un One2many est le nom du champ Many2one qui fait le lien, pas un champ du modèle courant.
  • Sans ondelete explicite, Odoo choisit 'restrict' pour un champ obligatoire et 'set null' sinon.
  • Un champ calculé stocké sans @api.depends n'est jamais recalculé — c'est une panne silencieuse.
  • Chaque nouveau modèle exige sa propre ligne dans security/ir.access.csv.
  • <list editable="bottom"> à l'intérieur d'un champ relationnel suffit à rendre les lignes saisissables ; aucune vue séparée n'est nécessaire.

La suite de la série fait entrer les adhérents, et avec eux les emprunts : une relation de plus, mais cette fois entre trois modèles.
