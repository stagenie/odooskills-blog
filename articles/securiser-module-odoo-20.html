Sécuriser son module Odoo 20 : ir.access, groupes, sudo, contrôleurs

Un module peut laisser fuir ses données par trois portes : une ligne d'accès mal comprise, un sudo() de trop, une route HTTP qui lit à la place de l'utilisateur. Cet article les ferme une à une sur un petit module de demandes internes, mesures à l'appui : qui voit quoi, comment se combinent les lignes ir.access, ce que fait vraiment sudo(), comment écrire une route user, public ou bearer, et les tests qui le prouvent.

~15 minutes de lecture · niveau intermédiaire · parcours Framework & ORM

Ce que tu vas apprendre

Cloisonner

Écrire des lignes ir.access à domaine (par utilisateur, par société) et prévoir leur combinaison au lieu de la découvrir.

Contrôler

Vérifier un droit dans le code, placer sudo() là où il ne fuit pas, et fermer les routes HTTP qui contournent les droits.

Prouver

Des tests qui attendent une AccessError ou un 404, et le portage sans surprise d'une sécurité écrite pour la 19.

Prérequis

  • Connaître le modèle ir.access, ses colonnes et la différence entre permission et restriction : c'est l'objet de Les droits d'accès en Odoo 20 : ir.access. Ici, on part de là.
  • Une base Odoo 20 Community de test, ma_base, avec les données de démonstration (elles fournissent trois sociétés), et la console odoo-bin shell -d ma_base.
  • Le module d'exemple oski_demandes_droits (version 20.0.1.0.0), et trois utilisateurs internes créés pour l'essai : Demandeur A (dem_a, société San Francisco), Demandeur B (dem_b, San Francisco et My US Company), Valideur (valideur, San Francisco). Cinq demandes : deux de A, une de B dans chaque société, une de l'administrateur dans My US Company, déjà approuvée.

1. Le module et sa matrice

Le module gère des demandes internes (oski.demande : objet, type, demandeur, société, montant, état) et leurs types (oski.demande.type). Deux groupes, rangés sous un privilège « Demandes internes » : Demandeur (crée ses demandes, ne voit que les siennes) et Valideur (voit et approuve toutes les demandes de ses sociétés ; il implique le groupe Demandeur). Toute la sécurité tient dans security/ir.access.csv :

id,name,model_id,group_id/id,operation,domain
demande_type_tous,Types de demande : lecture pour tous,oski.demande.type,base.group_everyone,r,
demande_type_valideur,Types de demande : gestion,oski.demande.type,group_demande_valideur,crud,
demande_siennes,Demandes : les siennes,oski.demande,group_demande_user,cru,"[('user_id', '=', user.id)]"
demande_toutes,Demandes : toutes,oski.demande,group_demande_valideur,crud,
demande_societes,Demandes : sociétés autorisées,oski.demande,,crud,"[('company_id', 'in', company_ids)]"
demande_figee,Demandes : une demande approuvée est figée,oski.demande,,ud,"[('state', '!=', 'approved')]"

Rappel en une phrase : une ligne avec groupe est une permission, une ligne sans groupe est une restriction qui s'applique à tout le monde. Les deux dernières lignes sont des restrictions : le cloisonnement par société, et le gel des demandes approuvées (opérations ud : modifier et supprimer).

2. Qui voit quoi : mesurer au lieu de deviner

Le domaine qu'Odoo ajoute à chaque recherche d'un utilisateur se lit directement : _access_domain(opération) renvoie le domaine final, une fois toutes les lignes combinées. C'est l'outil de diagnostic le plus utile de la sécurité Odoo 20. Dans la console :

Demande = env['oski.demande']
for login in ('dem_a', 'dem_b', 'valideur', 'admin'):
    user = env['res.users'].search([('login', '=', login)])
    print(login, Demande.with_user(user).search_count([]), Demande.with_user(user)._access_domain('read'))
dem_a 2 ['&', ('user_id', '=', 8), ('company_id', 'in', [1])] dem_b 2 ['&', ('user_id', '=', 9), ('company_id', 'in', [1, 2])] valideur 3 [('company_id', 'in', [1])] admin 5 [('company_id', 'in', [1, 3, 2])]
  • Demandeur A : sa permission (user_id = user.id) ET la restriction de société. Deux demandes.
  • Demandeur B : même forme, mais deux sociétés autorisées. Il voit sa demande de San Francisco et celle de My US Company.
  • Valideur : il est aussi Demandeur (le groupe est impliqué), donc deux permissions s'appliquent : « les siennes » OU « toutes ». Le OU avec une ligne sans domaine vaut « tout » : il ne reste que la restriction de société. Trois demandes, toutes de San Francisco.
  • Administrateur : il est Valideur (le module l'y place à l'installation) et a les trois sociétés. Les cinq demandes.

Dans le domaine, user et company_ids sont évalués pour l'utilisateur et le contexte de la requête. company_ids vaut les sociétés cochées dans le sélecteur de sociétés, pas toutes celles de la fiche utilisateur :

Hors contexte (console, action planifiée), ce sont toutes les sociétés de l'utilisateur.

3. Combiner les lignes : OU des permissions, ET des restrictions

Chaque opération a son propre domaine. Pour l'écriture, la restriction « figée » s'ajoute aux deux autres :

from odoo.exceptions import AccessError
Demande = env['oski.demande']
valideur = env['res.users'].search([('login', '=', 'valideur')])
admin = env.ref('base.user_admin')
print(Demande.with_user(valideur)._access_domain('write'))
formation = Demande.search([('name', '=', 'Formation Odoo')])
formation.with_user(valideur).action_approve()
for user in (valideur, admin):
    try:
        formation.with_user(user).write({'montant': 950})
    except AccessError as e:
        print(user.name, '->', str(e).splitlines()[2])
formation.sudo().write({'montant': 950})
print('console (superutilisateur) :', formation.montant)
env.cr.rollback()
['&', ('company_id', 'in', [1]), ('state', 'not in', ['approved'])] Valideur -> Désolé, Valideur (id=10) n'a pas d'accès 'écrire' à : Mitchell Admin -> Désolé, Mitchell Admin (id=2) n'a pas d'accès 'écrire' à : console (superutilisateur) : 950.0

Deux choses à retenir. Les restrictions se cumulent (ET) et ne s'additionnent jamais : chacune réduit encore ce que les permissions ont ouvert. Et une restriction s'applique aussi à l'administrateur : seul le superutilisateur (celui de la console, des actions planifiées système et de sudo()) passe outre. Une demande approuvée ne se modifie plus, par personne ; si l'administrateur doit pouvoir la corriger, la restriction doit le prévoir dans son domaine.

Côté permissions, c'est l'inverse : elles s'additionnent (OU). Une permission sans domaine, posée sur un groupe large, rend inutile toute permission à domaine posée sur un groupe plus étroit pour les mêmes opérations. La section 10 montre ce que cela donne quand on porte un module 19.

Pour relire les lignes d'un modèle, le menu Paramètres › Technique › Sécurité › Droits d'accès (mode développeur) liste tout, avec une colonne Type qui distingue permission et restriction :

Le menu « Règles d'enregistrement » de la 19 a disparu avec le modèle ir.rule : droits et domaines sont dans cette seule liste.

4. « Pour tout le monde » : base.group_everyone, jamais un groupe vide

La première ligne du fichier donne la lecture des types à base.group_everyone (« Rôle / Tout le monde », qui contient les utilisateurs internes, portail et public). Recopier l'habitude de la 19, groupe vide pour « tout le monde », produit l'inverse. Essai dans une transaction annulée :

Type = env['oski.demande.type']
dem_a = env['res.users'].search([('login', '=', 'dem_a')])
admin = env.ref('base.user_admin')
ligne = env.ref('oski_demandes_droits.demande_type_tous')
ligne.group_id = False                      # ce qu'on écrit en recopiant un « tout le monde » de la 19
print(ligne.kind, Type.with_user(dem_a).has_access('read'), Type.with_user(admin).has_access('read'))
print(Type.with_user(dem_a)._access_domain('read'), Type.with_user(admin)._access_domain('read'))
env.cr.rollback()
env['ir.access']._clear_caches()
print(ligne.group_id.display_name, Type.with_user(dem_a).has_access('read'))
restriction False True [(0, '=', 1)] [(1, '=', 1)] Rôle / Tout le monde True

La ligne devient une restriction, qui n'ouvre rien. Le demandeur n'a plus aucune permission sur les types : domaine toujours faux, il ne lit plus rien. L'administrateur lit encore, mais seulement grâce à sa permission « gestion » de Valideur : le défaut passe inaperçu si l'on teste en administrateur. Après le rollback(), env['ir.access']._clear_caches() est nécessaire : les droits sont gardés dans un cache que invalidate_ormcache(), sans argument, ne vide pas (l'écriture sur la ligne, elle, le vide d'elle-même).

5. Groupes, privilège et rôle

Les groupes se déclarent comme en 19 : un enregistrement res.groups.privilege (rangé dans une catégorie de modules) et des groupes qui le référencent par privilege_id, chaînés par implied_ids. La fiche utilisateur affiche alors un seul champ par privilège :

Au-dessus, le champ Rôle propose trois valeurs en 20 : Light, User, Administrateur. Il est calculé à partir des groupes donnés directement à l'utilisateur. Un utilisateur créé avec le seul groupe Demandeur (qui implique pourtant « utilisateur interne ») a un rôle vide : c'est ce qu'ont donné nos trois comptes à leur création. En ajoutant base.group_user à leurs groupes, le rôle devient « User ». Même réflexe dans les tests, plus bas : new_test_user reçoit base.group_user en plus du groupe métier.

6. Vérifier un droit dans le code : has_access, check_access, _filtered_access

Trois méthodes, publiques sur tout recordset :

print(toutes._filtered_access('read').mapped('name'))
try:
    toutes.check_access('read')
except AccessError as e:
    print(str(e).splitlines()[2:4])
for nom in ('check_access_rights', 'check_access_rule'):
    print(nom, hasattr(toutes, nom))
for modele in ('ir.model.access', 'ir.rule'):
    try:
        env[modele]
    except KeyError as e:
        print('KeyError', e)
True False True False ['Formation Odoo', 'Écran 27 pouces'] ["Désolé, Demandeur A (id=8) n'a pas d'accès 'lire' à :", '- Demande interne (oski.demande)'] check_access_rights False check_access_rule False KeyError 'ir.model.access' KeyError 'ir.rule'
  • has_access(op) renvoie un booléen. Sur un recordset vide, il répond pour le modèle (« a-t-il au moins une permission ? ») ; sur des enregistrements, pour l'ensemble : vrai seulement si tous sont accessibles. Le demandeur peut lire le modèle, pas les cinq demandes ensemble, mais bien la sienne. Il ne peut pas supprimer.
  • _filtered_access(op) garde les enregistrements accessibles, sans erreur.
  • check_access(op) lève l'AccessError, la même que l'utilisateur voit à l'écran.
  • check_access_rights et check_access_rule n'existent plus, pas plus que les modèles ir.model.access et ir.rule : un module qui les appelle casse au premier appel.

À l'écran, le demandeur qui ouvre par son URL la demande d'un collègue reçoit cette erreur :

Un bouton masqué n'est pas une sécurité

Le bouton « Approuver » porte groups="oski_demandes_droits.group_demande_valideur" dans la vue. Mais le demandeur a le droit de modifier ses demandes (cru), et n'importe quel appel RPC peut écrire state ou appeler action_approve sans passer par la vue. Le contrôle est donc dans le modèle, sur l'écriture elle-même :

7. sudo() et with_user() : ce qui change vraiment

Demande = env['oski.demande']
dem_a = env['res.users'].search([('login', '=', 'dem_a')])
valideur = env['res.users'].search([('login', '=', 'valideur')])
d = Demande.with_user(dem_a)
print(d.search_count([]), d.sudo().search_count([]), d.sudo().env.user.login)
cree = d.sudo().create({'name': "Créée en sudo"})
print(cree.create_uid.login, cree.user_id.login, cree.env.su, cree.user_id.env.su)
v = d.sudo().with_user(valideur)
print(v.env.user.login, v.env.su, v.search_count([]))
env.cr.rollback()
2 5 dem_a dem_a dem_a True True valideur False 4
  • sudo() ne change pas d'utilisateur : env.user reste le demandeur, la demande créée porte son nom en create_uid et en demandeur par défaut. Il supprime tous les contrôles : le demandeur voit alors les cinq demandes, toutes sociétés confondues.
  • Le drapeau suit les enregistrements : cree.user_id, lu à travers un recordset en sudo, est lui aussi en sudo. Tout ce qu'on atteint par lui échappe aux droits.
  • with_user(u) change d'utilisateur et remet su à faux : le valideur, même atteint depuis un recordset en sudo, retrouve ses droits (4 : les trois demandes de sa société et celle qu'on vient de créer).

Le bon usage de sudo() tient en une règle : sur le plus petit recordset, le plus tard possible, et pour un résultat qui ne contient aucun enregistrement que l'appelant n'a pas le droit de voir. Le module en a un exemple : un comptage par état, sans aucun champ des demandes.

    @api.model
    def _stats_publiques(self):
        """Nombre de demandes par état, sans rien d'autre : seul usage public."""
        groupes = self.sudo()._read_group([], ['state'], ['__count'])
        return {state: count for state, count in groupes}

Le reste de l'environnement (with_context, with_company, les clés de contexte) est détaillé dans env, with_context, sudo, with_company : l'environnement en Odoo 20.

8. Contrôleurs : user, public, bearer

Une route HTTP choisit d'abord qui est l'utilisateur, par son paramètre auth : 'user' exige une session, 'public' prend l'utilisateur public si personne n'est connecté, 'bearer' accepte une clé d'API dans l'en-tête Authorization. Ensuite, tout ce que fait la méthode se fait avec les droits de cet utilisateur… sauf si elle passe par sudo().

La fuite

Une route qui renvoie une demande en JSON, écrite vite :

    @http.route('/oski/demandes/<int:demande_id>/json', type='http', auth='user', methods=['GET'])
    def demande_json(self, demande_id):
        demande = request.env['oski.demande'].sudo().browse(demande_id)
        return request.make_json_response(demande.read(CHAMPS, load=None)[0])

Connecté en Demandeur A (cookie de session obtenu par /web/session/authenticate), il suffit de changer le numéro dans l'URL. Dans les sorties ci-dessous, le corps HTML des pages d'erreur est remplacé par … :

for id in 1 3 4 5 99; do curl -s -b cookies_dem_a -w "  [%{http_code}]\n" http://localhost:8069/oski/demandes/$id/json; done
{"id": 1, "name": "Écran 27 pouces", "user_id": 8, "company_id": 1, "montant": 320.0, "state": "draft"} [200] {"id": 3, "name": "Casque audio", "user_id": 9, "company_id": 1, "montant": 85.0, "state": "submitted"} [200] {"id": 4, "name": "Salon professionnel", "user_id": 9, "company_id": 2, "montant": 1450.0, "state": "draft"} [200] {"id": 5, "name": "Licence logicielle", "user_id": 2, "company_id": 2, "montant": 600.0, "state": "approved"} [200] … [500]

Les demandes d'un collègue, celles d'une société où il n'a pas accès, celle de l'administrateur : tout sort. Le numéro inexistant donne une erreur 500 (IndexError dans le journal), ce qui renseigne aussi sur les numéros qui existent. auth='user' a seulement vérifié qu'il y avait une session.

La correction

    @http.route('/oski/demandes/<int:demande_id>/json', type='http', auth='user', methods=['GET'])
    def demande_json(self, demande_id):
        # Pas de sudo() : browse() dans l'environnement de l'utilisateur connecté,
        # puis has_access() avant de lire. Une demande d'un autre = 404, comme une demande absente.
        demande = request.env['oski.demande'].browse(demande_id).exists()
        if not demande or not demande.has_access('read'):
            raise NotFound()
        return request.make_json_response(demande.read(CHAMPS, load=None)[0])
{"id": 1, "name": "Écran 27 pouces", "user_id": 8, "company_id": 1, "montant": 320.0, "state": "draft"} [200] … [404] … [404] … [404] … [404]

La demande d'un autre et une demande absente répondent pareil : rien ne permet de deviner ce qui existe. Autre écriture possible, le convertisseur <model("oski.demande"):demande> dans l'URL : Odoo vérifie lui-même la lecture avant d'appeler la méthode. Mesuré : 200 pour sa demande, 404 pour un numéro absent, mais 403 avec le message « Oups ! … n'a pas d'accès 'lire' » pour la demande d'un collègue, qui confirme donc son existence.

Le piège : sudo() pour « faire marcher » une route

Une route qui renvoie une AccessError en développement se « répare » en une ligne avec sudo(). Elle ne renvoie plus d'erreur à personne, y compris à ceux qui ne devaient rien voir, et rien dans le journal ne le signale. Dans un contrôleur, n'appliquer sudo() qu'à un calcul dont le résultat ne contient aucun enregistrement (un comptage, un jeton, un paramètre), jamais à ce qu'on renvoie.

auth='public' : le sudo borné

    @http.route('/oski/demandes/stats', type='http', auth='public', methods=['GET'])
    def demandes_stats(self):
        # sudo() utile et borné : des comptages, aucun enregistrement ne sort.
        return request.make_json_response(request.env['oski.demande']._stats_publiques())
$ curl -s http://localhost:8069/oski/demandes/stats {"draft": 2, "submitted": 2, "approved": 1}

Sans session, la requête tourne sous l'utilisateur public, qui n'a aucun droit sur les demandes : sans le sudo() de _stats_publiques, le comptage échouerait. Avec, seuls des nombres sortent. À comparer avec la route JSON en auth='user', qui redirige un visiteur anonyme vers la page de connexion (303).

auth='bearer' : une clé d'API, les droits de son propriétaire

    @http.route('/oski/api/demandes', type='http', auth='bearer', bearer_scope='rpc', methods=['GET'], csrf=False)
    def api_demandes(self):
        # Clé d'API : la requête s'exécute sous l'utilisateur de la clé, avec ses droits.
        demandes = request.env['oski.demande'].search([])
        return request.make_json_response(demandes.read(CHAMPS, load=None))

La clé se crée depuis les préférences de l'utilisateur (onglet Sécurité), ou dans la console pour un essai :

import datetime
a = env['res.users'].search([('login', '=', 'dem_a')])
k = env['res.users.apikeys'].with_user(a)._generate('rpc', 'Script de test', datetime.datetime.now() + datetime.timedelta(days=1))
env.cr.commit()
print("KEY", k)
curl -s -H "Authorization: Bearer $CLE" http://localhost:8069/oski/api/demandes
curl -s http://localhost:8069/oski/api/demandes
curl -s -H "Authorization: Bearer 0000" http://localhost:8069/oski/api/demandes
curl -s -b cookies_dem_a http://localhost:8069/oski/api/demandes

Chaque commande reçoit en plus -w " [%{http_code}]" ; pour les refus, seul le message de la page d'erreur est recopié, et les champs des demandes renvoyées sont abrégés.

[{"id": 2, "name": "Formation Odoo", …}, {"id": 1, "name": "Écran 27 pouces", …}] [200] User not authenticated, use an API Key with a Bearer Authorization header. [401] Invalid apikey [401] Missing "Authorization" or Sec-headers for interactive usage. [401]

Avec la clé du Demandeur A, la route renvoie ses deux demandes et rien d'autre : le search([]) est filtré par ses lignes ir.access, sans une ligne de contrôle dans la méthode. Sans clé, une session ne suffit pas depuis un script : il faut les en-têtes Sec-Fetch-* qu'envoie un navigateur qui ouvre la page (avec eux, la même session obtient 200). Le décorateur pose save_session=False sur une route bearer : l'appel par clé n'enregistre pas de session.

bearer_scope est obligatoire en 20 : sans lui, le décorateur échoue dès l'import du contrôleur, donc au chargement du module.

AssertionError: bearer_scope must be set for auth='bearer'

La clé de l'essai a été créée avec la portée rpc, celle que déclare la route.

9. Des tests qui prouvent la sécurité

Une sécurité non testée se dégrade au premier « correctif ». Les tests du module créent leurs utilisateurs avec new_test_user (groupes en liste d'identifiants externes) et vérifient les refus autant que les accès :

from odoo.exceptions import AccessError
from odoo.tests import TransactionCase, new_test_user, tagged


@tagged('post_install', '-at_install')
class TestDroitsDemandes(TransactionCase):

    @classmethod
    def setUpClass(cls):
        super().setUpClass()
        groupes = 'base.group_user,oski_demandes_droits.group_demande_user'
        cls.societe = cls.env.company
        cls.autre_societe = cls.env['res.company'].create({'name': "Société B"})
        cls.dem_a = new_test_user(cls.env, 'test_dem_a', groupes)
        cls.dem_b = new_test_user(cls.env, 'test_dem_b', groupes)
        cls.valideur = new_test_user(
            cls.env, 'test_valideur', 'base.group_user,oski_demandes_droits.group_demande_valideur')
        Demande = cls.env['oski.demande']
        cls.demande_a = Demande.create({'name': "Écran", 'user_id': cls.dem_a.id})
        cls.demande_b = Demande.create({'name': "Casque", 'user_id': cls.dem_b.id})
        cls.demande_ailleurs = Demande.create({
            'name': "Salon", 'user_id': cls.dem_b.id, 'company_id': cls.autre_societe.id})

    def test_demandeur_ne_voit_que_les_siennes(self):
        Demande = self.env['oski.demande'].with_user(self.dem_a)
        self.assertEqual(Demande.search([]), self.demande_a)
        with self.assertRaises(AccessError):
            self.demande_b.with_user(self.dem_a).read(['name'])
        self.assertFalse(self.demande_b.with_user(self.dem_a).has_access('read'))

    def test_demande_approuvee_figee_pour_tous(self):
        self.demande_a.with_user(self.valideur).action_approve()
        for user in (self.valideur, self.env.ref('base.user_admin')):
            with self.assertRaises(AccessError):
                self.demande_a.with_user(user).write({'montant': 10})

Le piège : une conversion qui élargit sans erreur

À retenir

  • Les permissions (avec groupe) s'additionnent, les restrictions (sans groupe) se cumulent et touchent aussi l'administrateur. _access_domain('read') montre le résultat pour un utilisateur donné.
  • « Tout le monde » s'écrit base.group_everyone. Une ligne sans groupe ferme au lieu d'ouvrir, et l'administrateur peut ne rien remarquer.
  • Une règle métier (qui approuve) se vérifie dans le modèle, sur l'écriture : la vue n'arrête pas un appel RPC.
  • sudo() garde l'utilisateur et enlève tous les contrôles, jusque sur les enregistrements liés. Dans un contrôleur, jamais sur ce qui est renvoyé ; has_access() puis 404.
  • Après un portage 19 → 20, testez chaque profil : une permission large sans domaine élargit en silence ce qu'une règle de groupe restreignait.
