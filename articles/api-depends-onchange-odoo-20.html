@api.depends ou @api.onchange : choisir et dépanner en Odoo 20

Un champ qui se remplit tout seul : calcul ou onchange ? Le premier vit dans l'ORM et suit chaque écriture, le second ne vit que dans le formulaire. Les trois formes de calcul, ce que l'onchange sait encore faire, et les six raisons, toutes reproduites, pour lesquelles « l'onchange ne part pas ».

~13 minutes de lecture · niveau intermédiaire · parcours Framework & ORM

Ce que tu vas apprendre

Choisir

Calcul non stocké, store=True, readonly=False, ou @api.onchange : qui part quand, et depuis où.

Dépanner

Appel ORM, champ absent ou en lecture seule, chemin pointé, domaine renvoyé, surcharge sans décorateur : six pannes, six symptômes.

Rejouer

Form de odoo.tests pour déclencher un onchange depuis la console ou un test, comme le ferait l'écran.

Prérequis

  • Une base Odoo 20 avec l'application Ventes et ses données de démonstration.
  • Un petit module de démonstration, donné en entier au § 2, qui ajoute six champs au devis (sale.order). L'onchange natif de la date de livraison (§ 4) se rejoue sans lui.
  • La console odoo-bin shell, où chaque extrait a été exécuté. Elle est présentée dans l'article sur la console.

1. Deux mécanismes, deux endroits

Les deux décorateurs répondent à « quand A change, mets à jour B », mais pas au même endroit.

  • @api.depends déclare la méthode de calcul d'un champ. C'est l'ORM qui la rappelle dès qu'une dépendance change : create, write, import, appel externe, action planifiée, et aussi le formulaire.
  • @api.onchange déclare une réaction du formulaire : le client web l'appelle quand l'utilisateur modifie un champ, sur un enregistrement provisoire qui n'est pas encore en base. Hors formulaire, personne ne l'appelle.

Déclenché partoute écriture d'une dépendance, par n'importe quel cheminune saisie dans un formulaire (client web, ou Form en test)

2. Le module de démonstration

Un module demo_onchange (manifeste en 20.0.1.0.0, dépendance sale) hérite du devis. Trois champs calculés, un sous chaque forme, trois champs remplis par un onchange, et deux onchanges volontairement fautifs pour la suite :

from odoo import api, fields, models


class SaleOrder(models.Model):
    _inherit = 'sale.order'

    # 1. calcul non stocké : recalculé à chaque lecture
    line_count = fields.Integer("Nombre de lignes", compute='_compute_line_count')
    # 2. calcul stocké, dépendance par chemin pointé
    partner_country = fields.Char("Pays du client", compute='_compute_partner_country', store=True)
    # 3. calcul stocké ET modifiable : la valeur proposée peut être corrigée
    delivery_city = fields.Char("Ville de livraison", compute='_compute_delivery_city',
                                store=True, readonly=False)
    # 4. champs remplis par un onchange
    onchange_note = fields.Char("Note (onchange)")
    hidden_note = fields.Char("Note hors vue")
    locked_note = fields.Char("Note en lecture seule")
    invisible_note = fields.Char("Note invisible")

    @api.depends('order_line')
    def _compute_line_count(self):
        for order in self:
            order.line_count = len(order.order_line)

    @api.depends('partner_id.country_id')
    def _compute_partner_country(self):
        for order in self:
            order.partner_country = order.partner_id.country_id.name

    @api.depends('partner_id')
    def _compute_delivery_city(self):
        for order in self:
            order.delivery_city = order.partner_id.city

    @api.onchange('partner_id')
    def _onchange_partner_note(self):
        self.onchange_note = f"Client choisi : {self.partner_id.name}"
        self.hidden_note = f"Client choisi : {self.partner_id.name}"
        self.locked_note = f"Client choisi : {self.partner_id.name}"
        self.invisible_note = f"Client choisi : {self.partner_id.name}"

    @api.onchange('partner_id.city')            # fautif : chemin pointé
    def _onchange_partner_city(self):
        self.onchange_note = "La ville du client a changé"

    @api.onchange('partner_id')                 # fautif : renvoie un domaine
    def _onchange_partner_domain(self):
        return {'domain': {'user_id': [('id', '=', self.env.uid)]}}

La vue ajoute cinq de ces champs sous le client. hidden_note n'y figure pas, locked_note y est en lecture seule, invisible_note y est masqué :

Rien à déclarer dans ir.access.csv : le module n'ajoute aucun modèle, seulement des champs sur un modèle qui a déjà ses droits.

3. Les trois formes d'un champ calculé

Tout se passe en Python, sans formulaire : un devis pour Acme Corporation, une correction à la main, un changement de client, puis un changement de pays chez ce client.

SO = env['sale.order']
acme = env['res.partner'].browse(10)
gemini = env['res.partner'].browse(11)
order = SO.create({'partner_id': acme.id})
print("create :", order.partner_country, "|", order.delivery_city, "|", order.onchange_note)
order.delivery_city = 'Oakland'
print("saisie :", order.delivery_city)
order.partner_id = gemini
print("write  :", order.partner_country, "|", order.delivery_city, "|", order.onchange_note)
gemini.country_id = env.ref('base.it')
print("pays   :", order.partner_country)
env.flush_all()
env.cr.execute("SELECT partner_country, delivery_city FROM sale_order WHERE id = %s", [order.id])
print("SQL    :", env.cr.fetchone())
create : États-Unis | Pleasant Hill | False saisie : Oakland write : Saint-Marin | Serravalle | False pays : Italie SQL : ('Italie', 'Serravalle')

Ligne par ligne :

  • create a calculé le pays et la ville. La note, elle, est vide : _onchange_partner_note n'a pas été appelé. C'est la première cause du § 5.
  • Saisie : delivery_city est readonly=False, la valeur tapée est gardée et stockée.
  • Changement de client : la dépendance partner_id a changé, le calcul repart et écrase « Oakland » par Serravalle. C'est le contrat du calcul modifiable : une valeur proposée, que l'utilisateur peut corriger, jusqu'au prochain changement de ce dont elle dépend.
  • Pays : le devis n'a pas été touché, seul le client l'a été. La dépendance pointée partner_id.country_id suffit pour que l'ORM recalcule partner_country de toutes les commandes de ce client, et la ligne SQL montre la valeur stockée en base.

Le champ non stocké, lui, est calculé à la lecture, et n'existe pas pour SQL :

print("lignes :", order.line_count)
env['sale.order.line'].create({'order_id': order.id, 'product_id': env.ref('product.product_product_4').id})
print("lignes :", order.line_count)
print("Italie :", SO.search_count([('partner_country', '=', 'Italie')]))
print(SO.search_count([('line_count', '>', 0)]))
lignes : 0 lignes : 1 Italie : 18 ValueError : Field has no SQL representation because it is not stored in condition ('line_count', '>', 0)

Les 18 commandes de Gemini Furniture (17 de la démonstration et le devis neuf) sont désormais « Italie » en base, et on peut chercher dessus. Chercher sur line_count lève une erreur : un calcul non stocké se recherche seulement si on lui écrit une méthode search=.

Le calcul modifiable remplace la plupart des onchange

« Quand le client change, propose sa ville » s'écrivait autrefois en onchange. En calcul stocké modifiable, la même règle s'applique aussi à un devis créé par import, par l'API ou par une autre méthode, et l'utilisateur garde la main (voir les champs calculés en Odoo 20). C'est la forme qu'utilise Odoo lui-même : price_unit et name des lignes de commande sont des calculs stockés readonly=False (addons/sale/models/sale_order_line.py). Réserver @api.onchange à ce qui n'a de sens qu'à l'écran : un avertissement, ou une modification qui ne doit jamais se produire hors saisie.

4. Ce que fait un onchange, à l'écran

Dans le formulaire d'un devis neuf, choisir Acme Corporation déclenche à la fois l'onchange et les calculs dont un champ est affiché : pays, ville et notes se remplissent avant tout enregistrement. Puis on enregistre :

La note en lecture seule était bien remplie à l'écran, puis elle est perdue à l'enregistrement : c'est l'une des pannes du § 5. Avant d'y venir, l'autre usage de l'onchange, celui qu'aucun calcul ne remplace : prévenir l'utilisateur. Odoo l'utilise sur le devis (addons/sale/models/sale_order.py) :

@api.onchange("commitment_date", "expected_date")
def _onchange_commitment_date(self):
    """Warn if the commitment dates is sooner than the expected date."""
    if (
        self.commitment_date
        and self.expected_date
        and self.commitment_date < self.expected_date
    ):
        return {
            "warning": {
                "title": self.env._("Requested date is too soon."),
                "message": self.env._(
                    "The delivery date is sooner than the expected date."
                    " You may be unable to honor the delivery date."
                ),
            }
        }

Sur le devis S00003 de la démonstration, saisir une date de livraison antérieure à la date prévue ouvre ce dialogue :

Avec 'type': 'notification' dans le dictionnaire warning, le même message s'affiche en notification au lieu d'un dialogue (docstring de api.onchange, odoo/orm/decorators.py). Le dialogue n'empêche rien : la date reste saisie.

5. « L'onchange ne part pas » : six causes

5.1 Le code passe par create ou write

La cause la plus fréquente, et ce n'est pas un défaut. Le même devis S00003, la même date trop proche, d'abord par write, puis par un formulaire simulé :

import datetime
from odoo.tests import Form
order = env['sale.order'].search([('name', '=', 'S00003')])
print(order.name, order.expected_date)
early = order.expected_date - datetime.timedelta(days=3)
order.write({'commitment_date': early})
print("write :", order.commitment_date)
with Form(order) as f:
    f.commitment_date = early - datetime.timedelta(days=1)
S00003 2026-10-07 08:33:44 write : 2026-10-04 08:33:44 2026-10-07 08:33:45,181 1043405 WARNING ma_base odoo.tests.form.onchange: La date demandée est trop proche. La date de livraison est antérieure à la date prévue. Vous ne pourrez peut-être pas honorer la date de livraison.

Le write enregistre la date sans un mot ; seul le formulaire produit l'avertissement. Au § 3, create avait laissé onchange_note vide pour la même raison. Remède : si la valeur doit suivre en toutes circonstances, en faire un calcul (§ 3) ; si c'est un contrôle, une contrainte @api.constrains. Appeler la méthode d'onchange à la main depuis du code serveur est un contournement fragile : elle est écrite pour un enregistrement provisoire.

5.2 Le champ n'est pas dans la vue

Deux variantes. Le champ déclencheur : à l'affichage, Odoo pose on_change="1" sur les champs présents dans la vue qui ont un onchange ou dont dépend un calcul affiché (odoo/addons/base/models/ir_ui_view.py). Le champ cible : le formulaire ne demande au serveur que les champs de la vue, et n'enregistre que ceux-là. hidden_note, rempli par l'onchange mais absent de la vue, finit vide (sortie au § 6). Remède : ajouter le champ à la vue, invisible si besoin.

5.3 Le champ cible est en lecture seule dans la vue

La capture du § 4 le montre : locked_note s'affiche, puis disparaît à l'enregistrement. Le client web n'envoie pas un champ en lecture seule, et le devis S00029 relu en console le confirme :

S00029 | Client choisi : Acme Corporation | Client choisi : Acme Corporation | False | False

Dans l'ordre : onchange_note, invisible_note, locked_note, hidden_note. Remède : force_save="1" sur le champ dans la vue, ou mieux, un calcul stocké (§ 3), qui se recalcule de toute façon à l'enregistrement.

Le champ invisible, à l'inverse, n'est pas une cause : invisible_note est bien enregistré. Masquer un champ ne l'empêche pas de recevoir la valeur d'un onchange ; c'est justement le remède du § 5.2.

5.4 @api.onchange('partner_id.city') : un chemin pointé

Le décorateur n'accepte que des noms de champs du modèle. Un chemin pointé ne lève pas d'erreur : il produit une ligne dans le journal, au premier formulaire ouvert sur le modèle, et la méthode ne part jamais.

2026-10-07 08:32:43,685 1037635 WARNING ma_base odoo.models: @api.onchange('partner_id.city',) parameters must be field names -> not valid: ['partner_id.city']

La raison se lit dans la table des onchanges du modèle : la méthode est rangée sous la clé 'partner_id.city', un nom qu'aucun formulaire n'envoie jamais.

methods = env['sale.order']._onchange_methods
for key in ('partner_id', 'partner_id.city'):
    print(key, '->', [getattr(m, '__name__', 'change_default') for m in methods.get(key, [])])
partner_id -> ['_onchange_partner_domain', '_onchange_partner_id', '_onchange_partner_note', 'change_default'] partner_id.city -> ['_onchange_partner_city']

Remède : réagir au champ du modèle (@api.onchange('partner_id')), ou, si la ville du client peut changer ailleurs, passer en calcul : @api.depends, lui, accepte les chemins pointés, comme partner_country au § 3.

5.5 La méthode renvoie un domaine

return {'domain': {…}} pour restreindre un autre champ se rencontre encore dans du code ancien. En Odoo 20, la valeur de retour d'un onchange n'est lue que pour deux clés, 'value' et 'warning' (_apply_onchange_methods, odoo/orm/models.py) : le reste est ignoré, sans erreur ni avertissement. Appel direct de la méthode que le client web utilise :

spec = {'partner_id': {}, 'onchange_note': {}}
res = env['sale.order'].onchange({'partner_id': 10}, ['partner_id'], spec)
print(sorted(res))
print(res['value'])
['value'] {'onchange_note': 'Client choisi : Acme Corporation'}

Aucune clé domain dans la réponse. Remède : le domaine se déclare sur le champ, sous forme de chaîne évaluée par le client avec les valeurs du formulaire. Odoo le fait sur le devis : domain="['|', ('company_id', '=', False), ('company_id', '=', company_id)]" (addons/sale/models/sale_order.py). Pour une règle plus complexe, un champ calculé qui produit le domaine, référencé par son nom : domain="dest_package_id_domain" (addons/stock/wizard/stock_quant_relocate.py).

5.6 La méthode est surchargée sans son décorateur

Plus sournois. Un module qui surcharge _onchange_commitment_date pour y ajouter une règle, mais oublie de recopier le décorateur :

class SaleOrder(models.Model):
    _inherit = 'sale.order'

    def _onchange_commitment_date(self):   # surcharge SANS @api.onchange
        return super()._onchange_commitment_date()

Le scénario du § 5.1 rejoué avec ce module installé :

S00003 2026-10-07 08:29:20 write : 2026-10-04 08:29:20

Plus d'avertissement, même par le formulaire. Odoo repère les onchanges en cherchant, sur la classe finale du modèle, les méthodes qui portent la marque du décorateur (_onchange_methods, odoo/orm/models.py) : la surcharge masque l'originale, et elle n'a pas la marque. Remède : recopier le décorateur, avec les mêmes champs, @api.onchange("commitment_date", "expected_date") ; le message revient. @api.depends, lui, ne craint pas ce piège : les dépendances sont lues sur toutes les définitions de la méthode de calcul le long de l'héritage (resolve_mro, odoo/orm/fields.py), une surcharge nue les conserve.

L'inverse : un onchange qui part trop tôt

À l'ouverture d'un formulaire neuf, le client web lance tous les onchanges de la vue, avant toute saisie (premier appel de onchange, addons/web/models/models.py). La méthode tourne donc avec un client vide, d'où « Client choisi : False » au § 6. Commencer par if not self.partner_id: return quand la valeur n'a de sens qu'une fois le champ rempli.

6. Rejouer un onchange avec Form

Form, du paquet odoo.tests, simule le formulaire : il charge la vue, appelle onchange à chaque affectation et n'enregistre que ce qu'enverrait le client web. Il marche aussi bien dans un test que dans la console :

from odoo.tests import Form
f = Form(env['sale.order'])
print("avant  :", f.onchange_note, "|", f.delivery_city, "|", f.locked_note)
f.partner_id = env['res.partner'].browse(10)     # Acme Corporation
print("après  :", f.onchange_note, "|", f.delivery_city, "|", f.locked_note)
order = f.save()
for name in ('onchange_note', 'invisible_note', 'locked_note', 'hidden_note'):
    print(name, "=", order[name])

Tout y est : la ligne du § 5.4, l'onchange lancé à vide, puis les champs en lecture seule et hors vue vides après save(), exactement comme dans le navigateur. Form refuse en outre ce que l'utilisateur ne pourrait pas faire, et ses messages nomment la cause :

AssertionError: 'hidden_note' was not found in the view AssertionError: can't write on readonly field 'locked_note' AssertionError: can't write on invisible field 'invisible_note'

Un avertissement renvoyé par un onchange arrive dans le journal, sous odoo.tests.form.onchange (§ 5.1). Dans un test, self.assertLogs sur ce nom vérifie qu'il est bien émis. Form(order) sur un enregistrement existant le passe en édition ; with Form(…) as f: enregistre à la sortie du bloc. Les tests eux-mêmes sont présentés dans l'article sur les tests automatisés.

Récapitulatif

  • @api.depends appartient à l'ORM : chaque écriture d'une dépendance, par n'importe quel chemin, relance le calcul ; les chemins pointés sont acceptés.
  • @api.onchange appartient au formulaire : ni create ni write ne l'appellent.
  • Un calcul store=True, readonly=False remplace la plupart des onchange qui proposent une valeur.
  • Un onchange n'écrit que dans les champs présents et modifiables de la vue (ou force_save="1") ; un champ invisible convient.
  • Chemin pointé ignoré avec un avertissement, domain renvoyé ignoré sans un mot, surcharge sans décorateur : l'onchange ne part plus.
  • Form de odoo.tests rejoue tout cela depuis la console ou un test. Ce comportement est le même en 19 : le code concerné n'a pas changé.
