Agir en Odoo 20 : méthodes, boutons et contraintes

Jusqu'ici le module enregistrait des données. L'emprunt, lui, doit faire quelque chose : rendre un exemplaire indisponible, calculer une échéance, refuser un prêt impossible et se clore d'un clic. Trois outils suffisent — une surcharge de create, un @api.constrains et un bouton.

~17 minutes de lecture · niveau intermédiaire · parcours Framework & ORM

Ce que tu vas apprendre

Surcharger

create réécrit proprement, en traitant les enregistrements par lots.

Interdire

@api.constrains pour les règles que le SQL ne sait pas exprimer.

Déclencher

Un bouton qui appelle une méthode, et une barre d'état qui suit le résultat.

Prérequis

  • Le module biblio des articles précédents : les livres, les exemplaires et les adhérents.
  • Le serveur Odoo 20 joignable sur http://localhost:8069, base biblio.
  • Quelques exemplaires disponibles et au moins un adhérent inscrit.

L'emprunt, ce nœud entre deux modèles

Un emprunt n'est ni un exemplaire ni un adhérent : c'est le fait qu'à une date donnée, l'un est parti chez l'autre. Un modèle à part, avec deux Many2one — et, pour la première fois dans cette série, du code qui modifie autre chose que lui-même.

1. Le modèle library.loan

Crée models/library_loan.py. Les champs d'abord, le comportement ensuite :

from dateutil.relativedelta import relativedelta

from odoo import api, fields, models
from odoo.exceptions import ValidationError


class LibraryLoan(models.Model):
    _name = 'library.loan'
    _description = "Emprunt"
    _order = 'date_out desc, id desc'

    member_id = fields.Many2one(
        'library.member', string="Adhérent", required=True, ondelete='cascade',
    )
    copy_id = fields.Many2one(
        'library.copy', string="Exemplaire", required=True, ondelete='restrict',
    )
    date_out = fields.Date(
        string="Emprunté le", required=True, default=fields.Date.context_today,
    )
    duration = fields.Integer(string="Durée (jours)", default=14, required=True)
    date_due = fields.Date(string="À rendre le", compute='_compute_date_due', store=True)
    date_return = fields.Date(string="Rendu le", readonly=True, copy=False)
    state = fields.Selection(
        [('ongoing', "En cours"), ('returned', "Rendu")],
        string="État", default='ongoing', required=True,
    )
    is_late = fields.Boolean(string="En retard", compute='_compute_is_late')

Deux ondelete différents, et ce n'est pas un oubli :

ChampValeurPourquoi
member_id'cascade'Radier un adhérent efface son historique d'emprunts avec lui.
copy_id'restrict'Un exemplaire qui a une histoire ne se supprime pas. La suppression est refusée.

En base, cela donne exactement :

FOREIGN KEY (copy_id) REFERENCES library_copy(id) ON DELETE RESTRICT FOREIGN KEY (member_id) REFERENCES library_member(id) ON DELETE CASCADE

Et si l'on tente tout de même d'effacer un exemplaire emprunté :

ForeignKeyViolation: update or delete on table "library_copy" violates foreign key constraint "library_loan_copy_id_fkey" on table "library_loan"

1.1 Deux calculs, deux choix de stockage

    @api.depends('date_out', 'duration')
    def _compute_date_due(self):
        for loan in self:
            if loan.date_out:
                loan.date_due = loan.date_out + relativedelta(days=loan.duration)
            else:
                loan.date_due = False

    @api.depends('date_due', 'date_return', 'state')
    def _compute_is_late(self):
        today = fields.Date.context_today(self)
        for loan in self:
            fin = loan.date_return or today
            loan.is_late = bool(loan.date_due) and loan.state == 'ongoing' and fin > loan.date_due

L'échéance est store=True : elle ne dépend que de données saisies, elle a une valeur stable, et on voudra trier dessus. Le retard, lui, n'est pas stocké — et il ne peut pas l'être : il dépend du jour où on regarde, pas d'un champ. Une colonne calculée hier serait fausse aujourd'hui.

-- la colonne de l'échéance existe SELECT date_due FROM library_loan WHERE id = 1; → 2026-09-15 -- celle du retard, non SELECT count(*) FROM information_schema.columns WHERE table_name = 'library_loan' AND column_name = 'is_late'; → 0

La règle qui tranche entre les deux

Un champ calculé se stocke quand sa valeur ne dépend que d'autres champs — c'est ce que déclare @api.depends. Dès qu'un calcul regarde l'heure, un paramètre système ou l'utilisateur connecté, store=True devient un piège : Odoo n'a aucun moyen de savoir quand recalculer, et la valeur se fige. En contrepartie, un champ non stocké ne se trie pas et ne se filtre pas en base.

2. Interdire ce qui n'a pas de sens

Un exemplaire ne peut pas être emprunté deux fois en même temps. Aucune contrainte SQL ne sait exprimer cela : la règle porte sur plusieurs lignes et sur un état. C'est le domaine de @api.constrains :

    @api.constrains('copy_id', 'state')
    def _check_copy_available(self):
        for loan in self:
            if loan.state != 'ongoing':
                continue
            autres = self.search_count([
                ('copy_id', '=', loan.copy_id.id),
                ('state', '=', 'ongoing'),
                ('id', '!=', loan.id),
            ])
            if autres:
                raise ValidationError(
                    f"L'exemplaire {loan.copy_id.name} est déjà emprunté."
                )
ÉlémentRôle
@api.constrains('copy_id', 'state')Les champs qui déclenchent la vérification. Toucher un autre champ ne la relance pas.
for loan in selfLa méthode reçoit tous les enregistrements écrits, pas un seul.
('id', '!=', loan.id)S'exclure soi-même : à la modification, l'enregistrement courant est déjà en base.
ValidationErrorImportée de odoo.exceptions. Annule l'écriture et affiche le message.

Contrainte Python ou contrainte SQL ?

Les deux existent et ne se remplacent pas. models.Constraint, vu aux articles précédents, délègue à PostgreSQL : imbattable pour l'unicité d'une colonne, et respectée même par un import massif. @api.constrains vit dans Python : elle peut interroger d'autres enregistrements, lire un paramètre, comparer des dates — mais elle ne s'applique que si l'écriture passe par l'ORM.

Différence visible à l'écran : le message d'une contrainte Python s'affiche seul, tandis que celui d'une contrainte SQL est précédé de « The operation cannot be completed: », ajouté par le cœur.

3. Agir sur autre chose que soi

3.1 Sortir l'exemplaire à la création

Créer un emprunt doit rendre l'exemplaire indisponible. On surcharge create :

    @api.model_create_multi
    def create(self, vals_list):
        emprunts = super().create(vals_list)
        emprunts.filtered(lambda e: e.state == 'ongoing').copy_id.state = 'borrowed'
        return emprunts

Trois points valent la lecture :

  • @api.model_create_multi annonce que la méthode reçoit une liste de dictionnaires. Odoo crée par lots — un import de mille lignes fait un seul appel — et ce décorateur est la forme attendue aujourd'hui.
  • super().create(...) d'abord : on laisse Odoo créer, puis on agit sur le résultat. L'ordre inverse priverait le code des identifiants.
  • emprunts.filtered(...).copy_id.state = 'borrowed' écrit en une fois sur tous les exemplaires concernés. Écrire dans une boucle ferait autant de requêtes que d'emprunts.

3.2 Le retour, déclenché par un bouton

    def action_return(self):
        for loan in self:
            if loan.state == 'returned':
                raise ValidationError("Cet emprunt est déjà clos.")
            loan.write({
                'state': 'returned',
                'date_return': fields.Date.context_today(loan),
            })
            loan.copy_id.state = 'available'

Aucun décorateur : une méthode ordinaire, appelée sur un jeu d'enregistrements. Le préfixe action_ est une convention — rien ne l'impose, tout le monde la suit.

La garde en tête de boucle n'est pas décorative. L'interface cache le bouton quand l'emprunt est clos, mais un appel distant, un bouton d'action en lot ou un futur automate ne passeront pas par l'interface. Une méthode se protège elle-même.

Le piège : self n'est pas un enregistrement

Une méthode reçoit toujours un jeu d'enregistrements, même quand l'écran n'en montre qu'un. Et les deux sens ne se comportent pas pareil. Lire un champ sur un jeu de plusieurs enregistrements s'arrête net :

>>> jeu = env['library.loan'].search([], limit=2) >>> jeu.state ValueError: Expected singleton: library.loan(20, 19)

Écrire, en revanche, ne dit rien — et applique la valeur à tous les enregistrements du jeu. C'est le sens dangereux : un self.state = 'returned' écrit sans réfléchir passe les tests sur un enregistrement et modifie tout le lot le jour où la méthode est appelée depuis une sélection multiple. La boucle for loan in self coûte une ligne et ferme les deux portes.

4. Le bouton, la barre d'état et la ligne rouge

Dans views/library_loan_views.xml, le formulaire s'ouvre sur un <header> — la bande qui porte les boutons et l'avancement :

    <record id="library_loan_view_form" model="ir.ui.view">
        <field name="name">library.loan.form</field>
        <field name="model">library.loan</field>
        <field name="arch" type="xml">
            <form string="Emprunt">
                <header>
                    <button name="action_return" type="object" string="Marquer comme rendu"
                            class="btn-primary" invisible="state == 'returned'"/>
                    <field name="state" widget="statusbar"/>
                </header>
                <sheet>
                    <group>
                        <group string="Emprunt">
                            <field name="copy_id"/>
                            <field name="member_id"/>
                        </group>
                        <group string="Dates">
                            <field name="date_out"/>
                            <field name="duration"/>
                            <field name="date_due"/>
                            <field name="date_return" invisible="state != 'returned'"/>
                        </group>
                    </group>
                </sheet>
            </form>
        </field>
    </record>
AttributEffet
name="action_return"Le nom de la méthode Python à appeler.
type="object"Appelle une méthode du modèle. type="action" lancerait une action enregistrée.
invisible="state == 'returned'"Une expression Python évaluée sur l'enregistrement affiché. Le bouton disparaît quand l'emprunt est clos.
widget="statusbar"Transforme le champ Selection en fil d'avancement cliquable.

Côté liste, une seule option colore les emprunts en retard :

            <list string="Emprunts" decoration-danger="is_late">
                <field name="copy_id"/>
                <field name="member_id"/>
                <field name="date_out"/>
                <field name="date_due"/>
                <field name="date_return"/>
                <field name="state"/>
            </list>

decoration-danger attend une expression vraie ou fausse ; d'autres existent (decoration-warning, decoration-success, decoration-muted). Remarque que is_late n'apparaît nulle part comme colonne : Odoo charge de lui-même les champs qu'une décoration utilise. Inutile d'ajouter un <field name="is_late" column_invisible="1"/> — la coloration fonctionne sans lui, vérification faite en retirant la ligne.

Vérifier une contrainte dans le shell : l'échec laisse des traces

Un ValidationError est levé après l'insertion de la ligne, au moment de la validation. Dans une session odoo-bin shell, rien n'annule automatiquement cette insertion : la ligne refusée reste dans la transaction et fausse tout ce qui suit — un second essai échouera pour une mauvaise raison. Il faut isoler l'échec attendu : with env.cr.savepoint():. Dans le navigateur, la question ne se pose pas, chaque requête étant annulée de bout en bout.

Récapitulatif

  • Un modèle de liaison porte deux Many2one, et leurs ondelete n'ont aucune raison d'être identiques.
  • @api.model_create_multi est la forme d'une surcharge de create : elle reçoit une liste.
  • Appeler super() d'abord, agir ensuite — et écrire sur le jeu entier plutôt que dans une boucle.
  • @api.constrains exprime ce que le SQL ne sait pas dire ; models.Constraint garde l'unicité.
  • Un bouton type="object" appelle une méthode ; celle-ci se protège elle-même, car l'interface n'est pas le seul chemin.
  • Toujours boucler sur self : une méthode reçoit un jeu d'enregistrements.
  • Un calcul qui regarde l'heure ne se stocke pas.
