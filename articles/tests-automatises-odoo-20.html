Tests automatisés en Odoo 20 : le module Bibliothèque sous contrôle

Seize articles de vérifications faites à la main : à l'écran, en base, dans le journal. On les confie aux tests automatisés d'Odoo 20. Un dossier tests/, treize tests écrits avec TransactionCase, lancés par --test-enable, et un résultat qu'on apprend à lire, y compris quand il annonce « 0 failed » sans avoir rien testé.

~14 minutes de lecture · niveau intermédiaire · parcours Framework & ORM

Ce que tu vas apprendre

Écrire

Un socle setUpClass, des assertions sur les règles métier, la date figée avec freeze_time.

Couvrir

Les droits avec with_user, l'assistant avec Form, le courriel avec MailCase, le rapport.

Lancer et lire

--test-enable, --test-tags, la ligne qui compte, le code de sortie.

Prérequis

  • Le module biblio des articles précédents, jusqu'à sa traduction : emprunts numérotés, assistant « Prolonger », relance par courriel, fiche de prêt PDF.
  • Les deux groupes Accueil et Bibliothécaire posés dans l'article sur les droits d'accès.
  • Un serveur Odoo 20 en ligne de commande. Les tests tournent sur une base dédiée, biblio_tests, jamais sur la base de travail.

1. Où vivent les tests

Odoo cherche les tests dans un paquet tests à la racine du module. Chaque fichier dont le nom commence par test_ est importé par tests/__init__.py ; le __init__.py du module, lui, ne l'importe pas : le code de test ne se charge qu'en mode test.

biblio/
├── __init__.py            # models, wizard — pas tests
├── __manifest__.py
└── tests/
    ├── __init__.py
    ├── common.py          # le socle partagé
    ├── test_loan.py
    ├── test_loan_access.py
    ├── test_loan_extend.py
    ├── test_loan_reminder.py
    └── test_loan_report.py
# tests/__init__.py
from . import test_loan
from . import test_loan_access
from . import test_loan_extend
from . import test_loan_reminder
from . import test_loan_report

Un fichier oublié ici n'est jamais lancé, sans message. Le fichier common.py n'y figure pas : il ne contient pas de test, les autres l'importent.

Chaque classe de test s'exécute dans une phase. at_install : juste après l'installation du module, avant ceux qui en dépendent. post_install : une fois tous les modules chargés, quand la base est dans son état final. En Odoo 20, une classe sans décorateur est en post_install : c'est la valeur par défaut (odoo/tests/common.py, cls.test_tags = {'standard', 'post_install'}). Une classe de test du module sans aucun @tagged a été lancée pour le vérifier : elle tourne avec les post-tests, et 'post_install' figure dans ses étiquettes.

Venant de la 19 : la phase par défaut s'est inversée

En 19, la valeur par défaut était {'standard', 'at_install'} : pour tester sur une base complète, il fallait écrire @tagged('post_install', '-at_install') sur chaque classe. En 20, ce décorateur ne change plus rien, et le module Bibliothèque s'en passe. Il sert désormais dans l'autre sens : @tagged('at_install', '-post_install') pour un test qui doit tourner pendant l'installation.

2. Un socle commun : setUpClass

Tous les tests ont besoin d'un livre, d'exemplaires, d'un adhérent et de deux utilisateurs, un par groupe. On les crée une fois par classe, dans setUpClass :

# tests/common.py
from odoo.tests import TransactionCase, new_test_user


class BiblioCase(TransactionCase):
    """Jeu de données commun : un livre, deux exemplaires, un adhérent, deux utilisateurs."""

    @classmethod
    def setUpClass(cls):
        super().setUpClass()
        cls.user_desk = new_test_user(cls.env, login='test_accueil', groups='biblio.group_library_desk')
        cls.user_manager = new_test_user(cls.env, login='test_biblio', groups='biblio.group_library_manager')
        cls.book = cls.env['library.book'].create({'title': "Python pour Odoo"})
        cls.copy_1, cls.copy_2 = cls.env['library.copy'].create([
            {'book_id': cls.book.id},
            {'book_id': cls.book.id},
        ])
        cls.member = cls.env['library.member'].create({
            'name': "Équipe Formation",
            'email': 'formation@example.com',
            'card_number': 'T-0001',
        })

    @classmethod
    def _emprunter(cls, copy, **vals):
        return cls.env['library.loan'].create({
            'member_id': cls.member.id,
            'copy_id': copy.id,
            **vals,
        })

TransactionCase ouvre une transaction pour la classe, et un point de sauvegarde par test, annulé à la fin du test. Chaque test repart donc des données de setUpClass, sans voir ce que le précédent a créé, et rien n'est jamais écrit dans la base.

new_test_user() crée un utilisateur à partir d'un login et d'une liste de groupes (identifiants XML séparés par des virgules) ; il remplit le nom, le courriel et le mot de passe. Les exemplaires reçoivent leur code BIB- par la séquence de l'article sur les séquences.

Venant de la 19 : deux imports ne passent plus

SingleTransactionCase, une transaction pour toute la classe sans retour arrière entre les tests, a disparu : from odoo.tests import SingleTransactionCase lève ImportError en 20. from odoo.tests.common import Form, que la 19 acceptait avec un avertissement de dépréciation, lève aussi ImportError : on écrit from odoo.tests import Form. Un module de test 19 qui utilisait l'un des deux ne se charge plus.

3. Les règles métier de l'emprunt

Un test est une méthode dont le nom commence par test_. Il agit, puis vérifie avec les assertions de unittest : assertEqual, assertTrue, assertIn, assertRegex… Premier fichier, les règles posées au fil de la série :

# tests/test_loan.py
from datetime import date

from psycopg2.errors import ForeignKeyViolation

from odoo.exceptions import ValidationError
from odoo.tests import freeze_time
from odoo.tools import mute_logger

from .common import BiblioCase


class TestLoan(BiblioCase):

    def test_reference_sequence(self):
        loan = self._emprunter(self.copy_1, date_out=date(2026, 9, 1))
        self.assertRegex(loan.reference, r'^EMP/2026/\d{4}$')

    def test_copy_state_follows_loan(self):
        loan = self._emprunter(self.copy_1)
        self.assertEqual(self.copy_1.state, 'borrowed')
        loan.action_return()
        self.assertEqual(self.copy_1.state, 'available')
        self.assertEqual(loan.state, 'returned')

    def test_copy_cannot_be_borrowed_twice(self):
        self._emprunter(self.copy_1)
        with self.assertRaises(ValidationError):
            self._emprunter(self.copy_1)

    def test_borrowed_copy_cannot_be_deleted(self):
        self._emprunter(self.copy_1)
        with self.assertRaises(ForeignKeyViolation), mute_logger('odoo.sql_db'):
            self.copy_1.unlink()

La séquence, l'état de l'exemplaire qui suit l'emprunt, la contrainte « un exemplaire n'est emprunté qu'une fois » et le ondelete='restrict' de l'article sur les méthodes et contraintes ont chacun leur test.

assertRaises fait plus que vérifier l'exception : dans un test Odoo, il ouvre un point de sauvegarde et l'annule si l'exception survient (BaseCase._raisesContext). Sans lui, la contrainte SQL refusée laisserait la transaction en erreur, et toutes les requêtes suivantes du test échoueraient. Le refus de la clé étrangère arrive brut de PostgreSQL, ForeignKeyViolation : le message français « Un autre modèle utilise l'enregistrement… » n'est posé que par la couche HTTP. mute_logger('odoo.sql_db') évite que la requête refusée s'affiche en ERROR dans le journal d'un test qui, lui, réussit.

4. Figer la date : freeze_time

Le retard dépend du jour où le test tourne. Un test qui passe aujourd'hui et échoue dans deux semaines ne vaut rien. freeze_time, importé de odoo.tests, fixe la date du test :

    @freeze_time('2026-09-30')
    def test_is_late(self):
        loan = self._emprunter(self.copy_1, date_out=date(2026, 9, 1), duration=14)
        self.assertEqual(loan.date_due, date(2026, 9, 15))
        self.assertTrue(loan.is_late)
        self.assertEqual(loan.days_late, 15)
        self.assertIn(loan, self.env['library.loan'].search([('is_late', '=', True)]))

    def test_return_posts_note(self):
        loan = self._emprunter(self.copy_1)
        loan.action_return()
        note = loan.message_ids[0]
        self.assertEqual(note.subtype_id, self.env.ref('mail.mt_note'))
        self.assertIn(f"<b>{self.copy_1.name}</b>", note.body)

Au 30 septembre, un emprunt du 1er pour 14 jours est dû le 15 et a 15 jours de retard. fields.Date.context_today(), qu'utilisent date_due et is_late, lit l'heure figée. La dernière ligne teste la recherche sur le champ calculé non stocké (_search_is_late), pas seulement sa valeur. Le second test vérifie la note du chatter posée par le retour : sous-type mt_note, et le code de l'exemplaire en gras, preuve que le Markup n'a pas été échappé.

Le freeze_time d'odoo.tests enveloppe celui de la bibliothèque freezegun : sur une méthode il s'emploie comme l'original, et posé sur une classe de test il fige toutes ses méthodes.

5. Lancer les tests et lire le résultat

Les tests ne tournent que si on le demande, avec --test-enable, et pendant l'installation ou la mise à jour du module. La première fois, sur une base neuve :

./odoo-bin -c odoo.conf -d biblio_tests -i biblio --test-enable --test-tags /biblio --stop-after-init

Ensuite, à chaque modification, -u biblio à la place de -i biblio. --test-tags /biblio limite la sélection aux tests du module ; sans lui, l'installation sur la base neuve lancerait aussi ceux de base, mail et de chaque module installé au passage. --stop-after-init arrête le serveur à la fin, comme il se doit dans un script.

Deux lignes donnent un compte, et elles ne disent pas la même chose. odoo.tests.stats annonce 23 : elle compte aussi, pour chaque classe, le setUpClass et le tearDownClass (5 classes, soit 10 entrées de plus ; odoo/tests/suite.py). Le nombre de tests, c'est celui de odoo.tests.result : 13.

Sur la base neuve, la première exécution en compte 15 : les deux suites JavaScript du module web, installé dans le même passage (WebSuite et MobileWebSuite, dans addons/web/tests/test_js.py), sont des tests « transverses » (odoo.tests.CrossModule) qui se lancent pour chaque module sélectionné. Le module n'ayant pas de test JavaScript, elles rendent la main aussitôt. Aux mises à jour suivantes, elles ne sont plus dans la sélection.

6. Un test qui échoue

Un test qui n'a jamais échoué n'a rien prouvé. On fausse volontairement une attente, 14 jours de retard au lieu de 15, et on relance :

Tout ce qu'il faut pour corriger est là : FAIL, le nom du test, la ligne du fichier et AssertionError: 15 != 14, la valeur obtenue en premier. On distingue FAIL (une assertion fausse) et ERROR (une exception imprévue dans le test) : le résumé les compte à part, « 1 failed, 0 error(s) ».

Le code de sortie passe à 1. C'est lui qu'une intégration continue regarde : un script qui enchaîne les tests puis le déploiement s'arrête là, sans lire le journal.

Venant de la 19 : la liste des échecs en fin de journal

En 20, après la ligne de résumé, le serveur récapitule chaque test en échec ou en erreur sur une ligne, « Failed: test - message » ou « Error: … » (odoo/service/server.py). La 19 s'arrêtait au résumé : il fallait remonter le journal pour trouver le test fautif. Le code de sortie, lui, se calcule de la même façon dans les deux versions.

On remet 15, on relance : « 0 failed, 0 error(s) of 13 tests », code de sortie 0.

7. Tester les droits : with_user

Le test tourne en superutilisateur, qui passe outre tous les droits. Pour vérifier la matrice ir.access.csv, on agit au nom d'un utilisateur du groupe avec with_user() :

# tests/test_loan_access.py
from odoo.exceptions import AccessError

from .common import BiblioCase


class TestLoanAccess(BiblioCase):

    def test_desk_can_lend_and_return(self):
        loan = self._emprunter(self.copy_1).with_user(self.user_desk)
        loan.action_return()
        self.assertEqual(loan.state, 'returned')

    def test_desk_cannot_create_book(self):
        with self.assertRaises(AccessError):
            self.env['library.book'].with_user(self.user_desk).create({'title': "Interdit"})

    def test_returned_loan_is_frozen(self):
        loan = self._emprunter(self.copy_1)
        loan.action_return()
        with self.assertRaises(AccessError):
            loan.with_user(self.user_manager).write({'duration': 30})

Trois cas : ce que l'accueil peut faire (rendre un emprunt), ce qu'il ne peut pas faire (créer un livre, lecture seule pour lui), et la restriction sans groupe qui fige un emprunt rendu, y compris pour la bibliothécaire. Tester un refus est aussi important que tester un accord : c'est lui qui casse en silence quand une ligne de la matrice change.

Avec AccessError, assertRaises vide aussi le cache de l'environnement avant d'exécuter le bloc : les droits sont réévalués pour de bon, pas relus d'un calcul fait en superutilisateur un peu plus haut.

8. Tester l'assistant avec Form

L'assistant « Prolonger » s'ouvre depuis la liste, avec les emprunts sélectionnés dans le contexte. Form rejoue ce parcours côté serveur : il charge la vue formulaire, applique les valeurs par défaut et les onchanges, et refuse d'enregistrer si un champ obligatoire est vide.

# tests/test_loan_extend.py
from odoo.exceptions import UserError
from odoo.tests import Form

from .common import BiblioCase


class TestLoanExtend(BiblioCase):

    def _assistant(self, loans):
        ctx = {'active_model': 'library.loan', 'active_ids': loans.ids}
        return Form(self.env['library.loan.extend'].with_user(self.user_desk).with_context(ctx))

    def test_extend_in_batch(self):
        loans = self._emprunter(self.copy_1) | self._emprunter(self.copy_2)
        echeances = loans.mapped('date_due')
        form = self._assistant(loans)
        form.days = 10
        form.save().action_extend()
        for loan, avant in zip(loans, echeances):
            self.assertEqual((loan.date_due - avant).days, 10)
            self.assertIn("Prolongé de <b>10</b> jour(s).", loan.message_ids[0].body)

    def test_returned_loan_refused(self):
        loan = self._emprunter(self.copy_1)
        loan.action_return()
        assistant = self._assistant(loan).save()
        with self.assertRaisesRegex(UserError, loan.reference):
            assistant.action_extend()

Le premier test couvre le lot : deux emprunts, dix jours chacun, une note dans chaque chatter. Le second vérifie le refus d'un emprunt rendu, et que le message nomme bien sa référence (assertRaisesRegex). L'assistant est ouvert par l'accueil : le test vérifie du même coup la ligne d'accès cr ajoutée pour le modèle transitoire.

9. Tester la relance par courriel : MailCase

L'action planifiée de relance envoie un vrai courriel. Le module mail fournit ses outils de test dans odoo.addons.mail.tests.common : MailCase et son gestionnaire de contexte mock_mail_gateway(), qui remplace la connexion SMTP par une fausse et garde chaque courriel construit en mémoire.

# tests/test_loan_reminder.py
from datetime import date

from odoo.addons.mail.tests.common import MailCase
from odoo.tests import freeze_time

from .common import BiblioCase


class TestLoanReminder(BiblioCase, MailCase):

    @freeze_time('2026-09-30')
    def test_cron_reminds_late_loans_once_a_day(self):
        late = self._emprunter(self.copy_1, date_out=date(2026, 9, 1))
        self._emprunter(self.copy_2)  # à l'heure : pas de relance
        with self.mock_mail_gateway():
            count = self.env['library.loan']._cron_relancer_retards()
        self.assertEqual(count, 1)
        self.assertEqual(late.reminder_count, 1)
        self.assertSentEmail(
            self.env.user.partner_id, [self.member.partner_id],
            subject="Retard : Python pour Odoo",
        )
        # Deuxième passage le même jour : rien.
        self.assertEqual(self.env['library.loan']._cron_relancer_retards(), 0)

On appelle la méthode de l'action planifiée directement, sans attendre le planificateur. Un emprunt en retard, un emprunt à l'heure : un seul courriel, adressé au contact de l'adhérent, avec le sujet rendu par le gabarit. Le dernier appel vérifie la règle « une relance par jour ».

Piège : en test, le courriel ne passe pas par la file

En production, un courriel posté part après la validation de la transaction. Un test ne valide jamais sa transaction : Odoo envoie donc tout de suite (addons/mail/models/mail_thread.py : « In tests, emails are sent immediately instead of in postcommit »). Un test qui attend un mail.mail à l'état « à envoyer » (assertMailMail(…, 'outgoing')) échoue : l'enregistrement est déjà à l'état « envoyé ». assertSentEmail vérifie ce qui a vraiment été remis à la passerelle, c'est lui qu'on garde.

L'expéditeur attendu est le partenaire de l'utilisateur du test : le gabarit prend l'adresse de la société et, faute d'en avoir une dans la base de test, celle de l'utilisateur qui lance le traitement.

10. Tester la fiche de prêt

# tests/test_loan_report.py
from .common import BiblioCase


class TestLoanReport(BiblioCase):

    def test_loan_sheet_content(self):
        loan = self._emprunter(self.copy_1)
        contenu, fmt = self.env['ir.actions.report']._render_qweb_pdf(
            'biblio.action_report_library_loan', loan.ids,
        )
        # Sous --test-enable, Odoo rend le HTML au lieu d'appeler wkhtmltopdf.
        self.assertEqual(fmt, 'html')
        self.assertIn(loan.reference, contenu.decode())
        self.assertIn("Python pour Odoo", contenu.decode())

_render_qweb_pdf() demande un PDF, mais en mode test Odoo rend le HTML du rapport à la place (_pre_render_qweb_pdf, dans odoo/addons/base/models/ir_actions_report.py) : un serveur de test n'a pas forcément de quoi servir les appels de wkhtmltopdf. Le format renvoyé le dit, 'html', et c'est ce qu'on vérifie avant le contenu : la référence de l'emprunt et le titre du livre sortent bien du gabarit QWeb. Pour obtenir le vrai PDF, on ajoute le contexte force_report_rendering=True et on enveloppe l'appel dans le gestionnaire with self.allow_pdf_render():. Essayé ici : le format vaut 'pdf' et le contenu commence par %PDF, mais le test prend deux secondes et laisse un WARNING de wkhtmltopdf dans le journal. Pour vérifier ce que la fiche contient, le HTML suffit.

11. Le piège du « 0 failed »

Une lettre oubliée dans l'étiquette, /bibli au lieu de /biblio :

Piège : « 0 failed » avec un code de sortie 0

Aucun module ne s'appelle bibli : la sélection est vide, rien ne tourne, et le serveur sort avec le code 0, comme un passage réussi. Une intégration continue qui ne regarde que le code de sortie passe au vert. Odoo le signale seulement par le niveau de la ligne, WARNING au lieu d'INFO, quand zéro test a tourné. Dans un script, vérifier le nombre de tests annoncé, pas seulement l'absence d'échec.

La syntaxe complète d'une étiquette est [-][étiquette][/module][:Classe][.méthode] dans sa forme courante, plusieurs séparées par des virgules (odoo/tests/tag_selector.py). --test-tags /biblio:TestLoanReminder ne lance que la classe du courriel ; --test-tags /biblio.test_is_late une seule méthode, pratique pendant qu'on corrige un échec.

Mémo

Récapitulatif

  • Les tests vivent dans tests/, chaque fichier test_*.py importé par tests/__init__.py.
  • TransactionCase annule tout à la fin de chaque test ; les données communes se créent une fois dans setUpClass.
  • En Odoo 20, un test est post_install sans rien écrire, SingleTransactionCase a disparu, et Form s'importe de odoo.tests.
  • freeze_time, with_user, Form et MailCase couvrent les dates, les droits, les assistants et les courriels.
  • Un échec donne le test, la ligne, les deux valeurs et un code de sortie à 1 ; « of 0 tests » avec un code 0 signale une sélection vide.

Treize tests automatisés gardent désormais les règles du module Odoo 20 : chaque changement à venir se vérifie en quelques secondes. Le module reste pour l'instant réservé au personnel. Prochaine étape de la série : ouvrir une porte aux adhérents, avec le portail où chacun voit ses emprunts en cours et ses dates de retour.
