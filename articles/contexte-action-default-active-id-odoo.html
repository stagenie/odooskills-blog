default_, search_default_, active_id : le contexte des actions Odoo 20

Pré-remplir un champ, ouvrir une liste déjà filtrée, savoir depuis quelle fiche l'action a été lancée : tout passe par le contexte de l'action. Ce qu'Odoo 20 en fait vraiment, clic après clic, relevé dans les requêtes du navigateur.

~6 minutes de lecture · niveau intermédiaire · série Astuces dev Odoo 20

Édition : Community. Vérifié sur Odoo 20.0 Community, octobre 2026, base de démonstration (Ventes) et module d'exemple.

La réponse en bref

Clé du contexteEffetQui la lit
default_<champ>pré-remplit le champ d'un nouvel enregistrementle serveur (default_get)
search_default_<nom>active un filtre ou une facette au chargement, que l'utilisateur peut retirerla vue de recherche, puis la clé disparaît
active_id, active_ids, active_modell'enregistrement (ou la sélection) d'où part l'actionposées par le client web au clic

Dans le XML, le contexte est une chaîne évaluée par le navigateur : {'default_partner_id': active_id} n'a de sens que si l'action part d'une fiche.

1. Lire une action native : le bouton « Ventes » d'un contact

Sur la fiche d'un contact, le bouton intelligent Ventes ouvre l'action sale.act_res_partner_2_sale_order. Dans odoo-bin shell :

act = env.ref('sale.act_res_partner_2_sale_order')
print(repr(act.context))
print(repr(act.domain))
"{'default_partner_id': active_id}" "[('partner_id', 'child_of', active_ids)]"

Deux chaînes, pas des dictionnaires : le serveur les transmet telles quelles et le client web les évalue au moment du clic. Sur la fiche d'Acme Corporation (id 10), le navigateur demande l'action avec active_id: 10, active_ids: [10] et active_model: 'res.partner' ; le contexte devient {'default_partner_id': 10}. Clique sur Nouveau dans la liste : le champ Client est déjà rempli.

Le domaine et le contexte ne se voient pas de la même façon. Le domaine est un filtre caché : la liste ouverte par « Ventes » n'affiche aucune facette, et l'utilisateur ne peut pas l'enlever. Un search_default_ pose au contraire une facette visible et amovible.

2. Écrire ta propre action : pré-remplir et pré-filtrer

Le module d'exemple ajoute au menu Actions (icône ⋮) du formulaire contact une entrée « Devis du contact » : les devis du contact, filtrés mais modifiables, et un nouveau devis pré-rempli.

<record id="action_devis_du_contact" model="ir.actions.act_window">
    <field name="name">Devis du contact</field>
    <field name="res_model">sale.order</field>
    <field name="view_mode">list,form</field>
    <field name="search_view_id" ref="sale.sale_order_view_search_inherit_quotation"/>
    <field name="context">{
        'default_partner_id': active_id,
        'search_default_partner_id': active_id,
        'search_default_draft': 1,
    }</field>
    <field name="binding_model_id" ref="base.model_res_partner"/>
    <field name="binding_view_types">form</field>
</record>

Trois clés, trois rôles :

  • search_default_partner_id vise le <field name="partner_id"> de la vue de recherche : la valeur (l'id 10) devient une facette Client, avec l'opérateur = pour un many2one.
  • search_default_draft vise le <filter name="draft"> (libellé « Devis ») : 1 l'active. Une valeur fausse (0, False) est ignorée.
  • default_partner_id remplit le client du devis créé depuis cette liste.

Ouvre la même action par son adresse, sans partir d'une fiche : Odoo 20 affiche « Oups ! » et la console du navigateur indique EvalError … Name 'active_id' is not defined. Une action dont le contexte cite active_id se lance depuis un enregistrement (bouton, menu Actions), jamais depuis un menu de l'application.

Un search_default_ qui ne fait rien

Sans la ligne search_view_id, l'action prend la vue de recherche par défaut des commandes, qui n'a pas de filtre draft : il n'existe que dans la vue des devis. Résultat constaté : facette Client seule, pas de facette « Devis », aucune erreur à l'écran ni dans le journal du serveur. La clé doit reprendre le name (pas le libellé) d'un filtre ou d'un champ présent dans la vue de recherche que l'action utilise.

3. Ce que devient le contexte au clic suivant

Le contexte d'une action ne s'arrête pas à la liste : il accompagne les fiches ouvertes depuis elle. Pour le voir, ouvre le devis S00005 depuis « Devis du contact » et clique sur Envoyer (bouton type="object" qui appelle action_quotation_send). Trois constats :

  1. Les search_default_ ont disparu dès la liste : la vue de recherche les consomme et les retire du contexte.
  2. La méthode du bouton reçoit tout le reste, dont default_partner_id: 10 et un active_id qui vaut toujours 10, active_model: 'res.partner' : c'est le contact d'origine, pas le devis. Le devis, lui, arrive en argument (args=[[5]]). Dans une méthode de bouton, travaille sur self, jamais sur active_id.
  3. L'action renvoyée repart propre : avant de l'ouvrir, le client web retire du contexte courant, entre autres, les clés default_*, search_default_*, group_by, active_id, active_ids, *_view_ref, puis pose active_id: 5 et active_model: 'sale.order'. La fenêtre de courriel ne voit plus default_partner_id. Les autres clés (ici res_partner_search_mode) suivent toujours.

Le point 2 explique le piège du default_* qui « fuit » côté Python vers un autre modèle : l'article sur l'environnement le montre et donne le remède, clean_context().

4. Depuis Python : un dictionnaire, pas une chaîne

Une méthode qui renvoie une action connaît déjà l'enregistrement : pas besoin d'active_id. Reprends l'action XML avec _for_xml_id et remplace domaine et contexte par des valeurs calculées :

acme = env['res.partner'].search([('name', '=', 'Acme Corporation')])
action = env['ir.actions.actions']._for_xml_id('sale.act_res_partner_2_sale_order')
print(repr(action['context']), '|', repr(action['domain']))
action['domain'] = [('partner_id', 'child_of', acme.ids)]
action['context'] = {'default_partner_id': acme.id, 'search_default_draft': 1}
print(env['sale.order'].with_context(action['context']).default_get(['partner_id']))
"{'default_partner_id': active_id}" | "[('partner_id', 'child_of', active_ids)]" {'partner_id': 10}

_for_xml_id rend encore les chaînes du XML : les écraser évite de dépendre de l'évaluation côté navigateur. La dernière ligne montre ce que fera le formulaire : default_get lit default_partner_id, et ignore search_default_draft, réservé à la vue de recherche. C'est aussi la façon de tester un contexte d'action sans écran.

À retenir

  • default_<champ> pré-remplit, search_default_<nom> pose une facette retirable, le domaine filtre sans rien montrer.
  • search_default_ doit viser le name d'un filtre ou d'un champ de la vue de recherche de l'action ; sinon il est ignoré en silence.
  • active_id n'existe que si l'action part d'un enregistrement ; dans une méthode de bouton, il peut désigner la fiche d'origine : utilise self.
  • En Python, renvoie un dictionnaire de contexte calculé ; le client web nettoie les default_* avant d'ouvrir l'action suivante.
