Installer, mettre à jour, désinstaller un module Odoo 20 en CLI

Pas d'écran Applications sur un serveur : on installe avec -i, on met à jour avec -u, et Odoo 20 ajoute à la sous-commande odoo-bin module une liste des modules et un mode « à blanc » qui montre ce qui va bouger avant de le faire. Avec, pour chaque commande, sa durée réelle et ce que son code de sortie ne dit pas.

~14 minutes de lecture · niveau intermédiaire · parcours Infrastructure

Ce que tu vas apprendre

Lancer

-i, -u, --stop-after-init, --no-http, et la sous-commande odoo-bin module.

Prévoir

module list et --dry-run : voir les modules entraînés avant d'installer, de mettre à jour ou de désinstaller.

Vérifier

Lire le journal, parce qu'un code de sortie 0 ne prouve rien, et mesurer ce que coûte un -u all.

Prérequis

  • Un Odoo 20 installé, avec son fichier de configuration odoo.conf (chemins des modules, accès PostgreSQL) : voir Installer Odoo 20 sur Ubuntu ou sur un serveur Ubuntu.
  • Une base de démonstration, appelée ici ma_base : Ventes et Inventaire installés, en français. Tous les essais destructifs ont été faits sur des copies jetables ; fais de même (createdb -T ma_base ma_base_essai et copie du dossier filestore/ma_base).
  • Les commandes sont lancées depuis le dossier des sources, d'où ./odoo-bin. Les durées citées viennent d'un poste de développement, avec workers = 0.

1. Les options du serveur : -i, -u, --stop-after-init

La forme historique passe par le serveur lui-même : il charge la base, installe ou met à jour, puis continue de servir les pages. Avec --stop-after-init, il s'arrête dès que la base est prête :

./odoo-bin -c odoo.conf -d ma_base -i purchase --stop-after-init --no-http
./odoo-bin -c odoo.conf -d ma_base -u sale --stop-after-init --no-http
OptionEffetMesuré sur la base de démonstration
-i purchaseInstalle le module, ses dépendances manquantes et les modules « pont » qui s'installent d'eux-mêmes (auto_install). Plusieurs modules : -i a,b. Si la base n'existe pas, elle est créée.5 modules (purchase, purchase_stock, sale_purchase…), 7,3 s. Une base neuve -i sale_management : 59 modules, 21,9 s.
-u saleRecharge le code et les fichiers de données du module et de tous les modules installés qui en dépendent.11 modules rechargés pour sale, 5,6 s.
--stop-after-initQuitte une fois la base chargée. Odoo 20 accepte aussi la forme courte --stop.—
--no-httpN'ouvre pas le port HTTP. Voir ci-dessous.—

Pourquoi --no-http, puisque le serveur s'arrête de toute façon ? Tout dépend du mode du serveur. En mode threadé (workers = 0), un lancement avec --stop-after-init n'ouvre jamais le port (odoo/service/server.py, méthode start). En mode multi-processus (workers > 0, le cas d'une production), le serveur ouvre le port avant de charger la base. Si le service tourne déjà sur ce port, la commande s'arrête net, sans avoir rien mis à jour :

Mets donc --no-http sur toute commande ponctuelle : elle ne coûte rien en mode threadé et t'évite l'erreur le jour où le fichier de configuration passe en workers = 4.

2. La sous-commande odoo-bin module

Plutôt que de démarrer un serveur pour l'arrêter aussitôt, odoo-bin module fait une seule chose et rend la main :

./odoo-bin module --help
positional arguments: {install,upgrade,uninstall,force-demo,list} Subcommands help install Install modules upgrade Upgrade modules uninstall Uninstall modules force-demo Install demo data (force) list List modules
CommandeCe qu'elle appelleDurée mesurée
module install purchasebutton_immediate_install(), comme le bouton Activer de l'écran Applications8,2 s (5 modules)
module upgrade sale / module upgrade allbutton_immediate_upgrade()—
module uninstall purchasebutton_immediate_uninstall()5,1 s
module force-democharge les données de démonstration de tous les modules installés9,8 s (59 modules)
module listlecture seule1,0 s

Trois règles la distinguent de -i et -u :

  • Elle n'accepte que -c, -d et -D (dossier de données). Tout le reste, chemins des modules, niveau de journal, mot de passe PostgreSQL, vient du fichier de configuration. module list --log-level=warn s'arrête sur error: unrecognized arguments: --log-level=warn. Seule exception : --addons-path=… placé avant le mot module est pris en compte.
  • Sans -c, elle ne lit pas ton odoo.conf : elle lit ~/.odoorc s'il existe, sinon les réglages par défaut et cherche PostgreSQL sur le port 5432 du socket local.
  • Elle ne crée pas la base : le texte d'aide renvoie à odoo-bin db init. Elle ajoute d'elle-même --no-http.

Une installation réussie n'écrit rien sur la sortie standard : tout part dans le journal, sur la sortie d'erreur. C'est ce qui permet de filtrer proprement la sortie de module list.

3. module list : ce qui est installé, et à quelle version

Une ligne par module installé, puis une ligne par module en attente (à installer, à mettre à jour, à retirer) s'il en reste. Le journal part sur la sortie d'erreur : 2>/dev/null laisse une liste qu'on peut passer à grep ou wc.

ColonneContenu
1Nom technique du module.
2Version enregistrée en base (champ latest_version) : celle de la dernière installation ou mise à jour.
3Version du manifeste sur le disque (champ installed_version, calculé). Un module absent du chemin des modules y affiche la valeur par défaut, pas une erreur.
4État : 'installed', 'to install', 'to upgrade', 'to remove'.
5Nom court du module, en anglais.

Les applications sortent en tête (_order = 'application desc,sequence,name'), puis le reste par ordre alphabétique. Le cas utile au quotidien est celui de la figure : après un git pull, les lignes dont les colonnes 2 et 3 diffèrent sont les modules à mettre à jour.

4. --dry-run : voir avant de faire

install, upgrade et uninstall acceptent -n ou --dry-run. Odoo marque les modules comme le ferait l'opération réelle, affiche tous ceux qui changeraient d'état, puis annule la transaction. Installer les Achats sur une base qui a Ventes et Inventaire :

./odoo-bin module install -n purchase -c odoo.conf -d ma_base 2>/dev/null
purchase - 20.0.1.2 'to install' Purchase purchase_stock - 20.0.1.2 'to install' Purchase Stock purchase_edi_ubl_bis3 - 20.0.1.0 'to install' Import/Export electronic orders with UBL sale_purchase - 20.0.1.0 'to install' Sale Purchase sale_purchase_stock - 20.0.1.0 'to install' MTO Sale <-> Purchase

Un module demandé, cinq installés : les quatre autres sont des modules auto_install qui relient les Achats à ce qui est déjà là. Le tiret de la deuxième colonne dit qu'aucune version n'est encore en base. Après la simulation (1,4 s), rien n'a bougé : purchase est toujours uninstalled.

Pour une mise à jour, la simulation montre les modules dépendants que -u rechargera :

./odoo-bin module upgrade -n stock -c odoo.conf -d ma_base 2>/dev/null
stock 20.0.1.1 20.0.1.1 'to upgrade' Inventory stock_account 20.0.1.1 20.0.1.1 'to upgrade' WMS Accounting sale_stock 20.0.1.0 20.0.1.0 'to upgrade' Sales and Warehouse Management sale_stock_margin 20.0.1.0 20.0.1.0 'to upgrade' Sale Stock Margin spreadsheet_dashboard_stock_account 20.0.1.0 20.0.1.0 'to upgrade' Spreadsheet dashboard for stock stock_sms 20.0.1.0 20.0.1.0 'to upgrade' Stock - SMS

Et l'option --outdated de upgrade ne garde que les modules dont le manifeste sur disque est plus récent que la version en base. Combinée à all et à -n, elle répond à « que faut-il mettre à jour après ce déploiement ? » :

./odoo-bin module upgrade --outdated -n all -c odoo.conf -d ma_base 2>/dev/null
mon_module 20.0.1.0.0 20.0.1.1.0 'to upgrade' Mon module

Sans -n, la même commande met à jour ce seul module au lieu des 70 installés.

5. Désinstaller : les dépendances partent avec

Il n'y a pas d'option du serveur pour désinstaller : c'est odoo-bin module uninstall, ou button_immediate_uninstall() depuis la console. Désinstaller un module retire aussi tous les modules installés qui en dépendent, sans question. La simulation le montre :

Ce que la désinstallation réelle supprime : les enregistrements créés par les modules retirés (vues, menus, droits, groupes, modèles de courriel… et leurs données de démonstration), puis les tables et les colonnes de leurs modèles. Sur la copie où les Achats venaient d'être installés, module uninstall purchase a pris 4,7 s et supprimé les 13 bons de commande, les réceptions liées et les tables purchase_order et purchase_order_line. Les bons de commande saisis à la main partent de la même façon, avec la table : une sauvegarde d'abord.

Le journal de cette désinstallation mérite d'être lu :

La désinstallation va jusqu'au bout, mais le colis PAL0000001 reste en base, rattaché à un identifiant externe d'un module désinstallé.

Désinstaller n'est pas annuler

Sur deux copies, réinstaller les Achats juste après les avoir désinstallés a échoué (code de sortie 1) : les données de démonstration de purchase_stock retrouvent un transfert laissé par la première installation et s'arrêtent sur UserError: Modifier le type d'opération de cet enregistrement est interdit à ce stade. La base reste à moitié installée : purchase installé, purchase_stock non. Pour tester un module, travaille sur une copie de la base et jette-la ; ne compte pas sur la désinstallation pour revenir en arrière.

Deux refus, eux, sont francs (code de sortie 1, UserError dans le journal) : module uninstall base (« Ces modules ne peuvent pas être désinstallés : base ») et la désinstallation d'un module déjà désinstallé.

6. Lire le journal : un code 0 ne prouve rien

Dans un script de déploiement, on est tenté de s'arrêter au code de sortie. Voici ce qu'il vaut, essai par essai :

CommandeCodeCe que dit le journal
-i purchse --stop-after-init (faute de frappe)0WARNING … invalid module names, ignored: purchse
-u purchse --stop-after-init0même WARNING
module install purchse0WARNING … module purchse: manifest not found
module uninstall purchse0rien
module uninstall purchase (figure ci-dessus)0une ligne ERROR … bad query
-i mon_module --stop-after-init, vue qui cite un champ inexistant255ParseError, CRITICAL … Failed to initialize database
module install mon_module, même module1ParseError, traceback

Une erreur qui empêche le registre de se charger donne bien un code non nul. Tout le reste, nom mal tapé ou erreur pendant une désinstallation, sort en 0. La vérification utile tient en deux lignes : garder le journal, puis le relire.

./odoo-bin -c odoo.conf -d ma_base -u sale --stop-after-init --no-http 2> maj.log
grep -E " (WARNING|ERROR|CRITICAL) " maj.log

Et pour un module qu'on vient d'installer, module list confirme qu'il est bien là, avec la bonne version.

7. force-demo : ajouter la démo après coup

En Odoo 20, une base n'a de données de démonstration que si on le demande (--with-demo à la création). Pour en ajouter à une base créée sans :

./odoo-bin module force-demo -c odoo.conf -d ma_base_vide

Sur une base neuve avec Ventes (59 modules, aucune commande, 5 contacts), la commande a pris 9,8 s et laissé 20 commandes de vente et 42 contacts. Elle fait plus qu'ajouter des enregistrements (odoo/modules/loading.py, force_demo) :

  • elle coche « démo » sur tous les modules connus, installés ou non : un module installé plus tard viendra lui aussi avec ses données de démonstration ;
  • elle ramène la longueur minimale des mots de passe (auth_password_policy.minlength) à 4.

Réservée aux bases de formation et de test, donc.

8. -u all et ses risques

-u all (ou module upgrade all) recharge chaque module installé. Sur la base de démonstration avec les Achats, 74 modules, il a pris 37,9 s, sans un seul WARNING. Le temps n'est pas le vrai risque : une mise à jour réécrit tout ce qui vient d'un fichier de données non marqué noupdate. Une retouche faite dans l'interface sur une vue, un menu ou une action standard disparaît. La preuve sur le menu Ventes, dans la console :

menu = env.ref('sale.sale_menu_root')
print("avant :", menu.name, menu.sequence)
menu.sequence = 1
env.cr.commit()
print("après écriture :", menu.sequence)
avant : Ventes 30 après écriture : 1

Puis ./odoo-bin -c odoo.conf -d ma_base -u sale --stop-after-init --no-http (5,6 s), et relecture :

après -u sale : Ventes 30

La séquence est revenue à la valeur du fichier sale/views/sale_menus.xml. Avec all, c'est vrai pour tous les modules à la fois ; les enregistrements chargés en noupdate="1" ne sont pas touchés.

Avant un -u all

  • Sauvegarder la base et le filestore.
  • Préférer la liste précise : module upgrade --outdated -n all dit quels modules ont changé de version, puis -u sur ceux-là seulement.
  • Garder le journal et y chercher WARNING et ERROR : le code de sortie ne suffit pas (section 6).
  • Sur une production en workers > 0 : --no-http, ou arrêter le service pendant la mise à jour.

Une opération sur les modules ne se lance pas pendant qu'une autre tourne : Odoo pose un verrou et abandonne au bout de 3 secondes avec « Odoo is currently processing another module operation » (ir_module.py, _button_immediate_function). Et comme le bouton Activer, module install valide la transaction : il n'y a pas de retour arrière.

Venant de la 19

  • odoo-bin module list est nouveau : la 19 n'a que install, upgrade, uninstall et force-demo.
  • -n / --dry-run est nouveau sur install, upgrade et uninstall.
  • --stop est un nouvel alias de --stop-after-init.
  • Inchangés : -D/--data-dir et upgrade --outdated existent aussi dans la 19 à jour.

Récapitulatif

  • -i et -u passent par le serveur ; odoo-bin module fait l'opération et rend la main, mais ne lit que -c, -d et -D.
  • --no-http évite l'OSError: [Errno 98] quand le service tourne en workers > 0.
  • module list compare version en base et version sur disque ; --dry-run montre les modules entraînés sans rien changer.
  • Désinstaller retire les modules dépendants, leurs données et leurs tables, et ne garantit pas une réinstallation propre.
  • Un code de sortie 0 n'exclut ni un nom mal tapé ni une erreur SQL : le journal fait foi.
  • -u all réécrit les données non noupdate de tous les modules : sauvegarde et liste ciblée d'abord.
