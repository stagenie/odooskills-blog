Rapport sur une vue SQL en Odoo 20 : _auto = False et _table_sql

Un modèle sans table, une requête SQL qui l'alimente, une liste et un pivot par-dessus : le rapport d'analyse à la manière des rapports de Ventes, rejoué sur la démo d'Odoo 20, avec le piège _table_query pour qui vient de la 19.

~6 minutes de lecture · niveau intermédiaire · série Astuces dev Odoo 20

Édition : Community. Vérifié sur Odoo 20.0 Community, octobre 2026, base de démonstration avec Ventes et Inventaire, et deux petits modules d'exemple.

La réponse en bref

  1. Un modèle avec _auto = False : Odoo ne crée pas de table, tes champs sont en readonly=True.
  2. Sa source : soit init() qui crée une vraie vue PostgreSQL (CREATE OR REPLACE VIEW), soit une propriété _table_sql qui renvoie SQL("(SELECT …)"). Dans les deux cas, une colonne id unique.
  3. _depends (ou to_flush) pour que le rapport voie les écritures en attente.
  4. Un droit de lecture dans ir.access.csv, une action liste/pivot, un menu.

L'attribut _table_query de la 19 n'existe plus : Odoo 20 l'ignore sans refuser le module.

1. Le modèle et sa vue SQL

Le besoin type : un tableau « ventes confirmées par client » qu'aucun champ calculé ne donne efficacement, parce qu'il regroupe des milliers de commandes. Une requête SQL le fait en une passe ; le modèle Odoo se contente de la lire. Le module d'exemple dépend de sale :

# mon_rapport_sql/models/mon_rapport_client.py
from odoo import fields, models, tools
from odoo.tools import SQL


class MonRapportClient(models.Model):
    _name = 'mon.rapport.client'
    _description = "Ventes confirmées par client"
    _auto = False                      # pas de table : c'est init() qui crée la vue
    _order = 'montant_ht desc'
    _depends = {
        'sale.order': ['partner_id', 'company_id', 'state', 'amount_untaxed', 'date_order'],
    }

    partner_id = fields.Many2one('res.partner', string="Client", readonly=True)
    company_id = fields.Many2one('res.company', string="Société", readonly=True)
    nb_commandes = fields.Integer("Commandes", readonly=True)
    montant_ht = fields.Float("Montant HT", readonly=True)
    derniere_commande = fields.Datetime("Dernière commande", readonly=True)

    def init(self):
        tools.drop_view_if_exists(self.env.cr, self._table)
        self.env.cr.execute(SQL("""
            CREATE OR REPLACE VIEW %s AS (
                SELECT MIN(so.id)            AS id,
                       so.partner_id,
                       so.company_id,
                       COUNT(*)              AS nb_commandes,
                       SUM(so.amount_untaxed) AS montant_ht,
                       MAX(so.date_order)    AS derniere_commande
                  FROM sale_order so
                 WHERE so.state = 'sale'
              GROUP BY so.partner_id, so.company_id
            )""", SQL.identifier(self._table)))

Trois points qui ne se devinent pas :

  • init() est appelée à chaque installation et mise à jour du module, juste après la création des tables (qu'Odoo saute ici, puisque _auto vaut False), au moment où le journal affiche « creating or updating database tables ». drop_view_if_exists supprime l'ancienne vue avant de recréer la nouvelle.
  • La colonne id est obligatoire : chaque requête de l'ORM commence par SELECT "table"."id". Avec un GROUP BY, MIN(so.id) donne un identifiant unique et stable par groupe.
  • Le nom de la vue est self._table, dérivé de _name : mon_rapport_client. SQL.identifier() le met entre guillemets.

La sécurité suit le format d'Odoo 20 : un fichier security/ir.access.csv, ici en lecture seule pour les vendeurs.

id,name,model_id,group_id/id,operation,domain
mon_rapport_client_vendeur,Rapport client : lecture vendeur,mon.rapport.client,sales_team.group_sale_salesman,r,

On installe, puis on interroge le modèle dans odoo-bin shell avec ce petit script :

# sonde_v1.py
Rapport = env['mon.rapport.client']
for r in Rapport.search([], limit=5):
    print(f"{r.partner_id.name:<28} {r.nb_commandes:>2}  {r.montant_ht:>10.2f}  {r.derniere_commande}")
print("lignes :", Rapport.search_count([]))
env.cr.execute("SELECT relkind FROM pg_class WHERE relname = 'mon_rapport_client'")
print("relkind :", env.cr.fetchone()[0])
print(Rapport._read_group([], ['company_id'], ['nb_commandes:sum', 'montant_ht:sum']))

Le modèle se lit comme un autre : search, search_count, _read_group, les relations (r.partner_id.name). La différence est en base : relkind vaut v (vue), pas r (table). Tu peux donc aussi la consulter dans psql avec un simple SELECT.

2. Une liste et un pivot dans le menu Analyse

Côté interface, rien de spécial : une vue liste sans création ni édition, une vue pivot, une action et un menu rangé sous sale.menu_sale_report.

Le menu parent Analyse est réservé au groupe des responsables (sales_team.group_sale_manager) : un vendeur n'y voit pas le rapport, même avec le droit de lecture. Range le menu ailleurs si le rapport leur est destiné. Le bouton à droite de la liste ouvre le pivot, avec les mêmes mesures.

3. _depends : voir les écritures pas encore en base

L'ORM garde les écritures en mémoire et ne les envoie à PostgreSQL qu'au besoin. Une vue SQL lit la base, pas cette mémoire. _depends dit à Odoo quels champs écrire avant d'interroger le rapport. Ce script confirme un devis en cache, sans rien valider, puis relit :

# sonde_depends.py
Rapport = env['mon.rapport.client']
devis = env['sale.order'].search([('state', '=', 'draft')], limit=1)
print("devis :", devis.name, devis.partner_id.name, devis.amount_untaxed)
print("avant :", Rapport.search_count([]), "lignes")
devis.state = 'sale'          # écrit en cache, pas encore en base
print("après :", Rapport.search_count([]), "lignes")
env.cr.rollback()

Avec _depends, puis en le retirant du modèle :

devis : S00003 Ready Mat 377.5 avant : 3 lignes après : 4 lignes devis : S00003 Ready Mat 377.5 avant : 3 lignes après : 3 lignes

Sans _depends, le rapport ignore la commande tant qu'aucune autre opération n'a écrit en base : un bouton qui confirme puis lit le rapport dans la même transaction obtient un chiffre en retard d'une écriture. Liste chaque champ que ta requête lit, modèle par modèle.

4. Venant de la 19 : _table_query est ignoré, passe à _table_sql

En 19, un rapport pouvait se passer de vue : l'attribut _table_query recevait la requête et Odoo l'utilisait comme sous-requête. Cet attribut a disparu du cœur de la 20. Un module qui le déclare encore s'installe pourtant :

class RapportV19(models.Model):
    _name = 'mon.rapport.v19'
    _auto = False
    _table_query = """
        SELECT MIN(id) AS id, partner_id, COUNT(*) AS nb_commandes
          FROM sale_order WHERE state = 'sale' GROUP BY partner_id
    """

_table_sql pointe vers une table mon_rapport_v19 qui n'existe pas : l'attribut est lu nulle part. Le test de qualité du cœur (test_lint) range d'ailleurs _table_query parmi les attributs dépréciés, avec la consigne « overwrite _table_sql ». La version 20 :

from odoo import fields, models
from odoo.tools import SQL


class RapportV19(models.Model):
    _name = 'mon.rapport.v19'
    _description = "Rapport écrit pour la 19"
    _auto = False

    partner_id = fields.Many2one('res.partner', readonly=True)
    nb_commandes = fields.Integer(readonly=True)

    @property
    def _table_sql(self):
        commande = self.env['sale.order']
        return SQL("""(
            SELECT MIN(id) AS id, partner_id, COUNT(*) AS nb_commandes
              FROM sale_order WHERE state = 'sale' GROUP BY partner_id
        )""", to_flush=[commande._fields['partner_id'], commande._fields['state']])

Après -u, l'erreur « has no table » disparaît : Odoo ne cherche plus de table pour un modèle qui fournit son propre _table_sql. La requête, entre parenthèses, devient le FROM de chaque recherche ; aucune vue n'est créée en base. C'est la forme que prennent en 20 les rapports de Ventes et d'Achats (sale.report, purchase.report).

Surcharger _table_sql fait perdre _depends

C'est la propriété _table_sql d'origine qui transforme _depends en champs à écrire avant la requête. La remplacer, c'est perdre ce mécanisme : avec un _depends déclaré et une _table_sql sans to_flush, la sonde du point 3 donne 3 puis 3. Avec to_flush=[…] comme ci-dessus, 3 puis 4. Un portage mécanique de _table_query vers _table_sql perd donc ce rafraîchissement sans aucun message.

Quelle forme choisir ? La vue d'init() se lit aussi hors d'Odoo (psql, un outil de tableau de bord) et sa requête est figée à l'installation. _table_sql est évaluée à chaque recherche : elle peut dépendre de l'environnement, de la date du jour ou d'un paramètre, comme le fait purchase.report.

À retenir

  • _auto = False, champs readonly, une colonne id unique (MIN(id) sur un GROUP BY).
  • Vue PostgreSQL : init() avec drop_view_if_exists puis CREATE OR REPLACE VIEW.
  • Sous-requête : @property _table_sql qui renvoie SQL("(…)", to_flush=[…]) ; _table_query est ignoré en 20.
  • _depends (ou to_flush) pour que le rapport voie les écritures du cache.
