pre-commit, ruff et GitHub Actions pour un module Odoo 20

Un dépôt de modules Odoo 20, des contrôles qui refusent un commit écrit avec des réflexes de la 19, et un workflow qui lance les tests sur PostgreSQL 16. Chaque version d'outil a été relevée le jour de l'écriture, chaque commande exécutée, et chaque étape du workflow rejouée en dehors de GitHub.

~12 minutes de lecture · niveau intermédiaire · parcours Qualité & tests

Ce que tu vas apprendre

Contrôler avant le commit

Un .pre-commit-config.yaml pour Odoo 20 : ruff, les outils OCA qui fonctionnent en 20.0, et deux contrôles maison pour les fichiers qui n'existent plus.

Régler ruff pour Odoo 20

target-version = "py312", l'ordre des imports d'Odoo, et des imports interdits qui attrapent les modules supprimés.

Tester sur GitHub

Un workflow à deux jobs, PostgreSQL 16 en service, et un script qui juge le code de sortie et le journal.

Prérequis

  • Un module Odoo 20 qui a des tests, et savoir les lancer en ligne de commande (Tests automatisés en Odoo 20 : TransactionCase).
  • Git, et Python 3.12 sur le poste : c'est le minimum d'Odoo 20, et la version utilisée ici pour tous les outils.
  • Pour la partie GitHub : un dépôt où vous pouvez ajouter un dossier .github/workflows. Aucun service payant n'est nécessaire.

1. Le dépôt et le pipeline

Le dépôt suit la disposition habituelle d'un dépôt de modules : un module par dossier, à la racine, et la configuration à côté. Le module d'exemple pose un code client sur les contacts (oski_code_client), avec ses tests, dont un tour joué dans Chrome, et un petit module réservé aux tests (test_oski_code_client).

├── .gitignore
├── .pre-commit-config.yaml        # les contrôles avant commit

├── ci/lancer_tests.sh             # lancement des tests + garde-fous
├── oski_code_client/
└── test_oski_code_client/

2. ruff réglé pour Odoo 20

ruff remplace à lui seul flake8, isort et pyupgrade, et sait aussi formater. Le réglage qui dépend de la version d'Odoo est target-version : il dit à ruff quelle version de Python le code doit supporter. Odoo 20 refuse de démarrer avec un Python plus ancien que 3.12 (MIN_PY_VERSION = (3, 12) dans odoo/release.py, contre (3, 10) en 19.0). Le dépôt d'Odoo contient d'ailleurs son propre ruff.toml : entre les branches 19.0 et 20.0, la seule ligne qui change est target-version = "py310" devenue "py312".

# Module Odoo 20 : Python >= 3.12 exigé (odoo/release.py, MIN_PY_VERSION)
target-version = "py312"
line-length = 120

[lint]
select = ["E", "W", "F", "I", "UP", "B", "PLE", "T20", "TID", "G", "LOG"]
ignore = [
    "E501",   # longueur de ligne : laissée au formateur
    "UP031",  # '%s-%05d' % (...) : style courant du code Odoo
]

[lint.per-file-ignores]
"**/__init__.py" = ["F401", "I001"]   # un « from . import x » par ligne, comme dans Odoo
"**/__manifest__.py" = ["B018"]       # le manifeste est un dictionnaire seul

[lint.isort]
section-order = ["future", "standard-library", "third-party", "odoo", "odoo-addons", "first-party", "local-folder"]

[lint.isort.sections]
"odoo" = ["odoo"]
"odoo-addons" = ["odoo.addons"]

[lint.flake8-tidy-imports.banned-api]
"odoo.osv".msg = "paquet supprimé en Odoo 20 : from odoo.fields import Domain"
"odoo.tools.ormcache".msg = "obsolète en Odoo 20 : from odoo.api import ormcache"
"pytz".msg = "retiré du requirements.txt d'Odoo 20 (encore tiré par Babel) : utiliser zoneinfo"

[format]
quote-style = "preserve"

Trois choix méritent une explication.

  • Les imports interdits (règle TID251) transforment trois écarts d'Odoo 20 en erreurs de lint : le paquet odoo.osv n'existe plus (il est remplacé par Domain, voir les domaines en Odoo 20), pytz a quitté le requirements.txt d'Odoo (il reste installé comme dépendance de Babel et de zeep, mais le cœur ne le garantit plus), et from odoo.tools import ormcache émet un DeprecationWarning « Since 20.0 ». Le message de chaque interdiction dit quoi écrire à la place.
  • target-version change ce que ruff propose. Sur la même ligne datetime.timezone.utc, la règle UP017 demande l'alias datetime.UTC avec py312, et ne dit rien avec py310 : l'alias n'existe que depuis Python 3.11.
  • quote-style = "preserve" : le code d'Odoo et de la plupart des modules utilise les apostrophes. Sans ce réglage, ruff format réécrit toutes les chaînes entre guillemets doubles : sur le module d'exemple, 10 fichiers sur 17.

Sur un fichier qui accumule ces réflexes de la 19 :

$ ruff check piege.py TID251 `pytz` is banned: retiré du requirements.txt d'Odoo 20 (encore tiré par Babel) : utiliser zoneinfo --> piege.py:3:8 TID251 `odoo.osv` is banned: paquet supprimé en Odoo 20 : from odoo.fields import Domain --> piege.py:4:1 TID251 `odoo.tools.ormcache` is banned: obsolète en Odoo 20 : from odoo.api import ormcache --> piege.py:5:24 UP017 [*] Use `datetime.UTC` alias --> piege.py:9:34 Found 5 errors. (extrait : la cinquième est l'ordre des imports, I001)

Le ruff.toml d'Odoo n'est pas un réglage de module

Copier tel quel le ruff.toml du dépôt d'Odoo est tentant. Son en-tête prévient pourtant qu'il est généré pour les contrôles nocturnes du runbot, et que certaines règles n'y sont « pas encore appliquées ». Lancé avec ruff 0.17.4 sur le seul module sale d'Odoo 20, il relève plus de 740 points, dont plus de 720 virgules finales manquantes (COM812). Et il n'a pas de section [format] : le cœur n'est pas formaté par ruff format, qui réécrirait deux fichiers sur trois dans sale et contacts, même en conservant les apostrophes. Partez d'un jeu de règles court, comme ci-dessus, et ajoutez-en au besoin.

3. Ce que les outils OCA proposent pour la 20.0

L'OCA maintient la plupart des outils de contrôle propres à Odoo. Avant de les mettre dans la configuration, chacun a été installé et essayé sur un module Odoo 20 :

pylint-odoo et oca-checks-odoo-module fonctionnent donc en 20.0, mais aucun ne repère les fichiers de droits de la 19. D'où deux contrôles locaux dans la configuration : un nom de fichier interdit, et un motif cherché dans le XML.

Les deux messages désactivés de pylint-odoo sont propres aux dépôts de l'OCA (auteur « OCA » obligatoire, fichier README.rst). Les versions (rev) sont les dernières publiées le jour de l'écriture ; pre-commit autoupdate l'a confirmé : already up to date! pour les quatre dépôts. Relancez-le de temps en temps : c'est lui qui fait avancer ces numéros.

4. Installer, puis le premier passage

pre-commit est un programme Python ; installez-le dans un environnement à part, pas dans celui d'Odoo, puis branchez-le sur le dépôt :

python3.12 -m venv ~/outils && ~/outils/bin/pip install pre-commit==4.7.0
cd mon_depot
~/outils/bin/pre-commit install        # écrit .git/hooks/pre-commit

Au premier git commit, pre-commit prépare un environnement par dépôt de contrôles (une fois pour toutes), puis les lance sur les fichiers du commit. Sur les deux modules, écrits sans ces outils, le premier commit a été refusé par trois contrôles :

ruff format...............................................................Failed - hook id: ruff-format - files were modified by this hook 4 files reformatted, 13 files left unchanged Checks for py, csv and xml files of Odoo modules..........................Failed oski_code_client/views/res_partner_views.xml:1: xml-header-wrong XML header expected '<?xml version="1.0" encoding="UTF-8" ?>' but received '<?xml version="1.0" encoding="utf-8"?>' Check for Odoo modules using pylint.......................................Failed oski_code_client/__manifest__.py:13:4: C8116: Manifest superfluous key "installable". It is the same as the default value: True. Better remove it (manifest-superfluous-key) …

ruff format a corrigé lui-même ses quatre fichiers : il suffit de les ajouter de nouveau au commit. Les deux autres points se corrigent à la main : l'en-tête XML, et la clé 'installable': True, qui ne fait que répéter la valeur par défaut. Le commit suivant passe.

5. Un commit refusé sur une vraie faute

Le cas qui justifie l'outil : une nouvelle méthode, écrite avec les habitudes de la 19, et un manifeste repris d'une branche 19.0 lors d'un report de correctif.

# models/res_partner.py (version refusée)
from odoo import api, models
from odoo.osv import expression


class ResPartner(models.Model):
    _name = 'res.partner'
    _inherit = ['res.partner', 'oski.code.mixin']
    _oski_code_prefixe = 'CLI'

    @api.model
    def _oski_domaine_sans_code(self, domaine=None):
        """Contacts encore sans code, dans le domaine donné."""
        return expression.AND([domaine or [], [('oski_code', '=', False)]])

# __manifest__.py : 'version': '19.0.1.1.0'

Ces deux fautes ne se voient pas de la même façon dans Odoo 20. L'import casse le chargement du module. La version 19.0.x, elle, ne casse rien : Odoo marque le module non installable avec un simple avertissement, et un -i sort avec le code 0 (voir les messages d'un module 19 sous Odoo 20). Le contrôle du manifeste attrape donc une panne silencieuse avant qu'elle ne parte.

# models/res_partner.py (version acceptée)
from odoo import api, models
from odoo.fields import Domain


class ResPartner(models.Model):
    _name = 'res.partner'
    _inherit = ['res.partner', 'oski.code.mixin']
    _oski_code_prefixe = 'CLI'

    @api.model
    def _oski_domaine_sans_code(self, domaine=None):
        """Contacts encore sans code, dans le domaine donné."""
        return Domain(domaine or []) & Domain('oski_code', '=', False)

# __manifest__.py : 'version': '20.0.1.1.0'
$ git commit -m "Contacts sans code : domaine réutilisable" … ruff check................................................................Passed ruff format...............................................................Passed Checks for py, csv and xml files of Odoo modules..........................Passed Check for Odoo modules using pylint.......................................Passed Odoo 20 : plus de ir.model.access.csv.................(no files to check)Skipped Odoo 20 : plus de ir.rule ni ir.model.access en XML...(no files to check)Skipped [main d3d4931] Contacts sans code : domaine réutilisable 3 files changed, 16 insertions(+), 2 deletions(-)

Le commit contient aussi un test de la méthode : il servira plus bas. Les trois autres réflexes de la 19 ont été essayés sur une branche jetable : un security/ir.model.access.csv, un <record model="ir.rule"> et un gabarit en t-esc, qui en Odoo 20 n'affiche plus rien (pannes silencieuses d'un module 19).

Les droits s'écrivent désormais dans security/ir.access.csv, détaillé dans les droits d'accès en Odoo 20.

6. Le workflow GitHub Actions

Les contrôles du poste se contournent (git commit --no-verify, ou un poste où pre-commit n'est pas installé). Le workflow, enregistré dans .github/workflows/test.yml, les rejoue sur chaque push vers la branche 20.0 et chaque pull request qui la vise, puis lance les tests. Le dépôt d'essai de cet article travaillait sur main : adaptez branches à la branche de vos modules 20.

name: tests

on:
  push:
    branches: ["20.0"]
  pull_request:
    branches: ["20.0"]

permissions:
  contents: read

jobs:
  pre-commit:
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v7
        with:
          persist-credentials: false
      - uses: actions/setup-python@v7
        with:
          python-version: "3.12"
      - run: pip install pre-commit==4.7.0
      - run: pre-commit run --all-files --show-diff-on-failure

  tests:
    runs-on: ubuntu-24.04
    needs: pre-commit
    services:
      postgres:
        image: postgres:16
        env:
          POSTGRES_USER: odoo
          POSTGRES_PASSWORD: odoo
          POSTGRES_DB: postgres
        ports:
          - 5432:5432
        options: >-
          --health-cmd pg_isready
          --health-interval 5s
          --health-timeout 5s
          --health-retries 10
    env:
      MODULES: oski_code_client,test_oski_code_client
      PGHOST: localhost
      PGPORT: "5432"
      PGUSER: odoo
      PGPASSWORD: odoo
      TMPDIR: /tmp
    steps:
      - uses: actions/checkout@v7
        with:
          path: addons
          persist-credentials: false
      - uses: actions/setup-python@v7
        with:
          python-version: "3.12"
      - name: Odoo 20 Community
        run: git clone --depth 1 --branch 20.0 https://github.com/odoo/odoo.git odoo
      - name: Dépendances Python
        run: |
          sudo apt-get update
          sudo apt-get install -y --no-install-recommends libldap2-dev libsasl2-dev libpq-dev
          python -m venv venv
          venv/bin/pip install -r odoo/requirements.txt websocket-client
      - name: Tests des modules
        env:
          ODOO: venv/bin/python odoo/odoo-bin --addons-path=odoo/addons,addons
        run: addons/ci/lancer_tests.sh "ci_${{ github.run_id }}" "$MODULES"
      - name: Journal et captures en cas d'échec
        if: failure()
        uses: actions/upload-artifact@v7
        with:
          name: journal-tests
          path: |
            tests.log
            /tmp/odoo_tests/
          if-no-files-found: ignore
  • postgres:16 : Odoo 20 attend PostgreSQL 16 au minimum (MIN_PG_VERSION = 16, 13 en 19.0). Une version plus ancienne ne bloque pas le démarrage : seul un avertissement dans le journal le signale, et le script ne le fait pas échouer.
  • Les variables PG* : sans option --db_host, --db_user…, Odoo laisse la bibliothèque PostgreSQL lire PGHOST, PGPORT, PGUSER et PGPASSWORD ; la ligne database: odoo@localhost:… en tête du journal le confirme. Aucun fichier de configuration n'est nécessaire.
  • Le clone : --depth 1 ne récupère que le dernier état de la branche 20.0, sans l'historique. Le module est testé contre l'Odoo publié le jour du passage, ce qui fait aussi de ce job une alerte précoce sur les changements du cœur.
  • websocket-client : ce paquet n'est pas dans le requirements.txt d'Odoo (ni en 20.0, ni en 19.0), et sans lui aucun tour ne tourne. La section suivante montre ce qui se passe quand on l'oublie.
  • TMPDIR: /tmp : Chrome crée son profil et son socket de contrôle dans le dossier temporaire ; un chemin trop long l'empêche de démarrer, et le tour est alors sauté sans échec. Le dossier temporaire du système est court, autant le fixer.
  • Les paquets système servent à compiler python-ldap 3.4.4 et psycopg2 2.9.9, que PyPI ne publie pas en roues pour Linux ; l'image ubuntu-24.04 fournit déjà Python 3.12 et Google Chrome, selon la liste de logiciels publiée pour cette image.

7. Juger le résultat : le code de sortie ET le journal

Odoo sort avec 1 quand un test échoue, et 255 quand la base ne se charge pas. Mais il sort avec 0 dans des cas où rien, ou presque, n'a été testé. Le script ci/lancer_tests.sh ajoute quatre contrôles du journal au code de sortie. Le workflow l'appelle directement : committez-le exécutable (chmod +x ci/lancer_tests.sh), sinon l'étape s'arrête sur « Permission denied ».

#!/bin/bash
# Lance les tests Odoo 20 d'une liste de modules sur une base neuve, et échoue
# si le code de sortie OU le journal montre un problème.
# Usage : ODOO="venv/bin/python odoo/odoo-bin --addons-path=…" ci/lancer_tests.sh <base_neuve> <module1,module2>
# Connexion PostgreSQL : variables PGHOST, PGPORT, PGUSER, PGPASSWORD.
set -o pipefail
BASE=$1
MODULES=$2
TAGS="/${MODULES//,/,/}"                 # oski_a,oski_b -> /oski_a,/oski_b
JOURNAL=${JOURNAL:-tests.log}

$ODOO -d "$BASE" -i "$MODULES" --with-demo --test-tags "$TAGS" \
      --db-filter="^${BASE}\$" --http-port="${ODOO_HTTP_PORT:-8069}" \
      --stop-after-init 2>&1 | tee "$JOURNAL"
RC=$?
echo "Code de sortie d'Odoo : $RC"

grep -q "odoo.tests.result: .* of 0 tests" "$JOURNAL" && { echo "ÉCHEC : aucun test lancé"; RC=1; }
grep -q " skipped" "$JOURNAL" && { echo "ÉCHEC : au moins un test sauté"; grep -m3 -E "SkipTest|skipped" "$JOURNAL"; RC=1; }
grep -qE "^[0-9-]+ [0-9:,]+ [0-9]+ (ERROR|CRITICAL) " "$JOURNAL" && { echo "ÉCHEC : ERROR ou CRITICAL dans le journal"; RC=1; }
grep -q "odoo.tests.result" "$JOURNAL" || { echo "ÉCHEC : pas de ligne de résultat"; RC=1; }
echo "Code de sortie : $RC"
exit $RC

La base est neuve à chaque passage (nommée d'après le numéro du passage) : -i sur un module déjà installé ne relance pas ses tests. Le filtre de bases strict évite qu'un test HTTP ne tombe sur une autre base. Les quatre cas ci-dessous ont été rejoués avec ce script, sur PostgreSQL 16 et un clone frais de la branche 20.0 :

CasLigne de résultat d'OdooCode d'OdooCode du script
Environnement installé avec requirements.txt seul0 failed, 0 error(s) of 16 tests — tour skipped01 (test sauté)
Même chose avec websocket-client0 failed, 0 error(s) of 16 tests — tour succeeded00
Une espace après la virgule dans MODULES0 failed, 0 error(s) of 14 tests01 (ERROR dans le journal)
Régression : | au lieu de & dans le domaine1 failed, 0 error(s) of 16 tests11

Le premier cas est le plus probable sur un environnement neuf : pip install -r requirements.txt ne suffit pas pour les tours. Les 16 tests sont bien annoncés, la ligne de résultat est verte, et le seul indice est le mot skipped.

Une espace dans la liste des modules, et deux tests disparaissent

Avec MODULES: oski_code_client, test_oski_code_client, -i installe bien les deux modules, mais la sélection devient /oski_code_client,/ test_oski_code_client. Odoo refuse le second élément (Invalid tag, 34 fois dans le journal), ne lance que les 14 tests de oski_code_client et sort avec 0. Seul le contrôle des lignes ERROR fait échouer le job. Le même contrôle attrape toute ligne ERROR écrite pendant l'installation sans interrompre Odoo.

8. Validé et rejoué, pas exécuté sur GitHub

Le workflow de cet article n'a pas tourné sur GitHub : il a été validé, puis chacune de ses étapes rejouée avec les mêmes commandes sur une machine Ubuntu 24.04. Avant de pousser un workflow, actionlint vérifie la syntaxe, les expressions ${{ … }}, les dépendances entre jobs et, si shellcheck est installé, les scripts des étapes run.

Étape du workflowRejouée ainsi
Job pre-commitclone neuf du dépôt, environnement Python 3.12 neuf, cache pre-commit vide, pre-commit run --all-files --show-diff-on-failure : tous les contrôles Passed
postgres:16un PostgreSQL 16 existant, mêmes variables PG* (port différent)
Clone d'Odoola même commande git clone --depth 1 --branch 20.0

Ce qui reste propre à GitHub et n'a pas été vérifié ici : le démarrage du conteneur de service, les actions checkout, setup-python et upload-artifact elles-mêmes, et le Chrome de l'image. Lors du premier passage, lisez le journal de l'étape « Tests des modules » jusqu'à la ligne tour succeeded.

Venant de la 19

  • target-version : py310 pour un module 19, py312 pour un module 20 ; c'est la seule différence entre les ruff.toml du dépôt d'Odoo des deux versions. Le gabarit OCA généré pour la 20.0 écrit encore py310 : corrigez-le.
  • PostgreSQL : 13 au minimum en 19.0, 16 en 20.0, avec le même simple avertissement en dessous. Un workflow 19 sur postgres:13 ou 14 est à changer.
  • pylint-odoo : --valid-odoo-versions=19.0 devient 20.0, sinon chaque manifeste porté est refusé, ou un manifeste oublié en 19.0 passe.
  • Les imports et fichiers interdits ci-dessus (odoo.osv, pytz, ir.model.access.csv, ir.rule) existent tous en 19.0 : ces contrôles n'ont de sens que sur une branche 20.0.
