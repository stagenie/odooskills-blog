Pièces jointes et champs Binary en Odoo 20 : raw, pas base64

En Odoo 20, un fichier ne voyage plus en base64 dans le code Python : une pièce jointe se crée avec des octets bruts, un champ Binary se lit comme un objet. Créer, lire et servir un fichier, chaque geste rejoué sur la démo.

1. Créer une pièce jointe : le champ raw

Une pièce jointe (ir.attachment) reçoit son contenu dans raw, en octets bruts : pas d'encodage préalable. Ce script, passé à odoo-bin shell, rattache un petit CSV à la fiche d'Acme Corporation :

# creer.py
partner = env['res.partner'].search([('name', '=', 'Acme Corporation')], limit=1)
contenu = "ref;quantite\nFURN_0001;3\n".encode()
att = env['ir.attachment'].create({
    'name': 'commande.csv',
    'raw': contenu,
    'res_model': 'res.partner',
    'res_id': partner.id,
})
print(att.id, att.name, att.mimetype, att.file_size)
print(type(att.raw).__name__, att.raw.content)
print(att.raw.to_base64())
print(att.checksum)
env.cr.commit()

Tu ne fournis que le nom et les octets : Odoo déduit text/csv, compte 25 octets et calcule la somme de contrôle SHA-1. Relu, att.raw n'est pas un bytes mais un objet (LocalBinaryFile, le fichier du filestore) : ses octets sont dans .content, sa forme base64 dans .to_base64(). raw est le seul champ Binary qui accepte des bytes nus. Le couple res_model / res_id fait apparaître le fichier dans le chatter de la fiche :

Venant de la 19 : le champ datas (« File Content (base64) ») n'existe plus sur ir.attachment ; seul raw reste. Dans un fichier de données XML, même logique : <field name="raw" type="bytes" file="mon_fichier/data/modele.csv"/>. L'ancien type="base64" est encore lu mais signalé au chargement : DeprecationWarning: Since 20.0, use type=bytes instead of type=base64.

2. Écrire et lire un champ Binary

Sur un champ Binary ordinaire (ici image_1920 du contact), les bytes sont refusés : Odoo ne peut pas savoir s'ils sont bruts ou déjà en base64. On les enveloppe dans un BinaryBytes. Le script se termine par rollback() : rien n'est enregistré.

# lire.py
import base64
from odoo.tools import BinaryBytes, file_open
partner = env['res.partner'].search([('name', '=', 'Acme Corporation')], limit=1)
with file_open('web/static/img/placeholder.png', 'rb') as f:
    png = f.read()
try:
    partner.image_1920 = png
except TypeError as e:
    print("bytes nus  ->", e)
partner.image_1920 = BinaryBytes(png)
img = partner.image_1920
print("lu         ->", type(img).__name__, img.size, img.mimetype)
print(".content   ->", img.content[:8], img.content == png)
print(".to_base64 ->", img.to_base64()[:20])
print("b64decode  ->", base64.b64decode(img)[:8])
vide = env['res.partner'].search([('image_1920', '=', False)], limit=1)
print("champ vide ->", repr(vide.image_1920), bool(vide.image_1920))
env.cr.rollback()

Ligne par ligne :

  • Écrire : BinaryBytes(octets). Une chaîne base64 reste acceptée (c'est ce qu'envoient le client web et les appels RPC) : partner.image_1920 = img.to_base64() passe. Des bytes base64, eux, lèvent la même TypeError que les octets bruts.
  • Lire : un BinaryBytes qui donne .content, .size (6078), .mimetype (image/png, deviné du contenu) et .to_base64() quand une API externe attend du base64.
  • Champ vide : jamais False, mais un BinaryBytes vide, faux dans un test. if partner.image_1920: fonctionne toujours.
  • Comparer, mesurer : img == png vaut False (compare img.content) ; len(img) lève TypeError: object of type 'BinaryBytes' has no len() : utilise img.size, et passe img.content à toute bibliothèque qui attend des bytes.
  • .decode() décode le contenu brut en texte : sur un PNG, UnicodeDecodeError. Pour une URL data:image/png;base64,…, c'est .to_base64().
  • read() (et donc l'API) renvoie un dictionnaire, ici {'content': <base64>, 'size': …}, plus une simple chaîne.

base64.b64decode(rec.champ) ne lève aucune erreur

En 19, un champ Binary se lisait en base64 et il fallait le décoder. En 20 la valeur est déjà brute, et b64decode l'accepte quand même : il ignore les caractères qui ne sont pas du base64 et rend des octets sans rapport avec le fichier (b'<\xd1\x88…' sur la capture). Le PNG reçu ensuite est illisible, sans trace dans le journal. Cherche b64decode et b64encode appliqués à un champ Binary dans ton code et remplace-les par .content et .to_base64().

3. Servir le fichier au navigateur

Pour un fichier déjà stocké, pas besoin de contrôleur : /web/content/<id> sert une pièce jointe, /web/content/<modèle>/<id>/<champ> n'importe quel champ Binary, ?download=true force le téléchargement, et /web/image/… ajoute le redimensionnement des images. Les droits de lecture de l'utilisateur s'appliquent.

Dans ton propre contrôleur, reprends l'outil de /web/content : ir.binary construit un flux (type MIME, nom de fichier, cache) à partir d'un enregistrement. Pour un fichier fabriqué à la volée, request.make_response suffit :

# mon_fichier/controllers/main.py
from odoo import http
from odoo.http import request
from odoo.http.stream import content_disposition


class MonFichier(http.Controller):

    @http.route('/mon_fichier/logo/<int:pid>', type='http', auth='user')
    def logo(self, pid):
        partner = request.env['res.partner'].browse(pid)
        stream = request.env['ir.binary']._get_stream_from(
            partner, 'image_1920', filename=f'logo-{pid}.png')
        return stream.get_response(as_attachment=True)

    @http.route('/mon_fichier/contact/<int:pid>.csv', type='http', auth='user')
    def contact_csv(self, pid):
        partner = request.env['res.partner'].browse(pid)
        partner.check_access('read')
        data = f"nom;ville\n{partner.name};{partner.city}\n".encode()
        return request.make_response(data, headers=[
            ('Content-Type', 'text/csv; charset=utf-8'),
            ('Content-Disposition', content_disposition(f'{partner.name}.csv')),
        ])

Module installé, $ODOO pointant vers l'instance et cookies.txt contenant une session ouverte, curl montre les en-têtes de chaque réponse :

Sans filename, le nom vient du champ name de l'enregistrement, complété par l'extension du type MIME : Acme Corporation.png. content_disposition encode l'espace du nom (filename*=UTF-8''Acme%20Corporation.csv). Venant de la 19 : cette fonction s'importait de odoo.http ; en 20, from odoo.http import content_disposition lève ImportError, elle vit dans odoo.http.stream.

À retenir

  • Pièce jointe : raw en octets bruts ; datas n'existe plus ; en XML, type="bytes".
  • Champ Binary : écrire BinaryBytes(octets), lire .content, .size, .to_base64().
  • Plus de b64decode sur un champ Binary : il ne plante pas, il corrompt.
  • Servir : /web/content/…, ou ir.binary._get_stream_from(…).get_response() ; content_disposition vient de odoo.http.stream.
