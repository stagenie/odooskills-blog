Module Odoo 19 sous Odoo 20 : les messages d'erreur et leur correctif

Un module écrit pour la 19, posé tel quel sur une base Odoo 20 : ce que le journal affiche, dans l'ordre où ça arrive, ce que chaque message veut dire et la ligne à changer. Et, plus traîtres, les changements qui ne lèvent aucune erreur : le module s'installe, la page reste vide.

~14 minutes de lecture · niveau intermédiaire · parcours Framework & ORM

Ce que tu vas apprendre

Lire le message

Le texte exact de chaque erreur d'Odoo 20 face à du code 19, à retrouver d'un coup de recherche dans cette page.

Corriger

La forme Odoo 20 de chaque appel, exécutée, et l'article qui détaille le sujet.

Voir ce qui se tait

QWeb vide, pièce jointe vide, droits trop larges, serveur injoignable : les pannes sans erreur, montrées par leur effet.

Prérequis

  • Une base Odoo 20 de test avec ses données de démonstration (ici Ventes, Inventaire et le Blog) et la console odoo-bin shell, présentée dans l'article sur la console.
  • Tous les messages de cette page ont été reproduits sur une telle base, avec un petit module mon_module écrit comme en 19 (un modèle, un fichier de droits, une règle, trois gabarits QWeb), puis corrigé étape par étape.
  • Le périmètre est le code serveur : Python, XML, données. Le JavaScript (OWL 3, icônes) est traité dans ce qui change techniquement en Odoo 20.

2. À l'installation : une erreur à la fois

Odoo charge un module dans un ordre fixe : le manifeste, puis le code Python, puis les fichiers de données dans l'ordre de la clé data. Il s'arrête à la première erreur. Le module 19 de départ, posé dans l'addons_path et installé avec -i mon_module --stop-after-init, donne donc ses erreurs une par une, à chaque correction :

La version du manifeste : le piège du code de sortie 0

La première tentative ne « plante » pas : code de sortie 0, deux lignes WARNING noyées dans le journal, et le module n'est pas installé. Odoo 20 refuse tout module dont la version ne commence pas par 20.0 et le marque installable=False. Si le module est déjà connu de la base (liste des applications mise à jour auparavant), le journal ajoute :

2026-10-07 08:32:08,372 1035742 WARNING ma_base odoo.modules.module_graph: module mon_module: not installable, skipped 2026-10-07 08:32:08,859 1035742 ERROR ma_base odoo.modules.loading: Some modules have inconsistent states, some dependencies may be missing: ['mon_module']

Toujours avec un code de sortie 0. Un script de déploiement qui ne teste que ce code croit l'installation réussie. Ce garde-fou existait déjà en 19 (même message) ; ce qu'il faut retenir, c'est de ne passer la version en 20.0.1.0.0 qu'après le portage : c'est elle qui déverrouille l'installation, et toutes les erreurs qui suivent.

odoo.osv, puis les droits

Le code Python est importé avant toute donnée : from odoo.osv import expression casse l'installation avant même le premier fichier XML. Domain, dans odoo.fields, remplace tout l'ancien module expression.

Viennent ensuite les droits. ir.model.access et ir.rule n'existent plus en Odoo 20 : un seul modèle, ir.access, porte à la fois le droit sur le modèle et le domaine de la règle. Le KeyError nomme le premier des deux que le manifeste charge. Le fichier s'écrit ainsi :

id,name,model_id,group_id/id,operation,domain
mon_modele_rule_own,Mon modèle : mes fiches,mon.modele,base.group_user,crud,"[('create_uid', '=', user.id)]"

model_id prend le nom du modèle tel quel, operation une combinaison des lettres c, r, u, d, et domain reste vide pour un droit sans condition. Avec ce fichier à la place des deux anciens, le module s'installe.

L'outil de conversion d'Odoo : upgrade_code

La ligne ci-dessus n'a pas été écrite à la main : elle sort de la sous-commande upgrade_code, qui réécrit les sources sur place (fais un commit avant). Lancée script par script sur une copie du module 19 :

./odoo-bin upgrade_code --addons-path=… --glob 'mon_module/**/*' --script 19.1-00-t-call
./odoo-bin upgrade_code --addons-path=… --glob 'mon_module/**/*' --script 19.4-00-ir-access
./odoo-bin upgrade_code --addons-path=… --glob 'mon_module/**/*' --script owl3-migration
updated: …/mon_module/views/mon_module_templates.xml updated: …/mon_module/__manifest__.py updated: …/mon_module/security/ir.access.csv deleted: …/mon_module/security/ir.model.access.csv deleted: …/mon_module/security/mon_module_security.xml
  • --glob n'est pas une option de confort. Sans elle, l'outil parcourt aussi les modules d'Odoo lui-même : un essai à blanc (--dry-run) du script 19.1-00-t-call listait onze fichiers, dont dix du cœur. De même, --from 19.1 (tous les scripts d'un coup) a planté ici sur un script de comptabilité (KeyError: 'ar_base') : passer les scripts un par un.
  • Le script des droits a fusionné le droit et la règle en une seule ligne, sous l'identifiant de la règle, et réécrit la clé data du manifeste.
  • Le script t-call a transformé le t-set du corps en attribut (ville.f="Bruxelles", une chaîne de format).
  • Il ne touche pas à la version du manifeste, à from odoo.osv, ni au t-esc des gabarits serveur : owl3-migration ne réécrit t-esc que dans les fichiers sous static/ (ici, aucun fichier modifié). Ni à datas=, pytz, get_param : tout ce qui suit reste à faire à la main.

Pour faire l'inventaire d'un module avant de commencer, une recherche suffit. Sur le module 19 de départ :

mon_module/security/mon_module_security.xml:3: <record id="mon_modele_rule_own" model="ir.rule"> mon_module/models/mon_modele.py:2:from odoo.osv import expression mon_module/views/mon_module_templates.xml:4: <p class="carte">Client : <t t-esc="client"/></p> mon_module/views/mon_module_templates.xml:12: <t t-call="mon_module.adresse"> mon_module/__manifest__.py:7: 'security/ir.model.access.csv',

Cinq lignes, dont deux (t-esc et le t-call ouvrant) ne lèveront jamais d'erreur : ce sont celles de la section 5.

3. Les droits convertis à la main : deux erreurs muettes

Le KeyError disparaît dès que les anciens fichiers sont remplacés par un ir.access.csv, qu'il soit juste ou non. Et deux conversions « évidentes » donnent un module qui s'installe sans un mot, avec des droits différents de la 19. Pour le voir, deux fiches (une créée par l'administrateur, une par l'utilisateur de démonstration), puis ce que voit l'utilisateur de démonstration selon les lignes présentes :

M = env['mon.modele']
admin, demo = env.ref('base.user_admin'), env.ref('base.user_demo')
M.with_user(admin).create({'name': "fiche de l'admin"})
M.with_user(demo).create({'name': 'fiche de demo'})

def voir(titre):
    env.invalidate_all()
    env.transaction.invalidate_ormcache()
    print(f">>> {titre}")
    print("   domaine :", M.with_user(demo)._access_domain('read'))
    print("   demo voit :", M.with_user(demo).search([]).mapped('name'))

voir("1 ligne (convertie) : base.group_user, crud, [('create_uid', '=', user.id)]")

A = env['ir.access']
naive = A.create({'name': 'mon.modele user (ex-ACL)', 'model_id': env['ir.model']._get_id('mon.modele'),
                  'group_id': env.ref('base.group_user').id, 'operation': 'crud'})
voir("+ ligne recopiée de l'ancien CSV : base.group_user, crud, sans domaine")
naive.unlink()

vide = A.create({'name': 'mon.modele lecture (ex-ACL sans groupe)', 'model_id': env['ir.model']._get_id('mon.modele'),
                 'group_id': False, 'operation': 'r', 'domain': "[('name', 'ilike', 'admin')]"})
voir("+ ligne sans groupe : r, [('name', 'ilike', 'admin')]")
env.cr.rollback()
>>> 1 ligne (convertie) : base.group_user, crud, [('create_uid', '=', user.id)] domaine : [('create_uid', '=', 5)] demo voit : ['fiche de demo'] >>> + ligne recopiée de l'ancien CSV : base.group_user, crud, sans domaine domaine : [(1, '=', 1)] demo voit : ["fiche de l'admin", 'fiche de demo'] >>> + ligne sans groupe : r, [('name', 'ilike', 'admin')] domaine : ['&', ('create_uid', '=', 5), ('name', 'ilike', 'admin')] demo voit : []
  • Une ligne avec groupe est une permission, et les permissions s'additionnent (OU). En 19, le droit sur le modèle et la règle se cumulaient : le droit ouvrait le modèle, la règle filtrait. En 20, recopier l'ancien droit à côté de la règle convertie fait deux permissions, dont une sans domaine : l'utilisateur voit tout. La conversion juste tient en une ligne, celle que produit upgrade_code.
  • Une ligne sans groupe est une restriction, appliquée à tous (ET). En 19, un droit sans groupe ouvrait le modèle à tout le monde. En 20, le même champ vide filtre tout le monde, y compris ceux qui avaient déjà une permission. Pour « tout le monde », écrire base.group_everyone.

Dans les deux cas, aucun message : seul un test avec un utilisateur non administrateur (with_user) le montre. Le modèle complet est expliqué dans l'article sur les droits d'accès en Odoo 20.

Deux de ces corrections demandent plus qu'un renommage. pytz a quitté les dépendances d'Odoo 20 : il peut encore être installé sur ta machine (il l'était ici), mais plus rien ne le garantit sur un serveur neuf, et les fuseaux qu'Odoo te donne sont des ZoneInfo. _force_unlink : l'erreur est la bonne

Un module 19 qui supprimait une commande confirmée avec with_context(_force_unlink=True).unlink() reçoit désormais le refus normal :

UserError: Vous ne pouvez pas supprimer un devis envoyé ou une commande client confirmée. Vous devez l'annuler au préalable.

Le drapeau ne saute plus les gardes de suppression. Fais ce que dit le message (annuler, puis supprimer) ; le détail est dans create, write et Command.

5. Les pannes silencieuses : aucune erreur, résultat faux

Une fois ses droits convertis, le module s'installe sans un avertissement, alors que ses gabarits n'ont pas été touchés. Le problème n'apparaît qu'au rendu. Le gabarit fiche appelle carte (qui affiche le client avec t-esc) et adresse (qui affiche une ville passée par un t-set dans le corps du t-call, comme en 19) :

<template id="carte">
    <p class="carte">Client : <t t-esc="client"/></p>
</template>
<template id="adresse">
    <p class="adresse">Ville : <t t-out="ville"/></p>
</template>
<template id="fiche">
    <div class="fiche">
        <t t-call="mon_module.carte"/>
        <t t-call="mon_module.adresse">
            <t t-set="ville" t-value="'Bruxelles'"/>
        </t>
    </div>
</template>
  • t-esc (et t-raw) : Odoo 20 ne les connaît plus. Le journal écrit un WARNING Unknown directives or unused attributes: {'t-esc'}, au rendu seulement, et la valeur n'est pas affichée. Écrire t-out.
  • t-set dans le corps d'un t-call : la variable n'arrive plus au gabarit appelé, et cette fois aucune ligne dans le journal. La passer en attribut du t-call (une expression : ville="'Bruxelles'", ou une chaîne de format : ville.f="Bruxelles").
  • datas= : la pièce jointe est créée, vide (0 octet), avec un UserWarning facile à rater. Écrire raw= avec les octets bruts, sans base64.
  • base64.b64decode(rec.image_1920) : le champ renvoie maintenant les octets du fichier, pas du base64. Le décodage ne lève rien (les caractères invalides sont ignorés) et rend des octets sans sens. Lire rec.image_1920.content.

Après correction (t-out et attribut), et mise à jour du module, le même rendu :

<t t-call="mon_module.carte"/>
<t t-call="mon_module.adresse" ville="'Bruxelles'"/>
<div class="fiche"> <p class="carte">Client : Acme Corporation</p> <p class="adresse">Ville : Bruxelles</p> </div>

Trois autres silences

force_company : la clé de contexte est ignorée, sans même un avertissement (la 19 en écrivait encore un).

other = env['res.company'].search([('name', '=', 'My Company (Chicago)')])
P = env['res.partner']
print(env.company.name)
print(P.with_context(force_company=other.id).env.company.name)
print(P.with_company(other).env.company.name)
My Company (San Francisco) My Company (San Francisco) My Company (Chicago)

Seul with_company change de société ; voir l'article sur l'environnement.

copy_translations : la méthode n'existe plus (hasattr(env['product.template'], 'copy_translations') vaut False). Une surcharge dans ton modèle reste une méthode ordinaire que personne n'appelle : la logique va dans copy_data.

Le serveur injoignable : lancé sans http_interface, Odoo 20 n'écoute que sur la machine elle-même. Le journal le dit, mais il faut le lire :

2026-10-07 08:32:48,207 1038323 INFO ? odoo.service.server: HTTP service running on 127.0.0.1:8069

Depuis le réseau, curl http://<ip-du-serveur>:8069/web/login échoue (code 000, connexion refusée). Sur un serveur derrière Nginx, c'est le bon réglage ; pour une instance jointe directement par son IP, écrire http_interface = 0.0.0.0 dans le fichier de configuration (voir l'installation sur un serveur).

Venant de la 19

Chacun de ces silences était un comportement accepté en 19 : t-esc y était compilé comme t-out ; les t-set du corps d'un t-call étaient recopiés dans les valeurs du gabarit appelé ; ir.attachment avait un champ datas en base64 et les champs Binary rendaient du base64 ; force_company déclenchait un DeprecationWarning ; copy appelait copy_translations ; et --http-interface valait 0.0.0.0. Rien de tout cela ne lève d'erreur en 20 : c'est pour ça qu'un module « qui s'installe » n'est pas un module porté.

6. Les avertissements : ça marche encore, plus pour longtemps

Certains appels 19 fonctionnent toujours mais écrivent un WARNING dans le journal, au niveau par défaut :

from odoo.tools import ormcache
P = env['res.partner']
print(P.browse(10).union(P.browse(11)))
2026-10-07 08:40:09,121 1059653 WARNING ma_base py.warnings: <string>:1: DeprecationWarning: Since 20.0 import ormcache from odoo.api 2026-10-07 08:40:09,121 1059653 WARNING ma_base py.warnings: …/odoo/orm/models.py:6094: UserWarning: Since 20.0, use union() on an empty recordset res.partner(10, 11)
  • from odoo.api import ormcache à la place de odoo.tools.
  • env['res.partner'].union([a, b]) : un seul itérable, sur un recordset vide (les opérations d'ensemble). Python n'affiche chaque avertissement qu'une fois par processus : une boucle qui l'appelle mille fois n'en laisse qu'un.
  • Un client externe en XML-RPC laisse à chaque appel :
    2026-10-07 08:32:57,428 1038323 WARNING ma_base odoo.addons.rpc.controllers.xmlrpc: The /xmlrpc, /xmlrpc/2 and /jsonrpc endpoints are deprecated in Odoo 19 and scheduled for removal in Odoo 22. Please report the problem to the client making the request.
    Le message existait déjà en 19 : rien ne casse en 20, mais c'est le moment de passer à l'API JSON-2.

7. Un ordre de portage qui ne laisse rien passer

  1. Copier le module sur une branche dédiée, faire l'inventaire (la recherche de la section 2).
  2. upgrade_code, script par script, avec --glob ; relire le diff, surtout le fichier de droits.
  3. Corriger à la main ce que l'outil ne fait pas : imports (odoo.osv, ormcache), t-esc, datas, Binary, pytz, get_param, read_group, domaines.
  4. Passer la version du manifeste en 20.0.1.0.0 et installer sur une base de test : lire le journal en entier (WARNING, ERROR, Unknown directives), pas seulement le code de sortie.
  5. Ouvrir chaque écran et chaque rapport du module, et tester les droits avec un utilisateur non administrateur.
  6. Lancer les tests du module (tests automatisés en Odoo 20).

Récapitulatif

  • Une version de manifeste 19.0 rend le module non installable avec un code de sortie 0 : lire le journal.
  • À l'installation, les erreurs arrivent une par une : odoo.osv, ir.model.access, ir.rule.
  • odoo-bin upgrade_code convertit les droits et les t-call, à condition de le limiter au module avec --glob ; le reste se fait à la main.
  • À l'exécution : clear_cache, get_param, check_access_rights, localize, base64 dans un Binary, read_group, <>, post_date lèvent une erreur au premier appel.
