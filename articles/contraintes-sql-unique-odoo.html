Contraintes SQL en Odoo 20 : models.Constraint, unique et check

Une référence qui ne doit exister qu'une fois, un prix qui ne doit jamais passer sous zéro : en Odoo 20, ces règles se déclarent comme attributs de classe et PostgreSQL les fait respecter. Voici la syntaxe, le message affiché, et le piège des doublons déjà présents en base.

~5 minutes de lecture · niveau intermédiaire · série Astuces dev Odoo 20

Édition : Community. Vérifié sur Odoo 20.0 Community, octobre 2026, base de démonstration (Ventes, Inventaire) et un petit module d'exemple qui hérite de res.partner et de product.template.

La réponse en bref

  1. Dans la classe du modèle : _ref_uniq = models.Constraint('UNIQUE(ref)', "message") ou models.Constraint('CHECK(list_price >= 0)', "message").
  2. Le nom commence par _ ; en base, la contrainte s'appelle <table>_<nom>, ici res_partner_ref_uniq.
  3. _sql_constraints = [...] est ignoré : un simple WARNING, aucune contrainte créée.
  4. Unicité sans la casse, ou limitée aux fiches actives : models.UniqueIndex("(lower(ref)) WHERE active IS TRUE", "message").
  5. Avant d'installer, cherche les doublons : sinon le module s'installe sans la contrainte.

1. models.Constraint : UNIQUE et CHECK

Une contrainte SQL est un objet models.Constraint posé comme attribut de la classe. Le premier argument est la définition SQL, celle qui suit ADD CONSTRAINT ; le second, le message montré à l'utilisateur. Le module d'exemple en déclare deux, sur des modèles de la démo :

# models/res_partner.py
from odoo import models


class ResPartner(models.Model):
    _inherit = 'res.partner'

    _ref_uniq = models.Constraint(
        'UNIQUE(ref)',
        "Cette référence interne est déjà utilisée par un autre contact.",
    )


# models/product_template.py
class ProductTemplate(models.Model):
    _inherit = 'product.template'

    _list_price_positive = models.Constraint(
        'CHECK(list_price >= 0)',
        "Le prix de vente ne peut pas être négatif.",
    )

Trois règles de forme :

  • le nom de l'attribut doit commencer par _ (Odoo le vérifie au chargement) ;
  • la contrainte prend en base le nom <table>_<nom sans le _> : res_partner_ref_uniq, product_template_list_price_positive ;
  • si tu changes la définition, le -u suivant supprime la contrainte et la recrée.

Le cœur s'en sert lui-même : res.partner porte nativement _check_name, un CHECK qui exige un nom sur tout contact de type « contact ». L'ancienne liste _sql_constraints = [(nom, définition, message)] ne fait plus rien : au -u, le journal affiche Model attribute '_sql_constraints' is no longer supported, please define models.Constraint on the model., le module se charge, et aucune contrainte n'apparaît dans PostgreSQL. C'est déjà le cas en 19 ; un module plus ancien porté tel quel perd donc ses contraintes sans erreur.

Ce script, passé à odoo-bin shell, provoque les deux violations dans des points de sauvegarde et affiche le message que la contrainte associe à l'erreur :

# essai.py
import psycopg2
Partner = env['res.partner']
print(Partner.search_count([('ref', '=', False)]), "contacts sans référence : NULL n'entre pas en conflit")
try:
    with env.cr.savepoint():
        Partner.create({'name': 'Doublon', 'ref': 'CLI-001'})
except psycopg2.Error as e:
    print(type(e).__name__, '|', e.diag.constraint_name)
    print(Partner._sql_error_to_message(e))
try:
    with env.cr.savepoint():
        env['product.template'].search([], limit=1).list_price = -5
        env.flush_all()
except psycopg2.Error as e:
    print(type(e).__name__, '|', e.diag.constraint_name)
    print(env['product.template']._sql_error_to_message(e))

Deux leçons dans cette sortie. D'abord, UNIQUE laisse passer autant de NULL qu'on veut : un champ vide n'est jamais un doublon. Ensuite, en Python, la violation remonte brute (psycopg2.errors.UniqueViolation) : c'est la couche HTTP qui la convertit en message pour l'écran. Le flush_all() envoie l'affectation à PostgreSQL à l'intérieur du point de sauvegarde, là où l'erreur est attrapée.

2. Quand UNIQUE ne suffit pas : models.UniqueIndex

UNIQUE(ref) accepte CLI-001 et cli-001 côte à côte, et compte les contacts archivés. Pour une unicité sur une expression ou sur une partie des lignes, il faut un index unique, que models.UniqueIndex déclare avec le même genre de message :

class ResPartner(models.Model):
    _inherit = 'res.partner'

    _ref_ci_uniq = models.UniqueIndex(
        "(lower(ref)) WHERE active IS TRUE",
        "Cette référence interne est déjà utilisée par un autre contact.",
    )

La définition est ce qui suit CREATE UNIQUE INDEX … ON res_partner. Après -u, PostgreSQL contient :

CREATE UNIQUE INDEX res_partner_ref_ci_uniq ON public.res_partner USING btree (lower((ref)::text)) WHERE (active IS TRUE)

L'ancienne contrainte res_partner_ref_uniq a disparu d'elle-même : le journal du -u affiche Deleting … (mon_contraintes.constraint_res_partner_ref_uniq). Donne une nouvelle clé à l'index plutôt que de réutiliser _ref_uniq : c'est ce changement de nom qui fait supprimer l'ancienne. Rejoué dans le shell, cli-001 est refusé (UniqueViolation | res_partner_ref_ci_uniq), tandis qu'un contact archivé avec CLI-001 est accepté. À l'écran, sur la fiche Azure Interior, onglet Ventes & Achats, champ Référence :

Le préfixe vient du cœur (odoo/http/retrying.py) ; seul le texte qui suit est le tien, écris-le donc comme une phrase complète, dans la langue de tes utilisateurs. Deux autres formes utiles se trouvent dans le code d'Odoo 20 lui-même :

BesoinExemple du cœur
une seule variante active par combinaisonproduct.product : UniqueIndex("(product_tmpl_id, combination_indices) WHERE active IS TRUE")
traiter deux NULL comme égauxres.currency.rate : UniqueIndex('(currency_id, company_id, name) NULLS NOT DISTINCT', "…")

NULLS NOT DISTINCT répond au cas d'un taux « sans société » : sans cette clause, deux taux du même jour avec company_id vide ne seraient pas des doublons. La clause demande PostgreSQL 15 ou plus ; Odoo 20 exige de toute façon PostgreSQL 16.

3. Les doublons déjà en base

Une contrainte ajoutée à une table déjà remplie doit être vraie pour toutes les lignes existantes. Sur la base d'essai, deux sociétés de la démo, Acme Corporation et Azure Interior, portaient la même référence CLI-001 avant l'installation du module :

Installé, mais sans la contrainte

Odoo n'interrompt pas l'installation : le module passe à l'état installé, la contrainte CHECK est créée, l'UNIQUE ne l'est pas. Le modèle ir.model.constraint liste pourtant les deux : ne t'y fie pas, interroge pg_constraint. Dans un script de déploiement qui ne regarde que le code retour, rien ne signale le trou.

Trouve les valeurs en cause, corrige-les, puis relance un -u :

# doublons.py
env.cr.execute("""
    SELECT ref, array_agg(id ORDER BY id) FROM res_partner
    WHERE ref IS NOT NULL GROUP BY ref HAVING count(*) > 1
""")
print(env.cr.fetchall())
[('CLI-001', [10, 16])]

Une fois la référence d'Azure Interior (id 16) passée à CLI-002, -u mon_contraintes crée la contrainte. Pour le vérifier, compare le catalogue de PostgreSQL et ce qu'Odoo a enregistré :

# voir_contraintes.py
for table in ('res_partner', 'product_template'):
    env.cr.execute("""SELECT conname, pg_get_constraintdef(oid) FROM pg_constraint
                      WHERE conrelid = %s::regclass AND contype IN ('u', 'c') ORDER BY conname""", [table])
    for row in env.cr.fetchall():
        print(*row)
for c in env['ir.model.constraint'].search([('module.name', '=', 'mon_contraintes')]):
    print(c.name, c.type, c.model.model)
res_partner_check_name CHECK (((((type)::text = 'contact'::text) AND (name IS NOT NULL)) OR ((type)::text <> 'contact'::text))) res_partner_ref_uniq UNIQUE (ref) product_template_list_price_positive CHECK ((list_price >= (0)::numeric)) res_partner_ref_uniq u res.partner product_template_list_price_positive u product.template

Les trois premières lignes viennent de PostgreSQL, les deux dernières d'Odoo. Avant la correction, la ligne res_partner_ref_uniq UNIQUE (ref) manquait, alors que les deux lignes d'ir.model.constraint étaient déjà là.

À retenir

  • _nom = models.Constraint('UNIQUE(…)' ou 'CHECK(…)', "message") ; _sql_constraints n'est plus lu.
  • models.UniqueIndex pour une expression (lower(ref)), une condition (WHERE active IS TRUE) ou NULLS NOT DISTINCT.
  • En Python, l'erreur est brute (UniqueViolation) ; à l'écran, ton message suit « The operation cannot be completed: ».
  • Doublons existants : installation réussie, contrainte absente. Vérifie pg_constraint.
