L'API de la Bibliothèque en Odoo 20 : ses emprunts en JSON-2

Une borne de retour, un tableau de bord externe, un script de relance : tous veulent lire les emprunts de la Bibliothèque et en clore quelques-uns. En Odoo 20, il n'y a pas de contrôleur à écrire. Chaque méthode publique d'un modèle est déjà une adresse /json/2/<modèle>/<méthode>. Le travail consiste à choisir ce qu'on expose, sous quelle identité, et ce que le client reçoit quand il se trompe.

~13 minutes de lecture · niveau intermédiaire · parcours Intégrations

Ce que tu vas apprendre

Ouvrir

Un utilisateur technique, sa clé API à portée rpc, et ce que JSON-2 sert sans une ligne de code.

Exposer

Deux méthodes d'API au format stable, @api.model, @api.readonly, et les méthodes qu'on cache.

Refuser proprement

Les codes 401, 403, 404 et 422 réellement renvoyés, la trace qu'on retire de la réponse, et les tests HTTP.

Prérequis

  • Le module biblio des articles précédents, jusqu'aux rayons hiérarchiques ; on n'ajoute ici qu'un fichier de tests et, sur l'emprunt, deux méthodes d'API et un utilitaire privé.
  • Les groupes « Accueil » et « Bibliothécaire » et le fichier ir.access.csv de l'article sur les droits d'accès : l'API les applique tels quels.
  • Le principe de JSON-2 (une route par méthode, une clé par en-tête) est détaillé, côté API standard, dans XML-RPC est déprécié : passer à l'API JSON-2 d'Odoo 20. Cet article-ci se place du côté du module.

1. Ce que fait Odoo d'un appel JSON-2

Le module rpc, installé d'office, déclare une seule route : POST /json/2/<modèle>/<méthode>, authentifiée par une clé API (auth='bearer', bearer_scope='rpc'). Le corps JSON porte les arguments nommés de la méthode, plus deux clés réservées : ids (les enregistrements visés) et context. Avant d'exécuter quoi que ce soit, Odoo fait passer l'appel par six contrôles, chacun avec son code de refus :

Deux conséquences pour un module. D'abord, l'API existe déjà : search_read, create, write, mais aussi action_return et toute autre méthode sans tiret bas initial. Ensuite, c'est l'utilisateur de la clé qui agit : ses groupes et ses lignes ir.access décident, exactement comme dans le client web.

2. Un utilisateur technique et sa clé

Une borne de retour n'a rien à faire avec les droits de l'administrateur. On lui donne un utilisateur à elle, dans le groupe « Accueil » : il lit le catalogue et les adhérents, crée et modifie des emprunts, ne supprime rien. Dans la console odoo-bin shell :

from datetime import datetime, timedelta

grp = env.ref('biblio.group_library_desk')
user = env['res.users'].create({
    'name': "API Bibliothèque",
    'login': 'api_biblio',
    'group_ids': [(6, 0, [grp.id])],
})
Keys = env['res.users.apikeys'].with_user(user)
try:
    Keys._generate('rpc', "Borne de retour", datetime.now() + timedelta(days=365))
except Exception as e:
    print(type(e).__name__, '|', e)
key = Keys._generate('rpc', "Borne de retour", datetime.now() + timedelta(days=90))
env.cr.commit()
print(len(key))
ValidationError | Vous ne pouvez pas dépasser la durée de 90.0 jours. 40
  • _generate(scope, nom, expiration) crée la clé pour l'utilisateur de l'environnement, d'où le with_user(user). Elle renvoie la clé en clair, une seule fois : Odoo n'en garde qu'une empreinte. On la range côté client, par exemple dans une variable d'environnement ODOO_KEY.
  • La portée doit être 'rpc' : c'est celle qu'exige la route JSON-2.
  • Un utilisateur ordinaire est plafonné : la durée maximale vient de ses groupes (champ api_key_duration, 90 jours pour « Rôle / Utilisateur »). Un an est refusé, 90 jours passent. Seul un administrateur peut créer une clé sans échéance.

Sans console, la même clé se crée dans le client web : se connecter avec l'utilisateur technique, ouvrir ses préférences, onglet « Sécurité », rubrique « Clés API », bouton « Create API Key » (libellé non traduit en 20.0). L'assistant d'Odoo 20 propose 1 jour, 1 mois ou 1 an selon le plafond (ici, 1 jour ou 1 mois), et « Jamais » à un administrateur.

Avec cette clé, l'API standard répond déjà. Les emprunts en retard, par le champ cherchable is_late posé à l'étape des retards :

curl -s http://localhost:8069/json/2/library.loan/search_read \
    -H "Authorization: bearer $ODOO_KEY" -H "X-Odoo-Database: ma_base" \
    -H "Content-Type: application/json" \
    -d '{"domain": [["is_late", "=", true]], "fields": ["reference", "member_id", "copy_id", "date_due"], "context": {"lang": "fr_FR"}}'
[{"id": 2, "reference": "EMP/2026/0002", "member_id": [2, "Équipe Support (C-0002)"], "copy_id": [3, "BIB-0011 (OWL 3 : le front-end d'Odoo)"], "date_due": "2026-10-12"}, {"id": 1, "reference": "EMP/2026/0001", "member_id": [1, "Service Formation (C-0001)"], "copy_id": [1, "BIB-0009 (Python pour Odoo)"], "date_due": "2026-10-02"}]

Ça marche, mais le client reçoit la forme interne d'Odoo : des Many2one en paires [id, nom affiché], des noms de champs qui changeront le jour où le modèle bouge, et un nom affiché composé (« BIB-0011 (OWL 3 : …) ») à redécouper. L'en-tête X-Odoo-Database désigne la base quand le serveur en sert plusieurs.

3. Deux méthodes d'API au format stable

On donne au client un contrat à lui : quelques méthodes publiques préfixées api_, qui renvoient des dictionnaires plats, et une méthode privée qui fabrique ces dictionnaires. Dans models/library_loan.py :

from odoo.exceptions import UserError, ValidationError
from odoo.fields import Domain
from odoo.http.dispatcher import conceal_debug_traceback


class LibraryLoan(models.Model):
    _name = 'library.loan'
    # … champs et méthodes des étapes précédentes …

    # API JSON-2 : chaque méthode publique est appelable par /json/2/library.loan/<méthode>
    @api.model
    @api.readonly
    @conceal_debug_traceback(UserError)
    def api_loans(self, state='ongoing', late=None, limit=80):
        """Emprunts au format de l'API : une liste de dictionnaires plats."""
        if state not in ('ongoing', 'returned'):
            raise UserError(self.env._("État inconnu : %(state)s.", state=state))
        domain = Domain('state', '=', state)
        if late is not None:
            domain &= Domain('is_late', '=', bool(late))
        return self.search(domain, limit=limit)._api_values()

    @api.model
    @conceal_debug_traceback(UserError)
    def api_return_copy(self, copy):
        """Retour d'un exemplaire par son code d'inventaire (borne de retour)."""
        loan = self.search([('copy_id.name', '=', copy), ('state', '=', 'ongoing')], limit=1)
        if not loan:
            raise UserError(self.env._("Aucun emprunt en cours pour l'exemplaire %(copy)s.", copy=copy))
        loan.action_return()
        return loan._api_values()[0]

    def _api_values(self):
        return [{
            'id': loan.id,
            'reference': loan.reference,
            'member': loan.member_id.card_number,
            'copy': loan.copy_id.name,
            'book': loan.book_id.title,
            'date_out': loan.date_out,
            'date_due': loan.date_due,
            'date_return': loan.date_return or None,
            'days_late': loan.days_late,
        } for loan in self]
LigneRôle dans l'API
@api.modelLa méthode travaille sur le modèle, pas sur des enregistrements. JSON-2 refuse alors un appel qui envoie des ids : 422 cannot call library.loan.api_loans with ids.
Arguments nommésstate, late, limit deviennent les clés du corps JSON. Odoo confronte le corps à la signature avant d'appeler : une clé inconnue ({"etat": "ongoing"}) donne 422 got an unexpected keyword argument 'etat'.
@api.readonlyLa route JSON-2 lit cet attribut sur la méthode appelée (_web_json_2_rpc_readonly) et sert alors l'appel sur un curseur en lecture seule, dirigé vers la réplique PostgreSQL quand db_replica_host est configuré. Si la méthode écrit quand même, le routeur journalise un avertissement et rejoue l'appel en lecture-écriture (odoo/http/router.py).
_api_valuesLe tiret bas la rend privée : appelable depuis Python, jamais depuis l'API.
date_return or NoneUn champ vide vaut False dans l'ORM, donc false en JSON. Pour un client, une date absente s'écrit null : on convertit.
conceal_debug_tracebackRetire la pile d'appels de la réponse d'erreur (section 5).

Le module passe en 20.0.1.18.0, mise à jour faite. L'appel du client :

Les dates sortent en chaînes sans rien faire : la sérialisation JSON d'Odoo convertit les date Python. Le nombre de jours de retard vient d'un champ calculé non stocké : la méthode le lit comme n'importe quel champ.

Toute méthode publique est une porte

Il n'y a pas de liste blanche : action_return, action_send_reminder, action_print_loan, les méthodes héritées de mail.thread sont appelables par quiconque a une clé et le droit d'accès au modèle. Un appel action_return avec {"ids": [3]} a bien clos l'emprunt 3 (réponse null, code 200). Une méthode utilitaire commence par un tiret bas ; une méthode publique qu'on ne peut pas renommer reçoit @api.private. La relance quotidienne _cron_relancer_retards, elle, était déjà à l'abri.

4. Écrire par l'API : le retour d'un exemplaire

La borne lit le code d'inventaire collé sur le livre et appelle api_return_copy :

curl -s http://localhost:8069/json/2/library.loan/api_return_copy \
    -H "Authorization: bearer $ODOO_KEY" -H "X-Odoo-Database: ma_base" \
    -H "Content-Type: application/json" -d '{"copy": "BIB-0011"}'
{"id": 2, "reference": "EMP/2026/0002", "member": "C-0002", "copy": "BIB-0011", "book": "OWL 3 : le front-end d'Odoo", "date_out": "2026-09-28", "date_due": "2026-10-12", "date_return": "2026-10-19", "days_late": 0}

La méthode réutilise action_return : état « Rendu », date de retour, exemplaire remis en rayon et note au chatter. Tout est fait au nom de l'utilisateur technique, et ça se voit dans l'historique :

La date de retour est celle du jour dans le fuseau de l'utilisateur de la clé (fields.Date.context_today) : l'appel a été passé juste après minuit à Paris, d'où le 19. L'utilisateur technique a ici le fuseau Europe/Paris : on le choisit à sa création (champ tz), comme pour une personne.

Le second passage du même exemplaire est refusé par la méthode, et une clôture en double par action_return l'est par la contrainte écrite à l'étape des boutons :

api_return_copy {"copy": "BIB-0011"} → 422 "Aucun emprunt en cours pour l'exemplaire BIB-0011." action_return {"ids": [3]} → 422 "Cet emprunt est déjà clos."

Une UserError comme une ValidationError donnent 422, avec le message dans la clé message. L'erreur annule la transaction : rien n'est écrit à moitié.

Les messages d'accès sont en français parce que l'appel portait "context": {"lang": "fr_FR"}. Sans contexte, JSON-2 répond en anglais (You are not allowed to delete 'Emprunt' (library.loan) records.) ; les messages du module, écrits en français dans le code, sortent tels quels.

Toutes ces réponses ont la même forme : name, message, arguments, timestamp, context et debug. Le dernier champ pose problème. Avant l'ajout de conceal_debug_traceback, le refus de api_return_copy renvoyait la pile complète, chemins du serveur compris (extrait) :

"debug": "Traceback (most recent call last):\n File \"…/odoo/http/router.py\", line 446, in serve_db\n … File \"…/addons/rpc/controllers/json2.py\", line 86, in web_json_2_rpc\n … File \"…/biblio/models/library_loan.py\", line …, in api_return_copy\n raise UserError(…)\n …"

Avec le décorateur, sur le même appel :

Venant de la 19 : ce qui bouge pour une API de module

La route JSON-2, @api.model, @api.readonly et @api.private existent déjà en 19.0 avec le même rôle. Deux choses changent. conceal_debug_traceback est nouveau : il vit dans odoo/http/dispatcher.py, car le fichier unique odoo/http.py de la 19 est devenu un paquet ; il n'y existe pas, et un module 19 ne peut donc pas l'importer. Et la clé doit porter la portée rpc : une clé sans portée, acceptée par la 19, reçoit 401 en 20.

Le décorateur ne couvre que ce qu'on lui nomme

conceal_debug_traceback(UserError) réduit les UserError et leurs sous-classes (dont ValidationError) levées dans la méthode décorée. Les refus du contrôleur lui-même (403 méthode privée, 404, 422 d'arguments) et les AccessError du unlink gardent leur pile complète. Une API ouverte sur Internet se place derrière un proxy inverse qui ne laisse sortir que message, ou un client qui n'affiche jamais debug.

6. Un client Python sans dépendance

Côté client, la bibliothèque standard suffit : urllib et json. Le script liste les retards, puis tente le retour d'un exemplaire qui n'est pas sorti :

"""Liste les emprunts en retard de la Bibliothèque par l'API JSON-2 d'Odoo 20."""
import json
import os
import urllib.error
import urllib.request

URL = os.environ['ODOO_URL']          # https://odoo.example.com
DB = os.environ['ODOO_DB']
KEY = os.environ['ODOO_KEY']


def call(model, method, **params):
    request = urllib.request.Request(
        f"{URL}/json/2/{model}/{method}",
        data=json.dumps(params).encode(),
        headers={
            'Authorization': f'bearer {KEY}',
            'X-Odoo-Database': DB,
            'Content-Type': 'application/json',
        },
    )
    try:
        with urllib.request.urlopen(request) as response:
            return json.load(response)
    except urllib.error.HTTPError as error:
        detail = json.load(error)
        raise SystemExit(f"{error.code} {detail['name']} : {detail['message']}") from None


for loan in call('library.loan', 'api_loans', late=True):
    print(f"{loan['reference']}  {loan['member']}  {loan['book']:<28} {loan['days_late']:>3} j de retard")

7. Tester l'API avec HttpCase

Un TransactionCase appellerait les méthodes en Python et ne verrait ni la clé, ni les codes HTTP, ni la sérialisation. HttpCase passe par un vrai serveur. La clé se génère dans la transaction du test, que le serveur de test partage. Fichier tests/test_api.py, déclaré dans tests/__init__.py :

from datetime import datetime, timedelta

from odoo.tests import HttpCase, new_test_user


class TestApi(HttpCase):

    @classmethod
    def setUpClass(cls):
        super().setUpClass()
        book = cls.env['library.book'].create({'title': "Python pour Odoo"})
        cls.copy_1, cls.copy_2 = cls.env['library.copy'].create([{'book_id': book.id}, {'book_id': book.id}])
        member = cls.env['library.member'].create({'name': "Service Formation", 'card_number': 'A-0001'})
        cls.late = cls.env['library.loan'].create({
            'member_id': member.id, 'copy_id': cls.copy_1.id,
            'date_out': datetime.now().date() - timedelta(days=30),
        })
        cls.on_time = cls.env['library.loan'].create({'member_id': member.id, 'copy_id': cls.copy_2.id})
        api_user = new_test_user(cls.env, login='test_api', groups='biblio.group_library_desk')
        cls.key = cls.env['res.users.apikeys'].with_user(api_user)._generate(
            'rpc', "Tests", datetime.now() + timedelta(days=1))

    def _call(self, method, **params):
        return self.url_open(
            f'/json/2/library.loan/{method}',
            json=params,
            headers={
                'Authorization': f'bearer {self.key}',
                'X-Odoo-Database': self.env.cr.dbname,
            },
        )

    def test_late_loans(self):
        response = self._call('api_loans', late=True)
        self.assertEqual(response.status_code, 200)
        loans = {loan['reference']: loan for loan in response.json()}
        self.assertNotIn(self.on_time.reference, loans)
        self.assertGreater(loans[self.late.reference]['days_late'], 0)
        self.assertIsNone(loans[self.late.reference]['date_return'])

    def test_return_copy(self):
        response = self._call('api_return_copy', copy=self.copy_1.name)
        self.assertEqual(response.status_code, 200)
        self.assertEqual(self.late.state, 'returned')
        again = self._call('api_return_copy', copy=self.copy_1.name, context={'lang': 'fr_FR'})
        self.assertEqual(again.status_code, 422)
        self.assertIn(self.copy_1.name, again.json()['message'])
        self.assertNotIn('Traceback', again.json()['debug'])

    def test_private_and_forbidden(self):
        self.assertEqual(self._call('_api_values', ids=self.late.ids).status_code, 403)
        self.assertEqual(self._call('unlink', ids=self.late.ids).status_code, 403)

Les trois tests passent, lancés seuls par l'étiquette /biblio:TestApi comme dans l'article sur les tests automatisés. Les assertions ne figent pas un nombre de jours exact : il dépend de la date du jour dans le fuseau de l'utilisateur, et un test qui échoue à minuit ne sert à personne.

À retenir

  • En Odoo 20, un module n'écrit pas de contrôleur pour avoir une API : chaque méthode publique est déjà servie par JSON-2.
  • C'est l'utilisateur de la clé qui agit : un utilisateur technique par client, dans le groupe le plus étroit, et le chatter dit qui a fait quoi.
  • Des méthodes api_… à dictionnaires plats donnent au client un format stable, que le modèle peut évoluer derrière.
  • Les refus sont des codes HTTP précis (401, 403, 404, 422) avec un message ; conceal_debug_traceback retire la pile des erreurs métier.
  • HttpCase teste l'API comme un client : clé, codes, JSON.
