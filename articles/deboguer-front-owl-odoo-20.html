Déboguer le front Odoo 20 : mode debug, console et points d'arrêt

Un devis sans commercial suffit à faire tomber un écran OWL. On le traque avec ce que le navigateur et Odoo 20 offrent vraiment : les trois modes debug, le menu de débogage, une trace qui pointe le bon fichier, la console, des points d'arrêt et un test Hoot qu'on garde à l'écran.

~13 minutes de lecture · niveau intermédiaire · parcours Web et interface

Ce que tu vas apprendre

Choisir le mode

?debug=1, ?debug=assets, ?debug=0 : ce que chacun change réellement, fichier servi, menu, trace d'erreur.

Lire et fouiller

Une trace qui nomme ton fichier et ta ligne, puis le composant fautif retrouvé et modifié depuis la console.

Arrêter le code

debugger;, point d'arrêt conditionnel, pause sur exception, et test.debug dans Hoot.

Prérequis

  • Une base Odoo 20 Community avec l'application Ventes et ses données de démonstration.
  • Chrome ou Chromium, outils de développement ouverts par F12.
  • Savoir lire un composant OWL 3 : useProps, proxy, computed, usePlugin (voir le badge de retard, un widget OWL 3).

Déboguer le client web d'Odoo, c'est d'abord lui demander d'être bavard. Par défaut, il sert un seul gros fichier JavaScript minifié, gardé un an en cache, et ne vérifie pas les props des composants. Le paramètre debug de l'adresse change cela, mais pas de la même façon selon sa valeur.

1. Le module d'exercice : des devis par commercial

Pour déboguer, il faut un bogue. Le module oski_owl_debogage ajoute au menu Ventes une action client « Devis par commercial » : les devis en brouillon ou envoyés, regroupés par commercial, avec leur total HT. Il dépend de sale et tient en quatre fichiers utiles : le manifeste, une action client en XML, le composant et son gabarit (plus un __init__.py vide et un fichier de test, section 8).

import { Component, computed, onWillStart, proxy, usePlugin, useProps } from "@odoo/owl";
import { ORM } from "@web/core/orm_plugin";
import { registry } from "@web/core/registry";
import { standardActionServiceProps } from "@web/webclient/actions/action_plugin";

/** Regroupe des devis lus par searchRead ; user_id vaut [id, nom] ou false. */
export function groupBySalesperson(orders) {
    const groups = new Map();
    for (const order of orders) {
        const name = order.user_id ? order.user_id[1] : "Sans commercial";
        const group = groups.get(name) || { name, count: 0, total: 0 };
        group.count += 1;
        group.total += order.amount_untaxed;
        groups.set(name, group);
    }
    return [...groups.values()].sort((a, b) => b.total - a.total);
}

export class DevisParCommercial extends Component {
    static template = "oski_owl_debogage.DevisParCommercial";

    props = useProps({ ...standardActionServiceProps });
    orm = usePlugin(ORM);

    setup() {
        this.state = proxy({ orders: [] });
        this.groups = computed(() => groupBySalesperson(this.state.orders));
        onWillStart(() => this.load());
    }

    async load() {
        this.state.orders = await this.orm.searchRead(
            "sale.order",
            [["state", "in", ["draft", "sent"]]],
            ["name", "user_id", "amount_untaxed"],
            { order: "name" }
        );
    }
}

registry.category("actions").add("oski_owl_debogage.devis_par_commercial", DevisParCommercial);

Le gabarit affiche un tableau (t-foreach="this.groups()") et un bouton « Actualiser » branché sur this.load. Voici la version correcte. La version fautive, celle qu'on va déboguer, remplace la ligne du nom par une déstructuration qui oublie qu'un devis peut ne pas avoir de commercial :

        const [, name] = order.user_id;   // false si le devis n'a pas de commercial

Sur la base de démonstration, tous les devis ont un commercial : l'écran fonctionne. Retire le commercial du devis S00003, et l'action ne s'affiche plus.

2. Les trois modes, et comment en sortir

Le serveur accepte quatre valeurs pour debug : vide, 1, assets et tests, combinables par une virgule (?debug=assets,tests). Toute autre valeur « vraie » (on, true…) devient 1. Dans la console, odoo.debug donne le mode actif. Relevé sur la même page, connecté en administrateur :

Adresseodoo.debugJavaScript chargéIcône de débogage
/odoo""/web/assets/<hash>/web.assets_web.min.js, 7,4 Mo, en cache un annon
/odoo?debug=1"1"le même fichieroui
/odoo?debug=assets"assets"/web/assets/debug/web.assets_web.js, 11,6 Mo, jamais mis en cacheoui
/odoo?debug=assets,tests"assets,tests"le même, plus web.assets_tests.jsoui

?debug=1 ne touche pas au JavaScript : il ajoute l'icône du menu de débogage, la classe o_debug sur la page et passe OWL en mode « dev ». La console l'annonce par Owl is running in 'dev' mode., et c'est ce mode qui valide les props des composants. ?debug=assets fait tout cela et sert en plus le JavaScript lisible : chaque fichier y est précédé d'un en-tête qui donne son chemin, et la dernière ligne pointe vers une carte des sources.

*  Lines: 47                                                        *
********************************************************************/

…
//# sourceMappingURL=/web/assets/ffe2657/web.assets_web.js.map

Cette carte liste les 1 574 fichiers sources du bundle, dont le tien. C'est grâce à elle que l'onglet Sources des outils de développement montre devis_par_commercial.js sous son vrai nom, et que les traces d'erreur, plus bas, citent la bonne ligne.

Le mode vit dans l'adresse, pas seulement dans la session

Le serveur garde le mode dans la session. Mais le client web le relit dans l'adresse : si l'URL ne contient pas debug, il remet odoo.debug à vide, même si le serveur l'a rendu à 1. Comme le client recopie debug d'une page à l'autre, tu ne le perds pas en naviguant. Tu le perds en tapant une adresse sans lui, ou en suivant un lien qui l'omet.

Point de vigilance : sortir du mode debug

Retirer ?debug=assets de l'adresse ne suffit pas. Le client se croit en mode normal : pas d'icône, odoo.debug vide. Le serveur, lui, continue de servir le JavaScript non minifié, sans cache, et la liste des menus chargée passe de 105 à 216 entrées, menus techniques compris. Sors par ?debug=0 ou par l'entrée « Quitter le mode débogage » du menu.

3. Le menu de débogage

En mode debug, une icône d'insecte apparaît dans la barre du haut. Son contenu dépend de l'écran. Sur un devis ouvert, il commence par l'enregistrement (métadonnées, données, valeurs par défaut), puis le modèle sale.order (vue, champs, filtres, arc calculé) et ses droits d'accès. Sur l'action client du module, il ne reste que les outils généraux.

  • Régénérer les actifs reconstruit les bundles et recharge la page : c'est le moyen de faire prendre en compte un fichier JavaScript modifié sans redémarrer le serveur (section 7).
  • Exécuter les tests unitaires ouvre le lanceur Hoot (section 8).
  • Activer le mode test recharge la page en ?debug=assets,tests.

« Disable RPC Cache » mérite d'être connu : le client garde en cache certaines réponses du serveur, et cette entrée recharge la page sans ce cache quand une donnée semble ne pas se mettre à jour.

4. Lire une erreur : « Oups ! » et ce qui ne s'affiche pas

Avec la version fautive et le devis S00003 sans commercial, l'action ne s'affiche pas. Une fenêtre « Oups ! » s'ouvre, dans les trois modes : une erreur levée pendant le rendu d'un composant est toujours remontée à l'utilisateur. Ce qui change, c'est la trace, sous « Voir les détails techniques ». Sans debug, elle pointe le fichier minifié :

La minification d'Odoo garde les noms de fonctions : groupBySalesperson et DevisParCommercial sont lisibles. Mais la ligne 26 406 d'un fichier de 7 Mo ne te dit pas où corriger, et ?debug=1 n'y change rien. En ?debug=assets, Odoo relit la carte des sources et ajoute à chaque ligne venue d'un fichier JavaScript le fichier et la ligne d'origine :

La pile se lit de haut en bas : la ligne 10 de ton fichier a levé l'erreur ; elle était appelée par la ligne 27, le computed du setup() ; lui-même lu par le gabarit pendant le rendu. Le bouton en haut à droite du cadre copie la trace complète, à joindre telle quelle à une demande d'aide.

Les erreurs que tu ne verras pas à l'écran

La fenêtre « Oups ! » n'est pas une garantie. D'autres fautes ne produisent rien à l'écran, ou seulement en debug. La console, elle, parle souvent dans tous les modes :

FauteSans debugEn debug
Erreur levée pendant le rendu (ici, user_id à false) « Oups ! », trace minifiée« Oups ! » ; trace annotée en assets
Import d'un fichier qui n'existe plus en 20 (par exemple @web/webclient/actions/action_service) Ton fichier n'est pas chargé, sans rien à l'écran. Deux console.error : « needed by other modules but have not been defined » et « unmet dependencies ». À l'ouverture de l'action, « Oups ! » Cannot find key … in the "actions" registry Pareil, plus un bandeau rouge en bas de page : « An error occurred while loading javascript modules »
Prop requise oubliée par le parentAucune validation : l'erreur, s'il y en a une, apparaît plus loin « Oups ! » Invalid component props
t-out="total" au lieu de t-out="this.total"Rien du tout : le gabarit rend vide, sans erreur ni message

D'où la règle de travail : ?debug=assets dans l'adresse et la console ouverte en permanence, filtrée sur les erreurs.

5. La console : retrouver le composant et le faire parler

La trace dit où l'erreur est levée, pas avec quelles données. Pour voir l'état d'un composant, Odoo laisse deux portes ouvertes dans la console, dans tous les modes, debug ou non :

  • odoo.__WOWL_DEBUG__.root : le composant racine du client web, WebClient, posé par mountComponent au démarrage ;
  • window.__OWL_DEVTOOLS__ : un objet exposé par OWL lui-même (apps, Fiber, RootFiber, toRaw, proxy). Son nom dit sa destination : une extension d'outils de développement pour OWL. Elle n'est pas traitée ici ; tout ce qui suit se fait depuis la console, sans rien installer.

Chaque composant OWL 3 porte son nœud interne dans __owl__, et ce nœud ses enfants dans children. Une fonction de quelques lignes, collée dans la console, parcourt l'arbre et rend le premier composant dont la classe porte le nom cherché :

function findComponent(name, node = odoo.__WOWL_DEBUG__.root.__owl__) {
    if (node.component.constructor.name === name) {
        return node.component;
    }
    for (const child of Object.values(node.children)) {
        const found = findComponent(name, child);
        if (found) {
            return found;
        }
    }
}

const c = findComponent("DevisParCommercial");
c.state.orders.length;   // 5
c.groups();              // [{ name: "Mitchell Admin", count: 2, total: 4687.5 },
                         //  { name: "Marc Demo", count: 2, total: 2145 },
                         //  { name: "Sans commercial", count: 1, total: 377.5 }]

Remets la version correcte et recharge l'action. Le chemin trouvé est WebClient → ActionContainer → ControllerComponent → DevisParCommercial. Les noms de classes restent lisibles même sans debug. Ce que tu lis là, ce sont les vraies données du composant, pas une copie : une écriture dans c.state passe par le proxy et redessine l'écran, comme si le composant l'avait faite.

c.state.orders.push({ id: 99, name: "S99999", user_id: [7, "Joel Willis"], amount_untaxed: 120 });
// le tableau gagne une ligne « Joel Willis », 1 devis, 120.00

await c.load();          // relit les devis depuis le serveur : la ligne de test disparaît

C'est utile pour tester une hypothèse sans toucher au code : injecter un devis sans commercial (user_id: false) reproduit le bogue en une ligne. Les services sont aussi à portée de main, par env.services (84 clés sur cette base) :

const env = odoo.__WOWL_DEBUG__.root.env;
await env.services.orm.searchCount("sale.order", [["user_id", "=", false]]);   // 1

Ces appels passent par les droits de l'utilisateur connecté, comme ceux de l'interface. N'utilise ce raccourci que pour inspecter : un composant, lui, obtient l'ORM par usePlugin(ORM).

Venant de la 19 : env.debug lève une erreur

En 19, un composant testait le mode par this.env.debug. En 20, la propriété est retirée et sa lecture lève une erreur au lieu de rendre undefined : "env.debug" was removed when the debug mode became DebugModePlugin. Use usePlugin(DebugModePlugin) in a component or a plugin, and odoo.debug outside of one. Dans un composant, écris debugMode = usePlugin(DebugModePlugin) (import depuis @web/core/debug_mode_plugin) puis this.debugMode.isActive(), ou isActive("assets") pour un mode précis.

6. Points d'arrêt : arrêter le code sur le devis fautif

La console montre l'état à un instant donné. Un point d'arrêt fige l'exécution au milieu de groupBySalesperson, avec ses variables locales. Les pauses relevées ci-dessous sont celles du moteur de débogage de Chromium ; l'interface des outils de développement n'est pas montrée en capture.

Méthode 1 : debugger; dans le code

    for (const order of orders) {
        if (!order.user_id) {
            debugger; // temporaire : arrêt sur le devis fautif
        }
        const [, name] = order.user_id;

Recharge la page en ?debug=assets, outils de développement ouverts : l'exécution s'arrête dans groupBySalesperson, et la portée locale donne order.name = "S00003", order.user_id = false. Outils fermés, l'instruction est ignorée : même page, aucune pause, la fenêtre « Oups ! » s'affiche comme avant.

Point de vigilance : un debugger; oublié part en production

La minification d'Odoo ne retire pas l'instruction. Après « Régénérer les actifs », le bundle minifié la contient, et un navigateur dont les outils de développement sont ouverts s'arrête dessus, sans debug dans l'adresse. Cherche debugger dans ton module avant chaque commit.

Méthode 2 : un point d'arrêt conditionnel, sans toucher au code

Dans l'onglet Sources, ouvre devis_par_commercial.js par Ctrl+P (le fichier y figure sous son nom grâce à la carte des sources), fais un clic droit sur le numéro de la ligne 10 et ajoute un point d'arrêt conditionnel : !order.user_id. La liste compte cinq devis ; l'exécution ne s'arrête que sur le fautif :

pause : groupBySalesperson, ligne 10 de devis_par_commercial.js
  order.name         → "S00003"
  order.user_id      → false
  orders.length      → 5

Sans condition, il s'arrêterait à chaque tour de boucle jusqu'au devis fautif. La condition est une expression JavaScript évaluée dans la portée de la ligne : tout ce que la fonction voit, elle le voit.

Méthode 3 : la pause sur exception… sur la bonne case

Les outils de développement savent s'arrêter au moment où une exception est levée. Ils proposent deux cases : exceptions non interceptées, exceptions interceptées. Avec Odoo, le résultat surprend :

RéglageOù l'exécution s'arrête
Exceptions non interceptéesDeux fois, dans le code d'Odoo (loadState, puis fullAnnotatedTraceback), sur le rejet de la promesse. Jamais dans ton fichier.
Exceptions interceptéesUne fois, dans groupBySalesperson, sur la ligne fautive, avec order.name = "S00003"

L'erreur de rendu est attrapée par OWL, qui la transmet au gestionnaire d'erreurs d'Odoo : pour le navigateur, elle est « interceptée ». Pour s'arrêter là où elle naît, coche donc les exceptions interceptées. Sur cette page, il ne s'est arrêté qu'une fois ; ailleurs, toute exception rattrapée l'arrêtera aussi : décoche la case une fois le bogue trouvé.

7. « J'ai corrigé, rien ne change » : le JavaScript en cache

Avant de chercher un bogue qui n'existe plus, vérifie que le navigateur exécute bien ton code. Relevé avec la version fautive enregistrée sur le disque, serveur en marche :

PageBundleRésultat
Sans debugl'ancien bundle minifiéancienne version : « Sans commercial », pas d'erreur
?debug=1le mêmeancienne version
?debug=assetsreconstruit au chargementnouvelle version : « Oups ! »
Sans debug, après « Régénérer les actifs »nouveau bundle minifiénouvelle version

Le mode assets reconstruit le bundle quand un fichier qui le compose a changé ; le bundle minifié, lui, garde l'ancienne version jusqu'à une régénération ou un redémarrage. Le cas des vues XML et du code Python est traité dans Mettre à jour un module Odoo 20 qui ne prend pas tes modifications.

8. Déboguer un test Hoot

Le module livre deux tests : la fonction de regroupement avec un devis sans commercial, et l'action montée avec un faux serveur. Le lanceur s'ouvre par l'entrée « Exécuter les tests unitaires » du menu, ou à cette adresse, connecté :

http://localhost:8069/web/tests?debug=assets&filter="@oski_owl_debogage"

Résultat : Passed 2 tests (5 assertions). Un premier essai avait échoué sur Cannot find a definition for model "discuss.channel" : le module dépend de sale, donc de mail, et le fichier de test doit appeler defineMailModels() (importé de @mail/../tests/mail_test_helpers). Un module qui ne dépend que de web n'en a pas besoin.

Quand un test échoue sans que tu comprennes pourquoi, remplace test( par test.debug( :

test.debug("l'action lit les devis en cours et se met à jour", async () => {
    // … le test, inchangé
});

Hoot ne lance alors que ce test, sans délai d'expiration, et ne nettoie pas l'écran à la fin : le composant reste affiché, tel que le test l'a laissé, et tu peux l'inspecter avec la console comme en section 5.

Dans ce mode, le lanceur reste bloqué sur ce test : retire .debug avant de commiter, comme le debugger;.

À retenir

  • Pour déboguer le front, travaille en ?debug=assets, console ouverte : la trace cite ton fichier et ta ligne, et ton code modifié est repris.
  • « Oups ! » n'est pas le seul signal : un import mort ou un this. oublié ne s'affichent pas, la console si.
  • odoo.__WOWL_DEBUG__.root ouvre l'arbre des composants et les services, dans tous les modes.
  • Pour s'arrêter sur une erreur de rendu, coche les exceptions interceptées : OWL rattrape l'erreur avant le navigateur.
  • debugger; et test.debug sont des outils de poste : ni l'un ni l'autre ne doit partir dans un commit.
