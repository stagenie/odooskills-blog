Développer un module multi-société en Odoo 19

Dans un module multi-société, un utilisateur qui coche deux sociétés dans le sélecteur change ce que voit ton code : les enregistrements lus, la société des valeurs par défaut, le compteur de séquence. Voici les six mécanismes à connaître, chacun vérifié sur un module testé.

~15 minutes de lecture · niveau intermédiaire · parcours Framework ORM

Ce que tu vas apprendre

Le contexte

env.company, env.companies et la liste des sociétés autorisées : qui décide de quoi.

Les verrous

La règle d'enregistrement qui cache, et check_company qui refuse les croisements.

Les pièges

Valeurs par société, numéros perdus, crons lancés dans la mauvaise société, menus en cache.

Prérequis

  • Odoo 19 Community, avec au moins deux sociétés (la création et le basculement côté administrateur sont traités dans l'article fonctionnel sur le multi-société dans Odoo 19).
  • Savoir déclarer un modèle et ses champs (voir les modèles de base Odoo 19).
  • Le module démo de l'article dépend uniquement de base : deux modèles (odooskills.work.site, odooskills.work.order), une extension de res.partner et de res.company, 18 tests.

1. Trois ensembles de sociétés dans l'environnement

Le code ne lit jamais « la société de l'utilisateur » d'un seul bloc. Il dispose de trois ensembles emboîtés, et chaque mécanisme de l'ORM lit l'un d'eux.

ExpressionContenuD'où vient la valeur
env.user.company_idsSociétés autoriséesFiche utilisateur
env.companiesSociétés activesContexte allowed_company_ids ; à défaut, toutes les sociétés autorisées
env.companySociété courantePremier id de allowed_company_ids ; à défaut, env.user.company_id

Dans le client web, les cases cochées du sélecteur de sociétés sont gardées dans le cookie cids (valeur du type 1-11). Le client les renvoie ensuite dans le contexte de chaque appel, sous la clé allowed_company_ids. L'ordre compte : la première société de la liste devient env.company. Le test suivant le vérifie avec un utilisateur autorisé sur A et B :

def test_env_company_follows_allowed_company_ids(self):
    env = self.env(user=self.user_ab, context={
        'allowed_company_ids': [self.company_b.id, self.company_a.id]})
    self.assertEqual(env.company, self.company_b)
    self.assertEqual(env.companies, self.company_b | self.company_a)

def test_unauthorized_company_in_context_raises(self):
    env = self.env(user=self.user_a, context={'allowed_company_ids': [self.company_b.id]})
    with self.assertRaises(AccessError):
        env.company  # noqa: B018

Mettre dans le contexte une société non autorisée lève une AccessError dès la lecture de env.company. En sudo(), ce contrôle est sauté (commentaire explicite dans odoo/orm/environments.py) : c'est ce qui permet les opérations inter-sociétés, et c'est aussi pourquoi un sudo() posé par confort ouvre toutes les sociétés.

2. Cacher les enregistrements : company_id + règle globale

Premier verrou : le modèle porte un champ company_id, rempli par défaut avec la société courante.

company_id = fields.Many2one(
    'res.company', string="Société", required=True, index=True,
    default=lambda self: self.env.company,
)

Le champ seul ne cache rien. Il faut une règle d'enregistrement globale (sans groupe) : elle s'applique à tous les utilisateurs, administrateur compris.

<record id="work_order_company_rule" model="ir.rule">
    <field name="name">Bons d'intervention : sociétés actives</field>
    <field name="model_id" ref="model_odooskills_work_order"/>
    <field name="domain_force">[('company_id', 'in', company_ids)]</field>
</record>

<record id="work_site_company_rule" model="ir.rule">
    <field name="name">Sites d'intervention : sociétés actives ou partagés</field>
    <field name="model_id" ref="model_odooskills_work_site"/>
    <field name="domain_force">['|', ('company_id', '=', False), ('company_id', 'in', company_ids)]</field>
</record>

Dans le domaine, company_ids vaut self.env.companies.ids (odoo/addons/base/models/ir_rule.py) : ce sont les sociétés cochées, pas toutes les sociétés autorisées. La seconde règle garde visibles les sites sans société, partagés entre toutes.

⚠️ sudo() ignore la règle

Un search() en sudo() renvoie les bons de toutes les sociétés, même pour un utilisateur autorisé sur une seule. Le test du module le montre : l'utilisateur de A ne voit pas le bon de B, sa version sudo() le voit. Si un sudo() est nécessaire, filtre toi-même sur company_id.

3. Refuser les croisements : _check_company_auto et check_company

La règle cache, mais n'empêche pas d'écrire un bon de Société A qui pointe vers un site de Société B. Ce second verrou tient en deux lignes :

class WorkOrder(models.Model):
    _name = 'odooskills.work.order'
    _description = "Bon d'intervention"
    _check_company_auto = True

    site_id = fields.Many2one(
        'odooskills.work.site', string="Site", required=True, check_company=True,
    )
    partner_id = fields.Many2one('res.partner', string="Client", check_company=True)

check_company=True a deux effets distincts.

Effet 1 — un domaine est ajouté au champ

Le champ reçoit un domaine calculé qui ne propose que les sites de la société du bon, ou sans société. Le module l'affiche en test :

DOMAINE site_id: (company_id and [('company_id', 'in', [company_id] + [False])] or [('company_id', '=', False)]) + ([])

Ce domaine se lit dans odoo/orm/fields_relational.py. Le modèle doit avoir un champ company_id ou company_ids. Sans l'un des deux, Odoo écrit un avertissement dans le journal et le domaine n'est pas ajouté. Côté res.partner, la règle est plus souple : le modèle déclare _check_company_domain = models.check_company_domain_parent_of. Un contact rattaché à une société mère est donc accepté dans ses filiales.

Effet 2 — create et write vérifient la cohérence

Avec _check_company_auto = True, la méthode _check_company() est appelée à la création et à chaque écriture. Elle vérifie tous les champs relationnels marqués check_company. Le domaine de l'effet 1 ne protège que la liste déroulante. Ce contrôle, lui, s'applique aussi aux imports, aux appels RPC et au code serveur :

def test_check_company_blocks_crossover(self):
    with self.assertRaises(UserError) as cm:
        self._order(self.company_a, self.site_b)
    print("\nMESSAGE check_company:\n" + str(cm.exception))

def test_changing_company_later_is_checked_too(self):
    order = self._order(self.company_a, self.site_a)
    with self.assertRaises(UserError):
        order.company_id = self.company_b
MESSAGE check_company: Uh-oh! You’ve got some company inconsistencies here: - “BI/2026/0002” belongs to company “Société A” while “Site” (site_id: 'Atelier B') belongs to another company. To avoid a mess, no company crossover is allowed!

⚠️ Le message reste en anglais

Sur une base en français, le titre du dialogue est traduit (« Opération invalide »), mais pas le corps du message. Dans le fr.po de base du commit vérifié, ces chaînes ne figurent plus que comme entrées obsolètes. Si tes utilisateurs ne lisent pas l'anglais, contrôle la cohérence dans un @api.constrains avec ton propre message avant que ce contrôle ne se déclenche. La mécanique des contraintes est détaillée dans l'article sur les contraintes et champs calculés.

4. Une valeur par société : company_dependent

Certaines données sont partagées mais prennent une valeur différente selon la société : un compte comptable, un délai, un tarif. Sur le contact partagé du module, le taux horaire d'intervention en est un exemple :

class ResPartner(models.Model):
    _inherit = 'res.partner'

    odooskills_hourly_rate = fields.Float(
        string="Taux horaire d'intervention",
        company_dependent=True,
    )

Chaque lecture et chaque écriture passe par env.company. Le test écrit 50 pour A et 80 pour B, puis lit la colonne en SQL :

self.partner.with_company(self.company_a).odooskills_hourly_rate = 50.0
self.partner.with_company(self.company_b).odooskills_hourly_rate = 80.0
self.env.flush_all()
self.env.cr.execute(
    "SELECT odooskills_hourly_rate FROM res_partner WHERE id = %s", [self.partner.id])
print("\nCOLONNE jsonb:", self.env.cr.fetchone()[0])
COLONNE jsonb: {'2': 50.0, '3': 80.0}

Si tu viens d'Odoo 16 ou 17

La table ir.property n'existe plus : la valeur vit dans une colonne jsonb du modèle, indexée par l'id de société (odoo/orm/fields.py). En l'absence de valeur pour une société, Odoo lit la valeur par défaut de ir.default pour cette société. Les types acceptés sont char, float, boolean, integer, text, many2one, date, datetime, selection et html. Un champ company_dependent ne peut être ni required ni translate (avertissement au chargement).

⚠️ Lire la valeur de la bonne société

Sans précaution, un bon de Société B lu par un utilisateur dont la société courante est A récupère le taux de A. Le calcul doit se placer dans la société du document :

@api.depends('partner_id', 'company_id')
def _compute_hourly_rate(self):
    for order in self:
        # La valeur company_dependent est lue pour la société du bon,
        # pas pour la société active de l'utilisateur.
        partner = order.partner_id.with_company(order.company_id)
        order.hourly_rate = partner.odooskills_hourly_rate

Le test le confirme. Pour un utilisateur dont la société courante est A, le bon de B prend 80, alors que order.partner_id.odooskills_hourly_rate, lu sans with_company, renvoie 50.

5. Une numérotation par société

next_by_code() cherche d'abord une séquence de la société courante, puis une séquence sans société (odoo/addons/base/models/ir_sequence.py) :

company_id = self.env.company.id
seq_ids = self.search([('code', '=', sequence_code), ('company_id', 'in', [company_id, False])], order='company_id')

Pour que chaque société ait son propre compteur, le module crée une séquence par société : pour les sociétés existantes à l'installation (post_init_hook), puis pour chaque nouvelle société :

class ResCompany(models.Model):
    _inherit = 'res.company'

    @api.model_create_multi
    def create(self, vals_list):
        companies = super().create(vals_list)
        companies._odooskills_create_work_order_sequence()
        return companies

    def _odooskills_create_work_order_sequence(self):
        Sequence = self.env['ir.sequence'].sudo()
        for company in self:
            if Sequence.search_count([
                ('code', '=', 'odooskills.work.order'),
                ('company_id', '=', company.id),
            ]):
                continue
            Sequence.create({
                'name': f"Bons d'intervention — {company.name}",
                'code': 'odooskills.work.order',
                'company_id': company.id,
                'prefix': 'BI/%(year)s/',
                'padding': 4,
            })

Au moment de numéroter, le bon ne se fie pas à la société courante mais à celle qu'il reçoit :

@api.model_create_multi
def create(self, vals_list):
    for vals in vals_list:
        if vals.get('name', '/') == '/':
            company = self.env['res.company'].browse(vals.get('company_id')) or self.env.company
            vals['name'] = self.env['ir.sequence'].sudo().with_company(company).next_by_code(
                'odooskills.work.order') or '/'
    return super().create(vals_list)

Deux sociétés neuves C et D, trois bons créés dans l'ordre C, D, C :

SEQUENCES: BI/2026/0001 BI/2026/0001 BI/2026/0002

⚠️ Un create refusé consomme quand même un numéro

L'implémentation par défaut (standard) appelle nextval() sur une séquence PostgreSQL. Ce compteur n'est pas annulé quand la transaction échoue. Dans le test, le deuxième bon est refusé par check_company après avoir reçu son numéro :

TROU: BI/2026/0001 -> BI/2026/0003

Si la loi ou le métier exige une suite sans trou, passe la séquence en implementation='no_gap'. Le numéro est alors lu dans la ligne ir_sequence avec SELECT … FOR UPDATE NOWAIT et annulé avec la transaction. En contrepartie, si deux créations arrivent en même temps dans la même société, la seconde échoue aussitôt sur le verrou (NOWAIT) et doit être rejouée.

6. Les crons tournent dans une seule société

Le champ user_id d'un ir.cron prend par défaut l'utilisateur qui crée la tâche. Une tâche déclarée en XML est chargée à l'installation par le superutilisateur. Le module affiche l'environnement dans lequel sa tâche tournera :

CRON user: __system__ su: True env.company: My Company

Deux conséquences. D'abord, su vaut True : les règles d'enregistrement sont ignorées et le cron voit toutes les sociétés. Ensuite, env.company est la société principale de cet utilisateur. Tout ce qui lit env.company (valeur par défaut, séquence, champ company_dependent) prend donc la même société pour tous les enregistrements. La parade consiste à parcourir les sociétés :

@api.model
def _cron_mark_late(self):
    today = fields.Date.context_today(self)
    for company in self.env['res.company'].search([]):
        late = self.with_company(company).search([
            ('company_id', '=', company.id),
            ('state', '=', 'draft'),
            ('date_deadline', '<', today),
        ])
        late.write({'state': 'late'})

Le filtre explicite sur company_id est indispensable : en superutilisateur, la règle ne filtre plus rien. La planification elle-même (intervalle, déclencheurs) est traitée dans l'article sur les actions serveur et les crons.

7. Masquer une application selon la société : le cache des menus

Tôt ou tard, un projet demande de montrer une application à une société et de la cacher à une autre. Le réflexe est de filtrer les menus sur env.company. Deux faits du code source rendent ce filtre peu fiable :

@api.model
@tools.ormcache('self.env.uid', 'debug', 'self.env.lang')
def load_menus(self, debug):
  • La clé de cache ne contient pas la société (odoo/addons/base/models/ir_ui_menu.py). Le premier calcul est resservi à l'utilisateur, quelle que soit la société cochée ensuite.
  • L'appel ne transporte pas les sociétés actives. Le client web charge les menus par un simple GET /web/webclient/load_menus (addons/web/static/src/webclient/menus/menu_service.js). Côté Python, le cookie cids n'est lu que pour être normalisé (addons/web/models/ir_http.py). Dans cette requête, env.company retombe donc sur la société principale de l'utilisateur.

Un masquage par société doit donc reposer sur une donnée que cette requête connaît vraiment, comme les groupes de l'utilisateur, et non sur la société cochée dans le sélecteur.

8. Tester avec deux sociétés

Tous les résultats cités viennent de la suite du module. Sa préparation crée deux sociétés, un utilisateur limité à A et un utilisateur autorisé sur A et B :

@classmethod
def setUpClass(cls):
    super().setUpClass()
    cls.company_a = cls.env['res.company'].create({'name': "Société A"})
    cls.company_b = cls.env['res.company'].create({'name': "Société B"})
    cls.user_a = new_test_user(
        cls.env, login='mc_user_a', groups='base.group_user',
        company_id=cls.company_a.id, company_ids=[cls.company_a.id],
    )
    cls.user_ab = new_test_user(
        cls.env, login='mc_user_ab', groups='base.group_user,base.group_multi_company',
        company_id=cls.company_a.id, company_ids=[cls.company_a.id, cls.company_b.id],
    )

Deux habitudes rendent ces tests fiables :

  • Tester en utilisateur, pas en superutilisateur. L'environnement de test par défaut ignore les règles. Seuls with_user() ou self.env(user=…) les font réellement jouer.
  • Ne pas supposer un compteur à zéro. Comme vu en section 5, les numéros consommés par un test ne sont pas rendus au retour arrière. Un test de numérotation doit créer ses propres sociétés.

Récapitulatif

  • env.companies = sociétés cochées, lues par les règles ; env.company = la première, lue par les valeurs par défaut, les séquences et les champs company_dependent.
  • Un champ company_id ne cache rien sans règle globale [('company_id', 'in', company_ids)], et sudo() contourne cette règle.
  • _check_company_auto = True + check_company=True : domaine sur le champ et refus en create/write, avec un message non traduit.
  • company_dependent = colonne jsonb par société ; lire avec with_company(document.company_id).
  • Une séquence par société, et la séquence standard laisse des trous : no_gap si la loi l'exige.
  • Un cron déclaré en XML tourne en __system__ dans la société principale : boucler sur les sociétés avec with_company().
  • load_menus est mis en cache sans la société : ne pas masquer une application sur env.company.
