Traceback Odoo 20 : lire une erreur et trouver la ligne fautive

Un clic sur un bouton, et Odoo 20 affiche « Oups ! ». Derrière cette fenêtre se cache une trace Python de quarante lignes, dont une seule t'intéresse vraiment. Voici où la trouver, dans l'interface comme dans le journal du serveur, et comment ne pas confondre l'erreur d'origine avec son enveloppe (RPC_ERROR, erreur 500).

~6 minutes de lecture · niveau intermédiaire · série Astuces dev Odoo 20

Édition : Community. Écrit et vérifié sur Odoo 20.0 Community, octobre 2026, sur la base de démonstration, avec un petit module d'exemple qui provoque de vraies erreurs.

La réponse en bref

  1. Dans la fenêtre « Oups ! », clique sur Voir les détails techniques, puis descends tout en bas de la trace.
  2. La dernière ligne Python (KeyError: 'SM'…) est l'erreur d'origine. RPC_ERROR et Odoo Server Error ne sont que l'enveloppe.
  3. Remonte jusqu'au dernier File "…", line N qui pointe dans ton module : c'est la ligne fautive.
  4. La même trace est dans le journal du serveur, sous ERROR … odoo.http: Exception during request handling.

1. Une vraie erreur pour s'exercer

Le module d'exemple ajoute un bouton Calculer la remise sur la fiche contact. Le taux dépend du pays, et le dictionnaire ne connaît que la France et les États-Unis :

# mon_module/models/res_partner.py
from odoo import models
from odoo.exceptions import UserError

TAUX_REMISE = {'FR': 5, 'US': 10}


class ResPartner(models.Model):
    _inherit = 'res.partner'

    def _taux_remise(self):
        return TAUX_REMISE[self.country_id.code]

    def action_calculer_remise(self):
        for partner in self:
            taux = partner._taux_remise()
            partner.comment = f"Remise : {taux} %"

    def action_verifier_email(self):
        if not self.email:
            raise UserError("Ce contact n'a pas d'adresse e-mail.")

2. Dans l'interface : déplier, descendre, copier

  1. Clique sur Voir les détails techniques. Le lien devient Masquer les détails techniques et la fenêtre s'élargit.
  2. Le bloc commence par Erreur de serveur Odoo, une ligne « Occurred on … on model res.partner on … », puis RPC_ERROR et Odoo Server Error. Ne t'arrête pas là : c'est l'emballage.
  3. Fais défiler la trace jusqu'en bas. La ligne KeyError: 'SM' donne la vraie erreur ; juste au-dessus, …/mon_module/models/res_partner.py", line 11, in _taux_remise donne le fichier, la ligne et la fonction. La ligne de code fautive est recopiée en dessous, soulignée de ~~~^^^.
  4. Pour la transmettre, clique sur l'icône presse-papiers en haut à droite du bloc : une info-bulle Copié confirme. Le texte copié contient le nom de l'erreur, le message, le contexte (serveur, modèle, heure) et la trace entière.

La trace se lit de bas en haut. Python l'écrit « most recent call last » : le dernier cadre est l'endroit où l'exception est levée (ligne 11), celui du dessus est l'appelant (ligne 15, action_calculer_remise). Tous les cadres plus haut — odoo/http/router.py, dispatcher.py, routing_map.py, web/controllers/dataset.py, odoo/service/model.py — sont la plomberie qui a transporté le clic jusqu'à ta méthode. La ligne à corriger est presque toujours dans le dernier cadre qui porte le chemin de ton module.

Petit repère si tu viens de la 19 : cette plomberie s'appelait odoo/http.py, un seul fichier ; en 20 elle est découpée dans le paquet odoo/http/. La lecture ne change pas.

3. Dans le journal du serveur : chercher « ERROR »

Le serveur a tout écrit au même moment, dans le terminal ou dans le fichier défini par logfile. Cherche ERROR à l'heure indiquée dans la fenêtre :

grep -n -A40 "Exception during request handling" odoo.log

La première ligne donne l'heure, le niveau ERROR et la base. La ligne d'accès qui suit nomme la route appelée, donc le bouton exact, et se termine par 200, pas par 500 : c'est le point suivant.

4. L'enveloppe : RPC_ERROR, 200 et 500

L'interface parle au serveur en JSON-RPC. Quand ta méthode lève une exception, la réponse HTTP reste 200 ; l'erreur voyage dans le corps JSON. Rejouée avec curl :

HTTP/1.1 200 OK { "code": 0, "message": "Odoo Server Error", "data": { "name": "builtins.KeyError", "message": "SM", "arguments": [ "SM" ] } }

(extrait du champ error ; data.debug porte la trace complète.) Le client web transforme cette réponse en exception JavaScript nommée RPC_ERROR. Ce nom ne dit rien de la cause : elle est dans data.name et dans la trace.

L'erreur 500 apparaît sur les routes type='http' (une page web, un export, un contrôleur maison). Même bug, appelé par une route de ce type (auth='user', d'où le cookie de session) :

$ curl -i -b cookies.txt http://localhost:8069/mon_module/remise/11 HTTP/1.1 500 INTERNAL SERVER ERROR date: Wed, 21 Oct 2026 11:21:53 GMT content-type: text/html; charset=utf-8 content-length: 265 connection: close server: odoo/20.0 python-h11/0.16.0 CPython/3.12.3 <!doctype html> <html lang=en> <title>500 Internal Server Error</title> <h1>Internal Server Error</h1> <p>The server encountered an internal error and was unable to complete your request. Either the server is overloaded or there is an error in the application.</p>

La page 500 ne dit rien de la cause, volontairement. La trace n'est que dans le journal, sous la même ligne ERROR … Exception during request handling., suivie de "GET /mon_module/remise/11 HTTP/1.1" 500. Face à une « odoo error 500 », le journal est donc le seul endroit utile.

5. Quand il n'y a pas de trace

Une erreur métier levée volontairement (UserError) n'a ni « Oups ! » ni détails techniques : la fenêtre affiche le message tel quel.

Le journal n'en garde qu'une ligne, sans trace :

2026-10-21 11:18:39,320 58304 WARNING ma_base odoo.http: Ce contact n'a pas d'adresse e-mail.

C'est voulu : le code a choisi ce message. Pour retrouver d'où il part, cherche son texte dans le code (grep -rn "pas d'adresse e-mail" mon_module/). Une erreur de droits (AccessError) est aussi journalisée en WARNING sans trace ; pour l'obtenir, relance le serveur avec --dev=access. Le même refus, sur ir.config_parameter avec l'utilisateur de démonstration, est alors suivi de sa pile complète :

2026-10-21 11:19:11,534 65282 WARNING ma_base odoo.http: You are not allowed to access 'System Parameter' (ir.config_parameter) records. This operation is allowed for the following groups: - Role / Administrator Contact your administrator to request access if necessary. Traceback (most recent call last): File "…/odoo/http/router.py", line 279, in __call__ response = serve_db(request)

--dev n'ouvre pas de débogueur

En Odoo 20, ./odoo-bin server --help liste cinq fonctions pour --dev : access, qweb, reload, replica, xml (all = access, reload, qweb, xml). Aucune n'arrête le serveur sur l'exception. Pour inspecter les variables au point fautif, place breakpoint() juste avant la ligne et lance le serveur au premier plan dans ton terminal : la requête s'y fige sur l'invite (Pdb). Essai sur une route du module d'exemple :

    @http.route('/mon_module/pause/<int:partner_id>', type='http', auth='user')
    def pause(self, partner_id):
        partner = request.env['res.partner'].browse(partner_id)
        breakpoint()
        return f"Remise de {partner.name} : {partner._taux_remise()} %"
> …/addons/mon_module/controllers/main.py(16)pause() -> return f"Remise de {partner.name} : {partner._taux_remise()} %" (Pdb) p partner.name, partner.country_id.code ('Gemini Furniture', 'SM') (Pdb) c

Tape c pour laisser la requête continuer, et retire le breakpoint() avant de livrer le module.

À retenir

  • Une trace se lit de bas en haut : dernière ligne = l'erreur, dernier File … line … de ton module = la ligne à corriger.
  • RPC_ERROR, Odoo Server Error et la page 500 sont des enveloppes ; la cause est dans data.name et la trace.
  • Le journal du serveur garde la trace complète, sous ERROR … Exception during request handling., même quand l'écran n'en montre rien.
  • UserError et AccessError n'écrivent qu'un WARNING ; --dev=access ajoute la trace des refus de droits.
