create, write et Command en Odoo 20 : écrire sur One2many et Many2many

Créer un ou plusieurs enregistrements, les modifier en un appel, puis toucher aux lignes d'une commande de vente et aux étiquettes d'un contact avec les sept Command. Chaque commande a été exécutée sur la démo d'Odoo 20, état avant et après : laquelle supprime vraiment, laquelle déplace une ligne sans prévenir, et ce que copy et unlink font de différent depuis la 19.

~12 minutes de lecture · niveau intermédiaire · parcours Framework & ORM

Ce que tu vas apprendre

Créer, modifier

create avec un dictionnaire ou une liste, write sur un ou plusieurs enregistrements, et l'ordre dans lequel Odoo 20 écrit les champs.

Les 7 Command

create, update, delete, unlink, link, clear, set : sur un One2many et sur un Many2many, ce qui reste en base.

Dupliquer, supprimer

copy et le suffixe « (copie) », unlink et @api.ondelete, et le drapeau qui ne contourne plus rien.

Prérequis

  • Une base Odoo 20 Community avec les modules Ventes et Inventaire et les données de démonstration, en français : les commandes S00002 à S00005, les contacts « Acme Corporation » ou « Lumber Inc » et les étiquettes de contact viennent de là.
  • La console ./odoo-bin shell -c odoo.conf -d ma_base : tous les extraits y ont été exécutés, et chaque série se termine par env.cr.rollback() pour laisser la base intacte, sauf celle de la section 4, validée pour la capture d'écran : rejoue-la sur une copie de la base. La console est présentée dans l'article sur le shell Odoo 20.

1. create : un dictionnaire ou une liste

create est décoré par @api.model_create_multi : il attend une liste de dictionnaires et crée tous les enregistrements en un appel. Un dictionnaire seul est encore accepté, le décorateur l'emballe dans une liste. Dans les deux cas, le retour est un recordset :

Partner = env['res.partner']
one = Partner.create({'name': "Atelier Nord"})
print(one, one.name)
several = Partner.create([
    {'name': "Atelier Sud"},
    {'name': "Atelier Est", 'city': "Lyon"},
])
print(several, several.mapped('name'))
print(Partner.create([]))
res.partner(51,) Atelier Nord res.partner(52, 53) ['Atelier Sud', 'Atelier Est'] res.partner()

Une liste vide ne crée rien et rend un recordset vide, sans erreur. Quand tu crées en boucle, construis la liste puis appelle create une fois : les champs calculés, les contraintes et les écritures SQL sont traités par lot.

Un enregistrement et ses lignes se créent ensemble : la valeur d'un One2many est une liste de commandes. Une commande de vente pour Acme Corporation avec deux lignes :

from odoo.fields import Command

acme = Partner.search([('name', '=', "Acme Corporation")])
chair = env['product.product'].search([('default_code', '=', 'FURN_7777')])
desk = env['product.product'].search([('default_code', '=', 'FURN_0789')])
order = env['sale.order'].create({
    'partner_id': acme.id,
    'order_line': [
        Command.create({'product_id': chair.id, 'product_uom_qty': 4}),
        Command.create({'product_id': desk.id, 'product_uom_qty': 1}),
    ],
})
print(order.name, order.state, order.order_line.mapped('product_id.name'), order.amount_total)
S00027 draft ['Chaise de bureau', 'Espace de travail individuel'] 1339.75

Le numéro, le prix, les taxes et le total sont calculés par Odoo, comme si la commande avait été saisie à l'écran. Command s'importe de odoo.fields ; from odoo import Command donne la même classe.

2. write : un ou plusieurs enregistrements

write applique le même dictionnaire à tous les enregistrements du recordset et renvoie True. Les trois ateliers créés plus haut, en un appel :

ateliers = one | several
print(ateliers.write({'city': "Nantes"}))
print(ateliers.mapped('city'))
True ['Nantes', 'Nantes', 'Nantes']

Pour donner des valeurs différentes à chaque enregistrement, il faut un write par valeur distincte (ou par enregistrement). Grouper les enregistrements qui reçoivent la même valeur reste le moyen le plus économe.

Venant de la 19 : l'ordre d'écriture des champs

Dans un même write, les champs sont triés par priorité (write_sequence : montants après leur devise, One2many et Many2many en dernier). À priorité égale, la 19 les écrivait dans l'ordre des clés du dictionnaire ; Odoo 20 les écrit dans l'ordre de déclaration du modèle (_fields_update_order__, couple (write_sequence, rang du champ)). Deux dictionnaires aux clés mélangées donnent maintenant le même ordre :

SO = env['sale.order']
for keys in (['order_line', 'note', 'partner_id', 'amount_total'], ['partner_id', 'amount_total', 'note', 'order_line']):
    print(keys, '->', [n for n in sorted(keys, key=lambda n: SO._fields_update_order__[SO._fields[n]])])
['order_line', 'note', 'partner_id', 'amount_total'] -> ['partner_id', 'note', 'amount_total', 'order_line'] ['partner_id', 'amount_total', 'note', 'order_line'] -> ['partner_id', 'note', 'amount_total', 'order_line']

Un code qui comptait sur l'ordre des clés pour qu'un champ à inverse passe avant un autre doit s'appuyer sur l'ordre des champs dans la classe, ou faire deux write.

3. Les sept Command sur les lignes d'une commande

Un One2many ou un Many2many ne s'écrit pas avec une liste d'ids : on lui passe une liste de commandes, chacune un triplet (code, id, valeurs) que les méthodes de Command fabriquent pour toi. Le terrain d'essai : le devis S00003 de la démo, deux lignes, et un petit affichage après chaque commande (id, article, quantité, puis total) :

order = env['sale.order'].search([('name', '=', 'S00003')])
other = env['sale.order'].search([('name', '=', 'S00002')])

def show(label):
    print(f"{label:<7}", [(l.id, l.product_id.name, l.product_uom_qty) for l in order.order_line], order.amount_total)

show("avant")
first, second = order.order_line
order.write({'order_line': [Command.create({'product_id': desk.id, 'product_uom_qty': 3})]})
show("create")
new = order.order_line - first - second
order.write({'order_line': [Command.update(new.id, {'product_uom_qty': 5})]})
show("update")
order.write({'order_line': [Command.delete(second.id)]})
show("delete")
print("        second.exists() ->", second.exists())
borrowed = other.order_line[0]
order.write({'order_line': [Command.link(borrowed.id)]})
show("link")
print("        borrowed.order_id ->", borrowed.order_id.name, "| S00002 garde", other.order_line.ids)
order.write({'order_line': [Command.unlink(borrowed.id)]})
show("unlink")
print("        borrowed.exists() ->", borrowed.exists())
order.write({'order_line': [Command.set([first.id])]})
show("set")
print("        new.exists() ->", new.exists())
order.write({'order_line': [Command.clear()]})
show("clear")
print("        first.exists() ->", first.exists())
env.cr.rollback()

Command.create(vals)Une ligne 58 est créée et rattachée au devis ; le total suit.

Sur un One2many, unlink peut supprimer

Une ligne détachée doit bien aller quelque part. Odoo regarde le champ inverse : s'il porte ondelete='cascade', comme sale.order.line.order_id, la ligne est supprimée ; sinon l'inverse est vidé et l'enregistrement reste orphelin (odoo/orm/fields_relational.py, fonction unlink de l'écriture d'un One2many). unlink, clear et set passent par là : sur des lignes de commande, les trois effacent. Et link sur une ligne d'un autre document la lui retire sans message.

4. Plusieurs commandes dans un seul write

En pratique, on combine. La liste passée au champ est exécutée dans l'ordre, en une écriture. Le devis S00003 d'origine :

On passe la première ligne à 4 unités, on supprime la chaise et on ajoute deux espaces de travail, puis on valide :

order = env['sale.order'].search([('name', '=', 'S00003')])
desk = env['product.product'].search([('default_code', '=', 'FURN_0789')])
design, chair = order.order_line
order.write({'order_line': [
    Command.update(design.id, {'product_uom_qty': 4}),
    Command.delete(chair.id),
    Command.create({'product_id': desk.id, 'product_uom_qty': 2}),
]})
print([(l.id, l.product_id.name, l.product_uom_qty) for l in order.order_line], order.amount_total)
env.cr.commit()
[(6, "Design d'intérieur virtuel", 4.0), (67, 'Espace de travail individuel', 2.0)] 2176.95

Le client web ne fait pas autre chose : quand tu modifies les lignes et enregistres, il appelle web_save, qui passe au write du devis une liste de commandes pour order_line (addons/web/models/models.py).

5. Les mêmes commandes sur un Many2many

Les étiquettes d'un contact (res.partner.category_id) sont un Many2many : une étiquette peut être posée sur plusieurs contacts, et le lien vit dans une table à deux colonnes, res_partner_res_partner_category_rel. On suit le contact Lumber Inc, qui n'a pas d'étiquette, en lisant à chaque étape le champ et la table :

partner = Partner.search([('name', '=', "Lumber Inc")])
Tag = env['res.partner.category']

def tags(label):
    env.flush_all()
    env.cr.execute(
        "SELECT category_id FROM res_partner_res_partner_category_rel"
        " WHERE partner_id = %s ORDER BY 1", [partner.id])
    print(f"{label:<7}", partner.category_id.mapped('name'), "| table :", [r[0] for r in env.cr.fetchall()])

tags("avant")
partner.write({'category_id': [Command.create({'name': "Grands comptes"})]})
tags("create")
key = partner.category_id
partner.write({'category_id': [Command.update(key.id, {'name': "Comptes clés"})]})
tags("update")
advice = Tag.search([('name', '=', "Services de conseil")])
partner.write({'category_id': [Command.link(advice.id)]})
tags("link")
partner.write({'category_id': [Command.unlink(advice.id)]})
tags("unlink")
print("        advice ->", advice.exists().name, "| encore sur", advice.partner_ids.mapped('name'))
partner.write({'category_id': [Command.delete(key.id)]})
tags("delete")
print("        key.exists() ->", key.exists())
partner.write({'category_id': [Command.set([5, 6])]})
tags("set")
partner.write({'category_id': [Command.clear()]})
tags("clear")
print("        5, 6 ->", Tag.browse([5, 6]).exists().mapped('name'))
env.cr.rollback()

La différence avec le One2many tient en deux lignes :

  • unlink, clear et set ne touchent qu'à la table de relation : « Services de conseil » quitte Lumber Inc mais reste sur Gemini Furniture, et les étiquettes 5 et 6 existent toujours après clear.
  • delete supprime l'étiquette elle-même, pour tous les contacts qui la portaient. Pour « retirer l'étiquette de ce contact », c'est unlink.

Le détail du Many2many (table, colonnes, ondelete de la relation) est dans l'article sur les genres d'un livre.

6. Les sept commandes d'un coup d'œil

Les méthodes ne font que fabriquer le triplet. Par RPC (JSON-2, XML-RPC), où la classe n'existe pas, on envoie le triplet lui-même, le premier élément étant le code entier :

print(Command.create({'name': "x"}), Command.link(4), Command.set([5, 6]), Command.clear())
(<Command.CREATE: 0>, 0, {'name': 'x'}) (<Command.LINK: 4>, 4, 0) (<Command.SET: 6>, 0, [5, 6]) (<Command.CLEAR: 5>, 0, 0)

Command est une énumération d'entiers : Command.LINK == 4, et [(4, 4, 0)] écrit en dur fait la même chose que [Command.link(4)]. Dans le code Python, préfère les méthodes : elles se lisent.

7. copy : dupliquer un enregistrement

copy(default=None) lit les valeurs à recopier (copy_data), y applique default, puis appelle create. Chaque champ décide s'il est recopié par son attribut copy : le numéro de commande ne l'est pas (copy=False), les lignes le sont (copy=True sur order_line), recréées par des Command.create.

s4 = env['sale.order'].search([('name', '=', 'S00004')])
dup = s4.copy()
print(dup.name, dup.state, len(dup.order_line), dup.amount_total, "| origine :", s4.name, s4.state)
dup2 = s4.copy({'client_order_ref': "REF-42"})
print(dup2.name, dup2.client_order_ref)
print(Tag.browse(5).copy().name)
print(Partner.search([('name', '=', "Lumber Inc")]).copy().name)
template = chair.product_tmpl_id
print(template.copy_data()[0]['name'])
print(hasattr(template, 'copy_translations'))
env.cr.rollback()
S00028 draft 4 2240.0 | origine : S00004 sale S00031 REF-42 Services (copie) Lumber Inc (copie) {'en_US': 'Office Chair (copy)', 'fr_FR': 'Chaise de bureau (copie)'} False

La commande confirmée donne un devis neuf (draft), avec ses quatre lignes et le même total. L'étiquette et le contact reçoivent le suffixe « (copie) ». Pour un champ traduit, copy_data rend toutes les traductions, chacune suffixée dans sa langue.

Venant de la 19 : deux changements dans copy

Le suffixe « (copy) » devient générique. En Odoo 20, tout champ Char nommé name (ou x_name) qui ne déclare pas copy reçoit copy=mark_as_copy('name') (odoo/orm/fields_textual.py, odoo/tools/translate.py). En 19, seuls les modèles qui surchargeaient copy_data ajoutaient « (copy) », comme res.partner et product.template ; une étiquette de contact, ou le modèle de ton module, était dupliquée sous le même nom. Si le nom doit rester identique (un code, une référence), déclare copy=True sur le champ ; s'il ne doit pas être recopié, copy=False.

copy_translations a disparu. En 19, copy appelait copy_translations(new) après la création pour recopier les traductions. En 20, elles voyagent dans copy_data et la méthode n'existe plus : une surcharge de copy_translations portée telle quelle n'est jamais appelée, sans erreur. La logique va dans copy_data.

8. unlink et @api.ondelete

unlink() supprime les enregistrements du recordset et renvoie True. Avant, il appelle les méthodes décorées par @api.ondelete du modèle : c'est là qu'un module refuse une suppression. Celle du module Ventes :

# addons/sale/models/sale_order.py (Odoo 20)
    @api.ondelete(at_uninstall=False)
    def _unlink_except_draft_or_cancel(self):
        for order in self:
            if order.state not in ("draft", "cancel"):
                raise UserError(
                    order.env._(
                        "You can not delete a sent quotation or a confirmed sales order."
                        " You must first cancel it."
                    )
                )

On essaie sur la commande confirmée S00004, avec et sans le drapeau force_delete, puis sur une de ses lignes, puis sur le devis S00005 :

from odoo.exceptions import UserError

confirmed = env['sale.order'].search([('name', '=', 'S00004')])
for ctx in ({}, {'force_delete': True}):
    try:
        with env.cr.savepoint():
            confirmed.with_context(**ctx).unlink()
    except UserError as e:
        print(ctx, "UserError :", e.args[0])
try:
    with env.cr.savepoint():
        confirmed.write({'order_line': [Command.delete(confirmed.order_line[0].id)]})
except UserError as e:
    print("Command.delete -> UserError :", e.args[0])
draft = env['sale.order'].search([('name', '=', 'S00005')])
print(draft.state, draft.unlink(), draft.exists())
env.cr.rollback()

Trois enseignements. Un Command.delete passe par l'unlink de la ligne, donc par ses gardes (_unlink_except_confirmed sur sale.order.line) : la console n'y échappe pas, bien qu'elle tourne en superutilisateur. Le devis, lui, part sans difficulté. Et le message de la ligne sort en anglais : il n'a pas de traduction française dans cette version, ce n'est pas ton code.

at_uninstall=False veut dire : « ne pas appliquer cette garde quand le module qui la déclare est en cours de désinstallation », pour que la désinstallation de Ventes puisse vider ses tables. Avec at_uninstall=True, la garde s'applique toujours.

Venant de la 19 : le drapeau ne contourne plus les gardes

En 19, la clé de contexte s'appelait _force_unlink (MODULE_UNINSTALL_FLAG) et unlink sautait toutes les méthodes at_uninstall=False dès qu'elle était présente : un with_context(_force_unlink=True).unlink() supprimait une commande confirmée. En 20, la clé s'appelle force_delete (odoo/addons/base/models/ir_model.py, la constante n'est gardée que pour compatibilité) et unlink ne regarde plus le contexte : une garde n'est sautée que si son propre module figure parmi les modules en désinstallation (self.pool.uninstalling_modules). La sortie ci-dessus le montre. Pour supprimer une commande confirmée, annule-la d'abord (action_cancel()), comme le demande le message.

Mémo

BesoinOdoo 20

Retirer une étiquette d'un contactCommand.unlink(id) (pas delete)

Récapitulatif

  • create prend une liste de dictionnaires et rend un recordset ; write applique les mêmes valeurs à tout le recordset, dans l'ordre de déclaration des champs en Odoo 20.
  • Les One2many et Many2many s'écrivent avec des Command, exécutées dans l'ordre de la liste, en un seul write.
  • delete supprime l'enregistrement lié. Sur un One2many dont l'inverse est en cascade, unlink, set et clear suppriment aussi, et link déplace la ligne d'un autre document.
  • Sur un Many2many, unlink, set et clear ne touchent qu'à la table de relation.
  • En Odoo 20, copy ajoute « (copie) » à tout champ name sans attribut copy, et les traductions passent par copy_data ; force_delete ne contourne plus les gardes @api.ondelete.
