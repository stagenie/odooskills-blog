search, search_read, search_fetch, fetch : lire vite en Odoo 20

Un recordset, une liste de dictionnaires, un nombre, des couples (id, nom) : l'ORM offre plusieurs façons de lire la base, et elles ne coûtent pas le même nombre de requêtes SQL. Ce que renvoie chaque méthode, ce qu'elle lit vraiment, la mesure sur 500 lignes de commande, et ce qu'Odoo 20 change à fetch et search_fetch.

~11 minutes de lecture · niveau intermédiaire · parcours Framework & ORM

Ce que tu vas apprendre

Chercher, compter

search (ids et prefetch), search_count et son limit, name_search pour un champ de saisie.

Lire en dictionnaires

search_read et read : le format RPC, les many2one en (id, nom), et ce que coûte ce nom.

Lire en une requête

search_fetch et fetch, le comptage des requêtes avec sql_log_count et --log-sql, et le tableau mesuré.

Pour rejouer les exemples

  • Une base Odoo 20 Community de test avec les données de démonstration et les applications Ventes et Inventaire. Aucun module à écrire.
  • La console : odoo-bin shell -c odoo.conf -d ma_base --no-http, présentée dans l'article sur la console. Toutes les sorties ci-dessous y ont été relevées telles quelles ; sur ta base, les ids peuvent différer.
  • La démo compte 50 lignes de commande. Pour que les mesures aient du poids, 45 devis de 10 lignes ont été ajoutés : 500 lignes en tout. C'est la seule écriture validée de l'article (le script ci-dessous) ; tout le reste tourne dans une transaction annulée.
# Création des lignes de mesure : 45 devis x 10 lignes (+ 50 lignes de démo = 500)
from odoo.fields import Command
P = env['product.product'].search([('sale_ok','=',True), ('type','=','consu')], order='id')
C = env['res.partner'].search([('is_company','=',True)], order='id')
vals = []
k = 0
for i in range(45):
    lines = []
    for j in range(10):
        lines.append(Command.create({'product_id': P[k % len(P)].id, 'product_uom_qty': 1 + (k % 7)}))
        k += 1
    vals.append({'partner_id': C[i % len(C)].id, 'order_line': lines})
orders = env['sale.order'].create(vals)
print('created', len(orders), orders[0].name, orders[-1].name)
print('lines', env['sale.order.line'].search_count([]))
env.cr.commit()
created 45 S00025 S00069 lines 500

1. search : des ids, et rien d'autre pour l'instant

search(domain, offset=0, limit=None, order=None) renvoie un recordset : les ids qui satisfont le domaine, dans l'ordre demandé (ou le _order du modèle). Aucun champ n'est lu à ce stade.

SOL = env['sale.order.line']
lines = SOL.search([('order_id.state', '=', 'sale')], order='price_subtotal desc', limit=3)
lines
lines.mapped(lambda l: (l.order_id.name, l.product_id.display_name, l.price_subtotal))
SOL.search([], order='id', offset=3, limit=4).ids
SOL.search([('product_uom_qty', '>', 100)])
sale.order.line(48, 50, 43) [('S00023', '[FURN_6667] Écrans anti-bruit (Noir)', 2950.0), ('S00024', "[E-COM06] Bureau d'angle avec siège à droite", 1990.0), ('S00020', "Design d'intérieur virtuel", 1800.0)] [4, 5, 6, 7] sale.order.line()

Dans le code d'Odoo 20, search tient en une ligne : return self.search_fetch(domain, [], …) (odoo/orm/models.py). Une liste de champs vide : une seule requête, qui ne ramène que la colonne id. Les valeurs arrivent au premier accès à un champ, et pour tout le recordset d'un coup grâce au prefetch : la boucle sur les 500 lignes coûte une requête de plus, pas 500. Cette requête lit toutes les colonnes marquées prefetch=True du modèle, 51 colonnes de sale_order_line dans cette base, même si la boucle n'en utilise que quatre. Aucun résultat n'est une erreur : le recordset vide sale.order.line() se teste avec if lines:.

2. search_count : compter sans charger

search_count(domain, limit=None) rend un entier, calculé par PostgreSQL :

SOL.search_count([])
SOL.search_count([('order_id.state', '=', 'sale')])
SOL.search_count([], limit=10)
bool(SOL.search_count([('discount', '>', 0)], limit=1))
500 39 10 False

Le limit fixe un plafond : la requête devient SELECT COUNT(*) FROM (SELECT FROM "sale_order_line" LIMIT 10) t (figure 03 plus bas), et PostgreSQL s'arrête à la dixième ligne. Pour savoir s'il existe au moins un enregistrement, search_count(domaine, limit=1) ou search(domaine, limit=1) évitent de compter toute la table. len(SOL.search(domaine)) donne le même nombre, mais en ramenant tous les ids en Python : à éviter dès que seul le nombre compte.

3. search_read : des dictionnaires, le format des appels RPC

search_read(domain, fields, offset, limit, order) cherche et lit en un appel, et rend une liste de dictionnaires, un par enregistrement, avec la clé id en plus des champs demandés :

SOL.search_read([('order_id.state', '=', 'sale')], ['order_id', 'product_id', 'price_subtotal'], limit=2)
SOL.search_read([('order_id.state', '=', 'sale')], ['order_id', 'product_id', 'price_subtotal'], limit=2, load=None)
len(SOL.search_read([], limit=1)[0])
[{'id': 50, 'order_id': (24, 'S00024'), 'product_id': (19, "[E-COM06] Bureau d'angle avec siège à droite"), 'price_subtotal': 1990.0}, {'id': 48, 'order_id': (23, 'S00023'), 'product_id': (38, '[FURN_6667] Écrans anti-bruit (Noir)'), 'price_subtotal': 2950.0}] [{'id': 50, 'order_id': 24, 'product_id': 19, 'price_subtotal': 1990.0}, {'id': 48, 'order_id': 23, 'product_id': 38, 'price_subtotal': 2950.0}] 107
  • Un many2one arrive en couple (id, nom affiché). Ce nom n'est pas une colonne de la table : Odoo le calcule (display_name) sur la commande et sur l'article. Avec load=None, il ne reste que l'id. La mesure plus bas montre ce que coûte ce confort : 9 requêtes au lieu d'une pour 500 lignes.
  • Sans liste de champs, tous les champs : 107 clés pour une ligne de commande, champs calculés compris. Toujours passer fields.
  • C'est la méthode des clients externes. Une application qui interroge Odoo par l'API appelle le plus souvent search_read : le résultat se sérialise directement en JSON. Dans le code Python d'un module, un dictionnaire est rarement utile : on travaille sur des recordsets.

4. read : les mêmes dictionnaires, à partir d'un recordset

read(fields) produit le même format que search_read, mais sur des enregistrements déjà désignés, par browse ou par un search :

SOL.browse([1, 2]).read(['product_id', 'price_subtotal'])
SOL.browse([1, 2]).read(['prix'])
SOL.browse(99999).read(['name'])
[{'id': 1, 'product_id': (38, '[FURN_6667] Écrans anti-bruit (Noir)'), 'price_subtotal': 885.0}, {'id': 2, 'product_id': (6, '[FURN_8888] Lampe de bureau'), 'price_subtotal': 725.0}] ValueError: Invalid field 'prix' on 'sale.order.line' []

Un nom de champ inconnu lève ValueError (dernière ligne de la trace). Un id qui n'existe pas ne lève rien : il disparaît du résultat, ici une liste vide. search_read n'est d'ailleurs rien d'autre qu'un search_fetch suivi de la mise en forme de read (_read_format).

5. Mesurer : compter les requêtes

Le curseur tient un compteur, env.cr.sql_log_count, incrémenté à chaque requête quel que soit le niveau de journal (« simple query count is always computed », odoo/sql_db.py). La différence avant / après un appel donne son coût. Pour une comparaison honnête, on vide d'abord le cache des enregistrements avec env.invalidate_all() : sinon le deuxième essai trouve tout en mémoire. La figure mesure le même travail, lire quatre champs sur les 500 lignes, avec les méthodes vues plus haut et avec search_fetch et fetch, détaillées à la section suivante.

browse(i) dans une boucle500Un prefetch d'un seul id par ligne : une requête par ligne.
search([]) puis boucle2Les ids, puis 51 colonnes (id compris) pour les 500 lignes au premier accès.
search_fetch([], FIELDS) puis boucle1Ids et 4 colonnes dans la même requête ; la boucle lit le cache.

Les mêmes nombres sortent en superutilisateur (la console), avec l'administrateur et avec l'utilisateur de démonstration : sur ces lectures, les droits d'accès ne changent pas le compte.

La première mesure compte plus

Dans une console qui vient de démarrer, trois mesures successives du même search_read donnent [10, 9, 9]. La première remplit au passage des caches internes du registre, que invalidate_all() ne vide pas. Mesurer deux fois et garder la seconde valeur, ou faire un appel d'échauffement avant la série.

6. search_fetch et fetch : chercher et lire en une requête

search_fetch(domain, field_names, offset, limit, order) fait le travail de search et met en cache les champs demandés dans la même requête SQL. Il rend un recordset, comme search. fetch(field_names) fait la même chose sur un recordset qu'on a déjà : il ne lit que ce qui manque au cache.

FIELDS = ['order_id', 'product_id', 'product_uom_qty', 'price_subtotal']
lines = SOL.search_fetch([('order_id.state', '=', 'sale')], FIELDS)   # une requête, 4 colonnes + id
lines = SOL.search([('order_id.state', '=', 'sale')])
lines.fetch(FIELDS)                                                   # rien ne se passe si tout est déjà en cache

Deux différences avec search suivi d'une boucle : une requête au lieu de deux, et seulement les colonnes demandées (5 au lieu de 51 dans la mesure). Le second point compte quand le modèle porte de gros champs texte ou beaucoup de colonnes. Ces deux méthodes sont réservées au code Python : elles portent le décorateur @api.private, qui interdit leur appel par RPC. Depuis l'extérieur, l'équivalent est search_read.

fetch sert aussi de remède au motif qui coûte le plus cher : une boucle qui fait un browse par id. Chaque browse(i) a son propre prefetch, réduit à un id, donc une requête par ligne. Un fetch sur l'ensemble avant la boucle remplit le cache pour toutes (fonctions mesure et lire définies en figure 01) :

def lire_ligne_a_ligne():
    for i in ids:
        lire(SOL.browse(i))

def avec_fetch_avant():
    SOL.browse(ids).fetch(FIELDS)
    lire_ligne_a_ligne()

mesure(lire_ligne_a_ligne), mesure(avec_fetch_avant)
(500, 1)

Les champs non stockés sont calculés pendant l'appel

En Odoo 20, fetch et search_fetch acceptent un champ calculé non stocké et le calculent avant de rendre la main, pour tous les enregistrements. Le nom affiché d'une ligne de commande en est un : il assemble le numéro de commande, l'article et le client.

Premier appel : 15 requêtes pendant fetch (les lignes, puis les commandes, clients et articles nécessaires au calcul), puis 0 pendant la boucle, qui fait pourtant un browse par id. Second appel : on ne demande que les quatre champs stockés dont dépend display_name. Une requête pendant fetch, puis 1 727 pendant la boucle : chaque ligne calcule son nom seule, et va chercher seule sa commande, son article et ses variantes.

Venant de la 19

Dans la branche 19.0 publique, search_fetch se termine par return self._fetch_query(query, fields_to_fetch) et la documentation de fetch prévient : « Non-stored fields are mostly ignored, except for their stored dependencies ». Un champ non stocké demandé y est remplacé par ses dépendances stockées, puis laissé non calculé : c'est le second appel de la figure 02, reproduit ici sur la 20. Odoo 20 ajoute aux deux méthodes un bloc « force computation of fields » qui calcule le champ en lot avant de rendre la main. Le code n'a pas à changer ; il gagne surtout là où le recordset préparé est ensuite parcouru par morceaux. Autre ajout de la 20 : fetch découpe les très gros recordsets en requêtes de 10 000 ids.

8. name_search : chercher sur le nom affiché

name_search(name='', domain=None, operator='ilike', limit=100) est la recherche d'un champ many2one dans un formulaire : on tape un bout de nom, Odoo propose des couples (id, nom affiché).

env['product.product'].name_search('bureau', limit=3)
env['res.partner'].name_search('acme')
env['product.product'].name_search('bureau', domain=[('lst_price', '<', 200)], limit=3)
[(15, '[DESK0005] Bureau personnalisable (Blanc, Personnalisé)'), (18, '[DESK0006] Bureau personnalisable (Noir, Personnalisé)'), (19, "[E-COM06] Bureau d'angle avec siège à droite")] [(10, 'Acme Corporation'), (37, 'Acme Corporation, Addison Olson'), (20, 'Acme Corporation, Douglas Fletcher'), (21, 'Acme Corporation, Floyd Steward')] [(19, "[E-COM06] Bureau d'angle avec siège à droite"), (49, '[FURN_0001] Rangement de bureau'), (31, '[FURN_0269] Chaise de bureau noire')]

Dans le code d'Odoo 20, c'est un search_fetch sur le domaine ('display_name', operator, name) combiné au domaine passé, qui demande ['display_name'] : le nom est donc calculé pendant la recherche. Les contacts d'une société sortent avec elle (« Acme Corporation, Addison Olson ») parce que leur nom affiché contient celui de la société.

Récapitulatif

  • search ne lit que les ids ; le premier accès à un champ lit toutes les colonnes préchargées, pour tout le recordset.
  • search_count compte en base ; son limit plafonne le comptage.
  • search_read et read rendent des dictionnaires ; le nom des many2one coûte des requêtes, load=None les supprime.
  • search_fetch et fetch lisent les champs choisis en une requête ; réservés au code Python (@api.private).
  • En Odoo 20, ils calculent aussi les champs non stockés demandés, en lot : 15 + 0 requêtes au lieu de 1 + 1 727 sur le nom affiché de 500 lignes parcourues une à une.
  • Mesurer avec env.cr.sql_log_count après env.invalidate_all(), deux fois ; voir les requêtes avec --log-sql.
