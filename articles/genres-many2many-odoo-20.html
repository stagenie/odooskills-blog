Many2many en Odoo 20 : les genres d'un livre

Un livre peut être à la fois « Développement » et « Python » ; le genre « Python » regroupe plusieurs livres. Ni le Many2one ni le One2many ne savent dire ça. Le troisième type de relation le sait, et il le range dans une table que personne ne déclare — mais que tout le monde doit connaître.

~16 minutes de lecture · niveau intermédiaire · parcours Framework & ORM

Ce que tu vas apprendre

Déclarer

Un Many2many et sa table de relation, nommée dès le premier jour.

Écrire

Les commandes Command, dont une qui supprime plus qu'on ne croit.

Chercher

Filtrer et regrouper par genre, et lire correctement des totaux qui se recouvrent.

Prérequis

  • Le module biblio des articles précédents, en particulier le modèle Livre et la relation Many2one / One2many des exemplaires.
  • Le serveur Odoo 20 joignable sur http://localhost:8069, base biblio.
  • Un accès à psql sur la base, pour regarder ce que l'ORM a créé.

Une relation qui n'habite chez personne

Un Many2one est une colonne : library_copy.book_id pointe vers un livre. Un One2many n'est rien en base, c'est la lecture inverse de cette colonne. Un Many2many ne peut être ni l'un ni l'autre : un livre a plusieurs genres, il faudrait plusieurs colonnes ; un genre a plusieurs livres, idem. La relation vit donc dans une troisième table, une ligne par couple livre–genre.

1. Le modèle Genre

Un genre n'a besoin que d'un nom et d'une couleur, que les étiquettes réutiliseront. Crée models/library_genre.py :

from odoo import api, fields, models

class LibraryGenre(models.Model):
    _name = 'library.genre'
    _description = "Genre"
    _order = 'name'

    name = fields.Char(string="Nom", required=True)
    color = fields.Integer(string="Couleur")
    book_ids = fields.Many2many(
        'library.book',
        'library_book_genre_rel',
        'genre_id',
        'book_id',
        string="Livres",
    )
    book_count = fields.Integer(string="Nombre de livres", compute='_compute_book_count')

    _name_unique = models.Constraint(
        'UNIQUE(name)',
        "Ce genre existe déjà.",
    )

    @api.depends('book_ids')
    def _compute_book_count(self):
        for genre in self:
            genre.book_count = len(genre.book_ids)

Déclare-le dans models/__init__.py, et donne-lui sa ligne dans security/ir.access.csv — sans elle, le modèle existe mais personne ne peut le lire :

from . import library_book
from . import library_genre
from . import library_copy
...
access_library_genre_user,library.genre utilisateur,library.genre,base.group_user,crud,

Cette ligne est aussi permissive que les quatre autres : tout utilisateur interne peut tout faire. C'est le sujet du prochain article de la série ; pour l'instant, le modèle doit simplement être accessible.

2. Le champ Many2many et sa table

Côté livre, dans models/library_book.py :

    genre_ids = fields.Many2many(
        'library.genre',            # le modèle visé
        'library_book_genre_rel',   # la table de relation
        'book_id',                  # la colonne qui désigne « ce » livre
        'genre_id',                 # la colonne qui désigne le genre
        string="Genres",
    )

Compare avec le champ du genre, plus haut : même table, colonnes inversées. Pour le livre, book_id est « moi » et genre_id « l'autre » ; pour le genre, c'est l'inverse. L'ORM reconnaît les deux champs comme l'inverse l'un de l'autre, et ce qu'on écrit d'un côté se lit aussitôt de l'autre.

Mets le module à jour (version 20.0.1.6.0 dans le manifeste), puis regarde ce qui a été créé :

psql biblio -c '\d library_book_genre_rel'
colonnes book_id integer NOT NULL, genre_id integer NOT NULL clé primaire PRIMARY KEY (book_id, genre_id) index (genre_id, book_id) clés book_id → library_book(id) ON DELETE CASCADE genre_id → library_genre(id) ON DELETE CASCADE commentaire RELATION BETWEEN library_book AND library_genre colonne genre_ids dans library_book : 0

Quatre choses à retenir de ce tableau :

  • la clé primaire sur le couple interdit les doublons : un livre ne peut pas être deux fois « Python » ;
  • l'index inversé (genre_id, book_id) rend rapide la question « quels livres dans ce genre ? », la clé primaire servant déjà l'autre sens ;
  • les deux clés étrangères sont en cascade : supprimer un livre ou un genre efface ses lignes de relation, jamais l'enregistrement d'en face ;
  • library_book n'a aucune colonne genre_ids.

Et si on ne nomme pas la table ?

Les trois arguments sont facultatifs. fields.Many2many('library.genre') seul fonctionne : Odoo fabrique le nom à partir des deux tables, triées par ordre alphabétique, et les colonnes à partir des noms de table. Essai sur une base jetable, champs déclarés sans argument des deux côtés :

livre → library_book_library_genre_rel library_book_id library_genre_id genre → library_book_library_genre_rel library_genre_id library_book_id inverses reconnus : ['library.genre.book_ids']

Le tri alphabétique garantit que les deux côtés tombent sur la même table : ça marche. Alors pourquoi nommer ? Parce que le nom implicite est calculé, et que ce qui est calculé change quand on change le calcul.

Nommer la table après coup, c'est perdre les liens — sans un message

Même base jetable, trois liens posés avec les noms implicites. On passe aux noms explicites (library_book_genre_rel, book_id, genre_id) et on met à jour le module :

-u biblio : code de sortie 0, aucun WARNING, aucune ERROR Livre A → [] Livre B → [] table library_book_genre_rel lignes 0 table library_book_library_genre_rel lignes 3

Odoo a créé la nouvelle table, vide, et laissé l'ancienne en place avec les données. Rien n'est détruit, mais plus rien n'est visible, et aucune ligne du journal ne le signale. Il faut une reprise en SQL (INSERT … SELECT de l'ancienne table vers la nouvelle) dans un script de migration. D'où la règle : le nom de la table se choisit à la déclaration, et ne bouge plus.

Le nom implicite a une seconde limite. Deux Many2many du même modèle vers le même modèle — des « genres » et des « genres suggérés », par exemple — calculeraient la même table. L'ORM le refuse, et le serveur ne démarre pas :

TypeError: Many2many fields library.book.other_genre_ids and library.book.suggested_genre_ids use the same table and columns code de sortie 255

Cette panne-là est bruyante, donc sans danger. La réponse est la même : nommer explicitement au moins le second champ.

3. Des étiquettes dans les vues

Dans un formulaire, un Many2many affiché tel quel est une liste imbriquée. Pour une poignée de valeurs courtes, le widget many2many_tags est plus lisible. Dans le formulaire du livre :

<field name="genre_ids" widget="many2many_tags"
       options="{'color_field': 'color', 'no_create_edit': True}"/>
  • color_field désigne le champ entier du genre qui colore l'étiquette ;
  • no_create_edit retire l'entrée « Créer et modifier… » de la liste déroulante. Taper un genre inconnu reste possible (création rapide par son seul nom), mais on n'ouvre pas un formulaire complet au milieu de celui du livre.

Le même widget fonctionne dans la liste, avec la même option de couleur :

<field name="genre_ids" widget="many2many_tags" options="{'color_field': 'color'}"/>

Enfin un menu Configuration → Genres et une vue formulaire du genre, qui affiche l'autre côté de la relation — sans rien écrire de plus que le champ book_ids :

<notebook>
    <page string="Livres" name="books">
        <field name="book_ids">
            <list>
                <field name="title"/>
                <field name="author_id"/>
                <field name="copy_count"/>
            </list>
        </field>
    </page>
</notebook>

Le bouton « Ajouter une ligne » et la croix de chaque ligne écrivent eux aussi dans la table de relation. La croix retire le lien ; elle ne supprime pas le livre.

4. Écrire dans un Many2many : les commandes

En Python, une relation multiple ne s'écrit pas en remplaçant une valeur : on envoie une liste de commandes. La classe Command s'importe indifféremment de odoo ou de odoo.fields ; les deux formes cohabitent dans les modules standard de la 20.0.

from odoo import Command

livre.write({'genre_ids': [Command.link(dev.id), Command.link(ref.id)]})

Chaque commande essayée dans la console, sur le livre Développement Odoo : le guide technique :

CommandeEffetRésultat observé
Command.link(id)ajoute un lien['Développement', 'Référence']
Command.link(id) déjà liérien — la clé primaire l'interdit, l'ORM l'ignore['Développement', 'Référence']
Command.unlink(id)retire le lien, garde le genre['Développement'] · le genre existe encore
Command.set([ids])remplace tous les liens['Développement', 'Python', 'Référence']
Command.create({...})crée un genre et le lie['Brouillon']
Command.clear()retire tous les liens[] · le genre existe encore
Command.delete(id)supprime le genrele genre n'existe plus

unlink et delete ne sont pas synonymes

Le nom trompe : Command.unlink défait un lien, Command.delete supprime l'enregistrement visé, de la base, pour tous les livres qui l'avaient. Sur un One2many d'exemplaires, c'est souvent ce qu'on veut ; sur des genres partagés, c'est une suppression en masse déguisée. Relis chaque Command.delete d'un Many2many en te demandant si tu voulais vraiment effacer la chose, et pas seulement la retirer de ce livre.

Deux raccourcis valent Command.set : affecter une liste d'identifiants, ou un recordset.

livre.genre_ids = [python.id, dev.id]    # → ['Python', 'Développement']
livre.genre_ids = front | dev            # → ['Front-end', 'Développement']

Et l'autre côté suit sans qu'on y touche. Après ces écritures, faites toutes côté livre :

Développement → 3 livres Python → 2 livres Front-end → 1 livre Administration → 1 livre Référence → 2 livres lignes dans library_book_genre_rel : 9

5. Chercher et regrouper par genre

Dans un domaine, un Many2many se lit « au moins un de ses genres… ». Essais sur les quatre livres :

DomaineLivres trouvés
[('genre_ids', 'in', [python])]le guide technique, Python pour Odoo
[('genre_ids.name', '=', 'Référence')]le guide technique, Administrer un serveur
[('genre_ids', 'not in', [dev])]Administrer un serveur
[('genre_ids', '!=', dev)]Administrer un serveur
[('genre_ids', '=', False)]aucun — tous ont au moins un genre

Les deux négations méritent un arrêt : elles ne veulent pas dire « a un genre autre que Développement » — le guide technique en a deux autres — mais « n'a pas le genre Développement ». Et = False signifie « n'a aucun genre ».

La vue de recherche du livre gagne un champ, un filtre et un regroupement :

<search string="Livres">
    <field name="title"/>
    <field name="author_id"/>
    <field name="genre_ids"/>
    <filter name="filter_no_genre" string="Sans genre" domain="[('genre_ids', '=', False)]"/>
    <group>
        <filter name="group_genre" string="Genre" context="{'group_by': 'genre_ids'}"/>
    </group>
</search>

Des groupes qui se recouvrent

Les effectifs affichés font 3 + 2 + 1 + 1 + 2 = 9 pour 4 livres : chaque livre est compté une fois par genre. Même chose pour les sommes — le nombre de pages du groupe « Développement » additionne trois livres dont l'un figure aussi sous « Python » et « Référence ». Additionner les groupes entre eux n'a aucun sens. C'est vrai à l'écran comme dans _read_group côté Python, qui renvoie les mêmes effectifs.

6. Supprimer, copier

Supprimer le genre « Référence » (dans une transaction annulée ensuite) :

le guide technique → ['Développement', 'Python'] Administrer un serveur → ['Administration'] lignes dans library_book_genre_rel : 7 (9 avant)

Les deux livres restent, ils perdent seulement l'étiquette. C'est la cascade vue en SQL. Elle peut être durcie : posé sur genre_ids, ondelete='restrict' transforme la clé étrangère genre_id en ON DELETE RESTRICT, et supprimer un genre encore utilisé échoue (essai sur la base jetable : ForeignKeyViolation … library_book_genre_rel_genre_id_fkey). 'cascade' et 'restrict' sont les deux seules valeurs admises ; le cœur refuse toute autre valeur par une ValueError au chargement du modèle.

À la duplication d'un livre, les genres suivent : l'attribut copy d'un Many2many vaut True par défaut, et la copie reçoit les mêmes liens — pas de nouveaux genres.

copie → ['Développement', 'Python', 'Référence']

L'essai a fait apparaître au passage un autre défaut du module : copier un livre échoue sur la contrainte d'unicité de l'ISBN, qui n'est pas marqué copy=False. La copie de la sonde a donc été faite avec livre.copy({'isbn': False}). C'est à retenir pour tout champ unique : sans copy=False, le bouton « Dupliquer » devient une erreur.

v19 → v20 : la déclaration ne change pas

Arguments, nommage implicite, garde contre deux tables identiques, commandes : le code de déclaration du champ est le même qu'en 19, à deux commentaires près. Ce qui a été réécrit, c'est la mécanique interne de lecture et d'écriture de la relation. Son comportement face aux droits d'accès — que voit un utilisateur à qui l'on cache les genres ? — se mesure dans l'article suivant.

Récapitulatif

  • Un Many2many vit dans une table de relation : clé primaire sur le couple, index inversé, deux clés étrangères en cascade.
  • Les deux côtés déclarent la même table avec les colonnes inversées ; l'ORM les relie.
  • Le nom implicite marche, mais changer de nom après coup crée une table vide et laisse les liens dans l'ancienne, sans message.
  • Deux Many2many implicites vers le même modèle empêchent le serveur de démarrer.
  • Command.unlink retire un lien, Command.delete supprime l'enregistrement.
  • Dans un domaine, not in et != veulent dire « n'a pas ce genre ».
  • Regrouper par un Many2many compte un enregistrement dans chacun de ses groupes.

Le module compte maintenant cinq modèles, et tout utilisateur interne peut tout y faire, y compris supprimer un livre. L'article suivant pose de vrais droits : deux profils, et une sécurité qui en Odoo 20 ne s'écrit plus comme avant.
