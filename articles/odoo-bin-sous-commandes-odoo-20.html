odoo-bin en Odoo 20 : toutes les sous-commandes et options utiles

odoo-bin ne sert pas qu'à lancer le serveur : seize sous-commandes copient une base, la neutralisent, réécrivent un module, comptent les lignes de code. Voici la liste réelle d'Odoo 20, les options du serveur qui comptent vraiment, et ce qui a bougé depuis la 19 : populate a changé de sens, -s a disparu et le serveur n'écoute plus que la machine locale.

~13 minutes de lecture · niveau intermédiaire · parcours Infrastructure

Ce que tu vas apprendre

Lister

odoo-bin help, le rôle de chaque sous-commande et d'où viennent celles qu'apportent les modules.

Configurer

Les options du serveur à connaître : -c, -d, --addons-path, --http-interface, --workers, --dev, --save.

Migrer ses scripts

Ce qui casse en passant de la 19 à la 20 : populate devenu duplicate, -s retiré, écoute sur 127.0.0.1.

Prérequis

  • Un Odoo 20 installé depuis les sources, avec son fichier odoo.conf : voir Installer Odoo 20 sur un serveur Ubuntu.
  • Une base de démonstration, appelée ici ma_base (Ventes et Inventaire, en français). Les commandes qui écrivent en base n'ont été lancées que sur une base jetable : fais de même.
  • Les commandes partent du dossier des sources, d'où ./odoo-bin. Dans une installation par paquet, la commande s'appelle odoo et accepte les mêmes arguments.

1. odoo-bin help : la liste réelle

Le premier mot après odoo-bin choisit la sous-commande. Sans lui, c'est server : ./odoo-bin -c odoo.conf et ./odoo-bin server -c odoo.conf font la même chose. ./odoo-bin -h seul, sans sous-commande, affiche la liste :

./odoo-bin help
./odoo-bin --version            # Odoo Server 20.0
./odoo-bin server --help        # toutes les options du serveur
./odoo-bin db --help            # les options d'une sous-commande

Quatorze sous-commandes vivent dans le cœur (odoo/cli/*.py). Les deux autres sont apportées par des modules : odoo-bin parcourt les chemins des modules à la recherche de fichiers <module>/cli/<commande>.py. genproxytoken vient de iot_drivers (boîtier IoT), populate du module populate. Elles apparaissent dès que le module est sur le disque, installé ou non dans la base.

Une sous-commande dans ton propre module

Le même mécanisme t'est ouvert. Un fichier cli/bonjour.py dans un module :

from odoo.cli import Command


class Bonjour(Command):
    """Dit bonjour (exemple de sous-commande apportée par un module)"""

    def run(self, cmdargs):
        print("Bonjour depuis ma_bibli :", cmdargs)

Le nom du fichier doit être celui de la commande (la classe Bonjour donne bonjour), et la docstring devient la ligne d'aide. Encore faut-il que odoo-bin trouve le module : il ne lit pas le odoo.conf pour cela, seulement un --addons-path= placé avant la sous-commande :

./odoo-bin --addons-path=mes_addons bonjour a b
./odoo-bin bonjour
Bonjour depuis ma_bibli : ['a', 'b'] Unknown command 'bonjour'. Use 'odoo-bin --help' to see the list of available commands.

Le mécanisme existait déjà en 19. Ce qui change en 20 : un module dont la commande ne s'importe pas affiche « Couldn't load » et la trace, là où la 19 l'ignorait sans un mot.

2. server : les options qui servent vraiment

./odoo-bin server --help affiche près de 90 options. La plupart ont leur équivalent dans odoo.conf (tirets remplacés par des soulignés : --http-port devient http_port) ; une option passée en ligne de commande l'emporte sur le fichier. Celles-ci reviennent tous les jours :

OptionEffet
-c odoo.confFichier de configuration. Sans lui, Odoo lit ~/.odoorc.
-d ma_baseLa base à charger (et la seule que voient les tâches planifiées de ce serveur).
--addons-path=a,bDossiers des modules, séparés par des virgules ; les modules du cœur sont ajoutés d'office.
-i mod / -u modInstaller / mettre à jour, avec --stop-after-init (ou sa forme courte --stop, nouvelle en 20) : détaillé dans l'article sur les modules en ligne de commande.
-p 8069, --http-portPort HTTP ; --gevent-port (8072) pour le port des websockets en mode multi-processus.
--http-interfaceAdresse d'écoute. Défaut 127.0.0.1 en 20 (voir plus bas).
--no-httpAucun service HTTP : pour une commande ponctuelle à côté d'un service en marche.
--workers=NMode multi-processus (production) ; 0 = un seul processus à fils (développement).
--proxy-modeDerrière Nginx : lire les en-têtes X-Forwarded-* (Mettre Odoo 20 en HTTPS avec Nginx).
--db-filter=^ma_base$Bases visibles depuis le navigateur (expression régulière).
--no-database-listMasque le sélecteur et le gestionnaire de bases.
--log-level, --log-handler, --logfileLe journal ; ses options font l'objet d'un prochain article de cette série.
--dev=reload,xmlFonctions de développement (tableau ci-dessous).
--saveÉcrit la configuration du moment dans le fichier -c (ou ~/.odoorc).

--http-interface : 127.0.0.1 par défaut

Sans --http-interface ni http_interface dans le fichier, Odoo 20 n'écoute que la machine elle-même. Depuis un autre poste, rien ne répond :

Derrière Nginx sur la même machine, c'est exactement ce qu'il faut. Pour un serveur joint directement par IP:port, ou un conteneur Docker dont le port est publié, écris l'adresse dans le fichier :

[options]
http_interface = 0.0.0.0

--dev : les valeurs acceptées

ValeurEffet
reloadRedémarre le serveur quand un fichier Python change.
xmlLit les vues depuis les fichiers XML plutôt que depuis la base : une vue modifiée s'affiche sans -u.
qwebÉcrit dans le journal le code compilé d'un gabarit QWeb en erreur.
accessÉcrit la trace complète des erreurs d'accès.
replicaSimule une base répliquée en lecture seule.
allaccess,reload,qweb,xml (pas replica).

Ces valeurs sont les mêmes qu'en 19. --dev= (vide) annule un dev_mode écrit dans le fichier : pratique pour lancer un second serveur sans surveillance des fichiers.

--save : générer un odoo.conf

Avec un -c qui n'existe pas encore, --save crée le fichier (sans lui, Odoo refuse un fichier absent) :

./odoo-bin -c essai.conf --save --addons-path=odoo/addons --db_host=localhost \
    --db_port=5433 --db_user=odoo --http-port=9134 --stop-after-init --no-http
[options] addons_path = …/odoo/addons admin_passwd = admin … http_enable = False http_interface = 127.0.0.1 http_port = 9134 … workers = 0 x_sendfile = False [colors] pid = never …

84 lignes : toutes les options, défauts compris, et une section [colors] (couleurs du journal) qui n'existait pas en 19.

Ce que --save enregistre aussi

  • Les options de la commande elle-même. Le --no-http ci-dessus est devenu http_enable = False : un serveur relancé avec ce fichier charge la base, démarre ses tâches planifiées… et n'ouvre aucun port. Le journal ne contient alors aucune ligne HTTP service running. Retire la ligne, ou génère le fichier sans --no-http.
  • admin_passwd = admin : le mot de passe maître par défaut, en clair. Remplace-le avant toute mise en service.

3. Une ligne par sous-commande

Pour chacune : à quoi elle sert et la forme qu'on tape. Les options propres d'une sous-commande se placent après son nom.

Sous-commandeSert àExemple
shellConsole Python sur une base (env, self) ; voir Le shell Odoo 20. ./odoo-bin shell -c odoo.conf -d ma_base --no-http
moduleInstaller, mettre à jour, désinstaller, lister ; voir les modules en ligne de commande. ./odoo-bin module install sale -c odoo.conf -d ma_base
dbGestionnaire de bases sans navigateur : init, dump, load, duplicate, rename, drop, filestore compris. ./odoo-bin db -c odoo.conf dump ma_base ma_base.zip
neutralizeNeutraliser une copie de production (courriels, tâches, paiements…). --stdout affiche le SQL sans l'appliquer. ./odoo-bin neutralize -c odoo.conf -d ma_copie
duplicateMultiplier les enregistrements existants pour tester les volumes. ./odoo-bin duplicate -c odoo.conf -d ma_copie --models res.partner --factors 10
populateGénérer des données de synthèse d'après un « blueprint » ; exige le module populate installé. ./odoo-bin populate -c odoo.conf -d ma_copie -b <blueprint>
obfuscateChiffrer des colonnes (noms, courriels, téléphones…) avec un mot de passe ; demande deux confirmations, sauf -y. Odoo prévient : pas une anonymisation sûre. ./odoo-bin obfuscate -c odoo.conf -d ma_copie --pwd=…
scaffoldSquelette de module (gabarits default et theme). ./odoo-bin scaffold ma_bibli mes_addons
upgrade_codeRéécrire automatiquement le code d'un module pour la nouvelle version (exemple plus bas). ./odoo-bin upgrade_code --addons-path=mes_addons --script 19.4-00-ir-access --dry-run
i18nExporter un .pot/.po, en importer un, charger une langue. ./odoo-bin i18n export -c odoo.conf -d ma_base ma_bibli
clocCompter les lignes de code d'un dossier, ou du seul code spécifique installé dans une base. ./odoo-bin cloc -p mes_addons/ma_bibli
deployEnvoyer un module à un serveur distant, qui doit avoir base_import_module. ./odoo-bin deploy mes_addons/ma_bibli https://exemple.com --db ma_base
startLancer vite un projet : base au nom du dossier, créée si besoin, --db-filter posé. ./odoo-bin start --path mes_addons
genproxytokenJeton d'accès du proxy IoT, écrit dans le fichier de configuration. ./odoo-bin genproxytoken -c odoo.conf

Copier la production en base de test (db et neutralize) et produire des données en masse (duplicate et populate) ont chacun leur article dans cette série.

cloc donne une mesure rapide du code à maintenir. Sur un squelette fraîchement créé, puis sur la base de démonstration, qui ne contient que des modules standard :

./odoo-bin cloc -p mes_addons/ma_bibli
./odoo-bin --addons-path=odoo/addons cloc -c odoo.conf -d ma_base

4. upgrade_code : réécrire un module, à blanc d'abord

C'est la sous-commande qui a le plus grossi : 9 scripts de réécriture dans la 19.0, 18 dans la 20.0 (conversion des droits ir.model.access vers ir.access, t-call, ormcache, OWL 3…). Exemple : un squelette généré par scaffold contient encore un security/ir.model.access.csv, format qu'Odoo 20 ne charge plus. Une fois la ligne du manifeste décommentée, le script 19.4-00-ir-access le convertit :

./odoo-bin upgrade_code --addons-path=mes_addons --script 19.4-00-ir-access \
    --glob 'ma_bibli/**/*' --dry-run
echo $?
updated: …/mes_addons/ma_bibli/__manifest__.py updated: …/mes_addons/ma_bibli/security/ir.access.csv deleted: …/mes_addons/ma_bibli/security/ir.model.access.csv 1

--dry-run liste sans rien écrire ; le code de sortie vaut 1 quand des fichiers changeraient, 0 sinon. Relance sans --dry-run pour appliquer, de préférence dans un dépôt git propre.

upgrade_code parcourt aussi les sources d'Odoo

Les modules du cœur sont ajoutés d'office aux chemins parcourus. Sans --glob, --from 19.4 --dry-run annonce « updated: …/odoo/addons/l10n_id_efaktur_coretax/… » : appliqué, il modifierait Odoo lui-même. Et --from 19.0 s'arrête sur KeyError: 'ar_base' dans le script 19.3-00-account-groups, qui cherche des plans comptables. Cible toujours tes modules avec --glob et préfère --script à --from.

5. Ce qui a changé depuis la 19

Comparaison faite contre la branche 19.0 publique du 7 octobre 2026 : fichiers odoo/cli/, commandes apportées par les modules et options de tools/config.py.

populate n'est plus la même commande

En 19, odoo-bin populate --models … --factors … dupliquait les données existantes. En 20, ce code s'appelle duplicate, avec les mêmes options, et le nom populate est repris par le module du même nom, qui génère des données de synthèse. Un script de la 19 échoue donc :

Dans un script, remplace populate par duplicate sans toucher aux options.

Venant de la 19

  • populate (duplication) → duplicate ; populate = données de synthèse, module populate à installer.
  • -s n'existe plus : ./odoo-bin -s … répond « no such option: -s ». Écris --save.
  • --http-interface vaut 127.0.0.1 par défaut (la 19 écoutait sur 0.0.0.0 et prévenait du changement dans son journal).
  • Nouvelles options : --stop (alias de --stop-after-init), --unsafe-policy, --db-system ; section [colors] dans un fichier généré par --save.
  • module list et --dry-run pour odoo-bin module.
  • scaffold perd le gabarit l10n_payroll ; upgrade_code passe de 9 à 18 scripts.
  • Inchangés : shell, db, neutralize, obfuscate, i18n, cloc, deploy, start gardent leurs options, comme les valeurs de --dev.

Récapitulatif

  • Odoo 20 compte seize sous-commandes : quatorze dans le cœur, genproxytoken et populate apportées par des modules.
  • Un module peut ajouter la sienne (cli/<nom>.py), trouvée seulement avec --addons-path= en tête.
  • Le serveur n'écoute plus que 127.0.0.1 par défaut : à régler pour un accès direct par le réseau.
  • --save écrit tout, y compris --no-http et le mot de passe maître par défaut.
  • populate de la 19 s'appelle duplicate ; -s a disparu.
  • upgrade_code s'essaie avec --dry-run et se limite à tes modules avec --glob.
