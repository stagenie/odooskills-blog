Cache et SQL en Odoo 20 : flush, invalidate et env.cr.execute avec SQL

L'ORM garde en mémoire ce qu'il a lu et retarde ce qu'il écrit. Tant qu'on passe par lui, c'est invisible. Dès qu'une requête SQL écrite à la main s'en mêle, elle peut lire une valeur périmée, ou laisser l'ORM en lire une. Quand faire flush, quand faire invalidate, comment écrire la requête avec l'objet SQL, et ce qui casse en venant de la 19.

~13 minutes de lecture · niveau avancé · parcours Framework & ORM

Ce que tu vas apprendre

Comprendre

Ce que contient le cache de l'ORM, pourquoi une écriture n'arrive pas tout de suite en base, et comment le mesurer avec env.cr.sql_log_count.

Synchroniser

flush_recordset avant une lecture SQL, invalidate_recordset après une écriture SQL, modified pour les champs calculés, to_flush= pour ne plus y penser.

Migrer

SQL.code, SQL.params et env.flush_query disparus, env.cache déprécié : les messages exacts et leur remplacement.

Prérequis

  • Une base Odoo 20 de test avec les données de démonstration, Ventes et Inventaire installés. Les exemples lisent et modifient le contact « Acme Corporation » (id 10) et la commande S00001 (id 1) de la démo ; chaque script se termine par env.cr.rollback() : rien n'est enregistré.
  • La console odoo-bin shell, à qui chaque script est passé par < (d'où les print()) : elle est présentée dans l'article sur le shell Odoo 20.
  • Savoir lire une requête SQL simple (SELECT, UPDATE).

1. Le cache de l'ORM : lire une fois, écrire plus tard

Chaque transaction (un curseur, donc une requête HTTP ou une session de console) possède un cache de valeurs de champs, partagé par tous les recordsets qui en sont issus. Deux règles le gouvernent :

  • En lecture, un champ absent du cache déclenche un SELECT qui charge d'un coup tous les champs stockés « préchargeables » du modèle, pour tous les enregistrements du lot. Les lectures suivantes ne coûtent plus rien.
  • En écriture, record.champ = valeur (ou write()) met la valeur dans le cache et la marque en attente. L'UPDATE part plus tard, d'un bloc : c'est le flush.

Le compteur env.cr.sql_log_count (nombre de requêtes exécutées par ce curseur) rend la première règle visible :

p = env['res.partner'].browse(10)
env.invalidate_all()
n = env.cr.sql_log_count
print(p.name, '|', p.city)
print('requêtes :', env.cr.sql_log_count - n)
n = env.cr.sql_log_count
print(p.name, '|', p.city, '|', p.email)
print('requêtes :', env.cr.sql_log_count - n)
p.invalidate_recordset(['city'])
n = env.cr.sql_log_count
print(p.city)
print('requêtes :', env.cr.sql_log_count - n)
Acme Corporation | Pleasant Hill requêtes : 1 Acme Corporation | Pleasant Hill | acme_corp@yourcompany.example.com requêtes : 0 Pleasant Hill requêtes : 1

Une requête pour lire le nom et la ville, aucune pour relire les deux et y ajouter l'adresse électronique : elle était dans le même SELECT. Après invalidate_recordset, la ville est oubliée et la lecture suivante retourne en base.

Pour l'écriture, il suffit d'observer les requêtes passées par odoo.sql_db au niveau DEBUG : p.city = 'Lyon' sur Acme Corporation en lance une vingtaine, toutes des SELECT (droits, champs liés, contacts enfants à synchroniser), et aucun UPDATE. L'UPDATE n'apparaît qu'au flush.

Tant que tout passe par l'ORM, ce décalage est sans conséquence : avant chacune de ses propres requêtes (search, _read_group, search_fetch…), l'ORM écrit lui-même les champs dont la requête dépend. Le problème ne naît qu'avec le SQL écrit à la main, dans un sens ou dans l'autre.

2. Le SQL qui lit une valeur pas encore écrite : flush

Premier cas : le code modifie un enregistrement par l'ORM, puis lit la table avec env.cr.execute. Le curseur interroge la base, et la base ne connaît pas encore la nouvelle valeur :

p = env['res.partner'].browse(10)
p.city = 'Lyon'
print('ORM :', p.city)
env.cr.execute("SELECT city FROM res_partner WHERE id = %s", [p.id])
print('SQL avant flush :', env.cr.fetchone())
p.flush_recordset(['city'])
env.cr.execute("SELECT city FROM res_partner WHERE id = %s", [p.id])
print('SQL après flush :', env.cr.fetchone())
env.cr.rollback()
ORM : Lyon SQL avant flush : ('Pleasant Hill',) SQL après flush : ('Lyon',)

Trois portées pour la même opération, de la plus fine à la plus large :

AppelCe qui part en base
records.flush_recordset(['city'])au moins les champs cités de ces enregistrements, recalculs compris (sans argument : tous leurs champs en attente) ; l'ORM peut en écrire davantage dans le même UPDATE
env['res.partner'].flush_model(['city'])au moins les champs cités, pour tous les enregistrements du modèle
env.flush_all()tout ce qui est en attente dans la transaction, recalculs compris

Avant une requête qui lit plusieurs tables, flush_model sur chacune (avec les seuls champs lus) suffit ; flush_all() est le filet de sécurité, plus coûteux.

Les champs calculés stockés aussi attendent

Le piège est plus sournois avec un champ calculé stocké : modifier une quantité de ligne ne recalcule pas tout de suite le total de la commande en base. L'ORM le recalcule à la lecture, en mémoire ; la colonne amount_total garde l'ancienne valeur jusqu'au flush :

from odoo.tools import SQL
so = env['sale.order'].browse(1)
line = so.order_line[0]
print(so.name, so.amount_total, '| ligne', line.product_uom_qty, 'x', line.price_unit)
line.product_uom_qty += 1
print('ORM :', so.amount_total)
print('SQL brut :', env.execute_query(SQL("SELECT amount_total FROM sale_order WHERE id = %s", so.id)))
print('SQL to_flush :', env.execute_query(SQL("SELECT amount_total FROM sale_order WHERE id = %s", so.id,
                                             to_flush=so._fields['amount_total'])))
env.cr.rollback()
S00001 2001.0 | ligne 3.0 x 295.0 ORM : 2340.25 SQL brut : [(2001.0,)] SQL to_flush : [(2340.25,)]

Une unité de plus à 295 (prix hors taxe), taxe de 15 % comprise : 2 001 + 339,25 = 2 340,25. La requête brute lit encore 2 001. La seconde déclare qu'elle dépend du champ amount_total (to_flush=) : env.execute_query l'écrit en base avant d'exécuter, et la lecture est juste.

to_flush : laisser la requête dire de quoi elle dépend

C'est exactement le mécanisme qu'utilise l'ORM pour ses propres requêtes : chaque colonne stockée qu'il place dans une requête est un SQL.identifier(..., to_flush=champ) (odoo/orm/fields.py). Mais la déclaration ne sert qu'à env.execute_query ; env.cr.execute l'ignore :

from odoo.tools import SQL
Partner = env['res.partner']
p = Partner.browse(10)
p.city = 'Lyon'
print('search :', Partner.search([('city', '=', 'Lyon'), ('id', '=', 10)]))
p.city = 'Nantes'
q = SQL("SELECT city FROM res_partner WHERE id = %s", p.id)
env.cr.execute(q)
print('cr.execute(SQL) :', env.cr.fetchall())
q = SQL("SELECT city FROM res_partner WHERE id = %s", p.id, to_flush=Partner._fields['city'])
env.cr.execute(q)
print('cr.execute(SQL, to_flush) :', env.cr.fetchall())
print('env.execute_query :', env.execute_query(q))
env.cr.rollback()
search : res.partner(10,) cr.execute(SQL) : [('Lyon',)] cr.execute(SQL, to_flush) : [('Lyon',)] env.execute_query : [('Nantes',)]
  • search trouve Acme Corporation à Lyon alors que rien n'a été écrit à la main : l'ORM a flushé city avant sa requête. Effet de bord : « Lyon » est maintenant en base.
  • « Nantes » est ensuite écrit dans le cache seulement. Les deux env.cr.execute lisent « Lyon », avec ou sans to_flush.
  • env.execute_query flushe les champs déclarés, puis exécute : « Nantes ».

D'où la règle pratique : pour une requête de lecture écrite à la main, passer par env.execute_query (ou env.execute_query_dict pour des dictionnaires) et déclarer ses champs en to_flush, plutôt que env.cr.execute suivi d'un flush qu'on finit par oublier.

3. Le SQL qui écrit, l'ORM qui relit l'ancienne valeur : invalidate

Cas inverse : un UPDATE écrit en SQL modifie la base, mais le cache garde la valeur qu'il avait lue. Tout code qui passe ensuite par l'ORM dans la même transaction travaille sur l'ancienne :

from odoo.tools import SQL
p = env['res.partner'].browse(10)
print('ORM avant :', p.city)
env.cr.execute(SQL("UPDATE res_partner SET city = %s WHERE id = %s", 'Lyon', p.id))
print('lignes modifiées :', env.cr.rowcount)
print('ORM après UPDATE :', p.city)
p.invalidate_recordset(['city'])
print('ORM après invalidate :', p.city)
env.cr.rollback()
ORM avant : Pleasant Hill lignes modifiées : 1 ORM après UPDATE : Pleasant Hill ORM après invalidate : Lyon

Mêmes portées que pour le flush : records.invalidate_recordset(['city']), env['res.partner'].invalidate_model(['city']) (le bon choix après un UPDATE qui touche un nombre inconnu de lignes), env.invalidate_all().

Piège : invalidate(flush=False) jette les écritures en attente

Les trois méthodes d'invalidation font d'abord un flush, par défaut. Le paramètre flush=False le supprime : une valeur écrite par l'ORM et pas encore en base est alors perdue, sans erreur.

p = env['res.partner'].browse(10)
p.city = 'Lyon'
p.invalidate_recordset(['city'], flush=False)
print('flush=False :', p.city)
env.flush_all()
env.cr.execute("SELECT city FROM res_partner WHERE id = 10")
print('en base :', env.cr.fetchone())
env.cr.rollback()
p = env['res.partner'].browse(10)
p.city = 'Lyon'
p.invalidate_recordset(['city'])
print('flush=True :', p.city)
env.cr.rollback()
flush=False : Pleasant Hill en base : ('Pleasant Hill',) flush=True : Lyon

Même un flush_all() ultérieur n'écrit plus « Lyon ». Ne passer flush=False que si l'on sait qu'aucune écriture n'est en attente sur ces champs.

Les champs calculés ne suivent pas un UPDATE SQL

Invalider le cache suffit pour relire la colonne modifiée. Mais les champs calculés stockés qui en dépendent ne sont recalculés que lorsque l'ORM apprend la modification. Un UPDATE de quantité en SQL laisse le sous-total et le total faux :

from odoo.tools import SQL
so = env['sale.order'].browse(1)
line = so.order_line[0]
print(so.amount_total, line.price_subtotal)
env.cr.execute(SQL("UPDATE sale_order_line SET product_uom_qty = product_uom_qty + 1 WHERE id = %s", line.id))
env.invalidate_all()
print(line.product_uom_qty, line.price_subtotal, so.amount_total)
env.cr.rollback()
2001.0 885.0 4.0 885.0 2001.0

Quatre articles, mais un sous-total de trois (885 = 3 × 295). Pour que l'ORM recalcule, il faut lui signaler la modification avec modified(), après l'invalidation :

from odoo.tools import SQL
so = env['sale.order'].browse(1)
line = so.order_line[0]
print(so.amount_total, line.price_subtotal)
env.cr.execute(SQL("UPDATE sale_order_line SET product_uom_qty = product_uom_qty + 1 WHERE id = %s", line.id))
line.invalidate_recordset(['product_uom_qty'])
line.modified(['product_uom_qty'])
print(line.product_uom_qty, line.price_subtotal, so.amount_total)
env.cr.rollback()
2001.0 885.0 4.0 1180.0 2340.25

modified(['product_uom_qty']) marque à recalculer tout ce qui en dépend, de proche en proche : le sous-total de la ligne (1 180), puis le total de la commande (2 340,25). Ce qui reste hors de portée du SQL brut, en revanche : les droits d'accès, les contraintes Python, le suivi dans le chatter, les surcharges de write() des autres modules. Aucun n'est appelé.

4. L'objet SQL : paramètres, identifiants, assemblage

from odoo.tools import SQL enveloppe un morceau de requête et ses paramètres. Il se passe tel quel à env.cr.execute ou env.execute_query, et surtout il se compose : un SQL peut en contenir d'autres, leurs paramètres suivent sans qu'on ait à les recoller.

from odoo.tools import SQL
Partner = env['res.partner']
col = 'city'
q = SQL(
    "SELECT %s, count(*) FROM %s WHERE %s = %s GROUP BY 1 ORDER BY 2 DESC, 1 LIMIT 3",
    SQL.identifier(col), SQL.identifier(Partner._table),
    SQL.identifier('res_partner', 'is_company'), True,
)
print(q)
print(env.execute_query(q))
filtre = SQL(" AND ").join([SQL("active"), SQL("name ILIKE %s", '%acme%')])
q2 = SQL("SELECT id, name FROM res_partner WHERE %(f)s ORDER BY id", f=filtre)
print(env.execute_query_dict(q2))
try:
    SQL.identifier('city; DROP TABLE res_partner')
except AssertionError as e:
    print('AssertionError', e)
SQL('SELECT "city", count(*) FROM "res_partner" WHERE "res_partner"."is_company" = %s GROUP BY 1 ORDER BY 2 DESC, 1 LIMIT 3', True) [('Tracy', 2), ('Fremont', 1), ('Pleasant Hill', 1)] [{'id': 10, 'name': 'Acme Corporation'}] AssertionError 'city; DROP TABLE res_partner' invalid for SQL.identifier()
ÉcritureRôle
SQL("… %s …", valeur)Une valeur : elle reste un paramètre, jamais collée dans le texte (le repr le montre : %s + True à part).
SQL("… %(nom)s …", nom=valeur)Même chose avec des noms ; positionnels et nommés ne se mélangent pas.
SQL.identifier(table), SQL.identifier(table, colonne)Un nom de table ou de colonne, mis entre guillemets et contrôlé : un nom qui n'est pas un identifiant lève AssertionError.
Un SQL passé en argumentInséré tel quel, avec ses paramètres.
SQL(" AND ").join([...])Assemble une liste de conditions ou de valeurs avec un séparateur.
to_flush=champ (ou liste de champs)Champs à écrire en base avant exécution, lu par env.execute_query.

Piège : le texte du SQL doit être une constante

L'objet SQL ne protège que si son premier argument est un texte littéral. SQL(f"… WHERE name = '{nom}'") fabrique une injection SQL parfaitement valide. Les valeurs passent en %s, les noms de tables et de colonnes en SQL.identifier(), et le caractère % s'écrit %% dans le texte (LIKE 'a%%'), même sans paramètre. Le motif '%acme%' de l'exemple, lui, est un paramètre : pas d'échappement.

5. Ce qui casse en venant de la 19

L'usage de SQL décrit plus haut fonctionne à l'identique en 19 et en 20. Ce qui change, ce sont les accès à l'intérieur de l'objet, qu'un module 19 utilise parfois pour journaliser une requête ou la passer à une autre bibliothèque. Le script suivant les essaie un par un sur Odoo 20 :

import warnings
from odoo.tools import SQL
q = SQL("SELECT id FROM res_partner WHERE id = %s", 10)
for essai in ("q.code", "q.params", "q.to_flush"):
    try:
        eval(essai)
    except AttributeError as e:
        print(essai, '->', type(e).__name__, e)
try:
    code, params = q
except TypeError as e:
    print('code, params = q ->', type(e).__name__, e)
print(q._sql_tuple)
try:
    env.cr.execute(q, [10])
except AssertionError as e:
    print('cr.execute(q, [10]) ->', type(e).__name__, e)
p = env['res.partner'].browse(10)
with warnings.catch_warnings(record=True) as w:
    warnings.simplefilter('always')
    env.cache.invalidate([(p._fields['city'], [p.id])])
print('env.cache ->', w[0].category.__name__, w[0].message)
print(env.cr.mogrify(q))
try:
    env.flush_query(q)
except AttributeError as e:
    print('env.flush_query ->', type(e).__name__, e)

Le contenu reste lisible en 20 par q._sql_tuple (texte, paramètres, champs à flusher), mais c'est un attribut privé : du code de module ne devrait pas en dépendre. flush_recordset, flush_model, invalidate_recordset, invalidate_model et modified, eux, ont gardé leur signature de la 19.

Venant de la 19 : SQL ne se lit plus de l'extérieur

En 19, odoo.tools.SQL exposait trois propriétés publiques, code, params et to_flush, et se laissait encore dépaqueter (code, params = sql) avec un DeprecationWarning: Deprecated since 19.0, use code and params properties directly. env.execute_query s'appuyait sur une méthode publique env.flush_query(sql). En 20, SQL(...) rend un LiteralSQL qui ne garde que _sql_tuple : les trois propriétés, le dépaquetage et flush_query ont disparu, et env.cache émet un DeprecationWarning. Chercher .code, .params, .to_flush et flush_query sur les objets SQL de tout module porté.

6. Quand le SQL brut vaut le coup

Le SQL écrit à la main contourne tout ce que fait l'ORM : droits d'accès, règles multi-sociétés, contraintes Python, recalculs (sauf modified), suivi, surcharges. Il se justifie quand ce contournement est voulu ou quand l'ORM n'a pas d'équivalent :

BesoinD'abordSQL brut si…
Sommes, comptages, regroupements_read_group (voir read_group en Odoo 20)jointure ou fonction de fenêtre que _read_group n'exprime pas
Lire vite beaucoup de lignessearch_fetch avec la liste des champs (voir search, search_read, search_fetch, fetch)le nombre de requêtes mesuré reste trop élevé
Modifier des milliers de lignesrecords.write(vals) en une fois (un seul UPDATE au flush)migration ou correctif ponctuel, sans logique métier à déclencher : UPDATE, puis invalidate_model et modified si des calculés en dépendent
Verrouiller une ligne—SELECT … FOR UPDATE NOWAIT, cas classique du SQL brut

Dans tous les cas, mesurer avant d'optimiser : env.cr.sql_log_count autour du code suspect, ou l'option --log-sql pour voir les requêtes elles-mêmes.

Récapitulatif

  • L'ORM lit par lots et garde en cache ; il écrit dans le cache et reporte l'UPDATE au flush. Ses propres requêtes flushent ce dont elles dépendent.
  • SQL qui lit après l'ORM : flush avant, ou to_flush= avec env.execute_query ; env.cr.execute ne flushe jamais.
  • SQL qui écrit avant l'ORM : invalidate après, modified si des calculés stockés en dépendent ; jamais flush=False à l'aveugle.
  • En 20, l'objet SQL ne se lit plus par .code / .params, env.flush_query a disparu et env.cache est déprécié.
