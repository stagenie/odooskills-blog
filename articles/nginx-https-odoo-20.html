Mettre Odoo 20 en HTTPS avec Nginx

Un Odoo qui n'écoute que sur 127.0.0.1, c'est sûr mais inutilisable. Nginx fait le lien : il reçoit les visiteurs en HTTPS, avec un certificat Let's Encrypt gratuit, et transmet à Odoo. On le pose devant deux instances Odoo 20 sur le même serveur : l'installation native de l'article précédent et l'installation Docker du premier article, chacune sur son propre nom de domaine. Tout a été rejoué sur le serveur de démonstration.

~14 minutes de lecture · niveau intermédiaire · parcours Infrastructure

Ce que tu vas apprendre

Le reverse proxy

Un site Nginx par instance, le temps réel (/websocket), les en-têtes que proxy_mode attend.

Le certificat

Let's Encrypt avec certbot : obtention, redirection HTTP vers HTTPS, renouvellement automatique, HSTS.

Deux instances

Odoo 20 natif et Odoo 20 sous Docker côte à côte : ports, bases, noms de domaine.

Prérequis

  • Le serveur Ubuntu 24.04 de Installer Odoo 20 sur un serveur Ubuntu : Odoo natif en service, sur 127.0.0.1:8069 et 8072, base prod.
  • Pour la seconde instance, la pile de Installer Odoo 20 avec Docker dans /opt/odoo20, base demo20. Une seule instance t'intéresse ? Saute la partie 2 et le second site.
  • Un nom de domaine par instance, chacun avec un enregistrement DNS de type A vers l'adresse IP du serveur. Ici : demo20.lab.odooskills.com (natif) et docker20.lab.odooskills.com (Docker). Vérifie avant de commencer : dig +short demo20.lab.odooskills.com doit afficher l'IP du serveur.
  • Les ports 80 et 443 joignables depuis Internet (pare-feu de l'hébergeur compris).

Vue d'ensemble

Deux règles tiennent l'ensemble : un port par instance (deux programmes ne peuvent pas écouter sur le même), et un nom de domaine par instance (c'est lui qui permet à Nginx de savoir à quel Odoo transmettre).

1. Installer Nginx et certbot, ouvrir le pare-feu

apt-get update
apt-get install -y nginx certbot python3-certbot-nginx
nginx -v
certbot --version

ufw allow 'Nginx Full'
ufw status
nginx version: nginx/1.24.0 (Ubuntu) certbot 2.9.0 Rule added Rule added (v6) Status: active To Action From -- ------ ---- OpenSSH ALLOW Anywhere Nginx Full ALLOW Anywhere OpenSSH (v6) ALLOW Anywhere (v6) Nginx Full (v6) ALLOW Anywhere (v6)

Nginx Full est un profil UFW livré avec Nginx : il ouvre 80 (HTTP, indispensable à la validation Let's Encrypt et à la redirection) et 443 (HTTPS). Les ports d'Odoo, eux, restent fermés : ils n'écoutent que sur 127.0.0.1.

2. Faire tourner les deux instances côte à côte

L'instance native occupe déjà 127.0.0.1:8069 et 8072. La pile Docker de l'article 1 publiait elle aussi le port 8069 : lancée telle quelle, elle échouerait. On la déplace sur 8169, dans /opt/odoo20/compose.yaml :

cd /opt/odoo20
nano compose.yaml

Dans le service odoo, remplace la ligne du port :

    ports:
      - "127.0.0.1:8169:8069"

Le conteneur continue d'écouter sur son port 8069 interne ; seul le port côté serveur change. Avant de l'exposer au public, ferme aussi son gestionnaire de bases, comme sur l'instance native. Dans nano config/odoo.conf, remplace la ligne list_db = True par ces deux lignes :

dbfilter = ^demo20$
list_db = False

DuplicateOptionError: option 'list_db' in section 'options' already exists

Si tu ajoutes list_db = False sans retirer list_db = True, Odoo refuse de démarrer : une même option ne peut apparaître qu'une fois dans odoo.conf. Vérifie avec grep -c ^list_db config/odoo.conf, qui doit afficher 1.

proxy_mode = True y figure déjà depuis l'article 1. docker compose up -d recrée le conteneur puisque son port a changé, et il relit odoo.conf au démarrage (pour une simple modification de odoo.conf, docker compose restart odoo suffit). Relance, puis vérifie les deux instances :

docker compose up -d
ss -tlnp | grep -E ':(8069|8072|8169) '
curl -s http://127.0.0.1:8069/web/webclient/version_info -H 'Content-Type: application/json' -d '{"jsonrpc":"2.0","params":{}}'
curl -s http://127.0.0.1:8169/web/webclient/version_info -H 'Content-Type: application/json' -d '{"jsonrpc":"2.0","params":{}}'

Deux Odoo 20 bien distincts : les sources de la branche 20.0 d'un côté (20.0), l'image Docker datée de l'autre (20.0-20260926). Chacun a sa base, son PostgreSQL (celui d'Ubuntu d'un côté, le conteneur postgres:17 de l'autre) et son filestore. Les deux ensemble occupent environ 1 Go de mémoire au repos sur ce serveur de 4 Go.

Pourquoi le conteneur n'a-t-il pas de port 8072 ?

L'instance native tourne avec des workers : Odoo sert alors le temps réel (/websocket) sur un port à part, 8072. Le conteneur de l'article 1 n'a pas de workers : pages et websocket passent par le même port. D'où deux sites Nginx légèrement différents.

3. Le site Nginx de l'instance native

D'abord, un petit fichier commun aux deux sites, qui calcule l'en-tête Connection du websocket :

nano /etc/nginx/conf.d/odoo-websocket.conf
nano en trois gestes. Colle le contenu (clic droit, ou Ctrl+Maj+V), enregistre avec Ctrl+O puis Entrée, quitte avec Ctrl+X. 
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}

Nginx lit conf.d/ avant les sites : la variable $connection_upgrade est ainsi disponible pour tous, et le bloc n'est écrit qu'une fois. Ensuite, le site lui-même : un fichier dans /etc/nginx/sites-available/, activé par un lien dans sites-enabled/. On l'écrit en HTTP simple ; certbot ajoutera la partie HTTPS à l'étape 5. Remplace le nom de domaine par le tien.

nano /etc/nginx/sites-available/demo20.lab.odooskills.com
upstream odoo {
    server 127.0.0.1:8069;
}
upstream odoochat {
    server 127.0.0.1:8072;
}

server {
    listen 80;
    server_name demo20.lab.odooskills.com;

    proxy_read_timeout 720s;
    proxy_connect_timeout 720s;
    proxy_send_timeout 720s;
    client_max_body_size 100m;

    access_log /var/log/nginx/odoo.access.log;
    error_log /var/log/nginx/odoo.error.log;

    location /websocket {
        proxy_pass http://odoochat;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
        proxy_set_header X-Forwarded-Host $http_host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Real-IP $remote_addr;
    }

    location / {
        proxy_set_header X-Forwarded-Host $http_host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_redirect off;
        proxy_pass http://odoo;
        proxy_cookie_flags session_id samesite=lax secure;
    }

    gzip on;
    gzip_types text/css text/scss text/plain text/xml application/xml application/json application/javascript;
}

C'est le modèle de la documentation officielle d'Odoo 20, en quatre idées :

  • upstream : les deux ports de l'instance, pages (8069) et temps réel (8072).
  • location /websocket vers 8072, avec Upgrade et Connection : sans eux, la connexion temps réel (notifications, discussions) ne s'établit pas.
  • X-Forwarded-* : l'adresse du visiteur, le nom de domaine et le protocole (HTTPS) d'origine. Odoo ne les lit que si proxy_mode = True.
  • proxy_cookie_flags : le cookie de session n'est envoyé qu'en HTTPS (secure) et pas par des sites tiers (samesite=lax). client_max_body_size autorise les pièces jointes jusqu'à 100 Mo (1 Mo par défaut dans Nginx).

Active le site, retire la page d'accueil par défaut de Nginx, vérifie et recharge :

ln -s /etc/nginx/sites-available/demo20.lab.odooskills.com /etc/nginx/sites-enabled/
rm /etc/nginx/sites-enabled/default
nginx -t && systemctl reload nginx
nginx: the configuration file /etc/nginx/nginx.conf syntax is ok nginx: configuration file /etc/nginx/nginx.conf test is successful

Côté Odoo, passe proxy_mode à True (nano /etc/odoo/odoo.conf), puis systemctl restart odoo.

4. Le site Nginx de l'instance Docker

nano /etc/nginx/sites-available/docker20.lab.odooskills.com
upstream odoo_docker {
    server 127.0.0.1:8169;
}

server {
    listen 80;
    server_name docker20.lab.odooskills.com;

    proxy_read_timeout 720s;
    proxy_connect_timeout 720s;
    proxy_send_timeout 720s;
    client_max_body_size 100m;

    access_log /var/log/nginx/odoo-docker.access.log;
    error_log /var/log/nginx/odoo-docker.error.log;

    # Conteneur sans workers : pages et websocket sur le même port
    location / {
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
        proxy_set_header X-Forwarded-Host $http_host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_redirect off;
        proxy_pass http://odoo_docker;
        proxy_cookie_flags session_id samesite=lax secure;
    }

    gzip on;
    gzip_types text/css text/scss text/plain text/xml application/xml application/json application/javascript;
}

Trois différences avec le premier site : un upstream au nom différent (odoo_docker : deux upstream odoo sur le même serveur Nginx seraient en conflit), une seule location qui transmet aussi Upgrade et Connection (le websocket passe par le même port), et des journaux séparés.

Deux erreurs de nginx -t à connaître

unknown "connection_upgrade" variable : le fichier conf.d/odoo-websocket.conf manque (c'est le cas si tu as copié ce site seul sur un autre serveur). duplicate upstream "odoo" : deux sites déclarent un upstream du même nom ; d'où odoo_docker ici.

ln -s /etc/nginx/sites-available/docker20.lab.odooskills.com /etc/nginx/sites-enabled/
nginx -t && systemctl reload nginx

5. Les certificats HTTPS

certbot demande un certificat à Let's Encrypt, prouve que le domaine pointe bien vers ce serveur (par une requête HTTP sur le port 80), puis modifie lui-même le site Nginx : ajout du HTTPS et redirection de HTTP vers HTTPS. Une commande par domaine :

certbot --nginx -d demo20.lab.odooskills.com --redirect --agree-tos --no-eff-email -m ton-adresse@exemple.com
certbot --nginx -d docker20.lab.odooskills.com --redirect --agree-tos --no-eff-email -m ton-adresse@exemple.com
Successfully received certificate. ... Successfully deployed certificate for demo20.lab.odooskills.com to /etc/nginx/sites-enabled/demo20.lab.odooskills.com Congratulations! You have successfully enabled HTTPS on https://demo20.lab.odooskills.com

L'adresse électronique sert aux avertissements de Let's Encrypt (renouvellement en échec, par exemple) ; --no-eff-email évite une question sur l'inscription à la lettre de l'EFF. Moins d'une minute par certificat. Rouvre le fichier du site : certbot a transformé le bloc listen 80 en listen 443 ssl avec les chemins des certificats (lignes marquées # managed by Certbot), et ajouté un second bloc server qui renvoie le HTTP vers le HTTPS.

HSTS : le HTTPS obligatoire côté navigateur

Dans chacun des deux fichiers, sous la ligne listen 443 ssl; # managed by Certbot, ajoute :

    add_header Strict-Transport-Security "max-age=31536000" always;

Le navigateur retient pendant un an que ce site ne se consulte qu'en HTTPS, même si on tape http://. Puis nginx -t && systemctl reload nginx. Trois précautions :

  • c'est un engagement : si le certificat venait à manquer, les visiteurs ne pourraient plus du tout entrer. Pour un premier essai, commence par max-age=300 (cinq minutes), puis passe à un an une fois tout vérifié ;
  • n'ajoute includeSubDomains que si tous les sous-domaines sont en HTTPS ;
  • la ligne est placée au niveau du bloc server ; si tu ajoutes un jour un add_header dans une location, Nginx n'hérite plus des en-têtes du bloc parent pour cette location : il faudra y répéter celui-ci.

Le renouvellement

Les certificats Let's Encrypt durent 90 jours. Le paquet certbot installe un minuteur systemd qui les renouvelle tout seul ; on vérifie qu'il existe et qu'un renouvellement fonctionnerait :

certbot certificates
systemctl list-timers certbot.timer

6. Vérifier depuis ton poste

Ces tests se lancent depuis ton poste, pas depuis le serveur : c'est le chemin qu'emprunteront les utilisateurs.

curl -s -o /dev/null -w "%{http_code} %{redirect_url}\n" http://demo20.lab.odooskills.com/web/login
curl -sI https://demo20.lab.odooskills.com/web/login | grep -i -E "^(HTTP|strict|set-cookie)"
echo | openssl s_client -connect demo20.lab.odooskills.com:443 -servername demo20.lab.odooskills.com 2>/dev/null \
    | openssl x509 -noout -subject -enddate
301 https://demo20.lab.odooskills.com/web/login HTTP/1.1 200 OK set-cookie: session_id=CV8Hl9qu...; Expires=Thu, 30 Sep 2027 08:52:57 GMT; Max-Age=604800; HttpOnly; Path=/; Secure; SameSite=Lax Strict-Transport-Security: max-age=31536000 subject=CN = demo20.lab.odooskills.com notAfter=Dec 29 07:19:41 2026 GMT

Redirection 301, page servie en HTTPS, cookie Secure; SameSite=Lax, en-tête HSTS, certificat au bon nom. Même résultat pour docker20. Le temps réel se teste en simulant l'ouverture d'un websocket :

curl -s -m 5 --http1.1 -o /dev/null -w "%{http_code}\n" \
    -H "Origin: https://demo20.lab.odooskills.com" -H "Connection: Upgrade" -H "Upgrade: websocket" \
    -H "Sec-WebSocket-Version: 13" -H "Sec-WebSocket-Key: $(openssl rand -base64 16)" \
    https://demo20.lab.odooskills.com/websocket
101

101 (« changement de protocole ») : le websocket est ouvert, sur les deux sites. En navigateur, le journal /var/log/nginx/odoo.access.log montre la même chose après une connexion : "GET /websocket?version=... HTTP/1.1" 101.

400 Bad Request: Empty or missing header(s): origin

Sans l'en-tête Origin, Odoo 20 refuse le websocket (400) et l'écrit dans son journal. Un navigateur l'envoie toujours ; un test à la main l'oublie facilement. Ce n'est donc pas une panne de Nginx.

Dernier contrôle, le plus important : seul Nginx doit être joignable. Depuis ton poste, les ports d'Odoo et de PostgreSQL doivent rester fermés :

for p in 8069 8072 8169 5432; do
    timeout 5 bash -c "</dev/tcp/demo20.lab.odooskills.com/$p" 2>/dev/null && echo "$p OUVERT" || echo "$p fermé"
done
8069 fermé 8072 fermé 8169 fermé 5432 fermé

Enfin, dans le journal d'Odoo, les requêtes portent maintenant la vraie adresse IP des visiteurs, et non plus 127.0.0.1 : c'est proxy_mode qui lit l'en-tête X-Forwarded-For. Tu y verras aussi, dès les premières minutes, des robots qui essaient des adresses comme /.vscode/sftp.json : un serveur en ligne est scanné en permanence, d'où l'intérêt d'un gestionnaire de bases fermé et de mots de passe forts.

Ce qui change par rapport à Odoo 19

  • Le modèle Nginx de la documentation est le même qu'en Odoo 19 (/websocket vers le port gevent, en-têtes X-Forwarded-*).
  • Odoo 20 écoute par défaut sur 127.0.0.1 : derrière Nginx, c'est exactement ce qu'on veut, sans rien régler. Sans Nginx, http://IP:8069 ne répond plus (il répondait en 19).
  • PostgreSQL 16 au minimum : sans effet ici, Nginx ne dépend pas de la base.

Et ensuite ?

Les deux Odoo sont en ligne, chiffrés et protégés. Pour une vraie production, il reste la sauvegarde automatique (bases et filestores), la rotation des journaux, la supervision et une procédure de mise à jour avec retour arrière. Ces sujets, avec la sécurisation du serveur et plusieurs versions d'Odoo sur la même machine, sont traités pas à pas dans l'ebook Déployer Odoo en production, dont l'édition Odoo 20 est en cours de rédaction sur ce même serveur.

Récapitulatif

  • apt-get install nginx certbot python3-certbot-nginx, puis ufw allow 'Nginx Full' (80 et 443).
  • Un port par instance (natif 8069 + 8072, Docker 8169), toujours sur 127.0.0.1 ; un nom de domaine par instance.
  • Un site Nginx par instance : /websocket vers 8072 pour l'instance avec workers, tout sur un port pour le conteneur ; le map du websocket une seule fois, dans conf.d/ ; des noms d'upstream différents.
  • proxy_mode = True dans chaque odoo.conf, et gestionnaire de bases fermé (list_db = False, en remplacement, jamais en double).
  • certbot --nginx -d … --redirect par domaine, HSTS ajouté à la main, renouvellement vérifié par certbot renew --dry-run.
  • Tests depuis l'extérieur : 301 puis 200, cookie Secure, websocket 101 (avec Origin), ports d'Odoo fermés.
