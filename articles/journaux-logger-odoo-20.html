Journaux Odoo 20 : _logger, --log-handler, --log-sql, --log-config

Un _logger.info() qui n'apparaît pas, un journal noyé sous les requêtes HTTP, une requête SQL qu'on voudrait voir passer : tout se règle par logger, en ligne de commande ou dans un fichier. Chaque option est montrée avec la sortie qu'elle produit vraiment, et avec ce qui a changé dans le journal d'Odoo 20.

~13 minutes de lecture · niveau intermédiaire · parcours Infrastructure

Ce que tu vas apprendre

Écrire

_logger = logging.getLogger(__name__), les niveaux, et lire une ligne du journal champ par champ.

Filtrer

--log-level, --log-handler par module, --log-sql, --log-web et les lignes de requêtes HTTP.

Diriger

--logfile, --syslog, --log-config (JSON ou TOML), la table ir.logging et --dev.

Prérequis

  • Un Odoo 20 installé avec son odoo.conf : voir Installer Odoo 20 sur Ubuntu ou sur un serveur Ubuntu. Le fichier ne contient ni dev_mode ni réglage de journal : tout part des valeurs par défaut.
  • Une base de démonstration, appelée ici ma_base : Ventes et Inventaire installés, en français.
  • Les commandes sont lancées depuis le dossier des sources (./odoo-bin). Les essais passent par la console odoo-bin shell (voir Le shell Odoo 20) : elle accepte les mêmes options de journal que le serveur.

1. _logger dans un module : la convention et les niveaux

Chaque fichier Python d'un module déclare son logger en tête, avec le nom du module Python courant :

import logging

from odoo import models

_logger = logging.getLogger(__name__)   # odoo.addons.mon_module.models.sale_order


class SaleOrder(models.Model):
    _inherit = 'sale.order'

    def action_confirm(self):
        for order in self:
            _logger.info("Commande %s (%s) pour %s", order.name, order.state, order.partner_id.name)
        return super().action_confirm()

Dans le fichier mon_module/models/sale_order.py, __name__ vaut odoo.addons.mon_module.models.sale_order. Ce nom est hiérarchique : tout réglage posé sur odoo.addons.mon_module s'applique aux loggers de tous les fichiers du module, et un réglage sur odoo à tout Odoo. C'est ce qui rend le filtrage par module possible (section 3).

Pour l'essayer sans écrire de module, le même logger se crée à la main dans un script passé à la console. Le fichier journal.py utilisé dans tout l'article :

import logging
_logger = logging.getLogger('odoo.addons.mon_module.models.sale_order')

order = env['sale.order'].search([], order='id', limit=1)
_logger.debug("Commande %s : %d ligne(s)", order.name, len(order.order_line))
_logger.info("Commande %s (%s) pour %s", order.name, order.state, order.partner_id.name)
if not order.commitment_date:
    _logger.warning("Commande %s : aucune date de livraison promise", order.name)
try:
    order.amount_total / 0
except ZeroDivisionError:
    _logger.exception("Calcul de remise impossible pour %s", order.name)
MéthodeNiveauPour quoi
_logger.debug()DEBUGLe détail utile pendant le développement. Invisible par défaut.
_logger.info()INFOLes étapes normales : un traitement lancé, un lot terminé.
_logger.warning()WARNINGQuelque chose d'anormal mais pas bloquant.
_logger.error()ERRORUne opération qui a échoué.
_logger.exception()ERROR + tracebackDans un except : ajoute la pile d'appels au message.
_logger.critical()CRITICALLe service ne peut plus fonctionner.

Passe les valeurs en arguments ("%s", order.name) plutôt qu'en f-string : le message n'est construit que si la ligne est réellement écrite, et un même message garde la même forme dans le journal, ce qui facilite un grep.

Le journal part sur la sortie d'erreur, d'où le 2>&1 avant le grep.

Le format vient de odoo/logging.py : %(asctime)s %(process)s %(levelname)s %(dbname)s %(name)s: %(message)s. Il ne se change pas par une option simple ; c'est le rôle de --log-config (section 7).

3. --log-level et --log-handler : régler le bruit

--log-handler=LOGGER:NIVEAU règle un logger et ses descendants. L'option se répète, et un nom vide désigne la racine (:INFO est la valeur par défaut) :

./odoo-bin -c odoo.conf -d ma_base \
    --log-handler=odoo.addons.mon_module:DEBUG \
    --log-handler=odoo.modules.loading:WARNING

La première ligne fait parler ton module, la seconde fait taire les lignes « loading 69 modules… » du démarrage. Dans odoo.conf, la même chose s'écrit en liste séparée par des virgules :

log_handler = odoo.addons.mon_module:DEBUG,odoo.modules.loading:WARNING

--log-level est un raccourci qui ajoute des réglages tout faits avant les tiens :

--log-level=Équivaut à
info (défaut)rien de plus que :INFO
debugodoo:DEBUG, odoo.sql_db:INFO (tout Odoo en DEBUG, sauf le SQL)
debug_sqlodoo.sql_db:DEBUG
warn / error / criticalodoo:WARNING / odoo:ERROR / odoo:CRITICAL
debug_rpc, debug_rpc_answer, test, notsetacceptés, mais sans effet : même journal qu'info

Avec --log-level=warn, le script de la section 1 n'écrit plus que ses lignes WARNING et ERROR, et getEffectiveLevel() du logger renvoie bien WARNING.

Le niveau s'écrit en majuscules

  • --log-handler=odoo.addons.mon_module:debug fait planter le démarrage : Odoo cherche le niveau avec getattr(logging, 'debug'), trouve la fonction logging.debug et s'arrête sur TypeError: Level not an integer or a valid string: <function debug …>.
  • Une faute de frappe, :DEBUGG, ne plante pas : le niveau retombe sur INFO sans un mot.
  • --log-level=debug_rpc, présent dans l'aide et accepté, ne change rien (tableau ci-dessus).

4. --log-sql : voir chaque requête

--log-sql est un raccourci pour --log-handler=odoo.sql_db:DEBUG. Chaque requête passe dans le journal, avec sa durée et ses paramètres déjà insérés :

./odoo-bin shell -c odoo.conf -d ma_base --no-http --log-sql
p = env['res.partner'].search([('name', 'ilike', 'acme')], limit=1)
print("partenaire :", p.name, p.city)
… DEBUG ma_base odoo.sql_db: [0.439 ms] query: SELECT "res_partner"."id" FROM "res_partner" WHERE ("res_partner"."active" IS TRUE AND "res_partner"."name" ILIKE '%acme%') ORDER BY "res_partner"."complete_name" ASC , "res_partner"."id" DESC LIMIT 1 … DEBUG ma_base odoo.sql_db: [0.218 ms] query: SELECT "res_partner"."id", "res_partner"."name", "res_partner"."complete_name", … partenaire : Acme Corporation Pleasant Hill

Deux requêtes : le search qui ne lit que les identifiants, puis la lecture des champs au premier accès à p.name. Lancée en console, la même commande affiche aussi le chargement du registre : 54 lignes odoo.sql_db pour ces deux instructions. Compte donc les requêtes autour du code qui t'intéresse plutôt que sur toute la sortie ; la méthode de mesure (compteur env.cr.sql_log_count, comparaison de search_read et search_fetch) est dans search, search_read, search_fetch, fetch.

Les paramètres apparaissent en clair dans la requête : un journal --log-sql de production contient des données clients, et parfois des jetons. À activer le temps d'un diagnostic, pas en continu.

5. Les lignes de requêtes HTTP et --log-web

Un serveur lancé écrit une ligne INFO par requête. Extrait du journal pendant qu'un client se connecte avec le compte portail de la démonstration, lit un contact, puis tente de lire les paramètres système :

Décomposition de la ligne "POST /web/dataset/call_kw/res.partner/search_read#res.partner.search_read HTTP/1.1" 200 44 9 0.004 0.007 rw et de son début :

ValeurSens
127.0.0.1Adresse du client.
lkrYr3TeDébut de l'identifiant de session : il suit l'utilisateur d'une requête à l'autre, et change à la connexion (ligne « Session rotated »).
#res.partner.search_readPour un appel RPC, le modèle et la méthode appelés.
200Code HTTP. Une erreur d'accès répond 200 avec une erreur JSON : c'est la ligne WARNING juste au-dessus qui la signale.
44Taille du corps de la réponse, en octets.
9Nombre de requêtes SQL de la requête.
0.004Temps passé dans PostgreSQL, en secondes.
0.007Temps restant, passé en Python (rendu, calculs).
rwMode du curseur : lecture-écriture (rw), lecture seule (ro) ou passé de l'un à l'autre (ro->rw).

Les trois chiffres de la fin sont le premier outil de diagnostic de lenteur : une page lente avec 900 requêtes SQL n'a pas le même problème qu'une page lente avec 10.

Faire taire les lignes de requêtes

Sur un serveur chargé, ces lignes noient le reste. Elles viennent du logger odoo.http.server :

./odoo-bin -c odoo.conf --log-handler=odoo.http.server:WARNING

Essai sur deux démarrages suivis d'un appel à /web/login : avec --log-handler=werkzeug:WARNING, la recette des versions précédentes encore citée en exemple dans l'aide de odoo-bin, les deux lignes de requêtes restent ; avec odoo.http.server:WARNING, il n'en reste aucune. Les erreurs, elles, passent toujours.

--log-web

--log-web vaut --log-handler=odoo.http:DEBUG. Il ajoute, pour chaque requête, une ligne [REQ] à l'arrivée et une ligne [RES] au départ, plus les messages DEBUG de la couche HTTP (sessions, géolocalisation) :

… DEBUG ma_base odoo.http.server: [REQ] 127.0.0.1 - - [Wed, 07 Oct 2026 08:30:31 GMT] "GET /web/login HTTP/1.1" - - 0 0 0.0 - … DEBUG ma_base odoo.http.server: [RES] 127.0.0.1 G2z754iZ - [07/Oct/2026 08:30:31] "GET /web/login HTTP/1.1" 200 6631 76 0.025 0.133 rw … INFO ma_base odoo.http.server: 127.0.0.1 G2z754iZ - [07/Oct/2026 08:30:31] "GET /web/login HTTP/1.1" 200 6631 76 0.025 0.133 rw

Utile pour repérer une requête qui arrive mais ne repart jamais : elle a son [REQ] et pas de [RES].

6. --logfile et --syslog : où va le journal

Sans option, le journal part sur la sortie d'erreur : c'est ce que récupère journalctl quand Odoo tourne en service systemd. --logfile l'écrit dans un fichier, et crée le dossier s'il manque :

./odoo-bin shell -c odoo.conf -d ma_base --no-http --logfile=logs/odoo.log < journal.py

Sur le terminal, il ne reste que ce que le script affiche par print() ; les 18 lignes du journal sont dans logs/odoo.log. En production, l'équivalent est logfile = /var/log/odoo/odoo.log dans odoo.conf. Odoo rouvre le fichier quand il a été déplacé : une rotation logrotate classique, sans copytruncate, suffit.

--syslog envoie au démon syslog (/dev/log), avec un format sans date ni PID, que syslog ajoute lui-même. Odoo 20 l'annonce comme obsolète dès le démarrage :

Odoo Server 20.0:?:WARNING:py.warnings:<argv>:1: DeprecationWarning: The --syslog option is deprecated since Odoo 20, switch to --log-config and configure a syslog handler. Odoo Server 20.0:ma_base:INFO:odoo.registry:Registry loaded in 0.367s

--syslog et --logfile s'excluent : Odoo refuse de démarrer avec les deux. Pour écrire à plusieurs endroits à la fois, il faut --log-config.

7. --log-config : toute la configuration logging de Python

--log-config=FICHIER charge un fichier au format dictConfig de Python : formats, destinations, niveaux, tout est permis. Exemple courant : garder le journal habituel à l'écran et écrire en plus les WARNING et au-delà, en JSON, dans un fichier qu'un outil de supervision lira.

{
  "version": 1,
  "keep_odoo_default": true,
  "formatters": {
    "json": {
      "()": "odoo.logging.JSONFormatter",
      "record_keys": ["asctime", "levelname", "dbname", "name", "message", "exc_info"]
    }
  },
  "handlers": {
    "alertes": {
      "class": "logging.FileHandler",
      "filename": "alertes.jsonl",
      "level": "WARNING",
      "formatter": "json"
    }
  },
  "root": {"handlers": ["alertes"]}
}

Le point qui surprend : "keep_odoo_default": true. Sans lui, Odoo applique ton fichier et s'arrête là : pas de sortie habituelle, et --log-level, --log-handler, --log-sql, --log-db sont ignorés. L'essai est net : avec un fichier qui met odoo.addons.mon_module en DEBUG, ajouter --log-handler=odoo.addons.mon_module:ERROR --log-level=warn laisse passer les lignes DEBUG et INFO.

Odoo 20 accepte aussi un fichier TOML, reconnu à son extension .toml. Le même principe, ici sans keep_odoo_default : une seule sortie au format Odoo, racine en WARNING, ton module en DEBUG.

version = 1

[formatters.odoo]
"()" = "odoo.logging.Formatter"

[handlers.console]
class = "logging.StreamHandler"
formatter = "odoo"

[loggers."odoo.addons.mon_module"]
level = "DEBUG"

[root]
level = "WARNING"
handlers = ["console"]

Avec ce fichier, le démarrage n'écrit plus aucune ligne de chargement, et les quatre lignes de journal.py, DEBUG comprise, sortent au format habituel. --log-config est aussi le remplaçant annoncé de --syslog : un handler logging.handlers.SysLogHandler dans ce fichier.

8. --log-db : le journal dans la table ir.logging

--log-db=NOM_DE_BASE copie les lignes dans la table ir_logging de cette base ; --log-db=%d désigne la base de la requête en cours. Seules les lignes à partir de WARNING sont copiées par défaut (--log-db-level pour changer). Après un passage de journal.py avec --log-db=%d, en console :

for log in env['ir.logging'].search([], order='id'):
    print(log.id, log.type, log.level, log.dbname, log.name, log.func, log.line, "|", log.message.splitlines()[0])
1 server WARNING ma_base odoo.addons.mon_module.models.sale_order <module> 6 | Commande S00001 : aucune date de livraison promise 2 server ERROR ma_base odoo.addons.mon_module.models.sale_order <module> 10 | Calcul de remise impossible pour S00001

Chaque ligne garde le fichier, la fonction et le numéro de ligne d'origine, et le message contient le traceback. On les retrouve dans l'interface en mode développeur, Paramètres › Technique › Structure de la base de données › Journalisation. Chaque écriture ouvre sa propre connexion à PostgreSQL : garde un niveau élevé (WARNING) pour ne pas doubler la charge de la base.

9. --dev et le journal, et les couleurs

Trois des modes de --dev touchent au journal :

ModeEffet sur le journal
accessUne erreur d'accès pendant une requête HTTP est écrite avec son traceback complet. Sans ce mode, seule la ligne WARNING « You are not allowed to access… » de la figure 2 apparaît ; avec lui, la pile mène jusqu'à check_access et à l'appel qui l'a déclenché.
qwebEn cas d'erreur de rendu QWeb, le XML compilé du gabarit est écrit dans le journal.
reloadLe serveur surveille les dossiers de modules et redémarre à chaque modification ; au démarrage : Watching addons folder …/odoo/addons puis AutoReload watcher running with inotify.

--dev=all active access, qweb, reload et xml. Les valeurs inconnues sont acceptées sans message : --dev=werkzeug, que de vieux tutoriels recommandent pour un débogueur dans le navigateur, ne fait plus rien.

Les couleurs

Le journal est coloré quand il sort sur un terminal, jamais dans un fichier. Odoo 20 se règle par une section [colors] d'odoo.conf (valeurs always, never, auto) et par les variables NO_COLOR et FORCE_COLOR :

[colors]
loglevel = never
pid = always

Clés reconnues : pid, loglevel, session_id, http_request_line, http_response_body, perf, cursor_mode, sql. La coloration des requêtes SQL (sql) demande le paquet pygments, qui n'est pas dans requirements.txt : avec FORCE_COLOR=1 et --log-sql sans lui, le journal affiche une fois UserWarning: Pygments needs to be installed in order to highlight SQL.

Venant de la 19

  • Les lignes de requêtes HTTP ne viennent plus du logger werkzeug mais de odoo.http.server (Odoo 20 a son propre serveur HTTP). --log-handler=werkzeug:WARNING ne fait plus taire les requêtes : écrire odoo.http.server:WARNING. La ligne gagne le début de l'identifiant de session, la taille de la réponse et le mode du curseur.
  • --log-level=debug_rpc et debug_rpc_answer passaient tout Odoo en DEBUG ; ils sont toujours acceptés mais sans effet. Écrire --log-level=debug.
  • --syslog est déclaré obsolète (avertissement au démarrage).
  • --log-config accepte un fichier TOML en plus du JSON.
  • Section [colors], NO_COLOR / FORCE_COLOR et coloration du SQL : nouveaux.
  • Inchangés dans la 19 à jour : --log-config en JSON avec keep_odoo_default, odoo.logging.JSONFormatter, --log-handler, --log-sql, --log-web, --log-db. La valeur werkzeug de --dev avait déjà disparu de la 19.

Récapitulatif

  • Le nom du logger suit le fichier (odoo.addons.mon_module.models.…) : c'est lui qu'on règle avec --log-handler.
  • Les heures du journal sont en UTC ; le PID distingue les workers ; ? signale une ligne hors base.
  • Un niveau en minuscules fait planter le démarrage, une faute de frappe retombe sur INFO, debug_rpc ne fait rien.
  • Les requêtes HTTP sont sur odoo.http.server, avec nombre de requêtes SQL et temps en fin de ligne.
  • --log-config remplace toute la configuration, sauf avec keep_odoo_default ; Odoo 20 lit aussi le TOML.
  • --log-sql et --log-db sont des outils de diagnostic, pas des réglages permanents.
