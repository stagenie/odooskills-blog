Déployer la Bibliothèque en production : service, conf, mises à jour

Le module est prêt, le serveur aussi. Reste à poser l'un sur l'autre proprement : un dépôt Git pour le module, un fichier de configuration qui ne laisse rien traîner, un service systemd qu'on peut essayer sans être root, et une procédure de mise à jour, du module comme d'Odoo, avec son retour arrière.

~16 minutes de lecture · niveau intermédiaire · parcours Infrastructure

Ce que tu vas apprendre

Une conf de production

http_interface, proxy_mode, list_db, dbfilter, db_name, mot de passe maître haché : ce que chaque ligne change, vérifié.

Un service éprouvé

L'unité systemd essayée sans droits root, puis sa version système durcie, contrôlée avant installation.

Des mises à jour sans surprise

Le module, puis Odoo lui-même : l'ordre des gestes, le temps d'arrêt mesuré, et le seul vrai retour arrière.

Prérequis

  • Un serveur Odoo 20 Community installé comme dans Installer Odoo 20 sur un serveur Ubuntu : compte système odoo (dossier personnel /opt/odoo), sources dans /opt/odoo/odoo, environnement Python dans /opt/odoo/venv, PostgreSQL 16.
  • Le module biblio de la série dans un dépôt Git que le serveur peut lire.
  • Une base de test pour répéter chaque geste avant de le faire sur la vraie.

Cette étape 26 de la série arrive avant les étapes 23 à 25, qui ne sont pas encore parues. On déploie donc le module tel qu'il est à la fin de l'étape 22, en version 20.0.1.20.0. Pour montrer une vraie mise à jour, le serveur reçoit d'abord la version de l'étape 21 (20.0.1.19.0), puis passe à la suivante. La démarche ne dépend pas du contenu du module : elle servira telle quelle pour les étapes à venir.

Toutes les commandes se lancent sous le compte odoo, depuis /opt/odoo, sauf les gestes réservés à root, signalés au passage : installer l'unité systemd et la rotation du journal, arrêter et démarrer le service système. Les essais ont tourné sur une copie d'une base de démonstration ; les noms (ma_base) et les chemins sont ceux d'un serveur type.

1. Le module dans son propre dépôt Git

Ne copie pas le module à la main dans custom-addons. Donne-lui un dépôt Git, cloné sur le serveur dans un dossier à lui : la version en place se lit alors en une commande, une mise à jour devient un git fetch, et le retour arrière un git reset sur une révision notée. Le dépôt contient un dossier par module (ici biblio/) ; c'est son dossier racine qui entre dans addons_path.

$ git clone https://forge.exemple.com/equipe/addons-bibliotheque.git /opt/odoo/addons-bibliotheque
$ git -C /opt/odoo/addons-bibliotheque log --oneline
2627855 biblio 20.0.1.19.0

Le compte odoo doit pouvoir lire ce dépôt, et rien de plus : une clé de déploiement en lecture seule suffit. Un dépôt par client ou par jeu de modules, une ligne par dépôt dans addons_path.

Première installation, une fois la configuration de la section suivante en place. Le service n'est pas encore démarré ; --no-http reste un réflexe pour toute commande ponctuelle : avec des workers, Odoo ouvre le port 8069 avant même de traiter -i ou -u, --stop-after-init compris, et la commande lancée à côté du service s'arrête sur OSError: [Errno 98] (essayé) :

$ venv/bin/python odoo/odoo-bin -c /etc/odoo/odoo.conf -i biblio --stop-after-init --no-http
$ venv/bin/python odoo/odoo-bin module list -c /etc/odoo/odoo.conf | grep -E "^(base|biblio) "
biblio 20.0.1.19.0 20.0.1.19.0 'installed' Bibliothèque
base 20.0.1.3 20.0.1.3 'installed' Base

Onze secondes, rien à l'écran : avec logfile, tout part dans le journal. Pas de -d non plus : la configuration fixe la base (db_name, plus bas). odoo-bin module list, nouveau en Odoo 20, donne pour chaque module installé la version en base puis la version sur le disque. On s'en servira à chaque mise à jour.

2. Le fichier de configuration de production

Celui de l'article d'installation, complété pour une instance qui sert une seule base derrière un reverse proxy ; le dépôt du module remplace custom-addons dans addons_path, et workers est ramené à 2 pour la petite machine d'essai :

[options]
; base et accès
db_user = odoo
db_name = ma_base
dbfilter = ^ma_base$
list_db = False
admin_passwd = $pbkdf2-sha512$600000$ZKz1XgvBeG.t9f7/X4vxHg$gV.eOXlgeqIJr9xleK.R0yhr…
; chemins
addons_path = /opt/odoo/odoo/addons,/opt/odoo/addons-bibliotheque
data_dir = /opt/odoo/data
logfile = /var/log/odoo/odoo.log
; réseau
http_interface = 127.0.0.1
http_port = 8069
gevent_port = 8072
proxy_mode = True
; processus
workers = 2
max_cron_threads = 1
limit_memory_soft = 671088640
limit_memory_hard = 805306368
limit_time_cpu = 60
limit_time_real = 120

Le fichier reste root:odoo en 640, comme à l'installation. Le nombre de workers et les limites de mémoire se calculent d'après la machine, comme expliqué dans l'article d'installation. Ligne par ligne, le reste.

2.1 http_interface = 127.0.0.1 : personne n'entre en direct

Valeur par défaut d'Odoo 20, à vérifier plutôt qu'à croire : dans la configuration vide, puis sur le service démarré.

$ venv/bin/python -c "import sys; sys.path.insert(0, 'odoo')
from odoo.tools import config; config.parse_config([])
print(config['http_interface'], config['proxy_mode'], config['list_db'], config['admin_passwd'])"
127.0.0.1 False True admin
$ ss -ltn | grep -E ":(8069|8072) "
LISTEN 0      16              127.0.0.1:8069       0.0.0.0:*
LISTEN 0      128             127.0.0.1:8072       0.0.0.0:*
$ curl -s -m 3 -o /dev/null -w "%{http_code} (curl rc %{exitcode})\n" http://ADRESSE_DU_SERVEUR:8069/web/login
000 (curl rc 7)

Depuis l'adresse réseau de la machine, la connexion est refusée (code 7 de curl). Seul le reverse proxy, posé sur la même machine, parlera à Odoo. La quatrième valeur de la première commande mérite un arrêt : sans ligne admin_passwd, le mot de passe maître vaut admin.

2.2 proxy_mode = True : croire le reverse proxy, et lui seul

Derrière Nginx, Odoo reçoit toutes les requêtes depuis 127.0.0.1, en HTTP. Avec proxy_mode, il lit les en-têtes X-Forwarded-* posés par le proxy : vraie adresse du visiteur, nom d'hôte public, schéma https. Deux effets se voient. Le journal, d'abord :

$ curl -s -o /dev/null -H 'X-Forwarded-Proto: https' -H 'X-Forwarded-For: 203.0.113.9' \
    "http://127.0.0.1:8069/web/login?sanshost=1"
$ curl -s -o /dev/null -H 'X-Forwarded-Host: erp.exemple.com' -H 'X-Forwarded-Proto: https' \
    -H 'X-Forwarded-For: 203.0.113.9' "http://127.0.0.1:8069/web/login?avechost=1"
$ grep -E "sanshost|avechost" /var/log/odoo/odoo.log
… INFO ma_base odoo.http.server: 127.0.0.1 JuRUMpS1 - [10/Nov/2026 21:41:00] "GET /web/login?sanshost=1 HTTP/1.1" 200 …
… INFO ma_base odoo.http.server: 203.0.113.9 N75CQAyC - [10/Nov/2026 21:41:00] "GET /web/login?avechost=1 HTTP/1.1" 200 …

Odoo n'applique la réécriture que si X-Forwarded-Host est présent (odoo/http/server.py:185) : un proxy qui n'envoie que X-Forwarded-For et X-Forwarded-Proto est ignoré en entier. Le second effet compte plus : à chaque connexion d'un administrateur, Odoo réécrit le paramètre web.base.url, l'adresse qu'il met dans les courriels, les liens de portail et les PDF. Même connexion, avec les en-têtes d'un proxy, proxy_mode coupé puis actif :

$ psql -d ma_base -Atc "select value from ir_config_parameter where key='web.base.url'"
http://127.0.0.1:8069          # proxy_mode = False
https://erp.exemple.com        # proxy_mode = True

Sans proxy_mode, tous les liens envoyés aux clients pointeraient vers http://127.0.0.1:8069. Côté Nginx, l'en-tête X-Forwarded-Host est donc à poser ; ses autres réglages (délais, websockets, fichiers volumineux) feront l'objet d'un article à venir de la série « Exploiter Odoo 20 en production ».

proxy_mode sur un port ouvert : n'importe qui choisit son adresse

Les requêtes ci-dessus venaient toutes du serveur lui-même, et le journal a pourtant inscrit 203.0.113.9 : Odoo croit les en-têtes, il ne vérifie pas qui les envoie. Si le port 8069 était joignable de l'extérieur, un visiteur pourrait écrire l'adresse de son choix dans le journal et dans les traces de connexion ; et si un administrateur se connectait par cette voie, web.base.url serait réécrit. Le paramètre système web.base.url.freeze à True verrouille cette URL. proxy_mode = True ne va qu'avec http_interface = 127.0.0.1 (ou un pare-feu qui ne laisse passer que le proxy).

2.3 list_db = False et le mot de passe maître haché

list_db = False ferme tout le gestionnaire de bases, pas seulement la liste. Avec le bon mot de passe maître, une sauvegarde par le navigateur est refusée quand même :

$ curl -s -o /dev/null -w "%{http_code}\n" --data-urlencode 'master_pwd=le-vrai-mot-de-passe' \
    -d name=ma_base -d backup_format=zip http://127.0.0.1:8069/web/database/backup
403
$ curl -s -H 'Content-Type: application/json' -d '{"jsonrpc":"2.0","params":{}}' \
    http://127.0.0.1:8069/web/database/list | python3 -c "import sys,json; print(json.load(sys.stdin)['error']['data']['message'])"
Database management functions blocked, admin disabled database listing.

Le mot de passe maître ne sert donc plus à rien ? Il redevient la seule protection du gestionnaire le jour où quelqu'un repasse list_db à True pour une manipulation ponctuelle. Ne le laisse ni absent (il vaudrait admin), ni en clair : Odoo accepte directement un hachage pbkdf2-sha512, le même format que celui qu'il écrit quand on change ce mot de passe depuis le gestionnaire (odoo/tools/config.py:1135-1149). On le fabrique avec la bibliothèque passlib, déjà présente dans l'environnement d'Odoo :

$ read -rsp 'Mot de passe maître : ' MP; echo
$ printf %s "$MP" | venv/bin/python -c 'import sys; from passlib.hash import pbkdf2_sha512
print(pbkdf2_sha512.using(rounds=600000).hash(sys.stdin.read()))'; unset MP
$pbkdf2-sha512$600000$ZKz1XgvBeG.t9f7/X4vxHg$gV.eOXlgeqIJr9xleK.R0yhr…

La ligne produite va telle quelle après admin_passwd = . Contrôle par Odoo lui-même, avec ce fichier de configuration : le bon mot de passe passe, admin non.

$ venv/bin/python -c "import sys; sys.path.insert(0, 'odoo')
from odoo.tools import config; config.parse_config(['-c', '/etc/odoo/odoo.conf'])
print(config.verify_admin_password('le-vrai-mot-de-passe'), config.verify_admin_password('admin'))"
True False

Pour un mot de passe maître perdu ou une erreur « Access Denied » dans le gestionnaire, voir Gestionnaire de bases Odoo 20 : Access Denied et mot de passe maître.

2.4 db_name et dbfilter : une base, et pas une de plus

dbfilter = ^ma_base$ décide quelle base le navigateur peut ouvrir. db_name fait trois autres choses : c'est la base par défaut des commandes odoo-bin lancées avec ce fichier (d'où l'absence de -d plus haut), la base préchargée par les workers au démarrage, et la seule où tournent les actions planifiées (odoo/service/server.py:112-114). Sans elle, le worker des tâches planifiées passe sur toutes les bases du rôle PostgreSQL, filtre ou pas : une copie de test restaurée sur le serveur enverrait ses courriels.

Revers de la médaille : au démarrage, Odoo crée la base nommée par db_name si elle n'existe pas (odoo/cli/server.py:101-108, déjà le cas en 19). Une faute de frappe ne donne pas d'erreur :

$ venv/bin/python odoo/odoo-bin -c /etc/odoo/odoo.conf -d ma_bsae --stop-after-init --no-http
$ psql -d ma_bsae -Atc "select count(*) from ir_module_module where state='installed'"
16

Onze secondes plus tard, une base vide de 16 modules existe à côté de la vraie, invisible depuis le navigateur grâce au filtre. Après toute modification de db_name, un psql -l s'impose.

2.5 data_dir et logfile

data_dir fixe l'emplacement du filestore et des sessions. Sans lui, Odoo écrit dans le dossier personnel du compte qui le lance, et la première commande lancée depuis un autre compte écrit ailleurs. logfile envoie le journal dans un fichier, que la section 4 fait tourner. Un dernier détail d'installation se voit dès le premier démarrage : requirements.txt ne contient pas markdown2, et le module mail le signale à chaque chargement.

$ grep -m1 markdown2 /var/log/odoo/odoo.log
… WARNING ma_base odoo.addons.mail.controllers.attachment: markdown2 is not installed, markdown will not be rendered
$ venv/bin/pip install markdown2

Après ce pip install et un redémarrage, le journal ne contient plus aucun WARNING : un journal propre au démarrage, c'est ce qui rend visible le premier vrai avertissement.

3. Le service systemd : l'essayer sans root, puis l'installer

Une unité système se pose en root, et une erreur de chemin ne se découvre qu'au redémarrage du serveur. systemd offre aussi à chaque compte ordinaire son propre gestionnaire de services (systemctl --user) : on y lance exactement la même commande, sans aucun droit root, pour valider configuration et démarrage. Le compte système odoo, lui, n'a pas de session ouverte : la répétition se fait sur une installation d'essai sous un compte ordinaire, comme pour les relevés de cet article.

3.1 La répétition, en service utilisateur

# ~/.config/systemd/user/odoo.service
[Unit]
Description=Odoo 20 (service utilisateur)

[Service]
Type=simple
WorkingDirectory=/opt/odoo
ExecStart=/opt/odoo/venv/bin/python /opt/odoo/odoo/odoo-bin --config /etc/odoo/odoo.conf
Restart=on-failure
RestartSec=5
KillMode=mixed
TimeoutStopSec=30
UMask=0027

[Install]
WantedBy=default.target
$ systemd-analyze --user verify ~/.config/systemd/user/odoo.service
$ systemctl --user daemon-reload
$ systemctl --user start odoo
$ systemctl --user status odoo --no-pager | head -3
* odoo.service - Odoo 20 (service utilisateur)
     Loaded: loaded (…/.config/systemd/user/odoo.service; disabled; preset: enabled)
     Active: active (running) since Tue 2026-11-10 22:24:39 CET; 6s ago
$ grep -E "running on|Alive" /var/log/odoo/odoo.log | tail -5
… INFO ? odoo.service.server: HTTP service running on 127.0.0.1:8069
… INFO ma_base odoo.service.server.WorkerHTTP: Alive
… INFO ma_base odoo.service.server.WorkerHTTP: Alive
… INFO ma_base odoo.service.server.WorkerCron: Alive
… INFO ma_base odoo.service.server.GeventServer: Evented/WebSocket service running on 127.0.0.1:8072
$ curl -s "http://127.0.0.1:8069/web/health?db_server_status=1"
{"status": "pass", "db_server_status": true}

systemd-analyze verify ne dit rien : la syntaxe est bonne et les chemins existent. Deux workers web, un worker de tâches planifiées, le serveur temps réel, tous sur 127.0.0.1 ; et grâce à db_name, le nom de la base apparaît sur chaque ligne des workers. La route /web/health est faite pour la supervision : avec db_server_status=1, elle teste aussi PostgreSQL. systemctl --user stop odoo arrête le tout. Cette répétition sert à valider la configuration et le démarrage ; en production, c'est l'unité système qui tourne, et on n'en garde qu'une : les deux en même temps se disputeraient le port 8069.

3.2 UMask=0027 : le filestore n'est pas public sur la machine

Odoo 20 écrit chaque fichier du filestore en lecture seule pour tout le monde : il le copie d'abord dans un dossier upload/, le passe en 0444, puis le déplace à sa place (odoo/addons/base/models/ir_attachment.py:155-215). Odoo 19 ne faisait rien de tel. Ce qui protège alors les pièces jointes des autres comptes de la machine, ce sont les dossiers, créés en 0751 moins le masque du processus. Avec le masque 0002 d'un compte ordinaire, n'importe quel compte peut traverser les dossiers (sans les lister : il lui faut le nom exact du fichier, son empreinte SHA-1) ; avec UMask=0027 dans l'unité, plus personne :

$ ls -ld /opt/odoo/data/filestore/ma_base/upload          # créé avant UMask=0027
drwxr-x--x … /opt/odoo/data/filestore/ma_base/upload
$ ls -ld /opt/odoo/data/filestore/ma_base/upload          # recréé par le service avec UMask=0027
drwxr-x--- … /opt/odoo/data/filestore/ma_base/upload
$ ls -l /opt/odoo/data/filestore/ma_base/4a/4abcf56337adc6b19ddac40cd132bbb7c5654004
-r--r--r-- … 4abcf56337adc6b19ddac40cd132bbb7c5654004
$ ls -l /var/log/odoo/odoo.log                              # journal recréé par le service
-rw-r----- … /var/log/odoo/odoo.log

Le masque ne change rien aux dossiers déjà là : sur un serveur existant, un chmod -R o-rwx /opt/odoo/data une fois pour toutes, sous le compte odoo.

3.3 L'unité système, durcie

Celle de l'article d'installation, avec cinq lignes de plus :

# /etc/systemd/system/odoo.service
[Unit]
Description=Odoo 20
After=network.target postgresql.service
Wants=postgresql.service

[Service]
Type=simple
User=odoo
Group=odoo
WorkingDirectory=/opt/odoo
ExecStart=/opt/odoo/venv/bin/python /opt/odoo/odoo/odoo-bin --config /etc/odoo/odoo.conf
Restart=on-failure
RestartSec=5
KillMode=mixed
TimeoutStopSec=30
LimitNOFILE=65536
UMask=0027
NoNewPrivileges=yes
PrivateTmp=yes
ProtectSystem=full
ProtectHome=yes

[Install]
WantedBy=multi-user.target
  • NoNewPrivileges : ni Odoo ni ses sous-processus (wkhtmltopdf) ne peuvent gagner de droits par un programme setuid.
  • PrivateTmp : un /tmp propre au service, invisible des autres comptes.
  • ProtectSystem=full : /usr, /boot et /etc en lecture seule pour le service. Conséquence voulue : Odoo ne peut plus réécrire /etc/odoo/odoo.conf, ce que fait le bouton de changement du mot de passe maître (inutile ici, le gestionnaire est fermé).
  • ProtectHome : /home et /root invisibles ; le dossier personnel du compte odoo est /opt/odoo, il n'est pas concerné.

Avant de l'installer, deux contrôles qui ne demandent pas de droits : la syntaxe et les chemins, puis l'exposition mesurée par systemd, avec ces lignes et sans elles (odoo-sans-durcissement.service : la même unité sans les cinq lignes) :

$ systemd-analyze verify odoo.service
$ systemd-analyze security --offline=yes odoo.service | tail -1
-> Overall exposure level for odoo.service: 8.4 EXPOSED :-(
$ systemd-analyze security --offline=yes odoo-sans-durcissement.service | tail -1
-> Overall exposure level for odoo-sans-durcissement.service: 9.0 UNSAFE :-{

Le score descend de 9.0 à 8.4. Il resterait des options à ajouter (systemd en propose une trentaine), mais chacune doit être essayée sur ton serveur ; celles-ci sont les moins susceptibles de gêner Odoo. Si le venv n'est pas là où l'unité le cherche, verify le dit tout de suite : Command /opt/odoo/venv/bin/python is not executable: No such file or directory.

L'installation elle-même (copie dans /etc/systemd/system/, systemctl daemon-reload, systemctl enable --now odoo) revient à root ; elle est décrite pas à pas dans l'article d'installation. Le service système démarré, regarde son journal : un dossier oublié par ProtectSystem s'y verrait comme une erreur d'écriture.

4. Le journal et sa rotation

Sans rotation, odoo.log grossit indéfiniment. Odoo 20 écrit son journal avec un gestionnaire qui rouvre le fichier quand il a été déplacé : pas besoin de copytruncate ni de redémarrage. Geste root : ce fichier dans /etc/logrotate.d/odoo :

/var/log/odoo/odoo.log {
    su odoo odoo
    weekly
    rotate 8
    compress
    delaycompress
    missingok
    notifempty
}

su odoo odoo fait travailler logrotate sous le compte propriétaire du dossier plutôt qu'en root. Pour voir sans attendre une semaine, le compte odoo peut forcer une rotation avec son propre fichier d'état, puis envoyer une requête :

$ logrotate -s /opt/odoo/logrotate.state -f /etc/logrotate.d/odoo
$ ls /var/log/odoo/
odoo.log.1
$ curl -s -o /dev/null http://127.0.0.1:8069/web/login; ls /var/log/odoo/; wc -l < /var/log/odoo/odoo.log
odoo.log  odoo.log.1
1

Le service a recréé odoo.log de lui-même et y écrit la nouvelle ligne. Pour régler la verbosité ou isoler un module dans le journal, voir Journaux Odoo 20 : _logger, --log-handler, --log-sql, --log-config.

5. Mettre à jour la Bibliothèque

Côté développement, la version de l'étape 22 est poussée sur la branche 20.0 du dépôt, avec son manifeste en 20.0.1.20.0 et ses tests passés sur une base neuve (voir Tests automatisés en Odoo 20). Côté serveur, sept gestes, toujours dans cet ordre.

1. Sauvegarder, et noter la révision en place. La sauvegarde complète (base et filestore) et sa vérification ont leur propre article dans cette même série technique, sur la sauvegarde et la restauration d'Odoo 20 ; avant une mise à jour, une commande suffit :

$ venv/bin/python odoo/odoo-bin db -c /etc/odoo/odoo.conf dump ma_base /var/backups/odoo/ma_base-$(date +%Y%m%d-%H%M).zip
$ git -C addons-bibliotheque rev-parse HEAD > /var/backups/odoo/bibliotheque.rev
$ ls /var/backups/odoo/
bibliotheque.rev  ma_base-20261110-2240.zip

2. Récupérer sans appliquer, pendant que le service tourne : git fetch ne touche pas aux fichiers du module.

$ git -C addons-bibliotheque fetch origin

3. Lire ce qui arrive. Une nouvelle version dans le manifeste, et surtout un script de migration :

$ git -C addons-bibliotheque log --oneline HEAD..origin/20.0
2fa2d56 biblio 20.0.1.20.0 : genres, rayons, modèles d'import
$ git -C addons-bibliotheque diff --stat HEAD origin/20.0 -- '*/__manifest__.py' '*/migrations/*'
 biblio/__manifest__.py                       |  4 +++-
 biblio/migrations/20.0.1.20.0/pre-migrate.py | 24 ++++++++++++++++++++++++
 2 files changed, 27 insertions(+), 1 deletion(-)

4. Arrêter le service, puis appliquer le code. En production, l'arrêt et le démarrage du service système passent par root (ou par une règle sudo limitée à ce service) ; les commandes ci-dessous sont celles de la répétition, en service utilisateur :

$ systemctl --user stop odoo
$ git -C addons-bibliotheque merge --ff-only origin/20.0
Mise à jour 2627855..2fa2d56
Fast-forward

L'écran Applications le montre déjà, et c'est trompeur. En mode développeur, la fiche du module affiche la version du disque, alors que la base est encore en 20.0.1.19.0 :

5. Mettre à jour la base. Un essai à blanc d'abord (-n, nouveau en Odoo 20), qui liste les modules dont la version a monté, puis la vraie commande :

$ venv/bin/python odoo/odoo-bin module upgrade -c /etc/odoo/odoo.conf -n --outdated all
biblio 20.0.1.19.0 20.0.1.20.0 'to upgrade' Bibliothèque
$ venv/bin/python odoo/odoo-bin -c /etc/odoo/odoo.conf -u biblio --stop-after-init --no-http
$ grep migration /var/log/odoo/odoo.log | tail -2
… INFO ma_base odoo.modules.migration: module biblio: Running upgrade [>20.0.1.20.0] pre-migrate
… INFO ma_base odoo.modules.migration.biblio.pre: biblio.pre from 20.0.1.19.0 to 20.0.1.20.0 in 0.002 seconds

6. Redémarrer, et 7. contrôler : aucune erreur dans le journal depuis la mise à jour, la route de santé, et les deux versions identiques.

$ systemctl --user start odoo
$ curl -s http://127.0.0.1:8069/web/health
{"status": "pass"}
$ venv/bin/python odoo/odoo-bin module list -c /etc/odoo/odoo.conf | grep ^biblio
biblio 20.0.1.20.0 20.0.1.20.0 'installed' Bibliothèque

De l'arrêt au redémarrage : six secondes sur la base d'essai. Les cinq genres livrés par l'étape 22 sont en base, et le lien « Modèle d'import des livres » apparaît dans l'écran d'import.

Un -u sans redémarrage laisse un Odoo à moitié à jour

Essai fait, service en marche : git pull, puis -u biblio --stop-after-init --no-http à côté. Le journal du service montre ses workers recharger le registre (Modules loaded.) et les cinq genres arrivent en base. Mais les workers gardent en mémoire le Python d'avant : library.book.get_import_templates() répond encore [] au lieu du modèle d'import. Données neuves, code ancien, jusqu'au redémarrage. D'où l'ordre arrêt, mise à jour, démarrage, et la règle détaillée dans Mettre à jour un module Odoo 20 qui ne prend pas tes modifications : du Python modifié demande un redémarrage, des données ou des vues un -u, souvent les deux.

6. Mettre à jour Odoo lui-même

Odoo publie des correctifs en continu sur la branche 20.0. Même procédure, appliquée aux sources. Le clone de l'installation est superficiel (--depth 1) ; un fetch sans --depth ne télécharge que ce qui manque depuis la révision en place, et la mise à jour reste une avance rapide :

$ venv/bin/python odoo/odoo-bin db -c /etc/odoo/odoo.conf dump ma_base /var/backups/odoo/ma_base-avant-maj-odoo.zip
$ git -C odoo rev-parse HEAD > /var/backups/odoo/odoo.rev
$ git -C odoo fetch origin 20.0
Depuis https://github.com/odoo/odoo
   3538ed824..e77213ec9  20.0       -> origin/20.0
$ git -C odoo log --oneline HEAD..origin/20.0 | wc -l
2108
$ git -C odoo diff --stat HEAD origin/20.0 -- requirements.txt
$ systemctl --user stop odoo
$ git -C odoo merge --ff-only origin/20.0
Mise à jour 3538ed824..e77213ec9
Fast-forward
 12931 files changed, 1573151 insertions(+), 584978 deletions(-)
$ venv/bin/python odoo/odoo-bin module list -c /etc/odoo/odoo.conf | awk '$2 != $3'
account 20.0.1.5 20.0.1.6 'installed' Invoicing
$ venv/bin/pip install -r odoo/requirements.txt
$ venv/bin/python odoo/odoo-bin -c /etc/odoo/odoo.conf -u all --stop-after-init --no-http
$ systemctl --user start odoo

Sept semaines de correctifs, 2 108 commits. requirements.txt n'a pas bougé (le diff est vide) ; le pip install reste dans la procédure parce que, le jour où il bouge, l'oublier fait tomber le service au démarrage. Le -u all a pris 37 secondes pour 70 modules, et l'arrêt complet 44 secondes, sans une erreur au journal.

Pourquoi -u all et pas module upgrade --outdated, comme pour la Bibliothèque ? Parce que les correctifs d'Odoo ne changent presque jamais la version des modules. Le module list lancé juste après le merge, filtré sur les lignes où version en base et version sur disque diffèrent, le montre : un seul module installé a changé de version, alors que 21 modules installés ont des vues ou des données modifiées par ces commits, et 46 leur traduction française. --outdated n'aurait mis à jour que account ; les vues corrigées des 20 autres ne seraient jamais arrivées en base. Pour le code d'Odoo, c'est donc -u all, et un essai préalable sur une copie de la base (voir Copier la prod en base de test Odoo 20 : db dump, load, neutralize) mesure le temps d'arrêt réel, qui croît avec la taille de la base.

7. Revenir en arrière

Une mise à jour a réussi techniquement, mais un écran métier est cassé : on revient à l'état d'avant. Le code revient avec la révision notée ; la base, avec la sauvegarde. Les deux, toujours ensemble. Pour Odoo :

$ systemctl --user stop odoo
$ git -C odoo cat-file -t $(cat /var/backups/odoo/odoo.rev)
commit
$ git -C odoo reset --hard $(cat /var/backups/odoo/odoo.rev)
$ venv/bin/python odoo/odoo-bin module list -c /etc/odoo/odoo.conf | grep ^account
account 20.0.1.6 20.0.1.5 'installed' Invoicing
$ venv/bin/python odoo/odoo-bin db -c /etc/odoo/odoo.conf load -f --move ma_base /var/backups/odoo/ma_base-avant-maj-odoo.zip
Restoring /var/backups/odoo/ma_base-avant-maj-odoo.zip...
$ systemctl --user start odoo
$ venv/bin/python odoo/odoo-bin module list -c /etc/odoo/odoo.conf | grep ^account
account 20.0.1.5 20.0.1.5 'installed' Invoicing

La révision d'avant est restée dans le clone superficiel (cat-file répond commit) : pas besoin du réseau pour revenir. Entre le reset et le load, module list montre l'état bancal à ne jamais démarrer : une base en 20.0.1.6 sous un code en 20.0.1.5. -f supprime la base et son filestore avant de recharger la sauvegarde, --move lui rend son identité d'origine (identifiant, secret) au lieu d'en faire une copie. Quatorze secondes d'arrêt sur la base d'essai. Pour le module, même chose avec addons-bibliotheque et bibliotheque.rev : retour vérifié en 20.0.1.19.0, sans les genres de l'étape 22.

Tout ce qui a été saisi entre la sauvegarde et le retour arrière est perdu : c'est pour cela que la sauvegarde se fait juste avant la mise à jour, service arrêté si l'activité le permet, et que le contrôle de l'étape 7 se fait tout de suite.

L'ancien code suivi d'un -u : Odoo efface la nouvelle version

Tentation : revenir au code d'avant et relancer -u biblio pour « redescendre » la base. Essai fait sur la version de l'étape 22 déjà installée :

$ git -C addons-bibliotheque reset --hard 2627855
$ venv/bin/python odoo/odoo-bin -c /etc/odoo/odoo.conf -u biblio --stop-after-init --no-http
$ grep Deleting /var/log/odoo/odoo.log
… INFO ma_base odoo.addons.base.models.ir_model: Deleting 5@library.genre (biblio.genre_jeunesse)
… INFO ma_base odoo.addons.base.models.ir_model: Deleting 4@library.genre (biblio.genre_policier)
… INFO ma_base odoo.addons.base.models.ir_model: Deleting 3@library.genre (biblio.genre_science_fiction)
… INFO ma_base odoo.addons.base.models.ir_model: Deleting 2@library.genre (biblio.genre_aventure)
… INFO ma_base odoo.addons.base.models.ir_model: Deleting 1@library.genre (biblio.genre_roman)

Aucune erreur, code de sortie 0, version en base revenue à 20.0.1.19.0. Mais Odoo a supprimé tout ce que la nouvelle version avait livré et que l'ancienne ne connaît pas (ici, aucun livre n'utilisait encore ces genres). Odoo ne sait pas « descendre » une version : le retour arrière, c'est la sauvegarde.

Ce qui change par rapport à Odoo 19

PointOdoo 19Odoo 20
http_interface par défaut0.0.0.0127.0.0.1
Fichiers du filestoreécrits directement, droits selon le masquecopiés dans upload/, passés en 0444, puis déplacés ; dossiers en 0751 moins le masque
Versions en base et sur disquepar l'écran Applications ou en SQLodoo-bin module list
Essai à blanc d'une mise à jour—odoo-bin module upgrade -n

Le reste est identique en 19 : proxy_mode et sa condition sur X-Forwarded-Host, list_db, le mot de passe maître haché, la création automatique de la base de db_name, les tâches planifiées limitées par db_name.

À retenir

  • Un dépôt Git par jeu de modules, cloné dans son dossier : la version se lit, la mise à jour est un fetch, le retour un reset.
  • proxy_mode = True seulement derrière un proxy, et avec http_interface = 127.0.0.1 ; sans X-Forwarded-Host, Odoo ignore le proxy.
  • list_db = False ferme tout le gestionnaire ; le mot de passe maître reste à poser, haché. db_name borne les tâches planifiées, mais crée la base si elle n'existe pas.
  • Mise à jour : sauvegarde et révision notée, fetch, lecture, arrêt, code, -u, redémarrage, contrôle. -u biblio pour le module, -u all pour Odoo.
  • Retour arrière = code et sauvegarde. Jamais l'ancien code suivi d'un -u.
