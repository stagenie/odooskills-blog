Webhooks en Odoo 20 : recevoir et émettre des appels HTTP

Un outil externe prévient Odoo qu'un devis est signé, Odoo confirme la commande et prévient à son tour un autre outil. Les deux sens se règlent sans une ligne de module, avec les règles d'automatisation. Pour authentifier l'appelant, il faut en revanche un petit contrôleur signé. Les trois montages sont exécutés ici sur une base Odoo 20 Community.

~13 minutes de lecture · niveau intermédiaire · parcours Intégrations

Ce que tu vas apprendre

Recevoir

Une règle « Sur webhook » : son URL secrète, la recherche de l'enregistrement cible à partir du payload, ses réponses 200, 404 et 500.

Émettre

L'action « Envoyer une notification webhook » : le JSON envoyé, le moment de l'envoi, et ce qui se passe quand le destinataire est lent ou absent.

Authentifier

Un contrôleur qui vérifie une signature HMAC-SHA256 et un horodatage, puis agit avec les droits d'un utilisateur dédié plutôt qu'en superutilisateur.

Prérequis

  • Odoo 20 Community avec Ventes et sa base de démonstration, plus le module Automatisations (base_automation) : il n'est pas installé d'office. Le mode développeur, pour le menu Technique, les boutons Renouveler et Journaux et l'option « Enregistrer les appels ».
  • curl et Python 3 (bibliothèque standard) pour jouer l'outil externe.
  • Pour la partie 3 : savoir installer un module. Les bases des contrôleurs sont dans Controllers HTTP et API REST (écrit pour la 19 ; route, Controller et request s'importent toujours de odoo.http en 20).

Un webhook est un simple appel HTTP POST envoyé quand un événement se produit. Pour Odoo il y a deux sens : recevoir (un outil appelle une URL d'Odoo) et émettre (Odoo appelle l'URL d'un outil). À l'inverse de l'API JSON-2, où le client va chercher ou écrire des données quand il le décide, le webhook pousse l'information au moment où elle naît.

1. Recevoir un webhook sans coder : la règle « Sur webhook »

Le cas d'école : un service de signature électronique appelle Odoo quand un client a signé son devis, avec un JSON du type {"commande": "S00032", "signataire": "…"}. Odoo doit noter la signature dans la discussion du devis et confirmer la commande.

Créer la règle

  1. Paramètres › Technique › Automatisation › Règles d'automatisation, puis Nouveau. Modèle : Commande client ; Déclencher : Sur webhook.
  2. Odoo affiche aussitôt l'URL secrète, de la forme <URL de la base>/web/hook/<uuid>, avec un bouton pour la copier et un bouton Renouveler.
  3. Enregistrement cible : une expression Python qui trouve, à partir du corps reçu, l'enregistrement sur lequel la règle s'exécute. La valeur par défaut, model.env[payload.get('_model')].browse(int(payload.get('_id'))), attend un appel venant d'une autre base Odoo (partie 2). Ici, la commande se retrouve par son numéro :
model.search([('name', '=', payload.get('commande'))], limit=1)
  1. Ajouter une action de type Exécuter le code. La variable payload y est disponible, comme dans l'enregistrement cible :
record.message_post(body="Devis signé en ligne par %s." % payload.get('signataire'))
if record.state in ('draft', 'sent'):
    record.action_confirm()
  1. En mode développeur, activer Enregistrer les appels : chaque appel est consigné, et le bouton Journaux en haut du formulaire les liste.

L'appeler

Trois appels : une commande qui existe, une qui n'existe pas, une URL fausse.

Après le premier appel, S00032 est confirmée et sa discussion porte la note « Devis signé en ligne par Service achats Ready Mat. ». Le corps de la réponse est toujours le même petit JSON (addons/base_automation/controllers/main.py) : l'appelant ne reçoit jamais le détail de l'erreur. Ce détail est dans les journaux de la règle :

INFO Webhook #1 triggered with payload {'commande': 'S00032', 'signataire': 'Service achats Ready Mat'} INFO Webhook #1 triggered with payload {'commande': 'S99999'} ERROR Webhook #1 could not be triggered because no record to run it on was found.

Le même appel en GET, avec ?commande=S00003&signataire=… dans l'URL, a aussi confirmé S00003 : quand le corps n'est pas du JSON, Odoo prend les paramètres de l'URL comme payload.

Avec quels droits la règle s'exécute

La route est publique (auth='public', sans jeton CSRF) et le contrôleur cherche la règle en sudo(). Les actions tournent donc en superutilisateur, mais au nom de l'utilisateur public : la note et la confirmation de S00032 sont signées Public user dans la discussion (capture plus bas). Rien n'empêche un appelant qui connaît l'URL d'agir sur n'importe quelle commande que l'enregistrement cible sait trouver.

L'URL est le seul secret, et elle dépend de web.base.url

  • Aucune authentification : qui a l'URL peut déclencher la règle. Ne la mettre que dans l'outil appelant, en HTTPS, et la changer par Renouveler si elle a circulé (essayé : l'ancienne répond aussitôt 404). Garder l'enregistrement cible et les actions aussi étroits que possible.
  • L'URL affichée est construite avec le paramètre système web.base.url. Or Odoo réécrit ce paramètre à chaque connexion d'un administrateur, avec l'adresse utilisée pour se connecter : sur la base de test, l'URL a changé de port après une simple connexion. Derrière un proxy, c'est une adresse interne qui finit copiée dans l'outil tiers. Mettre la bonne adresse dans web.base.url et ajouter le paramètre web.base.url.freeze à True.

2. Émettre un webhook sans coder : « Envoyer une notification webhook »

Dans l'autre sens, l'outil de facturation doit être prévenu de chaque commande confirmée. Une deuxième règle sur Commande client, déclenchée par Le statut est défini sur « Commande client », reçoit une action de type Envoyer une notification webhook : une URL et une liste de champs. La fenêtre montre un exemple du corps qui partira, calculé sur une commande de la base.

Pour voir ce qui arrive, un « outil externe » de quelques lignes suffit : il affiche chaque requête reçue, et peut simuler un destinataire lent.

# Un « outil externe » minimal : affiche chaque requête reçue. Usage : python3 recepteur.py [délai_en_s]
import json
import sys
import time
from http.server import BaseHTTPRequestHandler, HTTPServer

DELAI = float(sys.argv[1]) if len(sys.argv) > 1 else 0


class Recepteur(BaseHTTPRequestHandler):
    def do_POST(self):
        corps = self.rfile.read(int(self.headers["Content-Length"]))
        print(self.command, self.path, self.headers["Content-Type"], self.headers["User-Agent"])
        print(json.dumps(json.loads(corps), indent=2, ensure_ascii=False), flush=True)
        time.sleep(DELAI)
        self.send_response(200)
        self.end_headers()

    def log_message(self, *args):
        pass


HTTPServer(("localhost", 8000), Recepteur).serve_forever()

Avec python3 recepteur.py lancé, l'appel de la partie 1 sur S00032 a confirmé la commande, ce qui a déclenché la deuxième règle. Le récepteur a affiché :

POST /odoo/commande application/json python-requests/2.31.0 { "_action": "Prévenir l'outil de facturation(#491)", "_id": 32, "_model": "sale.order", "amount_total": 72.68, "date_order": "2026-10-25 22:14:37", "id": 32, "name": "S00032", "partner_id": 12, "state": "sale" } POST /odoo/commande application/json python-requests/2.31.0

Trois détails comptent pour l'outil qui reçoit :

  • les champs sont lus sans libellé : partner_id vaut 12, pas « Ready Mat ». Ajouter les champs utiles ou rappeler Odoo par l'API pour le reste ;
  • date_order est en UTC (22:14:37 pour une confirmation affichée 23:14 à Paris), sous forme de texte ;
  • la requête porte seulement Content-Type: application/json : ni signature, ni en-tête d'authentification. Si le destinataire veut s'assurer que l'appel vient bien d'Odoo, il faut mettre un jeton dans l'URL elle-même.

Quand part l'appel, et s'il échoue

L'action ne poste rien tout de suite : elle inscrit l'envoi pour après le commit de la transaction (_run_action_webhook, odoo/addons/base/models/ir_actions.py). Si la transaction est annulée, l'appel l'est aussi. Essai dans un odoo-bin shell : confirmer un devis, puis env.cr.rollback() :

INFO odoo.addons.base.models.ir_actions: Webhook call to http://localhost:8000/odoo/commande WARNING odoo.addons.base.models.ir_actions: Webhook call to http://localhost:8000/odoo/commande - cancelled due to a rollback

C'est ce qu'on veut : l'outil n'apprend jamais une confirmation qui n'a pas eu lieu. Ensuite, l'envoi est fait une seule fois, avec un délai d'attente maximal (timeout) d'une seconde. Trois commandes confirmées, avec un récepteur normal, arrêté, puis réglé pour répondre en 3 secondes (python3 recepteur.py 3), donnent dans le journal du serveur :

2026-10-25 22:15:44 INFO ma_base odoo.addons.base.models.ir_actions: Webhook call to http://localhost:8000/odoo/commande 2026-10-25 22:15:44 INFO ma_base odoo.addons.base.models.ir_actions: Webhook call to http://localhost:8000/odoo/commande - succeeded 2026-10-25 22:15:46 INFO ma_base odoo.addons.base.models.ir_actions: Webhook call to http://localhost:8000/odoo/commande 2026-10-25 22:15:46 WARNING ma_base odoo.addons.base.models.ir_actions: Webhook call failed: HTTPConnectionPool(host='localhost', port=8000): Max retries exceeded with url: /odoo/commande (Caused by NewConnectionError('<urllib3.connection.HTTPConnection object at 0x7f911d22d1f0>: Failed to establish a new connection: [Errno 111] Connection refused')) 2026-10-25 22:15:48 INFO ma_base odoo.addons.base.models.ir_actions: Webhook call to http://localhost:8000/odoo/commande 2026-10-25 22:15:50 WARNING ma_base odoo.addons.base.models.ir_actions: Webhook call timed out after 1s - it may or may not have failed. If this happens often, it may be a sign that the system you're trying to reach is slow or non-functional.

Un envoi unique, sans nouvel essai, qui peut ralentir l'appelant

  • Récepteur arrêté, ou qui répond par une erreur 4xx/5xx : un WARNING dans le journal du serveur, et c'est tout. La commande reste confirmée, rien n'est remis en file, aucune trace sur la commande. Avec un récepteur lent, Odoo abandonne au bout d'une seconde alors que le récepteur, lui, a bien reçu l'appel : « it may or may not have failed ».
  • L'envoi a lieu dans la requête qui a confirmé la commande, juste après le commit. Avec le récepteur lent, l'appel entrant de la partie 1 a mis 1,23 s à répondre, contre 0,24 s avec un récepteur normal. Chaque action webhook peut ajouter environ une seconde au clic de l'utilisateur.
  • Pour un flux qui ne doit rien perdre, le destinataire doit pouvoir rattraper : relire par l'API JSON-2 les commandes modifiées depuis son dernier passage, par exemple.

Dernière garde, lue dans le même fichier : un champ réservé à un groupe (attribut groups) ne peut pas faire partie du corps envoyé, et l'action affiche un avertissement qui demande de le retirer. Un webhook part sans contrôle de droits, il ne doit pas faire fuiter un champ protégé.

Le corps envoyé contient _model et _id, exactement ce qu'attend l'enregistrement cible par défaut d'une règle « Sur webhook ». Deux bases Odoo se branchent donc l'une sur l'autre sans écrire de code : l'action de la première vise l'URL secrète de la seconde.

3. Recevoir avec authentification : un contrôleur signé

Les services sérieux (paiement, signature, transport) signent leurs webhooks : ils calculent un HMAC-SHA256 du corps avec un secret partagé et l'envoient dans un en-tête. La règle native ne sait pas le vérifier. Le module oski_webhook_signe le fait en un contrôleur. Il signe horodatage.corps pour qu'une requête interceptée ne puisse plus être rejouée au-delà de cinq minutes.

import hashlib
import hmac
import json
import time

from odoo import http
from odoo.http import request

MAX_AGE = 300  # secondes : au-delà, une requête signée est refusée (rejeu)


class SignatureWebhook(http.Controller):

    @http.route('/oski/webhook/signature', type='http', auth='public', methods=['POST'],
                csrf=False, save_session=False)
    def signature_received(self):
        body = request.httprequest.get_data()
        timestamp = request.httprequest.headers.get('X-Timestamp', '')
        received = request.httprequest.headers.get('X-Signature', '')
        secret = request.env['ir.config_parameter'].sudo().get_str('oski_webhook_signe.secret')

        # 1. Authentifier : HMAC-SHA256 de « horodatage.corps » avec le secret partagé
        expected = hmac.new(secret.encode(), f"{timestamp}.".encode() + body, hashlib.sha256).hexdigest()
        if not secret or not hmac.compare_digest(received.encode(), expected.encode()):
            return request.make_json_response({'status': 'error', 'error': 'signature'}, status=401)
        if not timestamp.isdigit() or abs(time.time() - int(timestamp)) > MAX_AGE:
            return request.make_json_response({'status': 'error', 'error': 'expired'}, status=401)

        # 2. Lire le corps
        try:
            data = json.loads(body)
        except ValueError:
            data = None
        if not isinstance(data, dict):
            return request.make_json_response({'status': 'error', 'error': 'json'}, status=400)

        # 3. Agir avec les droits d'un utilisateur dédié, pas en superutilisateur
        request.update_env(user=request.env.ref('oski_webhook_signe.user_webhook'))
        order = request.env['sale.order'].search([('name', '=', data.get('commande'))], limit=1)
        if not order:
            return request.make_json_response({'status': 'error', 'error': 'commande'}, status=404)
        order.message_post(body=request.env._("Devis signé en ligne par %s.", data.get('signataire')))
        if order.state in ('draft', 'sent'):
            order.action_confirm()
        return request.make_json_response({'status': 'ok', 'commande': order.name, 'etat': order.state})
  • type='http' et non 'jsonrpc' : un service tiers envoie un JSON brut, pas une enveloppe JSON-RPC. Le corps se lit avec request.httprequest.get_data(), en octets : c'est sur eux qu'il faut calculer la signature, avant tout décodage.
  • csrf=False est obligatoire pour un POST venu d'ailleurs ; save_session=False évite de créer une session à chaque appel.
  • hmac.compare_digest compare en temps constant, ce que ne fait pas ==.
  • Le secret est lu par get_str : en Odoo 20, get_param et set_param d'ir.config_parameter n'existent plus.
  • sudo() ne sert qu'à lire ce paramètre. Le travail se fait avec request.update_env(user=…), sous un utilisateur dédié créé par le module, qui a les droits d'un commercial et rien de plus :
<?xml version="1.0" encoding="utf-8"?>
<odoo>
    <record id="user_webhook" model="res.users">
        <field name="name">Webhook signature</field>
        <field name="login">webhook-signature</field>
        <field name="group_ids" eval="[Command.set([ref('sales_team.group_sale_salesman_all_leads')])]"/>
    </record>
</odoo>

Le module installé et le secret enregistré (paramètre système oski_webhook_signe.secret), l'appelant se joue avec openssl :

# Envoie un webhook signé : HMAC-SHA256 de « horodatage.corps » avec le secret partagé
SECRET=${SECRET:-'change-moi-par-un-long-secret'}
TS=${TS:-$(date +%s)}
CORPS='{"commande": "S00039", "signataire": "Service achats Gemini Furniture"}'
SIG=$(printf '%s.%s' "$TS" "$CORPS" | openssl dgst -sha256 -hmac "$SECRET" | sed 's/^.* //')
curl -s -w '  → HTTP %{http_code}\n' -X POST http://localhost:8069/oski/webhook/signature \
     -H 'Content-Type: application/json' -H "X-Timestamp: $TS" -H "X-Signature: $SIG" -d "$CORPS"

La fenêtre de cinq minutes reste ouverte au rejeu : la même requête signée, envoyée deux fois de suite avec le même horodatage, a reçu deux 200 et ajouté deux notes à la commande. Si le service envoie un identifiant d'événement, le mémoriser et refuser un identifiant déjà vu ferme cette fenêtre.

La différence se voit dans la discussion de S00032 et de S00033, une commande confirmée par le contrôleur lors d'un premier essai : la règle native agit comme « Public user », le contrôleur comme l'utilisateur qu'on lui a donné. Et la confirmation de S00033 a, elle aussi, déclenché le webhook sortant de la partie 2 : les règles réagissent à l'événement, quel que soit le chemin qui l'a produit.

Le module contient aussi tests/test_webhook.py, un HttpCase qui signe ses requêtes de la même façon : signature valide (commande confirmée, auteur du message vérifié), secret faux, requête trop ancienne, commande inconnue, corps qui n'est pas un objet JSON. Les cinq tests passent sur Odoo 20 ; le détail des tests HTTP est dans Tests automatisés en Odoo 20.

Plusieurs bases sur le même serveur

Une route auth='public' a besoin de savoir quelle base servir. Sur un serveur qui en héberge plusieurs, l'appel sans session ne trouve pas de base et reçoit un 404, même avec une URL secrète juste. Essayé sur une instance à plusieurs bases : sans en-tête, 404 ; avec -H 'X-Odoo-Database: ma_base', la règle est atteinte (odoo/http/router.py lit cet en-tête quand la requête n'a pas de cookie de session, et la base doit passer le dbfilter). Comme un service tiers ne laisse pas toujours ajouter un en-tête, le plus simple reste une base par nom de domaine, avec dbfilter.

Venant de la 19 : rien à changer

Comparé à la branche 19.0 publique du 25/10/2026 : la route /web/hook est identique, l'envoi (_run_action_webhook : après le commit, timeout d'une seconde, champs à groupe refusés) aussi, et l'exécution d'une règle « Sur webhook » ne diffère que par le texte du journal d'échec. La réécriture de web.base.url à la connexion d'un administrateur existait déjà. Une règle webhook réglée en 19 garde son comportement après le passage en 20. Dans un contrôleur maison, en revanche, les lectures de paramètres en get_param sont à remplacer par get_str.

À retenir

  • Recevoir : une règle d'automatisation « Sur webhook » (module base_automation) donne une URL secrète /web/hook/<uuid> ; l'enregistrement cible et les actions lisent le corps dans payload.
  • Réponses natives : 200, 500 (enregistrement introuvable ou action en erreur), 404 (URL inconnue), toujours sans détail ; le détail est dans les journaux de la règle.
  • La règle tourne en sudo comme « Public user » : l'URL est le seul secret. Figer web.base.url pour qu'elle reste juste.
  • Émettre : l'action « Envoyer une notification webhook » poste _model, _id, _action et les champs choisis, après le commit, une seule fois, avec un timeout d'une seconde.
  • Authentifier : un contrôleur type='http', csrf=False, qui vérifie un HMAC sur les octets reçus et un horodatage, puis agit avec request.update_env(user=…). Dans la fenêtre de cinq minutes, un rejeu passe encore.
