Ce qui change techniquement en Odoo 20

Migration vers Odoo 20, côté développeur : ce qui casse, ce qui change. Un module écrit pour la 19 ne s'installe pas tel quel, et c'est la bonne nouvelle : l'erreur se voit. La mauvaise, ce sont les changements qui ne lèvent rien — un gabarit qui n'affiche plus rien, une pièce jointe vide, un utilisateur qui voit soudain les enregistrements des autres.

~28 minutes de lecture · niveau intermédiaire · parcours Framework & ORM

Ce que tu vas apprendre

Repérer

Les ruptures d'Odoo 20 qui cassent au chargement, et celles qui ne disent rien.

Réécrire

Chaque idiome 19 et son équivalent 20, en code court, avec la ligne du source qui le prouve.

Porter

Un module 19 vers 20 dans le bon ordre, outils officiels compris, et ce qu'ils oublient.

Community ou Enterprise : tout ce qui suit vaut pour les deux

L'ORM, le modèle ir.access, OWL 3, le moteur QWeb et les types de vue appartiennent au framework, et le framework est commun aux deux éditions : l'Enterprise est un ensemble de modules installés par-dessus la Community, sans cœur séparé. Un module porté selon cet article repose donc sur le même framework dans les deux éditions ; seules diffèrent les vues et les modèles que les modules Enterprise installés surchargent, d'où l'intérêt de vérifier un xpath sur les deux.

Les preuves viennent du code source Community 20.0, des notes de version officielles et du changelog de l'ORM. Le code Enterprise, dans un dépôt privé, n'a pas été lu. Ce que la 20 change dans les applications Enterprise elles-mêmes est rassemblé au § 9, « Côté Enterprise ».

Comment ce qui suit a été établi

Chaque écart compare le source 20.0 au source 19.0 d'Odoo Community ; les références odoo/…:ligne renvoient à l'arbre 20.0 publié en septembre 2026 (sauf mention « 19 : »). Chaque fois que c'était possible, le comportement a été exécuté sur une base Odoo 20 (Python 3.12, PostgreSQL 16) : sonde dans odoo-bin shell en transaction annulée, ou module jouet installé sur une base jetable. Les sorties reproduites plus bas sont celles de ces exécutions.

Les nouveautés visibles par l'utilisateur métier, édition par édition, sont dans l'article compagnon Les nouveautés d'Odoo 20, en Community et en Enterprise.

1. Sécurité : ir.access remplace les ACL et les règles

C'est le changement le plus visible, et les notes de version officielles le présentent ainsi dans leur rubrique Général : « Les droits d'accès ont été simplifiés en supprimant les règles d'enregistrement et en ajoutant un domaine directement au niveau du droit d'accès ». Dans le code, cela veut dire que les modèles ir.model.access et ir.rule n'existent plus. Un seul modèle les remplace, ir.access (odoo/addons/base/models/ir_access.py:66), alimenté par un fichier security/ir.access.csv.

1.1 Une ligne au lieu de deux enregistrements

En 19, un droit « le vendeur lit et modifie ses propres devis » demandait une ligne d'ACL dans le CSV et une règle dans un fichier XML. En 20, c'est une ligne, domaine compris. L'exemple vient du module sale lui-même :

# Odoo 19 — addons/sale/security/ir.model.access.csv + ir_rules.xml
access_sale_order,sale.order,model_sale_order,sales_team.group_sale_salesman,1,1,1,0
# + <record id="sale_order_personal_rule" model="ir.rule"> … domain_force … </record>

# Odoo 20 — addons/sale/security/ir.access.csv:32 et :35
sale_order_personal_rule,Personal Orders,sale.order,sales_team.group_sale_salesman,cru,"['|',('user_id','=',user.id),('user_id','=',False)]"
sale_order_comp_rule,Sales Order multi-company,sale.order,,crud,"[('company_id', 'in', company_ids)]"

L'en-tête est le même dans les 226 fichiers security/ir.access.csv du dossier addons/ de la 20.0 : id,name,model_id,group_id/id,operation,domain. Le modèle s'écrit par son nom pointé (sale.order), l'opération est un sous-ensemble ordonné de crud (u = écrire, d = supprimer), le domaine ne connaît que user, time, company_ids et company_id (ir_access.py:312-324). Il n'y a plus un seul ir.model.access.csv dans ce dossier ; il y en avait 209 en 19 (comptage des fichiers security/ de chaque module).

1.2 Permission ou restriction : tout dépend du groupe

Une ligne avec groupe est une permission ; une ligne sans groupe est une restriction, appliquée à tout le monde. Le calcul final tient en une ligne (odoo/orm/models.py:3647) :

return Domain.OR(permissions) & Domain.AND(restrictions)

Aucune permission applicable, et l'accès est refusé : une restriction seule ne donne jamais aucun droit. Les deux captures ci-dessous montrent les deux cas sur le modèle Contact : ce sont des lignes standard d'Odoo 20, ouvertes en mode développeur par Paramètres › Technique › Sécurité, et recadrées sur la feuille du formulaire, dont le ruban d'angle indique la nature de la ligne.

Panne silencieuse n° 1 : la ligne d'ACL « pour tout le monde »

En 19, une ACL sans groupe voulait dire « tout le monde ». En 20, une ligne sans groupe est une restriction : sur un modèle qui n'a qu'elle, personne n'a plus accès, administrateur compris. L'équivalent de l'ancien « tout le monde » est le nouveau groupe base.group_everyone, impliqué par les groupes utilisateur, portail et public (odoo/addons/base/security/base_groups.xml:92-96). Même une restriction ajoutée à un modèle déjà ouvert s'applique à l'administrateur : essai sur res.partner.industry, une ligne sans groupe créée puis annulée, et le domaine d'accès de l'admin devient exactement le domaine de la restriction.

1.3 La conversion officielle, et le changement qu'elle signale sans le corriger

Odoo 20 livre un script de conversion. Lancé sur un petit module 19 (une ACL pour les utilisateurs internes, une ACL de lecture sans groupe, une règle « mes notes » sur les utilisateurs internes et une règle multi-société), il produit ceci :

cd odoo
../venv/bin/python odoo-bin upgrade_code --addons-path=/chemin/mes_addons --script 19.4-00-ir-access
WARNING with model=demo.note, operation=r acl group without rules, giving access to ALL records: - base.group_everyone: acl demo_v19.access_demo_note_all may interact with rules in groups, giving access to LESS records: - base.group_user: rule demo_v19.demo_note_own_rule (with acl) updated: …/demo_v19/__manifest__.py deleted: …/demo_v19/security/demo_rules.xml updated: …/demo_v19/security/ir.access.csv deleted: …/demo_v19/security/ir.model.access.csv
# security/ir.access.csv produit par le script
id,name,model_id,group_id/id,operation,domain
demo_note_own_rule,Own notes,demo.note,base.group_user,cru,"[('create_uid', '=', user.id)]"
access_demo_note_all,demo.note all,demo.note,base.group_everyone,r,
demo_note_company_rule,Multi-company,demo.note,,crud,"[('company_id', 'in', company_ids + [False])]"

Le fichier est propre, le manifeste est mis à jour, l'ACL sans groupe est bien devenue base.group_everyone. Mais le WARNING annonce un changement de sens : en 19, les règles d'un groupe restreignaient la lecture même quand une autre ACL l'ouvrait ; en 20, les permissions s'additionnent. Le même module, installé des deux côtés sur des bases jetables, deux utilisateurs internes créant chacun une note :

# Odoo 19, module d'origine lu par A : ['note de A'] # Odoo 20, module converti lu par A : ['note de A', 'note de B'] domaine de lecture de A : [('company_id', 'in', [1, False])]

L'utilisateur A lit désormais la note de B. Aucune erreur, aucun test de syntaxe ne le détecte : seule la ligne WARNING du script le signale. Le remède est de décider, modèle par modèle, si la lecture doit être ouverte (garder la permission base.group_everyone) ou restreinte (supprimer cette ligne, ou lui donner le même domaine que la règle).

Ce que le script ne convertit pas

  • Une règle posée sur un modèle standard (sale.order…) quand les dépendances sont déjà au format 20 : le script ne trouve pas d'ACL compatible, retire la règle du XML et ne la recrée pas. La convertir contre une copie des sources 19.0, ou la réécrire à la main.
  • Les enregistrements inactifs, ceux qui surchargent l'xmlid d'un autre module, et tout ce qui est créé en Python (hooks, tests).
  • Le noupdate="1" : les lignes du CSV sont rechargées à chaque mise à jour du module.

Un module 19 dont la sécurité n'est pas convertie ne s'installe pas : essai sur une base 20, manifeste passé en 20.0.1.0.0, ir.model.access.csv laissé en place.

ERROR base_jetable odoo.registry: Failed to load registry KeyError: 'ir.model.access'

1.4 L'API Python de l'accès

# Odoo 19                                        # Odoo 20
records.check_access_rights('read')               records.check_access('read')   # ou has_access('read')
records.check_access_rule('write')                records.check_access('write')
env['ir.rule']._compute_domain(model, 'read')     env[model]._access_domain('read')

def _check_access(self, operation):               def _access_domain(self, operation):
    ...                                               if not self.env['ir.attachment'].has_access(operation):
                                                          return Domain.FALSE
                                                      return super()._access_domain(operation)

check_access_rights et check_access_rule ont disparu (hasattr → False sur une base 20). Plus traître : _check_access existe encore, marqué @deprecated("Since 20.0, use Model._access_domain instead") (odoo/orm/models.py:3575-3576), mais plus rien ne l'appelle dans odoo/orm ni dans base. Une surcharge portée telle quelle est silencieuse : elle ne sera jamais exécutée. Le nouveau point d'extension est _access_domain(operation) (models.py:3603), qui renvoie un Domain.

Deux autres écarts à connaître. Un modèle en délégation (_inherits) exige désormais aussi le droit sur le modèle parent : son domaine d'accès complet devient une restriction (models.py:463, _check_inherits_access). Et un nouvel opérateur de domaine, ('move_id', 'access', 'read'), exprime « l'utilisateur a ce droit sur l'enregistrement lié ». La mise en œuvre pas à pas, sur un vrai module, est dans Les droits d'accès en Odoo 20 : ir.access et, pour la délégation, dans Hériter d'un modèle Odoo 20.

2. ORM et Python : imports, fichiers, dates, caches

2.1 odoo.osv supprimé : les domaines passent par Domain

# Odoo 19
from odoo.osv import expression
domain = expression.AND([[('is_company', '=', True)], [('country_id.code', '=', 'FR')]])

# Odoo 20
from odoo.fields import Domain
domain = Domain('is_company', '=', True) & Domain('country_id.code', '=', 'FR')
odoo.osv -> ModuleNotFoundError No module named 'odoo.osv' Domain -> DomainAnd ['&', ('is_company', '=', True), ('country_id.code', '=', 'FR')]

Preuve : le dossier odoo/osv n'existe plus ; Domain est exporté par odoo/fields/__init__.py:20. Le paquet était déjà déprécié en 19.0 (changelog ORM, PR #217708). Dans une action, 'domain': list(mon_domaine).

2.2 Champs Binary : fin du base64, place à BinaryValue

En 19, un champ binaire transportait du base64 d'un bout à l'autre. En 20, il porte un objet BinaryValue (odoo/tools/binary.py:9) : contenu brut, nom de fichier, type, taille.

# Odoo 19                                   # Odoo 20
rec.file = base64.b64encode(pdf)             from odoo.tools import BinaryBytes
                                             rec.file = BinaryBytes(pdf, filename='f.pdf')
raw = base64.b64decode(rec.file)             raw = rec.file.content
bytes base64 -> TypeError res.partner.image_1920: use BinaryValue instead of bytes

Preuve : odoo/orm/fields_binary.py:112. Le changelog ORM officiel le résume : « The type of Binary fields is now a BinaryValue. We no longer encode using base64 all over the data flow ». Par RPC, une chaîne base64 reste acceptée en écriture, et la lecture renvoie un dictionnaire (content, size, filename) au lieu d'une chaîne.

Panne silencieuse n° 2 : la pièce jointe créée avec datas=

Le champ ir.attachment.datas a été supprimé (19 : ir_attachment.py:455). Créer une pièce jointe avec lui ne lève rien : Odoo émet un avertissement et enregistre un fichier vide.

WARNING py.warnings: …/ir_attachment.py:535: UserWarning: Use raw, datas has beeen removed datas= -> file_size 0 | raw Binary(b'', filename='') raw= -> file_size 5 LocalBinaryFile
env['ir.attachment'].create({'name': 'f.pdf', 'raw': pdf_bytes, 'res_model': …, 'res_id': …})

Preuve : odoo/orm/environments.py:320 (return ZoneInfo(timezone)) contre 19 : environments.py:291 (pytz.timezone) ; pytz a quitté requirements.txt (19 : ligne 74). Un import pytz peut encore réussir parce qu'une autre bibliothèque l'installe, ce qui masque le problème jusqu'au premier localize().

self.env.registry.clear_cache()                       self.env.transaction.invalidate_ormcache()
ICP.get_param('mon.parametre', 'x')                   ICP.get_str('mon.parametre', 'x')   # get_int, get_bool, get_float

read_group n'a pas disparu : il revient avec une autre signature, read_group(domain, groupby, aggregates, having, offset, limit, order), et renvoie des tuples (odoo/orm/models.py:1932-1941). Un appel 19 écrit dans l'ordre (domaine, champs, regroupements) intervertit donc les deux listes. Dans les essais faits, l'erreur est bruyante (ValueError ou, avec lazy=, TypeError) ; côté serveur, écrire _read_group, et formatted_read_group quand il faut des dictionnaires.

Preuve : environments.py:833 (invalidate_ormcache) ; ir_config_parameter.py:124 (get_str) ; le script officiel 19.4-00-ormcache-on-transaction fait le remplacement de clear_cache.

2.5 Ce qui disparaît sans remplaçant direct

  • _table_query (modèle adossé à une requête SQL) : ignoré en silence, plus aucune lecture dans odoo/orm ; le remplaçant est la propriété _table_sql qui renvoie un SQL (models.py:531). Le changelog officiel l'annonce : « Removing Model._table_query » (PR #281202).
  • toggle_active() → action_archive() / action_unarchive() (models.py:5273) ; _check_recursion() → _has_cycle() (models.py:5116). Sonde : hasattr(env['res.partner'], 'toggle_active') → False.
  • from odoo.tools import ormcache marche encore avec un avertissement : écrire from odoo.api import ormcache.
  • odoo.http n'exporte plus que request, route, Controller, Response : content_disposition et Stream vivent dans odoo.http.stream, root dans odoo.http.router.

Pour éprouver ces appels sans cliquer, la console reste l'outil de choix : la console odoo-bin shell.

3. QWeb : deux habitudes qui n'affichent plus rien

Ces deux pannes touchent tout ce que le serveur rend : rapports PDF, gabarits de courriel, pages du site, portail. Elles ne lèvent aucune erreur.

3.1 t-esc et t-raw ne rendent plus rien

<!-- Odoo 19 -->                         <!-- Odoo 20 -->
<p>Bonjour <t t-esc="nom"/></p>          <p>Bonjour <t t-out="nom"/></p>
t-out -> '<p>Bonjour Ada</p>' t-esc -> '<p>Bonjour </p>' t-raw -> '<p>Bonjour </p>' WARNING odoo.addons.base.models.ir_qweb: Unknown directives or unused attributes: {'t-esc'} from <t t-esc="nom"/>

Seul un WARNING dans le journal (odoo/addons/base/models/ir_qweb.py:1929). Un courriel part avec « Bonjour , », une facture sort sans montant. t-out échappe le texte et laisse passer un Markup : il couvre les deux anciens usages. La directive fonctionnait déjà en 19 ; la remplacer avant de porter ne coûte rien.

3.2 t-set dans le corps d'un t-call

<!-- Odoo 19 : la variable est posée dans le corps de l'appel -->
<t t-call="mon_module.sous_gabarit"><t t-set="label" t-value="'Livre'"/></t>

<!-- Odoo 20 : elle est passée en attribut -->
<t t-call="mon_module.sous_gabarit" label="'Livre'"/>
t-set dans t-call -> '<div></div>' attribut -> '<div><span>Livre</span></div>'

Cette fois, aucun avertissement : le sous-gabarit reçoit une variable absente et rend du vide. Le script officiel 19.1-00-t-call (dans odoo/upgrade_code/) déplace ces t-set avant l'appel ; la forme par attribut, elle, marche aussi en 19. Le cas réel du rapport PDF, adresse passée au bloc d'en-tête, est traité dans Le rapport PDF en Odoo 20 ; celui du gabarit de courriel dans Relancer par courriel en Odoo 20.

4. Client web : OWL 3, plugins, icônes

Odoo 19 embarquait OWL 2.8.1 (19 : addons/web/static/lib/owl/owl.js:5819). Odoo 20 embarque OWL 3.0.0-alpha.49 (owl.js:1776) : une version alpha livrée dans une version finale, avec une couche de compatibilité (web/static/src/owl2/) que son propre en-tête présente comme un pont provisoire, « a temporary bridge » (owl3_compatibility_layer.js:5).

4.1 this. obligatoire dans les templates

En 19, le contexte d'un template héritait du composant (Object.create(this.component), 19 : owl.js:2431). En 20, il ne contient plus que this ({ this: this.component, __owl__: this }, owl.js:3715). Le champ booléen du cœur, avant et après :

<!-- 19 --> <CheckBox id="props.id" value="state.value" disabled="props.readonly" onChange.bind="onChange"/>
<!-- 20 --> <CheckBox id="this.props.id" value="this.state.value" disabled="this.props.readonly" onChange.bind="this.onChange"/>

Les variables de t-foreach et de t-set ne prennent pas this. : seuls les membres du composant. Un xpath tiers qui visait @t-if='state.x' ne trouve plus rien, puisque l'attribut est devenu this.state.x.

4.2 Hooks : useState et useRef n'existent plus

// Odoo 19 — web/static/src/views/fields/boolean/boolean_field.js
import { Component, useState } from "@odoo/owl";
static props = { ...standardFieldProps };
setup() { this.state = useState({}); }

// Odoo 20 — même fichier
import { Component, proxy, useEffect, useProps } from "@odoo/owl";
props = useProps(booleanFieldProps);
setup() { this.state = proxy({}); }
  • useState → proxy ; useRef → signal.ref(), lu en appelant la référence. Ni useState, ni useRef, ni reactive ne figurent dans les exports d'OWL 3 (owl.js:23-83), et la couche de compatibilité ne les rétablit pas : l'import donne undefined.
  • static props = {…} est ignoré : plus de validation. Écrire props = useProps({…}) avec les types t.string(), t.boolean().optional()… static defaultProps, lui, lève une exception.
  • useEffect(fn, deps) change de sens : l'effet est réactif et le tableau de dépendances est ignoré. L'ancien comportement s'appelle useLayoutEffect, importé de @web/owl2/utils.
  • t-esc côté OWL ne casse pas mais avertit en console ; t-slot devient t-call-slot.

4.3 Services devenus plugins ; jQuery et publicWidget retirés

Les services du client web ont été réécrits en plugins (usePlugin(UIPlugin), fichiers *_plugin.js) ; les imports des anciens *_service.js échouent, mais useService("orm") fonctionne encore grâce à un pont. Le dossier web/static/src/legacy a disparu, publicWidget passe de 36 occurrences à 0 dans le JavaScript du dossier addons/ : le JavaScript public s'écrit en Interactions.

4.4 FontAwesome n'est plus chargé

La classe fa fa- apparaissait 2 313 fois dans les fichiers XML du dossier addons/ de la 19.0 (bibliothèques tierces exclues) ; elle n'y apparaît plus une seule fois en 20.0, et aucun manifeste ne charge plus la feuille de style (19 : web/__manifest__.py:60). Les icônes sont des ligatures Material Symbols : <i class="oi" data-icon="check"/> ; sur un bouton de vue, icon="warning".

Panne silencieuse n° 3 : icon="fa-list" sur un bouton

En 20, la chaîne de l'attribut icon est rendue telle quelle par ligature (web/static/src/views/view_button/view_button.js:27, webclient/icons.scss:49 : content: attr(data-icon)). Un bouton intelligent hérité de la 19 n'échoue pas : il affiche le texte « fa-list ». Et une balise <i class="fa fa-check"/> ne montre plus rien. Noms valides : list, schedule, group, book_5… L'écran corrigé est visible dans Les retards en Odoo 20.

Le script officiel owl3-migration n'est pas lancé par --from 19.0 (son nom ne porte pas de version) : il faut le demander par --script owl3-migration, puis relire. Il ne convertit ni static props ni defaultProps, et produit des t-custom-ref que l'arbre 20.0 ne sait pas exécuter.

5. Vues : le type card et des vues du cœur réécrites

  • Nouveau type de vue card (odoo/addons/base/models/ir_ui_view.py:164, absent de 19). Une vue <card> porte le gabarit t-name="card" ; un kanban la réutilise par card_id="%(xmlid)d". La carte écrite dans le <templates> du kanban reste acceptée. Sonde : 'card' figure bien dans la sélection du champ type d'ir.ui.view.
  • Widgets : le préfixe de registre kanban. devient card. (card.many2many_tags…) ; selection_badge → badges_selection, remaining_days → relative_date. Un widget maison enregistré seulement sous kanban.x est remplacé par le widget par défaut, avec un simple avertissement en console.
  • Vues du cœur réécrites : le formulaire contact (base.view_partner_form) n'a plus le champ company_type (supprimé du modèle). Une vue héritée qui le vise refuse de s'installer — c'est bruyant, mais il faut relire chaque xpath vers une vue standard.
  • Inchangé : list (jamais tree), pas d'attrs, models.Constraint, <chatter/>.

Mise en pratique : Kanban, graphique et pivot en Odoo 20 et Héritage de vues en Odoo 20.

6. Serveur, tests, messagerie

Panne silencieuse n° 4 : --http-interface vaut 127.0.0.1

Le défaut est passé de 0.0.0.0 (19 : odoo/tools/config.py:255) à 127.0.0.1 (config.py:289). Derrière un nginx local, rien ne change. Mais une instance jointe directement par IP:port — serveur de recette, conteneur, machine virtuelle — ne répond plus, sans message d'erreur côté Odoo. Poser http_interface = 0.0.0.0 dans le fichier de configuration quand c'est voulu.

http_interface -> '127.0.0.1'
  • Prérequis : Python ≥ 3.12 et PostgreSQL ≥ 16 (odoo/release.py:39-41). L'installation pas à pas est dans Installer Odoo 20 sur Ubuntu et le lancer dans PyCharm.
  • Tests : une classe sans @tagged est désormais post_install (odoo/tests/common.py:605 ; 19 : at_install, common.py:319). SingleTransactionCase n'existe plus (essai d'import : ImportError: cannot import name 'SingleTransactionCase'), from odoo.tests.common import Form lève ImportError (écrire from odoo.tests import Form). Détails dans Tests automatisés en Odoo 20.
  • Suivi des modifications : les notes de version (rubrique Technique) l'annoncent — « Tracking values have been removed; the tracking message is now generated on the fly ». En code : mail.message.tracking_value_ids et mail.tracking.value ont quitté mail pour le module facultatif mail_tracking ; le suivi s'écrit dans le corps du message (mail/models/mail_thread.py:3139). Sonde sur une base sans ce module : 'tracking_value_ids' in env['mail.message']._fields → False. Tout code 19 qui lit ces valeurs lève AttributeError. Voir Le chatter en Odoo 20.
  • CLI : l'option courte -s disparaît (19 : odoo/tools/config.py:225 ; reste --save) ; la sous-commande populate (19 : odoo/cli/populate.py) quitte le cœur au profit de duplicate (odoo/cli/duplicate.py), et un addon populate génère des données de synthèse pour les tests de charge.
  • RPC : /xmlrpc et /jsonrpc restent servis, mais le message de dépréciation annonce leur retrait pour Odoo 22 (addons/rpc/controllers/__init__.py:5-8) ; la cible est /json/2/<modèle>/<méthode> ; le service db n'est plus exposé par dispatch_rpc.

7. Modules supprimés, fusionnés, ajoutés

Comptage des manifestes du dossier addons/ (les modules de base rangés sous odoo/addons non compris), face à la 19.0 publique du 28 septembre 2026 : 638 modules en 19.0, 641 en 20.0. 50 ont disparu (31 hors localisations), 53 sont apparus (33 hors localisations et modules de test). Un module qui dépend d'un addon supprimé ne s'installe plus : il faut reporter la dépendance vers son module d'accueil.

Le code du reste de l'article est comparé à une 19.0 de novembre 2025. La branche a continué de recevoir des modules depuis : une quarantaine, surtout des localisations, des fournisseurs de paiement et de petits modules propres à la version stable. Face à cette 19.0 de novembre (598 modules), l'écart paraît autre : 44 ajouts et 27 retraits hors localisations, car onze de ces « ajouts » existent déjà dans la 19.0 publique (payment_payu, pos_mollie, cloud_storage_migration…) et quatre retraits n'y figuraient pas encore : account_add_gln, account_peppol_response, hr_holidays_homeworking et pos_self_order_viva_com. 8. Ce que disent les sources officielles

Deux documents d'Odoo couvrent le technique. Ils sont courts, et ils ne disent pas tout : l'essentiel de ce qui précède n'y figure pas, d'où l'intérêt de lire le code.

8.1 Les notes de version, rubrique Technique

Les notes de version d'Odoo 20 listent, sous « Technique » : le suivi dans le corps du message, l'amélioration des champs many2one (« synchronisés avec le backend », y compris avec de grandes listes), des notifications push qui « ne sont plus gérées par Firebase, mais par les outils push internes d'Odoo », l'origine du contenu désormais notée sur les mail.mail, et la journalisation des changements de groupes d'un utilisateur, dans son chatter et dans les journaux du serveur. Les droits d'accès simplifiés figurent, eux, dans la rubrique Général.

8.2 Le changelog de l'ORM

Le changelog ORM officiel range les changements par version. Pour Odoo 20, il faut lire la section « 20.0 » et les versions Online 19.1 à 19.4, toutes livrées dans la 20 :

9. Côté Enterprise : applications et modules

Tout ce qui précède touche aussi l'Enterprise, puisque le framework est le même. Restent les applications propres à l'Enterprise : un module maison qui hérite de Studio, de Services sur site ou de la Paie doit aussi suivre ce que la 20 y change. Deux sources publiques permettent de le cerner sans lire le code Enterprise : les notes de version, et la liste des modules d'une base de test Enterprise.

9.1 Ce que les notes de version annoncent pour les applications Enterprise

Les notes de version d'Odoo 20 consacrent une rubrique à chaque application. Les limites de ce relevé

  • Un module présent sur la base de test est un module du dépôt Enterprise de cette branche : sa présence ne dit pas qu'il est vendu, ni qu'il est installé chez un client.
  • Le relevé compare des noms. Un module renommé compte une fois en retrait et une fois en ajout ; le lien entre les deux vient des notes de version ou des dépendances, pas du code.
  • Les deux bases datent des 26 et 27 septembre 2026. La branche 19.0 reçoit encore des modules (§ 7) : un relevé plus tardif peut bouger de quelques unités.
  • Les localisations sont comptées à part : leurs mouvements (50 ajouts, 46 retraits) relèvent surtout de la paie et des déclarations fiscales pays par pays.

10. Checklist de portage d'un module 19 vers 20

Dans cet ordre, un module à la fois, en suivant les dépendances. Le marqueur est la version du manifeste : Odoo 20 déclare lui-même non installable tout module dont la version n'est pas en 20.0.x (odoo/modules/module.py:500), ce qui permet de faire cohabiter modules portés et non portés.

  1. Valider dans git l'état 19 : les scripts réécrivent les fichiers en place.
  2. Inventaire à blanc : 
    cd odoo
../venv/bin/python odoo-bin upgrade_code --addons-path=/chemin/mes_addons --from 19.1 --dry-run
../venv/bin/python odoo-bin upgrade_code --addons-path=/chemin/mes_addons --script owl3-migration --dry-run
    Le code de sortie vaut 1 dès qu'un fichier changerait : c'est normal.
  3. Sécurité : --script 19.4-00-ir-access, puis lire chaque WARNING « acl group without rules » et trancher ; réécrire à la main les règles posées sur des modèles standard ; remplacer toute ACL sans groupe restée à la main par base.group_everyone.
  4. Python, à la main (aucun script ne le fait) : odoo.osv → Domain ; datas= → raw= ; base64 des Binary → BinaryBytes / .content ; pytz → zoneinfo ; get_param → get_str… ; _check_access → _access_domain ; read_group → _read_group ; _table_query → _table_sql ; imports odoo.http.*. 
    grep -rnE "odoo\.osv|datas['\"]?\s*[:=]|b64encode|pytz|get_param|set_param|_check_access|read_group\(|_table_query|clear_cache|check_access_rule|check_access_rights|toggle_active" mon_module/
  5. XML et QWeb : t-esc/t-raw → t-out ; t-set dans un t-call → attribut ; icon="fa-…" et class="fa …" → icônes oi ; relire chaque xpath vers une vue standard ; widgets kanban. → card.. 
    grep -rnE "t-esc|t-raw|fa fa-|icon=\"fa-|kanban\.|company_type" mon_module/
  6. JavaScript : relire la sortie d'owl3-migration ; this. dans les templates ; useProps à la place de static props ; plus de defaultProps, de useRef, de jQuery ni de publicWidget.
  7. Manifeste en 20.0.1.0.0, dépendances vers les modules supprimés remplacées, y compris celles vers des modules Enterprise disparus (Services sur site : industry_fsm → planning_field_service ; IA : ai_app → ai_agentic ; § 9.2).
  8. Installer sur une base jetable et lire tout le journal : ERROR, mais aussi WARNING, Unknown directives, datas has beeen removed (sic).
  9. Regarder les écrans, rapports et courriels : les pannes silencieuses ne se voient que là. Puis vérifier les droits avec deux utilisateurs de même groupe, comme au § 1.3.
  10. Lancer les tests et lire le nombre de tests exécutés, pas seulement l'absence d'échec.

À retenir

  • La sécurité tient dans ir.access : avec groupe = permission (OU), sans groupe = restriction (ET). Une ACL « tout le monde » devient base.group_everyone.
  • La conversion officielle marche, mais peut élargir la lecture : lire ses WARNING et tester avec deux utilisateurs.
  • Quatre pannes muettes à chercher : t-esc/t-raw, t-set dans un t-call, datas=, --http-interface — plus les surcharges de _check_access et les icônes FontAwesome.
  • Côté Python : Domain, BinaryValue, zoneinfo, invalidate_ormcache, get_str. Côté client : OWL 3, this., proxy, useProps, plugins.
  • Côté Enterprise, le framework est le même ; ce qui bouge, ce sont les applications : Services sur site passe dans Planification, les entrées de travail de la Paie disparaissent, l'IA change de module. 127 modules Enterprise apparaissent, 43 disparaissent (hors localisations et tests).
  • Un code de sortie 0 ne prouve rien : un portage est fini quand l'écran a été regardé.
