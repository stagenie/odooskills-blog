Quelle licence pour votre module Odoo 19 ?

Les 10 valeurs légales de la clé license, ce qu'elle déclenche réellement dans le code d'Odoo 19, la règle de contamination LGPL / AGPL / OPL / OEEL — et l'arbre de décision qui tranche en trois questions.

La règle de contamination

Qui peut dépendre de qui. Un tableau, un arbre de décision, et le mythe du « payant = OPL obligatoire » démonté.

Prérequis — une instance Odoo 19 Community en local, l'accès au dossier source (odoo/addons/), et le mode développeur activable. Aucune connaissance juridique préalable n'est nécessaire : tout ce qui est affirmé ici est soit lu dans le code, soit cité depuis un texte de licence public.

Avertissement

Cet article est une lecture technique du fonctionnement d'Odoo 19 et des textes de licence publiés. Ce n'est pas un avis juridique. Pour un montage contractuel engageant (revente, sous-licence, prestation encadrée), la validation par un juriste spécialisé en propriété intellectuelle reste indispensable.

1. Les dix valeurs légales de license

Beaucoup de manifestes recopient 'license': 'LGPL-3' sans savoir ce qui est accepté à côté. La réponse n'est pas dans la documentation : elle est dans la définition du champ, sur le modèle ir.module.module.

# odoo/odoo/addons/base/models/ir_module.py — Odoo 19.0
license = fields.Selection([
    ('GPL-2', 'GPL Version 2'),
    ('GPL-2 or any later version', 'GPL-2 or later version'),
    ('GPL-3', 'GPL Version 3'),
    ('GPL-3 or any later version', 'GPL-3 or later version'),
    ('AGPL-3', 'Affero GPL-3'),
    ('LGPL-3', 'LGPL Version 3'),
    ('Other OSI approved licence', 'Other OSI Approved License'),
    ('OEEL-1', 'Odoo Enterprise Edition License v1.0'),
    ('OPL-1', 'Odoo Proprietary License v1.0'),
    ('Other proprietary', 'Other Proprietary')
], string='License', default='LGPL-3', readonly=True)

Dix valeurs, et seulement dix. Trois familles s'en dégagent :

FamilleValeursCe que ça engage
Copyleft fort GPL-2, GPL-3 (et variantes « or later »), AGPL-3 Toute œuvre dérivée doit être publiée sous la même licence. L'AGPL étend l'obligation à l'usage réseau : un utilisateur qui se connecte à l'instance peut réclamer les sources.
Copyleft faible LGPL-3, Other OSI approved licence Les modifications du code couvert restent ouvertes, mais du code propriétaire peut s'articuler autour sans être contaminé. C'est la licence d'Odoo Community.
Propriétaire OPL-1, OEEL-1, Other proprietary Usage conditionné à un achat ou à un abonnement. Redistribution interdite. OEEL-1 est réservée à Odoo S.A. et à l'écosystème Enterprise.

Le socle est posé par le fichier LICENSE à la racine du dépôt, qui ne laisse aucune ambiguïté :

« Odoo is published under the GNU LESSER GENERAL PUBLIC LICENSE, Version 3 (LGPLv3), as included below. »

Fichier LICENSE, dépôt odoo/odoo, branche 19.0

Ce choix n'a rien d'anecdotique : jusqu'à la version 8, Odoo était publié sous AGPL. Le passage à la LGPLv3 a été annoncé le 5 février 2015, pour la version 9, avec un objectif assumé — « ouvrir un véritable App store » et permettre à des éditeurs tiers de publier des modules propriétaires par-dessus le socle. Toute l'économie actuelle des modules payants découle de cette décision.

2. Ce que la clé fait vraiment — et ce qu'elle ne fait pas

Trois modules jetables suffisent à cartographier le comportement réel. Chacun ne contient qu'un __manifest__.py et un __init__.py vide.

# content/blog/modules/oski_licence_default/__manifest__.py
{
    'name': 'OdooSkills — Licence par défaut',
    'version': '19.0.1.0.0',
    'author': 'OdooSkills',
    'depends': ['base'],
    'installable': True,
    # aucune clé 'license' : c'est tout l'intérêt du test
}

Les deux autres sont identiques, avec respectivement 'license': 'OPL-1' — une valeur de la liste — et 'license': 'MIT' — une valeur qui n'y figure pas. Installation groupée :

venv/bin/python odoo/odoo-bin \
  --addons-path=odoo/addons,content/blog/modules \
  -d vs19_blog_licence \
  -i oski_licence_default,oski_licence_opl,oski_licence_mit \
  --stop-after-init --log-level=warn

Résultat 1 — la clé absente est tolérée, avec un avertissement

2026-07-26 05:15:23,986 WARNING vs19_blog_licence odoo.modules.module:
  Missing `license` key in manifest for 'oski_licence_default', defaulting to LGPL-3

Le comportement est codé en clair dans le chargeur de manifeste :

# odoo/odoo/modules/module.py — fonction _load_manifest()
if not manifest.get('license'):
    manifest['license'] = 'LGPL-3'
    _logger.warning("Missing `license` key in manifest for %r, defaulting to LGPL-3", module)

Autrement dit : un module sans clé license est publié en LGPL-3. Pas « sans licence », pas « propriétaire par défaut ». Un module interne qu'on distribue ensuite à un client, sans avoir jamais écrit la ligne, est un module LGPL-3 — avec les obligations qui vont avec. C'est probablement la conséquence la plus coûteuse d'un oubli de trois mots.

Résultat 2 — une valeur hors liste s'installe sans broncher

Le module déclaré MIT s'installe. Aucune erreur, aucun avertissement. En base :

SELECT name, license, state FROM ir_module_module WHERE name LIKE 'oski_licence%';

         name         | license |   state
----------------------+---------+-----------
 oski_licence_default | LGPL-3  | installed
 oski_licence_mit     | MIT     | installed
 oski_licence_opl     | OPL-1   | installed

Surprenant, puisque license est un Selection, et que l'ORM refuse normalement toute valeur inconnue :

>>> module.write({'license': 'WTFPL'})
ValueError: Wrong value for ir.module.module.license: 'WTFPL'

L'explication tient en une ligne du code d'amorçage : à la création de la base, les modules ne sont pas insérés par l'ORM, mais en SQL brut.

# odoo/odoo/modules/db.py — initialize()
cr.execute('INSERT INTO ir_module_module \
        (author, website, name, shortdesc, description, \
            category_id, auto_install, state, web, license, application, icon, sequence, summary) \
        VALUES (%s, %s, %s, %s, %s, %s, %s, %s, %s, %s, %s, %s, %s, %s) RETURNING id', (...))

La colonne correspondante est déclarée license character varying(32) dans base/data/base_data.sql, sans contrainte CHECK. Toute chaîne de moins de 33 caractères passe. La validation du Selection ne s'applique qu'aux écritures par l'ORM, c'est-à-dire plus tard — ce qui produit un piège différé.

⚠️ Le piège : une valeur exotique casse l'interface, pas l'installation

  • À l'installation initiale : rien. Le module fonctionne.
  • Dans la liste des applications, le module est regroupé sous un libellé vide : le client web ne sait pas traduire une valeur absente de la sélection.
  • Sur la fiche du module, l'onglet Information — celui qui contient justement le champ License — ne s'affiche plus, et une boîte « Oops! » peut apparaître.
  • Si la valeur du manifeste change ensuite (par exemple MIT → WTFPL), « Mettre à jour la liste des applications » passe par l'ORM et échoue franchement : ValueError: Wrong value for ir.module.module.license.

Résultat 3 — le champ est invisible hors mode développeur

Détail qui explique pourquoi si peu de développeurs vérifient la licence d'un module tiers : dans la vue formulaire standard, le champ est enfermé dans un bloc réservé au mode développeur.

<!-- odoo/odoo/addons/base/views/ir_module_views.xml -->
<notebook groups="base.group_no_one">
    <page string="Information" name="information">
        <group>
            <group>
                <field name="category_id" options="{'no_open': True, 'no_create': True}"/>
                <field name="name" />
                <field name="license"/>
                <field name="installed_version"/>
            </group>
        </group>
    </page>

Sans mode développeur, aucun onglet. La licence d'un module installé sur une instance de production n'est donc jamais sous les yeux de l'administrateur fonctionnel. Le seul contrôle fiable reste la requête SQL, ou le regroupement montré plus haut.

3. Odoo 19 Community n'est pas 100 % LGPL

Affirmation répandue : « tout le code de la Community est en LGPL-3 ». Un recensement direct des manifestes du dépôt, branche 19.0, dit autre chose.

import ast, pathlib, collections

c = collections.Counter()
for root in ("odoo/addons", "odoo/odoo/addons"):
    for m in pathlib.Path(root).glob("*/__manifest__.py"):
        d = ast.literal_eval(m.read_text())
        c[d.get("license", "<absente>")] += 1

print(sum(c.values()), "manifestes")   # 622 manifestes
for k, v in c.most_common():
    print(" ", k, v)                   #   LGPL-3 620
                                       #   OEEL-1 2

Deux modules du dépôt Community sont déclarés sous licence Enterprise : certificate et project_hr_skills. Leur manifeste ne laisse aucun doute :

# odoo/addons/project_hr_skills/__manifest__.py
{
    'name': 'Project - Skills',
    'category': 'Services/Project',
    'depends': ['project', 'hr_skills'],
    'auto_install': True,
    'author': 'Odoo S.A.',
    'license': 'OEEL-1',
}

La conséquence pratique compte : un module qui déclare depends sur l'un des deux hérite d'une dépendance propriétaire, même sur une instance qui se croit intégralement libre.

Et sur une base installée, le compte grimpe encore. Le regroupement par licence affiche 23 modules OEEL-1, pas 2. La différence vient d'un fichier de données :

SELECT license, to_buy, count(*) FROM ir_module_module GROUP BY 1,2 ORDER BY 1;

 license | to_buy | count
---------+--------+-------
 LGPL-3  | f      |   649
 OEEL-1  | t      |    21     <-- fiches vitrines, aucun code
 OEEL-1  | f      |     2     <-- certificate, project_hr_skills
 OPL-1   | f      |     1

Les 21 enregistrements marqués to_buy = True sont créés par base/data/ir_module_module.xml. Ce sont les vitrines Enterprise — accountant, helpdesk, sign, web_studio, planning… — qui affichent un bouton Upgrade dans la liste des applications. Aucun code ne les accompagne dans le dépôt Community. Un audit de licences qui compte les lignes de ir_module_module sans filtrer to_buy produit donc un faux positif à répétition.

À retenir pour un audit

La bonne requête d'audit exclut les vitrines et se concentre sur ce qui est réellement installé :

SELECT license, count(*) FROM ir_module_module
WHERE state = 'installed' AND to_buy = false
GROUP BY license ORDER BY 2 DESC;

4. La règle de contamination

C'est la seule question qui compte au moment de choisir. Elle ne porte pas sur le socle Odoo — la LGPL-3 autorise explicitement à construire du propriétaire par-dessus — mais sur les modules tiers dont on dépend.

La documentation officielle formule l'autorisation dans les deux sens :

« You may develop Odoo modules based on the Software and distribute them under the license of your choice, provided that it is compatible with the terms of the Odoo Enterprise Edition License (For example: LGPL, MIT, or proprietary licenses similar to this one). »

Documentation Odoo 19, page Licenses

Le texte de l'Odoo Proprietary License v1.0 dit la même chose côté modules payants : dépendre d'un module OPL-1 n'oblige pas à publier son propre code sous OPL-1, à condition de ne pas en recopier le source.

« You may develop Odoo modules that use the Software as a library (typically by depending on it, importing it and using its resources), but without copying any source code or material from the Software. […] It is forbidden to publish, distribute, sublicense, or sell copies of the Software. »

Odoo Proprietary License v1.0

Reste le cas qui piège tout le monde : l'AGPL-3. La majorité du catalogue historique de l'OCA est publiée sous cette licence, et la position de l'association est explicite — dépendre d'un module AGPL-3 interdit de garder son propre module fermé.

Votre module est… …dépend d'un module LGPL-3 …dépend d'un module AGPL-3 …dépend d'un module OPL-1 / OEEL-1
LGPL-3 ✅ compatible ❌ le module doit passer en AGPL-3 ✅ compatible
AGPL-3 ✅ compatible ✅ compatible ❌ incompatible en pratique
OPL-1 / propriétaire ✅ compatible ❌ interdit ✅ compatible

Le sens de la contamination se lit dans une seule direction : l'AGPL remonte, la LGPL non. Un module propriétaire ne peut pas dépendre d'un module AGPL-3, alors qu'il peut sans difficulté dépendre du socle Community ou d'un module Enterprise.

⚠️ Les trois façons de se contaminer sans s'en apercevoir

  • Par depends — le cas évident. Une ligne ajoutée six mois plus tard dans le manifeste suffit à changer la licence obligatoire du module.
  • Par copier-coller — reprendre trente lignes d'une méthode d'un module AGPL-3 crée une œuvre dérivée, que le manifeste le déclare ou non.
  • Par héritage de vue ou de modèle — étendre un modèle défini par un module AGPL-3 place le code dans une zone que les positions publiées ne tranchent pas uniformément. En cas de distribution commerciale, c'est le point à faire arbitrer.

Un mot sur l'AGPL et l'hébergement, souvent mal compris : c'est la seule licence de la liste qui considère qu'un utilisateur connecté à travers le réseau est un destinataire du logiciel. Héberger une instance qui contient un module AGPL-3 et la mettre à disposition de tiers crée donc une obligation de fourniture des sources — y compris des modifications maison. C'est exactement l'effet recherché par l'OCA : garantir qu'un client puisse quitter son prestataire avec l'intégralité du code de son instance.

5. L'arbre de décision

Trois questions, dans cet ordre. La première qui donne une réponse ferme clôt le débat.

Q1. Le module dépend-il d'un module AGPL-3 (catalogue OCA, la plupart du temps) ? ├─ OUI → AGPL-3. Pas de choix. Vendre reste possible, garder fermé non. └─ NON → passer à Q2 Q2. Le module va-t-il être distribué hors de l'organisation qui l'a écrit ? ├─ NON (usage strictement interne) │ → LGPL-3. Aucune obligation de publication tant qu'il n'y a pas │ de distribution. Choix par défaut, cohérent avec le socle. └─ OUI → passer à Q3 Q3. Le code doit-il rester fermé, avec un droit d'usage vendu ? ├─ NON → LGPL-3 pour la compatibilité maximale, │ AGPL-3 pour interdire la reprise fermée par un concurrent. └─ OUI → OPL-1, licence prévue pour ce cas et reconnue par l'écosystème. Other proprietary uniquement si un contrat maison existe déjà.

OEEL-1 n'apparaît jamais dans cet arbre : cette valeur est celle d'Odoo S.A. pour son propre code Enterprise. La déclarer sur un module tiers n'a aucun sens et laisse entendre une origine que le module n'a pas.

6. Trois idées reçues à corriger

« Un module payant doit obligatoirement être en OPL-1 »

Faux. Les règles publiées à destination des éditeurs sont ouvertes : « any license can be applied to your app, as long as it respects the licenses of its dependencies, libraries or other derivative works ». OPL-1 est recommandée pour un module propriétaire, LGPL-3 pour un module ouvert — mais rien n'interdit de vendre un module publié en LGPL-3. Ce qui est réellement contraint, c'est la compatibilité avec les dépendances, pas le modèle économique.

« Déclarer Other proprietary protège mon code »

La clé license est une déclaration, pas un mécanisme technique. Le serveur ne l'utilise ni pour restreindre l'installation, ni pour brider une fonctionnalité, ni pour vérifier quoi que ce soit à l'exécution — les expériences de la section 2 le montrent. Elle a une valeur juridique et documentaire ; elle n'a aucune valeur de protection.

« Mon module interne n'a pas de licence, donc il est fermé »

Faux, et c'est le piège le plus courant. Sans clé license, Odoo écrit LGPL-3 dans la base et le journalise. Un module qui n'a jamais quitté l'entreprise reste sans conséquence tant qu'il n'est pas distribué — mais le jour où il est livré à un client, il l'est sous LGPL-3, faute d'avoir écrit trois mots dans le manifeste.

Récapitulatif

  • 10 valeurs possibles, codées en dur dans le Selection de ir.module.module. Toute autre chaîne est acceptée au premier chargement, puis casse l'interface.
  • Clé absente = LGPL-3, avec un avertissement dans le journal. Ce n'est pas neutre au moment de distribuer.
  • La Community n'est pas intégralement LGPL : deux modules du dépôt sont déclarés OEEL-1, et 21 fiches vitrines to_buy polluent tout audit naïf.
  • Seule l'AGPL-3 remonte. Dépendre d'un module AGPL-3 impose l'AGPL-3 ; dépendre du socle LGPL-3 ou d'un module OPL-1 n'impose rien.
  • Le champ est masqué hors mode développeur. Pour auditer une instance, passer par SQL ou par un regroupement sur la liste des applications.

Prochaine étape : le manifeste ne contient pas que license. L'article 2/3 démonte chaque clé de __manifest__.py en Odoo 19 et mesure ce qu'elle déclenche réellement au chargement.
