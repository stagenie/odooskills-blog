Créer son premier module Odoo 20 : le modèle Livre

Un modèle, ses droits d'accès, sa liste, son formulaire et son menu : c'est tout ce qu'il faut pour qu'une nouvelle application apparaisse dans Odoo 20. On part du squelette généré par odoo-bin scaffold, et on désamorce au passage les deux pièges qui font échouer la première installation en version 20.

~16 minutes de lecture · niveau débutant · parcours Fondamentaux

Ce que tu vas apprendre

Le squelette

Ce que génère odoo-bin scaffold, ce qu'il faut garder, et le manifeste qui rend le module visible.

Le modèle

Une classe Python, six champs, une contrainte d'unicité et un nom affiché calculé.

L'écran

Les droits dans ir.access.csv, une vue liste, une vue formulaire, une action et un menu.

Prérequis

  • Un poste de développement Odoo 20 qui démarre, monté dans l'article précédent : sources en branche 20.0, environnement Python dans .venv, fichier odoo.conf et dossier custom-addons/.
  • Une base de données vide — ici biblio — et le serveur joignable sur http://localhost:8069.
  • Un éditeur. Les chemins de cet article sont ceux du terminal ; PyCharm exécute exactement les mêmes commandes.

Ce que tu vas construire

Un module Odoo est un dossier. Dedans, un fichier déclare ce qu'il est (__manifest__.py), du Python déclare des modèles, et du XML déclare des vues. Odoo lit le tout au chargement, crée la table en base, puis dessine l'écran.

Le module s'appellera biblio, et son premier modèle library.book. Les articles suivants lui ajouteront les exemplaires, les adhérents et les emprunts.

1. Le squelette

Odoo sait générer un module vide. Depuis ~/odoo20 :

.venv/bin/python odoo/odoo-bin scaffold biblio custom-addons

Le dossier custom-addons/biblio/ apparaît :

biblio/
├── __init__.py
├── __manifest__.py
├── controllers/
│   ├── __init__.py
│   └── controllers.py
├── demo/
│   └── demo.xml
├── models/
│   ├── __init__.py
│   └── models.py
├── security/
│   └── ir.model.access.csv
└── views/
    ├── templates.xml
    └── views.xml

Presque tout y est commenté : le squelette ne fait rien tant qu'on n'a pas écrit dedans. Trois éléments ne serviront pas dans cet article — les contrôleurs HTTP, les données de démonstration et les gabarits de site web. On les retire pour garder un module lisible :

cd custom-addons/biblio
rm -rf controllers demo views/templates.xml views/views.xml models/models.py

Le fichier de sécurité du squelette est périmé

Le générateur d'Odoo 20 produit encore security/ir.model.access.csv. Ce modèle n'existe plus en version 20. On le supprime tout de suite, l'étape 4 le remplace :

rm security/ir.model.access.csv

2. Le manifeste

__manifest__.py est la carte d'identité du module : c'est le seul fichier qu'Odoo lit avant de décider s'il peut être installé. Remplace son contenu par :

{
    'name': "Bibliothèque",
    'summary': "Gérer les livres d'une bibliothèque",
    'description': """
Premier module de la série « Développer avec Odoo 20 ».
Un modèle Livre, ses droits d'accès, sa liste, son formulaire et son menu.
    """,
    'author': "OdooSkills",
    'website': "https://odooskills.com",
    'category': 'Services',
    'version': '20.0.1.0.0',
    'license': 'LGPL-3',
    'depends': ['base'],
    'data': [
        'security/ir.access.csv',
        'views/library_book_views.xml',
    ],
    'application': True,
}
CléCe qu'elle décide
versionLa série d'Odoo visée, puis le numéro du module. Voir l'encadré ci-dessous : c'est la clé qui fait disparaître un module.
licenseSans elle, Odoo journalise un avertissement et retient LGPL-3 d'office. Autant l'écrire.
dependsLes modules chargés avant celui-ci. base suffit tant qu'on n'utilise rien d'autre.
dataLes fichiers XML et CSV chargés à l'installation, dans cet ordre : les droits avant les vues.
applicationTrue affiche le module comme une application à part entière, pas comme un simple complément.

Le piège n°1 : un module en version 19 devient invisible

Odoo 20 vérifie que la version du manifeste appartient bien à sa série. Un module repris d'une instance Odoo 19, avec 'version': '19.0.1.0.0', est mis de côté au chargement :

WARNING biblio odoo.modules.module: The module biblio has an incompatible version, setting installable=False

Aucune erreur, aucun écran rouge : le module n'apparaît simplement pas dans la liste des applications. C'est la première chose à vérifier quand un module reste introuvable.

La règle exacte : une version à deux ou trois nombres (1.0, 1.0.0) est automatiquement préfixée par 20.0. et passe. Une version à quatre ou cinq nombres est prise telle quelle et doit commencer par 20.0.. En clair : écris 20.0.1.0.0 et tu n'y penses plus.

Il reste à brancher les dossiers entre eux. À la racine du module :

# biblio/__init__.py
from . import models
# biblio/models/__init__.py
from . import library_book

3. Le modèle library.book

Un modèle est une classe Python. Odoo en déduit une table PostgreSQL, ses colonnes, ses clés étrangères et ses index — on n'écrit aucun SQL. Crée models/library_book.py :

from odoo import api, fields, models


class LibraryBook(models.Model):
    _name = 'library.book'
    _description = "Livre"
    _order = 'title'

    title = fields.Char(string="Titre", required=True)
    author_id = fields.Many2one('res.partner', string="Auteur")
    isbn = fields.Char(string="ISBN", size=13)
    publication_date = fields.Date(string="Date de parution")
    page_count = fields.Integer(string="Nombre de pages")
    summary = fields.Text(string="Résumé")
    active = fields.Boolean(string="Actif", default=True)
ÉlémentRôle
_nameL'identifiant technique du modèle. Le point devient un tiret bas dans la table : library_book.
_descriptionObligatoire en pratique : sans elle, chaque chargement journalise The model library.book has no _description.
_orderL'ordre de tri par défaut des listes. Ici, par titre.
Many2oneUn lien vers un autre modèle. res.partner est le carnet d'adresses d'Odoo : l'auteur y sera une fiche.
activeNom réservé : Odoo masque d'office les enregistrements dont active est faux, au lieu de les supprimer.

Les champs ne sont pas des types Python : ce sont des descripteurs qui portent aussi le libellé affiché, l'obligation de saisie et le comportement en base. Le catalogue complet des types de modèles et les attributs de classe disponibles sont détaillés dans deux articles dédiés.

4. Les droits d'accès

Un modèle sans droits est un modèle que personne ne peut lire — pas même l'administrateur. C'est la cause la plus fréquente d'une première installation qui « ne montre rien ». Crée security/ir.access.csv :

id,name,model_id,group_id/id,operation,domain
access_library_book_user,library.book utilisateur,library.book,base.group_user,crud,
ColonneValeur
idUn identifiant unique dans le module. Le nom est libre.
model_idLe nom pointé du modèle, tel quel : library.book.
group_id/idLe groupe qui reçoit le droit. base.group_user = tout utilisateur interne.
operationLes lettres de crud : create, read, update, delete. Ici, les quatre.
domainFiltre facultatif, pour restreindre la ligne à certains enregistrements. Vide ici.

Ce qui change depuis Odoo 19

Les modèles ir.model.access et ir.rule ont disparu. Un seul modèle les remplace, ir.access, et un seul fichier : security/ir.access.csv. Les quatre colonnes perm_read, perm_write, perm_create et perm_unlink sont remplacées par la colonne operation, et le domain d'une règle d'enregistrement se pose désormais sur la même ligne que le droit.

Conséquence pratique : un fichier de sécurité copié d'un module Odoo 19 fait échouer l'installation. C'est le premier fichier à reprendre quand on porte un module vers la version 20.

Le piège n°2 : une ligne sans groupe n'est pas une permission

En version 20, une ligne dont la colonne group_id/id est vide devient une restriction appliquée à tout le monde, et non plus un droit ouvert à tous. Pour donner un accès général, il faut nommer un groupe — base.group_user pour les utilisateurs internes, base.group_everyone pour vraiment tout le monde.

5. La liste, le formulaire et le menu

Trois choses à déclarer : comment afficher les données (les vues), quoi ouvrir (l'action), et où cliquer (le menu). Le tout dans views/library_book_views.xml :

<?xml version="1.0" encoding="utf-8"?>
<odoo>

    <record id="library_book_view_list" model="ir.ui.view">
        <field name="name">library.book.list</field>
        <field name="model">library.book</field>
        <field name="arch" type="xml">
            <list string="Livres">
                <field name="title"/>
                <field name="author_id"/>
                <field name="isbn"/>
                <field name="publication_date"/>
                <field name="page_count"/>
            </list>
        </field>
    </record>

    <record id="library_book_view_form" model="ir.ui.view">
        <field name="name">library.book.form</field>
        <field name="model">library.book</field>
        <field name="arch" type="xml">
            <form string="Livre">
                <sheet>
                    <div class="oe_title">
                        <label for="title"/>
                        <h1>
                            <field name="title" placeholder="Titre du livre"/>
                        </h1>
                    </div>
                    <group>
                        <group>
                            <field name="author_id"/>
                            <field name="isbn"/>
                        </group>
                        <group>
                            <field name="publication_date"/>
                            <field name="page_count"/>
                            <field name="active"/>
                        </group>
                    </group>
                    <group string="Résumé">
                        <field name="summary" nolabel="1" placeholder="Quelques lignes sur le livre…"/>
                    </group>
                </sheet>
            </form>
        </field>
    </record>

    <record id="library_book_action" model="ir.actions.act_window">
        <field name="name">Livres</field>
        <field name="res_model">library.book</field>
        <field name="view_mode">list,form</field>
        <field name="help" type="html">
            <p class="o_view_nocontent_smiling_face">Enregistrer un premier livre</p>
            <p>Le catalogue de la bibliothèque est encore vide.</p>
        </field>
    </record>

    <menuitem id="library_menu_root" name="Bibliothèque" sequence="10"/>
    <menuitem id="library_menu_book" name="Livres" parent="library_menu_root"
              action="library_book_action" sequence="10"/>

</odoo>

Deux points méritent l'attention :

  • La balise de la vue tabulaire s'écrit <list>. Avec l'ancienne balise <tree>, le module ne se charge pas du tout : Invalid view type: 'tree', et le registre échoue.
  • Un <menuitem> sans parent crée une entrée de premier niveau ; les suivants s'y accrochent par leur identifiant.

Le bloc help est le message affiché quand la liste est vide — un détail qui distingue un module fini d'un module en chantier. Les vues liste, formulaire et recherche ont leur article dédié, widgets compris.

6. Installer et regarder

Retour à la racine ~/odoo20. Le module s'installe avec l'option -i :

.venv/bin/python odoo/odoo-bin -c odoo.conf -d biblio -i biblio --stop-after-init

Dans le journal, la ligne qui compte :

INFO biblio odoo.modules.loading: Loading module biblio INFO biblio odoo.registry: module biblio: creating or updating database tables

Relance le serveur, ouvre http://localhost:8069, puis les Applications. Le module y figure avec son nom, son résumé et son icône par défaut :

Un nouveau menu Bibliothèque est apparu dans la barre du haut. Son entrée Livres ouvre la vue liste :

Un clic sur une ligne ouvre le formulaire, avec le titre en grand et les champs répartis en deux colonnes :

Le module ne s'installe pas ?

Trois causes, dans l'ordre de fréquence : la version du manifeste n'est pas en 20.0.x (le module n'apparaît alors nulle part) ; un fichier listé dans data n'existe pas ou est mal orthographié ; le fichier de sécurité est resté au format de la version 19. Dans les trois cas, la réponse est dans le journal du serveur, pas dans le navigateur.

7. Deux finitions qui changent tout

7.1 Interdire deux fois le même ISBN

Un ISBN désigne une édition et une seule. Une contrainte au niveau de la base l'impose, quel que soit le chemin d'écriture — interface, import ou appel distant. Ajoute dans la classe :

    _isbn_unique = models.Constraint(
        'UNIQUE(isbn)',
        "Un ISBN ne peut désigner qu'un seul livre.",
    )

Puis mets le module à jour avec -u :

.venv/bin/python odoo/odoo-bin -c odoo.conf -d biblio -u biblio --stop-after-init

Odoo crée la contrainte PostgreSQL et retient le message. À la saisie d'un doublon, l'enregistrement est refusé et le message s'affiche :

On peut vérifier le résultat côté base : la contrainte porte le nom de la table suivi de celui de l'attribut.

library_book_isbn_unique | UNIQUE (isbn)

Ce qui change depuis Odoo 19

L'ancienne liste _sql_constraints = [(...)] n'est plus utilisée. Chaque contrainte devient un attribut de classe construit avec models.Constraint, dont le nom commence par un tiret bas. Les contraintes Python décorées par @api.constrains, elles, ne changent pas — l'article sur les contraintes et champs calculés détaille quand choisir l'une ou l'autre.

7.2 Un nom affiché parlant

Partout où un livre est référencé — fil d'Ariane, liste déroulante, champ relationnel — Odoo affiche son nom affiché. Par défaut, c'est le champ name ; ce modèle n'en a pas, il a un title. On le calcule :

    @api.depends('title', 'author_id')
    def _compute_display_name(self):
        for book in self:
            if book.author_id:
                book.display_name = f"{book.title} — {book.author_id.name}"
            else:
                book.display_name = book.title

Après une nouvelle mise à jour du module, le fil d'Ariane du formulaire affiche Développement Odoo : le guide technique — OdooSkills au lieu d'un identifiant. Le décorateur @api.depends indique à Odoo quels champs recalculer le nom : sans lui, l'affichage se figerait à la première lecture.

Pense-bête des commandes

Toutes se lancent depuis ~/odoo20.

# Générer un squelette de module
.venv/bin/python odoo/odoo-bin scaffold nom_du_module custom-addons

# Installer un module pour la première fois
.venv/bin/python odoo/odoo-bin -c odoo.conf -d biblio -i biblio --stop-after-init

# Mettre à jour un module après modification du Python ou du XML
.venv/bin/python odoo/odoo-bin -c odoo.conf -d biblio -u biblio --stop-after-init

# Démarrer le serveur et travailler dans le navigateur
.venv/bin/python odoo/odoo-bin -c odoo.conf -d biblio

Avec dev_mode = reload,xml dans odoo.conf, une modification de fichier Python redémarre le serveur toute seule. L'ajout d'un champ ou d'un fichier de données, lui, demande toujours un -u.

Récapitulatif

  • Un module utile tient en quatre fichiers : manifeste, modèle Python, droits d'accès, vues XML.
  • 'version': '20.0.1.0.0' — une version d'une autre série rend le module invisible, avec un simple avertissement dans le journal.
  • Les droits vivent dans security/ir.access.csv, modèle ir.access ; ir.model.access et ir.rule n'existent plus.
  • Une ligne de droits sans groupe est une restriction pour tous, pas une permission générale.
  • La vue tabulaire s'écrit <list>, et l'ordre des fichiers dans data compte : les droits avant les vues.
  • Les contraintes SQL se déclarent avec models.Constraint, en attribut de classe.
  • -i installe, -u met à jour ; le journal du serveur dit toujours pourquoi ça a échoué.

La suite de la série ajoute les exemplaires au module Bibliothèque, et avec eux la première relation un-à-plusieurs entre deux modèles.
