Traduire un module en Odoo 20 : le .pot, le .po et les champs traduits

Le module Bibliothèque parle français. On le fait parler arabe : messages Python rendus traduisibles avec self.env._(), fichier .pot exporté, ar.po chargé, noms de genres traduits dans la base. En chemin, trois pièges qui ne lèvent aucune erreur, et la raison pour laquelle l'anglais, lui, ne se traduit pas.

~13 minutes de lecture · niveau intermédiaire · parcours Framework & ORM

Ce que tu vas apprendre

Rendre traduisible

Ce qu'Odoo traduit seul, et les messages Python qu'il faut passer par self.env._().

Exporter, charger

odoo-bin i18n, le .pot, le .po et --i18n-overwrite.

Traduire les données

translate=True, la colonne jsonb et ce qu'elle change aux contraintes.

Prérequis

  • Le module biblio des articles précédents, jusqu'à l'onglet Emprunts sur le contact ; ses libellés sont écrits en français.
  • Un utilisateur de l'accueil (groupe créé dans l'article sur les droits d'accès), qu'on passera en arabe.
  • Le serveur Odoo 20 joignable sur http://localhost:8069, base biblio, installée en français.

1. Ce qui se traduit, et dans quelle langue on part

Odoo range chaque champ traduisible dans une colonne jsonb, une clé par langue. La clé en_US est la langue source : c'est le texte tel qu'il est écrit dans le module, quelle que soit sa langue réelle. Le menu « Livres » du module, relu en base :

{'en_US': 'Livres'}

Le module est écrit en français, donc la clé en_US contient du français. Un utilisateur français ne trouve pas de clé fr_FR et retombe sur la source : il lit « Livres ». Traduire, c'est ajouter d'autres clés à côté de celle-ci.

Une bonne partie du module est traduisible sans rien écrire : Odoo sait extraire les libellés des champs (string=), les valeurs de Selection, les noms de modèles, de menus et d'actions, les textes des vues, les messages de models.Constraint, le sujet et le corps d'un mail.template. Le reste, ce sont les chaînes écrites en Python : un raise UserError("…") reste tel quel tant qu'on ne le signale pas.

2. Les messages Python : self.env._()

Le module lève quatre messages d'erreur et nomme deux fenêtres en Python. Un premier export du .pot (point 3) montre qu'aucun n'y figure : ni « Cet emprunt est déjà clos. », ni « Le nombre de jours doit être positif. ». Pour qu'un message soit extrait puis traduit, on l'enveloppe dans self.env._() :

# models/library_loan.py
    def action_return(self):
        for loan in self:
            if loan.state == 'returned':
                raise ValidationError(self.env._("Cet emprunt est déjà clos."))
            ...

# la contrainte sur l'exemplaire déjà emprunté
                raise ValidationError(self.env._(
                    "L'exemplaire %(exemplaire)s est déjà emprunté.",
                    exemplaire=loan.copy_id.name,
                ))

Deux règles tiennent dans cet exemple. La valeur variable passe en argument nommé, jamais dans la chaîne : le traducteur reçoit L'exemplaire %(exemplaire)s est déjà emprunté., déplace %(exemplaire)s où sa langue le veut, et Odoo remplit ensuite. Et la chaîne est un littéral : l'ancien code du module écrivait f"L'exemplaire {loan.copy_id.name} est déjà emprunté.", que l'extracteur ne sait pas lire.

Piège : la f-string disparaît du .pot sans prévenir

Essai fait : deux méthodes ajoutées le temps d'un export, l'une avec self.env._(f"… {self.days} jours"), l'autre avec self.env._("Piege concat " + "suite"). Le .pot contient la seconde (« Piege concat suite », les littéraux sont recollés) et pas la première. Aucun message dans le journal. Le texte reste affiché, simplement jamais traduit.

from odoo import _ existe toujours en Odoo 20 et fait la même chose ; self.env._() a l'avantage de prendre la langue de l'environnement qu'on lui donne. Les deux devinent le module en remontant la pile d'appel. Conséquence pratique : un env._("Cet emprunt est déjà clos.") tapé dans odoo-bin shell ne traduit rien, puisque l'appelant n'est pas le module. Pour vérifier une traduction, on appelle la vraie méthode :

ar_001 ValidationError هذه الإعارة مغلقة مسبقًا.
fr_FR  ValidationError Cet emprunt est déjà clos.
shell  Cet emprunt est déjà clos.

3. Exporter le modèle de traduction (.pot)

Le .pot est la liste de toutes les chaînes traduisibles du module, sans traduction. La commande i18n d'odoo-bin le produit à partir d'une base où le module est installé ; sans -o, elle l'écrit directement dans le dossier i18n/ du module :

.venv/bin/python odoo/odoo-bin i18n export -c odoo.conf -d biblio biblio
# → biblio/i18n/biblio.pot

Avant d'envelopper les messages Python, le fichier compte 231 entrées ; après, 237 : les quatre erreurs et les deux titres de fenêtre. Chaque entrée dit d'où vient la chaîne :

#. module: biblio
#. odoo-python
#: code:addons/biblio/models/library_loan.py:0
msgid "Cet emprunt est déjà clos."
msgstr ""

#. module: biblio
#: model:ir.model.fields.selection,name:biblio.selection__library_loan__state__ongoing
#: model_terms:ir.ui.view,arch_db:biblio.library_loan_view_search
msgid "En cours"
msgstr ""

Le .pot contient aussi des libellés anglais : Created by, Followers, Activities… Ce sont les champs que les emprunts reçoivent de mail.thread et que l'adhérent reçoit du contact. Ils ne sont pas à nous ; on les laisse vides.

On régénère le .pot à chaque chaîne ajoutée. Ce n'est pas une formalité : au chargement, Odoo ne garde du .po que les entrées dont la source figure dans le .pot voisin, et jette les autres sans rien dire.

4. Ajouter l'arabe : ar.po

La langue doit d'abord exister dans la base. La même commande l'installe ; le code ar désigne l'arabe générique, ar_001, qui s'écrit de droite à gauche :

.venv/bin/python odoo/odoo-bin i18n loadlang -c odoo.conf -d biblio -l ar

Le fichier de traduction est une copie du .pot dont on remplit les msgstr, nommée d'après la langue : i18n/ar.po. Les placeholders restent intacts :

"Language: ar\n"

#. module: biblio
#. odoo-python
#: code:addons/biblio/models/library_loan.py:0
msgid "Cet emprunt est déjà clos."
msgstr "هذه الإعارة مغلقة مسبقًا."

#. module: biblio
#. odoo-python
#: code:addons/biblio/models/library_member.py:0
#: code:addons/biblio/models/res_partner.py:0
msgid "Emprunts de %(nom)s"
msgstr "إعارات %(nom)s"

Notre ar.po traduit les 96 chaînes propres au module et omet les libellés anglais hérités. Il est lu à la mise à jour du module, pour chaque langue installée :

.venv/bin/python odoo/odoo-bin -c odoo.conf -d biblio -u biblio --stop-after-init
module biblio: loading translation file …/biblio/i18n/ar.po for language ar_001
module biblio: no translation for language fr_FR

La seconde ligne est normale : il n'y a pas de fr.po, le français est la source. En base, le menu a gagné une clé :

{'en_US': 'Livres', 'ar_001': 'الكتب'}

On passe l'utilisateur de l'accueil en arabe (ses préférences, ou le champ lang de sa fiche). Toute l'interface bascule de droite à gauche : menus, colonnes, états, dates.

Les messages enveloppés au point 2 suivent. Dans l'assistant « Prolonger », un nombre de jours à zéro donne :

Le courriel de relance aussi : son champ lang vaut {{ object.member_id.partner_id.lang }}, donc le sujet prend la langue de l'adhérent. Rendu pour le même emprunt, avant et après avoir passé l'adhérent en arabe :

fr_FR   Retard : Administrer un serveur Odoo
ar_001  تأخير: Administrer un serveur Odoo

Le corps du courriel est traduisible lui aussi, d'un seul bloc ; notre ar.po ne le traduit pas, il part donc en français.

5. Corriger une traduction déjà chargée

Un traducteur corrige « الكتب » en « كتب المكتبة » dans ar.po. Un simple -u biblio ne change rien : Odoo ne remplace pas une traduction qui existe déjà en base. Il faut le demander :

.venv/bin/python odoo/odoo-bin -c odoo.conf -d biblio -u biblio --i18n-overwrite --stop-after-init
après -u                   {'en_US': 'Livres', 'ar_001': 'الكتب'}
après -u --i18n-overwrite  {'en_US': 'Livres', 'ar_001': 'كتب المكتبة'}

Les noms de genres traduits au point suivant, qui sont des données et non des chaînes du module, ont traversé tous ces --i18n-overwrite sans bouger.

6. Traduire les données : translate=True

Les .po traduisent ce qu'écrit le développeur. Les noms de genres sont saisis par le bibliothécaire : pour qu'ils aient une version arabe, c'est le champ qui doit être traduisible.

# models/library_genre.py
    name = fields.Char(string="Nom", required=True, translate=True)

À la mise à jour, la colonne change de type sans message dans le journal : elle passe de character varying à jsonb, et chaque valeur existante devient la clé source.

avant  TYPE character varying   (8, 'Python')
après  TYPE jsonb               (8, {'en_US': 'Python'})

Le chemin inverse existe aussi : retirer translate=True reconvertit la colonne en ne gardant que la clé en_US. Les traductions saisies sont alors perdues.

À l'écran, le champ gagne un bouton de langue (« FR ») qui ouvre le dialogue de traduction, une ligne par langue installée :

Piège : traduire en arabe peut effacer le français

Dans une base installée en français seul, l'anglais n'est pas une langue active. Essai : on ouvre le genre « Python », on tape « بايثون » sur la ligne arabe, on enregistre. Le navigateur n'envoie que ce qui a changé :

/web/translations/save_translation_for_field
  "changes": {"ar_001": "بايثون"}

et le serveur, faute d'anglais actif, recopie la première valeur reçue dans la clé source :

{'en_US': 'بايثون', 'ar_001': 'بايثون'}

Il n'y a pas de clé fr_FR : les utilisateurs français lisent désormais le genre en arabe. La même chose arrive en Python, avec genre.update_field_translations('name', {'ar_001': 'بايثون'}) ou un write fait en lang='ar_001'.

Le remède essayé : activer l'anglais (odoo-bin i18n loadlang … -l en). Même saisie, même requête, et cette fois la source reste en place : {'en_US': 'Python', 'ar_001': 'بايثون'}. En Python, on peut aussi passer la valeur française avec l'arabe : {'fr_FR': 'Python', 'ar_001': 'بايثون'}.

7. L'unicité d'un champ traduit

Le genre porte depuis l'article sur le Many2many une contrainte UNIQUE(name). Sur une colonne jsonb, PostgreSQL compare l'objet entier. Or un genre créé par un utilisateur français est enregistré avec deux clés :

(8,  {'en_US': 'Python'})
(15, {'en_US': 'Python', 'fr_FR': 'Python'})

Les deux objets diffèrent, la contrainte laisse passer le doublon, sans erreur. On la remplace par un index unique sur la seule clé source :

    _name_uniq_index = models.UniqueIndex(
        "((name->>'en_US'))",
        "Ce genre existe déjà.",
    )

Après -u biblio, le journal annonce la suppression de l'ancienne contrainte (« Deleting …@ir.model.constraint (biblio.constraint_library_genre_name_unique) ») et le second « Python » est refusé : UniqueViolation … "library_genre_name_uniq_index".

Piège : garder le même nom d'attribut

Premier essai, avec _name_unique = models.UniqueIndex(…) au lieu d'une nouvelle clé : la mise à jour passe, mais l'ancienne contrainte UNIQUE(name) reste en base sous ce nom et le doublon est toujours accepté. Au renommage suivant, -u échoue : DependentObjectsStillExist: cannot drop index library_genre_name_unique because constraint library_genre_name_unique on table library_genre requires it. Une contrainte qui change de nature change de nom.

8. Et l'anglais ?

L'article précédent promettait des libellés français « aussi en anglais ». Essai fait avec un i18n/en.po complet, et il échoue sur trois points.

  • Le fichier est lu, et il remplace la source. Le journal affiche « loading translation file …/en.po for language en_US », et le menu devient {'en_US': 'Books'}. Sans clé fr_FR, les utilisateurs français lisent « Books ». Il faut ajouter un fr.po dont chaque msgstr recopie son msgid, pour recréer le français à côté.
  • Les messages Python restent en français. En en_US, self.env._() rend la chaîne source sans consulter le module : « Cet emprunt est déjà clos. » s'affiche tel quel pour un utilisateur anglais.
  • Les états perdent leurs traductions. Avec en.po présent, un -u biblio --i18n-overwrite ramène les libellés de Selection à {'en_US': 'En cours'} : l'arabe « جارية » disparaît. Sans en.po, la même commande les laisse intacts.

C'est la raison de la convention d'Odoo : les chaînes d'un module s'écrivent en anglais, et chaque autre langue, français compris, arrive par un .po. Cette série écrit les siennes en français pour rester lisible ; un module destiné à être distribué suivrait la convention. Le en.po et le fr.po ont été retirés du module.

Venant de la 19 : le dialogue de traduction passe par une nouvelle route

La commande odoo-bin i18n (export, import, loadlang) est identique à celle de la 19, tout comme --i18n-overwrite et self.env._(). Ce qui a changé, c'est l'enregistrement d'une traduction. En 19, le dialogue appelait update_field_translations, qui fusionnait en SQL l'ancienne valeur et la nouvelle : la clé en_US existante était conservée. En 20, il appelle /web/translations/save_translation_for_field, et update_field_translations passe par l'écriture ordinaire du champ. Quand l'anglais n'est pas actif, la source est réécrite avec la langue traduite (point 6). Une base française migrée de 19 est concernée : activer l'anglais avant de laisser traduire.

Récapitulatif

  • La clé en_US contient la langue source du module, ici le français.
  • Vues, champs, menus, états et courriels s'extraient seuls ; les chaînes Python passent par self.env._().
  • Le .pot se régénère à chaque nouvelle chaîne ; le .po se charge à la mise à jour, et --i18n-overwrite remplace ce qui existe.
  • translate=True convertit la colonne en jsonb : une contrainte UNIQUE classique n'y protège plus rien.
  • Sans anglais actif, traduire en une langue réécrit la source.

Le module s'affiche maintenant en français et en arabe, et chaque étape a été vérifiée à l'écran ou en base. Il est temps que ces vérifications tournent seules : prochaine étape de la série, les tests automatisés.
