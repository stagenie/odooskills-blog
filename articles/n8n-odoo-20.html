n8n et Odoo 20 : un flux complet par JSON-2

Une demande de devis arrive dans n8n : il lit l'article dans Odoo, retrouve ou crée le client, crée le devis et répond avec son numéro. Quand la commande est confirmée, Odoo prévient n8n, qui écrit une note dans le fil. Un workflow Odoo n8n en trois flux, une clé API, aucune ligne de module, exécutés ici avec n8n 2.45 et Odoo 20 Community.

~12 minutes de lecture · niveau intermédiaire · parcours Intégrations

Ce que tu vas apprendre

Lire

Le nœud Odoo de n8n avec le credential « Odoo API (API Key) » : il appelle /json/2, et son champ Database Name ne doit pas rester vide.

Créer

Le nœud HTTP Request avec le même credential, pour appeler n'importe quelle méthode : find_or_create, un create avec ses lignes, le context.

Réagir

Une règle d'automatisation Odoo qui appelle un Webhook n8n quand la commande est confirmée, et n8n qui répond dans le fil de la commande.

Prérequis

  • Odoo 20 Community avec Ventes et sa base de démonstration. Pour la partie 5, le module Automatisations (base_automation), qui n'est pas installé d'office.
  • Une instance n8n auto-hébergée. L'article a été exécuté avec n8n 2.45.7. Installé par npm, ce paquet exige Node.js 24 ou plus, et n8n signale au démarrage que l'installation hors conteneur est dépréciée : l'image Docker officielle est la voie qu'il recommande.
  • Les bases de l'API : XML-RPC est déprécié : passer à l'API JSON-2 d'Odoo 20, et pour le sens Odoo → outil, Webhooks en Odoo 20.

n8n parle à Odoo de deux façons. Dans un sens, n8n appelle l'API JSON-2 (POST /json/2/<modèle>/<méthode>, une clé API dans l'en-tête Authorization) pour lire et écrire. Dans l'autre, Odoo appelle un nœud Webhook de n8n quand un événement se produit. Le fil conducteur : une demande de devis venue d'un formulaire, puis la confirmation de la commande.

1. Côté Odoo : un utilisateur technique et sa clé API

n8n agira dans Odoo avec les droits du propriétaire de la clé. Une clé d'administrateur marche, mais tout ce que fait n8n est alors permis et signé « administrateur ». Mieux vaut un utilisateur interne dédié (ici « Intégration n8n »), avec seulement les droits du flux :

  • Ventes : Utilisateur : tous les documents, pour créer les devis et écrire dans leur fil ;
  • Contact : Création, pour créer un client inconnu.

Sans ce second droit, l'appel qui crée le client répond 403 (essayé), et le message d'Odoo dit précisément ce qui manque :

HTTP 403 {"name": "odoo.exceptions.AccessError", "message": "You are not allowed to create 'Contact' (res.partner) records.\n\nThis operation is allowed for the following groups:\n\t- Sales / Administrator\n\t- Contact / Creation\n …"}

Le message est en anglais : l'appel n'envoyait pas de context avec une langue (on y revient à l'étape 4).

Créer la clé

Une clé API se crée par son propriétaire. Connecté en « Intégration n8n », ouvrir le menu utilisateur › Mes préférences › onglet Sécurité › Clés API, donner une description (n8n), choisir la durée, puis copier la clé affichée. Elle ne sera plus jamais montrée. En Odoo 20, une clé a toujours la portée rpc, la seule acceptée par /json/2.

La durée dépend du compte. Pour un utilisateur interne qui n'est pas administrateur, l'assistant propose seulement 1 jour ou 1 mois (1 mois par défaut). 1 an et Jamais ne sont proposés qu'à un administrateur. Le plafond vient du champ « Durée maximale en jours des clés API » des groupes de l'utilisateur (90 jours pour le rôle Utilisateur sur la base de test). Une clé créée par programme pour cet utilisateur sans date d'expiration est refusée : « La clé API doit avoir une date d'expiration ». Conséquence pratique : le flux n8n tombera en 401 à l'échéance. Il faut noter la date et renouveler la clé avant (nouvelle clé, mise à jour du credential, suppression de l'ancienne).

2. Côté n8n : le credential « Odoo API (API Key) »

Dans n8n 2.45, le nœud Odoo (version 2) propose deux authentifications. API Key (Recommended) utilise le credential (fiche d'authentification enregistrée dans n8n) Odoo API (API Key), qui appelle /json/2 avec l'en-tête Authorization: bearer <clé>. Username & Password est l'ancienne voie, par /jsonrpc. Pour Odoo 20, c'est la première qui convient. Trois champs à remplir :

ChampValeurRemarque
Site URLhttp://localhost:8069L'adresse d'Odoo vue depuis la machine n8n
Database Namele nom exact de la baseÀ remplir même avec une seule base (encadré ci-dessous)
API Keyla clé copiée à l'étape 1Masquée une fois enregistrée

Au test, n8n appelle res.partner/search_read avec limit: 1 : une réponse 200 prouve à la fois l'adresse, la base et la clé.

Database Name vide : « NOT FOUND », même sur un serveur à une seule base

Le champ est marqué facultatif, avec l'aide « Leave blank to auto-detect from the Site URL ». Laissé vide, n8n n'omet pas la base : il envoie l'en-tête X-Odoo-Database déduit de l'URL : le premier mot du nom d'hôte (localhost pour http://localhost:8069, odoo pour https://odoo.exemple.fr ; le test du credential, lui, garde le port : localhost:8069). Odoo cherche alors une base de ce nom et répond 404. Le test du credential affiche NOT FOUND, alors que le même appel curl sans en-tête passe. Ce comportement est conçu pour Odoo Online, où le sous-domaine est le nom de la base. En auto-hébergé, il faut saisir toujours le nom exact.

3. Lire : le nœud Odoo

Le premier workflow, « Demande de devis → Odoo 20 », démarre par un nœud Webhook (méthode POST, chemin demande-devis). Il reçoit le JSON d'un formulaire : {"nom", "email", "reference", "quantite"}. Il enchaîne ensuite quatre nœuds :

« Lire l'article » est un nœud Odoo. Le nœud propose quatre ressources toutes prêtes : Contact, Opportunity (qui demande l'application CRM), Activity et Custom Resource, c'est-à-dire n'importe quel modèle. Pour chacune, cinq opérations : Create, Delete, Get, Get Many, Update. Réglages utilisés :

ParamètreValeur
Resource / Custom ResourceCustom Resource, modèle product.product (mode By Name)
OperationGet Many, Limit 1
Filtersdefault_code Equal {{ $json.body.reference }}
Options › Fields to Includeid,name,list_price

Le nœud en tire un appel search_read. Ce corps, rejoué en curl, donne :

POST /json/2/product.product/search_read
{"domain": [["default_code", "=", "E-COM07"]], "fields": ["id", "name", "list_price"], "offset": 0, "limit": 1}

→ 200  [{"id": 20, "name": "Large Cabinet", "list_price": 320.0}]

n8n fait de chaque enregistrement un item, l'unité de donnée qui circule entre les nœuds : ici un seul, que les nœuds suivants lisent par $('Lire l\'article').item.json.id. Le champ Value du filtre est un texte : avec In / Not In, il est découpé aux virgules et les nombres sont convertis. Pour un domaine plus riche (|, any, dates relatives), le nœud HTTP Request de l'étape suivante.

4. Créer : le nœud HTTP Request, avec le même credential

Le nœud Odoo ne sait ni appeler une méthode métier, ni écrire des lignes de commande. Pour cela, on utilise le nœud HTTP Request, en lui donnant le credential Odoo : Authentication Predefined Credential Type, Credential Type Odoo API (API Key). L'en-tête Authorization est ajouté tout seul. En revanche, X-Odoo-Database ne l'est pas : sur un serveur à plusieurs bases, il faut l'ajouter dans Send Headers. Réglages communs aux deux nœuds HTTP : Method POST, Send Body, Body Content Type JSON, Specify Body Using JSON. Une option est à activer sur les deux nœuds : Options › Response › Include Response Headers and Status (sans elle, $json.body[0] n'existe pas).

Retrouver ou créer le client

Odoo a déjà la méthode qu'il faut : res.partner.find_or_create(email) cherche un contact par son adresse et le crée s'il n'existe pas, avec le nom tiré de « Nom <adresse> ». URL http://localhost:8069/json/2/res.partner/find_or_create, corps :

{{ JSON.stringify({ email: $('Demande de devis').item.json.body.nom + ' <' + $('Demande de devis').item.json.body.email + '>' }) }}

Odoo répond [52], la liste des ids. Sans l'option « Include Response Headers and Status », n8n fait de cette liste un item par élément, et un nombre seul n'est pas un objet : lors d'un premier essai, l'expression suivante valait undefined, et n8n a refusé le corps (« The value in the "JSON Body" field is not valid JSON »). Avec l'option, la sortie devient {"body": [52], "statusCode": 200, …} et l'id se lit par $json.body[0].

Créer le devis, lignes comprises

URL …/json/2/sale.order/create, corps :

{{ JSON.stringify({
  vals_list: [{
    partner_id: $json.body[0],
    order_line: [[0, 0, {
      product_id: $('Lire l\'article').item.json.id,
      product_uom_qty: $('Demande de devis').item.json.body.quantite
    }]]
  }],
  context: { lang: 'fr_FR' }
}) }}
  • create prend une liste de dictionnaires (vals_list) et rend une liste d'ids, même pour un seul devis.
  • Une ligne se crée par la commande [0, 0, {…}] dans le champ order_line, comme en Python. Le prix et les taxes viennent de l'article.
  • context est une clé du corps JSON-2, à côté des arguments. Sans lui, Odoo travaille en anglais. Le premier devis créé sans context portait dans son fil « Sales Order créé ». Avec lang: 'fr_FR', on lit « Commande client créé ».
  • Le vendeur du devis est l'utilisateur de la clé (user_id = « Intégration n8n »). Passez user_id dans les valeurs si un vendeur doit être désigné.

Relire et répondre

Dernier nœud : un nœud Odoo, Custom Resource sale.order, opération Get, Record By ID {{ $json.body[0] }}, Fields to Include name,partner_id,amount_total,state. Le Webhook de départ est réglé sur Respond When Last Node Finishes : l'appelant reçoit ce dernier résultat. Le workflow est publié (bouton Publish), ce qui active son URL de production /webhook/demande-devis. Trois appels :

Le second appel réutilise le contact 52 au lieu d'en créer un doublon : c'est find_or_create qui compare les adresses. Les montants sont TTC (3 × 320 + 15 % de taxe = 1 104).

Zéro élément : le flux s'arrête, l'exécution est « Succeeded », l'appelant reçoit un 500

Avec une référence inconnue, « Lire l'article » rend 0 item. n8n n'exécute pas les nœuds suivants, ce qui est normal, et rien n'est créé dans Odoo. L'exécution est notée Succeeded (celle du haut de la liste, 122 ms), donc aucune alerte d'erreur ne part. Mais le Webhook, qui attend le dernier nœud, répond 500 {"code":0,"message":"No item to return was found"}. Si l'appelant compte sur une réponse, ce cas est à traiter dans le flux : un nœud If après la lecture, et un nœud Respond to Webhook pour chaque issue.

5. Réagir : Odoo prévient n8n quand la commande est confirmée

Ici, ce n'est plus n8n qui interroge Odoo : c'est Odoo qui pousse l'événement. Le montage côté Odoo est celui de l'article Webhooks en Odoo 20, dans Paramètres › Technique › Automatisation › Règles d'automatisation (mode développeur) :

  • règle « Commande confirmée → n8n », modèle Commande client, déclencheur Le statut est défini sur, valeur Commande client. Sans valeur, le filtre est vide et la règle part à chaque écriture de l'état, création comprise : un premier essai ainsi réglé a prévenu n8n pour un simple devis ;
  • action « Prévenir n8n » de type Envoyer une notification webhook, URL http://localhost:5678/webhook/commande-confirmee, champs Référence commande, Client, Total et Vendeur.

Le second workflow, « Commande confirmée (Odoo 20) → note », a deux nœuds. Le premier est un Webhook (POST, chemin commande-confirmee) réglé sur Respond Immediately. Odoo n'attend la réponse qu'une seconde et ne réessaie jamais : le webhook doit répondre tout de suite, avant de travailler. Voici ce qu'Odoo a envoyé à la confirmation de S00029 :

{"_action": "Prévenir n8n(#490)", "_id": 29, "_model": "sale.order", "amount_total": 1104,
 "id": 29, "name": "S00029", "partner_id": 52, "user_id": 9}

Les relations arrivent en ids seuls (partner_id: 52), sans libellé. Le second nœud est un HTTP Request avec le credential Odoo, URL …/json/2/sale.order/message_post, corps :

{{ JSON.stringify({
  ids: [$json.body._id],
  body: 'n8n a reçu la commande ' + $json.body.name + ' : préparation lancée.',
  message_type: 'comment',
  subtype_xmlid: 'mail.mt_note',
  context: { lang: 'fr_FR' }
}) }}

Une méthode d'enregistrement s'appelle avec ids dans le corps. Odoo rend l'id du message créé. Contrôle : le devis S00029 est confirmé dans Odoo, avec le bouton Confirmer.

Deux points de réglage. D'abord, n8n a deux URL par webhook. /webhook-test/… ne répond que pendant une écoute lancée depuis l'éditeur ; sinon, c'est 404 The requested webhook "commande-confirmee" is not registered. Odoo doit viser /webhook/…, celle du workflow publié. Ensuite, l'action webhook d'Odoo n'envoie que l'en-tête Content-Type, sans aucun moyen d'authentification. Le chemin du webhook n8n doit donc avoir une valeur longue et impossible à deviner (commande-confirmee n'est qu'un exemple lisible ; en production, plutôt commande-confirmee-7f3c…). Côté n8n, l'id reçu sert ensuite à agir sur une seule commande.

Venant de la 19, ou d'un ancien flux n8n

L'ancien credential Odoo API (identifiant + mot de passe ou clé) passe par /jsonrpc. Il fonctionne encore sur Odoo 20 : son test a répondu « Authentication successful! ». Mais Odoo écrit un avertissement de dépréciation à chaque appel, et la route doit disparaître en Odoo 22 ; n8n l'annonce aussi dans le formulaire. L'API JSON-2 existait déjà en 19. La différence en 20 : la route exige une clé de portée rpc. Une vieille clé 19 sans portée reçoit un 401 (voir Réécrire un script XML-RPC en JSON-2). Côté règle d'automatisation, rien ne change.

À retenir

  • Une clé API de portée rpc, portée par un utilisateur interne dédié, avec les seuls droits du flux. Pour un compte non administrateur, l'assistant propose au plus un mois : son renouvellement est à prévoir.
  • Credential n8n Odoo API (API Key) : il appelle /json/2. Le champ Database Name est à remplir avec le nom exact de la base, sinon NOT FOUND.
  • Le nœud Odoo couvre la lecture et le CRUD simple. Pour une méthode (find_or_create, message_post, action_confirm…) ou des lignes [0, 0, {…}], c'est le nœud HTTP Request avec le même credential, l'option « Include Response Headers and Status » et un context pour la langue.
  • Un nœud qui rend 0 item arrête le flux sans erreur. Si un appelant attend la réponse, ce cas est à traiter.
  • Pour réagir, une règle d'automatisation Odoo « Le statut est défini sur » appelle l'URL de production du Webhook n8n. Ce webhook répond aussitôt (Odoo attend une seconde, sans nouvel essai), puis n8n écrit dans Odoo par JSON-2.
