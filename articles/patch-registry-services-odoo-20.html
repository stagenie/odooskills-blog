Patch, registres et services : étendre le JS d'Odoo 20 sans le casser

Un module qui retient les derniers enregistrements ouverts et les propose dans la barre du haut. Pour y arriver, trois outils du client web : un service maison, un patch() du formulaire natif et deux registres. Avec cinq tests Hoot, et ce qui se passe quand on s'y prend mal.

~13 minutes de lecture · niveau intermédiaire · parcours Web et interface

Ce que tu vas apprendre

Partager

Un service écrit à la manière d'Odoo 20 : une classe Plugin, ses dépendances, son état, et le pont qui le rend accessible par useService.

Modifier

patch() sur un composant natif, l'appel à super, l'ordre des patchs et leur retrait.

Brancher

Les registres systray et user_menuitems, et l'écart avec la 19 qui ne lève aucune erreur (show ignoré).

Prérequis

  • Une base Odoo 20 Community. Le module ne dépend que de web.
  • Connaître un composant OWL 3 : useProps, proxy, gabarit en this. (voir le badge de retard, un widget OWL 3).
  • Savoir installer un module et ouvrir le client en ?debug=1.

Un composant OWL sait afficher un écran. Mais beaucoup de besoins ne demandent pas d'écran nouveau : ajouter une icône dans la barre du haut, une entrée dans le menu de l'utilisateur, un comportement à toutes les vues formulaire. Pour cela, le client web d'Odoo offre trois outils :

  • un service porte l'état ou le comportement partagé par plusieurs composants ;
  • un registre branche ton code là où le client web l'a prévu : on ajoute une clé, sans toucher au code d'Odoo. C'est toujours le premier choix ;
  • un patch modifie une classe existante quand rien n'est prévu, et doit le faire sans casser ce qu'elle faisait.

L'exemple les réunit. À chaque ouverture d'un formulaire, le formulaire patché signale l'enregistrement au service. Le service garde les huit derniers, par utilisateur. Une icône du systray les liste, et une entrée du menu utilisateur vide la liste.

Le module tient en huit fichiers :

oski_owl_recents/

├── __manifest__.py                   # dépend de web, déclare les assets
├── static/src/

1. Le service : une classe Plugin

Un service est un objet unique, créé au démarrage du client web et partagé par tous les composants. En Odoo 20, on l'écrit comme une classe qui étend Plugin (fourni par OWL 3), puis on l'ajoute à la ressource services du cœur :

import { Plugin, proxy, usePlugin } from "@odoo/owl";
import { browser } from "@web/core/browser/browser";
import { registry } from "@web/core/registry";
import { services } from "@web/core/services";
import { user } from "@web/core/user";
import { ActionPlugin } from "@web/webclient/actions/action_plugin";

export const MAX_RECENTS = 8;

export function storageKey() {
    return `oski_owl_recents.${user.userId}`;
}

/** Service : les derniers enregistrements ouverts en formulaire, par utilisateur. */
export class RecentsPlugin extends Plugin {
    // dépendance : un autre service, déclaré comme un champ
    action = usePlugin(ActionPlugin);
    // état partagé par tous les composants qui utilisent le service
    items = proxy([]);

    setup() {
        try {
            this.items.push(...(JSON.parse(browser.localStorage.getItem(storageKey())) || []));
        } catch {
            // valeur illisible : on repart d'une liste vide
        }
    }

    visit({ resModel, resId, displayName }) {
        const index = this.items.findIndex((i) => i.resModel === resModel && i.resId === resId);
        if (index >= 0) {
            this.items.splice(index, 1);
        }
        this.items.unshift({ resModel, resId, displayName });
        this.items.splice(MAX_RECENTS);
        this.save();
    }

    open(item) {
        return this.action.doAction({
            type: "ir.actions.act_window",
            res_model: item.resModel,
            res_id: item.resId,
            views: [[false, "form"]],
        });
    }

    clear() {
        this.items.splice(0);
        this.save();
    }

    save() {
        browser.localStorage.setItem(storageKey(), JSON.stringify(this.items));
    }
}

// 1. le service lui-même : démarré par le client web avec les autres
services.add(RecentsPlugin);

// 2. un pont facultatif, pour le code qui appelle encore useService("oski_recents")
registry.category("services").add("oski_recents", {
    start() {
        return usePlugin(RecentsPlugin);
    },
});

Les points à retenir :

  • Les dépendances sont des champs. action = usePlugin(ActionPlugin) demande le gestionnaire d'actions. Le service n'a ni liste dependencies ni fonction start : OWL démarre ce dont il a besoin.
  • L'état est réactif. items est un proxy. Un composant qui lit this.recents.items dans son gabarit se redessine quand la liste change, comme pour son propre état.
  • services.add(RecentsPlugin) inscrit le service : le client web le démarre avec ceux du cœur. La ressource n'accepte que des classes Plugin (core/services.js, lignes 7 à 10).
  • Le pont registry.category("services") est facultatif. Il permet d'écrire useService("oski_recents"). Le cœur garde ce pont pour ses propres services convertis, avec la mention « temporary » (notification_plugin.js, action_plugin.js). Un test le vérifie plus bas : il rend la même instance que usePlugin(RecentsPlugin).

Venant de la 19

En 19, un service s'écrivait registry.category("services").add("nom", { dependencies: […], start(env, deps) { … } }). Cette forme démarre encore en 20 : un service d'essai déclaré ainsi a reçu notification et action, et useService l'a rendu. Le cœur la fait tourner par legacy_service_starter.js, dont l'en-tête dit « temporary - to remove when all service are converted ». Ce qui ne passe plus, c'est son contenu habituel : reactive n'est plus exporté par OWL 3 (undefined à l'import). Pour un service neuf, écris une classe Plugin.

Deux erreurs à reconnaître. useService("nom") sur un nom inconnu lève Service nom is not available (core/utils/hooks.js, ligne 160). Un Plugin oublié dans services.add et demandé par un composant lève Unknown plugin "Orphelin" (owl.js, ligne 1755) : l'identifiant d'un plugin est le nom de sa classe.

2. Le patch : compléter le formulaire natif

Aucun registre ne permet d'être prévenu qu'un formulaire vient de charger son enregistrement. Il faut donc modifier FormController, la classe qui pilote toutes les vues formulaire. On ne copie pas la classe, on la patche :

import { usePlugin } from "@odoo/owl";
import { patch } from "@web/core/utils/patch";
import { FormController } from "@web/views/form/form_controller";
import { RecentsPlugin } from "./recents_plugin";

patch(FormController.prototype, {
    setup() {
        super.setup(...arguments);
        this.recents = usePlugin(RecentsPlugin);
    },

    async onRootLoaded() {
        await super.onRootLoaded(...arguments);
        const root = this.model.root;
        if (root.resId && !this.env.inDialog) {
            this.recents.visit({
                resModel: root.resModel,
                resId: root.resId,
                displayName: this.displayName(),
            });
        }
    },
});
  • On patche le prototype. Les méthodes d'une classe vivent sur son prototype ; patcher FormController lui-même ne toucherait que ses propriétés statiques.
  • super appelle le code d'avant. patch() place l'ancienne version derrière la nouvelle (web/static/src/core/utils/patch.js), si bien que super.setup(...arguments) exécute le setup d'origine, ou celui d'un autre module qui l'aurait patché avant toi. Dans le cœur Community, mail patche déjà ce même setup.
  • On choisit le bon crochet. onRootLoaded est appelé par le modèle après chaque chargement de l'enregistrement principal, à l'ouverture comme avec les flèches de pagination (model/relational_model/relational_model.js, ligne 233). Le formulaire s'en sert déjà pour afficher le nom de l'enregistrement dans le fil d'Ariane.
  • On écarte ce qui ne doit pas compter : un enregistrement pas encore créé (pas de resId) et un formulaire ouvert dans une fenêtre (this.env.inDialog).

Oublier super casse tous les formulaires

Pour l'essai, on a mis en commentaire la ligne super.setup(...arguments). Le setup d'origine ne s'exécute plus, le formulaire n'a plus ses services, et toute fiche s'ouvre sur une fenêtre « Oups ! » : contacts, devis, articles… pas seulement ceux que le module vise.

Autre erreur fréquente : écrire la méthode en fonction fléchée, setup: () => { super.setup(); }. Le navigateur refuse le fichier ('super' keyword unexpected here) et, comme tous les fichiers JavaScript sont regroupés dans un même bundle, une erreur de syntaxe en bloque la lecture et le client web entier reste une page blanche. Écris toujours setup() { … }.

Plusieurs patchs sur la même méthode

patch() rend une fonction qui retire le patch. Le dernier test du module montre comment les patchs s'empilent, sur un objet simple :

test("patch : ordre d'application et dépatch", () => {
    const salut = {
        dire() {
            return "original";
        },
    };
    const unpatchA = patch(salut, {
        dire() {
            return `A(${super.dire()})`;
        },
    });
    const unpatchB = patch(salut, {
        dire() {
            return `B(${super.dire()})`;
        },
    });
    expect(salut.dire()).toBe("B(A(original))"); // le dernier patch appliqué s'exécute en premier

    unpatchA(); // retire A, réapplique B
    expect(salut.dire()).toBe("B(original)");
    unpatchB();
    expect(salut.dire()).toBe("original");

    expect(() => patch(salut, "mon_patch", {})).toThrow(/Second argument is not the patch name anymore/);
});
  • Le dernier patch appliqué s'exécute en premier ; chaque super descend d'un cran.
  • Retirer un patch du milieu (unpatchA()) remet l'original puis réapplique les autres patchs (patch.js, lignes 118 à 136) : B reste en place.
  • L'ancienne signature avec un nom, patch(obj, "nom", {…}), lève Patch "nom": Second argument is not the patch name anymore.

Le code de patch.js est identique en 19.0 et en 20.0 : un patch écrit en 19 se porte tel quel, à condition que ce qu'il appelle existe encore (voir la section 4).

3. Les registres : le systray et le menu utilisateur

Un registre est une liste de clés que le client web parcourt à un endroit précis. La barre du haut lit systray (la zone d'icônes à droite), le menu de l'avatar lit user_menuitems, les vues lisent fields, les actions client actions. Ajouter une clé suffit : aucun patch n'est nécessaire.

Une icône dans le systray

import { Component, usePlugin } from "@odoo/owl";
import { Dropdown } from "@web/core/dropdown/dropdown";
import { DropdownItem } from "@web/core/dropdown/dropdown_item";
import { registry } from "@web/core/registry";
import { RecentsPlugin } from "./recents_plugin";

export class RecentsSystray extends Component {
    static template = "oski_owl_recents.RecentsSystray";
    static components = { Dropdown, DropdownItem };

    recents = usePlugin(RecentsPlugin);
}

registry.category("systray").add("oski_owl_recents.systray", { Component: RecentsSystray }, { sequence: 5 });
<?xml version="1.0" encoding="UTF-8"?>
<templates xml:space="preserve">

    <t t-name="oski_owl_recents.RecentsSystray">
        <Dropdown position="'bottom-end'" menuClass="'o_recents_menu'">
            <button type="button" class="o_recents_systray o_nav_entry" title="Derniers consultés">
                <i class="oi" data-icon="history"/>
                <span t-if="this.recents.items.length" class="o_recents_count badge rounded-pill"
                      t-out="this.recents.items.length"/>
            </button>
            <t t-set-slot="content">
                <div class="dropdown-header">Derniers consultés</div>
                <t t-if="this.recents.items.length">
                    <t t-foreach="this.recents.items" t-as="item" t-key="item.resModel + ',' + item.resId">
                        <DropdownItem class="'o_recents_item'" onSelected="() => this.recents.open(item)">
                            <span t-out="item.displayName"/>
                            <small class="text-muted ms-2" t-out="item.resModel"/>
                        </DropdownItem>
                    </t>
                </t>
                <div t-else="" class="o_recents_empty dropdown-item-text text-muted">Aucun enregistrement ouvert.</div>
            </t>
        </Dropdown>
    </t>

</templates>
  • L'entrée du registre est un objet { Component }. La sequence place l'icône : la barre affiche les entrées dans l'ordre inverse de leur séquence (webclient/navbar/navbar.js), le menu de l'avatar (séquence 0) reste donc tout à droite.
  • Le composant demande le service par usePlugin(RecentsPlugin) et lit this.recents.items dans son gabarit : le compteur suit la liste sans rien de plus.
  • Le menu déroulant est le composant Dropdown du cœur : le bouton en contenu par défaut, la liste dans le slot content.

Cliquer sur une ligne appelle open() du service, qui ouvre la fiche par le gestionnaire d'actions. La liste est gardée dans le navigateur sous la clé oski_owl_recents.<id de l'utilisateur> : deux utilisateurs sur le même poste ont chacun la leur.

Une entrée dans le menu utilisateur

import { usePlugin } from "@odoo/owl";
import { registry } from "@web/core/registry";
import { RecentsPlugin } from "./recents_plugin";

export function clearRecentsItem() {
    // en Odoo 20, la fonction est appelée dans la portée du menu : les hooks y sont permis
    const recents = usePlugin(RecentsPlugin);
    return {
        type: "item",
        id: "oski_recents_clear",
        description: "Vider les derniers consultés",
        hide: !recents.items.length,
        callback: () => recents.clear(),
        sequence: 45,
    };
}

registry.category("user_menuitems").add("oski_recents_clear", clearRecentsItem);

Une entrée de user_menuitems est une fonction qui rend la description de la ligne. En Odoo 20, le menu l'appelle dans sa propre portée (this.scope.run(…), user_menu.js, ligne 34) : on peut y appeler usePlugin ou useService, comme le fait le cœur pour « Mes préférences ». En 19, elle recevait déjà env, mais était appelée hors de toute portée : les services passaient par env.services.

Les registres : un écart silencieux, une erreur à connaître

show n'est plus lu. En 19, le menu utilisateur filtrait les entrées par show() (user_menu.js 19.0, ligne 30). Ce filtre a disparu en 20 : une entrée qui renvoie show: () => false s'affiche, sans erreur. Seul hide: true la masque. Un test Hoot jetable l'a vérifié pour les deux clés.

Une clé déjà prise lève une erreur au chargement du fichier, comme en 19 : Cannot add key "oski_owl_recents.systray" in the "systray" registry: it already exists. Pour remplacer volontairement l'entrée d'un autre module, passe { force: true }. La validation des entrées par schéma, elle, n'est faite qu'en mode debug (core/registry.js, ligne 15).

4. Un import mort : le module disparaît sans bruit

Le piège le plus courant en portant une extension 19 vers 20 n'est pas dans le patch lui-même mais dans ses imports. Odoo 20 a remplacé une partie de ses services par des plugins et supprimé les fichiers correspondants : @web/webclient/actions/action_service, @web/core/orm_service, @web/core/ui/ui_service… Pour l'essai, on a ajouté à recents_plugin.js une seule ligne venue de la 19 :

import { actionService } from "@web/webclient/actions/action_service";

Le client web démarre, le formulaire s'affiche, mais l'icône du systray n'est plus là, ni l'entrée du menu. Rien à l'écran ne le signale. La console du navigateur, elle, dit tout :

The following modules are needed by other modules but have not been defined, they may not be
present in the correct asset bundle: [@web/webclient/actions/action_service]
The following modules could not be loaded because they have unmet dependencies, this is a secondary
error which is likely caused by one of the above problems: [@oski_owl_recents/form_controller_patch,
@oski_owl_recents/recents_plugin, @oski_owl_recents/recents_systray, @oski_owl_recents/user_menu_item]

Le chargeur écarte le fichier fautif et tous ceux qui l'importent : ici les quatre fichiers JavaScript du module (les trois autres importent recents_plugin.js). Seul le mode debug ajoute un bandeau rouge en bas de page, « An error occurred while loading javascript modules » (web/static/src/module_loader.js). D'où la règle : développe en ?debug=1, console ouverte.

5. Les tests Hoot

Le manifeste ajoute static/tests/ au bundle web.assets_unit_tests. Ces tests tournent dans le navigateur, contre un serveur simulé : aucune donnée de la base n'est lue.

import { beforeEach, describe, expect, test } from "@odoo/hoot";
import { queryAllTexts } from "@odoo/hoot-dom";
import { browser } from "@web/core/browser/browser";
import { registry } from "@web/core/registry";
import { patch } from "@web/core/utils/patch";
import { UserMenu } from "@web/webclient/user_menu/user_menu";
import {
    clearRegistry,
    contains,
    defineModels,
    fields,
    getService,
    makeTestApp,
    mockService,
    models,
    mountView,
    mountWithCleanup,
    serverState,
} from "@web/../tests/web_test_helpers";
import { MAX_RECENTS, RecentsPlugin } from "@oski_owl_recents/recents_plugin";
import { RecentsSystray } from "@oski_owl_recents/recents_systray";
import { clearRecentsItem } from "@oski_owl_recents/user_menu_item";

class Partner extends models.Model {
    name = fields.Char();
    _records = [
        { id: 1, name: "Azure Interior" },
        { id: 2, name: "Wood Corner" },
    ];
}
defineModels([Partner]);

describe.current.tags("desktop");

function mockDoAction() {
    mockService("action", {
        doAction(action) {
            expect.step(`${action.res_model},${action.res_id}`);
        },
    });
}

beforeEach(() => {
    serverState.userId = 7;
});

test("le service garde les derniers consultés, sans doublon, par utilisateur", async () => {
    await makeTestApp();
    const recents = getService(RecentsPlugin);
    expect(getService("oski_recents")).toBe(recents); // le pont rend la même instance

    for (let id = 1; id <= MAX_RECENTS + 2; id++) {
        recents.visit({ resModel: "partner", resId: id, displayName: `P${id}` });
    }
    recents.visit({ resModel: "partner", resId: 5, displayName: "P5" });
    expect(recents.items.length).toBe(MAX_RECENTS);
    expect(recents.items.slice(0, 3).map((i) => i.displayName)).toEqual(["P5", "P10", "P9"]);
    const stored = JSON.parse(browser.localStorage.getItem("oski_owl_recents.7"));
    expect(stored[0]).toEqual({ resModel: "partner", resId: 5, displayName: "P5" });
});

test("le formulaire patché alimente le service", async () => {
    await mountView({ type: "form", resModel: "partner", resId: 1, resIds: [1, 2] });
    const recents = getService(RecentsPlugin);
    expect(recents.items.map((i) => i.displayName)).toEqual(["Azure Interior"]);

    await contains(".o_pager_next").click();
    expect(recents.items.map((i) => i.displayName)).toEqual(["Wood Corner", "Azure Interior"]);
});

test("le systray liste les récents et rouvre l'enregistrement", async () => {
    mockDoAction();
    await mountWithCleanup(RecentsSystray);
    expect(".o_recents_count").toHaveCount(0);

    getService(RecentsPlugin).visit({ resModel: "partner", resId: 2, displayName: "Wood Corner" });
    await contains(".o_recents_systray").click();
    expect(".o_recents_count").toHaveText("1");
    expect(queryAllTexts(".o_recents_item span")).toEqual(["Wood Corner"]);

    await contains(".o_recents_item").click();
    expect.verifySteps(["partner,2"]);
});
  • getService(RecentsPlugin) rend l'instance du service démarrée pour le test ; getService("oski_recents") rend ce que le pont a démarré ; le premier test vérifie que c'est le même objet.
  • mountView monte un vrai formulaire : le patch est actif dans les tests, car le bundle de tests inclut le code du module. Le clic sur la flèche suivante recharge l'enregistrement, et le service en reçoit un second.
  • mockService("action", { doAction }) remplace l'ouverture de la fiche par une trace, vérifiée par expect.verifySteps.
  • Dans Hoot, patch est remplacé par une version qui se retire seule à la fin du test. Le test de l'ordre des patchs appelle quand même unpatchA() et unpatchB() : c'est ce qu'il vérifie.

À retenir

  • Cherche d'abord un registre. Un patch n'est utile que si le client web n'a rien prévu.
  • Un service Odoo 20 est une classe Plugin ajoutée à services ; ses dépendances sont des champs usePlugin(…).
  • Un patch se pose sur le prototype, en méthodes classiques, et appelle toujours super avec ...arguments.
  • En 20, user_menuitems ignore show : utilise hide.
  • Un import vers un fichier supprimé ne casse pas l'écran, il fait disparaître ton module. Travaille en ?debug=1, console ouverte.
