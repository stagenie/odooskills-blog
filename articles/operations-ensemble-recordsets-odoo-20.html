Union, intersection, différence de recordsets en Odoo 20

Les clients qui ont un devis, ceux qui ont une commande confirmée : lesquels sont dans les deux, lesquels sont à relancer ? Sur les recordsets, Odoo fournit les opérations d'ensemble de Python : |, &, -, +, in, <=. Ce qu'elles renvoient, l'ordre et les doublons, la nouvelle forme de union() en Odoo 20, et les recordsets vides ou fantômes.

~9 minutes de lecture · niveau débutant · parcours Framework & ORM

Ce que tu vas apprendre

Combiner

|, &, - et + : ce qui est gardé, dans quel ordre, avec ou sans doublon.

Comparer

in, <=, <, ==, et le piège de in avec plusieurs enregistrements.

Construire

union() et concat() version Odoo 20, le recordset vide, browse, exists, ensure_one.

1. Deux ensembles de clients

Un recordset est une suite d'ids d'un même modèle. Les opérations d'ensemble prennent deux recordsets du même modèle et en rendent un troisième, en mémoire, sans requête de recherche. Pour les voir à l'œuvre, deux ensembles de contacts tirés des commandes de vente :

SO = env['sale.order']
devis = SO.search([('state', 'in', ('draft', 'sent'))], order='id')
confirmees = SO.search([('state', '=', 'sale')], order='id')
a = devis.partner_id          # clients d'un devis en cours
b = confirmees.partner_id     # clients d'une commande confirmée
a.mapped('name')
b.mapped('name')
['Acme Corporation', 'Ready Mat', 'Joel Willis'] ['Gemini Furniture', 'Lumber Inc', 'Joel Willis']

devis.partner_id lu sur plusieurs commandes donne directement le recordset de leurs clients, sans doublon : a vaut res.partner(10, 12, 8), b vaut res.partner(11, 17, 8). Joel Willis (id 8) est dans les deux : il a un devis envoyé et une commande confirmée.

2. Les quatre opérateurs : |, &, -, +

a | b      # union
a & b      # intersection
a - b      # différence
b - a
a + b      # concaténation
b | a
OpérateurRésultatOrdre et doublons
a | bles enregistrements de a ou de bsans doublon, ordre de première apparition : ceux de a, puis les nouveaux de b. b | a donne les mêmes enregistrements dans un autre ordre.
a & bceux qui sont dans les deuxsans doublon, dans l'ordre de a.
a - bceux de a absents de bordre de a conservé. Ici : les clients d'un devis qui n'ont aucune commande confirmée, Acme Corporation et Ready Mat.
a + bles ids de a suivis de ceux de bdoublons gardés : Joel Willis apparaît deux fois, len(a + b) vaut 6.

Les formes augmentées existent aussi : clients |= autre, reste -= traites. Elles ne modifient pas le recordset de départ ; elles en créent un nouveau et le rangent dans la variable.

+ n'est pas l'union

Un recordset avec doublons se parcourt deux fois sur le même enregistrement : une boucle qui envoie un courriel par client en enverrait deux à Joel Willis. Pour réunir des ensembles, | ; + sert quand l'ordre et la répétition comptent (une liste de lignes à rendre telles quelles, par exemple).

En Odoo 20, ces opérateurs gardent aussi le jeu de prefetch de leurs opérandes (les ids dont Odoo lit les champs d'un coup), là où la 19 repartait des seuls ids du résultat : rien à changer dans le code, parfois une requête de moins.

3. Appartenance et sous-ensembles

P = env['res.partner']
joel = P.browse(8)
joel in a
a[:2] in a
a[:2] <= a
(a & b) <= a, a < (a | b), a <= b
a == P.browse([12, 8, 10])
'name' in a
a | env['res.users'].browse(2)
True False True (True, True, False) True True TypeError: inconsistent models in: res.partner(10, 12, 8) | res.users(2,)
  • rec in a teste un enregistrement. Avec plusieurs, la réponse est False même s'ils sont tous dans a : le test exige len(item) == 1 (__contains__, odoo/orm/models.py). Pour « tous ceux-ci sont-ils dans a ? », écrire sous_ensemble <= a.
  • <= et < : sous-ensemble et sous-ensemble strict ; >= et > dans l'autre sens. Un recordset vide est sous-ensemble de tout.
  • == compare les ensembles d'ids sans tenir compte de l'ordre : (10, 12, 8) égale (12, 8, 10).
  • Une chaîne à gauche de in teste l'existence d'un champ sur le modèle : 'name' in a.
  • Deux modèles différents : TypeError, que ce soit |, &, - ou +. Une liste d'ids à la place d'un recordset aussi (unsupported operand types) : passer par P.browse(ids).

4. union() et concat() : plusieurs recordsets d'un coup

union() fait le travail de |, concat() celui de +, mais sur autant de recordsets qu'on veut. En Odoo 20, la forme attendue est précise : on l'appelle sur le recordset vide du modèle, avec un seul itérable de recordsets (liste, tuple, générateur).

P.union([a, b])
P.concat([a, b])
P.union(o.partner_id for o in SO.search([], order='id'))
a.union(b)          # ancienne forme
P.union(a, b)       # ancienne forme
a.concat(b)         # ancienne forme
for i in range(3):
    x = a.union(b)

Le générateur de la troisième ligne est l'usage typique : réunir les clients des 24 commandes de la démo sans construire de liste intermédiaire. Résultat : cinq clients, dans l'ordre de leur première apparition.

Les anciennes formes donnent toujours le bon résultat, mais chacune émet un UserWarning qui commence par Since 20.0 : « on an empty recordset » quand l'objet de départ n'est pas vide, « with only one iterable » quand plusieurs arguments sont passés. Odoo le consigne au niveau WARNING, avec la pile d'appels. Le filtre par défaut de Python ne le montre qu'une fois par processus, quel que soit l'appelant (il est rattaché à la ligne d'Odoo qui l'émet) : la boucle qui suit, qui refait trois fois a.union(b), n'en ajoute aucun. Un avertissement vu une fois au démarrage peut donc cacher un appel exécuté des milliers de fois.

Pourquoi pas |= dans une boucle ?

Chaque | recopie le recordset accumulé : sur une longue boucle, le coût grimpe avec le carré du nombre d'éléments. union() parcourt tout en une passe (sa docstring parle de temps linéaire). Mesure sur 20 000 ids de contacts passés à browse (aucune lecture en base) :

import time
recs = [P.browse(i) for i in range(1, 20001)]

def boucle():
    total = P
    for r in recs:
        total |= r
    return total

def chrono(f):
    t = time.perf_counter()
    res = f()
    return len(res), round(time.perf_counter() - t, 3)

chrono(boucle)
chrono(lambda: P.union(recs))
(20000, 4.319) (20000, 0.002)

Plus de quatre secondes contre deux millisecondes sur la machine de test, pour le même recordset. Dès qu'on accumule dans une boucle, ranger les morceaux dans une liste et finir par P.union(morceaux).

Venant de la 19

Dans la branche 19.0 publique, union(self, *args) et concat(self, *args) prennent des recordsets en arguments séparés, sans aucun avertissement. L'idiome 20 P.union([a, b]) y échoue : la liste n'a pas d'attribut _name, d'où un TypeError: unsupported operand types. Pour un module qui doit tourner sur les deux versions, P.union(*morceaux) fonctionne partout (en 20, avec l'avertissement « only one iterable ») ; pour un module 20 seulement, P.union(morceaux).

5. Le recordset vide et la vérité d'un recordset

vide = env['res.partner']
vide, len(vide), bool(vide)
P.browse(), P.browse(False), P.browse(0)
bool(a - a), a - a == vide
if not (a & P.browse(17)):
    print("aucun client commun")
(res.partner(), 0, False) (res.partner(), res.partner(), res.partner()) (False, True) aucun client commun

env['res.partner'] est déjà un recordset : vide, du bon modèle. C'est le point de départ naturel d'une accumulation et l'objet sur lequel appeler union(). browse() sans argument, avec False ou avec 0 donne aussi un recordset vide. Un recordset est vrai s'il contient au moins un enregistrement : if not (a & c) se lit « s'ils n'ont rien en commun ». Il n'y a pas besoin de len(...) == 0.

AppelCe qu'il fait
browse(ids)Construit le recordset tel quel, doublons compris, sans requête. Un id qui n'existe pas donne un recordset non vide (bool(fantome) vaut True) ; l'erreur n'arrive qu'à la lecture d'un champ : MissingError.
browse([0]), browse([8, None])AssertionError: Invalid falsy real id : un id faux (0, None, False) dans une liste est refusé tout de suite.
exists()Une requête, et le sous-ensemble des enregistrements encore présents, dans l'ordre d'origine. À appeler sur un id venu de l'extérieur (contexte, paramètre d'URL, autre transaction).
ensure_one()Renvoie le recordset s'il contient exactement un enregistrement, sinon ValueError: Expected singleton, aussi bien pour trois que pour zéro. Il s'enchaîne : (a & b).ensure_one().name.

Un id absent dans une liste

Le cas courant : P.browse([vals.get('partner_id')]) quand la clé manque, ou une liste d'ids remplie à partir d'un Many2one vide. browse(None) ou browse(False) seuls donnent un recordset vide ; dans une liste, ces valeurs lèvent l'AssertionError. Filtrer avant : P.browse([i for i in ids if i]).

Venant de la 19

Dans la branche 19.0 publique, browse ne contrôle pas les ids : browse([0]) construit res.partner(0,) sans erreur, et le problème ne se voit que plus loin. En 20, le contrôle ajouté à browse (odoo/orm/models.py) fait échouer l'appel lui-même. Un code 19 qui passait des ids vides à browse sans dommage visible lève désormais AssertionError.

Récapitulatif

  • | et & retirent les doublons et gardent l'ordre de première apparition ; - garde l'ordre du premier opérande ; + garde tout, doublons compris.
  • in teste un seul enregistrement ; pour un sous-ensemble, <=. == ignore l'ordre.
  • En Odoo 20, union() et concat() s'appellent sur le recordset vide avec un seul itérable ; les anciennes formes marchent avec un WARNING, une seule fois par processus.
  • Accumuler par |= dans une longue boucle coûte cher ; union() sur une liste est linéaire.
  • browse ne lit rien en base et refuse en 20 un id faux dans une liste ; exists() vérifie la présence ; ensure_one() exige un enregistrement, ni zéro ni plusieurs.
